## 「项目级兜底回检」的边界（对应 `step-1.6-落盘后回检.md`）

约定 21 规定 SKILL 是单一信源、命令端不复述其规则。但 `dev-logic-architect` 有几处**规范已写、
核验脚本未提供**的地方（对外接口文档形态、B.7 第三方对接职责边界），命令端在 step-1.6 用 grep
做**兜底**——这不是复述 SKILL 规则，而是补它缺的执行力。判定标准：

- **可以兜底**：SKILL 有规范、无脚本 → 命令端 grep 兜住，并注明"SKILL 端补齐脚本后本段精简为脚本调用"。
- **不可兜底**：SKILL 有规范也有脚本（如上游引用覆盖率由「上游溯源完备性」维度内置回检）→
  命令端**只留自己能独立判定的基础格式检查**，不重写维度逻辑；SKILL QR 标记通过但实际违规，
  按 **SKILL Bug 上报**处理，绝不在命令端绕过——绕过等于让两套判定各自演进，很快就会打架。
- **别拿名字像的脚本顶替**：`check_third_party_dep_reverse.py` 是「第三方依赖反向识别」，
  与「对外职责边界核验」用途不同，不能互相代替。


## 代码侧加跑组：为什么显式接线、为什么一律 report-only

**为什么要显式接线**：SKILL 的调度表把这一组标为「需额外入参 / 需 `code_root`」并写明
「具备该入参时自行加跑」——代价是**调用方不主动传，它们就永不运行**，对应维度只剩语义判断。
本项目恰好具备这些入参，不接线等于白白丢掉几个确定性维度。

**为什么不做阻断**：它们吃的是**代码现状**而非设计产物，在「设计已改、代码还没跟上」的
规划期天然会红——那是**时序差、不是缺陷**。先按告警跑几轮、确认某项假红率确实低，
再逐个提到阻断档；**别一上来就设硬门**（SKILL 自陈「假红常驻 = 硬门被绕过」，一次也不例外）。

## SQL 版本隔离门为何必须识别两轨布局

约定 37 的 SQL 在 `docs/deployment/{version}/sql/增量|全量/` 下两层。只认 `{root}/{version}/*.sql` 扁平布局、
非递归 glob 的实现，在两轨布局下无论 root 怎么传都扫到 0 个文件并 exit 0——失效形态是「判通过」，
比报错更隐蔽。故该门（`check_sql_version_isolation.py`）按 `{version}/sql/增量|全量` 自动识别并递归扫描，
基线复制检测只比较本版与上一版的增量轨。

## 回检表为何只留「哪些等级不占退出码」、不复述码表

约定 21：命令端只做编排 + 项目级补充，**不复述 SKILL 已有规则**。发现码（U1~U4 / W1/W2 /
E1~E5 / D1 等）的**含义**属 SKILL 单一信源——上游改码即漂移，而复述过的地方不会自动跟着改。

命令端**确实需要**的只有一条编排信息：**「退出码之外还要读哪些字段」**。
因为多个上游脚本把「缺表」这类最常见的违规判成 **Important、不占退出码**——
只看 exit code 会把它当通过放行。所以回检表各行只留：
① 触发条件 ② 哪些等级不占退出码、须读 `--json` 的哪个键 ③ 处置动作。
具体码表指向 SKILL 的 `references/quality-review-checklist.md` 对应维度。


## Step 1.6~1.7.5 为什么统一派一个子 Agent

这些步骤要把 `接口设计.md` / `对外开放接口.md` / `集成对接.md` / `*事实清单.md`
读进来做 grep + 路径比对 + 级联对账。逐步内联会把多份产物文档正文塞进主上下文，
而主对话真正需要的只是「阻塞 / 不阻塞」这一个判断——产物正文与脚本 stdout
都是中间态。合并成一个子 Agent 后，产物只被读一次、回传的是紧凑结论。

用 general-purpose 而非 Explore：本步不只读，还要就地写各「⚠️ 告警」表与归一化修复。
