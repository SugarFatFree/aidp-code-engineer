#### Step 2.4.5：四个子调用的串联说明（研发自测由 /sprint-selftest 独立承载）

- 四个子命令按顺序依赖（需求 → 设计 → 研发执行计划 → 研发自测）
- 如某个命令失败，停止并报告错误
- 如用户希望跳过某步（例如已有需求文档），可单独手动调用后续命令
- 研发自测用例的生成 + 落盘核验 + 输出前硬门**全部在 `/sprint-selftest`（Step 2.4.3.5）内部完成**；/version 不直接调用 dev-manual-testcase SKILL

**★ 三步落盘自检（进入 Step 2.5 前必须执行）**：Step 2.4.1~2.4.3.5 全部跑完后，命令端在进入 Step 2.5 之前必须执行下方 bash 一次性确认 **6 类主产物**（研发需求 / 详细设计 / 研发执行计划 / 研发自测用例 / 研发自测方案 / 测试环境与账号）全部落盘（注：后 3 类由 /sprint-selftest（Step 2.4.3.5）生成，本步骤一并核验；漏产即在此拦截、绝不放行）；任一缺失则视为“上游 SKILL 偷跑/漏调用”，必须暂停并列出缺失项。

```bash
# 三步落盘自检（fresh 模式；6 类产物核验）
MISS=()
# 1. 研发需求（Step 2.4.1 产物；现行主文档 01_研发需求.md + 00_索引.md，兼容历史裸名/无前缀）
[ -f docs/requirements/{version}/研发需求/01_研发需求.md ] || \
[ -f docs/requirements/{version}/研发需求/00_索引.md ] || \
[ -f docs/requirements/{version}/研发需求/00_研发需求.md ] || \
[ -f docs/requirements/{version}/研发需求/研发需求.md ] || MISS+=("研发需求")
# 2. 详细设计（Step 2.4.2 产物，至少 1 份主文档；现行 01_/02_/03_ + 00_索引，兼容历史裸名/00_<专题>）
DESIGN_COUNT=$(ls docs/design/detail/{version}/{01_详细设计,02_数据库设计,03_接口设计,00_索引,详细设计,数据库设计,接口设计,00_详细设计,00_数据库设计,00_接口设计}.md 2>/dev/null | wc -l)  # 兼容：拆分态 01_/02_/03_+00_索引（现行）/ 单份态 00_<专题> / 历史存量并列态裸名（dev-logic-architect check_doc_split.py 识别）
DESIGN_SPLIT=$(ls docs/design/detail/{version}/0[1-9]_*.md 2>/dev/null | wc -l)
[ "$DESIGN_COUNT" -eq 0 ] && [ "$DESIGN_SPLIT" -eq 0 ] && MISS+=("详细设计")
# 3. 研发执行计划（Step 2.4.3 产物；当前规范 00_索引.md + 01_研发执行计划.md，兼容历史无前缀 / 总览）
[ -f docs/plans/{version}/00_索引.md ] || \
[ -f docs/plans/{version}/01_研发执行计划.md ] || \
[ -f docs/plans/{version}/00_研发执行计划.md ] || \
[ -f docs/plans/{version}/研发执行计划.md ] || \
[ -f docs/plans/{version}/00_研发执行计划-总览.md ] || MISS+=("研发执行计划")
# 4. 研发自测用例（Step 2.4.3.5 /sprint-selftest 产物；★ glob 容 dedup 后序号漂移：NN_*自测用例* / NN_*自测.md）
ls docs/testing/{version}/研发自测/*自测用例*.md >/dev/null 2>&1 || \
[ -f docs/testing/{version}/研发自测.md ] || \
ls docs/testing/{version}/研发自测/0[0-9]_研发自测.md >/dev/null 2>&1 || \
[ -f docs/testing/{version}/研发自测用例.md ] || MISS+=("研发自测用例")
# 5. ★ 研发自测方案（SKILL 第零步产出；当前规范方案在 01_，旧锚 00_ grandfather；导航锚 = 00_索引 由 SKILL 第八步产出）
[ -f docs/testing/{version}/研发自测/01_研发自测方案.md ] || \
ls docs/testing/{version}/研发自测/0[0-9]_研发自测方案.md >/dev/null 2>&1 || MISS+=("研发自测方案")
# 6. ★ 测试环境与账号配置文件（/sprint-selftest Step 3 产出；固定 01_测试环境与账号，★ glob 稳健定位不写死序号）
ls docs/testing/{version}/研发自测/[0-9][0-9]_测试环境与账号.md >/dev/null 2>&1 || MISS+=("测试环境与账号")

if [ ${#MISS[@]} -gt 0 ]; then
  echo "❌ Step 2.4 三步落盘自检失败：缺失 ${MISS[*]}"
  echo "   - 命令必须暂停，不得进入 Step 2.5"
  echo "   - 用户处置：检查上游 SKILL 调用日志（自测用例 / 测试方案若缺失需检查 Step 2.4.3.5 /sprint-selftest 是否被跳过），重跑对应 Step 2.4.x"
  exit 1
fi
echo "✅ Step 2.4 三步落盘自检通过：研发需求 / 详细设计 / 研发执行计划 / 研发自测用例 / 研发自测方案 / 测试环境与账号 全部就位"
```

> **判定**：6 类产物全过 → 进入 Step 2.4.5.5（补充模式回写）→ Step 2.5；任一不过 → 暂停 + 在终端清晰列出缺失项让用户接管。**禁止**使用"基本通过"、"主要齐全"等模糊措辞绕过。

**★ 文档结构（约定 15）**：四类版本规划文档目录**恒有专职导航锚 + 内容文档从 `01_` 起 + 无重号**（由 Step 2.4.4〔`planning-4.md`〕 `promote_content_main`/`dedup_prefix`/`gen_index` 维护）。**导航锚**：研发需求 `00_索引.md` + `01_研发需求.md`；设计详情 `00_索引.md` + `01_详细设计.md`·`02_数据库设计.md`·`03_接口设计.md`；研发执行计划 `00_索引.md` + `01_研发执行计划.md`（里程碑拆分态**同样用 `00_索引.md`** + `0N_M{N}`；`00_研发执行计划-总览.md` 仅识别存量、不新产）；**研发自测目录已对齐通用范式——导航锚 = `00_索引.md`**（SKILL 第八步产出）+ `01_研发自测方案.md`（方案）+ 用例总览 `02_自测用例-总览.md`·`03_<模块>.md`（分册间唯一前缀），`01_测试环境与账号.md` 是 aiauto-test 配置文件（类别 ≠ 用例分册，与 `01_研发自测方案.md` 同处 `01_`、均按名排除 dedup）；旧锚 `00_研发自测方案.md` 目录 grandfather 兼容。完整拆分阈值表见 `docs/init/02_迭代输入指导.md §10.4`。

#### Step 2.4.5.5：★ `00_索引.md` 补充登记增强（仅补充模式 B-2 执行）

补充模式下，Step 2.4.4 `gen_index` 已把本轮新增的 `NN_<业务主题>.md` 以 `类型=补充` + 生成时间登记进各目录 `00_索引.md`。本步在此基础上**给 `00_索引.md` 增补三列**（`关联输入变更` / `状态` / `取代关系`），让索引成为完整"导航中心"——**补充身份、时序、取代关系全部沉淀在 `00_索引.md`，文件名不带"补充"字眼**（约定 15）。每轮补充结束后 `00_索引.md` 应长成：

```markdown
# 00_索引

> 本目录文档索引。类型 = 主（版本规划首产）/ 补充（后续增量，靠更晚生成时间 + 本列区分）。阅读时按生成时间合并「主 + 全部补充」才是当前生效的完整需求/设计/计划/用例。

| 序号 | 文件 | 生成时间 | 类型 | 关联输入变更 | 状态 | 取代关系 |
|---|---|---|---|---|---|---|
| 03 | [03_账单明细域.md](./03_账单明细域.md) | 2026-05-15 14:30 | 补充 | [输入变更-02.md](./输入变更-02.md) | 已采纳 | 🔄 取代 02 的账单明细部分 |
| 02 | [02_优惠券域.md](./02_优惠券域.md) | 2026-05-12 10:15 | 补充 | [输入变更-01.md](./输入变更-01.md) | ⚠️ 部分被 03 取代 | — |
| 01 | [01_研发需求.md](./01_研发需求.md) | 2026-05-08 09:00 | 主 | — | 已采纳 | — |
```

> **「类型」列 = 主/补充身份的唯一裁决**：`序号` 只反映本目录续编顺序（不携带补充语义）；补充身份靠 `类型=补充` + 生成时间晚于主文档区分。**文件名一律 `NN_<业务主题>.md`、绝不带"补充"字眼**（约定 15；上游 SKILL 本就产出干净名，命令端不再回补）。
> **「取代关系」列**（由 Step 2.4.5.6 维护）：本轮补充推翻 / 修订前序某行的某部分 → 填 `🔄 取代 {被取代序号} 的 <被取代点>`；被取代行「状态」改 `⚠️ 部分被 {本轮序号} 取代`。纯增量轮两列填 `—`。

**回写算法**：
1. 读取目录 `00_索引.md`（Step 2.4.4 已生成基础表）
2. 为本轮新增行补 `关联输入变更`（指向 `输入变更-{NN}.md`）/ `状态` / `取代关系` 三列（表头缺列则先扩表头）
3. 保持按生成时间倒序（新行在上）；append-only，不改历史行正文
4. 本轮某类（如 数据库设计）实际无补充产物 → 该目录索引不动

**补充文档自身的「关联文档」表特殊化**（每份 `NN_<业务主题>.md` 头部）：

- ⬅ 上游输入：`<指向 docs/requirements/{version}/研发需求/输入变更-NN.md 的相对路径>` + 本目录 `00_索引.md`（回链）
- ↔ 同版本平行：本目录其他同轮 `NN_<业务主题>.md`（同轮其他类型补充）+ `00_索引.md`
- ⏮ 前序补充：本目录已登记的前序补充行对应文件（如有）

**到 `输入变更-NN.md` 的相对路径速查**（路径约定：版本作用域内一律相对）：

| 补充文档位置 | 相对路径 |
|------------|---------|
| `docs/requirements/{version}/研发需求/NN_<业务主题>.md` | `./输入变更-{NN}.md` |
| `docs/design/detail/{version}/NN_<业务主题>.md` | `../../../requirements/{version}/研发需求/输入变更-{NN}.md` |
| `docs/plans/{version}/NN_<业务主题>.md` | `../../requirements/{version}/研发需求/输入变更-{NN}.md` |
| `docs/testing/{version}/研发自测/NN_<业务主题>.md`（强制子目录化） | `../../../requirements/{version}/研发需求/输入变更-{NN}.md` |
| `docs/testing/{version}/正式用例/01_<模块>测试方案.md`（测试人员手动维护，如有） | `../../../requirements/{version}/研发需求/输入变更-{NN}.md` |

#### Step 2.4.5.6：★ 结论取代传播（仅补充模式 B-2；存在「结论取代」时执行）

补充模型坚持 **append-only**——前序补充文档的正文**永不删除 / 改写**（审计轨迹必须完整保全）。但当后一轮补充**推翻 / 修订**前一轮的结论（典型：第三方接口"缺失→已交付"使账单明细从 Mock 占位转真实对接；字段"待确认→已确认"；某需求"作废"；数据来源 / 接口契约变更）时，前序文档里的旧结论字面仍在、若无失效标记，读者极易被旧表述（如"本期 Mock、不实现后端"）误导。本步在**不动前序正文**的前提下，自动补"取代标记"。

**触发判定**：读 `输入变更-{NN}.md`「四、对前序结论的影响（取代判定）」表 + 本轮各 `NN_*.md` 增量文档头部「对前序的修订」段（由 4 个 SKILL `--supplement` 产物提供）：
- 两处均无「结论取代」行（全纯增量）→ **跳过本步**（维持 Step 2.4.5.5 现状，仅追加，不打横幅）。
- 任一处声明了对前序的取代 → 执行下方 a / b / c。

**a. 校验 / 兜底「对前序的修订」段**：本轮每份声明了取代的 `NN_*.md` 增量文档头部必须含「对前序的修订」段（声明：取代了哪一轮、哪些 REQ / 章节、由什么旧结论改成什么新结论）。SKILL 已产出则直接采信；**缺失但 `输入变更-{NN}.md` 四段已声明取代** → 命令端按四段表**追加**该段到补充文档头部（append-only，不动其余正文），保证传播依据齐全。

**b. 给被取代的前序增量文档打 🔄 横幅**（不删除、不改写正文）：对每条取代关系，定位被取代的前序 `{被取代轮}_*.md`（凭 `00_索引.md` 类型=补充 的行定位）：
1. **文档顶部**（标题行之后、首段之前）插入横幅行：
   ```markdown
   > 🔄 **部分内容已被 supplement-{本轮NN} 取代**：<被取代点（REQ/章节）> 现行结论见 [{本轮NN}_<业务主题>.md](./{本轮NN}_<业务主题>.md)。本文档其余内容仍有效；本段保留作审计轨迹，正文不改写。
   ```
2. **被取代的具体章节标题下**（该 REQ / 章节 H 标题的下一行）插入同样一行 `> 🔄 此处结论已被 supplement-{本轮NN} 取代，现行结论见 <链接>`。
3. 横幅**幂等**：重跑 /version 时若同位置已存在指向同一 `{本轮NN}` 的 🔄 行则不重复插入。

**c. 回写 `00_索引.md` 取代关系**（Step 2.4.5.5 表的「取代关系」/「状态」两列）：本轮新行「取代关系」填 `🔄 取代 {被取代序号} 的 <被取代点>`；被取代的前序行「状态」改 `⚠️ 部分被 {本轮序号} 取代`，让索引一眼看清哪些前序已被推翻。

**铁律**：本步只**追加**失效横幅 + 取代关系登记，**绝不删除 / 改写**任何前序增量文档正文（核心不变量）。仅作用于**本轮新触发**的取代；存量已漂移文档"改到哪标到哪"，不强制回溯。校验交 version-auditor E-07（缺横幅 / 缺清单标记 → warn）。
