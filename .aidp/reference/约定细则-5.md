### 约定 37 — **★ 版本发布双轨部署基线（全量 + 增量）**

> 技术栈中立：下文出现的 `@TableName` / `@ConfigurationProperties` / Nacos / bootstrap / 达梦 / Redis 一律为**示例**，按本项目实际 ORM、配置中心（Apollo / Consul / k8s ConfigMap / `.env` 注入）、数据库、中间件对应等价机制。

部署 Markdown 的时机、内容和备份策略统一见 `{{AIDP_HOME}}/reference/部署操作约定.md`：日常只记机器待同步引用，版本规划/正式发布集中校准。本节不把发布核验扩成每次部署的全库审计。

#### 37.1 两轨定位（先立边界，再谈产物）

| | 增量轨 | 全量轨 |
| :- | :- | :- |
| 回答的问题 | 已有上一版环境**怎么升级** | 空库 / 空配置中心**从零怎么搭** |
| 口径 | 相对上一个**已发布 tag** 的变更 | **只跟最新代码走，无历史包袱** |
| 含 ALTER / 数据迁移 | ✅ 以此为主 | ❌ 一条都不含 |
| 与"本版有无变更"的关系 | 零变更时为空（但要**显式成文**） | **无关——零变更的版本同样要产全量** |

- **⛔ 铁律一：两套绝不叠加执行**。产物索引里必须写死"选一条路"：全新部署只跑全量、升级只跑增量。同时跑会重复建表 / 重复插初始化数据。
- **⛔ 铁律二：全量的难点不在导出，在判断什么该进、什么不该进**。「代码有但库没有的表」「值重复但只有一处生效的配置」「跨环境结构漂移」「语义不同但当前同值的地址」——这些都要**代码 × 真实环境交叉核对**才判得了，把库和配置中心 dump 出来交差 = 没做本约定。

**Why 必须有全量轨**：纯增量思维下，新环境交付只能把历史增量按版本顺序重放。而实际演进中表名/结构会漂移——真实回流：某项目早期建 `ep_xxx` 小写表，中途整版重建为 `T_XXX` 前缀，历史脚本从未清理；照历史顺序执行得到的库与真实库表名全对不上，且无任何地方记录这件事。另一项目重放会建出 2 张代码已不用、物理库根本不存在的表。

#### 37.2 产物落位（★ 两轨对称同级，`sql/` 与 `配置文件/` 根下不再直放两轨产物）

```
docs/deployment/{version}/
├── README.md                     # 【固定名】「全新部署 / 升级 分别拿哪些」场景导航（+ 零变更声明）
├── sql/
│   ├── 增量/                      # ★【增量轨】开发期持续产出（原 sql/ 顶层，本约定起下沉一层）
│   │   ├── {NN}_<中文名>.sql       # 中文命名 + 两位序号前缀，01_~98_
│   │   └── 99_回滚脚本.sql         # 99_ 序号固定保留给本版回滚
│   └── 全量/                      # ★【全量轨】发布期产出
│       ├── 建表说明.md            # 【固定名】在什么库、按什么顺序执行哪些 SQL + 一行来源
│       ├── {NN}_建表-<业务域>.sql  # 按业务域分文件，不是一个大文件；建表带幂等
│       └── {NN}_初始化数据.sql     # 全新部署必需的最小数据集
├── 部署流程/                        # 与两轨无关：必要 SOP + 两列 SQL 操作表
│   ├── 部署流程.md
│   └── SQL执行台账.md
└── 配置文件/                        # ⛔ 根下不再直放任何配置产物
    ├── 增量/                       # ★【增量轨】规划/正式发布集中校准
    │   └── 配置项清单.md            # 【固定名】只讲本版改了什么：新增 / 删除 / 运行时配置文件变更
    │                               #   纯代码块 + 行内 # 注释 ≤20 字符；⛔ 无表格、无判定依据、无各环境对照
    └── 全量/                       # ★【全量轨】发布期产出
        ├── 配置说明.md             # 【固定名】必要文件路径 + 换环境必改
        ├── <引导层环境文件>          # 如 bootstrap-prod.yml，与配置中心目录【平级平铺】
        ├── nginx.conf              # 运行时部署配置文件【完整份】——具体值，密码类填示例值
        ├── docker-compose.yml      # 同上
        ├── k8s-*.yaml              # 同上
        └── <配置中心>/*.yml         # 子目录名按实际中间件命名（nacos/ apollo/…），一 dataId 一文件
```

- **说明文件只写操作信息，不重复**：版本根 `README.md` 是已有唯一入口时原地维护，全新部署/升级各选一条轨、两套不叠加。`建表说明.md` 只给目标库与必要执行顺序，已由两列 SQL 台账覆盖则只引用；`配置说明.md` 只给实际文件路径、放置位置和换环境必改项。无实际内容不造目录或子索引。
- **核查事实留既有机器记录**：baseline 的 `deployment_baseline_checks.{version}` 下按 `sql` / `配置文件` 记录 `source`（实际源实例/schema/namespace）、`read_method`（只读视图/API）、`excluded`（实际剔除项数组，无则 []）、`files`（本轨全量非 Markdown 产物的仓库版本目录相对路径 → SHA256）。`release_baseline_check.py` 对照产物哈希读取，不要求把分析、测试数字或生成过程写进运维说明；历史说明只读兼容。
- **⛔ `sql/` 根下不得再直放 `.sql`**：两轨产物一律进 `增量/` 或 `全量/`，根下只允许这两个子目录。回检 = `verify.py::check_deployment_two_track_layout`（发现根下散落 `.sql` 或 `配置项清单.md` 即 **ERROR**）。**不设双读兼容**——"两处都可能有"的歧义比一次性迁移更贵：运维照哪份跑说不清、脚本 glob 到两份会重复执行建表。存量目录由 `verify.py` 检出后按其指引手工 `git mv` 搬迁（见 37.9）。
- **★ 为什么值得付这次迁移成本**：`sql/` 顶层 `NN_*.sql` 与 `配置文件/配置项清单.md` 此前被约定 6 自动应用的 glob、`SQL执行台账` 登记、发布期重组、`verify.py` 两个检查、`/sprint-bugfix` mode-b 联动等**十余处读取端**按固定路径定位，搬家确有代价。但**「同类事物落在不同层级」本身就是设计缺陷**——增量 SQL 平铺在 `sql/` 根、全量 SQL 缩在 `sql/全量/`，打开目录的人第一反应是"这两个是一回事吗"。范式文件的读者是下游开发者与运维，**目录结构就是它最先说的那句话**；一次性迁移换永久可读，划算。
- **★ 配置增量不另起文档、只下沉一层**：本版配置变更的单一信源**仍是** `配置项清单.md`（其结构 = **3 段代码块**：①新增配置 ②删除配置 ③运行时配置文件变更；⛔ **无表格**，见 37.5-5 与生产端 `postdev-writeback-2.md`。日常由 X.7/X.8 记录机器待同步引用，规划/正式发布集中追加），只是位置从 `配置文件/` 根移到 `配置文件/增量/`。**绝不**另起 `增量/01_新增配置.md` + `02_删除配置.md` 与它并列——那是与既有清单的双写，直接违反约定 25；删除粒度等信息按 37.5-5 写进该清单内部。
- **★ 运行时部署配置文件（nginx / compose / k8s）同样走两轨，不是第三类**：`nginx.conf` / `docker-compose.yml` / `k8s-*.yaml` 与 SQL、配置中心配置**是同一个形状**——**文件本身 = 全量**（新环境从零就要这一整份），**本版对它的改动 = 增量**（典型：本版新增 WebSocket 要加 `location /ws` + `Upgrade` 头，新增 SSE 要 `proxy_buffering off` + 拉长 `proxy_read_timeout`）。
  - **全量侧**：完整文件放 `全量/`，与配置中心目录**平级平铺**（同 37.4-2 的扁平化），每项写具体值（证书路径写基线环境实际路径并注释「换环境必改」），密码类按 37.4-7 填示例值。
  - **⛔ 增量侧只写「改动片段 + 插入位置 + 生效动作」，绝不放整份文件**。**Why**：部署方现网那份通常带**环境特有的 TLS 证书路径、限流、IP 白名单、日志格式**——给他一份完整文件，他会直接覆盖，把这些静默冲掉。整份文件是"从零"的语义，升级场景给整份文件就是诱导覆盖。
  - **落点**：`增量/配置项清单.md` 的「本版运行时配置文件变更」段（**不另起文件**——本版配置侧改了什么只应有一个入口）。每条须含四要素：**改哪个文件 / 片段（代码块）/ 插在哪个 server 或 location 块内 / 生效动作**（`nginx -s reload` 还是重启容器；漏写会让运维改完不生效还以为改错了）。
  - **本版无改动 → 该段写"无"**，不省略（同 37.5-7 零变更显式成文）。

#### 37.3 全量 SQL 的判据链（不可简化为「导出一下数据库」）

1. **表清单以代码为准，不以数据库为准**。判据 = 代码里的 ORM 表映射声明（`@TableName` / `@Entity` / Model `table_name` 等），再与真实库**交叉核对**，三态分别处置：

   | 情况 | 处置 |
   | :- | :- |
   | 代码有、库也有 | ✅ 进全量 |
   | **代码有、库查无** | ❌ **不进全量**，在既有机器核对记录中写明剔除项和原因 |
   | 代码无、库有 | 不进全量（属同库其它应用的表，见第 3 点分区） |

   > 真实回流：某项目 35 个 `@TableName` 中 2 张表在研发库与演示环境的库**两侧均查无**——实体与 Mapper 仍在代码里、还有服务持有其依赖，但对应售卖形态早被别的模型取代。全量的定义是"跟最新代码走"，而最新代码在真实库上跑得通，**恰恰证明这两张表不需要**。机械按 ORM 声明建表 = 给新环境凭空造两张死表。

2. **⛔ 导出源必须是「应用实际连接的那个库」**。连接串从**应用的数据源配置**反查（配置中心 / 生效 profile 的 datasource），**不得用数据库客户端的默认连接**。
   - 真实回流 A：某项目研发库已迁库，而查询工具还连着旧库，数据差 8 倍。
   - 真实回流 B：同一实例上两个 schema 表名大量重叠但结构不完全一致，运维工具默认连其中一个、应用配置写的是另一个——取错会得到一套"看起来对、细节不对"的 DDL，**这种错在新环境跑起来之前发现不了**。
   - 产出要求：`建表说明.md` 来源行写明导出源（实例地址 + schema 名）；同实例有近似 schema 时加一句警示。

3. **按表归属分区 + 幂等**。多系统同库共享是常态，脚本内必须分区标注：
   - **A 区 自有表**：本项目是唯一 owner（判定 = 交叉比对各相关系统仓库的建表脚本，只有本项目建过）→ 全新部署必须执行；
   - **B 区 共享表**：与其它系统同库同表、DDL 权威在对方 → 独立部署时执行，与对方同库部署时可跳过。
   - 建表一律加幂等（`CREATE TABLE IF NOT EXISTS` 或等价），让 B 区重复执行无害。

4. **去掉「环境绑定物」**，使脚本可落到任意 schema / 任意表空间：
   - **去除**：schema 限定前缀（`"SCHEMA"."TABLE"` → `TABLE`；标识符不加引号，与 `dev-logic-architect` 核心原则 12 一致。导出标识符为全大写且无特殊字符时直接去引号；含小写或特殊字符的引号标识符属历史库既有写法，按 SKILL 的历史沿用登记口径保留、不静默改名；导出后跑 `flows/version/release-4.md` Step 3.3.7.9 的 `sql-identifier-case` 采集）、表空间子句（如 `STORAGE(ON "xxx", CLUSTERBTR)`）、主键索引的表空间子句（如 `USING INDEX TABLESPACE "xxx"`）；
   - **保留**：列类型与默认值、NOT NULL、主键、唯一约束、二级索引、**表注释与列注释**；
   - 索引导出**排除主键/唯一约束的附属索引**，否则重复创建报错。

5. **初始化数据 ≠ 把字典表整张导出**。判据 = 代码实际消费的字典类型（常量 / `@Value` / 前端请求的 dictType）。真实回流：某项目字典表 561 条，与本应用相关的只有 3 类，其余属同库另一应用。逐条标注「必需 / 可选（可自愈）」。

6. **声明基础数据边界**：明确写出哪些数据本脚本**不含**、由谁初始化（商品主数据 / 展示位内容 / 租户数据等），避免"执行完脚本页面还是空的"时无处追责。

7. **跨环境结构核对是必做项，不是加分项**。用同一方法导出**所有可达环境**逐表比对，差异留既有机器核对记录；仅影响操作的补救命令进指引。
   - **⚠️ 差异 ≠ 缺陷，必须实测验证再下结论**。真实回流：某项目 33 张表中 6 张有差异——一张演示环境的库缺 2 列而代码实体有对应字段（**疑似漏执行历史增量的真问题**）、一张演示环境的库多一列（属同库另一应用的扩展列，不进全量）、一张列名大小写不同（**实测该库标识符大小写不敏感、运行时等价，不是缺陷**）。把正常现象报成 bug 会消耗团队信任。

8. **历史脚本显式作废**：全量 SQL 头部写明「历史增量脚本自本文件起仅作沿革留档、不再用于全新部署」+ 为什么（表名/结构已漂移）。

#### 37.4 全量配置的判据链

1. **★ 定位决定一切取舍**：全量配置是**「拿到即可对照使用的示例配置」**——既回答「新环境需要哪些配置项」（判据是**「项有没有漏」**），也给出每项**可直接参照的具体值**。⛔ **值必须可见**：不写 `${XXX:__FILL_ME__}`、不写**无默认值**的 `${ENV_VAR}`——占位符满篇的配置拿到手没法用。✅ `${ENV_VAR:默认值}` 合规（默认值按下一条取，部署方一眼可见、也可注入覆盖）；属性引用按第 8 点。**「真值不入 git」只对密码类成立**（见第 7 点）。
   - **取值来源**：优先取**基线环境（通常是研发环境）配置中心实况值**；基线环境没配、实际生效的是代码默认值的项，填该默认值，或填研发环境里真实可用的地址。**不知道怎么填时尽量用研发环境的值。**
   - 由此推出一条常被漏掉的规则：**代码需要、但当前环境配置中心里没有的项，也必须作为正式配置项出现在全量里**（值按上一条取），而不是塞进附录说明——否则照它部署到新环境就会漏配。
   - **注释口径**：换环境要改的值注明「研发环境取值，换环境必改」；密码注明「示例值，部署时填目标环境真实口令」。

2. **收录矩阵：只收「部署方要配」的那些，⛔ 不只是后端**：

   | 层 | 仓库内有无权威原文件 | 部署方要配吗 | 收录 |
   | :- | :-: | :-: | :-: |
   | 引导层**通用**文件/段（服务名、端口、context-path、加载哪些 dataId） | ✅ 有 | 不用（随代码走，改它要重新构建镜像） | ❌ |
   | 引导层**环境**文件/段（连哪个配置中心、账号口令、namespace） | ✅ 有 | 要 | ✅ **只放目标环境那一份** |
   | 配置中心的业务配置 | ❌ 无（只存在于配置中心服务器） | 要 | ✅ 仓库内唯一基线 |
   | **运行时部署文件**（nginx 反代 / 静态托管、docker-compose、k8s，**含前端**） | 视项目：仓库里有就是权威原件 | 要 | ✅ **完整份**（37.2） |
   | **前端运行时配置**（部署后可改、不需重新构建的，如 `public/config.js`、容器启动时注入的 env 文件） | ✅ 有 | 要 | ✅ 目标环境那一份 |

   - **⛔ 前端与网关侧不得漏**：真实回流——发布产出的 `配置文件/全量/` 只有后端配置，nginx 配置一份没有，照它部署前端起不来。**来源**：仓库里有权威原件（如 `code/frontend/*/nginx.conf`、`deploy/`、`docker/`）→ 以它为准（口令换示例值）；仓库里没有、只维护在服务器上 → 从基线环境**只读**取回（如 `kubectl get configmap -o yaml`、只读查看现网 nginx 配置）；都拿不到 → 在 `配置文件/全量/配置说明.md` 写明「本项目无 nginx / compose / k8s 运行时文件」或「未取回 + 原因」，⛔ 不静默缺失。
   - 回检 = `release_baseline_check.py` 第 1 项「结构完整性」：仓库里有的运行时部署文件 `全量/` 缺同名份、且 `配置说明.md` 未提及该文件名 → ERROR；有前端子项目但 `全量/` 无任何 nginx 配置、`配置说明.md` 也未提及 nginx → WARN。

   - **引导层为什么"有权威原文件也要放快照"**：拿到这套产物的部署方**未必有代码仓库**，只给指向等于没给；而生产要参考的恰恰就是引导层。**放，但文件头必须写明 `# 权威源码：<源码路径>`（多服务共用一份时逐行列出）+「权威仍是代码里的原文件，改了记得同步这里」**。
   - **不放通用文件**：非目标环境的 profile 不复制，只复制**目标 profile 那一份**；其中的真实口令换成示例值（37.4-7），其余照源码。
   - **★ 环境段副本必须与源码同形**（副本自己声明"权威是源码、改副本不生效"，同形是最基本的要求）：
     - 源码是 `${环境变量:默认值}` 的项，副本**保留同一个环境变量名、同样的写法**；默认值照抄源码，真实口令换示例口令。
     - 源码**故意不给默认值**的项（如 prod 的配置中心地址 / 账号 / 口令，没注入即启动失败），副本可补一个示例默认值方便对照（地址、账号取研发环境，口令用示例值），也可保持无默认值，但**该行或上一行注释必须写明「源码没有默认值，未注入即启动失败，部署侧必须注入」**。
     - 源码是写死值的项，副本照写死值（口令换示例值），⛔ 不自行改成环境变量写法。
   - **★ 跨 profile 补齐**：同一服务各 profile 的环境段文件（`bootstrap-{profile}.yml`，以及 `application-{profile}.yml` 等同类环境段，按实际技术栈）本应是**同一组配置项、只是取值不同**。生成副本时按**解析后的完整配置路径**（不按文本行）比对所有 profile 的配置项集合，列出目标 profile 缺少的项：
     - **默认要补**，补成 `${环境变量:默认值}`，默认值**按目标环境的语义取，⛔ 不照抄 dev 的取值**（例：dev 的 `mybatis-plus.configuration.log-impl` 是 `StdOutImpl`，会把每条 SQL 打到标准输出，生产应取 `Slf4jImpl`）。
     - **⛔ 不能只改副本**：副本里有、源码里没有的项不会生效。补的项由发布流程**同步写进源码**的目标 profile 文件（交互模式先经用户确认；无人值守不改源码，登记发布欠账）。
     - **确实有意不配**的项，在副本里写固定标记 `# baseline-check: profile-skip <完整配置路径> <理由>`，不能静默缺失。
   - 回检 = `release_baseline_check.py` 第 13 项「引导层同形」：源码有而副本无、副本有而源码无、写法 / 环境变量名 / 默认值与源码不一致、跨 profile 缺项且无 `profile-skip` 标记 → ERROR。
   - 通用文件里"部署要知道但不该改"的事实（端口、context-path）权威在代码里，`配置说明.md` 文件清单里一句带过即可，⛔ 不另列表格。
   - **目录扁平化**：引导层只剩一个文件时不为它单开子目录，直接与配置中心目录平级平铺。
   - 多服务若环境段内容相同，**逐字比对确认后合并成一份**并注明"两服务共用"。

3. **业务配置只留一份模板，不为每个环境各存一份**。它们是同一份配置的多个环境实例，并存只会让人纠结"该用哪份"。**留一份模板 + 在 `配置说明.md`「换环境必改」里列各环境的键集合差异**（有才写；值差异属正常环境隔离，不计）。
   - 真实回流：某项目误以为 dataId 命名规律是"研发无后缀 / 演示带后缀"，实查**已交付现场**用的也是无后缀——**无后缀才是标准形态**。自动判定命名规律必须扫**所有**环境，不能只看研发 + 当前环境两个样本。

4. **值取配置中心实况，直连只读读取，不信仓库里的镜像目录**。真实回流：某项目仓库镜像落后三个版本——缺了新版必配项、多了已退役项、库名还是迁库前的、还多出三个线上已删的 dataId。

5. **按代码消费面筛选（三重检索，三者皆无命中才判死）**：① 配置全名（覆盖前后端所有源码类型）② **驼峰字段名**（配置绑定按字段名而非全名，只搜全名会漏判）③ **外部 SDK**（有些前缀由依赖的 SDK 消费，本仓库搜不到 → 需解包扫描依赖包）。再逐一比对各配置绑定类（`@ConfigurationProperties` 等）的字段清单。
   - 扫代码消费面时注意**全限定写法**（`@org.springframework.beans.factory.annotation.Value`）与 `@ConditionalOnProperty` 容易被正则漏掉。

6. **剔除死配置**（配置中心有、代码零消费）→ 进删除清单。最值得清的一类是**「同值重复但只有一处生效」**：真实回流，某项目 `storage.minio.*` 与 `minio.*` 值完全相同，但只有后者有绑定类——**改前者不会有任何效果**，留着会让人排障白忙一整天。另一类是 **Mock 兜底开关残留**（对应代码已切真实对接并删除）→ 与**约定 26 Mock 清理**联动，清代码时必须连配置一并清。

7. **敏感性只按「密码」划分：密码填虚构示例值，其余一律填真实值**。
   - **密码类**：`password` / `passwd` / `pwd`，以及本质上就是口令的字段（如 MinIO 的 `secret-key` 实为 admin 账号口令）、URL userinfo 与 HTTP Basic 里的口令部分。填**一眼能看出是假的**虚构值（如 `Nacos@Example2026`、`Dm@Example2026`），并在行内或上一行注释写明「示例值，非真实口令」——真实口令不进 git（git 历史不可逆）。
   - **其余一律填真实值**：IP / 主机 / 端口、账号 / 用户名、应用 ID、应用编码、租户 ID、auth-code、token、api-key、URL 里内嵌的 token 等——它们不按密码处理。
   - 回检 = `release_baseline_check.py` 第 4 项（密码类值既无「示例值」声明、也非示例形态 → ERROR）。

8. **重复值：写具体值 + 注释同步关系，或用可解析的属性引用**：同一配置集里语义上**本就是同一个东西**的重复值（真实回流：某项目一个主机 IP 出现 4 次，换环境要逐处改、极易漏），两种写法都合规：

   ```yaml
   # 写法一：每处写具体值 + 注释标明同步关系
   sso:
     authn-url: http://192.0.2.8:8080/sso-authn   # 研发环境取值，换环境必改；与 sso.api-url 共 2 处须同步修改
     api-url:   http://192.0.2.8:8080/sso-api     # 研发环境取值，换环境必改；与 sso.authn-url 共 2 处须同步修改
   # 写法二：属性引用（被引用键必须存在于同一配置集，或引用自带默认值）
   ep-hosts:                          # 纯聚合锚点，不对应任何 @ConfigurationProperties
     sso: http://192.0.2.8:8080       # 研发环境取值，换环境必改
   sso:
     authn-url: ${ep-hosts.sso}/sso-authn
   ```

   - **⚠️「值相同」不等于「同一个东西」**：语义不同、将来可能分化的值（如一个面向浏览器、一个面向服务端内网，当前环境恰好同值）**不做引用、不标同步关系**——那会错误暗示"两者必须相同"；保持独立 + 注释说明关系。
   - 属性占位符在所有配置源加载完后统一解析，**跨 dataId 引用同样有效**，但只能引用"一定会被一起加载"的 dataId 里的 key。
   - 回检 = `release_baseline_check.py` 第 6 项（被引用键不存在且无默认值 → ERROR，启动期解析会失败）。
   - 若某服务的 `shared-configs` 已加载另一服务的 dataId，则与之逐字相同的项**直接删掉即可继承**（真实回流：两个 dataId 各写了 20 项完全相同的配置），并在文件末尾说明"为什么能继承、什么时候才需要在此覆盖（加载顺序在后，同名 key 会覆盖）"。

9. **注释写业务含义与后果，不是字面复述**。逐行扫描「既无行内注释、上一行也非注释」的配置项，全部补齐。合格示例：`database: 10` → 标明该库号为本项目专用、与其它系统隔离，且各环境不同，部署前须确认；`max-lifetime` → 应小于数据库侧的连接空闲断开阈值；`sms.url` → 当前指向预发地址，正式启用前须换生产端点；角色编码 / 租户 ID → 标注"换环境必改，不跨环境通用"。

10. **★ 中间件多形态：两种（多种）都写进配置，当前生效的启用、其余整段注释**。有些配置在不同环境是**结构不同**而非值不同（Redis 单机 / 集群 / 哨兵，数据库单实例 / 多节点），且生产与研发形态很可能相反。校验**生效形态唯一**（同时配两套时框架只认其一、另一套静默失效）。写时必须覆盖两类坑：
    - **① 结构切换会让既有机制失效**：Redis 单机切集群时 `database` 必须删除（Cluster 只有 db0、不支持 SELECT），而项目可能正靠库号与其它系统隔离——**该隔离机制会直接失效**，需提前决策改用独立集群或 key 前缀。这不是改配置能解决的，必须在文件里预警。同类还有跨 slot 批量操作报 `CROSSSLOT`、拓扑自适应刷新必须配（不开则主从切换后客户端不感知，表现为持续报错、重启才恢复）。
    - **② 配置与依赖的隐式耦合，且要写全两条路径的后果**：真实生产故障——配了 `lettuce.pool.enabled: true` 但 classpath 无 `commons-pool2`，启动直接 `NoClassDefFoundError: GenericObjectPoolConfig`，报错完全不提示是配置引起的。框架判定逻辑 `(pool.getEnabled() != null) ? pool.getEnabled() : COMMONS_POOL2_AVAILABLE` 意味着：**不写该项 → 取 classpath 检测值 → 缺依赖时自动降级、正常启动；显式写 `true` → 强制池化 → 启动直接失败**。而网上抄来的模板大多带 `enabled: true`，粘贴即炸。
    - **⛔ 由此立规**：写多形态配置时**不能只描述 happy path 的降级行为**，必须把**两条路径的不同后果都写明，尤其「哪种写法会让应用起不来」**。生成时应主动核查此类耦合（如 `mvn dependency:tree -Dincludes=<groupId>:<artifactId>` 确认依赖是否真在 classpath）并把结论写进注释。

#### 37.5 增量轨的发布期校准

增量 SQL 随实际开发持续产出，配置变化留机器待同步引用；规划/正式发布集中校准 `配置文件/增量/配置项清单.md` 的必要代码片段，不抄全量：

1. **基线区间 = 上一个已发布 tag → 本次版本**，且必须**跨过中间过渡版本**（某 tag 合并承载了多个未单独发布的中间版本时，升级区间要覆盖它们）。区间计算用 `python3 {{AIDP_HOME}}/scripts/release_scope.py`（已处理版本号按数字段比较——按字符串比 `V0.9 > V0.11` 会直接翻车）。
2. **判定方式是比对两个时点的代码消费面**（`git grep <tag>` 扫描），得出净增/移除的项，**而不是凭改动印象**。
3. **⛔ 比对必须覆盖两层**：只比配置中心会漏掉引导层。真实回流：某版本恰有一个 commit 把引导层接入参数从写死改成可注入——向后兼容、升级无需动作，但漏记就是漏记。
4. **比对基线要能回溯到发布时点**：配置中心是活的，产出历史版本增量时应从**配置中心的变更历史 API** 取该版本发布时点的快照，不能拿当前内容冒充。若该环境配置在目标时点尚不存在，**如实说明无法回溯，不要用其它环境的内容顶替**。
5. **删除侧标注粒度**（这层信息平铺成表格会丢），用 YAML 缩进表达 + 前提与风险；共享 dataId 的删除需与其它系统会签：

   ```yaml
   auth:                   # 整段删 · 无消费
   sso:
     platform-org-id:      # 单键删 · 无消费
   ec:
     v06-ops:              # 整棵子树删 · Mock 残留
   ```

   `sso.platform-org-id` 只删一个键，**不能把整个 `sso` 段删掉**（那段全是认证必配项）。
6. **★ 极简，只说「改了什么」**：增量侧**只用代码块**列新增/删除项，保留 dataId 坐标 / 项名 / 必配可选之分，**注释直接写进代码块**（YAML 用 `#`）且**行内注释 ≤20 字符**。
   - **⛔ 不做「代码块 + 下方表格」两处对照**——同一条变更写两遍必然漂移，且真正要看的被淹没。
   - **⛔ 判定依据 / 背景论述 / 各环境对照表 / 执行建议 / 风险评估一律不进增量**——判定依据与背景归 git 提交记录，各环境差异归 `全量/配置说明.md`「换环境必改」（不双写，约定 25）。
   - **⛔ 文件清单 / 换环境必改 这类常驻信息也不进增量**——它们不是本版变更；开发期手工维护它们正是"仓库镜像落后三个版本"（37.4-4）的来源，改由发布期从真实环境只读重建进 `全量/配置说明.md`。本版新增的敏感项在代码块里标 `# 必填·敏感` 即可。
   - 真实回流：某项目 6 个增量文档 414 行 → 168 行（-59%），信息零丢失。
   - 回检 = `release_baseline_check.py` 第 10 项「增量极简度」（增量文档出现 Markdown 表格 / 行内注释超 20 字符 → WARN）。
7. **零变更是合法结论，但要留文档**：`sql/增量/` 本版无脚本 / 配置本版无变更时，在版本根 `README.md` 写清「为什么是零」+ 判据（如配置中心历史在该区间无变更记录），并对 SQL 附**只读核验脚本**（表/序列存在性、关键列约束），让"确实不用执行"这个结论**可自证**，而不是一句空话。**不产出空文件，也不省略说明。**

#### 37.5bis 增量轨 DDL 的**执行顺序与注释实查**（改表结构时恒适用）

增量轨的 SQL 不只是"产出来"，还要"**按正确顺序执行、执行完核验库里的状态**"。两条硬规则：

**① 发布顺序铁律 —— 加列先 DDL 后代码；删列先代码后 DDL。**
判据只有一条：**恒定保证「代码引用的列集合」⊆「库中实际列集合」**。顺序做反的后果不是
"某个功能不可用"——MyBatis-Plus 这类**按实体全字段拼 SELECT** 的 ORM 会让**整表查询全部报错**，
读该表的接口一起 500（下游实测一次波及 30+ 个 controller，且同一版本内**正反各犯一次**）。
⚠️ **滚动发布的混合实例期**：灰度期间新旧代码同时在跑、旧实例仍在 SELECT 那一列，
故**删列 DDL 必须等到「全部实例都已是新代码」之后**才执行——是"发布完成后"，不是"发布开始后"。

**② 注释覆盖率必须【实查库】、不看脚本。**
本版每个 `ADD COLUMN` 在库中都必须有列注释，**覆盖率 100%，缺一即 Critical**。
⛔ 核对对象是 `ALL_COL_COMMENTS` / `information_schema.COLUMNS` 的**实际状态**，
**不是** SQL 脚本的内容——下游实测事故里脚本**写了** `COMMENT ON COLUMN`，但手工执行时
只跑了 `ALTER TABLE ADD` 那一段循环、注释语句整段漏掉，**而没有任何一步会发现**：
实查结果新增 10 列 10/10 无注释。**脚本内容正确 ≠ 库里状态正确。**
实查结果留既有 baseline 的 `deployment_sql_checks.{version}`，每个本版增量脚本一项：`script`（仓库相对路径）、`sha256`、`database`、`checked_at`（真实带时区时点）、`columns:[{name,comment}]`（实际查询结果）。查询方法随数据库选 `ALL_COL_COMMENTS` / `information_schema` 等，不把脚本里的 COMMENT 冒充查库结果。
机器门 = `python3 {{AIDP_HOME}}/scripts/check_sql_ledger_comment.py --version {version}`，只在正式发布已授权校准范围核验本版新增列，记录缺失/变化/真实缺注释不能判过；不向 SQL 操作表添加实查报告，不自动扫历史无注释列。

#### 37.6 边界情况与只读纪律

- **同一 commit 被打了多个 tag**：全量——各自版本目录都产出（它是该发布点的基线）；增量——**指向先产出的那份，不复制**（同一份脚本两处维护必然漂移，且运维照哪份跑会产生歧义）。
- **⛔ 全程只读（约定 35 同源）**：DDL 经**元数据视图**导出、配置经**只读 API** 拉取，**不执行任何 DDL/DML、不改任何环境的配置、不启动任何服务**。本步读的是"已在运行的真实环境"，不属约定 35 禁止的"擅自起服务 / 完整构建"，但只读边界必须守死。
- **基线环境须用户确认**：生成前确认"以哪个环境为全量基线"。真实回流：某项目配置中心里**根本不存在生产 namespace**（生产尚未建立），此时应如实告知让用户选择，**不得默认拿研发环境冒充生产**。
- **★ 如实登记核查中发现的问题，不要只交一份漂亮的配置**。真实回流：某次实践顺带查出——一组接口因配置缺失处于"全拒"状态、两项配置在吃不可用的默认值（一处签名密钥默认值字面就是 `dev-secret-please-replace`、一处跳转地址默认值是 `console.example.com` 假域名，**都在生产静默生效**）、两个实体有代码无表（死代码，联动约定 29）、一处列名在十余处文档中写错。**这些副产品的价值往往高于产物本身**，留既有机器核对记录；仅本次交付所需补救操作进入部署指引，按当前授权处理相关上游文档，不自动纳入历史债务。

#### 37.7 ★ 与约定 25「配置文件分层」的边界（唯一例外，不是推翻）

约定 25 禁止的是**在 Markdown 里复抄完整配置文件**、维护 key→示例值全量大表、创建 `.env.example` 类示例副本——理由是**双信源漂移**（仓库里的真实配置文件才是权威）。本约定的 `配置文件/全量/` **不落入该禁令**，判据有三条，缺一条就退回约定 25 管辖：

1. **产物形态是真实 `.yml`/`.conf` 文件，不是 Markdown 复抄**（`配置说明.md` 只放文件清单、必改项、来源，**不复抄配置正文**）；
2. **主体是「仓库内无权威原文件」的配置中心层**——它在仓库里根本没有第二信源，谈不上双写；两个例外须显式标注来源：**引导层快照**（权威在代码里的原文件，文件头写死"改了记得同步这里"）、**nginx/compose/k8s**（`全量/` 里这一份**就是**权威原件本身，不是副本，按约定 25「原文件为权威」原地成立）；
3. **它是发布期冻结的一次性基线快照**（随 tag 走、不再改），**不是与原文件并行维护的活文档**。

> 换句话说：约定 25 治的是"日常维护两份、必然漂移"；本约定产的是"发布时刻钉一份、随 tag 冻结"。二者不冲突。**`配置项清单.md` 与 `全量/配置说明.md` 之间仍然适用约定 25 的不双写**——清单讲"本版改了什么与权威路径"，全量讲"一共有哪些项"。

#### 37.8 机器门（不靠自觉）

发布期产出后**必须**跑：

```bash

python3 {{AIDP_HOME}}/scripts/release_baseline_check.py --version <version> --json
```

### 约定 38 — **★ 开发期环境地址 / 账号即时归档到研发自测**

> 技术栈中立：下文的达梦 / MySQL / Nacos 一律为**示例**，按本项目实际数据库与配置中心对应。

#### 38.1 为什么需要（问题形态）

用户在开发过程中会**随口**给出环境信息——"你连 `http://192.0.2.10:8080` 看看"、"用 admin/Abc@123 登录试试"、
"库在 `192.0.2.20:5236`，账号 SYSDBA"。这些信息的特点是：

- **只出现一次**：夹在一句业务描述里，用完当次操作就滚出上下文；
- **下游强依赖**：`/sprint-aiauto-test` Phase 0.0.5 要靠它启动浏览器 + 登录，`auto-test-runner` 缺账号会把
  整个模块判成 `block(前置不满足)`；约定 33 的双源对账要靠 DB 连接；缺陷复现的跨系统前置要靠联动系统 URL；
- **丢了代价高**：只能回头再问人，而人往往已经不在会话里；无人值守链路则直接卡住。

**结论：给出即归档，不是"顺手记一下"，而是硬要求。**

#### 38.2 触发识别（什么算"环境信息"）

用户消息中出现下列任一，即触发本约定（**不要求用户说"记一下"**，给出本身就是触发）：

| 类别 | 形态举例 |
| :- | :- |
| 环境访问地址 | `http(s)://<host>[:port][/path]`、`<ip>:<port>`、内网域名；含前端页面地址与后端接口 base |
| 登录账号 | `账号/密码`、`用户名 xxx 密码 yyy`、`admin/Abc@123`、明确说"用这个号登录" |
| DB 连接 | JDBC 串、`host:port` + 库名 + 账号密码、"库在…"、达梦/MySQL/PG 连接信息 |
| 联动系统入口 | "订单中心在 `http://…`，先去那儿删条数据" 这类**跨系统前置**用的地址/账号 |

**不触发**（避免噪音与误归档）：

- 第三方公共服务地址（`https://github.com/…`、文档链接、镜像仓库地址）；
- 代码/配置文件里**本来就有**的地址（那属约定 25「原文件为权威」，不复抄进 md）；
- 用户明确说"临时试一下 / 别记"、或一次性的调试端口。

#### 38.3 落点与字段映射（两处都写，各服务一类消费者）

**主落点（机器消费权威）** `docs/testing/{version}/研发自测/01_测试环境与账号.md`：

| 用户给出 | 写入段 | 字段 |
| :- | :- | :- |
| 前端/后端 URL | 三、测试环境 | `系统角色`（被测主系统 / 联动系统 N）· `系统名` · `前端 URL` · `后端 URL` · `说明` |
| 账号密码 | 四、测试账号 | `所属系统` · `角色` · `用户名` · `密码` · `账号最近验证时间` · `可用环境` |
| DB 连接 | 五、DB 连接 | **字段以模板为准**（`flows/sprint-selftest/step-3-2.md` 的表头，现为 9 列、比此处旧抄多 `DB MCP 名`）——⛔ 不在此复抄列名 |

- **`账号最近验证时间`**：本轮**真正登录成功过**才填当天日期；只是用户口述、未验证 → 填 `未验证`（口径见该文件内注，不自造）。
- **`environment` 必填**：`dev/test/uat/研究/演示/prod`；与「三、测试环境」被测 URL 所属环境不一致要就地标 `❌ 环境不匹配`（用错库的对账比不对账更危险）。
- **信息不全就留原槽位**：用户只给了 URL 没给账号，就只填 URL 行，账号列保持 `<请填写>`，**不臆造、不猜端口、不推断角色**。

**同步落点（人工阅读面）** `01_研发自测方案.md` §3「测试环境与准入」（§3.1 环境信息 / §3.2 测试账号 / §3.3 前置数据）：
该文件由上游 `dev-manual-testcase` SKILL 产出，此处**只更新 §3 已有表格的数据行**、不改其结构与其余章节。
两份并存时以 `01_测试环境与账号.md` 为准（SKILL 自身即如此声明），§3 属其人工可读镜像。

#### 38.4 文件缺失 / 冲突 / 版本归属

- **版本归属**：写当前开发版本（`AGENTS.md`「当前状态 → 当前版本」）；该版本目录不存在则**按 `/sprint-selftest` Step 3 的模板建骨架**再填，不要因"还没跑过 selftest"就丢弃信息。
- **`01_测试环境与账号.md` 不存在** → 建之（模板单一信源 = `flows/sprint-selftest/step-3-2.md`），只填已知字段，其余留 `<请填写>`。
- **`01_研发自测方案.md` 不存在** → **不为本约定单独造**（它是 SKILL 的产物，凭空造会与后续 SKILL 生成冲突）；只写主落点，并提示"跑 `/sprint-selftest` 后会补齐方案 §3"。
- **冲突（同系统同角色已有值且不同）**：**绝不静默覆盖**（沿用 Step 3 的 append-only 精神）——用 `AskUserQuestion` 让用户选「更新为新值（旧值移入备注）／新增一行（多环境并存）／保持不变」；无人值守下**追加新行 + 备注注明来源与时间**，不动旧行。
- **幂等**：同一信息重复给出、值一致 → no-op，不重复追加行。

#### 38.5 敏感分流（沿用既有设计，不另造规则）

`01_测试环境与账号.md` 本就声明「仅用于开发测试环境，账号可直接明文维护」，故：

- **dev / test / 研究 / 演示 环境** → 明文写入该文件（入库、团队共享，这正是它的设计用途）。
- **prod / UAT 凭据** → **不写入该文件**，改存 `memory/.sprint-autopilot-credentials.json`（chmod 600 + `.gitignore`），
  且**须用户显式确认后再存**；该文件里只留一行指针（如 `生产账号：见本机凭据文件，未入库`）。
- **判不准是哪个环境** → 按 `prod` 从严处理并问用户，不赌。
- ⛔ 无论哪种，都**不得**把凭据回显进 commit message、报告正文、里程碑通知。

#### 38.6 告知与留痕

归档后必须在**当轮回复**里明确告知（不静默写文件）：`已归档到 docs/testing/{version}/研发自测/01_测试环境与账号.md
「四、测试账号」：<系统>/<角色>`。改动**不单独 commit**，随本轮其余产出一并提交（与规划期产物同口径）。

#### 38.7 显式补录入口

用户主动要求归档（"把这些环境记一下"、"补录测试账号"）→ `/sprint-selftest --capture`：**只跑归档**，
不重生成用例、不调 SKILL。自动触发（本约定主路径）与显式补录**共用同一套落点与冲突规则**。

#### 38.8 写操作授权档位（归档面从「能登录」扩到「能改什么」）

**问题形态**：38.1~38.7 归档的是**读用**信息（URL / 账号 / DB 连接），执行体据此能登录、能看——
但**不知道自己被允许做哪些写操作**。缺省的保守行为是什么都不动，于是每一条"环境里没有现成数据"的用例
都被判成 `block(前置不满足)`，而其中相当一部分只要造两条数据就能跑完。
下游实证：一轮 71 条用例标了 13 条 block，复查发现 7 条属于**有权限造却没去造**，实际造数后 5 条当场转 pass。
⇒ **「这条真的造不出」与「执行体不知道自己能造」在产物上完全同形**，没有任何门能区分。

**落点**：`01_测试环境与账号.md`「八、写操作授权档位」（模板单一信源 = `flows/sprint-selftest/step-3-2.md`），
三档一行：只读 / 可逆写（须记原值、可还原）/ ⛔ 不可逆写（禁止），另记**授权来源**（谁、何时、口头或书面）。

**触发**：与 38.2 同口径——用户在**任意时刻**说出授权或禁止类表述即当轮归档，不要求他说"记一下"：

- 授权向：「这两个平台你随便操作」「可以在订单中心建测试订单」「要什么数据自己造」
- 禁止向：「别动生产数据」「不要新增用户，会真发短信」「那个库只读」

**默认档位 = 只读（fail-closed）**：本表缺失、或某系统未登记 ⇒ 该系统按只读处理。
⛔ 不得把"表里没写"读成"没限制"——代价不对称：少造数只是多一条 block（可事后补），
误做不可逆操作（真发短信 / 删了共享数据 / 重置了别人密码）无法回滚。

**与 block 判定的关系**：标 `block` 之前先答一句「造这条用例的前置数据需要哪些操作？我有权限做吗？其中有不可逆的吗？」——
全部可逆且有授权 → ⛔ **不许标 block，去造**；存在不可逆操作 → 标 block 并写明**是哪一步**不可逆；
页面根本不存在该形态 → 标 block 并给出结构性证据（这类本该在规划期就识别出来，不该拖到实测第三轮）。
⚠️ `block_reason` 的枚举细分以 `auto-test-runner` 的 `scripts/check_result.py::BLOCK_REASON_ENUM` 为单一信源（`result-schema.json` 只是示例、非可校验 Schema）（变更在模板仓库改该 SKILL，约定 16）；
本条能落地的是**授权档位归档**这一侧——把默认答案从「标 block」翻回「去造数」。

#### 38.9 反向对账（写进文件却未归档）

正向归档靠执行体自觉，漏归档的典型形态是：地址 / 账号被写进需求、计划、记忆或方案 §3 正文，权威文件里却没有，下游照样判缺前置。
`python3 {{AIDP_HOME}}/scripts/check_env_archive.py --version {V}` 扫人工阅读面（`docs/`、`memory/` 的 `.md` 与根级记忆文件），
检出内网 / IP / 带端口地址、JDBC 连接与带标签账号，与权威文件及本机凭据文件对账；exit 1 = 有未归档项，按 38.3~38.5 补录。

- 扫描面与 38.2 同口径：代码 / 配置文件不扫，`docs/init/` 示例不扫；回环、文档保留网段、保留域名与占位符不算。
- 用户明确说「别记」的临时地址 → 行尾 `<!-- env-archive: ignore 理由 -->`。
- 调用点：`/sprint-selftest --capture` 归档后自检、`/sprint-autopilot` 0.6bis。输出只含地址与用户名，⛔ 不回显密码。

### 约定 41 — light/formal 身份与动作边界

#### 41.1 身份由用户意图与父上下文决定

普通自然语言默认 light；自动路由到 `/sprint-start`、`/sprint-dev`、`/sprint-test`、`/sprint-bugfix`、`/sprint-close` 是复用能力，不使任务变为正式 Sprint。显式 Sprint、版本规划/发布与 full/batch/autopilot 为 formal。已有 activeContext、未关闭历史 Sprint、文件数量、接口/DDL 变更均不是身份判据。

入口先执行 `entry_context.py resolve/route`，light 执行 `{{AIDP_HOME}}/flows/sprint-dev/light-context.md` 对应能力后 return；formal 才过原 Sprint 门。嵌套、重试、验收内修复与续跑继承同一 `--execution-context`，不靠当前命令名重新判定。formal 批次按明确 Sprint fork 子上下文，父身份不改。身份不能由执行体自建卡片“批准”。

#### 41.2 两种身份的动作边界

| 动作 | formal | light |
| :- | :- | :- |
| 受影响族增量、提交门、推送分类 | 按相应阶段执行 | 同样执行；只有实际影响才登记，不建空册 |
| 静态验证与代码审查 | 只核当前已授权动作的真实证据 | 默认static；review/tests获授权才有对应证据 |
| Sprint 号、卡片、启动记录 | 先原门再创建/更新 | 不创建，不伪造 Sprint-000 |
| activeContext/progress/Sprint 归档 | 当前明确 Sprint 的状态 | 保留既有状态，不认领、不重置 |
| 人工任务/审批文档 | 按正式契约 | 不新增；机器上下文和 JSON 报告自动落盘 |
| 四族正式正文 | document已授权的正式汇合/收口点消费 | 开发期只攒批；收尾不自动 cascade |
| build | 仅有相应正式编排职责时 | 不铸造 |
| 部署/浏览器实测 | 仍按授权与专用入口 | 默认不执行；用户明确要求才走相应入口 |

light 推送若已获授权仍用 `classify_push.py --version <V> --standalone`，提交前 `commit_gate.py --execution-context <PATH>` 消费真实任务上下文。命令复用不构成 commit/push、部署或不可逆操作授权。`memory/.aidp/entry-contexts/<id>/` 下机器证据不替代业务授权，也不要求用户人工维护它。

#### 41.3 风险、复杂度、成本独立

唯一评估实现与 pre/post 配方见 `{{AIDP_HOME}}/flows/sprint-dev/light-context.md`。`development_scope.py` 从同一冻结 baseline delta 计算 risk_tier、complexity、cost；文件数只影响成本，不能把 >10 files 直接判 L。兼容 ALTER、新表、破坏性与 SQL unknown 单列；未知需核影响，不按无DDL或全量审计处理。

风险提示不授予新的 action。light不因风险变 formal，formal不因规模开启tests/review/docs。收束只验本轮已授权证据；NOT_REQUESTED不是欠账或PASS，工具/环境失败与业务FAIL各留原结果。

#### 41.4 与正式编排不变式的边界

`flows/sprint-autopilot/invariants.md` 的不变式仅适用于该正式编排。light 不因复用 dev/test/bugfix/close 被套入 autopilot 仪式；formal 也不能借 light 协议跳过自身开工、契约、已授权验收及归档门。两种身份均保留协作写集、版本/破坏性授权、不可逆数据库限制与完整构建禁止。

#### 41.5 formal Sprint 归档篇幅分档

本节只约束 formal Sprint 归档，light 不生成该产物。约定 9 的未归档不得开始下一 Sprint 门不适用于 light 收束。
下游实证：两个 0.75pd 的口述累进 Sprint，归档分别写了 **93 行**和 **106 行**。

**建议上限**（超出不阻断，但须自问"这些是不是事后查得到的"）：口述累进 ≤40 行 / 计划内 Sprint ≤80 行 / 含口径反转 ≤120 行。

**归档只记【事后查不到的东西】** —— 判据直接复用约定 22 增量册的"不要记"清单：
⛔ 不记 git log 查得到的（改了哪些文件、什么时候提交的）、⛔ 不记文档里已有的（需求原文、设计结论）、
⛔ 不记下一轮会重算的（覆盖率、通过率）。**记的是判断与取舍**：为什么选这个方案、放弃了什么、留下什么已知失准点。

#### 41.6 变异对照的轮数（消除"已成惯例却无规定"的方差）

「变异对照」（植入必然被抓的错误 → 确认工具报出来 → 移除 → 再采信）在约定 35 里是**必须**做的，
但**做几轮从无规定**，于是每个执行体自行决定（下游实证同一会话里分别做了 3 轮和 4 轮）。

**定规**：**每个新增/修改的判据各做 1 轮**（1 个阳性 + 1 个阴性）即满足约定 35；
⛔ 同一判据重复多轮**不增加可信度**，只增加耗时。判据本身有多个分支时，**按分支各 1 轮**，
而不是整体多跑几遍。⚠️ 例外：阳性对照**没报**时必须先查"是不是夹具写错了"再改判据 ——
本仓多次实证第一次阳性对照假绿的根因是夹具放错位置，而不是判据失效。
