# sprint-bugfix · rationale（理据 / 根因 / 历史事故）

> 本文件收集 `/sprint-bugfix` 各段的**理据 / 根因 / 反例 / 历史事故**——对人类维护者有价值、但对执行期模型是噪音（稀释祈使信号），故从执行路径剥离、执行时**不加载**。
>
> 权威执行步骤见命令主体 `.aidp/commands/sprint-bugfix.md` 与同目录 flow 分片（`mode-b.md`）。本文件**只解释「为什么这么定」、不定义任何执行步骤**；与命令主体/分片冲突时一律以后者为准。

---

## 1. 「缺陷处置默认决策纪律」为何从二分改成先问一句

**旧二分**："要什么（需求不明）"→ 等人；"写错了（实现有误）"→ 当场改。

**问题**：边界模糊的缺陷（失败被伪装成成功、前端吞后端 error、上游不可达无提示、安全 fail-open）两边都能套，**缺默认值** → 执行体保守选"等人" → 无谓阻塞。真实反馈：三件本该默认修的事被挂起等了一夜。

**现设计**：先问一句「**不做这个修复，当前行为是不是错的？**」——是 → 默认直接修、不问；**拿不准也默认修**。只有"口径/单位/默认值需产品定义""涉及版本号/tag/对外承诺"才归"必须问"。要点是把默认值从「挂起」翻转为「修」，让举证责任落在"不修"那一侧。

## 2. 为什么增量设计固定走 `dev-logic-architect` skill、而非就地手写

Bug 修复的增量设计同样要落进 `docs/design/detail/{version}/` 的既有分册体系（主题对号入座 + `00_索引.md` 维护 + 溯源标注 + SKILL 内置多维度 QR）。手写增量会绕过这些硬门，产出**格式不合、无溯源、逃检**的段落，下一版全量重算时被判漂移。故固定走 SKILL，命令端只做主题定位与落盘编排（约定 21）。

## 3. 为什么「问题汇总清单」要三种序号前缀（T- / C- / R-）

三类缺陷的**根因定位路径不同**，混编会误导排查：

- `T-NNN`（人工自测发现）、`C-NNN`（AI 自动化测试失败用例）→ 有对应用例，可**反查用例执行步骤**定位根因。
- `R-NNN`（chrome 运行时错误）→ 其「用例 ID」可能是 `运行时-<页面>`（无对应用例断言），**反查用例会扑空**；必须以「复现步骤」列（角色 + 页面 URL + 触发动作 + 报告引用）为准。

前缀是"该怎么查"的路由标记，不是流水号装饰。

## 4. 为什么路径/URL 类根因要强制精读「路径消费者点」表

路径类缺陷（404 / 双前缀 `/<base>/<base>/...` / CORS / 跳转错）的典型失败模式是**只改一处、漏改级联消费者**——`context-path`、前端 `baseURL`、反代 `proxy_pass`、网关路由、对外接口 base 各持一份，改一处其余仍指旧值，症状换个入口照样复现。故把「路径消费者点」表设为这类根因的**强制输入**，让"还有谁消费这个路径"变成可枚举清单，而不是靠记性。

## 5. 为什么 P0/P1 缺陷修复后强制沉淀回归用例

缺陷本身就是**最精准的回归用例来源**（复现步骤现成、边界真实）。但 `docs/bugfix/{version}/` 的缺陷记录**修复后即终结**——release suite 不因此增长，于是同类缺陷可在后续版本重复发生、每次都从零复现排查。强制沉淀 + 跨版本继承（`/sprint-aiauto-test` Phase 2.0 自动并入历史 `[回归]` 用例）才能让历史教训自动累积、不逐版从零。

## 6. 为什么 `[回归]` 用例失败一律锁 Critical

回归用例代表"**曾修好过、且已明确承诺不再发生**"的行为。它再次失败意味着修复被推翻或被新改动覆盖，性质比首次发现同等现象严重得多——若仍按用例自身优先级映射（P2 失败判 P3），最该被看见的退化反而排到最后。故在 `auto-test-runner` 的缺陷分级里对该用例族**锁 Critical、覆盖优先级映射**（环境类 `block_reason` 除外——环境没起来不算产品缺陷）。

## bug 修复的设计增量为何不写回主文档正文

曾要求「内联追加对应专题主文档、非 `NN_补充`」，理由是"bug 修复属对现有设计的修补，
与新增功能刻意区分"。这个理由本身讲得通，但它**不是一条可执行的指令**——
`dev-logic-architect` 的增量产物契约明写「统一 `NN_<业务主题>.md`…**且不改内容主文档正文**」，
而命令端无权覆盖 SKILL 自己的产物契约（约定 21）。

两条同时挂着的结果是：**执行体无论怎么做都违反一边**。这类"互斥指令"比缺指令更糟，
因为它让合规与否取决于执行体先读到哪一条。

**溯源不因此变弱**：`00_索引.md` 记「类型=补充 + 生成时间」，
增量文档头部三类回链（专职索引 / 本轮输入来源 / 同轮其他层补充）指回主文档，
比内联追加更可审计。

## 方式 B 为什么必须有 L1 研发需求增量

Step 5 开篇自述「若变更触达**研发需求** / 详细设计 / 研发执行计划 / 研发自测用例 多层……
按约定 22 级联」，而回写步骤一度从**详细设计**起步——缺的正好是最上游那一层，
逐字命中约定 22 的典型漏项「只补了详细设计、把需求与自测用例留在旧口径」。

方式 C（`sprint-bugfix.md` 方式 C 第 2 步）与 `/sprint-dev` Phase 0B.1.1 都有这一层。
方式 B 是本命令自称「★ 最常用」的路径，方式 A 又以方式 B 全流程为执行体——
即 `/sprint-batch` → `/sprint-full` 的 bugfix 循环走的就是它，是无人值守主链的常态。
在最常跑的那条路上缺一层，比在冷门路径上缺十层更贵。

## 方式 B 为什么要单独挂一份累进产物审计

`version-auditor` 的八项 Critical 只在 `/version` Step 2.4.7 激活。`/sprint-dev` 侧的四条
累进路径已在 `flows/sprint-dev/postdev-writeback-3.md` 统一收口，**但方式 B 全程不调用
`/sprint-dev`、到不了那段**。两处因此是**同一套规格的两个落点，必须同步改**。


## 部署流程 + SQL执行台账联动的检测驱动细则（mode-b.md 的外置正文）

7. ★ **部署流程 + SQL执行台账联动（检测驱动，独立于是否改配置）**：如本 bug 修复引入**部署侧实质变更**（新增/变更 SQL、新增部署后回填/迁移接口、需重启、context-path/启动参数变更、新增中间件依赖），必须**同步执行 `/sprint-dev` Step X.8 的检测驱动维护流程**——按检测 bootstrap/增量更新 `docs/deployment/{version}/部署流程/部署流程.md` + `SQL执行台账.md`（台账追加本 bug 引入的 SQL 行、登记开发库列），并遵守 Step X.8 的反静默失败 WARN（模板缺失/生成失败/有部署变更却无文档 → 标「部署阻断风险」）。**注意与第 6 条区别**：第 6 条是"改了配置文件才触发"，本条是"部署侧变更即触发"（新增 SQL/重启/回填接口不改配置也触发），二者独立


## Step 5 为何默认攒批、而不是修完当场级联

原先本步是**修完立即**跑四级级联、当场产 `NN_<业务主题>.md` 并登记 `00_索引.md`。
它与约定 22 的攒批形态**从未对过账**——于是同一个项目里出现两套时机：
`/sprint-dev` 的漂移攒批、`/sprint-bugfix` 的当场级联。

下游实证的观感是「开发过程中版本规划文件在被实时更新」，而攒批明明写着
"开发期只写台账、收口期才成文"。执行体在两条都写在契约里的指令之间只能临场权衡，
同一项目不同会话行为不一致。

攒批的收益在这里同样成立：N 次 bug 修复各自级联，要付 N 份「读上下游文档 + 起分册 +
写文件头 + 关联文档表 + 索引登记」的固定开销；攒成一批只付一份。而**该记录的信息一条不少**——
只是从"即时写成正式文档"改成"先记台账、后批量成文"。

判定规则一条不改（触发条件、L1 必产、破坏性变更门），变的只是执行时机与承载中间态。

## P0/P1 缺陷为何强制转回归用例并跨版本继承

投入产出比最高的漏测收敛手段：缺陷的复现步骤是现成的、命中的是真实薄弱点，
比凭空补用例精准得多。
