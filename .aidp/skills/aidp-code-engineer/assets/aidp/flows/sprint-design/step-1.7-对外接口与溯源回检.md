### Step 1.7：★ 对外开放接口规范回检（仅 HAS_OPEN_API=true 触发）

> **项目级兜底回检**（约定 21，边界口径见 `rationale.md`）：SKILL 已规范对外接口文档形态（`flow-output-format.md`：独立 `12_对外开放接口.md`、与 `11_内部接口契约.md` 分离）但**无核验脚本** → 此处 grep 兜底。

当 Step 0.4.5 判定 `HAS_OPEN_API=true` 且本次产出含 `docs/design/detail/{version}/对外开放接口.md`（或拆分后含「对外」字样的分册）时，命令端必须执行以下 9 项硬规范回检：

| # | 检查项 | grep / 判定 | 不通过处置 |
|---|--------|------------|----------|
| 1 | **独立文档 + 统一文档**：(a) 对外接口不与内部接口混在 `接口设计.md`；(b) 所有对外接口统一在一份文档中，不按对接系统/第三方租户/业务域拆分 | (a) `接口设计.md` 中 grep `/api/open/\|对外开放\|external\|第三方调用` 应为 0 命中；(b) `docs/design/detail/{version}/` 下文件名含「对外」字样的 markdown 数应 ≤1 | (a) 把误置内容迁移到 `对外开放接口.md`；(b) 合并多份对外接口文档为单文件 |
| 2 | **免登录设计**（严禁依赖 Session/Cookie/JWT）| `对外开放接口.md` 中 grep `Session\|Cookie\|JWT\|Authorization: Bearer`，**先剔禁令语境行**（同行含 `严禁\|不依赖\|不得\|禁止\|无需` 即跳过）后应 0 命中 | 标红写入「⚠️ 对外接口规范告警」表，**暂停 2~6** |
| 3 | **认证方式声明**：每个接口必须明确写出"无认证 / API Key / OAuth 2.0"之一 | 每个接口段必含 `**认证方式**` 行 | 缺失则告警，要求 skill 补齐 |
| 4 | **路径前缀**：URL 必须用事实清单「对外开放接口 base」前缀，且与内部 base 不重叠 | 取事实清单对外 base；grep 对外文档中所有 URL 必须以该前缀开头 | 不一致 → 写入路径回检告警表，**暂停** |
| 5 | **限流策略**：每个接口必含 `限流策略` 行（默认单 IP/Key 100 QPS） | 每个接口段必含 `限流策略` 字样 | 缺失则告警，让 skill 补默认值 |
| 6 | **幂等设计**：写操作（POST/PUT/PATCH/DELETE）必含 `幂等` 字样 | 解析每个接口段的 HTTP Method + 是否含 `幂等` | 写操作缺幂等 → 告警，**暂停** |
| 7 | **错误码体系** | 判据以 `check_error_contract.py` 为准（C0 缺全局枚举章节 / C8 接口自编码）；⛔ 本表不另设计数式 grep——上游错误码已改带反引号 5 列表，旧 `40\\d{3}` 计数对合规产物恒不匹配 | 依脚本输出 |
| 8 | **版本策略**：必有 `版本策略` 段说明 URL 路径版本号 + 兼容期 | grep `版本策略\|兼容期` 各 ≥1 次 | 缺失则告警 |
| 9 | **审计日志**：必有审计日志规范 | grep `审计日志\|审计` ≥1 次 | 缺失则告警 |

**告警表写法**（追加到 `对外开放接口.md` 头部，与 Step 1.6 的「⚠️ 路径回检告警」表并列）：

```markdown
## ⚠️ 对外接口规范告警

| # | 检查项 | 当前状态 | 期望状态 | 修复建议 |
|---|--------|---------|---------|---------|
| 2 | 免登录设计 | 第 N 行出现 `JWT Token` | 严禁 | 改用 API Key + HMAC 签名或无认证 |
```

**暂停条件**：检查项 2 / 4 / 6 任一不通过 → 必须暂停（这三项属于安全/路径级硬伤）；其余检查项告警但不暂停，附在表中由用户决定是否要求 skill 重新生成。

### Step 1.7.5：★ 需第三方提供接口职责边界回检（仅 HAS_THIRD_PARTY_DEP=true 触发）

> **项目级兜底回检**（约定 21）：SKILL B.7 已规范职责边界但**无核验脚本** → 此处 grep 兜底。⚠️ `check_third_party_dep_reverse.py` 是「依赖反向识别」、**不是**职责边界核验，别拿它顶替。

当 Step 0.4.6 判定 `HAS_THIRD_PARTY_DEP=true` 且本次产出含 `docs/design/detail/{version}/集成对接.md`（或拆分后含「集成」/「对接」字样的分册）时，命令端必须执行以下 5 项硬规范回检：

| # | 检查项 | grep / 判定 | 不通过处置 |
|---|--------|------------|----------|
| 1 | **接口清单存在**：必有「需第三方提供的接口清单」表 | grep `需第三方提供的接口清单` ≥1 次 | 缺失则告警，要求 skill 补齐 |
| 2 | **清单业务诉求导向齐备**：表头含 `序号 / 功能·业务诉求 / 对应第三方功能位置 / 业务数据项 / 调用时机 / 调用量 / SLA / 优先级 / 期望就绪时间 / 反馈状态`（**业务含义表述，严禁出现我方拟定的对方 URL / 字段名 / Method / 响应结构**——依 `code-verification-loop/references/third-party-mock-protocol.md` 一·C「对外提需求=业务诉求」7 项原则，单一信源归属 code-verification-loop）| 表头为业务诉求列（含「业务数据项」「对应第三方功能位置」）且**无 URL/字段名列** | 出现 URL/字段名列或缺业务列 → 标红写入「⚠️ 第三方接口职责边界告警」表 |
| 3 | **不越俎代庖（功能层）**：每个能力描述用业务语言（功能需求/输入业务含义/返回业务含义），**严禁**出现接口路径 / HTTP Method / 请求字段名定义 / 响应 JSON 结构 | grep `集成对接.md`：① `GET\\|POST\\|PUT\\|PATCH\\|DELETE\\s+/` 应为 0 命中；② ```json``` 或 `\\| code \\|\\|.*\\| data \\|` 等响应结构片段应为 0 命中；③ `请求参数:\\|响应结构:\\|响应字段:` 应为 0 命中 | 命中 → 标红，**暂停 Step 2~6** |
| 4 | **失败降级必填**：每个能力必含"失败降级"段 | 解析每个能力段必含 `失败降级\|降级方案` 字样 | 缺失则告警 |
| 5 | **反馈状态合法**：表内"第三方反馈状态"列只能取 6 种 emoji 之一 | 状态列 grep 应只命中 `⏳\|🔄\|📄\|✅\|❌\|⛔` | 非法值 → 告警，要求改正 |

**告警表写法**（追加到 `集成对接.md` 头部）：

```markdown
## ⚠️ 第三方接口职责边界告警

| # | 检查项 | 当前状态 | 期望状态 | 修复建议 |
|---|--------|---------|---------|---------|
| 3 | 不越俎代庖 | 第 N 行出现 `POST /api/payment/query` | 严禁 | 删除路径/Method/字段定义，仅保留业务语言描述 |
```

**暂停条件**：检查项 3（越俎代庖）不通过 → 必须暂停（这是职责边界硬伤，会让我方文档误导第三方）；其余告警但不暂停。

### Step 1.8：★ 上游溯源完整性回检（配合 dev-logic-architect 引用强制规范）

对 `docs/design/detail/{version}/` 下所有 markdown 执行以下 4 项硬规范回检（无触发标志，无条件执行）：

| # | 检查项 | grep / 判定 | 不通过处置 |
|---|--------|------------|----------|
| 1 | **多文件 NN_ 前缀**：若目录下 ≥2 个 `.md`，所有文件名必须以两位数字前缀开头 | `ls docs/design/detail/{version}/*.md` 后逐项 `[[ "$f" =~ ^[0-9]{2}_ ]]` 应全部为真；存在裸文件名 → 违规 | 重命名加前缀；如仍单文件则免检 |
| 2 | **B.1 功规点必含 PRD + 原型来源**：功规点映射段必须标注上游 | 含「B.1 功规点」或「功规点实现映射」章节的文件，每个功规点段必有 `PRD 来源:` 与 `原型来源:` 字样 | 缺失 → 标红，要求 skill 补齐 |
