### Step 2：Architect Agent 补充

读取 `.aidp/agents/architect.md` 获取 Architect Agent 角色定义，对 skill 生成的内容进行补充：

1. **检查数据库基线**：读取 `memory/databaseBaseline.md`，对比已有表
   - 已有表标注为"复用，本次不变更"
   - 新增表加入数据库设计文件（默认 `数据库设计.md`；如本目录已拆分则加入对应分册，如 `01_用户域.md`）
   - 变更表标注为"变更"并说明字段变化
2. **★ 检查架构文档（全目录识别 + 约束三态判定）**：读 `docs/architecture/` 时**全目录扫描**——识别两类文档：
   - **架构约束类**（架构约束.md / 技术选型.md / UI规范约束.md）：按下表三态判定。
   - **架构设计类**（可选）：`架构设计.md`（单文档）或 `架构设计/` 子文件夹（多文档，`00_索引.md`+`NN_*.md`）；存量任意命名的架构设计文档/子文件夹亦识别（详见 `06_版本与用户目录约定.md` §2.1.1）。**存在即作为详细设计的上游输入通读**（整体架构/分层/模块划分/技术选型意图须与本次详细设计对齐）；不存在则跳过、不强制创建。

   约束三态判定（针对约束三件套）：

   | 文档状态 | 判定标准 | 处理方式 |
   |---------|---------|---------|
   | **有效约束** | 文件非空 且 不含「待填充」「待 /sprint-design」等占位标记 且 内容与当前项目相关（非明显从其他项目复制的过期内容） | ★ **设计必须遵循**：详细设计的技术选型、分层、命名、安全等必须符合这些约束 |
   | **空/模板** | 文件为空 或 仅含占位标记（如「（待填充）」「待 /sprint-design 阶段动态填充」） | 跳过约束检查，Step 4 反向填充；**★ 若架构设计文档存在 → Step 4 优先据架构设计派生约束**（见分片 `step-2to4-架构补充与SQL-2.md` 的 Step 4.2） |
   | **过期/不匹配** | 文件有内容但明显属于其他项目（如项目名不匹配、技术栈与实际代码矛盾、日期远早于本项目创建时间） | 视为空模板处理，Step 4 反向填充覆盖 |

   > **★ 仅有架构设计、缺架构约束时的派生（版本规划期）**：若 `docs/architecture/` 下**只有架构设计文档、`架构约束.md` 缺失或为空/模板** → Step 4.2 **据架构设计派生一份 `架构约束.md`**（从架构设计提取分层规则、技术选型、命名规范、安全策略、性能要求等约束条目），再叠加本次详细设计的增量；技术选型 / UI 规范约束同理可据架构设计补足。详见 `06_版本与用户目录约定.md` §2.1.1。

   **过期判定参考**（满足任一即判定为过期）：
   - 文档中出现的项目名与当前 `git` 项目名不一致
   - 文档中的技术栈与 `code/` 下实际脚手架明显矛盾（如文档写 React 但代码是 Vue）
   - 文档「最后更新」日期早于本项目首次 commit 日期
   - 文档中引用的版本号在本项目 `memory/` 和 `docs/` 中不存在

3. **识别公共组件**：分析跨页面的公共 UI 元素，在 `详细设计.md` 中添加公共组件清单章节
4. **追加 ADR**：如有新的架构决策，追加到 `memory/systemPatterns.md`
5. **★ 注入关联文档章节**：在 `详细设计.md` 头部（紧跟「基线引用」之后，正文之前）写入「关联文档」表；其余设计文档（`接口设计.md` / `数据库设计.md` / 各专题 / 拆分后的 `0N_*.md`）同样写入，但内容按各自定位调整。

   **共享模板**（所有设计文档共用，类型特有条目在下方「按文档类型微调」表追加）：

   ```markdown
   ## 关联文档

   > 路径约定：见 `docs/init/06_版本与用户目录约定.md` §4.x「文档内引用路径的写法」（单一信源，本处不复述）。

   | 关系 | 文档 |
   |------|------|
   | ⬅ 上游输入 | `../../../requirements/{version}/研发需求/*.md`；`../../../prototype/{version}/code/`（如有）；`../../../prototype/{version}/mockup/`（如有） |
   | ➡ 下游引用 | `../../../plans/{version}/01_研发执行计划.md`；Sprint 期 `code/` 实现 |
   | ↔ 同版本平行 | 本目录其他 `*.md`（详细设计 ↔ 接口设计 ↔ 数据库设计 ↔ 各专题）；拆分时回链 `00_索引.md` |
   | 🔗 全局约束 | `docs/architecture/架构约束.md`；`docs/architecture/技术选型.md`；`docs/architecture/UI规范约束.md`；`docs/architecture/架构设计.md` 或 `架构设计/`（如有）；`memory/systemPatterns.md` |
   | ⏮ 跨版本前序 | `../{prev-version}/*.md`（如 `{prev-version}` 存在；详见「基线引用」） |
   ```

   **按文档类型微调**（在共享模板基础上 追加/替换 对应行的内容）：

   | 文档 | 关键调整 |
   |------|---------|
   | `详细设计.md` | 「↔ 同版本平行」必须明确列出 `接口设计.md` / `数据库设计.md` / 各专题文件名（不止"本目录其他 *.md"）；如本版本生成了 `*事实清单.md` 也要列入 |
   | `接口设计.md` | 「⬅ 上游输入」尽可能指向 `01_研发需求.md` 的具体小节锚点（如 `../../../requirements/{version}/研发需求/01_研发需求.md#功能清单`）而非整文件；「↔ 同版本平行」必引 `./数据库设计.md`（接口涉及表时）+ `./*事实清单.md`（如存在）+ `./对外开放接口.md`（HAS_OPEN_API=true 时存在）；「➡ 下游引用」加 `code/backend/` 控制器/服务 |
   | `对外开放接口.md`（HAS_OPEN_API=true 时存在）| 「⬅ 上游输入」必引 `01_研发需求.md` 中对外接口章节锚点；「↔ 同版本平行」必引 `./接口设计.md`（内部接口对照）+ `./*事实清单.md`（对外 base 前缀来源）+ `./安全设计.md`（如存在，鉴权/签名/审计联动）；「➡ 下游引用」加 `code/backend/` 对外控制器目录 + `docs/testing/{version}/` 对外接口测试用例 |
   | `数据库设计.md` | 「➡ 下游引用」增加 `docs/deployment/{version}/sql/增量/*.sql`；「🔗 全局约束」增加 `memory/databaseBaseline.md`；「⏮ 跨版本前序」必引 `docs/deployment/{prev-version}/sql/增量/*.sql` + `../{prev-version}/数据库设计.md` |
   | 专题文档（安全/缓存/集成/消息/部署/测试/性能） | 「⬅ 上游输入」必引 `./详细设计.md`；「↔ 同版本平行」回链 `./详细设计.md` 与同版本其他专题文件名 |
   | `00_索引.md`（拆分时） | 「↔ 同版本平行」**逐行列出全部分册**（含简短范围 / 对应 Sprint）；各分册的「↔ 同版本平行」也回链 `./00_索引.md` |
