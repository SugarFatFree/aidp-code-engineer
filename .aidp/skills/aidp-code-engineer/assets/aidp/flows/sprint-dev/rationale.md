# sprint-dev · 理据 / 根因 / 反例（人类维护者用，执行期不加载）

> 本文件承载 `/sprint-dev` 各 flow 段的**理据 / 根因 / 反例 / 历史事故**——对人类维护者有价值、但对执行期模型是噪音（稀释祈使信号），故从执行路径剥离、执行时不加载（见 `.aidp/flows/README.md` 约定 2）。

## 为什么把 Phase 1 开发执行、开发完成后回写外置

`/sprint-dev` 命令主体原 839 行，一次性整份入上下文会触发 README 所述三症（lost-in-the-middle 漏步 / 指令互相稀释 / 满足即止跳步）。两大段——**Phase 1 开发执行（1.0–1.4，约 180 行）** 与 **开发完成后回写（Step X.0.0–X.8，约 270 行）**——都自包含、且只在"真正进入开发/回写时"才需要，故外置为按需加载的 flow 文件：

- `phase-1-dev-1.md` / `phase-1-dev-2.md` ← 原命令 Phase 1 开发执行段（分支 A/B 共用：Sprint 编号置位/范围/目录门/前后端开发/并行），二次切分为两片（-1 = 1.0pre/1.1/1.1.5/1.2 后端；-2 = 1.3 前端/1.4 并行），每片 ≤~15KB。
- `postdev-writeback-1.md` / `-2.md` / `-3.md` ← 原命令「开发完成后：自动回写需求 + 设计文档」段（约定 22 级联 + 约定 25 配置/部署产物），二次切分为三片（-1 = Step X.0.0；-2 = Step X.0–X.7；-3 = Step X.8 部署流程），每片 ≤~15KB。

命令主体每段替换为「关键规则一句提醒 + 骨架表 + Read 指针」，主体压到约 430 行。

## 保留在主体、未外置的段（及原因）

- **顶层规则**（统一决策纪律、参数解析）、**Phase 0B.0 版本落点决策门**（约定 2 关键门、含 3 个 ⛔，最高优先，须常驻）、**Phase 0A.5 死代码扫描**（<100 行）、**Phase 0B.1.1 自动文档增量流**（<100 行）——按 README「≥100 行才外置 / 顶层规则留主体」约定保留。

## 维护

命令主体与 flow 文件必须成对同步；改 flow 后镜像进脚手架 bundle `assets/aidp/flows/sprint-dev/`（`scaffold.py::sync_gated` 下发）。

## Sprint 编号为何必须跨版本扫（路径不得带 `{version}` 限定）

Sprint 编号是**项目全局流水号**、跨版本连续自增（`06_版本与用户目录约定.md` §3.3）。

曾经的写法是扫 `memory/{version}/{user}/sprints/` 与 `docs/plans/{version}/01_研发执行计划.md`——
**两个路径都带 `{version}` 限定**。新版本刚建时这两个目录天然是空的 → `MAX=0` →
新版本又从 `sprint-001` 起（下游实测问题），于是同一项目里出现多个 `sprint-001`，
归档目录、Sprint 记录与提交历史全部对不上号。

正确做法：用 `check_sprint_numbering.py next` 子命令**跨全部版本**扫
`memory/*/*/sprints/` + `docs/plans/*/…研发执行计划.md` 取 MAX+1。
`/sprint-full` 有同一处判据，两边必须同源。

## Step X.0.0 步骤 3.5 改动量档位门（`dev_scale`）的动机与硬边界成因

**动机（下游实测）**：某 Sprint 只改 **2 个前端文件**（两个 `v-if` + 一个 emit），却配套产出
**16 份文档改动、1139 行新增、耗时 23 分钟**，其中约 80% 花在写文档上——代码本身 3~5 分钟。
小改动上投入产出严重失衡，故设本门让级联的**承载形态**按改动量伸缩。

**为什么只能伸缩承载形态、绝不能砍级联本身**：同一轮下游实测里有 **3 个「静态检查全绿、
只有运行时才炸」的缺陷，其中 2 个是写文档对照设计时发现的、不是写代码时发现的**
（聚合改造后 `skuId` 恒 `undefined` → 开通链路整条不可用；增购计价数据源失效 → 取到别的规格订单
**算错价**）。二者 `vue-tsc` 与 eslint **全绿**，靠的就是级联时逐条对照设计的连锁点清单。
故正文把 L4 自测用例（反向断言载体）、L1 需求留痕、约定 22 检测项清单与触发级别判定
钉成任何档位都不裁剪的硬边界，可省的只有"另起分册 + 重复索引登记"这类承载开销。

## S（语义子档）为何存在：`HAS_SEMANTIC` 布尔化的代价

原判据把 `HAS_SEMANTIC` 当成一个**布尔**、命中即抬出 S 档，于是"一个展示占位值从 `—` 改成 `0`"
与"新建一个业务域"落进同一档。

**下游实测一轮**：**6 个正式代码文件、零建表、零 SQL、零配置项、零新增端点**，有效代码新增
约 440 行（含 228 行单测）另有净减 70 行；按规模本该接近 S 档，**只因"有语义口径变更 +
接口出参值域扩充"两条升到 M**，结果产出 **762 行**四层规划文档 + 分散 8 个文件的级联订正，
文档:代码 ≈ **5:1**。

语义变更的影响面**明确、可枚举**——真正该管的是"有没有逐条清算"，不是"要不要另写一套册子"。
故拆出 S 语义子档：**降承载形态、不降级联保证**，用强制的「受影响结论清单」把
"文档详略"与"级联完整性"这两件被绑在同一档位上的事**解耦**。

同一个教训此前已在 `THIRD_PARTY` 上吃过一次——布尔化会把"只消费既有上游新加的字段"
误升到 L，故那条改成了四值。本条是同构修复。

## 计划增量为何必须独立一步（不能并进「设计补充」那一步）

`/sprint-design` **不产研发执行计划**——它全文不涉及 `dev-execution-planner`，
补充模式产物只有 详细设计 / 接口设计 / 对外开放接口 / 数据库设计 / DDL SQL 五类。

把"计划增量"一并挂在设计那一步的后果是**无人生产**：下方硬门第 6 项是
「不可 N/A 的必 Pass 项」，于是恒 Fail → 无人值守下按"重跑仍 Fail"走熔断冻结。
一个纯编排疏漏，最终表现成"版本被冻结"，排查方向完全被带偏。

**即便临场改为直调 `dev-execution-planner` 兜住也不行**：会绕过 `/sprint-plan` 的
Step 1.5 三脚本回检、Step 1.6 SQL 路径回写、Step 2 关联文档注入。
必须走命令编排、不得直调 SKILL。
