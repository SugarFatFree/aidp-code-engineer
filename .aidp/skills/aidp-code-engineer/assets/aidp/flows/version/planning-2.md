**2.3.2：★ 散落 PRD 自动归位（防止用户散落 PRD 文件到 `requirements/{version}/` 顶层）**

用户常把产品提供的 PRD 文件（如 `v0.5.2.md` / `v0.5.2.docx` / `接口文档-xxx.md` / `media/` 资源目录）直接放在版本目录顶层。命令端**必须**自动检测并归位到 `产品提供/`，否则下游 sprint-requirements Step 0.1 扫描 `产品提供/**/*.md` 会找不到走兜底失败：

```bash
# 把 docs/requirements/{version}/ 顶层散落的产品文档 / docx / pdf / media 移到 产品提供/
cd docs/requirements/{version}
shopt -s nullglob
for f in *.md *.docx *.pdf *.doc; do
  # 保留 README.md 在版本目录顶层（项目说明），其余产品文档归位
  [ -f "$f" ] && [ "$f" != "README.md" ] && mv "$f" 产品提供/
done
# media/ 图片资源目录（产品文档常见的图片附件）一并归位
[ -d media ] && [ ! -d 产品提供/media ] && mv media 产品提供/
cd -
```

**归位规则**：
- 归位到 `产品提供/`：`*.md`（除 `README.md`）/ `*.docx` / `*.pdf` / `*.doc` / `media/`
- 保留在顶层：`README.md`、`产品提供/`、`研发需求/`（输入快照 `.aidp-inputs-snapshot.json` 已迁至 `memory/{version}/`，不再落需求目录根）
- 已在 `产品提供/` 的不重复处理

**输出**：终端打印归位行数：`📦 已归位 N 份产品文档到 产品提供/`

### Step 2.4：协调调用四个文档生成步骤（★）

> **★ 串联场景铁律（必须传递给每个子命令）**：上游来源文件（PRD / 原型 / 研发需求 / 详细设计 / 研发执行计划）在本项目 `/version` 串联场景下**齐全可用**。各子命令在调用 SKILL 时必须**额外追加"项目级 prompt 增强"**（详见各 sprint-* 命令文档），强制 SKILL 在产出每个 REQ / 数据表 / API / 功规点 / Task / 测试套件段都标完整的上游引用四源/五源；引用密度 < 100% 即 SKILL QR 不通过。这是因为 SKILL 独立使用时上游不一定齐全，规则强制度有"模糊度"，但本项目串联场景下必须强制 100% 落实。每个子命令在调用 SKILL 前**必须**完成下列动作：
>
> 1. 显式确认上游产物存在（bash `[ -d ... ]` 核验）
> 2. 把 prompt 增强段（"调用约束 + 引用铁律"）作为 system prompt 追加给 SKILL
> 3. SKILL 落盘后跑命令端 grep 兜底核验，引用密度 < 100% 暂停并要求 SKILL 重写

**版本规划的核心产出由四个 skill 调用串联完成**（研发需求 → 详细设计 → 研发执行计划 → **研发自测**；研发自测方案 + 自测用例 + 测试环境与账号由 **Step 2.4.3.5（`planning-3.md`）显式调 `/sprint-selftest`** 生成——研发自测已从 `/sprint-plan` 抽出为独立命令、与前三类对称，用显式独立步骤杜绝“主动收尾跳过自测”的高频问题）：

| 模式 | Step 2.4.1 | Step 2.4.2 | Step 2.4.3 | Step 2.4.3.5 |

| fresh（情况 A） | /sprint-requirements 全量 `[--unattended]` | /sprint-design 全量 `[--unattended]` | /sprint-plan 全量 `[--unattended]`（研发执行计划）| /sprint-selftest 全量 `[--unattended]`（研发自测方案 + 自测用例 + 测试环境与账号）|

#### Step 2.4.0：★ 生成输入变更摘要（仅补充模式 B-2 执行）

> ★ **必做前置（补充模式起点）**：在调用任何 SKILL（Step 2.4.1）**之前**先 `touch /tmp/skill_start`——它是本轮 SKILL 产物的**时间基线**，Step 2.4.4 命名归一靠 `find -newer /tmp/skill_start` 只挑本轮新产物；**缺这个 touch 则 `-newer` 报错被吞、`SRC` 恒空、补充文件命名归一静默失效**。

#### Step 2.4.0.8：★ 上游契约待确认点前置提取（fresh / 补充**两种模式都执行**；非阻塞）

**动机**：本版依赖的**上游契约判据**（第三方/兄弟系统的字段语义、状态取值域、失败分类、
空值约定、哪些字段无落库保证）几乎**没有一条能靠读本方代码得出**——必须问上游。而它们
又**直接决定需求怎么写**。串行等回复不可接受，写完再问则必然返工：下游实测一版因此吃了
两批订正 + 一次子 Agent 返工，其中一条是"上游状态字段其实是三态、判定必须用 `!= ADDED`
而非 `== PENDING`"，需求全写完才拿到。

**本步只做一件事：把等待时间与生成时间【重叠】。** 提取 + 发出，**然后立刻继续 Step 2.4.1，
⛔ 不等回复、不阻塞链路**。

**1. 提取**（扫 `产品提供/**` PRD + `docs/prototype/{version}/`）——只收**四类**、其余不进：

| 类别 | 典型问法 |
| :- | :- |
| **取值域** | 该状态字段到底几个取值？有没有"缺省 / 字段不存在"这种第三态？ |
| **失败语义** | 失败分几类？各类的落库形态一样吗？ |
| **空值约定** | 这个 id 恒空吗？空代表什么？能否据它加总？ |
| **契约强度** | 这组字段是服务端保证的契约，还是运营人工维护、无落库保证？ |

> ⛔ **不收**「本方自己能定的事」（交互细节、文案、样式）——那是 `99_待澄清问题清单.md`
> 的 `Q-NNN` 管的，混进来会让本清单变成第二份待澄清清单、失去"必须外部才能答"的锐度。

**2. 落盘**：`docs/requirements/{version}/_上游契约待确认.md`（`_` 起头 = **过程文件**，
同族增量册 `_开发期{族}增量.md` 的定位：不占 `NN_` 序号、不进 `00_索引.md`、不是交付物）。
每条一行：`U-{NNN} · <上游系统> · <一句话问题> · 影响到的 REQ/页面 · 提出时间`。

**3. 立即发出**：按项目既有的三方协同渠道发（留言簿目录 / 对外需求文档 / 群播报，
有哪条用哪条；**都没有则只落盘 + 在本步打印提示由人转发**，⛔ 不为此新造渠道）。

**4. 回复到达后**：按约定 22 级联（多半是 L1 需求 + L4 用例）；该条**并入
`99_待澄清问题清单.md` 留痕后从本文件删除**，**清空即删文件**——与台账同一套精神，
"文件存在"本身即等于"还有没答的外部依赖"。

**5. 版本发布期**：本文件若仍存在 → 其残余条目转记 `docs/audit/{version}/发布欠账.md`
后删档（与 Step 3.3.9.5 处置台账同一动作，一并做，不单设步骤）。

**打印**：`📮 上游契约待确认：提取 N 条（已发出 <渠道> | 待人工转发）→ 不阻塞，继续 Step 2.4.1`。
