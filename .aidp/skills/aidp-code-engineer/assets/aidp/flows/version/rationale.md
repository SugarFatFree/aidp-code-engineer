## Step 2.7.3 为何放在规划期（而不是发布期）

Step 2.7 刚把「当前版本」写进项目记忆文件（`AGENTS.md` / `CLAUDE.md`），但那只是**文档侧**的版本。
代码侧自报的版本（`pom.xml` `<version>`、`package.json` `"version"` …）若不同步，整个开发期
构建出的制品都还挂着**上一版**的版本号——开发期部署、测试期 `/health` 自报、CICD 产物命名
全部对不上，一路漂到发布期 Step 3.3.13 才被发现，那时改就得再走一次 bugfix + 重新部署。

## Step 2.7.3 默认档为何可以无人值守直接改

构建描述符里的版本**就是制品版本本身**，纯机械、无业务语义；且本步在规划期（不是打 tag 前一刻），
后续整个开发 / 测试周期都能暴露问题，还有 Step 3.3.13 复核兜底。这与 Step 3.3.13
「无人值守绝不自动改」并不冲突——那条约束的是**代码常量类**落点，正是本步 scope 外那档。

## 收口后台账为何要有机器门、且版本级收口为何是"必删"（Step 2.7.4 / 3.3.9.5）

"成功级联即删、清空即删文件"写了三处（台账详规「清理规则」+ 本命令两个收口点），但三处
**全是纯文字**——执行体级联完把台账留着，规划期与发布期都照样通过。于是台账跨版本堆积：
同一条信息既在正式文档里、又在台账里，下一次收口还得重新判断"这条到底级联过没有"，
正是详规明令要杜绝的第二份信源。

机器门补上后还剩一个口子：判据若写成"文件存在 ⟺ 确有未决条目"，"还有失败条目"就成了
把台账留到下个版本的合法理由——而**版本规划与版本发布恰恰是不允许把账带走的两个点**：
规划期要给新版本一个干净起点，发布期发出去的版本目录里不该有任何残留台账。故这两处收紧为
`--must-delete`：**目标版本台账必须不存在，不看内容**；`LEDGER-ARCHIVED` 任何档都不认（标记不替代删除）。

失败条目不会因此丢失，它们只是换了个去处——规划期**迁移进当前版本台账**继续攒批，
发布期**转记 `发布欠账.md`** 由 `--finalize-docs` 驱动补跑。**条目既然已有确定去处，
台账文件就没有任何理由继续存在**；留着只会让同一条目在两处并存，下个收口点又要重新分辨。
`/sprint-batch` 的收口点 4 仍用默认档：那时版本还在开发中，未决条目留到下个收口点是正常节奏。

## 专题级增量为何不够（Step 3.3.11 的 section 级前滚）

3.3.11 的「变更范围增量」原本只到**专题层**：一个专题只要进了 Δ，就从零重新合成整份分册
（读旧全量 + 本版设计 + 全量需求 + 代码事实后重写整个文件）。于是"增量"只在专题**数量**上省，
专题**内容**上一分没省。

下游 V0.13.0 正式发布实测：全量 6342 行，Δ 命中 4/5 个专题，**5245 行（83%）被重新合成**，
只前滚了唯一能靠 git diff 一眼判零 DDL 的那册。该步 41m49s / 551k tokens / 170 次工具调用，
占发布主体 54%、**关键路径 72%**。

**这不是特例**：凡"多域并行的正常版本"——6 个 Sprint 铺满各领域——Δ 都会几乎全覆盖，
增量必然退化为准全量。所以必须再下一层：以旧分册为底本，只重写 Δ 命中的 H2 章节。
机械部分（切段/合并/计数/覆盖率）交 `design_full_rollforward.py`，
语义部分（哪些章节要重写）留给执行体按 Δ 映射判断。

配套的一条同样重要：**覆盖率必须在开工前打印**。否则执行体和用户都要等四十分钟才发现
"这次其实接近全量"，而那时已经没有改主意的机会了。

## Step 3.3.11 增量安全网为何必须额外扫研发需求（git 文件级 diff 的语义盲区）

git 文件 diff **抓不到**「无新增实体的语义/口径/单位/默认值/状态机/权限范围变更
（约定 22 第三类）」与「跨版本需求作废（约定 34 表 F）」——这类改动大面积传播设计，
却**不表现为新增文件**。只按 `git diff --name-only` 算 Δ，它们就会被整批漏掉，
而被漏掉的专题会被"原样前滚"，把已经反转的口径原封不动带进新一版全量设计。
故必须额外扫本版研发需求，命中即把受影响专题强制并入 Δ；落在跨专题共享单元
（公共基础设施 / 基类实体 / 共享 DTO / 全局配置）时保守地把所有引用方并入 Δ。

## Step 3.3.11 全集索引核对为何廉价

它是**成员校验、非重新推导**：只枚举全集代码事实索引（接口签名/路由 ∪ 表 ∪ 模块 ∪
全量需求项），逐项问"在某个 staging 分册里有归属吗"，量级 O(索引) 而非 O(推导)。
所以它可以在每次组装后无条件跑一遍，用来兜住前滚专题不做深核留下的风险面。

## Step 3.3.11 分块 staging 原子替换的动机

早期做法是先 `git rm -r docs/design/detail/全量/` 再整体重生，一旦重生中途失败就会出现
「旧版已 rm、新版没成 → 全量设计凭空消失」。分块产出到 `.全量-staging/`、
全部守恒通过才原子替换，把这个脆弱点堵死：任一块没过就整体保留旧 `全量/`，
交付面永远不会出现空全量。

## Step 3.3.11 section 级前滚为何派独立子 Agent

它是发布期最重的一步，隔离上下文既省主对话、也让守恒核对有干净的判断面
（不被主对话里其它版本的设计片段污染判断）。

## Step 3.3.11 自包含铁律的目标

**拿走整个仓库、只留 `全量/` 目录也能完整读懂本系统设计**——交付 / 新人 / 审计三类读者
拿到的常常只是这一个目录，任何 `../{version}/…`、`docs/requirements/…`、`code/…` 外链
到了他们手里都是断链。

## Step 3.3.11 全量设计为何只跟随正式发布重算

全量设计只跟随正式对外发版更新，避免每次准发布（`--no-tag`，autopilot 无人值守）
都重算一遍——那是发布期最重的一步，按准发布频率跑代价过高而收益为零。

## Step 3.3.11 现状 vs 规范如实留痕的立场

设计快照要反映系统**真实长什么样**，而非它**本应长什么样**。占位桩 / mock 骨架、
`@Deprecated` 废弃接口、违反规范的存量写法一律照实写进设计并标注偏离。

## Step 3.3.11 上游收敛部分失败为何不阻断全量重算

因为**最新代码是唯一事实源**（优先级最高）、全量设计**主要据代码事实生成**、
版本设计只作补充叙述来源。上游 Step 3.3.10 收敛部分失败只影响"补充叙述"这一路输入，
不影响主输入，故不构成整步跳过的理由。

## Step 3.3.13 无人值守为何绝不自动改代码内版本标识

版本常量看似机械替换，但落点可能被业务逻辑读取（如按版本走兼容分支）。
无人值守只负责**让漂移可见且有台账**，不替人做代码决策。这也是本步定 Important
而非 Critical 的原因。

## Step 3.4.2 tag 用小写 v SemVer 风格的由来

采用社区通用 SemVer tag 习惯（如 `git tag v1.2.3`），与本项目的分支命名
（大写 `V0.1.0` / `release/V0.1.0` / `feature/...`）完全隔离——同一 ref 命名空间里
两套风格互不撞名，靠 case-sensitive 天然分开。版本分支保留该版本的发布快照，
便于后续在其上做 hotfix / cherry-pick / 追溯。

## Step 3.4.2.2 移动远端已存在的 tag 为何须先授权

别人可能已基于该 tag 构建 / 部署 / 拉分支，移动它是 destructive 动作。
交互式二选一里之所以给「中止发布、改用新补丁号」这一项：同名冲突多半意味着版本号搞错了，
而不是真要重跑上一次失败的发布。

## Step 3.4.3 为何先判部署形态再监听

`mode=local` / `none` / 未接入 CICD 流水线的项目没有云端流水线可等。缺这道门的后果不是"多等一会"：
其后的 fail-closed 会在 `git push` + `git push tag` **已完成之后** exit 1 —— tag 已推出去，
而 Step 3.5（更新项目记忆文件）与 3.6（发布报告）全都不执行，版本停在"推了 tag、没收口"的半截态。

## Step 3.4.3 发布期为何绝不自动 trigger CICD

发布推送常对应**生产环境**流水线，主动触发是有外部副作用的高风险动作，
必须由用户主动要求才执行 `cicd_watch.py --mode trigger`。

## Step 3.4.4 `git push -f` 被拒时降级删除重推的依据

公司代码平台（GitLab 系）常对已存在 tag 配 pre-receive hook 保护、拒绝强制更新，
但**允许删除后重推**，故降级路径成立。若删除同样被拒（tag 完全不可变策略），
就没有自动路径可走，只能转人工。

**降级为什么也要过授权门**：删远端 tag 比移动 tag 更具破坏性——移动还留着一个指向别处的 ref，
删除是把它从远端抹掉。二者同属「已发布出去的东西不被静默改写：改写须用户显式授权」的授权面（移动/删除 tag、补跑改写已发布版本产物、重新发布均在其内）。
授权位跨不过 Bash 围栏，必须从 baseline 的 `release_force_authorized` 读回（Step 3.4.2 已落盘）。

## Step 3.4.2 撞名检测为何必须同时查远端 tag

分支侧一直用 `git branch -r` 查远端，tag 侧只用 `git tag -l` 查本地——这个不对称留下一个
致命缺口：**新克隆 / 浅克隆 / CI runner / 他人已推同名 tag** 时本地恒无该 tag ⇒ `REPUBLISH=0`
⇒ 授权门根本不触发 ⇒ 一路走到 push 被远端拒 ⇒ 落进 Step 3.4.4 的强推与「删远端 tag 再推」。
撞名判定必须在推之前就成立，故补 `git ls-remote --tags`；远端不可达时 `|| true` 退化为
「只按本地判」，而不是让 `set -e` 中断整个发布。

## Step 3.3.13 为何要调脚本写回而非手工逐处改

`check_version_identifier.py --apply` 内含复验归零 + `-SNAPSHOT` 后缀保留 +
Maven 反应堆 `<parent><version>` 连带同步；手工改极易漏掉后两者。

## Step 2.7.3 scope 外落点为何无人值守不改

代码常量 / `application.y(a)ml` / Dockerfile 裸 `ARG VERSION=` 这几类落点**可能被业务逻辑读取**
（按版本走兼容分支），**或根本指的是别的组件**（Dockerfile 裸 `VERSION` 多半是被装组件的版本）。
无人复核时不替人做代码决策，只让漂移可见并交发布期 Step 3.3.13 兜底。

## 强推授权为何必须是独立变量（`FORCE_AUTHORIZED` ≠ `REPUBLISH`）

Step 3.4.2 原先只有一个 `REPUBLISH`：撞名即置 1，随后 `git tag -f` / `git branch -f` /
`git push -f` 三处全部只认它。而「撞名」与「获准强推」是两件事，合成一个变量后：

- **无人值守恒强推**。散文里写着「⛔ 无人值守不得自行强推」，但那句话没有任何一行代码承载它。
  `--unattended` 并不跳过 Step 3.4（只有 `--no-tag` 才跳），于是撞名时照 bash 逐字跑就是
  `-f` 三连——正是散文明令恒不走的那条路径。
- **拒绝无处表达**。即便交互式用户选了「中止发布」并把 `REPUBLISH` 清零，建版本分支那一支
  `[ "$REPUBLISH" = 1 ] || [ -n "$EXISTING_VBRANCH_LOCAL" ] || [ -n "$EXISTING_VBRANCH_REMOTE" ]`
  会仅凭「分支已存在」把它**重新置 1**，tag 强推随之复活。拒绝在控制流上活不到 push。

同一份文件的 Step 3.3.13 是同类门的正确范式（交互式三选一 / 无人值守 WARN + 登记发布欠账），
本门照抄其形态：`FORCE_AUTHORIZED` 默认 0、只由交互式授权就地置 1、未授权即置空
`TAG_NAME`/`BRANCH_NAME` 并登记欠账。另把检测→授权→打 tag→建分支合并进**一个 Bash 块**——
围栏之间不共享 shell 变量，拆开时 `REPUBLISH` 恒取空落 0，把「未授权」与「无冲突」混成同一条路径。
跨块只经 baseline 传递（`release_tag_name` / `release_branch_name` / `release_republish` /
`release_force_authorized`）。

## Step 3.4 各围栏为何自取版本号（⛔ 不得写 `VERSION="${VERSION:?}"`）

`VERSION` 在 `/version` 全链路**没有任何供给点**——`autopilot_tick_flags.py --shell` 只输出
`TARGET_VERSION`，从不输出 `VERSION`。于是 `VERSION="${VERSION:?}"` 是一个**自引用**：
`:?` 在 VERSION 未设时让**整个围栏在第一行就中止**（rc≠0，后面一行都不执行）。

失败形态是"失败伪装成成功"而非报错：Step 3.4.1 中止 ⇒ 发布提交没打；Step 3.4.3 中止 ⇒ 没 push、
没跑推送分类、没进 CICD 监听；而回到 `phase-2.md` 后 `set internal_released_at @now` **照常执行**，
版本翻 S3 退出候选、照发「✅ 准发布完成」里程碑通知。**净效果：产物全留在工作区未提交未推送，
链路与里程碑通知都报告成功，且该版本再不会被重试。**

⚠️ `check_flow_var_refs.py` 抓不到它：`VERSION="..."` 整行被当作本地赋值记入已知赋值集，
看不到 RHS 读的正是同一个未定义变量。

正确写法 = 本块自取：优先用 `{version}` 占位符（`/version` 的版本号实参，文本替换），
未被替换时回落 `baseline_edit.py current-version` / `TARGET_VERSION`，两者都取不到即显式中止。

## Step 3.4.1 的 `git add` 清单为何必须含 `docs/`

3.3.9.5（台账收口，直接改主文档）、3.3.10（`NN_` 增量合并回 `01_` + `git rm`）、
3.3.11（全量设计重算：`git rm` 旧分册 + 生成新分册）**都只改工作区**，落库全靠 3.4.1。

而 3.4.1 原来的清单里根本没有 `docs/requirements/` `docs/design/detail/` `docs/plans/`
`docs/testing/`。更糟的是 **`git rm` 会进索引、改写与新建不会**——于是发布提交里
「旧版已删、新版没成」，`git show <tag> --stat` 呈现的正是 release-6.md 发誓
「绝不出现」的那个空全量，终端却照打「🎉 发布成功」。

`release-5.md` 与 `release-6.md` 都写着「3.4.1 的 `git add docs/` 会兜住」——
**那句 `git add docs/` 从来不存在**。三份分片各自局部推理都对（"我 `git rm` 了，
下游会 add"），错在 3.4.1 owner 的清单从未含 `docs/`：逐段读都合理，顺控制流走一遍才暴露。

配套加了提交后断言（`git status --porcelain docs/` 非空即 exit 1），
让"以为提交了"变成可判定的失败。

## Step 3.3.13 交互式为什么不再三选一

代码自报 `0.12.1` 而 tag 是 `v0.14.0`，**这不是决策、是确定性错误**。原三选一里的
「保持不变」实际是个陷阱选项：选中就产出「构建产物版本 ≠ tag」的不一致交付，
没有任何业务场景需要它。

而本步的定位本就是**兜底复核**——规划期 Step 2.7.3 已经要求改齐了。
兜底动作发现漏网的正确反应是补上，不是回头把已决策的事重新拿出来议。

真实的决策点在**后面一格**：`--apply` 写回之后复检**仍然**不一致——那说明脚本能力到头了
（跨反应堆引用、非常规落点），剩下的只能由人判。问询留在那里才有内容可决策。

**关于中止出口**：原白名单把「选项③中止发布」称作整条发布路径唯一的中止出口。
中止能力不该寄生在一个本该自动化的门上——为了保住出口，这个门就永远自动化不了。
中止是用户随时可用的能力（Ctrl+C / 显式指令），不需要某个门的第三个选项兜着。

## 占位符不能落在命令位

需要由执行体经工具（而非 shell）完成的动作，写进 bash 围栏本就跑不了。
但写成 `<某工具子命令> --commit "$C"` 比写错更隐蔽：那一串**恰好是合法 shell 语法** ——
`<` 被当成输入重定向、`>` 被当成输出重定向，于是 `bash -n` 通过、`check_flow_bash_syntax.py`
的占位符中和也通过，两道门都报绿。运行时它只会新建一个名为 `--commit` 的空文件，
真正的命令一次没跑、下游取到的值恒空，依赖它的重试链在这里静默断掉。

判据已加进 `check_flow_bash_syntax.py`（`placeholder-in-command-position`）：只判**命令位**
（行首、或仅隔着 `VAR=值` 环境前缀）的尖括号占位符；参数位/值位的 `<...>` 是正常模板写法，
判它会满屏假红。

## baseline 归档为什么用「墓碑」而不是删节点

`memory/.sprint-autopilot-baseline.json` 只增不减（下游实测 80KB / 16 个版本，`versions` 段
占一半，其中 9 个早已发布的版本永不再读），而每次 `baseline_edit.py` 都要持 flock
**全量读写**它，一次会话 30+ 次。Step 3.5bis 在打完 tag 那一刻把历史明细搬走。

**难点不在搬，在"搬走之后谁会取空"**。按版本号回查 baseline 的读方分两类：

- **`baseline_edit.py get`**：已加归档回落（`load_archived_node`，`--build` 形态一并覆盖），
  主文件取不到就去 `memory/.aidp-baseline-archive/baseline-<V>.json` 读，取不到才回默认值。
- **`jq -r '.versions."<V>".…'` 直读**（`phase-2.md` / `phase-3-4.md` / `phase-0-6.md` 等）：
  **拿不到任何回落**。它们的版本入参恒是 `TARGET_VERSION` / `PRE_RELEASE_VERSION`，
  所以归档面必须把**最近两版**整个排除在外 —— 这正是 `--keep 2` 的由来
  （留 1 版不够：Phase 2 的准发布双门读的就是上一版）。

即便如此也不能整段删。Phase 0.3.3 状态机**按 S0→S4 顺序、首个命中即生效**：

    S2 = 计划在 + 所有 Sprint ✅ + `versions.<V>.internal_released_at` 为空

`internal_released_at` 取空 ⇒ 一个早已 tag 发布的版本重新命中 S2（S4 排在它后面、轮不到），
被选成 `PRE_RELEASE_VERSION`，autopilot 下一 tick 对它再跑一遍准发布归档；`current-version`
的排除条件同样建立在它身上。**"数据还在但机器读不到"比不归档更糟，且全程零告警。**

故保留「墓碑」：`KEEP_KEYS` 里全是有确定读方的标量（状态机判据 / 选版判据 /
`/sprint-batch` step-6b 的体系判据 / Phase 2 双门的 jq 读点 / build 发号连续性）。
反过来，**没保留的键恰恰应当读空**——`run_state.next_phase`、`auto_fixable_pending`
是 0.3.4「不论 S 态优先作 TARGET」的两个入口，已发布版本读空正是期望行为。

**顺序也是判据的一部分**：明细**先写归档文件、再把主文件改成墓碑**。反过来一旦中途失败，
主文件已成墓碑而明细无处可读，正是上面要避免的那种不可逆丢失。全部改动在
`LockedBaseline(write=True)` 的同一把 flock 内完成，**不新增锁文件**、不裸 read-modify-write。


## 零残留断言为何要有发布总闸

规划期强制产出的「零残留断言登记表」只增不退；Sprint 收尾只跑「守护面 ∩ 本轮 git diff ≠ ∅」
的那些、其余标 `skipped(out-of-scope)`。这在 Sprint 内是对的——没碰到的面不必每轮重跑。

但如果**发布期也接受 `skipped`**，整张表就在测试期和发布期**都没有消费入口**：
每一轮都合法地跳过一部分，而没有任何一个时刻要求它全跑一次。结果是规划期强制产出的基线
产出即沉睡（约定 33 要防的正是这个形态）。发布是唯一"这一版不会再变"的时刻，
也就是唯一能要求全跑的时刻，所以总闸设在这里、且不接受任何 `skipped`。

## 推送口径为何从 baseline 读回

Step 3.4.2 与 3.4.3 是**两个独立的 Bash 围栏**，shell 变量不跨围栏存活。
靠变量传 `REPUBLISH` 的后果不是报错而是静默落默认值 0 —— 于是 tag 撞名时，
「未授权强推」和「根本没撞名」走进同一条路径，两种完全不同的情形在输出上无法区分。
`-f` 的唯一通行条件 = 撞名 AND 已获显式授权；未授权时 `TAG_NAME`/`BRANCH_NAME` 已被置空、整段跳过。


## push 失败为何必须显式分流

Step 3.4.3 的围栏没有 `set -e`，而 `git push` 失败只会留下一个非零 rc 然后**继续往下跑**。
下一行 `PUSH_COMMIT=$(git rev-parse HEAD)` 取的是**本地** HEAD，于是后续 CICD 监听、就绪探针
全都拿着一个**远端并不存在**的 commit 去比对——它们比的是本地事实，所以一路全绿，
最后宣告"发布完成"。这直接推翻「推送 ≠ 交付完成」。

Step 3.4.4「失败处置」（`release-7c.md`）写得很完整，但它的入场前提是"push 失败"，
而**没有任何语句能产生这个前提** ⇒ 整片处置逻辑不可达。这是"门建好了但走不到"的典型：
文档上看它有两条路径，运行时只有一条。

捕获时用 `if` 而不是 `[ -n "$TAG_NAME" ] && git push ...`：后者在变量为空时整体返回 1，
拿它接 `||` 会把"本轮压根不推 tag"误判成"推送失败"——把一个正常路径变成假红。


## 版本标识三档分流

Step 3.3.13 按「交互式 / 交互式复检仍不一致 / 无人值守」三档分流，而不是一律问人或一律自动改：
交互式下脚本能自动修就自动修（打印逐处 `旧值 → 新值`，改动交 3.4.1 一并提交），
`--apply` 后复检仍不一致才轮到 `AskUserQuestion`——脚本已尽力，剩下只能由人判；
无人值守则 **WARN + 自动登记欠账**、⛔ 不自动改代码（没有人复核，改错了没人发现）。

**Step 3.6 报告必须体现**：对齐 → 一行「✅ 代码内版本标识 N 处均与 {version} 一致」；
不一致 → 「⚠️ 版本标识漂移 N 处（已自动修正 / 已登记欠账 / 用户确认保持）」+ 逐处定位。
⛔ 报告不写等于这道 Important 级检查跑完就蒸发。

## 输入快照为什么必须含第三类 `code_files`

补充模式（`planning-1.md` Step 2.0 第 2 条）一直在算「代码变更清单」并把
`{code_diff_files}` 传给 Step 2.4.0 —— 判定侧是齐的。缺的是**基线侧**：
Step 2.7.5 此前只写 PRD 与原型两类，于是那份比对永远拿一个空基线去比，
`code_diff_files` 恒空、`/sprint-design` Step 0.3 四象限的「③ 代码超前-补写」恒不触发。

后果不是"少查一项"，而是「PRD 没动、原型没动、但代码已经把设计里的事实改掉了」
这一整类漂移被 `/version` 判成 fresh 无变化，四份上游文档原样通过 ——
**代码单边成为真相**，而这正是「文档之间不存在单边真相」这条设计目标要堵的形状。

取值刻意不逐文件 hash 整个 `code/`：大仓会很慢，而 `code_inventory.json`
本就已经把设计关心的那些事实（控制器 / 实体 / 路由 / 页面 / SQL）摘了出来，
它的内容变了就代表事实变了。清单文件不存在时记 `unavailable` 而不是空 ——
「没采到」与「代码没变」必须可区分，否则又是一个「做了与没做同形」。
