### Step 3.3.5：生成/追加 版本更新日志.md（简明版本更新日志，文件位于项目根目录）

**目标**：在项目根目录 `版本更新日志.md` **两处写入**（顶部版本概览表 + 下方详情区块）本版本条目，简明记录本版本相对**前一已发布版本**的新增功能与修复的问题；条目控制在一页内可读完，不展开实现细节。

**前置数据采集**：
- 前一版本 `{prev-version}`：按「tag 风格识别约定」取最新已发布 tag 并归一为 `V*` 形式；首次发布则记为 `（首版）`
- 新增功能来源：`memory/{version}/*/progress.md` 的「功能模块完成状态」/「Sprint 列表」摘要
- 修复**候选集**来源：`docs/bugfix/{version}/bugfix-*.md` 状态为「已修复 / 已验证」的条目
- 兜底/补全：`git log {prev-version}..HEAD --pretty=format:'%s' | grep -E '^(feat|fix)\('`，`feat(*)` 归入新增；`fix(*)` **只取候选集**，⛔ **不得直接把 `fix(` 提交等同于对外修复项**——该前缀只说明提交类型，不说明这个缺陷对使用者存在过
- **两类候选都必须逐条过下方「修复段准入判据」才能进 🐛 修复段**


**★ 修复段准入判据（逐条过，不靠印象）**

更新日志是**给使用者读的**。列一条「修复了 X」等于告诉他「你之前遇到的 X 现在好了」——而本版新功能自己引入、又在本版修掉的缺陷，**带 bug 的那版根本没发出去**，使用者从来没遇到过 X。

> **准入判据（唯一）：该问题在上一个已发布版本中真实存在，且使用者可触达。**

判定方法 —— 对每条候选修复，查「被修的那个东西是哪个版本引入的」：

```bash
PREV_TAG=$(git describe --tags --abbrev=0 2>/dev/null)   # 上一个已发布 tag
# ① 被修的文件是哪次提交新增的
git log --diff-filter=A --pretty='%h %ad %s' --date=short -- <被修文件>
# ② 被改的那段代码/文案何时引入（比 ① 更准，能穿透文件重命名）
git log -S "<被删掉的那段原文>" --pretty='%h %ad %s' --date=short -- <被修文件>
# 引入点晚于 $PREV_TAG ⇒ 本版自产自消 ⇒ 剔除
```

三条边界规则（缺一会判错）：

| 情形 | 判定 | 理由 |
|---|---|---|
| 根因是历史代码，但**暴露面**是本版新功能 | **剔除** | 使用者在已发布版本上触达不到 |
| 本版做的修复，但改的是**全局机制**（全局异常处理 / 拦截器 / 公共组件），惠及全部历史功能 | **保留** | 已发布版本的用户真实受益 |
| 本版新增、又在本版删除的功能 | **两段都不进** | 同理适用于 🆕 新增段 |

配套三条：

1. **剔除 ≠ 丢弃**：这些缺陷仍完整留在 `docs/bugfix/{version}/`、Sprint 归档、git log 里供内部复盘与质量度量，只是不进对外日志。
2. **允许修复段很少甚至为空**：功能版本本就可能没有历史欠债要还。⛔ **严禁为凑数把自产缺陷填回去**；为空时写「本版无面向已发布版本的缺陷修复」。
3. **判据不写进日志正文**：准入判据是**编写规则**，不是给使用者看的内容。⛔ 不得在「🐛 修复」段插入「本段只列……」这类解释性文字——日志的读者是使用者，他不需要知道我们怎么筛的，条目本身干净列出即可。修复段为空时也只写一句「本版无面向已发布版本的缺陷修复」，**不附理由**。

⛔ 概览表「🐛 修复」列计的是**过判据之后**的条数——它的真实含义是「清理了多少历史欠债」，不是「这版返工了多少次」。迭代过程不是交付物。

**回检**：`python3 {{AIDP_HOME}}/scripts/check_changelog_fix_scope.py --version {version}`（Important 级、不阻断发布；确属误报用 `<!-- changelog-scope-ignore: 理由 -->` 显式豁免）。

**条目格式**（必须严格遵守，保持简明；每个版本均含"发布时间 + 更新日志"两要素）：

```markdown
## [{version}]

- **发布时间**：{YYYY-MM-DD HH:MM}
- **里程碑**：{里程碑}（相对 {prev-version}）

### 🆕 新增
- 用户登录支持企微扫码
- 订单列表新增「批量导出 Excel」
- ...（每行一句话，禁止贴代码、禁止罗列文件路径）

### 🐛 修复
- 修复批量删除时事务回滚不一致
- 修复菜单缓存在切换租户后未刷新
- ...（过不了准入判据时本段写「本版无面向已发布版本的缺陷修复」）

```

- 发布时间取本次 `/version` 实际执行时刻：`date '+%Y-%m-%d %H:%M'`（本地时区）；若 CI 环境固定 UTC，可改用 `date -u '+%Y-%m-%d %H:%M UTC'`
- `{prev-version}` 来源同前置数据采集步骤；首版填 `（首版）`

**首次创建**（项目根目录 `版本更新日志.md` 不存在时）：先写入文件头 + 版本概览空表：

```markdown
# 版本更新日志

> 本项目所有版本变更记录（含已发布版本的发布时间与更新日志：功能新增 + 缺陷修复），**采用倒叙排列**：最新版本在文件顶部，越往下版本越旧。
> 格式参考 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)，版本号遵循 [SemVer](https://semver.org/lang/zh-CN/)。

## 版本概览

| 版本号 | 发布时间 | 里程碑 | 🆕 新增 | 🐛 修复 | 详情 |
|--------|---------|--------|--------|--------|------|

---

```

然后写入本版本条目（含表格新行 + 详情区块）。

**已存在文件**：执行**双处写入**：
1. **版本概览表**：在表头分隔行（`|-----|`）下方、上一版本行之上插入新行（保持表格倒叙）
2. **详情区块**：在分隔线 `---` 之后、上一版本 `## [...]` 块之前插入本版本完整条目

**排列规则（倒叙 — 强制，两处对齐）**：
1. 版本概览表：表头下第一条数据行永远是**最新发布**的版本
2. 详情区块：第一个 `## [{version}]` 永远是**最新发布**的版本
3. 整个文件呈"最新在顶、最旧在底"的倒叙时间线；**严禁**在文末追加（追加 = 正序，违规）
4. 命令端执行后可用 `head -40 版本更新日志.md` 自检：表头下第一行版本号 == 第一个 `## [` 后版本号 == 本次 `{version}`

**控量约束**：
- 「🆕 新增」与「🐛 修复」每段建议 ≤10 行；超过则只列**用户可感知的**条目，技术性内部改动归并到一条"内部优化 / 重构"
- 单条 ≤80 字符；超过则改写为更简洁的业务语言
- 仅当本版本有对应内容时才出现该子段，整段为空则省略子段标题

**README.md 引用同步**：

写完 `版本更新日志.md` 后，命令端**必须**确保项目根目录 `README.md` 引用该文件：

1. 检查 `README.md` 是否已含 `[版本更新日志.md](版本更新日志.md)` 链接 — 已有则跳过
2. 若 `README.md` 已有 "版本历史" / "CHANGELOG" 章节但引用的是旧名（`CHANGELOG.md`），替换为新链接：
   - 旧文本：`详细变更记录见 [CHANGELOG.md](CHANGELOG.md)（如有）。`
   - 新文本：`完整的版本发布记录（含发布时间、新增功能、修复问题，倒叙排列）见 [版本更新日志.md](版本更新日志.md)。每次 /version 发布会自动追加。`
3. 若 `README.md` 没有相关章节，在文末 `## 📄 许可证` 之前插入 `## 📝 版本历史` 章节，含上述引用
4. `README.md` 已在 Step 3.4.1 `git add` 列表中；若本步骤修改了它，会自动被发布提交捕获，无需额外操作
