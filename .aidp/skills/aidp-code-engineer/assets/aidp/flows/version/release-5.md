### Step 3.3.9.5：★ 收口本版本开发期变更台账（约定 22 攒批级联 · 收口点 3，**必须先于 3.3.10**）

> **单一信源 = `.aidp/reference/开发期族增量.md`**（格式 / 收口执行要点 / 清理规则全在那份）。
> **进入本步第一动作 = Read 该文件**；本处只说明触发、范围与"为什么必须排在 3.3.10 之前"。

> ⛔ **为什么必须先于 Step 3.3.10**：3.3.10 要把 `NN_<业务主题>.md` 增量**合并回主文档**、
> 并做整个发布期唯一一次「清除废弃/延期需求」的全局清理。台账里的待级联项此时**还没进主文档**——
> 先跑 3.3.10 再收口，这批内容就赶不上那次全局清理。**顺序错 = 发布出去的文档不全。**

- **触发**：本版**四族任一**增量册（`docs/requirements/{version}/研发需求/_开发期需求增量.md` · `docs/design/detail/{version}/_开发期设计增量.md` · `docs/plans/{version}/_开发期计划增量.md` · `docs/testing/{version}/研发自测/_开发期用例增量.md`，外加存量单册台账）存在且有「待级联」条目；四族全无 → 打印 INFO 跳过。
  路径与条目解析一律走 `commit_gate.cascade_ledger_paths()` / `pending_cascade()`，⛔ 不自拼路径。
- **范围**：**当前版本全部**待级联条目 —— **必须清空**，⛔ 不得带着待级联项发布。
- **动作**：派**独立子 Agent** 读台账 → 结合代码现状核实（被后续改动推翻的条目直接删、不产文档）→ 合并同类项
  → 按合并后总量重判档位 → 跑四级级联 **直接写进各族内容主文档正文**（⛔ 不产中转增量册、不新建分册）。
- **★ 清理（必定清理，⛔ 不存在要保留的场景）**：本步结束时**本版本台账文件必须已删除**——
  发布出去的版本目录里不留任何残留台账。
- **失败处置**：任一条级联失败 → **条目全文转记 `docs/audit/{version}/发布欠账.md`**
  （步骤=Step 3.3.9.5，逐条写明编号/原文/失败原因，补跑命令 `/version {version} --finalize-docs`）
  **随后照样 `git rm` 台账**——⛔ **不许**把失败条目留在台账里当"下次再说"，欠账台账才是它们的去处；
  **不阻断发布**（Important 级，同 3.3.7/3.3.10/3.3.11/3.3.13 口径）。
- **★ 终态机器门（确定性，不通过不得进入 3.3.10）**：
  ```bash
  # ★ 落点门（模式 A）与终态门并列跑（二者正交，见 planning-8 同款注释）
  python3 .aidp/scripts/check_cascade_landing.py --worktree --version {version} || exit 1
  python3 .aidp/scripts/check_cascade_landing.py --must-delete --version {version} \
    --transfer-to docs/audit/{version}/发布欠账.md
  ```
  ① 断言**本版本台账不存在**，无任何例外（有未决条目、打了 `LEDGER-ARCHIVED` 一律判失败——标记不替代删除）；
  ② **配套断言转出到位**——从 git 取回被删的那份，若删前仍有 N 条未决，则发布欠账里必须
  写明它们（含来源版本号），否则判 `deleted-without-transfer`。**必删 ≠ 把账删没**。
  **门失败按上条失败处置**（登记发布欠账、不阻断发布），但**不得当作通过**。理据见 `rationale.md`。
- **打印**：`📋 本版本攒批级联：处理 N 条（成功 M / 失效 K / 失败 J）→ 已写入各族主文档；台账已删除；J 条未决已转记 发布欠账.md`（**台账恒为已删除**，无「保留」分支）。

### Step 3.3.10：★ 版本规划文档整合（补充合并回主文档 + 去除补充痕迹 + 清除废弃/延期需求）

> **★ 本步只处理一种增量形态**：**`NN_<业务主题>.md`** —— 产品侧 PRD/原型变更与 `/sprint-dev` 口述累进产出，
> `00_索引.md` 类型=补充、append-only，在本步**文件级**合并回 `01_` 并 `git rm`。
> ⛔ **开发期约定 22 级联的内容不在本步处理**——它在收口时就**直接写进主文档**了。
> ⛔ 某族没有 `NN_` 补充**也不能就此判「无需整合」跳过本步**——本步第二件事「清除废弃/延期需求」
> 是整个发布期唯一一次全局清理，与有没有补充无关，**必须照跑**。

**目标**：把 4 类版本规划文档 + `docs/references/{version}`（版本专属对外需求）**共 5 个收敛目标**收敛成**只反映本版本实际交付内容**的干净版本——两件事：① 开发期各级产出的增量文档 `NN_<业务主题>.md`（文件名无"补充"字眼，`00_索引.md` 类型=补充）是 **append-only 增量**（不改内容主文档正文、靠 `00_索引.md` 登记 +「结论取代」串联），发布前**全部合并回 `01_` 内容主文档**（应用结论取代、失效增量丢弃）+ **`git rm` 已合并的增量文件 + 刷新 `00_索引.md`**（移除已合并增量行、保留主文档行）；② **清除废弃 / 延期的需求**——版本规划期标了后来又决定不做（废弃/作废）或移到后续版本（延期）的需求，发布时从版本文档里**整条删除**（连带其设计/计划/用例/对外需求产物），让发布出去的文档规范、完整、无碎片、无"画了饼没交付"的残留。落地约定 22「发布期收敛」。

**执行时机**：Step 3.3.9（`release-4.md`；references 归档 + 已满足标注）之后、Step 3.4.1（`release-7.md`；发布提交）之前**自动执行**（与 SQL 整理 Step 3.3.7（`release-3.md`）同为无人值守友好的发布前整理；`--no-tag` 准发布路径同样执行）。references/{version} 的收敛承接 Step 3.3.9：3.3.9 先标注 ✅已满足 / ⏳待交付，本步再合并补充 + 清废弃/延期（两步互补不重复）。

**5 个收敛目标 + 主文档/补充定位**：

| 收敛目标 | 目录 | 内容主文档（`01_`+，目录含 `00_索引.md`）| 增量（类型=补充）|
|---|---|---|---|

| 详细设计 / 接口 / 数据库 | `docs/design/detail/{version}/` | `01_详细设计.md` / `02_数据库设计.md` / `03_接口设计.md`（历史裸名兼容）| `NN_<业务主题>.md` |
| 研发执行计划 | `docs/plans/{version}/` | `01_研发执行计划.md`（历史裸 `00_研发执行计划.md` 兼容）| `NN_<业务主题>.md` |
| 研发自测方案和用例 | `docs/testing/{version}/研发自测/` | `00_索引.md`（导航锚）+ `01_研发自测方案.md`（方案）+ `02_全量自测用例.md` / `02_自测用例-总览.md` | `NN_<业务主题>.md` |

**执行步骤**（逐文档族循环；某族无补充则跳过、报告标"无补充，跳过"）：

0. **★ 前置：历史格式归一 + 取代链消解 + 编号冲突自动重编（防「格式不规范/编号冲突」直接判失败）**：进入合并前先做三件机械预处理，把不规范存量拉回当前范式再合并——**这是消除「历史格式文档直接触发失败兜底」脆弱点的关键前置**：
   - **① 历史格式归一**（纯 `git mv` + 索引补建，不改正文语义）：
     - 裸名主文档（`详细设计.md`/`接口设计.md`/`研发需求.md` 等无 `00_索引.md`、无 `NN_` 前缀）→ 归一为 `01_<语义名>.md` + 补 `00_索引.md`（记文件清单/生成时间/主·补充标识）；同目录 ≥2 裸名内容主文档按约定 14/15 加唯一两位序号。
     - 旧式增量命名 `NN_补充-<主题>.md` / `<主题>-补充-NN.md` → `git mv` 为 `NN_<主题>.md`（去「补充」字眼，补充身份记入 `00_索引.md`）。
     - 研发自测旧锚 `00_研发自测方案.md`（方案占 `00_`、用例从 `01_` 起）→ `00_索引.md`（导航锚）+ `01_研发自测方案.md`（方案）+ 用例顺延 `02_`+。
   - **② 取代链消解**：一个主题历经多轮「结论取代」修订链（补充 A → 补充 B 取代 A → 补充 C 取代 B）时，**逐条应用至链尾最终结论**——只保留**最终有效结论**并入主文档，链中被取代的中间补充**标失效、整份丢弃**（不并入）。取代关系读 `00_索引.md` 取代列 + 各轮「四、对前序结论的影响（取代判定）」。
   - **③ 编号冲突自动重编**：用例/需求编号跨补充**重复**（如两份补充都出现 `TC-PTS-008`、或需求 `REQ-012` 撞号）→ **自动重编**后来者为目录内**下一空闲编号**（`TC-PTS-008` → `TC-PTS-{max+1}`）并同步更新其被引用处，重编动作记入报告。
   - **失败降级（登记欠账、不阻塞）**：某文件归一/重编无法机械判定（无法确定续编序号 / 取代关系矛盾）→ **该文件登记 `docs/audit/{version}/发布欠账.md`**（步骤=Step 3.3.10 归一），不阻塞其余文档，进入步骤 1 时把它当「未归一项」挂起、不并入。

1. **收集本族增量清单 + 取代关系**：`ls {族目录}/NN_*.md`（排除 `00_索引`/`01_` 内容主文档/`98_`/`99_`；含历史 `NN_补充-*.md` / `*-补充-*.md`）按 NN 升序，凭 `00_索引.md` 类型=补充 的行确认增量身份；读 `00_索引.md` 取代关系列 + 各轮「四、对前序结论的影响（取代判定）」记录（输入变更摘要 `docs/requirements/{version}/研发需求/输入变更-*.md` 或主文档内），标出**哪些增量已被后续结论取代（🔄 失效横幅）**。

2. **合并回主文档（语义改写，逐族委派对应 Agent 保证格式一致）**：读主文档 + 全部**未失效**补充，把补充内容**并入主文档对应章节**（新增接口并入接口章节、新增表并入数据模型、改写的业务规则替换原文等）：
   - **结论取代**：被 🔄 失效横幅标记的补充**整份丢弃不并入**（其内容已被后续补充取代）；只并入每条主题的**最终有效结论**。
   - **★ Mock→真实对接收敛（直接服务诉求）**：补充里"第三方已交付、改真实对接、补后端实现"类结论**取代**主文档原"本期 Mock、不实现后端"段——合并后主文档只留**真实对接方案**（真实端点/鉴权/字段映射/错误码/超时重试），**删掉所有已切真实的 Mock 占位描述**；仍未交付、发布时仍是 Mock 的第三方接口保留 Mock 说明 + `⏳ 待交付` 标注（与 Step 3.3.9 已满足判定一致）。
   - **委派**：研发需求族 → PM Agent（`.aidp/agents/pm.md`）；设计族 + references 对外需求族（同由 `/sprint-design` 生成）→ Architect Agent（`.aidp/agents/architect.md`）；计划/自测族 → 命令端按主文档结构直接改写。大文档（主文档 > 800 行或补充 > 5 份）派后台子 Agent 隔离上下文执行。
   - **产物守恒**：合并后主文档必须**覆盖所有未失效补充的每一个新增项**（接口/表/规则/用例逐条核对，不漏并）；主文档超约定 15/约定 20 行数阈值时按其拆分规则拆分主文档，**不得**因合并而新造"补充"。

3. **刷新 `00_索引.md` + 去除增量指向痕迹**：① 刷新 `00_索引.md`——移除已合并增量的行，只留 `01_`+ 内容主文档行及其最新生成时间（合并后目录里已无增量文件）② 内容主文档正文清除"（补充 NN）""见增量文档"等指向增量的行内引用，改为正文直述 ③ 更新主文档头部「关联文档」表（若增量引入的新交叉引用需保留则并入主表）。

4. **★ 清除废弃 / 延期需求（发布 = 只留实际交付）**：扫**合并后**的 5 个收敛目标主文档，识别**整条**废弃/延期的需求，跨 5 目标**联动整块删除**——
   - **废弃/作废信号**（本期后来决定彻底不做）：`❌ 废弃` / `已废弃` / `作废` / `取消` / `下线` / `不再实现` / `@Deprecated`（接口级）；
   - **延期/延后信号**（移到后续版本）：`延期` / `延后` / `暂缓` / `推迟` / `移至下期` / `移至 V0.X` / `本期整体不做` / `标 V0.X 再交付` / `⏳ 延期`；
   - **联动删除铁律**：删一条需求必须**连带删**它在设计（详细设计章节 + 接口 + 表/DDL）、计划（执行计划 Task）、自测（用例）、**对外需求（`docs/references/{version}/` 提给第三方的需求）**里的**全部对应产物**（按需求 ID / 主题名跨目标匹配），避免"需求删了、Task/用例/接口/对外需求成孤儿"——否则 version-auditor 审计 E 报断链（对外需求↔研发需求/详设的强制引用链见 `06_版本与用户目录约定.md` §2.6）；
   - **★ references/{version} 特有语义**：对外需求**废弃**（我方决定不再需要该第三方接口）/ **延期**（移到后续版本再对接）→ 删；**保留**——① **已满足**（第三方已交付、已切真实对接，Step 3.3.9 标 `✅已满足`）② 本期在范围内、只是仍**待交付**（Step 3.3.9 标 `⏳待交付`）的对外需求，都是本期交付/在范围内容，留；
   - **★ deployment 配置项联动（确认制，不自动删）**：删一条废弃/延期需求时，**扫** `docs/deployment/{version}/配置文件/增量/配置项清单*.md` 里属于它的死配置项（该功能专属的开关 / 第三方端点 / 密钥等，按主题 / key 前缀匹配），**只在发布报告列出"疑似死配置"清单提示用户确认，不自动删除**——配置项删错会导致部署失败、且 key 可能被多功能共享，须人工裁决（与本步其余"自动删"目标不同，配置项走确认制）；
   - **★ 保留（严禁误删）**：① 约定 4 的「原型字段 → 处置」**字段裁剪留痕**（裁剪原因 + 产品确认，是强制留痕、不是废弃需求，留）② 本期**已交付但仍走 Mock**（第三方未交付）的接口——那是本期交付内容，只标 `⏳ 待交付`，不删（见 Step 3.3.9 判定）③ 被「结论取代」**推翻**了废弃/本期不做、现已实际实现的项（如"字段从无到有推翻本期不做"）——现已交付，留 ④ **「明确排除 / 范围外」scope 声明段**（如研发需求里"明确排除：XX 移入 V0.2.0"）——这是本版本**主动划边界的合法文档**、不是漂浮的废弃/延期需求条目，留；
   - **安全边界**：只删**明确标注**废弃/延期状态的项；状态模糊 / 无法机械判定归属范围 → **不删** + 报告列出待人工确认，宁可留错不误删；
   - **延期追溯**：被删的延期需求（含对外需求）在发布报告列出 + 附提示"如需后续实现，请在对应版本规划时重新纳入"（git 历史保留原文，可追回）。

4.5. **★ 文档 vs 已上线代码一致性收敛（默认按代码对齐，堵"取消原因必填性反转 13 处漂移"类高频场景）**：扫本版本「待澄清清单」（`99_待澄清问题清单.md`）「事实清单」（`*事实清单.md`）里登记的**代码/文档差异项**，逐条核验**当前 master 代码事实**（★ 清单记录的是登记**当时**的代码状态，其后可能已被后续 commit 推翻——必须重新查 `code/` 现状，不按清单旧值判定）：
   - **不一致** → **默认按代码对齐文档**，全链路回改（研发需求正文 + 字段规格表 + 验收测试点 + 详细设计 + 接口 + `*事实清单.md` + 自测用例 + 各层待澄清记录），并在 Step 3.6 发布报告逐条列出；
   - **涉及业务规则实质变更 / 疑似代码缺陷**（非文档滞后、而是代码本身可能错）→ 标「待产品确认」+ 登记 `docs/audit/{version}/发布欠账.md`，**不阻塞发布**；
   - **★ 必须全仓 grep 复查残留**：一处口径常散布 10+ 处文档，漏改即形成新漂移——回改一处后 `grep -rn "<旧口径关键字>" docs/{version}/ docs/requirements/{version}/ docs/design/detail/{version}/` 复查，直到无残留；
   - **★ 先读待澄清清单再动手**（避免"未尽调查即处置"）：`99_待澄清问题清单.md` 里已标「已裁决落地」的项**不再作漂移处理**，只处理真实未收敛项。

6. **发布报告段**：Step 3.6 发布报告新增「版本规划文档整合」段，逐族列：合并了 N 份补充 / 丢弃 M 份失效补充 / **清除了 X 条废弃 + Y 条延期需求（含跨目标联动删除项清单）** / **deployment 配置项清单里疑似死配置清单（待用户确认删除，不自动删）** / 主文档是否拆分 / 已 `git rm` 的补充文件清单 / 待人工确认的模糊状态项；无补充无废弃延期的目标标"无需整合"。

**失败兜底（★ 项级粒度，非整族放弃 + 待人工合并清单 + 欠账登记）**：把原「某族失败 → 整族保留不动」细化为**项级**，消除「个别项不规范拖垮整族」的脆弱点——
- **能机械合并的项先合并**：族内逐条补充项（接口/表/规则/用例）能守恒并入主文档的**先并入**；只有**真无法机械合并的具体项**（守恒后主文档找不到落点 / 语义冲突需人工裁决 / 废弃·延期联动删除会造成引用不一致）才**留该项不处理**，**绝不因个别项失败而回退整族主文档**。
- **待人工合并清单 + 精确定位**：无法自动合并/清除的项**逐项**登记 `docs/audit/{version}/发布欠账.md`（步骤=Step 3.3.10，格式见「发布期整理欠账台账」段）——族/文件/章节/编号 + 无法合并原因 + 建议处理方式 + 补跑命令 `/version {version} --finalize-docs`；**不整段放弃**。
- **删除守恒（文件级）**：`NN_<业务主题>.md` **全部项并入才 `git rm`**，尚有残留项则整份保留。⛔ 不得因为"大部分并完了"就整份删掉——那 2 条没并进去的会随文件一起消失。⚠️ **历史遗留形态**：旧版本目录里若存在 `_开发期{族}增量.md`，按**条目级**处理（成功并入的条目逐条删、清空即 `git rm`）——⛔ 不得对它套用文件级守恒：一份增量里 18 条合并成功、2 条待裁决时若整份保留，那 18 条就成了与主文档并存的第二份信源。两种粒度都杜绝「删了但内容没进主文档」。
