# 开发期族增量册 — 攒批级联机制（约定 22 的执行形态，单一信源）

> AIDP 查阅型资料分片（非 @import、不常驻、按需 Read）。各收口点（清单见下方「收口点」表）与 `/sprint-dev` Step X.0.0 都引用本文件，规则只此一份。

## 一、解决什么问题

约定 22 的四级级联（研发需求 → 详细设计 → 研发执行计划 → 自测用例）若**每次开发完当场跑完**，
小改动上投入产出严重失衡——实际项目中：改 **2 个前端文件**（两个 `v-if` + 一个 emit），配套产出
**16 份文档、1139 行、23 分钟**，其中约 80% 花在写文档上；而耗时大头是**生成的文本量**，不是工具调用次数
（同轮对照：55 次调用/23 分钟 vs 纯只读调研 34 次/4 分钟，次数差 1.6 倍、耗时差 5.75 倍）。

**攒批的收益不在"少写"，在"摊薄固定开销"**：N 次小改动各自级联要付 N 份「读上下游文档 + 起分册 + 写文件头 +
关联文档表 + 索引登记」的固定成本；攒成一批只付一份。**每次改动该被记录的信息一条不少**，
只是从"即时写成正式文档"改为"先记族增量册、后批量成文"。

> ⛔ **本机制不改变约定 22 的任何判定**：检测项清单、四级触发规则、破坏性变更确认门、L4 自测用例必产
> ——全部照旧。变的只是**执行时机**（即时 → 攒批）与**承载中间态**（四族增量册）。

## 二、族增量册（四份，与各族内容主文档同目录）

**落点**（`{version}` 每版一套；多人协作同文件追加）：

| 族 | 文件 | 与谁同目录 |
|---|---|---|
| 需求 | `docs/requirements/{version}/研发需求/_开发期需求增量.md` | `01_研发需求.md` 等 |
| 设计 | `docs/design/detail/{version}/_开发期设计增量.md` | `01_详细设计.md`·`02_数据库设计.md`·`03_接口设计.md` |
| 计划 | `docs/plans/{version}/_开发期计划增量.md` | `01_研发执行计划.md` |
| 用例 | `docs/testing/{version}/研发自测/_开发期用例增量.md` | 既有用例册 |

> **★ 与该族内容主文档【同目录】是刻意的**：收口就是**就地合并**——把增量册的条目并进旁边那本主文档，
> 不跨目录搬运、不新建分册。路径的单一实现 = `commit_gate.py::CASCADE_FAMILIES` +
> `cascade_ledger_paths()`，收口点与两道机器门一律调它，**⛔ 禁止各处各拼一次**（拼错的失败形态是
> **静默漏检**：该扫的文件根本没被看到，输出与"都合规"完全同形）。

**★ `_` 前缀不会被上游命名门拦**：`docs/requirements/{version}/研发需求/` 与
`docs/testing/{version}/研发自测/` 受上游 `check_doc_split.py` 的两位数字前缀命名门管辖，但其
`collect_sub_docs()` 明确跳过 `_` 开头的文件（注释原文：「`_` 前缀是开发期过程性文件，不属于交付子文档，
不参与任何拆分判定」）。三份副本（dla / ule / dep）**都有**这段豁免，已实测（含阳性对照：同目录放一个
裸名 `.md` 立刻判 error，放增量册不判）。

### ★ 通则：`_` 前缀文件**永远不是**用例源 / 文档源，任何发现型 glob 都要排除

四族增量册与该族交付文档同住一个目录，于是**每一处"找用例 / 找文档"的 glob 都必须把它排除掉**。
⛔ **黑名单式 glob 是这条通则最容易翻车的地方**——`-not -name "00_索引.md" -not -name "99_*" …`
逐个点名排除时，新来的 `_开发期*.md` **一条都不命中**，于是被当成交付文档收进去。
（实测：`/sprint-aiauto-test` 的 `DEV_CASES`、`/sprint-batch` Step 6 的 `DEV_HAS`、
`/sprint-test` 的 `DEV_CASES` 三处都会误收；其中 `DEV_HAS` 是**存在性判据**，
增量册一在"有没有用例册"就恒真 —— 零用例也判成"用例齐备"。）

**统一口径：所有此类 glob 一律带 `-not -name "_*"`**（脚本侧对应 `not f.startswith("_")`）。
上游 `check_doc_split.py::collect_sub_docs` 与本项目 `check_testdata_prereq.py` 已是同一口径。
机器门 = `python3 .aidp/scripts/check_underscore_glob.py`（扫四族目录的发现型 glob 是否漏排 `_*`）。

**★ 不带 `NN_` 前缀**：增量册是**级联完即删的临时中间态**、不是交付文档序列的一员；带上会被
`00_索引.md` 当内容主文档登记（删文件时还得回头删登记行）、被按内容主文档规则校验、并占用序号空间。

- **不登记进 `00_索引.md`**（它不是交付物，且随时会被删）。
- **不参与** Step X.0.0 的共享 `NN` 锚定扫描、不参与重号/dedup/拆分判定。
- 与 `docs/testing/{version}/研发自测/99_待澄清问题清单.md` 无关（不同用途）。

### ★ 为什么是四份，不是一份

**一份的版本试过，问题出在收口那天。** 单册只记「改了什么」，收口时子 Agent 是**全新上下文**，
必须重新推导「这条变更对需求/设计/计划/用例各自意味着什么」——而那正是固定开销里最贵的一段。
拆成四族之后，**推导发生在变更当下**（刚改完代码、知道为什么，几乎免费），收口从「生成」降为
「合并」，token 量与出错率都显著下降。

配套收益三条：**① 失败隔离**（一族级联失败不拖累其他三族；单册时一条卡住整批留着）
**② 档位可按族独立判**（不会因为总改动量把设计册顶到 L 档）
**③ 可发现性**（四族各自可见；单册时只有 `requirements/` 下有东西，看起来像"只跟踪了需求"）。

代价是开发期从"记 1 行"变成"在受影响的族里各记 1 行"——**只记与本族相关的那一面，
⛔ 不在一族里复述另一族的内容**（复述正是拆分要消除的东西）。多数变更不会四族全中。

### ★ `C-NNN` 编号：版本级、四族共用

同一次变更牵动三族，就在三族册里用**同一个 `C-NNN`**（各记各的那一面）。
⛔ 不要各族各起一套序号——那会让「同一次变更」在收口时无从合并同类项。
取号 = 本版**四族册里现有最大** `C-NNN` + 1（拆分子项用 `C-036-01` 这类子编号）。

**格式**（四族**共用同一套骨架**；多人协作同文件追加）：

> ⛔⛔ **条目格式是【机器判据】，不是排版偏好** —— `commit_gate.py::pending_cascade()` 按下面的
> 形态识别条目（一行式 / `### C-NNN` / 表格首列三种形态，**有内容却一条都认不出就告警**）。
> 自拟其他写法会让它**一条都认不出**：`stale` 恒 0 → 收口点 1 从不触发 → 增量册无限增长，
> 而「没有待级联」与「根本没看见」在退出码上长得一模一样。
> **写入侧一律从 `.aidp/templates/_开发期族增量.md` 拷骨架**（拷到对应落点时把 `{族}` 换成 需求/设计/计划/用例）。

> ⚠️⚠️ **条目只记一行，能省则省**——这是本机制成立的前提。条目若写得详细，记录本身就成了新的耗时，
> 正好抵消攒批省下的时间（攒批要解决的正是"文档写太多"，别在这里把它请回来）。

```markdown
# 开发期{族}增量 — {version}

> append-only：只追加，绝不改删已有条目；收口时成功级联的条目即删、清空即删本文件。
> 条目只记一行：编号 · 时间 · 一句话 · 🔴破坏性 · sprint 号。

## ⚠️ 已知失准点（🔴 条目未级联期间，文档与代码不符之处）

- 🔴 C-008：详设 §4.2 与接口设计 `format` 枚举仍含 XLSX（实际已删）

## 待级联

- C-008 · 08-27 16:05 · 🔴 导出去掉 XLSX 选项 · sprint-012
- C-007 · 08-27 14:32 · 企业列表增加「已停用」筛选项 · sprint-012
- C-006 · 08-26 09:15 · 用户导出新增 CSV 格式 · sprint-011
```

**只记这些**（事后查不到的）：

| 字段 | 为什么必须当时记 |
| :- | :- |
| `C-{NNN}` 流水号 | 引用与去重用；**版本级、四族共用一套序号**，连续自增，跨 Sprint、跨天、跨族均不重置 |
| 时间 `MM-DD HH:MM` | 收口点 1 靠它区分"昨天及更早"与"今天新增"；也是变更顺序的唯一依据 |
| 一句话描述 | **改了什么、为什么改**——`git diff` 只能看出代码变了，看不出意图。这是唯一真正事后查不到的信息 |
| 🔴 破坏性标记 | 决定是否登记「已知失准点」；事后重新判定成本高 |
| sprint 号 | 定位用，很短，顺手带上 |

**⛔ 不要记**（级联时从代码 / git 现查，且现查更准——以现状为准）：

- ~~代码落点、行号~~ → 收口时 `git log`/`git diff` 查，比手记的准（手记的可能已被后续改动挪位）
- ~~影响级别 L1/L2/L3/L4~~ → 收口时按约定 22 四级触发表重新判定
- ~~变更类型（新增接口/表/规则…）~~ → 收口时对照代码判定
- ~~级联目标（落到哪一族）~~ → **文件所在的族就是级联目标**，再记一遍纯属冗余
- ~~档位 S/M/L~~ → 收口时**按族各自重判**（单条的档位没有意义；四族分册后各族独立判档，不再把总改动量加总）
- ~~详细线索、上下文、待办说明~~ → 一句话说不清的，说明它不是小改动，本就该走 `--cascade-now` 当场级联

> 📌 **破坏性条目多写一行**：在「已知失准点」段登记**哪份文档哪一节现在是错的**（一行）。
> 这是本机制唯一的风险缓解手段，不能省；但也只需一行，不必展开。

> 📌 **没有「已级联」段**：级联成功的条目**直接删除**，不留存档。若保留，册子会随版本推进无限膨胀，
> 而它承载的信息此时已经进入正式文档——留着是第二份信源，反而制造歧义。

**条目编号**：`C-{NNN}`，本文件内连续自增（`C` = Change）。**跨 Sprint、跨天连续**，不随 Sprint 或日期重置
（同 Sprint 编号的全局流水号精神）。

## 三、写入时机（谁往增量册里记）

> **★ 作用域 = 变更事实、与命令入口无关**：裸对话路径（用户口述 → 执行体直接改代码 → 直接 commit+push、全程没走 `/sprint-*`）
> **同样必须先记增量册**，⛔ 不得以"本轮没走 `/sprint-*`"为由当场改写四册上游规划文档——绕过后册子为空，与"本轮确实没有实质变更"
> 在机器上完全同形。反向检出 = `commit_gate.py::suspected_cascade_bypass`：同一次变更里既有正式代码又有上游规划产物、却没动任何增量册
> → WARN + 退出码 3；唯一合法例外 = 显式 `--cascade-now`。攒批只改变执行时机，**判定规则一条不改**（检测项 / 四级触发 / 破坏性变更门 / L4 必产）。

`/sprint-dev` Step X.0.0 检出上游文档变更后——**不再当场跑四级级联**，改为把影响清单的每一行**按受影响的族追加为增量册条目**（同一变更跨族共用同一个 `C-NNN`），
然后继续后续步骤。原 `sprint-{NNN}-upstream-impact-{时间戳}.md` 影响清单**照常产出**（复盘用，不受影响）。

- 🔴 **破坏性变更同样进增量册**（不当场级联），但**必须**：① 条目标 `🔴 破坏性` ② 在「⚠️ 已知失准点」段登记
  具体失准位置（哪份文档的哪一节现在是错的）。
  > ⚠️ **这是本机制唯一的已知风险敞口，明示如下**：增量变更攒着，文档只是"暂时不全"；破坏性变更攒着，
  > 文档在级联前**明确是错的**——它仍在描述一个已被删除的接口 / 已被推翻的规则。「已知失准点」段是唯一的
  > 缓解手段，**读上游文档做决策前必须先看它**。（该风险为项目方知情选择：一律攒、不设例外。）
  >
  > **机器门**：`commit_gate.py::pending_cascade` 逐份册子做交叉核对——「待级联」里带 🔴 的条目编号
  > 必须在「已知失准点」段出现同一个编号，缺一即进 `destructive_unregistered`、**恒打印 stderr
  > 且抬退出码到 3**（不受 `--quiet` 压制）。⚠️ 本机制的其它每条不变式都配了脚本，唯独这条
  > 长期是纯散文——而它偏偏是机制自称的「唯一缓解手段」。

### ★ 边界：什么走增量册、什么不走（常被问到，此处为唯一权威）

增量册收的是**「开发过程中检出的、相对既有文档的漂移」**，**不是**"所有需求变更"。二者路径不同、
不可互相替代：

| 来源 | 走哪条路 | 落盘形态 | 为什么 |
|---|---|---|---|
| **`/sprint-dev` Step X.0.0 检出的开发期漂移**（临时加的接口/字段/规则、Mock 转真实、口径微调） | **✅ 走增量册攒批** | 增量册条目 → 收口点批量写进各族主文档 | 它是"代码已经这样了、文档还没跟上"的**事后回填**，攒起来批量做纯赚 |
| **`/sprint-dev "<描述>"` 分支 B 口述累进**（产品口述一个要做的新功能/新口径） | **❌ 不走增量册**，走 Phase 0B.1.1 当场产增量 | `NN_<业务主题>.md` 正式交付增量 | 它是**开发的输入规格**——"先补文档、后写代码"。攒到明天再写，等于**今天在没有规格的情况下开发**，这不是省开销、是丢规格 |
| **产品侧 PRD / 原型变更** | **❌ 不走增量册**，走 `/version` 补充模式 | `NN_<业务主题>.md` | 同上，且产品要读 |
| `skip-doc-sync` 显式跳过文档增量流时的口述内容 | **✅ 必须补记增量册** | 增量册条目 | 见 `/sprint-dev` Phase 0B.1.1「跳过」段：不写 = 欠账不可发现，会被收口点 3 当合法终态放行 |

> **★ 常见误解澄清**：「每天的需求变更是不是都该只写增量册、不动已生成的版本规划文件？」
> —— **一半对**。对的部分：**已定稿的版本规划主文档（`01_研发需求.md` 等）本来就不该被就地改写**，
> 任何新东西都以**正式增量文档**或**族增量册条目**承载（约定 1 + 约定 15）。不对的部分：**口述的新需求不能压到族增量册里等明天**，
> 因为它是**开发的输入**，不是开发的产物——真攒到下个工作日，今天这轮开发就没有规格可依。
> **成本问题由档位门解决、不由攒批解决**：小口述走 `/sprint-dev` Phase 0B.1.1 **步骤 2.5 的 S 档
> （含语义子档）**，就地在既有册追加小节 + 「受影响结论清单」，而不是另起 700 行新册。

## 四、收口点（谁消费增量册）

**共 4 个**。每个收口点的动作一致：**派子 Agent 读【四族】增量册的「待级联」条目 → 结合代码现状核实 →
按 `C-NNN` 跨族合并同类项 → 跑四级级联（四级均传 `--ledger-cascade`，**就地改各族内容主文档正文**，
见「收口执行要点」第 3 条）→ 逐族删除已成功级联的条目 → 某族再无待级联条目则删除该族的册子**。
⛔ **四族必须各自走完判定，不得"任一族干净即收工"**——设计册清了、用例册还攒着 8 条，那不是收口完成。
**★ 版本级收口点（2 / 3）另加一条**：目标版本的**每一份**增量册（含存量单册台账）**必定删除、
不存在保留场景**——未能级联的条目先转出（规划期迁移进当前版本**对应族**的册子 / 发布期转记发布欠账），
再连文件一起删（见下方「终态机器门」档 ①）。

| # | 收口点 | 触发 | 范围 | 清理后 |
| :-: | :- | :- | :- | :- |
| 1 | **每日首次提交** | ⛔ **`git push` 成功【之后】**判定并派后台子 Agent（约定 24 `commit_gate.py` 的 `should_dispatch_cascade`）；判据 = `pending_cascade.stale > 0` | **四族**昨天及更早的待级联条目（**当天新增的不动**，留到明天——否则刚记就级联，失去攒批意义） | 逐族删除已级联条目；某族清空即删该族册子 |
| 2 | **版本规划** | `/version` 规划期 **Step 2.7.4** | **上一版本**四族遗留的全部待级联条目（含存量单册台账） | ⛔ **必定删除上一版本的每一份册子，无保留场景**；未能级联的条目**迁移进当前版本【对应族】的册子**（行尾标 `← 承接自 {上一版本}`）后照删 |
| 3 | **版本发布** | `/version` 发布期 **Step 3.3.9.5**（必须先于 3.3.10 文档收敛） | **当前版本**四族全部待级联条目（**必须清空**，不得带着待级联项发布） | ⛔ **必定删除本版本的每一份册子，无保留场景**；未能级联的条目**转记 `docs/audit/{version}/发布欠账.md`** 后照删 |
| 4 | **批量 Sprint 收尾** | `/sprint-batch` **Step 5.5**（必须先于 Step 6 浏览器实测）| **★ 按族分流**：`用例` 册**含当天新增**必须当天级联（紧接着就要用这批用例做实测）；`需求`/`设计`/`计划` 三族仅处理**昨天及更早**（同收口点 1），当天新增留到明天 | 逐族成功即删、清空即删该族册子 |

> ⛔ **删除是收口的一部分、不是可选的收尾**：留着已级联的条目 = 同一信息在册子与正式文档里各存一份，
> 下次收口还要重新判断"这条到底级联过没有"。**清空即删文件**，让"某族的册子存在"本身就等于
> "该族有待级联项"——这是最省事也最不会错的状态表达。
>
> **★ 收口点 4 为什么按族分流**（本机制唯一一处族间差别）：Step 5.5 立起来的理由是「紧接着 Step 6
> 就要用这批用例做实测，用例不能留到明天」。但 **autopilot 链内恒传 `--skip-aiauto-test`**，Step 6
> 整段跳过、浏览器实测归独立的 `/sprint-aiauto-test` 链路——**紧迫性只对「用例」这一族成立**。
> 需求/设计/计划三族当天没有任何下游消费者，跟着一起当天级联纯属把最重的那部分（尤其详细设计）
> 压进当天。故只有用例族含当天新增，其余三族与收口点 1 同口径。

### ★ 终态机器门（收口点 2 / 3 / 4 必跑；把上面那句话变成可判定的断言）

收口跑完**必须**过这道门。它**分两档，按收口点选**——版本级收口（2/3）是"必删"，
批次级收口（4）是"存在即须有未决条目"：

```bash
# 档 ①：版本收口点 2 / 3 —— 目标版本【四族每一份】册子都必须不存在，无任何保留场景
python3 .aidp/scripts/check_cascade_landing.py --must-delete --version {收口的版本}

# 档 ②：收口点 4（/sprint-batch 批次收尾）—— 文件存在 ⟺ 确有未决条目
python3 .aidp/scripts/check_cascade_landing.py --ledger-closed --version {version}
# 两档都可省 --version 扫全部版本；--json 出结构化结果
```

**档 ① `--must-delete`（版本规划 / 版本发布）**：唯一合法终态 = **四族每一份（含存量单册台账）
都不存在**。版本规划必定清掉上一版本的、版本发布必定清掉本版本的；**有未决条目、打了
`<!-- LEDGER-ARCHIVED -->` 一律判失败**，不看内容。未能级联的条目**另有去处**，不会丢：

| 收口点 | 未能级联的条目去哪 |
| :- | :- |
| 2 版本规划 | **迁移进当前版本【对应族】的册子**（原文照搬 + 行尾 `← 承接自 {上一版本}`，编号在新册内重排连续；存量单册的条目按内容分派到对应族），继续攒批 |
| 3 版本发布 | **转记 `docs/audit/{version}/发布欠账.md`**（逐条写编号/原文/失败原因），由 `/version {version} --finalize-docs` 驱动补跑 |

> ⛔ **为什么不留"还有失败条目就先留着"这个口子**：留着 = 同一条目在册子与（迁移目标 / 欠账台账）
> 两处并存，下个收口点又要重新判断"这条到底处理过没有"——正是本机制要消灭的第二份信源。
> 条目既然已有确定去处，册子就没有任何理由继续存在。

**档 ② `--ledger-closed`（批次收尾）**：批次收尾时版本仍在开发中，未决条目留到下个收口点
是正常节奏，故只禁"已级联却不删"：

| 某一族的册子状态（**四族逐份判**）| 判定 |
| :- | :- |
| 文件不存在 | ✅ 收口完成的正常终态 |
| 整档打了 `<!-- LEDGER-ARCHIVED -->` | ❌ FAIL：**标记不替代删除**（见下方「即删与溯源的取舍」）|
| 仍有未决（失败 / 未级联）条目 | ✅ 合法保留，打印剩余条数 |
| 文件在、却一条未决条目都没有（空册 / 条条已划删线或标 ✅已级联）| ❌ **该删没删** |
| 有实质内容却一条条目都解析不出 | ❌ 格式漂移，无从证明已收口（fail-closed，不放行）|

条目解析复用 `commit_gate.pending_cascade()`、路径复用其 `cascade_ledger_paths()`，
与收口点 1 的判定同一套读数与同一组文件，不另写一份正则、不另拼一次路径。
收口点 1（每日首次提交）不单独跑本门——它的欠账由 `commit_gate` 的 `cascaded_not_cleaned`
在下次 gate 运行时结算并抬高退出码，路径已闭合。

### ★ 子 Agent 执行时的派单契约（攒批机制唯一会整段失效的地方）

约定 36 授权 `/sprint-dev` 自动派子 Agent 执行开发任务。**攒批的判定结果活在主链路 flow 里，
子 Agent 读不到它**——`postdev-writeback-1.md` 不在子 Agent 的上下文中，它无从知道
「脚手架默认应该攒批」。于是只要派单简报里直接罗列了待改文档清单，就**等价于一次强制
`--cascade-now` 全量级联**：攒批在主链路上生效、在派单路径上 100% 失效。

而口述累进（`/sprint-dev "<描述>"`）恰恰**既是最常派子 Agent 的路径、又是最需要攒批的路径**。
实测代价：一次 6 个源文件的小改动，文档改动量是代码的 **1.75 倍**、约 60% 的工具调用花在级联上。

**故派单简报【必须】携带下面两个字段，缺一即视为派单不合规：**

| 字段 | 取值 | 由谁判 |
|---|---|---|
| `cascade_mode` | `ledger`（默认攒批）/ `now`（`--cascade-now` 或命中收口点）| 主链路按步骤 3.8 判据先判好再派 |
| `dev_scale` | `S` / `M` / `L` | 主链路按步骤 3.5 档位门先判好再派 |

**`cascade_mode: ledger` 时，简报的「文档级联」段必须整段替换为：**

```
## 文档级联（约定 22 —— 本轮【攒批】，⛔ 不跑四级级联）
把本轮每条变更按下面**一行格式**追加到【受影响的每一族】的增量册（同一变更跨族共用同一个 C-NNN，
只记与该族相关的那一面、不复述别族）：
  需求 → docs/requirements/{version}/研发需求/_开发期需求增量.md
  设计 → docs/design/detail/{version}/_开发期设计增量.md
  计划 → docs/plans/{version}/_开发期计划增量.md
  用例 → docs/testing/{version}/研发自测/_开发期用例增量.md
（不存在则从 .aidp/templates/_开发期族增量.md 拷骨架，把 {族} 换成对应族名）：
  - C-{NNN} · MM-DD HH:MM · 一句话说清改了什么·为什么 · 🔴破坏性（可选）· sprint-{NNN}
⛔ 本轮不改研发需求 / 详细设计 / 研发执行计划 / 自测用例中的任何一份；
⛔ 不做全库计数回扫。这些留到收口点批量做。
```

> ⛔⛔ **`cascade_mode: ledger` 下，简报里【不得】出现待改文档清单**——罗列即等价于
> 强制 `--cascade-now`，本机制当场失效。子 Agent 读不到 `.aidp/reference/` 的话，
> 上面那行条目格式**必须内联进简报**（它就是为此写成一行的），四族落点也要一并带上。

> ⛔ **`dev_scale` 漏传的代价**：子 Agent 回退 L 档「现状全套」——3.5 的档位判定就只省下
> 分册文件头与索引登记行这类样板，正文（用例 100+ 条、全套设计）一行没少，**等于白判一次档**。

### ★ 「即删」与「溯源引用」的取舍（曾是一条自相矛盾、逼执行体两边违规的规定）

本条要求「成功级联的条目即删」，同时又要求级联时在目标文档里标注溯源。下游据此在详设、
接口设计、待澄清清单、Sprint 归档里写了一批 `增量册 C-036-03`、`（C-039-05）` 这类
**对增量册编号的引用**——于是删档会让这些引用集体断链，执行体只能在「即删」与「不断链」之间
二选一，**选哪个都违反另一半规定**。这不是执行体的判断失误，是规定本身缺了一句话。

**定则（默认路径，新版本一律走这条）**：
**级联时在目标文档里写明【变更内容与理由本身】，⛔ 不写增量册编号。**
增量册是**中转站**、不承担长期溯源——变更的最终归宿是那四份正式文档，它们自己就该把
「改成什么、为什么」说清楚。写编号相当于把权威指向一个注定要被删掉的文件。
这样「即删」与「不断链」不再冲突：**没有引用，就没有断链**。

**⛔⛔ 没有"打个标记留档"这条出路——标记不替代删除。**
`<!-- LEDGER-ARCHIVED -->` **不豁免任何东西**：不豁免级联义务、不豁免条目即删、不豁免文件即删。
打标记只是把"没删"换了个说法——**册子仍在、条目仍在**，读上游文档的人照样分不清
哪条已生效、哪条还欠着，而那正是本机制要消灭的状态。机器侧同口径：
`commit_gate.py::pending_cascade()` **照常解析、照常计数**，另把打过标记的点名
`archived_not_deleted`（恒打印 + 抬退出码）；`check_cascade_landing.py` 两档**一律判 FAIL**。

**编号引用删不掉时的唯一正确做法**：先按上面的定则把引用处改写成
**变更内容与理由本身**（增量册是中转站、不承担长期溯源），**再把册子真删掉**。

> ⛔⛔ **收口点 1 必须在 `push` 之后判定，不能在 commit 前——这是多人协作防重复的唯一依据**：
> 增量册是**入库共享文件**，各人本地都可能落后。A 已收口清空并推送后，B 若按自己 commit 前的本地状态
> 判定，会认为"我是今天第一个"→ **重复级联同一批条目、在增量文件里写出重复条目**。
> 而 **push 成功本身即天然同步点**：推送被拒会强制先 `pull`/`rebase`，故 push 成功 = 本地册子已与远程一致。
> **子 Agent 启动后第一件事是重新读四族增量册**（不得消费主 Agent 在 commit 前算的快照，那份可能已被别人作废）；
> 重读后已无 `stale` 条目 → **直接退出、不做事、不报错**，这是正常路径而非异常。
> 同理，子 Agent 自己 commit+push 前也要先 `pull --rebase`。

> ⚠️ **残余空档（项目方知情选择：不设 `/sprint-close` 收口点）**：**单独**跑 `/sprint-full` 或
> `/sprint-dev` 且当天就关闭 Sprint 时，其 L4 用例要到次日才成文——该 Sprint 的 `/sprint-test`
> 拿不到新增用例。**规避方式**：`--cascade-now` 当场级联。
> 📌 走 `/sprint-batch` 的**主链路已由收口点 4 覆盖**（它一次跑 N 个 Sprint、当天就进 Step 6 实测，
> 是这个空档影响面最大的场景，不能只靠人记得加 flag）。

### 收口执行要点

1. **派独立子 Agent**（隔离上下文，避免把攒批的全部细节灌进主对话）。
2. **★ 内容从【代码现状】重新产出，不照抄增量册的条目行**——条目记的是**线索不是结论**。
   攒批期间后一条变更可能推翻前一条（加了字段又删掉、改了口径又改回），**一律以代码为准**：
   核实后已失效的条目**直接删除、不产文档**，收口报告列一行 `⊘ C-0NN 已失效（被 C-0NN 覆盖），未产文档`。
   **这是攒批相对即时级联的额外收益**——中间态自动消解，即时级联反而会把每个中间态都写成正式文档。

   **★★ 读代码用【增量范围】，⛔ 不全量扫 `code/`**（全量扫一遍在真实工程上是分钟级、且绝大部分与本批次无关）：
   ```bash
   # 起点 = 该族主文档最后一次被改动的那个提交（= 上次级联落地点，无需另存状态文件）
   SINCE=$(git log -1 --format=%H -- "docs/design/detail/{version}/01_详细设计.md")
   # 取该点之后的代码增量：改了哪些文件、改了什么
   git diff --name-only "$SINCE"..HEAD -- code/
   git diff          "$SINCE"..HEAD -- code/
   ```
   - 每个族各算各的 `SINCE`（四族主文档的最后改动点不同步是常态）。
   - 主文档从未被改过（`SINCE` 为空）→ 退回该版本的起点（版本首个提交 / 上一版本 tag），仍**不是**全量扫盘。
   - 增量册条目自带时间戳，可与 `git log --since` 交叉印证，但**结论以 diff 为准**。
   - **只有 diff 读不清的地方才回去读整份源文件**（如需要看清一个类的完整签名），按需、逐个，不成片读。
3. **★ 落盘形态 = 直接改该族的【内容主文档】正文，⛔ 不新建任何分册**：
   四级级联调 `/sprint-requirements`·`/sprint-design`·`/sprint-plan`·`/sprint-selftest` 时**必须**传
   `--ledger-cascade`（**不是** `--supplement={NN}`），把结论**就地写进对应族的内容主文档**：

   | 级 | 落点（就地改正文） |
   |---|---|
   | L1 需求 | `docs/requirements/{version}/研发需求/01_研发需求.md`（多系统按各自 `01_<系统>.md`）|
   | L2 设计 | `docs/design/detail/{version}/01_详细设计.md` · `02_数据库设计.md` · `03_接口设计.md`（按实际范围）|
   | L3 计划 | `docs/plans/{version}/01_研发执行计划.md` |
   | L4 用例 | `docs/testing/{version}/研发自测/` 的既有用例册 |

   - **改完刷该目录 `00_索引.md` 的生成时间**（约定 15）——主文档动了，索引的时间戳就该跟着动。
   - **合并同类项**：同一业务主题的多条变更改到**同一处**，不是一条改一处。
   - **⛔ 不新建分册**：`NN_<业务主题>.md` 是**产品侧 PRD/原型变更与口述累进**的命名空间，收口级联不占它。
   - **⛔ 增量册不是级联的落点**：结论**一次到位**落进主文档 → 该族增量册的对应条目即删。
     （族增量册是**开发期的入口**、不是收口期的出口；往它里面写级联结论 = 内容永远到不了主文档。）
     增量册是开发期入口、不是收口出口；内容在主文档之外再存一份、还要再搬一次，只会变成第二份信源
     （根因见同目录 `rationale.md` 无此文件时见本文件「一、解决什么问题」）。
4. **档位按合并后的总改动量重判**（Step X.0.0 步骤 3.5）——攒了 8 条小改动，合计可能已是 M 档。
5. **★ 落点门（提交前必跑，机器判据）**：收口子 Agent 在自己 commit 之前跑
   `python3 .aidp/scripts/check_cascade_landing.py --worktree`（或 commit 后
   `--base-ref <收口前 HEAD>`）——四族目录下的改动里**不得出现**：
   ① 任何 `_开发期{族}增量.md` 形态的中转册 ② **本批次新建的** `NN_<业务主题>.md` 分册。
   改既有主文档与 `00_索引.md` 属正常落点。任一违规 **exit 1**，须先把内容挪进主文档再提交。
   > ⚠️ **判"新建"而不是判文件名**：主文档 `01_研发需求.md` 与增量 `07_订单主题.md` 名字**完全同形**
   > （两位数字前缀 + 中文名），正则区分不了；唯一确定性的判据是"这份文件是不是本批次新建的"。
   base-ref 解析不了 / 识别不出版本目录 → 同样 exit 1（fail-closed，不给结论就是不通过）。
   > 📌 落点门只看**改动落在哪个文件**，不看内容。**语义/口径变更类条目**还须过下方
   > 「口径残留门」——旧口径散布在多处，落点全对也可能只改到第一处。

6. **失败不吞（失败条目必须有去处，但去处不一定是增量册）**：任一级级联失败 → 终端 WARN +
   按收口点分流，**绝不当作已完成一删了事**：
   - **收口点 1 / 4**（每日首次提交 / 批次收尾）：条目**保留在该族增量册**（因而该族文件也不会被删），
     留到下个收口点——此时版本仍在开发中，这是正常节奏。
   - **★ 收口点 2 / 3**（版本规划 / 版本发布）：条目**转出后连文件一起删**——规划期迁移进
     当前版本台账（行尾 `← 承接自 {上一版本}`）、发布期转记 `docs/audit/{version}/发布欠账.md`；
     ⛔ **不许**以"还有失败条目"为由把册子留着（`--must-delete` 档会判失败）。
7. **收口报告**：终端打印 `📋 攒批级联：处理 N 条（成功 M / 失效 K / 失败 J）→ 已写入各族主文档；四族册：需求删除/设计删除/计划保留 J 条/用例删除`
   （**收口点 2 / 3 恒为 `台账已删除`**，失败条目另报去处：`J 条转出至 <当前版本台账 | 发布欠账.md>`）。

### ★ 口径残留门（语义 / 口径变更类条目专用；级联完成后逐条跑）

落点门与增量册终态门都**只看文件、不看内容**：一条口径变更把「不向用户解释」改成
「列级范围说明」，只要落进了主文档、册子清了，两个门全绿——哪怕字段处置表 /
验收测试点 / 用例断言 / 索引摘要里旧口径原封不动。而**同一句口径天然散布在多处**，
执行体按「条目编号」改，只会改到第一处。

**故语义/口径/范围/单位/默认值类条目级联完成后，逐条跑：**

```bash
python3 .aidp/scripts/check_cascade_residue.py --version {version} \
  --old "<旧口径>" [--old "<旧口径变体>" …] --new "<新口径>" \
  [--scope requirements,design,plans,testing] [--json]
# 0 = 无残留 / 2 = 检出真残留 / 1 = 参数或版本目录错（fail-closed）
```

门把命中分两类，**分类本身就是它的全部难点**：

| 类别 | 含义 | 处置 |
| :- | :- | :- |
| **真残留** | 旧口径仍作为**当前生效规则**出现 | ❌ 必须逐处改；改完重跑 |
| **订正留痕** | 旧口径出现在「原口径…已作废」「由…订正为…」「变更历史」等上下文 | ✅ **保留**，改掉反而抹掉审计痕迹 |

留痕判据 = 同行/上下文含留痕词（作废 / 原口径 / 订正 / 取代 / 废弃 / deprecated…）、
同行含新口径、所属章节为留痕型、或 `--allow` 白名单；**上下文扫描遇标题即止**——
跨过章节边界的留痕词说的不是这一处，不设这条边界会让"下面正好开了个 `## 变更历史`"
的真残留被判成留痕、从此隐形。

`--new` 另给一份**落地分布**：新口径 0 命中的族大概率整族漏级联（下游实测正是这样让
一条用例断言与研发需求规则**直接互斥**、跑必 Fail）。该提示**不进退出码**——有的口径
本就不涉及某族，硬判会把门变成噪音。

四族增量册本身不扫：它们正记着"把 X 改成 Y"，必然含旧口径，是过程记录不是生效规则。

### 跨版本落点

级联产物**落回变更发生时的原版本**目录的各族主文档（否则历史版本文档永久缺失该部分，事后回溯对不上账）。
**例外**：原版本**已发布**（已打 tag、文档已冻结）→ 落**当前版本**，并在产物头部注明
`> 追溯自 {原版本}：本内容对应 {原版本} 开发期变更 C-0NN，因该版本已发布故落于本版本`。
