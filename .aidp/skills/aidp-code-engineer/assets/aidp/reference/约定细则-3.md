### 约定 31 — **★ CICD 与协作平台集成（多提供方，默认 GitHub Actions）**
- **31.3 开发/缺陷读取（`/sprint-dev`·`/sprint-bugfix`，可选）**：用户**主动提及 GitHub Issue**（编号或链接）时，用 `gh issue view <num>` / `gh issue list` 读取 → **先预读、确认缺陷存在/可复现再修**（人工填写的标题不可盲信）；未提及不强制拉取；未安装或未登录 `gh` 即跳过、不阻塞。
- **31.5 CICD 编排 —— 推送分类与监听（★ 作用域 = **代码推送这一事实**、与命令入口无关：**裸对话路径**〔用户口述 → 执行体改码 → 直接 `commit`+`push`、全程没走 `/sprint-*`〕**同样适用**，与约定 22 / 24 / 36 同口径；不限 `/sprint-autopilot`）**：CICD 平台 = `memory/aidp-config.yaml` 的 **`cicd.provider`**：`github-actions`（默认，经 `gh` CLI）/ `gitlab-ci`（REST API，`cicd.gitlab-ci`）/ `jenkins`（REST API，`cicd.jenkins`）/ `command`（任意平台自定义命令模板，如 Gitee、Gitea、自建平台，`cicd.command`）/ `none`；部署环境 → 流水线标识映射在 `cicd.pipelines`（如 `{dev: deploy-dev.yml, test: deploy-test.yml}`，含义随 provider：workflow 文件名 / 分支名 / Job 路径 / 命令模板的 `{pipeline}`）；⛔ 令牌只经 `*_env` 指向的环境变量引用。`provider=none`、未配置流水线或提供方 CLI/凭据不可用 → 回落为仅 git push、不监听。已接入时，**先过推送分类门再决定要不要监听**：
    **⓪ 分类（每次 push 前必跑，主行为单一信源）**：`python3 .aidp/scripts/classify_push.py --root . --version "$VERSION" {--build "$BUILD" | --standalone}`（⛔ 落盘的是 `classify_push.py`；`classify_commit_change.py` 只出分类、不落盘），完整结果写入当前 build；链外任务（约定 41 不铸 build）走 `--standalone`。
    **无正式代码变更且分类无错误** → 仍校验 push 成功并记 `cicd_skipped=true`，**不触发/不监听远端 CICD、不等待部署、不跑就绪探针**，本条后续六步整段跳过。
    **有正式代码变更、分类结果缺失或分类出错** → fail-closed 进入编排——① 防重复触发（push 后等 ~10s 按 **commit sha 强绑定**查是否已有运行：`cicd_watch.py --mode detect --commit <sha> --env <env>`）② 未触发则主动触发（`cicd_watch.py --mode trigger --env <env> --ref <branch>`）③ **轮询锚定的那次运行至终态、失败重试最多 3 次**（`cicd_watch.py --mode retry --env <env> --run-id <id>`，重跑针对原运行的 commit）④ 成功后**等冷启动**（15s+ 按后端栈延长）⑤ 过**部署就绪探针**（**⛔ 不能用登录页可达判就绪、须登录后自身鉴权接口连续 2 次取到数据**）⑥ 通过才写 `last_deployed_at` 放行测试；探针超时=人工介入不重跑。★ 六步编号与 `invariants.md`「推送分类与监听不变式」一致。
  - **★ 写动作授权**：触发与重试由命令端显式调 `cicd_watch.py --mode trigger|retry` 执行（⛔ 命令端不内嵌任何平台 CLI）；无人值守下受 `cicd.auto_trigger`（默认 `true`）控制、无需人工确认；`auto_trigger=false` 时交互式先征询、无人值守置 `needs_human` 响亮冻结。重试上限 = `cicd.max_retries`（默认 3）。
  - **★ 环境事实以「CICD 运行记录」为唯一权威，⛔ 不得引用只在特定链路才被写入的本地状态字段**：判断「代码部署了没 / 当前环境跑的是哪个提交」时，**权威事实源 = CICD 平台运行记录里的 commit**；本地 baseline 的 `last_deployed_at` / `last_autopilot_head` 这类字段**只有走完特定链路才会被写**（推送自动触发的部署就不写它），当环境事实用必然误判。**判定口径**：任何状态字段被用作判据前，先回答「**这个字段是谁写的？当前路径下它会被写吗？**」——答不上来就不能拿它下结论（写入方声明义务见 `flows/sprint-autopilot/invariants.md` IRON-9）。
  - **⛔⛔ `cicd_watch.py` 调不通时【不得自行实现轮询】**：自写轮询能「看状态」，却丢掉了本脚本**唯一重要的产出**——`next_action`（该不该重试、第几次）、`retry_run_id`/`retry_commit`、`retry_count`/`max_retries`、`trigger_cmd`/`retry_cmd`。执行体失去权威指令就会「自己判断」，而「构建失败」天然诱导人回头查业务代码。正确做法：**报修脚本**；报修前若需推进，**直接重试**（失败的第一动作恒为重试、最多 3 次），**不查业务代码**。
  - **★ 脚本可用性要有主动信号**：`python3 .aidp/scripts/cicd_watch.py --selftest`（离线自测，用假平台输出覆盖各提供方，不访问网络），已挂进 `verify.py`。**Why**：脚本坏掉时调用方会回落到自写轮询把故障吸收掉，主路径死了却零信号。
  - **★ 两个触发场景，监听与重试口径完全相同**：**【场景 A · push 自动触发】** 流水线配了 push 自动触发 → 任何命令 push 完代码后都必须接着监听（按运行的 commit `== 本次 push HEAD` 认领），失败自动重试 ≤3 次；⛔ 有正式代码变更时绝不"推了就当完事"；分类判定「无正式代码变更」的 push 不监听。**【场景 B · 用户主动要求执行】** 用户明确说要跑流水线 / 部署 / 重新构建 → `cicd_watch.py --mode trigger` 主动触发，之后同样监听至终态 + 失败重试。两场景只在"谁把运行拉起来"上不同，起跑之后的监听 / 重试 / 就绪探针 / 写 `last_deployed_at` 完全同一套。
  - **★ 分工（读写分离、全部经同一脚本）**：①③ 由确定性脚本 `python3 .aidp/scripts/cicd_watch.py --mode watch|detect|poll --commit <sha> (--env <env> | --pipeline <标识>) [--run-id <id>] [--version <v>] [--max-retries N]` 承担（平台差异收在 `cicd_providers.py`；输出 `provider` / `pipeline` / `pipeline_source` / `verdict` + `next_action`：`trigger`/`retry`/`probe`/`poll`/`abort`，需写动作时附 `trigger_cmd` / `retry_cmd`）；② 与重试由命令端显式调 `--mode trigger [--ref <branch>]` / `--mode retry --run-id <id>`（受理后 `next_action=poll` 已拿到 run id，`=detect` 需按 commit 再探测）。**退出码** 0=运行成功 / 已命中 / 写动作已受理 · 1=需调用方做写动作（触发/重试）· 2=需人工（含 `trigger-failed` / `retry-failed`）· 3=未接入或环境不满足（`disabled` / `not-configured` / `cli-missing` / `unauthenticated` / `provider-unavailable` / `bad-args`）。④⑤⑥ 就绪探针走 `python3 .aidp/scripts/autopilot-deploy-watch.py`。
  - **★ 穷尽判定，不留悬空态**：运行**失败** → 重试（配额未尽）；**CICD 平台不可达 / 提供方凭据中途失效** → ≠ 失败态，**不消耗重试配额、不空触发新运行**，告警后下次再查；**锚定运行消失/被顶替** → 判异常交人工，⛔ 绝不静默滑到"最近一条"顶替；**结论无法归类**（如 `cancelled`/`action_required`）→ 不给绿灯、交人工。
  - **★ 单次调用有上限、跨 tick 续跑**：`cicd_watch.py` poll / watch 到 `--timeout`（默认 480s）仍在运行 → `verdict=running`、`next_action=poll`、退出码 0，下个 tick 按同一 run id 续 poll（不交人工、不耗重试配额）；就绪探针 `--max-seconds`（默认 480）到时未就绪 → 退出码 4（pending），下个 tick 带同一 `--since` 续探。
  - **★ 部署终态必须留痕**：监听结束后 `python3 .aidp/scripts/classify_push.py --version <V> --record-terminal success|failed|unknown:<原因>` 记该次推送的部署终态；`provider=none` / CLI 不可用等无法获知终态的情形记 `unknown:<原因>`——显式降级，不算欠账，但在门禁输出里可见。`commit_gate.py::pending_cicd` 的适用条件 = `cicd.provider != none`：按 HEAD commit 查分类记录，正式代码推送超过 1 小时仍无部署终态即计欠账（约定 24 退出码 3）。
  - 编排细节单一信源 = `/sprint-autopilot` Phase 3.2.1（`.aidp/flows/sprint-autopilot/phase-3-6.md` Step A0–C + `phase-3-7.md` Step D）+ 「推送分类与监听不变式」（`invariants.md`）；其余命令的 push 点**引用**它们、不复述（约定 21）。
- **Why**：推送后不监听，部署在远端红了也无人知，依赖它的测试链路对着旧版本空转；就绪探针兜住"部署完成≠可测"。

### 约定 32 — **★ 里程碑通知渠道装配**
- **发送入口**：`python3 .aidp/scripts/notify.py`，字段式参数 `--title --header-color --section --section-file --link-text --link-url --footer --node --version --build --gate --project-name --check-name`，`--print-only` 仅渲染不发送、`--json` 输出结构化结果。
- **渠道选择**：`--auto` 按 `memory/aidp-config.yaml` 的 `notify.channels` 顺序依次尝试，成功即停（`notify.fallback=false` 时只试第一个）；`--sender '<命令>'` 指定自定义发送命令（从 stdin 读消息 JSON）。支持渠道：`feishu`（飞书自定义机器人 webhook）/ `lark-cli`（飞书 CLI）/ `dingtalk`（钉钉机器人 webhook）/ `wecom`（企业微信机器人 webhook）/ `command`（自定义命令读 stdin JSON）。
- **配置示例**：
  ```yaml
  notify:
    enabled: true
    fallback: true
    channels:
      - {type: feishu, webhook_env: AIDP_FEISHU_WEBHOOK, secret_env: AIDP_FEISHU_SECRET}
      - {type: wecom, webhook_env: AIDP_WECOM_WEBHOOK}
  ```
- **⛔ 密钥不入库**：webhook 地址与签名密钥**只经环境变量引用**（`webhook_env` / `secret_env`），⛔ 不把明文写进 `aidp-config.yaml` 或任何入库文件。
- **退出码**：0 成功 / 1 全部渠道失败 / 2 参数错误 / 3 未配置任何渠道或 `notify.enabled=false`——**3 = 合规降级：静默跳过本播报节点，⛔ 不弹窗问人**；1 仅告警、不阻塞主流程。
- **Why**：7×24 无人值守下，里程碑通知是人感知进度与冻结的唯一主动信号；渠道配置化让不同团队各用各的 IM，密钥走环境变量避免泄露。
