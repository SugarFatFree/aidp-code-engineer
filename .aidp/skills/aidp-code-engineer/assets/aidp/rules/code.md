> 前端另见 `.aidp/rules/frontend.md`（约定 4）；后端另见 `.aidp/rules/backend.md`（约定 27）。技术栈中立：下文具体技术（`@Profile`/`el-*`/`@Size`/`VITE_USE_MOCK`/MyBatis 等）均为示例，按项目实际技术选型对应等价机制。

## 约定 17 — 代码注释强制规范（覆盖 Claude 默认"无注释"原则，Agent/Skill/手工产物统一遵守）

- **类/接口/枚举/组件**：声明上方文档注释，说明职责 + 业务背景；状态/枚举类加值域含义
- **方法/函数**：上方文档注释含 用途/参数语义/返回值/抛出语义；核心业务方法加业务规则要点或上下游说明
- **字段/属性/常量**：注释标业务含义（非字段名直译）；状态/枚举写取值范围+含义或引枚举类；DTO/Entity 与 DB COMMENT/PRD 字段规格对齐
- **代码正文关键段必加注释**：复杂业务规则 / 性能或缓存策略 / 并发或事务边界 / 安全（鉴权加密脱敏）/ 第三方对接边界 / TODO·FIXME·HACK（带原因+责任人）/ 反直觉有坑的代码
- **不算注释场景**：纯样式标签、test-only 测试桩、迁移期临时占位、第三方代码搬运
- **回检**：`code-verification-loop` 检「注释完备性」，**按下方 A/B/C 分档加权**——A 档裸代码即标红回 `/sprint-bugfix`，B 档仅记录，C 档不计分

### ★ 注释强度按代码性质分三档（⛔ 不是一刀切；密度不等于价值）

一刀切的等密度要求会把成本花在没有信息量的地方：实测某 Service 净增 75 行中 **93% 是注释**、
实际逻辑仅 +10 行；某组件 328 行里非注释有效行仅 226——由此还连锁触发约定 20 的复杂度告警，
又要额外登记偏差写说明。**生成 5000 行文本的耗时是 1500 行的三倍多**，而多出来的那部分
多是同义反复。故按"改错了会不会当场报错"分档：

| 档 | 覆盖对象 | 要求 |
| :-: | :- | :- |
| **A** | 判据 / 口径 / 状态机迁移 / **上游契约消费点** / fail-closed 分支 / 并发与事务边界 / 安全（鉴权加密脱敏）/ 反直觉有坑处 | **保持现有强度**——这些是"改错了不报错"的地方，注释是唯一防线；必须写清**业务含义与为什么**，不是复述代码 |
| **B** | 常规 CRUD、DTO 组装、简单类型转换、直白的编排方法 | **一句话即可**（说清它在业务上干什么），不必展开参数/返回/抛出三段式 |
| **C** | getter/setter、字段声明的直白赋值、框架样板、显而易见的委托 | **可省** |

> ⛔ **禁止为满足覆盖率而写同义反复的注释**（`// 设置用户名` 配 `setUserName()`、
> `// 返回结果` 配 `return result;`）。这类注释不增加任何信息、却要被后人一起维护，
> 是纯负债——**宁可不写**。评审看到即按"未覆盖"处理，不因它存在而算作已注释。
>
> **分档不削弱 A 档**：约定 17 存在的理由（多条历史教训靠注释传承）全部落在 A 档；
> 本分级要砍的是 B/C 档的同义反复，不是给"少写注释"开口子。**判不准时按高一档写。**

- **回检口径随之调整**：覆盖率**按 A 档加权**，而非按行数均摊——A 档裸代码即标红，
  B/C 档不因缺注释拉低分数。（该口径在 `code-verification-loop` SKILL 侧落地，
  本项目只是其消费方；SKILL 未更新前，命令端按本条判读其报告、不据均摊分数回 `/sprint-bugfix`。）
- **★ 反向门（注释写太多同样是缺陷）**：`python3 .aidp/scripts/check_comment_ratio.py`，由 `/sprint-dev` Phase 1 Step 7bis 调用。
  **只判「声明之外的注释」**：本约定本就要求给类/接口/方法/字段逐个写文档，故「短注释块 + 紧随声明」这部分先从分子里扣除；
  剩余注释/代码行数比 > 1.0 且未命中 A 档特征 → **Important 不阻断**。A 档与 JSDoc 契约型注释（`@typedef` / `@param`、类型声明文件）
  整档豁免，行内 `comment-ratio-ignore: <原因>` 可就地豁免。
  **Why 两个方向都要有**：只查「写少了」一侧时，过度注释零成本、零反馈信号，分档规则只在那一侧生效。

## 约定 18 — 代码目录统一标准（`{子项目}` 中间层为铁律）

新建项目 `code/` 强制前后端二分 `code/frontend/{子项目}/` + `code/backend/{子项目}/`，**单/多项目都套父目录**。

- **★ `{子项目}` 层强制铁律（堵"src 直放 code/backend"的口子）**：`code/frontend/` 与 `code/backend/` 是**父目录**，其下**必须再有一层 `{子项目}` 目录**（对应 `package.json` 的 `name` / Gradle `rootProject.name` / Maven `artifactId` / 模块名），源码根标志文件（`src/`、`pom.xml`、`build.gradle`/`build.gradle.kts`、`settings.gradle*`、`package.json`、`go.mod`、`Cargo.toml`、`requirements.txt`/`pyproject.toml` 等）**只能落在 `code/{side}/{子项目}/` 下**。**即便单项目也必须有 `{子项目}` 这一层**——**严禁**把 `src/`/`pom.xml`/`package.json` 等**直接放到 `code/frontend`/`code/backend` 根**（这是最易犯的错：AI 见父目录已存在就直接往里写 src）。
- **★ `{子项目}名` 用户确认门（不静默派生）**：`{子项目}名` 必须**经用户确认**再建目录——**默认推荐 `<项目名>-backend` / `<项目名>-frontend`**（`<项目名>` 取 `memory/aidp-config.yaml` 的 `project.name` / git 仓库名），但**不静默采用**，须经确认门。触发时机：① `/sprint-design` 的「工程结构 + 运行时端点契约确认门」（版本规划期，与端口/访问前缀一并确认，单一信源见 `/sprint-design`）；② 兜底——`/sprint-dev` **首次为某端写代码前**，若基线未确定 `{子项目}名` 则用 `AskUserQuestion` 现场确认/派生，再建 `code/{side}/{子项目}/`。**访问前缀/context-path 一般 == `{子项目}名` 或模块名**，故两者同门确认。
- **init**：scaffold 建 `code/frontend/` + `code/backend/` **父目录**（含 `.gitkeep`）；**`{子项目}` 层不由 scaffold 建**（scaffold 不知道名字）——由上面的确认门在首次写码前创建
- **migrate**：code/ 空时按 init 建父目录；已有代码子目录则保留不动，不建空规范目录
- **upgrade**：已有任何代码子目录（`code/web/`+`code/server/` 等历史命名）→ 保留不动，不主动建空目录/README 指针；用户在 `memory/techContext.md` 指向实际路径（文档跟随代码）
- **Agent 读写边界**：规范项目 `code/frontend/{子项目}/` 由 Frontend Agent 独占写、`code/backend/{子项目}/` 由 Backend Agent 独占写；upgrade 按实际路径走
- **回检**：`verify.py::check_code_layout` — `code/frontend`/`code/backend` 根**直接**出现源码根标志（`src/`/`pom.xml`/`build.gradle`/`package.json` 等）而无 `{子项目}` 中间层 → **报错 + 提示 `git mv` 迁入 `code/{side}/{子项目}/`**
- **强制范围**：仅约束"新建/空 code/"；已有代码项目（upgrade）尊重历史结构，`{子项目}` 铁律不追溯改造既有布局

## 约定 19 — README 强制规范（三档：代码单元 / 导航枢纽 / 平铺叶子）

README 自动生成分**三档**，判定的唯一实现是 `readme_policy.py::is_readme_required_directory`——
`scaffold.py` / `migrate.py` / `verify.py` 一律调它，**任何脚本、SKILL 或命令都不得再各写一套路径判断**。
判定顺序：代码单元 → 显式 `README_REQUIRED` → 导航判据 → 否则不需要。

### 第 1 档 · 代码单元 README（`required=True`）

目标是让新人/AI/CI 5 分钟跑起来，内容含用途、技术栈、启动命令、目录概览、主要配置和外部依赖。

- **正式源码根 / 前后端子项目根**：`code/frontend/{子项目}/`、`code/backend/{子项目}/`，含 `code/web`·`code/server` 存量布局与根级 `web`·`server`·`src`
- **正式多模块的模块根**（Maven / Gradle / NPM workspaces / pnpm workspace / Go workspace）：父聚合根与被构建描述符真实声明的模块根各有一份
- **源码单元内部目录不生成**（`reason=code-tree-internal`）：子目录深度在这里是包结构、不是导航需求；不按文件数量或散落的入口文件自动升级
- **豁免**：纯占位骨架（仅 `.gitkeep`）、`example-`/`demo-`/`samples-` 前缀的示例子项目

### 第 2 档 · 导航 README（`required=True`，`reason=navigation-hub`）

源码树之外、**目录结构本身需要导航**的枢纽目录。判据确定性、只看子目录结构，**不按目录名猜测**：

- 直接子目录数 **≥ 2**；或
- 直接子目录数 = 1 且该子目录非空（存在多级结构）

依赖树、构建产物、备份与隐藏目录（`node_modules`/`dist`/`build`/`target`/`vendor`/`out`/`coverage`/`__pycache__`/`.aidp-backup-*`/`.` 开头）不计入子目录数，也不参与判定。

内容形态与代码 README 不同：**只做子目录清单 + 各自用途**，不写技术栈与启动命令。

### 第 3 档 · 不需要 README（`required=False`，`reason=flat-leaf-directory`）

源码树之外、且无多级子目录的平铺目录——仅平铺少量 SQL / 脚本 / Markdown / 图片。文件再多也不构成导航需求。
典型：`docs/deployment/tools/<上游系统>/`（0 子目录，仅几个工具文件）。

### 结构性 README 的门控

`docs/{分类}/README.md` 与版本枢纽目录 README **同受**上述三档门控，脚手架资产只决定用什么内容渲染、不决定该不该铺。

### 显式声明与存量处置

- **显式例外**：`memory/.sprint-autopilot-baseline.json` 的 `project_state.README_REQUIRED` 数组可声明任意项目内目录，**优先级高于全部自动判据**；越界路径（`../` 等）被过滤
- **存量范围外 README**：升级/迁移/刷新只输出 `README_OUT_OF_SCOPE` 与 `preserve-and-report`，**不得自动删除、不得覆盖**；删除与否由用户显式决定
- **范围外扫描降噪**：扫描排除上列依赖/产物/备份目录，且**未被 git 跟踪的文件一律不报**（第三方包自带 README 不是本项目资产）；输出先给汇总行 `README_OUT_OF_SCOPE: N 处`，N=0 时明确打印"无范围外 README"
- **触发**：① `/sprint-dev` 首次为正式代码单元写代码前确认/创建 ② `/sprint-init`/迁移流程按统一判定创建 ③ `verify.py::check_code_readme` 巡检

## 约定 20 — 文件复杂度 + 复用封装强制规范（覆盖 Claude 默认偏差：任务需要的复用 ≠ 过度抽象）

- **单文件行数软阈值**（参考值，其他语言按相近惯例）：Java/Kotlin ≤ 500、Vue SFC/React ≤ 300、TS/JS ≤ 400、Python ≤ 600、Go ≤ 500、SQL DDL ≤ 800（按业务域拆，`99_回滚脚本.sql` 序号保留）
- **单方法/函数硬阈值 ≤ 50 行**（不含注释空行），超过必拆
- **复用判别（同 Sprint 内 3 次即抽；★ 前端视觉单元收紧到 2 次，见 `.aidp/rules/frontend.md`「约定 20 前端特例」）**：按语言惯例抽共享单元（如 Java 工具类/私有方法/Bean、Vue Composable/公共组件、React Hook/组件）；跨页面跨模块提升到公共目录（如 `src/common|shared|utils`）
- **SRP**：单文件/类/方法只做一件可用"动词+名词"命名的事
- **禁止**：> 1000 行 God Class（直接不合规）；200 行瑞士军刀方法；同逻辑 3+ 页面复制粘贴；为"未来可能"做空抽象（无 3 次复用就抽 = 过度设计）
- **★ 判据类逻辑禁止平行实现（前后端通用，比"3 次复用即抽"更严——散落 ≥2 处即须收敛）**：「URL / base-path 拼装」「鉴权头组装」「租户 / 上下文解析」「时间格式化」「金额 / 单位换算」「字段归一 / 脱敏」这类**判据型逻辑**，一旦项目内已有实现，新增场景**必须复用、禁止另写一份——哪怕新写的那份当下是对的**。与普通"重复代码"不同：重复代码的代价是**维护成本**（够 3 次才值得抽）；**判据平行实现的代价是"分叉"**——各份因作者不同在**边界条件**上出现差异，且差异只在特定输入下暴露（如 URL 拼装只在"已含 context-path 的绝对路径"这类输入上炸成 `/{ctx}/{ctx}/…` 404），日常测试完全覆盖不到。**判定**：同一语义的判断散落 ≥2 处 → 下次触碰时**先收敛成单一信源再改**、不在第 3 处继续复制。前端「请求通道 URL 拼装」是本条最高频实例（详规见 `.aidp/rules/frontend.md`「请求通道单一判据」）。
- **★ 复制型代码的两条硬要求（「复制 + 登记技术债」不是免责声明）**：确因技术限制只能复制而非复用时，必须同时满足——① 复制段起始处落**可检索的同步义务标记** `SYNC-WITH: <源文件路径>`；② 技术债台账项写明 **「为什么现在不抽」**（抽取会引入的具体风险，不是"时间紧"）与 **「解除条件」**，**缺任一字段即视为未处理**、不算已登记。⛔ 只写"这是技术债"等于把登记当免责声明——真实代价：逐值复制三套卡片样式并登记技术债后，接下来每一轮返工都源于"复制的那份没跟上宿主"。
- **★ 抽取必须整族 + 全参数化，且与重构分两次提交**：容器 + 单元 + 子元素一并抽（只抽一半 = 单一信源只落一半）；凡「各调用方必然不同」的量都必须参数化（漏一个就等于没共用）；抽取前先列**「调用方 × 差异量」矩阵**，逐项落 `参数化 / 保留在调用方 / 确认无差异`；⛔ 抽取时不得顺手优化任何一条规则——否则等价性无法证明。前端视觉单元的完整落地细则见 `.aidp/rules/frontend.md`「约定 20 前端特例」20F.3。
- **回检**：`wc -l` + grep 找 3+ 重复；超阈值/未抽标 **Important**（建议返工）；> 2 倍阈值标 **Critical**（强阻塞回 `/sprint-bugfix`）。豁免：自动生成代码 / 第三方搬运 / 一次性迁移脚本 / test fixture

## 约定 23 — DB 约束写代码硬规范

DDL 声明的字段约束（NOT NULL/长度/唯一/外键/数值范围）必须前置校验到**接口层/服务层/前端表单层**，禁止依赖 DB 抛错回滚、禁止把数据库异常（如 `SQLException`/`DataIntegrityViolationException`）原样暴露前端（须包业务码 + 友好提示）。本条要点（后端长度/唯一查/外键查 + 前端必填·长度·失焦查唯一·枚举对齐·数值范围 + 反模式）以本文件为技术栈中立单一信源；具体语言的等价校验写法参见对应角色 agent（`agents/backend.md`/`agents/frontend.md` 核心原则，以 Java/Vue 为例）。回检在 `code-verification-loop` 维度 4 + `dev-manual-testcase` 4 类边界场景（null/超长/重复/外键缺失）。

## 约定 23 姊妹条 — ★ 错误契约与失败可见性 + 安全 fail-closed + 上游契约权威（编码期硬规范）

> **定位**：约定 23 管"DB 约束前置校验、不把 DB 异常原样抛前端"；本节把同一"失败必须被正确表达"的原则**扩到错误契约 / 失败可见性 / 安全判据 / 上游契约**——是 `/sprint-bugfix`「缺陷处置默认决策纪律」（**处置层单一信源**：找到这类缺陷时默认直接修、不问人）在**编码期的前移**：**写代码时就按下面产出，让这类缺陷从源头不发生**。两者互补——本节说"正确代码长什么样"，纪律说"发现了默认怎么修"，不重复（约定 21）。

1. **失败绝不伪装成成功 / 空（最高频）**：任何失败（业务校验不通过 / 依赖出错 / 数据缺失）**必须以错误表达**，**严禁** `HTTP 200 + "操作成功" + 空数据`、**严禁**前端 `catch` 把 error 吞成"暂无数据"空态。
   - 后端：失败返**明确业务错误码 + 面向用户的中文 message**（不是 `200` 裹一个空 `data`）。
   - 前端：**原样呈现后端 message**（错误态/toast/错误区块），**不得**替换成"暂无数据""空列表"等看似正常的态；`catch` 里不得静默吞错。
2. **上游 / 依赖不可达 → 明确报错、服务名用中文**：调用的上游服务 / 第三方 / 中间件不可达时，返回错误、文案格式 `「{上游中文名}服务无法连接，请稍后再试」`——**服务名必须是用户看得懂的中文**，不得暴露 `ORD`/`order-center` 等系统代号。确需降级（如字典类可回退默认值）→ **在该接口就地注明降级理由**，不做全局静默降级。
3. **安全判据一律 fail-closed（宁可报错，不给看似正常的错误答案）**：鉴权 / 权限 / 关联归属 / 签名校验等安全相关判断，**"取不到""解析失败""查询异常"一律按"拒绝 / 报错"处理**，**严禁** fail-open（把"取不到"当"没有限制"、把"解析失败"当"无关联"而放行）——错误的放行比报错危险得多。
4. **上游契约以上游为权威、及时跟进**：上游已交付更优接口 / 变更了契约（字段 / 结构 / 端点）→ **以上游为准跟进**（上游是契约权威方，其优化即应跟进），不因"要改本地"而滞留旧契约；切换会破坏已交付功能 / 需数据迁移时才升级为决策门问用户（属纪律"必须问"例外）。

> **反模式速查**：`return R.ok(emptyList)` 表达"查询失败/依赖挂了"｜前端 `catch(e){ list=[] }` 吞错渲染空态｜错误提示写 `order-center 连接失败`（系统代号）｜`if(!token) return allow()`（fail-open）｜上游改了字段本地仍按旧结构解析。
> **回检**：`code-verification-loop` 维度 4「**错误契约与失败可见性（fail-closed）**」行——专管「错误有没有被表达出来」，四类一并核：① 成功响应表达失败 ② 前端 `catch` 吞错渲染空态 ③ 安全判据 fail-open ④ 上游契约变更后解析失败静默落默认值；**①②③ 判 🔴 Critical、④ 判 🟡 Important**。与同维度「错误处理」行互补不重叠（那行管「错误抛出之后提示友不友好」）。⚠️ 该行**刻意不配脚本**（grep 判不准「这是不是失败分支」，判错方向是假红），靠语义核对 + `dev-manual-testcase`「失败路径 / 依赖不可达 / 权限拒绝」用例（断言错误被正确呈现，而非空态/放行）。**发现残留**按 `/sprint-bugfix`「缺陷处置默认决策纪律」映射表**默认直接修、不问人**。

## 约定 26 — Mock 实现位置选型优先级（项目允许 mock 的合规场景）

- **P0 前端 mock（首选）**：axios/fetch 拦截器 / MSW / 本地 JSON
- **P1 后端 mock（次选）**：后端运行时开关控制的 mock 实现类/桩（如 Spring `@Profile("mock")` / WireMock）— 仅当第三方供后端服务端调用（鉴权/代扣/报关/回调验签）；**禁止用环境专属守卫**（如 `@Profile("dev")`，部署到 prod 时不加载、部署期 Mock 失效）
- **P2 中间件 mock（最后）**：json-server / Mockoon / WireMock standalone，仅长期未交付需团队共享
- **口诀**："前端能拦截就前端拦截"；**同项目后端接口未部署严禁后端写一次性假数据接口**，前端按契约自 mock
- **6 字段标注块必填**：`THIRD_PARTY_MOCK`（vendor/api/since/expected_ready/owner/REMOVE_WHEN）；后端未部署的 `DEV_MOCK` 带 since/owner/REMOVE_WHEN
- **30% 工时上限**：Mock 是临时占位，不投入超过真实对接 30% 工时
- **★ 守卫策略按标记分流（⛔ 两类目的相反，绝不能混用）**——两个上游 SKILL 同一口径，单一信源 = `code-verification-loop` 维度 2B + `dev-execution-planner`「情况 0 / 情况 1」：
  - **`THIRD_PARTY_MOCK`（第三方未交付）→ 必须运行时开关**（前端 env `VITE_THIRD_PARTY_MOCK_ENABLED` / 后端 `@Profile("mock")`）。它**要活到 UAT/Demo**，用构建期守卫会让它部署后失效。⛔ 严禁 `import.meta.env.DEV` / `@Profile("dev")` 这类构建期或环境专属守卫 → 机器门判 **Critical**。
  - **`DEV_MOCK`（同项目后端接口未部署）→ 应当构建期裁掉**。它**绝不能进生产**，`if (import.meta.env.DEV)` 正是**要求的合规形态**；反过来给它套运行时开关才该提示（那意味着这个 dev mock 在生产有机会被打开）→ 机器门判 **Important**（`dev_mock_runtime_switch`）。
  - ⛔ **别拿其中一类的结论去套另一类**：扫描器「构建期守卫 = Critical」**只对 `THIRD_PARTY_MOCK` 成立**。
- **★ 全生命周期 4 阶段**（`dev-manual-testcase` + `code-verification-loop` 维度 2B 核验）：① 开发期 Mock → ② 开发期切真实 → ③ 部署期 Mock（UAT/Demo）→ ④ 真实对接后清理验证（代码/fixture/开关/拦截全删 + grep 验证）。`.env.*` baseURL 已切真实但 mock 任一残留 → **Critical** 回 `/sprint-bugfix`
  - **★ 阶段②/④ 必触发约定 22 文档级联（不止清代码）**：切真实不是"改改 baseURL 删删 mock"就完了——按约定 22「第三方 Mock→真实对接」实质变更走文档级联（级联层级见约定 22，此处不复述）。**分工**：代码侧 Mock 残留由 `code-verification-loop` 维度 2B 核验；**文档侧**（详细设计/接口设计仍写 Mock）由约定 22 的 `/sprint-dev` Step X.0.0 维度 6 开发期回写 + `/version` Step 3.3.10 发布期收敛兜底。**只清代码不回写设计 = 违反约定 22**。
- 详规跨 `dev-logic-architect` / `dev-execution-planner` / `code-verification-loop` / `dev-manual-testcase` 4 SKILL + `third-party-mock-protocol.md`。

## 约定 28 — 实现层"已有技术栈/组件复用优先"原则

视觉/功能须与原型一致（约定 4），但**实现层优先用项目已有技术栈和组件**，不强行引入原型用而项目没有的库（前后端通用）。

- **★ 作用域仅限"实现选型层"，不豁免约定 4 的视觉 + 内容 + 操作逻辑 三层对齐（铁律，消除误读）**：本约定只管**"用哪个库/组件去实现"**（如原型用 Antd `<Table>` → 项目改用 Element Plus `<el-table>`）；**绝不**延伸到**"视觉观感也用组件库默认"**、更**不**豁免**"原型内容/功能覆盖"与"操作逻辑/交互行为一致"**。**"用项目已有组件" ≠ "用组件库默认观感" ≠ "可以少做原型上的区块/列/字段/交互态" ≠ "可以简化/改原型的操作流程"**——约定 4「对齐原型 = 视觉 + 内容 + 操作逻辑 三层」下：① 视觉层 L1（颜色/主色/字号/行高/间距/圆角/阴影/布局）仍须严格对齐原型 `code/`，L2 组件默认样式主题 token 取自原型体系；② 内容层原型可见元素除显式裁剪外一个不许漏；③ 操作逻辑层原型的交互行为/流程除显式标注外须与原型一致、不得借"换组件"简化。把本约定放大成"视觉也用默认 / 内容可以砍 / 流程可以简化"都是错误理解。
- **核心立场**：原型代码是功能+视觉参考，**不是**技术栈选型依据（同项目并存两套同功能库——如两个 UI 组件库 / 两个 ORM / 两个日期库——是维护噩梦）
- **典型映射**（以原型→项目为例）：原型用某 UI 组件库 → 改用项目组件库的等价组件；原型用某图表库 → 复用项目已有图表组件；原型用某 HTTP 客户端 → 改用项目已封装的；原型用某代码生成库而项目无 → 手写等价代码
- **判定**：前端看依赖清单（如 `package.json`）+ 公共目录（`components`/`composables`/`utils` 等）；后端看依赖清单（如 `pom.xml`/`build.gradle`）+ 已有工具类/公共组件
- **边界**：已有栈能满足（哪怕多写几行）→ **禁止**引新库；已有栈根本不支持 → 引新库前必须 `AskUserQuestion` 同意 + 写 `systemPatterns.md` ADR；未询问未写 ADR 自行引依赖 = 禁止
- 具体语言的等价复用/引库判定示例参见 `agents/frontend.md`/`agents/backend.md` 核心原则；`code-verification-loop` 维度 4 grep 新增 import/依赖是否在 baseline。

## 约定 29 — 历史死代码识别与处置（重做型开发铁律）

开发的板块/页面/接口在历史版本已有同名/同语义代码时，先做死代码识别**再**写新代码，**禁止**在旧文件上叠加新内容（约定 28 复用前提是"仍在使用"，死代码不算可复用）。

- **死代码 4 信号**（任一命中即死代码；④ 是强信号，命中即强制走 B）：① 无菜单入口 ② 无父组件/调用方引用（前端无 import、后端无注入/无调用，如 Spring 无 `@Autowired`）③ 无路由引用 / 无外部调用方 ④ 需求/设计/计划显式标"重做/重构"
- **3 类处置**：

  | 情形 | 旧代码状态 | 需求意图 | 处置 | 弹问询 |
  |---|---|---|---|---|
  | A | 仍在使用（4 信号不命中）| 增量增强 | 按约定 28 复用、不重做 | 否 |
  | B | 死代码（任一物理信号命中）| 重做 | **先 `git rm` 旧文件**（组件/路由/接口/服务/DTO/测试/SQL）**再**写全新代码、严禁叠加 | 否（自动）|
  | C | 仍在使用 + ④ 命中（显式重构）| 兼容重构 | "新版并存 → 切流量 → 删旧版" | **是**（让用户选）|

- **判定时机**：`/sprint-dev` Phase 0A 后新增 **Phase 0A.5「死代码扫描决策门」**，结果写 `*事实清单.md`「死代码删除清单」段；B 自动 `git rm` 留档、C 弹问询
- **回检**：`code-verification-loop` 维度 4「死代码/死引用残留」grep 新代码是否引用旧组件/class/路由/字段 → Critical 回 `/sprint-bugfix`
- **留档**：`*事实清单.md` + Sprint 归档报告「死代码清理」段（不写 ADR）。具体语言的死代码识别/处置示例参见 `agents/frontend.md`/`agents/backend.md` 核心原则。

## 约定 35 — 运行时验证纪律（开发期默认只静态验证；不擅自启动前后端服务、不完整构建）

开发/验证代码时**默认只做静态验证**：类型检查（`vue-tsc --noEmit` / `tsc --noEmit` / `check_di_resolvability.py` 等确定性脚本）、语法、lint。**★ Java 侧的编译验证命令 = `mvn -q compiler:compile`，⛔ 不是 `mvn compile`**：后者并非「只编译」——会跑完 `validate → generate-sources → process-sources → generate-resources → compile` 整条 lifecycle，**绑在这些相上的插件全部执行**；最常见的 `frontend-maven-plugin` 官方默认就绑 `generate-resources`，于是它会真的去跑 `npm install` + `npm run build`——**一条自称「不打包」的命令直接触发本条②禁止的完整构建**。`compiler:compile` 直调插件 goal、**不走 lifecycle**，是唯一有确定性保证的写法。⚠️ **别拿 grep pom 的结果当放行依据**——插件可以用自己的默认相绑定、pom 里根本不写 `<phase>`，**grep 只能证伪不能证实**。⛔ 也别写 `mvn -o -q compile -D<跳过属性>`：跳过属性因项目而异，猜错即触发构建。**命令选择判据（含三路决策表与「项目真的依赖 generate-sources 产码时开发期不做编译验证、交 CI」这一档）单一信源 = `dev-execution-planner` 的 `references/stack-java-spring.md`「二、开发期轻量验证」**，本条不复述。⚠️ **第三档别漏**：项目真的依赖 `generate-sources` 产码时（protobuf / jOOQ / OpenAPI codegen / MapStruct 走 `<execution>` 级 `annotationProcessorPaths`），`compiler:compile` 会漏掉生成源码而**假红**（报 `cannot find symbol`、缺失符号来自 `target/generated-sources/`）、`mvn compile` 又触发全量构建——两条都不成立，**开发期不做编译验证、交 CI**。Java 装配类问题另有 `check_di_resolvability.py`（纯 grep、零构建）覆盖。**除非用户显式要求，绝对禁止下列两类独立动作**：

| 禁止项 | 典型命令（技术栈中立示例） | 危害 |
|---|---|---|
| **① 启动前后端服务** | `npm run dev` / `pnpm dev` / `yarn dev` / `vite`〔无 `build` 子命令〕/ `npx vite` / `vue-cli-service serve` / `mvn spring-boot:run` / `gradle bootRun` / `python manage.py runserver` / `flask run` / `nodemon` / `node server.js` 等 dev server / 后端常驻进程 | **抢端口 / 与用户已运行服务冲突 / 常驻进程占资源 / 前台阻塞会话 tick / 把机器搞卡**（真实事故：为"验证 UI"擅自 `npx vite` 抢端口致开发机卡死） |
| **② 完整打包构建** | `npm run build` / `pnpm build` / `vite build` / `mvn package` / `mvn install` / `gradle build` / `gradle assemble` | OOM / 耗资源 |

**需要运行时 / 浏览器验证时的正确路径（按优先级）**：
- **(a) 已部署环境**：CICD 部署后的地址 / PRD `deployment` 已配 URL / 测试环境；
- **(b) 用户已在运行的服务**：**先探端口是否已有服务**（`lsof -i:<port>` / `curl -sf localhost:<port>`），**有则复用、绝不另起**；
- **(c) 两者都无** → **必须先 `AskUserQuestion` 征得同意，由用户确认如何启动 / 由用户自己启动，AI 绝不自起**。

**唯一例外（已授权）**：PRD `autopilot_decisions.deployment.mode=local` 这类**用户显式声明的本地部署模式**（`/sprint-aiauto-test` / `/sprint-autopilot` 场景，命令端已按"先探端口、幂等复用、`Bash({run_in_background:true})` 后台启动、绝不前台常驻"落地）——属显式授权。**日常 `/sprint-dev`、`/sprint-bugfix`、即席改动中 AI 为验证而自起服务，一律未授权、禁止**。

**★ Bash 启动常驻服务前的自检（确定性防线）**：执行任何"① 启动服务类"命令前必须先自问——`是否用户显式要求 / 是否命中 mode=local 授权例外？` 否 → **中止该命令，改走上面 (a)/(b)/(c)**（(c) 先 `AskUserQuestion`）。**绝不**以"我需要看看 UI 效果 / 验证一下运行时"为由自起。

- **UI 改动的验证正确路径**（对齐约定 4 视觉还原）：静态比对 style/token（见 `agents/frontend.md`）+ 走已部署 / 已运行环境看真实渲染；**绝不**把"验证 UI"等同于"本地起 dev server + 浏览器"。
### ★ 静态验证工具的阳性对照（把「没问题」与「根本没跑」区分开）

**任何静态验证工具在被当作「零新增 / 通过」的判据之前，必须先做一次阳性对照**：
**植入一个必然被抓到的错误 → 确认工具确实报出来 → 移除 → 再采信它的结果。**

**Why（这条不是洁癖，是这类工具的失效形态决定的）**：类型检查 / lint / 契约扫描
**失效时的输出恰好是「0 错误」**，与「通过」在字面上**完全一致**——
"未执行"被完美伪装成"无问题"。真实样本：

| 形态 | 实际发生了什么 | 看起来是什么 |
|---|---|---|
| `vue-tsc` 默认 `tsconfig.json` 的 `types` 指向未安装的包 → 提前中止 | **源码零检查** | 「0 错误」，于是「19≡19 / 22≡22 零新增」这类记录**全是假绿** |
| 上游返回 400 被外层 `catch` 吞掉 | 一条都没取到 | 「0 条」 |
| 用通用子串判断 javadoc 是否进了 Swagger | 判据恒真 | 「已生成」 |

**★ 本项目自带的契约检查脚本已把这件事做成常备能力**：
`.aidp/scripts/check_*.py` **每一个都支持 `--self-check`**——注入一个必然被它抓到的探针，
确认它确实报红，才可以采信它的绿；全量跑 `python3 .aidp/scripts/selfcheck.py`。
骨架用「克隆真实契约树 + 注入」而非手搓最小 fixture：**手搓 fixture 写少一层目录，
检查器就扫不到探针、返回 0 命中，而这与"检查器坏了"完全同形**——本该发现问题的自检自己先假绿。
**尚未登记探针 / 需 git 夹具无法登记的脚本会被点名报出**（`unregistered` / `unsupported`），
⛔ 覆盖缺口刻意可见，不许静默当成"全都自检过了"。

**★ 基线对照另须先判定「基线那次真的跑起来了」**：拿改动前后做差值对比时，
先确认基线那次**确有执行**（输出行数是否合理、有无「路径不存在 / 未执行」类信号）——
空结果 / 未执行信号一律**拒绝比较**，不得给出差值。
真实事故：用 `git stash` 取基线时把验证依赖的**未跟踪配置文件**一起带走了，
基线那次实际未执行却产出一个看似正常的基线，差点把假的「错误变少了」当成好消息。

⛔ **不做阳性对照就无法区分「没问题」与「根本没跑」**——两者输出一模一样。
本条与「反向断言必须配阳性对照」同源：**期望值为 0 的判据，必须先证明它能不为 0。**

### ★ 格式化类 autofix 只允许作用于【本次新建】的文件

`eslint --fix` / `prettier --write` / `mvn spotless:apply` / `gofmt -w` / `black` 等
**格式化类 autofix，只允许跑在本次新建的文件上**。

对**既有文件**：只手工消除**自己引入的那几处**告警，⛔ **不得整文件 autofix**。

**Why**：整文件 autofix 会把无关的历史格式问题一并卷进本次 diff——
真实事故：为消除 **2 处** lint 告警对一个 **2800 行**的既有文件跑 `eslint --fix`，
产生 **+343 / −118 行**与本次需求完全无关的改动（已回退重做）。后果有三：
① review 无法区分「需求改动」与「格式噪音」；② 污染 `git blame`，后来者查不到真实改动人；
③ 放大冲突面。**存量格式问题应独立立项统一处理**，不搭需求改动的车。

### ★ 批量替换与切片编辑：锚点唯一 ≠ 替换对了

**「工具成功」与「做对了事」是两回事。** 自动化编辑必须满足下列四条：

1. **文本替换用精确整段匹配**；使用「起点索引 → 终点索引」的**切片替换**时，
   **必须先确认区间内没有别的内容**（打印区间原文再替换）。
2. **`assert 出现次数 == 1` 只能证明锚点唯一，证明不了被替换掉的正是你以为的那一段。**
   区间型编辑要断言的是**被替换内容本身**（长度、首尾行、条目数），不是锚点计数。
3. **结构性内容改完必须校验结构本身**（编号是否连续、条目数是否符合预期、清单项数是否守恒），
   ⛔ 不能只看脚本有没有报错——脚本报错只覆盖"跑挂了"，覆盖不了"跑通了但吞了东西"。
   机器门：`python3 .aidp/scripts/check_doc_numbering.py --json`（重号 = ERROR、跳号 = WARN）。
4. **单文件改动行数远超本次预期量级（> 3× 声明的改动面）时须停下确认**，
   排除格式化噪音或区间吞并，再继续。

**Why（真实事故）**：用切片替换某个编号条目时，把插在区间内的**另外两条条目一并吞掉**，
脚本 `assert` 通过、照常打印「成功」⇒ **跨 4 个迭代无人发觉**，直到有人去数编号才发现。
这类失效的特征与本约定其余各条同源：**失败形态是"看起来成功"**，不是报错。

- **回检**：`verify.py::check_project_claude_aidp_conflict`（关键词库含**完整构建类 + 服务启动类**双组，扫根级项目记忆文件（AGENTS.md / CLAUDE.md）是否把起服务/完整构建列为开发期例行命令 → WARN）+ `agents/frontend.md`·`agents/backend.md` 验证步骤纪律。**运行时验证唯一合规生产者 = `/sprint-aiauto-test`（且部署环境就绪），静态验收 SKILL（`code-verification-loop`）全程不起服务。**

## 约定 39 — 通用还原度规则集（R1–R13，与业务领域无关）

> **本段是约定 39 的单一信源。** 全部 13 条来自下游一个真实项目两个月 71 条已关闭缺陷的反向归纳，
> 只保留**与业务领域完全无关**的那部分（30 条缺陷 → 13 条规则），故可对所有下游项目生效。
> 依赖领域知识的那两类（跨系统账号生命周期、业务口径本身）**刻意不下沉**——它们该由各项目自己维护端到端冒烟链路。
>
> **★ 为什么需要这一条，而不是「按约定 4 做好就行」**：约定 4 已要求三层对齐并强制产出「原型内容基线」，
> 方向对、粒度不够。实际失效模式是——**基线写成散文式整体描述，核对时只能"看着像不像"，
> 于是漏掉的永远是单个元素**（少一列、少一个按钮、少一个 tooltip）。本条把「整体判断」换成「逐项打勾」。
>
> **★ 定性依据（决定了本条的重心）**：那 71 条里 **96%（68/71）的发现深度是「正常发现」**——
> 走一遍正常流程就会碰到，不需要刁钻构造，却全部漏到 QA 侧才被发现。
> **问题不是「测得不够狠」，是「测得太晚」**。故本条的落点重心在**开发期自检 + 规划期清单**，而非加测试强度。

### R1 六类元素守恒清单

「原型内容基线」必须按页面拆成**六类**逐项列出、实现后逐项打勾，不得写成整段描述。
六类的定义与产出物结构见 **`.aidp/rules/frontend.md` 约定 4「原型内容基线」条**（单一信源，此处不复制）。
生产者 = `agents/ui.md` 流程 A Step 1.5；规划期核对 = `agents/version-auditor.md` 审计 F（逐项核对 + 输出缺失明细）。

### R2 状态类字段必须有视觉区分

枚举/状态字段渲染为 tag / badge / 进度条时，不同取值**必须有可区分的视觉编码**；禁止所有取值共用同一 `type` / 颜色。
- **判据（机器）**：`check_ui_fidelity.py --check R2` —— **内容随数据变化、而 `type`/`color` 是字面量常量** → Important。
  写死内容 + 写死颜色（固定角标）正当，动态内容 + 动态颜色正确，只有前者动后者不动才是缺陷特征。
- 真实反例：已生效 / 未生效标签同色；完成率进度条无颜色区分。

### R3 长文本截断必须配套完整可读途径

任何承载**用户输入内容**（姓名、名称、备注、原因说明）的展示位必须显式声明截断策略；
采用省略号截断的**必须**同时提供 `title` 或 tooltip 给出完整内容。
- **判据（机器）**：`check_ui_fidelity.py --check R3` —— 截断（`text-overflow:ellipsis` / `-webkit-line-clamp` / `truncate` 原子类）
  且同节点或父节点无 `title`/tooltip → Important。
- 真实反例：员工姓名过长展示不全。**同一模式两个月内复发**（组织树节点的灰字提示被横向截断，
  管理员看不全「为何不可选」）——**复发是本条存在的理由**：它不是偶发，是缺规则。

### R4 破坏性与不可逆操作必须二次确认

删除、批量操作、配置保存、状态不可逆流转，一律需二次确认。
**原型画了二次确认 = 必须实现；原型没画但操作不可逆 = 也必须加**（后半句是本条独立于约定 4 的部分）。
- 真实反例：企业员工欠费额度配置保存无二次确认（与原型不符）。

### R5 失效实体的操作入口必须拦截

已下架 / 已删除 / 已过期 / 已失效的实体，其详情、跳转、购买、开通等入口必须**隐藏或禁用**；
不得「按钮还在、点了报错或跳到空页」。
- 真实反例：运营侧已下架的产品，控制台仍可点详情并跳转成功。

### R6 被引用实体已删除时必须降级为可读展示

引用的上游实体被删除后，展示层**不得裸露编码 / ID / 空值**，必须降级为可读名称（保留快照名，或显式展示「已删除的 XX」）。
- 典型反例：上游系统已删除的商品，本系统列表展示商品编码而非原有名称。

### R7 加载未完成时不得渲染「看起来是真的」的脏数据

异步数据到达前，不得用旧值、缓存值或默认值渲染出**与最终结果不一致**的内容；
应展示骨架屏 / 空态 / 隐藏，而非先给一个会跳变的数字。
- **口诀（下游独立总结、直接采纳）**：**未取到配置先隐藏——少显示一个按钮无伤，闪出一个点了就死的按钮才是要消灭的现象。**
- 真实反例：按量计费开通页加载中展示 14 个模型，加载完只剩 3 个。

### R8 编辑成功后当前视图必须自动同步

新增 / 编辑 / 删除成功后，当前列表或详情必须刷新到最新状态，不得要求用户切换页面、刷新浏览器才能看到变更。
- 真实反例：部门名称编辑后页面不同步，需切换页面才更新。

### R9 存量数据兼容性验证

改动数据结构、新增必填字段、收窄取值范围时，必须显式验证**改动前产生的存量数据**在新代码路径下的表现，
并在用例中留一条存量数据场景。
- 真实反例：智能体点击「旧数据」开通直接报错。

### R10 导出必须导全量，且与页面严格一致

① 导出范围 = 当前**筛选条件下的全量**，而非当前分页；② 导出的字段、单位、精度、脱敏规则必须与页面展示一致。
- **判据（机器）**：`check_ui_fidelity.py --check R10` —— 导出方法体内透传 `pageNo`/`pageSize`/`PageHelper`/`Pageable`/`limit` → **Critical**。
  窗口内出现循环 / `hasNext` / `MAX_VALUE` 等「翻页捞全量」特征则放行（那是正当写法）。
- 真实反例：积分分配导出只导出当前页；导出的「分配额度」列没有单位。

### R11 数值字段五要素必须在详细设计中显式声明

任何展示数字的字段，详细设计必须写清 **单位 / 小数精度 / 时间窗 / 统计范围 / 取数粒度**，缺任一项即视为设计不完整。
- 真实反例（同一项目两个月内 12 条，是单类最高频的根因）：预付费明细金额单位写「元」实为积分；
  三处小数位互不一致；趋势图漏统计某日期之前的数据；积分统计漏掉「已回收」；
  「最近购买时间」误用 SKU 级首次购买时间冒充订单级购买时间。
- **落点**：`dev-logic-architect`（上游 SKILL）—— 与其已有的「货币金额字段整数化」同族。

### R12 同一指标跨页面必须同源

同一业务指标在多个页面/组件出现时，必须来自**同一取数口径**；禁止各页面各算一遍。
- **口诀（下游独立总结、直接采纳）**：**判据全站唯一化，不在 N 处各写一遍**（现有缺陷正是各写一遍、结果漏了一个入口）。
  与约定 20「判据类逻辑禁止平行实现」同源，此为其**数据口径维度**的延伸。
- 真实反例：总览页 token 调用量 / 模型管理页用量 / 用量监控页三者互不一致；活动卡片「已结束场次数」与列表数量不一致。

### R13 列表页必须声明数据量级与分页策略

详细设计中每个列表页须写明**预期最大数据量级**及分页 / 虚拟滚动策略；
存在「一个企业几千员工」这类量级的页面，用例中必须有大数据量场景。
- 真实反例：员工与部门较多的账号，用户与组织页加载缓慢；员工 Key 加载慢、删除后刷新慢。

## 约定 40 — 上游/第三方接口调用日志强制规范

**一句话**：只要调用了**进程外**的第三方/上游接口，**无论成功还是失败**，都必须打印**完整 URL 与入参、出参**；
入参或出参是文件等二进制流时，只打印文件名等**元信息**。

> **定位（与约定 23 姊妹条的边界，别混用）**：姊妹条管「失败必须被**用户**看见」——错误契约、不伪装成 200 空数据、fail-closed；
> 本条管「调用必须被**日志**看见」——**成功路径同样要打**。两者互补：一次调用可以完全符合姊妹条（失败时正确报错给前端），
> 却依然让排查无从下手（成功路径零日志，看不出到底有没有调、调的哪个环境）。
>
> **★ 为什么必须成规则、而不是靠自觉**：真实样本里同一个仓库、同一个团队的 4 个上游客户端写出了 4 种规格——
> 一个双向 `>>>`/`<<<` 带耗时（好范例）、一个**四条日志全是 error**（成功路径零日志）、一个**一行日志都没有**、其余各写各的。
> **正确写法当时就存在于同一个仓库里**，但因为它只是"某个人写得比较好"而不是一条规则，隔壁新写的客户端依然零日志。
> 代价是现场报「看不到数据」时，后台日志**无法区分**「① 前端没发请求 ② 请求没到后端 ③ 后端没调上游 ④ 上游返回空」——
> 四种情况的日志表现都是「什么都没有」，只能读源码反推 + 让现场开 F12 抓包。**打了日志的话一条 grep 就结束。**

### 40.1 适用范围

本应用作为**调用方**发起的、指向**进程外依赖**的调用：第三方/上游平台 HTTP API · 内部微服务 RPC/Feign ·
对象存储（MinIO/OSS/S3）· 短信/邮件/消息网关/推送 · 支付/OAuth·SSO/鉴权中心。

**不含**本地数据库与本地缓存——它们有各自成熟的 SQL / 命令日志机制，重复打只会稀释信噪比。

### 40.2 必打字段

| 段 | 必打 |
|---|---|
| **请求段** | **完整 URL（含 query string）** · method · 请求体 · 关键请求头（按需）|
| **响应段** | URL 或配对标识 · HTTP status · **上游业务 code** · 响应体 · **耗时 ms** |

- ⛔ **成功和失败都要打**；失败额外带异常栈。
- ⛔ **URL 必须完整**：只打 path 不打 base-url 是最常见的偷懒写法，但多环境排查时
  **"到底调的哪个环境的上游"恰恰是第一个要确认的事**。
- **请求与响应必须可配对**：并发下 `>>>` 与 `<<<` 会交错，须带 traceId / 调用序号，使一次调用的两行能被 grep 到一起。

### 40.3 级别：成功 INFO，失败 WARN/ERROR

⛔ **不接受「成功路径用 DEBUG」这个折中**：生产默认 INFO，配成 DEBUG 等于生产环境看不到，
而**需要看日志的时刻永远在生产**。担心日志量走 40.5 截断与 40.7 例外，**不要靠降级别解决**。

### 40.4 二进制 / 大对象降级

入参或出参为文件流 / 字节数组 / 上传对象 / `multipart/form-data` / `application/octet-stream` 时
**不打内容**，只打元信息：**文件名 · 大小(bytes) · contentType · 目标路径或 objectName · 存储桶**。
超大文本响应（导出、批量拉取）同理，只打**条数 / 字节数**。

### 40.5 截断

文本体超阈值（建议 2000~4096 字节）截断，并**标注原始长度**（如 `...(truncated, total=15234)`）——
标注原长很重要，否则无法判断关键字段是不是被截掉了。

### 40.6 ★ 脱敏必须与本条同时落地（否则规则一落地就变成合规事故）

「打印完整入参出参」若不配套脱敏，会把凭据和个人信息写进日志。**这不是可选项**：
真实样本里那个走短信通道的服务，一旦按本条给它补上入参日志，**短信验证码就会明文落盘**——
而实际上它**在补日志之前就已经泄漏了**（`log.warn("...验证码仅存入Redis未实际发送: phone={}, code={}", phone, code)`）。

- **默认掩码字段名黑名单**（大小写不敏感、支持嵌套 JSON）：`password` `passwd` `pwd` `secret` `appSecret`
  `token` `accessToken` `refreshToken` `authorization` `apiKey` `privateKey` `signature` `verifyCode` `smsCode`
  `captcha` `idCard` `idNo` `bankCard` `cardNo` `phone` `mobile` `email`。黑名单须可由项目配置扩展。
- **掩码策略**：保留首尾各 3 位、中间 `***`。
- **掩码写在赋值处也算合规**（`String tokenPreview = t.substring(0,6) + "***" + t.substring(n)` 后再打印）。

### 40.7 实现方式：拦截器优先，⛔ 禁止每个 client 各写各的

优先在 **HTTP 客户端层挂一次拦截器/过滤器**，一处接线、全局生效；不具备拦截点的 SDK（对象存储、短信等）
包一层**薄封装**统一打点。**⛔ 不接受「每个 client 手写两行 log」**——真实样本的 4 种规格、2 个直接漏掉，
正是这条路走出来的。各框架的具体挂载点、**以及"挂了拦截器却读不到响应体"这个必踩的坑**，
见 **`.aidp/rules/backend.md` 约定 40 实现侧**（编辑后端代码时自动加载）；参考实现骨架见
**`.aidp/reference/上游调用日志参考实现.md`**。

### 40.8 例外（须在代码注释写明理由）

- **高频轮询类调用**（心跳、健康检查、就绪探针）：允许降采样（每 N 次打一次）或降级为 DEBUG。
- **响应体天然巨大**（导出、全量同步）：按 40.4 只打元信息。

⛔ 除以上两类外，**不接受**以「日志量大」「上线赶时间」「这个接口不重要」为由豁免。
