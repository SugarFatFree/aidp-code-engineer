## 约定 4 — UI 优先级

- **⚠️ 前提（铁律）**：视觉对齐建立在「遵守研发需求的功能完整性/字段/流程/业务规则/权限/状态机」之上。视觉基准没画但需求写了的 → 按需求实现；视觉画了但需求禁止/未涵盖的 → 视觉让位需求 + 触发约定 22 级联补回。绝不为"对齐视觉"漏需求功能，也绝不因"视觉好看"违背需求规则。
- **⚠️ 字段/列裁剪三件套（铁律）**：原型可见的列表列 / 表单字段，**任何一次裁剪、改名、被接口字段覆盖、或"接口暂不支持"的删减都禁止静默发生**，必须同时满足三件套——① **需求文档留痕**：在研发需求保留一张「原型字段 → 处置」对照表（处置 ∈ 保留 / 裁剪 / 前端计算还原 / 请第三方补；裁剪项标注裁剪原因 + 待产品确认）② **产品确认**：经决策门（C/D 类用户显式选）确认，不得 AI 自行裁剪 ③ **触发约定 22 级联**：回写研发需求 → 详细设计 → 研发执行计划 → 研发自测用例。绝不"接口少了字段就跟着把原型列删掉、文档却不留痕"。
  - **★ 三件套作用域补齐双重盲区（堵"研发需求字段漏列/增列"静默漂移）**：三件套**不止覆盖"原型 → 实现"，同样覆盖"PRD 条目 → 研发需求"「研发需求字段 → 详细设计/实现"每一段转化**（上游任一层列出的字段/列，下游都不许静默增删）；**也不止管"裁剪（少列）"，同样管"未经确认的增列（多列）"**——**漏列**（研发需求/PRD 有、实现无，如「参训课程数 enrolledCount」漏渲染）与**增列**（研发需求/PRD 均无、实现自造，如凭空多出「总学习时长」列）**两个方向都属违规**，都须留痕 + 产品确认 + 约定 22 级联。**回检三处**：规划期 `version-auditor` C-4（PRD 条目→研发需求）/ C-5（研发需求字段→详细设计，双向：漏列 Critical、增列 Important）；开发/测试期 `dev-manual-testcase`「列集合 vs 需求字段核对」用例 + `code-verification-loop`「字段/列对账」维度。**统一原则**：每段转化都做**反向覆盖校验**（以上游为基准查下游是否 100% 落点），而非只做正向引用校验（以下游为基准查是否有出处）——方向反了才会让漏列/增列连穿多关。
- **⚠️ ★ "对齐原型" = 视觉 + 内容 + 操作逻辑 三层（铁律，堵"对齐被窄化为视觉/内容、原型行为被简化改样"的口子）**：**"对齐原型"从来不只是"长得像""东西都在"，还包括"操作起来行为一致"**——除非走下面裁剪三件套显式说明，三层**都**须与原型一致：
  - **① 视觉层**：颜色/主色/字号/行高/间距/圆角/阴影/布局（L1，见下「视觉对齐 L1/L2」+「设计令牌提取铁律」）。
  - **② 内容/功能覆盖层**：原型 `code/` 里可见的**区块/卡片、表格列、表单字段、筛选/排序项、按钮与次级操作、空态/加载/错误/成功等交互态、跳转入口**，**一个都不许静默漏掉或简化**。
  - **③ 操作逻辑/交互行为层（★ 无特殊说明须与原型一致）**：原型元素的**行为与交互流**——点击/提交后的反馈与跳转、表单校验规则与时机、字段联动（选 A 显隐/联动 B）、条件显隐与禁用条件、筛选/排序/分页/搜索的行为、编辑-保存-取消/新增-删除/批量操作流、二次确认流、默认值与初始态、多步向导步序、错误处理流、权限态差异——**除非显式标注"改为 X / 裁剪 / 延期"，否则实现的操作逻辑必须与原型一致，禁止擅自简化、改流程、砍交互步骤或改默认行为**。内容层保证"元素在"，本层保证"行为对"，是不同的轴。
  - **④ 说明性文案正确性（★ 判据 = 与当前实际行为一致，而非与原型/上一版一致 — 堵"口径变了、解释文案没跟"的口子）**：tooltip / 区块副标题 / 图例注释 / 空态文案 / 单位标注 / 导出表头 / 帮助文档 / 筛选标签 / 告警提示等**说明性文案**属**内容层**，但其正确性判据与"元素是否存在"不同——**是"与当前实际行为/数据口径一致"**。原型和历史版本的文案都可能已过期，"和原型一致 / 和上一版一致"**不构成正确**。统计口径 / 单位 / 默认值 / 范围 / 状态机语义等**语义变更（约定 22 第三类触发，无新增元素）**时，代码改了数值/行为、页面却零新增元素，最易只改取数忘改解释文案 → 文案与实际展示值相反、误导用户。此时必须**同步核对并改写所有解释该数值/行为的文案**，**旧语义字样残留 = 缺陷**。回检 = `code-verification-loop`「文案与数据口径一致性」维度（grep 改了口径的展示位是否仍含被推翻表述）+ `dev-manual-testcase` **反向断言**用例（旧语义字样出现即判 Critical，与约定 33 原型内容基线反向断言同思路、此为其文案维度延伸）。
  - **三层都不因约定 28「用项目已有组件」豁免，也不因「研发需求没逐字转写」就允许丢失/简化**（原型可见即行为 = 隐含需求，需求没写不等于不做、不等于可以随意改逻辑）。
  - **★★ 规划期铁律（根因在源头：漏写 = 违规，不是"默认不做"）**：**版本规划时，若未对某原型元素/功能/操作逻辑特意标注"裁剪/延期/改为 X"，则默认必须实现原型的全部功能、内容与操作逻辑**。原型 `code/` 是**功能、内容与交互行为的事实基线之一**（与 PRD 并列）；规划期把原型元素/行为"漏写进研发需求/详细设计" = **违规**（设计本身就不全，开发只能照不全的设计做、系统性漏内容或简化流程），**绝不视为"没写=默认不做/可随意改逻辑"**。要取舍或改某原型板块/字段/流程 → 规划期必须 `AskUserQuestion` 让用户显式选，**默认项恒为"照原型实现"**，严禁命令端/AI 自行判"不做/简化"。
  - **★ 强制产出物「原型内容基线」（规划期先清点、后转写/开发，作全程验收基线）**：有原型 `code/` 时（尤其情形 B/C），**版本规划期**（经 `/sprint-requirements` 或 `/sprint-design`，由 UI Agent 流程 A Step 1.5 落地）必须先**逐页遍历原型**产出 `docs/design/detail/{version}/NN_原型内容基线.md`（**属详细设计目录的一部分，遵约定 14/15**：`NN` 为**实际续编序号、不写死**——命令端归一时按该目录现存最大序号自动续编分配〔设计三态 `01_详细设计`/`02_数据库设计`/`03_接口设计` 按约定 14 占各自语义位，基线续编其后、典型 `04_`〕，**实际序号以 `00_索引.md` 为准**；**必须登记进详细设计 `00_索引.md`**——文件清单 + 生成时间 + 主标识 + 一句话范围〔标注"规划基线/前置输入"〕，并被研发需求 `00_索引.md` 交叉引用）——逐页 → **① 全部可见元素清单**（区块/列/字段/筛选/按钮/交互态/跳转）**② 该页/元素的操作逻辑与交互流**（点击→反馈/跳转、校验规则与时机、字段联动、条件显隐/禁用、筛选排序分页行为、增删改-保存-取消流、二次确认、默认值/初始态、多步步序、错误处理）→ **每项标处置**（`实现`（默认，行为照原型）/ `裁剪`〔原因 + 待产品确认〕/ `延期`〔移至哪版〕/ `改为 X`〔说明差异 + 产品确认〕）。**裁剪/延期/改逻辑项必须走上面「字段/列裁剪三件套」**（留痕 + 产品确认门 + 约定 22 级联）；**未显式标注的元素与操作逻辑默认必须照原型实现**。该基线**随版本规划产物提交、登记进详细设计 `00_索引.md` 并被研发需求 `00_索引.md` 交叉引用**，是研发需求/详细设计转写的**全覆盖依据** + 前端开发**强制输入** + `/sprint-test`/研发自测的**验收基线**，禁止绕过。
  - **★★ 基线结构 = 六类逐项清单，不是散文（约定 39 R1 的单一信源<!-- singlesource-scope: R1六类 -->；堵"整体看着像、单个元素漏掉"）**：基线**必须按页面拆成下列六类分别逐项列出**，每项一行、实现后**逐项打勾**；**禁止写成整段描述性文字**——散文式基线核对时只能"看着像不像"，于是漏掉的永远是单个元素（少一列、少一个按钮、少一个 tooltip）。六类：
    | # | 类别 | 逐项列出什么 |
    |---|---|---|
    | ① | **数据字段** | 列表每一列、详情每一个字段（**逐个列名/字段名**，不写"若干字段"）|
    | ② | **操作入口** | 按钮 / 链接 / 右键菜单 / 行内操作 / **批量操作** / 更多菜单（逐个名称）|
    | ③ | **统计卡片** | 卡片**数量** + **每张卡片的统计口径**（口径必写，见约定 39 R11 五要素）|
    | ④ | **筛选与排序项** | 每一个筛选条件、每一个可排序列（逐个）|
    | ⑤ | **空态 / 加载态 / 错误态** | 每页各态是否存在及其表现（约定 39 R7：加载态不得渲染会跳变的脏数据）|
    | ⑥ | **二次确认弹窗** | 每一处破坏性/不可逆操作的二次确认（约定 39 R4：原型没画但操作不可逆的也必须列）|
    - **每项固定四列**：`页面 → 类别 → 元素名 → 处置（实现/裁剪/延期/改为 X）`，外加实现后回填的 **`✓ 已实现`** 打勾列。
    - **①②④ 三类机器可检**：从清单提字段名/按钮名/筛选项名 → grep 实现模板 → 产出覆盖率；③⑤⑥ 依赖语义判断，由 `version-auditor` 审计 F 逐项核对。
    - **典型反例（这六类各自漏过什么）**：少了「已购商品数」列（①）· 详情缺提交人（①）· 没有导出按钮（②）· 少一个排序按钮（④）· 汇总卡片四个与功规不符（③）· 保存配置缺二次确认（⑥）。
  - **★ 与约定 39 的关系**：本条（约定 4）管**"原型有什么、实现是否都有"**；约定 39 管**"实现出来的东西对不对"**（状态可区分 / 截断可读 / 失效实体拦截 / 导出全量 / 口径同源等 13 条通用还原度规则，与业务领域无关）。二者正交、都要过。详见 `{{AIDP_HOME}}/rules/code.md` 约定 39。
  - **★ 消费原型自带设计交接 manifest**：原型目录若含 `DESIGN-MANIFEST.json` / `DESIGN-HANDOFF.md`（列 `screens`/`appModules`/`requiredStates`/`tokens`/`flows` 等）→ 命令必须**主动读取**、据其生成/校对「原型内容基线」与验收项（`requiredStates` 逐项纳入交互态核对、`flows` 纳入操作逻辑核对），不得只当视觉参考。
  - **回检（三道，覆盖规划期 + 开发期 + 测试期；三层齐查）**：① **规划期** `version-auditor` 新增「原型覆盖度」审计（Critical 硬门）——以「原型内容基线」为准，校验每个未标裁剪/延期/改逻辑的原型**元素、交互态与操作逻辑**是否被**研发需求 + 详细设计**覆盖，"原型有、需求/设计无、未标处置" → Critical 阻塞规划通过（除非 `--skip-audit`）；② **开发期** `/sprint-dev` Step 0.4 逐页对照门（含操作逻辑）；③ **测试期** `code-verification-loop`「内容完整性」逐页核对（原型有/实现无或行为不符/未标处置 → Critical 回 `/sprint-bugfix`，交互态与操作逻辑缺失/被简化同判）+ `dev-manual-testcase` 据基线为每个原型元素/状态/**操作流**生成一条可验证用例。上游 `ux-logic-extractor`/`dev-logic-architect` 转写时须保证「基线」每个"实现"项都有对应功能点/字段/**流程/交互规则**（覆盖到字段、状态与操作逻辑级）。
- **4 种情形**（决策时机：`/sprint-dev` 前端开发前 Step 0 必执行 1 次 / `/version` 阶段；C/D 必须用户显式选，命令端不自动决定；结果写入当前 Sprint UI 规范基线）：
  - **A 有高保真**（`mockup/` 存在）：按 L1/L2 分级对齐高保真；功能/交互参考 `code/`
  - **B 无高保真 + 无 UI 规范**：按 L1/L2 对齐**产品原型代码**（沿用 `code/` 设计语言 + 项目技术栈等价替换）
  - **C 无高保真 + 有 UI 规范 + 有原型 + 用户选"直接对齐原型"**：同 B
  - **D 同上 + 用户选"参考原型 + UI 规范优化"**：UI Agent 流程 C 基于 UI 规范生成高保真到 `mockup/` → 之后按 A
- **★ 情形 B/C 设计令牌提取铁律（先提取、后开发、作验收基线 — 堵"无高保真就退化成组件库默认观感"的口子）**：无高保真 + 对齐产品原型（情形 B、C）时，**前端开发前必须先从原型 `code/` 提取「设计令牌 design tokens」再写页面**，绝不"边写边猜"或直接用组件库默认主题充数：
  - **提取内容**：主色 / 品牌色 / 辅助色 / 文字色（主/次/禁用）/ 背景色 / 边框色、成功·警告·危险·信息语义色、字号阶梯（h1~caption）、行高、间距刻度、圆角等级、阴影等级、字体族 —— 逐项标注**原型来源**（`code/` 里的文件:选择器/变量）。
  - **两份强制产出物**：① `docs/design/detail/{version}/NN_设计令牌.md`（人读基线：token 名→值→原型来源 对照表；**属详细设计目录的一部分，遵约定 14/15**：`NN` 为**实际续编序号、不写死**〔命令端归一续编分配、紧随 `原型内容基线.md`、典型 `05_`〕，**实际序号以 `00_索引.md` 为准**；**必须登记进详细设计 `00_索引.md`**——文件清单 + 生成时间 + 主标识 + 一句话范围〔标注"规划基线/前置输入"〕）② **一份全局主题文件**（按项目技术栈：`src/theme/variables.scss` / `src/styles/tokens.css` CSS 自定义属性 / 组件库 theme 覆写如 Element Plus `$--color-primary`；主题文件属前端代码资产、不进详细设计目录）——**页面样式一律引用主题变量，禁止散落硬编码色值/尺寸**。
  - **强制输入 + 验收基线**：这两份是前端开发的**强制输入**；`code-verification-loop` 维度 4「视觉还原」**对情形 B/C 同样据此强校验 L1**（主色/字号/间距/圆角/布局须取自原型 token，非组件库默认），L1 偏差 Critical。
  - **★ 与约定 28 的边界（消除"用已有组件 ⇒ 视觉也用默认"的误读）**：约定 28「优先用项目已有技术栈/组件」**仅是"组件实现选型层"**（用 Element Plus `<el-table>` 而非引原型的 Antd `<Table>`）；本条视觉对齐是**"观感层"**（颜色/字号/间距/布局/圆角）。**二者正交、后者不因前者豁免**：用项目组件不等于用组件库默认观感——组件默认样式（L2）可用，但其**主题 token 必须取自 L1 原型体系**（见下「L2 主题 token 仍受 L1 约束」）。"用已有组件"省的是实现层引库，不省视觉层对齐。**★ 实现选型层的具体范围 = 仅"内部原子/叶子小组件"可替换为项目等价组件**（白名单见下 L2，含 Layout/Container/Color/Link 等实现载体）；**替换的只是"用哪个组件/机制去实现"，不是"实现成什么样"——页面结构 / 版心与栅格布局的度量 / 视觉体系具体值（主色·字号·行高·间距·圆角·阴影）/ 内容元素 / 操作逻辑 这些"呈现结果"均须对齐原型**（哪怕用项目的 Layout/Container 组件搭栅格、用项目色彩变量承载配色，栅格划分/版心宽度/色值本身仍取自原型，由 L2 硬约束①锁定）。**无特殊说明 + 无高保真 + 无 UI 规范（情形 B）时：样式（含布局）· 内容 · 操作逻辑三层须尽量 100% 还原原型**，唯一合规偏离就是这批叶子小组件的"实现载体替换"。
- **视觉对齐 L1/L2 二层分级**：
  - **L1 大体页面样式（必须严格对齐）**：① 视觉基准出现的元素一个不能少（漏项按约定 22 级联补回）② 设计语言体系（颜色 token/字号/行高/间距/圆角/阴影/字体，**误差 ≤ 2px / 一阶色阶**）③ 页面级布局（栅格/Flex/版心/模块占位）。偏差 → `code-verification-loop` 维度 4「视觉还原」**Critical**，回 `/sprint-bugfix`
  - **L2 组件内部细节（用项目已引入组件默认样式）**：表单/反馈/数据展示/导航各类**内部原子/叶子小组件**（如 Element Plus）默认样式直接用，不强行覆写成原型组件库样子；图标用项目已引入图标库。偏差标 **Important** 不阻塞验收（仅 L1 偏差为 Critical 才强阻塞；除非该 L2 偏差影响到 L1）
    - **★ 可替换叶子组件白名单（约定 28 实现选型层的落地边界 — 只有这批"内部小组件"才允许用项目等价组件替换原型组件库同类件）**：Layout 布局 / Container 布局容器 / Color 色彩 / Link 文字链接 / 单选框 / 多选框 / 下拉选择 / 日期时间选择器 / 进度条 / Tab 页 / Tag / Icon 图标 / 消息提醒 / 计数器 / 开关 / 滑块 / 上传 / 表单 / 列表 / 表格 / 分页 / Alert / Loading / MessageBox 弹框 / Message 消息提示 / NavMenu 导航菜单 / Card 卡片 等**内部叶子小组件**。**替换仍受两条硬约束**：① **主题 token / 布局度量取自 L1 原型体系**（主色/文字色/语义色 + 版心宽度/栅格划分/间距，见下「L2 主题 token 仍受 L1 约束」，不得用组件库默认观感）② **操作逻辑/交互行为仍须与原型一致**（约定 4 操作逻辑层——换的是组件实现、不是行为，禁止借"换组件"简化/改流程）。**★ Layout/Container/Color/Link 是"实现载体"入白名单、非"结构与色值可偏离"**：允许用项目的 `<el-container>`/`<el-row>`/`<el-col>`/`<el-link>`/项目色彩变量机制去**实现**原型的布局与配色，但**栅格如何划分、版心多宽、模块位置、主色/语义色的具体值仍须对齐原型**（由硬约束①锁定），绝不借"Layout 进白名单"就把版心/栅格结构或色值改成组件库默认。**白名单之外一律不替换**：页面结构、区块/卡片编排、内容元素与操作流程都须对齐原型（情形 B 尽量 100% 还原）。
  - **L2 主题 token 仍受 L1 约束**：L2 用默认样式但主题 token（主色/文字色/警告/品牌色）必须取自 L1 体系（如组件库成功色取原型品牌绿、而非组件库内置默认绿）；经全局主题变量（如 SCSS 变量 / CSS 自定义属性 / 组件库主题 token）统一覆写，避免逐组件 style
  - **图标缺失**：原型用了项目图标库没有的图标 → **抽 SVG 源文件入项目前端资产目录**（如 `src/assets/icons/`）作自有资产统一调用；禁止为单个图标引完整图标库（约定 28）、禁止用"差不多"的替代图标
  - **★ 图标语义化选取（款式可与原型不同，语义不可乱 — 堵"随机取图标 / 不同功能撞图标"的口子）**：约定 28 / L2 允许图标**款式**用项目图标库的等价件、可与原型不完全一致，但**选哪个图标必须由「功能语义」决定，不得随机取或顺手凑数**：① 图标语义须匹配其承载的功能/动作（删除→垃圾桶、编辑→铅笔、查看→眼睛、搜索→放大镜、新增→加号、导出→下载/外流、刷新→循环箭头、成功→对勾、警告→感叹三角…），**语义相符优先于「长得像原型」**；② **同一界面 / 同一功能族内，不同功能的图标必须可区分**——禁止多个不同动作复用同一图标造成误认（"编辑"与"查看"、"删除"与"清空"、"保存"与"提交"不得同图标）；③ **同一语义的动作全项目图标一致**（"删除"到处都用同一个删除图标，别这页垃圾桶、那页叉号）；④ 拿不准某功能用哪个图标时，参照原型该处图标的语义 + 项目已有同类功能的既用图标，取语义最贴切者，不"顺手拿一个"。**与「图标缺失」条不冲突**：缺失条管「原型特定图标款项目库没有 → 抽 SVG、别用 lookalike 充数」（保真具体款式）；本条管「用项目库图标时 → 按语义选、别随机、别撞图标」（保证语义正确 + 功能可区分）。**回检**：frontend agent 图标处置自检 + `code-verification-loop` 维度 4「视觉还原」L2 子项兜底核对——图标语义错配 / 不同功能撞图标标 **Important**；若撞图标导致操作误认、影响页面可用性则升 **Critical**
  - **判定速查**：L1 = 容器/版心 + 颜色/字号/间距/圆角/阴影体系 + 必须出现的元素；L2 = 组件内部实现 + 微交互；不确定默认归 L1
  - **回检**：`/sprint-test` `code-verification-loop` 维度 4 按 L1/L2 分级；L1 偏差 Critical 强阻塞、L2 偏差 Important 不阻塞验收

## 约定 20 前端特例 — UI 组件公共化（视觉单元第二次出现即抽）

> 本节是 `{{AIDP_HOME}}/rules/code.md` 约定 20「同 Sprint 内 3 次复用即抽」在**前端视觉单元**上的**收紧特例**，
> 只覆盖「视觉单元」（卡片模板 / 列表行 / 空态块 / 统计格 / 栅格容器 / 公共样式段），
> **逻辑复用（工具函数 / composable / hook / 服务）仍按约定 20 的 3 次阈值，本节不改它**。
>
> **★ 为什么前端要收紧到 2 次**：逻辑的重复会被"改了一份忘了另一份"直接打出 bug；
> **样式的重复不会报错，只会分叉**——两份样式当下看起来一样、改其中一份另一份不会报错，
> 只有人在两个页面并排比对时才发现。且约定 20 的机器回检（`wc -l` + grep 找 3+ 重复）
> 对样式块基本无效。故前端把阈值前移一格，用"第二份根本不存在"取代"事后发现分叉"。

### 20F.1 第二次出现即抽（不是等第三次）

- 同一视觉单元**第二次出现时就必须抽公共**。
- **新建一个「与既有列表 / 卡片视觉一致」的组件时，开工前必须先回答：这套视觉现在住在哪？**
  - 已是独立组件 → **复用**；
  - **内联在宿主文件里 → 先抽再写**，⛔ 不是"先复制再说"。
- **宿主文件已超约定 20 复杂度阈值时，新增内容不得再往里堆**，新视觉单元一律外置。
- **⭐ 执行体必须主动提出抽取建议，不等使用者追问。**
  正在写下「本处样式逐值抄自 X」「与 X 保持一致（手工）」这类注释时，
  **那句注释本身就是抽取信号**——写得出这句话，就说明该抽了。

### 20F.2 ⛔「复制 + 登记技术债」不是合法出路

技术债登记**只在"抽取本身会引入更大风险"时才成立**，且登记项必须写明两个字段：

| 必填字段 | 含义 | 缺失后果 |
|---|---|---|
| **为什么现在不抽** | 抽取会引入的具体风险（不是"时间紧"）| 缺 = 该项视为**未处理**，不是"已登记" |
| **解除条件** | 什么条件满足后必须回来抽 | 缺 = 该项视为**未处理** |

只写"这是技术债"等于**把登记当免责声明**——真实代价：三套卡片样式逐值复制并登记技术债后，
接下来每一轮返工都源于"复制的那份没跟上宿主"。

### 20F.3 抽取必须「整族 + 全参数化」，否则等于没抽

1. **整族抽取**：**容器 + 单元 + 子元素**一并抽走。只抽一半 ⇒ 单一信源只落一半，剩下那半继续各写各的。
   （真实反例：只抽了单元样式、没抽栅格容器 ⇒ 容器仍各写各的，后续照样分叉。）
2. **全参数化**：凡「各调用方**必然不同**」的量都必须参数化——**漏一个就等于没共用**。
   （真实反例：抽出来后列数传错 + 缩进写死未参数化 ⇒ 共用了同一份样式，却还是长得不一样。）
3. **抽取前先列「调用方 × 差异量」矩阵**，逐项落一个决定：`参数化` / `保留在调用方` / `确认无差异`。
   矩阵留在该公共单元的头部注释或 `docs/design/detail/{version}/` 对应章节，**不留矩阵 = 抽取未完成**。
4. **抽取的是"实现载体"，不是"呈现结果"**：共用样式 ≠ 共用内容。
   多个位点可以共用同一个卡片外壳，而各自的统计项、字段、列数完全可以不同——
   **先厘清"共用什么、不共用什么"再动手**。
   （真实反例：把"共用卡片样式"误解成"共用统计项"，做成三个页签一套四格，被打回；
   实际是三套命名、三套统计项、只共用一个外壳。）
5. **⛔ 抽取时不得"顺手优化"任何一条规则**：**抽取与重构必须分两次提交**，否则等价性无法证明。
6. **技术限制导致只能复制**（如作用域样式不跨组件继承）时，必须同时做两件事：
   - 在复制处落**可检索的同步义务标记**：`SYNC-WITH: <源文件路径>`（一行注释，写在复制段起始处）；
   - 进技术债台账，并满足 20F.2 的两个必填字段。

### 20F.4 样式改动的验证：现有静态检查一条都不覆盖

- **⛔ 类型检查（`vue-tsc --noEmit`）与 lint 都不编译样式块**——**"类型检查过了"对样式毫无意义**，
  不得据其得出"样式改动无回归"的结论（这是约定 35「阳性对照」在样式面上的具体形态）。
- **样式重构（抽公共 / 参数化 / 移动位置）须做编译等价性对照**——重构的定义就是**产物不变**：
  用被测项目**自己的** `./node_modules/.bin/sass` / `lessc` / `stylus` 分别编译改动前后的样式段，
  再跑 `python3 {{AIDP_HOME}}/skills/code-verification-loop/scripts/check_css_equivalence.py <old.css> <new.css> --json`。
  零构建、只编译改动的样式段，不打包（**不违反约定 35 的"不完整构建"**）。
  **归一规则 / 刻意不归一项 / 基线有效性判定 / 「仅顺序变化」分档，一律以该脚本与 `code-verification-loop`
  维度 14 为单一信源，本处不复述**（约定 21）。三条只讲怎么读结果：
  - ⚠️ **`exit 2` = 基线无效（空 / 疑似未执行），语义是「须修好再跑」，⛔ 不是通过**——
    报告写「基线无效，本项未核验」。这正是约定 35「基线对照须先判定基线跑起来了」的机器化落点。
  - ⚠️ **`order_only_change: true`（原序不等价、排序后等价）= 仅顺序变化 → Important，⛔ 不当通过**：
    CSS 有层叠语义，同选择器同属性后写的胜出，排序会掩盖这类真差异，须人确认。
  - 手工 `diff` **做不到**上面两档（没有基线有效性判定、也不分层叠顺序），故不接受以手工 diff 替代。
- **公共样式文件的文档注释必须用行注释 `//`**——块注释 `/* */` 会被编译进产物。
- **模板语法错误**（如把注释写进标签的属性列表中间）会导致整个模板解析失败，
  而**类型检查零报错、只有 lint 抓得到** ⇒ 前端最低静态验证组合固定为：
  **类型检查（带阳性对照）+ lint（同文件集基线对照）+ 预处理器一致性比对（改样式时，见本文件头部 ⚠️ 段）**，
  三者盲区互不重叠，**缺一不可**。
- **回检**：`code-verification-loop` **维度 4「视觉还原」**+ 其下**四条「UI 公共化」子行**
  （① 新增组件含与既有文件重复的样式声明块 ② 公共单元被引用处仍有同名属性覆盖〔说明该量本应参数化〕
  ③ **「抄自 / 复制自 / copied from / 与 X 保持一致（手工）」类注释 → 触发一次抽取评估**
  ④ `SYNC-WITH:` 标记纳入技术债扫描）+ **维度 7「CSS 预处理器一致性」**
  + **维度 14「样式重构编译等价性对照」**。⚠️ 第 ③ 条与本文件 20F.3 第 6 条互为正反：
  20F.3 要求技术限制下复制时**必须写** `SYNC-WITH:`，③ 则把「写了这类注释」本身当作抽取信号——
  两者不冲突：先评估能不能抽，抽不了才登记。
