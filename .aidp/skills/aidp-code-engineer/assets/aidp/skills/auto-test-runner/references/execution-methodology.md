# 通用执行方法论层(端无关)

> 本文件是「自动化测试执行方法论」的唯一信源。SKILL.md「执行流程」是主干摘要,本文件展开细则。**本层所有逻辑对所有被测端一致,只依赖驱动适配层的四个原子能力(locate/act/observe/capture),不感知具体端。**

---

## 一、分模块批量执行(降 token 内核)

**批次粒度 = 一个模块(套件)。** 每个模块启动一个执行子 Agent,在其内部**串行**执行本模块全部用例。

> ⚠️ **执行子 Agent 无 Skill 工具,必须先用 `Read` 读方法论文件:** 通过 Task/Agent 工具派生的执行子 Agent **拿不到 Skill 工具**(即便 `tools:*` 也没有,Skill 是主循环级能力),**加载不了本 skill、拿不到方法论**。因此主 Agent 派发时必须在 Task prompt 里**要求子 Agent 先 `Read` 本 skill 的 `SKILL.md` + `references/execution-methodology.md`(以及本模块用到的 `references/driver-adapters.md`/`references/usecase-format.md`)拿到完整方法论,再用驱动执行**。主 Agent 只传「方法论文件路径 + 本模块用例文件路径 + run-context 路径」,不把方法论正文塞进 prompt(既拿到完整方法论又不牺牲降 token)。

- **会话复用**:模块内所有用例**共享同一会话 / 一次登录**。执行子 Agent 内浏览器/驱动会话执行完不关闭,后续用例复用;只在模块开头走一次入口流程(打开端 → 登录 → 进工作台),模块内用例通过导航切换连续执行,**禁止逐条重登录**。
- **降 token 做法**:① 同模块一次性把全部用例交给一个子 Agent,避免每条重新加载文档 + 重付 Agent 启动开销;② 会话/导航上下文复用(不重复导航登录);③ observe 优先用动作返回的**增量状态**,不每步全量重读页面。
- **实测收益**:相比逐条调度,token 消耗降低约 **3.6 倍**、执行时间缩短约 **3 倍**(参考同类实现)。
- **降载记账**:每模块执行完可记 `token-usage.json`(字段 `module / case_count / total_tokens / tool_uses / duration_ms`),供报告 Token 统计。
- **tasks.md 只存 ID + 名称**,详细用例内容执行时按 TC-ID 现查,避免进度文件膨胀。

**模块间并行度(默认串行):**

- **默认:模块与模块之间串行执行**——因为多数被测系统共享同一测试环境/账号,并行会导致**登录态互相污染、数据竞争、会话串号**。串行最稳,是无人值守默认。
- **可选并行:仅在会话完全隔离时允许**。若确需模块间并行(大用例集提速),**每个并行模块必须使用独立会话**:独立浏览器实例 / 独立 `--user-data-dir` / 独立 driver session / 独立测试账号,彼此登录态与数据不共享。并行度由 run-context 的 `module_parallelism` 配置(默认 1 = 串行);>1 时调度层必须为每个并行 slot 分配隔离会话,否则退回串行。
- **模块内始终串行**(单个执行子 Agent 内逐条跑,共享该模块会话),这一条不受上面影响。

**★跨角色套件之间必须重建干净会话(端无关调度步骤):**

「一次登录、模块内共享会话」是降 token 的核心,但它有一条**硬边界**:**下一个套件要用另一个角色登录时,不能直接接着用上一个套件的会话**。

1. **调度期识别**:排模块顺序时读各套件声明的登录角色;**相邻两个套件角色不同 = 跨角色边界**。尽量把同角色套件排在一起,减少切换次数。
2. **边界处**:进入新角色的首个套件前,先 `observe` 读登录态——已是目标角色则直接跑;**残留的是上一个角色** → 调 `act(—, 'resetSession')` 重建干净会话(端无关动作词,见 [`driver-adapters.md`](./driver-adapters.md) 第一节)。
3. **恢复检验(必做)**:`resetSession` 后再 `observe` 一次,核对**登录态已清空 / 进入登录页**,再走入口流程登录新角色;登录后核对**当前登录角色 = 目标角色**(复用第二节「observe 恢复检验清单」的「切换角色/账号」行)。
4. **验证不过 = 前置不满足**:标 `block(precondition-unmet)` + 证据,继续下一个套件,**不带着错误角色硬跑**——用错角色跑出来的权限类结论全是错的,且看上去很正常。

> ⚠️ **为什么要写成显式步骤而不是「让执行方现场想办法」:** 2026-08-18 上游实测,被测系统用 **HttpOnly 的 SSO 会话**,现场试了两条看似合理的路子**全部无效**——页面级隔离上下文隔离不了驱动实例级的 SSO 会话;脚本清 cookie 清不掉 HttpOnly cookie,点「登录」直接跳回上一账号的结果页、**根本出不来登录表单**。最后靠重启驱动实例换全新 profile 才拿到干净会话。整个过程是**现场试错试出来的**,而这本该是方法论里的一步。各端「怎么重建」属端专有,落 `driver-<端>.md`。

## 一·补、前置数据面探测(解析后、驱动浏览器前)

**目标:** 将用例声明的可预先确认的数据前置从浏览器闭环中前移,避免为必然 `block(precondition-unmet)` 的用例启动会话、登录、导航和定位。该阶段属于执行内核的前置阶段,不替代后续感知-执行-校验-决策闭环。

### 执行顺序

1. **解析并归组:** 读取用例的结构化「前置探测」字段,按全册唯一 `ED-NNN` 聚合;同一前置项只执行一次,结果广播给所有关联用例。没有结构化 `ED-NNN` 的自然语言前置不得擅自猜测探测式,按旧流程由浏览器内感知或标 block 并记录缺少结构化声明。
2. **批量只读探测:** 通过编排层/适配器提供的数据面能力执行最小只读接口或查询,不得在此阶段写入、修改或删除业务数据。探测结果至少包含 `success`、状态码/等价成功状态、结果计数或状态事实及证据。
3. **三态判定:** `success=true` 且数据满足声明 → 关联用例进入浏览器;`success=true` 但数据不满足 → 关联用例直接写 `block(precondition-unmet)`;detail 原样采用前置项的「不满足时 block 归因」并写出具体缺位项;`success=false` / 非 2xx / 响应无法判定 → 探测阶段自身标 `block(network-error)` 或 `block(env-unavailable)`,记录错误和证据,**不得**把它转换成“0 条”或前置不满足。
4. **浏览器门控:** 只有前置探测满足的用例才连接/驱动浏览器并进入第三节闭环;前置缺位或探测失败的用例不执行任何浏览器动作。所有 block 仍进入结果 JSON 与报告,不计为 pass,不静默丢弃。

### 探测安全网

- 前置探测属于探测类断言,必须遵守方向、特异性和阳性对照分档纪律;尤其 `success=false` / 非 2xx 必须与合法空结果有不同返回态。
- 仅当探测响应明确成功且业务契约允许空集合时,`count=0` 才是合法空结果;HTTP 400 参数缺失、鉴权失败、5xx、超时和解析失败都必须走错误态。
- 每个 `ED-NNN` 保存探测命令/入口、实际响应摘要、判定和复用的用例 ID;探测本身失败时,不要给所有关联用例伪造同一条“数据缺位”结论。
- 前置探测不得改变被测系统状态;需要造/删数仍走「前置数据编排」与对应驱动能力,完成后可重新执行该 `ED-NNN` 只读探测。

### 一·补·补、环境能力前置(`EC-NNN`,与 `ED-NNN` 同段执行、判据不同)

**为什么单列一档(2026-09-10 下游实证):** 两轮实测 116 条里 **41 条(35%)因前置不满足被判 block**,
成因高度集中 —— **25 条缺 `exposure=public` 独立实例 / 10 条缺服务端日志读取通道 / 6 条缺靶场样本**,
而这些**全部是逐条执行到前置检查时才发现的**,每条白走一遍「导航 → 等待 → 探测 → 判定」,
耗时全部落在执行跨度里。

⚠️ **它们够不着既有的 `ED-NNN`**:`ED-NNN` 的定义是「可通过**只读接口或数据面查询**确认的**数据状态**」,
而「部署形态是不是独立实例」「有没有服务端日志读取通道」「靶场里有没有 ≥3 级目录的样本」
是**环境能力**,不是数据样本。两者判据、探测方式、失效频次都不同:

| | `ED-NNN` 数据面前置 | `EC-NNN` 环境能力前置 |
| :- | :- | :- |
| 问的是 | **样本在不在**(≥1 条待交付订单) | **这个环境提供不提供这个能力**(独立实例 / 日志通道 / 靶场资产) |
| 探测方式 | 只读接口 / 数据面查询 | run-context 已知事实 + 一次性能力探测 |
| 频次 | **每轮**都要重探(数据会变) | **整轮一次**(环境形态一轮内不变) |
| 不满足时 | 该前置项关联的用例 block | **同一能力的整批用例一次性 block** |

**执行顺序(与 `ED-NNN` 同在「解析后、驱动浏览器前」这一段):**

1. **一次性探明环境能力**:把 run-context 里已知的部署形态、通道、靶场资产清单,加上必要的一次性探测,
   汇成本轮的**能力集合**。
2. **集合运算**:用例册声明的 `EC-NNN` 需求集合 − 环境能力集合 = **缺位集合**。
3. **整批判定**:缺位能力关联的用例**一条都不进浏览器**,直接写 `block(precondition-unmet)`,
   `precondition_probe.detail` 原样采用该 `EC-NNN` 的「不满足时 block 归因」。
4. **报告登记**:报告须给出「本轮可执行集 / 前置不满足集(按能力分组)」,让「35% 被 block」
   一眼看出是**环境没给能力**而不是产品有问题。

> **这与既有「优雅降级」是同一思路的推广。** 驱动不可用时已经整体标 `block(driver-missing)` 而不逐条试;
> **环境能力理应享受同等待遇** —— 逐条试出来的 41 个 block 与一次性判出来的 41 个 block 结论完全相同,
> 差别只是前者白烧了执行跨度。

**「能力标识」受控词表 `<类别>:<值>`,类别是闭集(⚠️ 与 `dev-manual-testcase` 逐字一致的副本,
按 SKILL 独立性原则各持一份、⛔ 不跨 skill 引用;改一处必须同步改另一处):**

| 类别 | 含义 | 例 |
| :- | :- | :- |
| `deploy` | 部署形态 | `deploy:standalone-public` / `deploy:multi-env` |
| `channel` | 可读写的通道 | `channel:server-log` / `channel:db-readonly` |
| `fixture` | 靶场/样本资产 | `fixture:deep-tree` / `fixture:ws-sse-node` / `fixture:frozen-project` |
| `account` | 角色账号能力 | `account:admin` / `account:guest-link` |
| `data` | 环境级数据形态(≠ 单条样本,那是 `ED-NNN`) | `data:multi-tenant` |

⚠️ **执行端「识别 / 未识别」的判据就是这张表** —— **类别不在闭集内即判「未识别」**,走下面第 1 条回落。
⛔ **不得把这张表留在上游而本端不写**:本端不持有词表时,「未识别」这条规矩没有可执行的判据,
执行体只能猜,而两种猜法(当满足 / 当缺位)恰好就是下面点名要禁的两个方向。

**⚠️ 三条不可退让(与上游 `dev-manual-testcase` 逐字一致,⛔ 两边不得各定一套):**

- **未识别的能力标识 → 按「未探明」处理,`⛔ 不得静默当作满足、也不得静默当作缺位`。**
  该用例**回落旧流程**(照常进浏览器、由用例内前置检查判定),并在报告显式登记
  「`EC-NNN` 词表未识别,本轮未预判」。
  ⚠️ 两个方向都危险且**长得一模一样**:当作满足 = 该跳过的没跳过(白跑,与「前置真的满足」同形);
  当作缺位 = **不该跳过的被跳过了,而报告显示 block、看上去很正常**。后者是漏测,更坏。
- **无声明 = 无前置**(向后兼容)。存量用例册没有 `EC-NNN` 时**一切照旧**,
  ⛔ 不得因为「没写声明」就整批跳过。
- **能力探测本身失败** → 与 `ED-NNN` 同款:标 `block(env-unavailable)` 并记证据,
  ⛔ **不得**转换成「该能力不具备」。

**上游契约:** `EC-NNN` 的声明格式由 `dev-manual-testcase` 产出(用例级「环境能力前置」段,
四列 `前置项 | 能力标识 | 判定方式 | 不满足时 block 归因`),**两端格式必须逐字一致** ——
各定一套的结果是执行端读不到、或读错,**两种失效都是静默的**。

## 一·补三、★WebMCP 分层铁律(硬规则,方法论层)

**WebMCP 是测试加速器,不是被测对象的替代品 —— 但它只能加速一半的事。**

下游实证(2026-09-10):WebMCP 已在被测页面启用、驱动原生支持工具列举与调用,而 116 条用例里
**只有 16 条用到它,且全部在测 WebMCP 自己**(能力面回归)。其余 100 条里大量「登录 / 切环境 /
选中某接口 / 构造请求参数 / 发起调用」这类**状态准备**步骤,仍走「快照 → 找元素 → 点击 → 等待 →
再快照」的 **5+ 次驱动往返**,本可压缩成 **1 次工具调用**。

**分层铁律(⛔ 不得一刀切,两个方向都会出事):**

| 步骤性质 | 走什么 | 为什么 |
| :- | :- | :- |
| 状态准备 / 数据构造 / 业务流程驱动 / **非视觉**断言 | **可走 WebMCP 工具调用** | 快、稳、不依赖选择器 |
| **视觉还原度 / 布局 / 样式 /** 通用规则集 约定39-R1·R2·R3 | ⛔ **必须 DOM + 截图** | **WebMCP 读的是页面「声明的能力」,不是「渲染结果」** —— 用它验还原度会让渲染层缺陷 **100% 漏测,而且全绿** |

⚠️⚠️ **为什么这条必须写死在方法论层、而不是留给执行体临场判断:** 不写死,执行体只有两种结局 ——

- **不敢用**(现状:100 条用例零加速);
- **用过头**(把还原度用例也走工具调用,测了个寂寞)。

**后者比前者危险得多,因为它是静默的**:前者只是慢,后者会产出一份**全绿而无效**的报告。

**落地约束:**

- 结果 JSON 的 `mechanism` 字段如实填 `dom` / `webmcp` / `mixed`;
  **视觉还原度类用例填 `webmcp` 由 `check_result.py` C14 判 Critical**。
  ⚠️ `mixed`(状态准备走 WebMCP、断言走 DOM)**是被鼓励的形态,不判**。
- 证据须体现「经 WebMCP 达成」还是「纯 DOM/CDP 模拟」,⛔ 不得混为一谈 —— 两者失败形态不同,
  混记会让缺陷归因整体走偏(该约束原已存在,此处只是与本铁律对齐)。
- 上游 `dev-manual-testcase` 在**步骤级**给出 `[加速可选]` 标注(见其用例格式);
  **没有标注不等于可以自行改走 WebMCP** —— 判据是上表的「步骤性质」,标注只是把判断提前固定下来。
- 端专有的工具列举/调用写法只在 `references/driver-web-webmcp.md`(适配层),本节零端专有 API。

## 一·补四、还原度核对用「一次取数 + 集合比对」,⛔ 不要逐项遍历

下游实证:一条还原度用例 **`TC-PXY-F01` 耗时 36.8 min,占整轮总时长 25%、占执行跨度 40%**;
6 条还原度用例合计 41.9 min。它做的是「六类元素逐项核对 + 反证无字段被删」,
而当时的实现是**逐个 DOM 查询 + 多次快照**。

**正确姿势:一次 `observe()` 取回页面可见字段 / 操作入口 / 统计卡片的全集,再与「原型内容基线」做集合比对。**

⚠️ **这不需要新增原子能力** —— `observe()` 的返回里本来就有 `{可见元素[], 关键文本, 列表计数}`,
⛔ **不要为此新造第五个原子能力**(那会直接破坏维度 1-2 的两层解耦)。

**为什么集合比对不只是「更快」:**

| | 逐项遍历 | 一次取数 + 集合比对 |
| :- | :- | :- |
| 能回答「**少了什么**」 | ✅ | ✅ |
| 能回答「**多出了什么**」 | ❌ **天然回答不了** | ✅ |
| 驱动往返次数 | O(元素数) | O(1) |

通用规则集 约定39-R1 要求的本来就是**集合语义**(有没有漏、有没有多),
逐项遍历是把集合语义**退化**成了遍历实现 —— 慢只是表象,**漏掉「多出了什么」才是判据缺口**。

## 一·补二、客户端故障注入(标准手段,仅验证前端呈现)

客户端故障注入用于在不改变服务端配置、业务代码和业务数据的前提下,验证前端对失败、变慢和空响应的呈现。由端适配层提供客户端初始化脚本能力包裹请求通道,只注入请求失败或延迟;其它端如无等价能力则标「本端不适用」,不得臆造端专有调用。

- **适用:** 骨架屏、空态、错误态、重试入口、超时文案等只依赖前端请求结果的表现。
- **不适用:** 需要服务端真实状态的用例,例如上游字段落库、名额扣减、幂等去重、事务状态流转;这些仍须准备真实样本,不能用客户端注入替代。
- **零副作用边界:** 注入脚本只拦截/延迟客户端请求,不改服务端配置、不改业务代码、不写业务数据;注入范围、端点和故障类型必须记录在用例证据中。
- **阳性对照(强制):** 故障注入下「元素 0 命中」可能只是页面没有走到该渲染路径。每组故障断言必须配一个反向注入：让全端点返回 `200 + 空数据`，确认整页合法空态按预期出现,以证明断言不是恒真;阳性对照失败时不得把故障注入结果判为通过。
- **与真实请求失败区分:** 注入脚本自身安装失败、目标请求未被拦截或返回无法判定时,记录为环境/注入失败并 block,不得伪装成页面错误态已验证。

## 二、执行模式分级(按优先级/类型自动选,以取证强度区分)

三级模式**都执行**,区别在**取证强度 + 是否自愈**,由方法论层据用例字段自动判定:

| 模式 | 触发条件(按序判定) | 取证 | 自愈 |
| :- | :- | :-: | :-: |
| **失败自愈 self-heal** | 类型含「集成/跨模块」**或** 上一轮该用例 `fail`/`block` | 强制 | ✅ 失败→恢复状态→重试一遍 |
| **强制取证 verified** | 优先级 **P0/P1** | 强制(每 pass 必有证据) | ❌ |
| **直接执行 direct** | **P2** 及其他(兜底) | pass 至少记一条轻量事实;不要求完整截图 | ❌ |

**判定顺序**:self-heal(集成 / 失败复测)优先 → 否则 P0/P1 → verified → 否则 direct。

**self-heal 的「状态恢复」**动作(端无关):回到起始页 / 重新登录 / 重建前置数据 → 再跑一遍该用例;仍失败才落定 block。用于最易受环境波动影响(集成链路、历史 flaky)的用例。

**自愈恢复动作的归属(决策树,明确谁在哪个 context 处理):**

```
用例失败(单操作重试到顶 / 关键预期失败)
   │
   ├─ 该用例是 self-heal 模式? ──否──▶ 直接落定 fail/block(执行子 Agent 内,不自愈)
   │                          （归属:执行子 Agent · 模块会话 context)
   └─是─▶ 恢复动作是否只需「本模块会话内」操作?
           （回起始页 / 模块内重新登录 / 重建本模块前置数据)
             │
             ├─是─▶ 执行子 Agent 自主调驱动完成恢复 → 重试一遍该用例
             │        （归属:执行子 Agent 自主处理,不回主流程;复用当前模块会话)
             │        重试仍失败 → 落定 block + 证据,继续下一条
             │
             └─否─▶ 恢复需「跨模块 / 换账号 / 重建全局会话」等模块外资源?
                      （归属:执行子 Agent 标 block(need-global-recover) 回传主流程;
                       主流程在编排 context 决定是否新起一个隔离会话的补跑子 Agent,
                       放到本轮 checker 阶段或下一轮 self-heal 复测处理)
```

**要点**:**模块会话内可完成的恢复,一律由执行子 Agent 自主处理**(省一次主流程往返、复用会话降 token);**只有需要模块外资源的恢复才回主流程**,由主流程在隔离会话中安排补跑。执行子 Agent 绝不因自愈而挂起等主流程实时应答(无人值守)。

**恢复成功如何可观测判定(observe 恢复检验清单):** 执行恢复动作后,**必须用 `observe` 读页面状态、逐项核对下列适用项**,全部通过才算恢复成功、方可重试用例;任一不通过则判恢复失败 → 落定 block(block_reason=precondition-unmet)+ 证据。

| 恢复动作 | observe 检验项(可观测) |
| :- | :- |
| 重新登录 | 登录态 = 已登录(用户名/头像可见、无跳登录页)、当前 URL 为工作台而非登录页 |
| 回到起始页 | 当前 URL/路由 = 用例前置要求的起始页、页面标题匹配 |
| 重建前置数据 | 目标列表**计数 ≥ 期望**(如"应有 3 条工单"→ observe 列表计数=3)、关键数据行可见 |
| 切换角色/账号 | 当前登录角色 = 目标角色、越权入口按预期可见/隐藏 |
| 清理脏数据 | 目标记录已不在列表(计数回落)、无残留状态标签 |

> 恢复检验只用 `observe` 的可观测信号(URL / 登录态 / 列表计数 / 元素可见性),不写"数据库已重置"这类不可视断言;检验通过后重试用例,仍失败才落定 block。**窄口径豁免(不可视断言禁令的唯一例外):** 仅 `[双源对账]` 用例经**驱动适配层的 DB 断言驱动**作数据真值对账(执行用例给出的等价 SQL,取 DB 值与页面取值比对)时,允许读取 DB 值级信号——这是刻意的**可插拔 assertion driver 能力**(落在端相关层,不破坏两层解耦,见 [`driver-db-assertion.md`](./driver-db-assertion.md))。其余一切断言仍走 UI `observe` 可观测信号,禁不可视断言。

**★落定后写 `self_heal_trace`(self-heal 用例的结构化失败反思,可选字段):** 凡触发过状态恢复重试(`self_heal_applied=true`)的用例,落定时在结果 JSON 写 `self_heal_trace` 三要素——`cause`(失败根因判断,如"网络超时致按钮未响应"/"前置数据缺失")、`recovery`(执行的恢复动作 + observe 恢复检验结果,**证据来源就是上表「observe 恢复检验清单」的可观测信号**,不新造机制)、`outcome`(复测结论,枚举 `recovered-pass` / `still-fail-block`)。**非 self-heal 用例省略或置 null**,不增加普通用例负担;字段缺省时报告行为与旧版本一致(schema 见 `report-format.md` §一、示例见 `../assets/result-schema.json`)。

**取证分级铁律**:verified/self-heal 的 pass 必须有完整证据;direct 的 pass 也不能零依据,至少在 `evidence` 记录一条轻量事实(实际值、命中文案、列表计数或产物路径),但不要求截图类型。没有任何轻量事实的 direct pass 只报 Important、仍不阻断执行;报告单列「无依据的 direct pass」数量,使其与已留痕的 pass 可区分。

**★值级断言硬约束(端无关,不限 P0/P1,所有模式通用):** 凡用例涉及**数值 / 状态 / 权限**判定,**必须带值级断言**(列表行数=N / 字段"标签"显示为"值" / 状态由 A 变 B / 元素置灰·不可见 等,DSL 见 [`usecase-format.md`](./usecase-format.md) 第六节)对结果做确定化比对;**严禁把「页面加载成功 / 无 console error / 元素存在」当作业务用例的唯一通过判据**——元素存在只是前置可见性,不代表业务值正确。此约束**不再限于 verified/self-heal(P0/P1)**:direct 模式的数值/状态/权限用例同样适用;仅纯导航/纯展示、无值语义的用例才可回退自然语言「预期现象」判定。`[双源对账]` 类用例的值级断言由**驱动适配层的 DB 断言驱动**对账 SQL 真值(见 [`driver-db-assertion.md`](./driver-db-assertion.md))。

## 三、感知-执行-校验-决策闭环(单条用例)

> **前置:环境准备与数据面探测(不属于本闭环,频次也不同)。** 解析用例后、驱动浏览器前先按 `ED-NNN` 做前置数据面探测(第「一·补」节);驱动连接后、首条用例前再做「实例归属防呆」与「运行环境取证」,**三者频次不同**,见第七节的频次表。下面的 1~5 步才是**每条已通过前置门控的用例**都走一遍的闭环。

每条用例四阶段,**全程只调四原子能力**:

1. **感知 observe**:读当前页面/会话状态 → 判前置是否满足(满足则跳过导航/登录,复用会话;不满足才 `act` 导航/登录)。
2. **执行 act**:按用例四要素步骤表逐步执行——`locate`(语义定位符)→ `act`(动作词 + 数据)。动作词端无关:tap/click、input/type、select、swipe/scroll、back、upload、dialog、waitFor(完整枚举与各端映射见 driver-adapters.md 第一节)。
   > **★locate 先查 run-context 预置定位符段(降重复探测):** `locate` 前先查 run-context「四、关键元素定位方式 + 常用测试数据(执行前预置·只读)」是否已给出该元素的稳定语义定位符——**命中即直接用**,减少每进新页面重复 observe 探测的抖动与 token 开销;**未命中(或该节整体缺失)再退回 observe 现场探测**。该预置段**可选**:无此段时行为与现状**完全一致**(全程现场探测),不因缺此段失败。预置段仍只用语义定位符(禁选择器),现场探测得到的新定位符不回写该只读段(它执行中不更新)。
3. **校验 assert**:每步后 `observe` 读结果 → 与用例「预期现象」比对;verified/self-heal 模式 `capture` 取证并写入 evidence。**若用例步骤带 `断言:` 行,优先按语义断言做确定化判定**(逐条映射到 `observe` 可观测信号:存在/不存在文本、列表行数±N/=N、字段"标签"显示为"值"、状态由 A 变 B、元素可点击/置灰/不可见、断言(反向)期望错误提示出现——DSL 与映射见 [`usecase-format.md`](./usecase-format.md) 第六节);**无断言行才回退自然语言「预期现象」由 AI 判定**。
4. **运行时错误捕获(★每条用例执行后必做)**:用例执行完(无论 pass/fail/block),**通过 `observe` 的运行时错误通道(console/network,端相关·可选)拉一次 console 消息 + network 请求列表**(通道定义见 driver-adapters.md 第一节 observe 契约),把 **console 报错 / network 非 2xx / 页面级错误 UI** 逐条写入结果 JSON 的 `runtimeErrors`(`{type, message, detail, severity, artifact}`)。**pass 用例也要拉**——页面功能通过但后台有 500/JS 报错时,这些错误供下游"升级 bug"。severity 参考:JS 未捕获异常/登录类接口 5xx → P1;一般接口非 2xx → P2;告警类 → P3。**★P3 告警类受 `capture_warnings` 开关控制(默认关,不记录)**:真实前端的框架废弃警告/devtools 提示极多,恒记录会让每条用例都挂一串不改变 pass/fail 的 P3,显著抬高报告体积与 token。**P1/P2 不受该开关影响、恒记录**。**端相关降级**:Web 端 console/network 通道齐备必拉;移动/桌面/小程序端若驱动不提供该通道,`runtimeErrors` 留空(不因缺通道失败,与优雅降级一致)。
5. **决策 decide**:见「失败分级」判定 pass/fail/block,并置 `block_reason` 枚举(**7 值**:retry-exhausted / driver-missing / **driver-hung** / precondition-unmet / network-error / env-unavailable / account-invalid,权威定义见 `report-format.md` §一)。判定后写结果 JSON + 更新 run-context「当前页面/会话状态」(供下一条感知复用,形成感知链)。

## 四、失败分级不中断(阈值,**配置化**)

**下表阈值均为默认值,实际取自 run-context 的「执行参数」配置位**(见 `../assets/run-context-template.md`);**严禁硬编码**——远程/云环境网络慢时,编排层可在 run-context 上调阈值避免误判超时。

| 情形 | 处理 | 默认阈值 | run-context 配置键 |
| :- | :- | :-: | :- |
| **关键预期验证失败** | 立即判 `fail`,不重试 | — | — |
| **单操作失败** | 快速重试 | **≤ 3 次** | `retry_limit` |
| **重试仍失败** | 判 `block` + 记 error/证据 | 到顶 | (同上) |
| **单步等待** | 超时即判卡死,记录当前状态截图后继续 | 每步 ≤ 3s / 首开 ≤ 30s | `step_timeout_s` / `first_open_timeout_s` |
| **功能入口探测**(入口是否存在) | 快照确认不存在 → 最多 1 次替代交互 → 仍无判 fail | 总时长 ≤ 60s | `entry_probe_timeout_s` |
| **驱动/子 Agent 调用失败** | 重试 ≤ `retry_limit`,仍失败标 block 后继续 | ≤ 3 次 | `retry_limit` |
| **★驱动进程级无响应(driver 卡死)** | **健康探测判定 → `resetSession` 重建驱动 → 恢复登录 → 断点续跑**;连续 `driver_heal_retry_limit` 次自愈都失败才判 `block(driver-hung)` + 证据 | 探测阈值 ≤ 15s / 自愈 ≤ 3 次 | `driver_health_timeout_s` / `driver_heal_retry_limit` |
| **框架脚本调用失败**(tasks_state/gen_report/detect_drivers 等自身参数踩坑/报错) | 先 `--help` 校正参数,重试 ≤ 2 次;仍失败**立即降级到手动等价操作** + 记入报告「遗留风险/改进建议」,**绝不反复试错空转** | ≤ 2 次 | — |

> **★框架脚本调用失败降级(无人值守必守,防空转卡死):** tasks_state / gen_report / detect_drivers 等**框架脚本自身**参数踩坑 / 调用失败时,**最多重试 2 次**(先按 `--help` 校正参数)。仍失败**立即降级到手动等价操作**——
> - `tasks_state` 失败 → **手写状态记号**(直接编辑 tasks.md 的 `[ ]/[>]/[√]/[!]`);
> - `gen_report` 失败 → **手动按 `results/*.json` 聚合**成报告(人工数 pass/fail/block、填章节);
> - `detect_drivers` 失败 → **人工判定端可用性**(如 web 看会话是否挂载 chrome-devtools MCP、本机有无 Chrome)。
>
> 降级动作**记入报告「遗留风险 / 改进建议」**,**绝不反复试错空转卡死**。框架自身失败与用例级失败**同规格**:重试上限 → 降级 → 记录 → 继续。

> **★驱动健康探测 + 自愈重启(端无关,`block` 之前的一层):** 上表其余各行都是**用例级/元素级**失败;这一行处理的是**驱动进程级故障**——驱动整体卡死后,旧规则下每条用例都要各自把超时与重试耗尽再逐条 `block`,**既救不活也拖慢整批**(实测:一次无人值守跑中驱动卡死两次,第一次子 Agent 一路空等到单步超时上限才交回,第二次靠人工重启才救回)。故在 `block` 之前插一层自愈:
>
> 1. **触发判定(关键是与元素级失败区分开)**:单元素 `locate` 失败 / 单步断言不符 → **仍走老路** `retry_limit` → `fail`/`block`,**不进自愈**。只有表征为**驱动整体无响应**时才进——判据:**连续多次原子调用全部超时**(而非某一次某元素),且**一次轻量探活也无回应**。探活走 `observe` 的**健康探活通道**(端无关信号 `driverAlive`,见 [`driver-adapters.md`](./driver-adapters.md) 第一节;具体探活命令属端专有,只落 `driver-<端>.md`)。
> 2. **自愈动作**:`act(—, 'resetSession')` 重建驱动/会话 → **恢复登录** → **断点续跑**(tasks.md 4 态:`[√]` 跳过、`[>]`/`[ ]` 续跑,**不跨 build/round、不从头重来**)。恢复后必须按第二节「observe 恢复检验清单」核对**登录态 = 已登录、当前页 = 起始页**,核不过算本次自愈失败。
> 3. **上抛边界(硬)**:**连续 `driver_heal_retry_limit`(默认 3)次自愈都失败**才判 `block`,`block_reason` = **`driver-hung`**,并附证据(探活输出 / 重建返回 / 时间戳 / 已重试次数)。**未达上限不许直接 `block`,更不许空等到单步超时逐条耗尽。**
> 4. **红线不变**:自愈**只重置运行态**(驱动进程 / 会话 / 登录 / 前置数据),**绝不触碰业务代码**——与 self-heal 同一条铁律。
> 5. **端相关降级**:某端驱动不提供健康探活或 `resetSession` 时,**声明「本端不适用」并退回旧路径**(逐条超时→`block`),不因缺此能力硬失败(与优雅降级一致)。
>
> **两层分工务必保持**:方法论层只出现「健康探测 / `resetSession` / 恢复登录 / 断点续跑」这组**端无关抽象**,**不得出现任何具体驱动的重启命令**;端专有映射(如何探活、如何重建、重建时可否重新指定启动参数)只落 `driver-<端>.md`。

> **配置化铁律**:执行子 Agent 读 run-context 的这几个键作为阈值;缺省才用上表默认值。三个超时键(`step_timeout_s`/`first_open_timeout_s`/`entry_probe_timeout_s`)+ `retry_limit` + `driver_health_timeout_s` + `driver_heal_retry_limit` + `module_parallelism` 是 run-context 必开的执行参数配置位。

**共同铁律(无人值守):**
- **不阻断整批**:任一用例 fail/block 后**继续下一条**,绝不半途挂起等人。
- **有证据**:所有 fail/block 必须在结果 JSON 的 `error`/`evidence` 记录详细原因 + 证据路径。
- **不无限等待**:所有等待/重试/探测都有硬上限,到顶即判定。
- **★测试执行内绝不修改业务代码、绝不修复缺陷(红线,不可逾越):** 执行内核只做「判定 + 记录」,**不做「修复」**。发现缺陷时,只【记录进结果 JSON 的 `error`/`evidence` 与报告的 problem/缺陷汇总清单、把该用例标 `block`/`fail`、继续测完剩余用例】,**绝不中断本 build 去改被测业务代码、绝不改配置/数据库表结构/接口实现绕过缺陷**。修复一律交给**外层 bugfix 流程**(修完再起新一轮回归),测试执行器不越界碰业务代码。**self-heal 的「状态恢复」仅限会话/登录/前置数据等运行态**(回起始页、重新登录、重建前置数据 —— 见第二节恢复检验清单),**绝不触碰业务代码**;凡"改代码才能过"的失败一律落定为缺陷、记录、继续,不在执行内修。

## 五、进度断点恢复(tasks.md 4 态状态机)

- **状态**:`[ ]` 待执行 / `[>]` 执行中 / `[√]` 已完成(pass) / `[!]` 阻塞或失败(fail/block)。
- **落盘**:`{产物目录}/build-{N}/round-{M}/tasks.md`,按 `## {模块名}` 分组,条目 `- [ ] TC-001 - 用例名`。
- **流转**:批量前整模块 `[ ]→[>]`;据结果 `[>]→[√]` 或 `[>]→[!]`。
- **轮次**:扫 `build-{N}/round-*` 取最大号 +1 建新轮次;旧轮次完整保留(round-1…N 各自独立结果集)。
- **续跑**:中断后重跑,`tasks_state.py resume` 列出所有 `[ ]`/`[>]` 续跑,已 `[√]` 跳过,不从头重来。
- **★resume/`[√]`-跳过的作用域 = 仅「同一 build 内的中断恢复」(硬边界,绝不跨 build):** `resume` 与「已 `[√]` 跳过」只适用于**同一 `build-{N}` 内**某轮执行被中断后的续跑——跳过的是**本 build 已跑完的用例**,续的是**本 build 未跑完的用例**。**跨 build 边界**:新 `build-{N+1}` = 一次**全新回归轮**,必须用 `tasks_state.py init` **重建全新 tasks.md**、全部用例回初始态 `[ ]`、**全量重跑**;**绝不沿用上一 build 的 `[√]`、绝不 `resume` 跨 build、绝不只复跑被修用例**——只复验被修用例会漏掉同源缺陷(如修完 P0 只验那一条、漏掉同根因的 P1),故新 build 一律全量。**`tasks_state.py init --select smoke|regression` 同受本硬边界约束**:选集属编排层显式决策(与 `usecase-format.md` 三节「筛选决策归编排层」同向,不是执行内核自作主张跳过),但 `regression` 语义就是「只跑回归子集」,**绝不可用于新 build 的回归轮** —— 那正是本条要禁的「只复跑被修用例」。选集生成的 tasks.md 头部会写一行子集留痕,报告读者可据此识别。
- **★build 递增 vs round 递增(两级作用域划清)**:
  - **build 递增(build 级 · 全量)** = 上一 build 的缺陷经外层 bugfix 修复后的**新回归轮** → 新建 `build-{N+1}`、`init` 全新 tasks.md、**全部 `[ ]` 全量重跑**,不继承任何旧 `[√]`。
  - **round 递增(round 级 · 同 build 内)** = 同一 build 内的 **self-heal 复测**,仅针对 flaky / 集成链路等环境波动用例在本 build 内重试(见第二节 self-heal),**不是跨 build 回归**,可复用本 build 上下文。
  - 一句话:**self-heal 复测锁 round 级/同 build;新回归锁 build 级/全量**,两者边界不得混用。
- **安全检查点(checker)**:批量后独立扫 tasks.md,补齐残留 `[ ]`/`[>]` 至全部 `[√]`/`[!]`;**报告必须在此之后**,确保无遗漏用例。

## 七、四阶段执行编排(方法论层主干)

```
第零步 运行上下文对齐(一次性取齐 → run-context.md;detect_drivers 探测 + 优雅降级)
   │      探测命令:python3 <SKILL_DIR>/scripts/detect_drivers.py <web|miniprogram|mobile|desktop|all> --json
   │
第一步 prepare  定轮次 round-{M} + 建 tasks.md(全 [ ]) + 初始化 run-context 状态区
   │
第二步前置阶段  解析 ED-NNN → 按前置项去重 → 批量只读探测 → 不满足直接 block(precondition-unmet)
   │              （探测失败标 network-error/env-unavailable；未通过项不连接浏览器）
   │
第二步 execute  仅对前置探测满足的用例:整模块 [ ]→[>] → 启执行子 Agent(会话复用,逐条走闭环+模式分级)
   │              ├ 每个子 Agent 连上驱动后:实例归属防呆(每模块各一次)
   │              ├ 首模块首条用例前:运行环境取证一次 → round-{M}/env-facts.json(第十节)
   │              → 写 results/{TC-ID}.json → [>]→[√]/[!] → 更新 run-context 状态区
   │
第三步 checker  安全检查点:扫 tasks.md 补齐 [ ]/[>] → 全部落定 [√]/[!]
   │
第三步·补 free scan(可选·默认关,见第十二节)
   │              run-context free_scan=true 时:observe 读导航结构 − 已覆盖页面 → 逐页导航 + 拉运行时错误
   │              → 写 results/(entry_kind=free-scan);不计入用例统计、单列报告 §2.6
   │
第四步 report   聚合 results/*.json → 固定结构报告(见 report-format.md)
```

**子 Agent 协同**:主流程只做编排(维护 tasks.md、派发执行/检查/报告子 Agent、聚合结果),**不直接调驱动**;执行子 Agent 在隔离上下文内跑一个模块并回传结果,避免污染主上下文。派发时须按第一节要求让子 Agent 先 `Read` 方法论文件(子 Agent 无 Skill 工具)。

**★驱动连接后、跑用例前的「环境准备」——两件事,★频次不同,别混为一谈:**

| 事项 | 频次 | 为什么是这个频次 |
| :- | :- | :- |
| **① 实例归属防呆** | **每个执行子 Agent 连上驱动后各做一次** | 第二步是**每模块一个执行子 Agent**、各自连驱动,**每一次连接都可能连错实例**;首模块查过不能代表后续模块安全 |
| **② 运行环境取证** | **每轮一次(首模块)** | 环境事实对全轮一致,产出 `round-{M}/env-facts.json`(第十节);后续模块直接复用,**不重复取证、不覆盖该文件** |

**前置数据面探测在连接驱动前独立执行**(按 `ED-NNN` 去重,与浏览器会话无关);只有探测满足的用例进入下方环境准备。首模块里「实例归属」与「运行环境取证」共用**同一次** `observe` 读取(不重复调用驱动);后续模块只做实例归属检查。

**①「实例归属」防呆(端相关自检,防连错共享实例):** 核对当前会话的页面/标签集合是否属本任务。若出现**非本任务测试 URL 的业务页 / 明显非目标测试标签页**(疑似连到共享/他人实例)→ **告警并停下人工确认实例归属**,确认前不在该实例上执行任何用例动作(避免污染共享实例)。该自检的**端相关落地细则**(Web 驱动如何读标签、与 CLI↔MCP 变体硬边界的关系)见 [`driver-web.md`](./driver-web.md)「三·补二、Web 驱动执行前防呆」;移动/桌面/小程序端各自独立会话,无此风险时跳过(优雅降级)。

**★第零步「探测→block」的 web 端例外(防误杀主场景):** **web 端不因 `detect_drivers` 的 npm 探测为空就 block**——web 主驱动是 **chrome-devtools MCP 插件工具**(运行时能力,脚本探不到)。只要**会话已挂载 chrome-devtools MCP 工具**,或**本机有 Chrome/Chromium**,即视 web 可用;**仅当「MCP 工具未挂载 且 本机无 Chrome 且 无 npm 驱动」三者皆空时才 block web**。其它端(小程序/移动/桌面)仍按 detect_drivers 探测结果正常降级(缺失→block(driver-missing)+ 继续)。detect_drivers 已对 web 按「npm 包 或 本机 Chrome 任一即可用」放宽,其 `hint`/`degrade` 字段会明示 MCP 工具属运行时能力。

## 十、运行环境取证(env forensics · 环境准备阶段的原子步骤)

**要解决的问题:** 报告「一、测试概况」里的**环境事实类**字段(渲染模式 / 浏览器版本 / viewport / 是否复用已有实例 / 被测 URL / 登录角色)若来自**意图推断或模板默认**,就与实际运行形态无关。典型翻车:**在没有图形界面的远程机器上,被测端本就只能无头运行,报告却恒填「有头」**——读报告的人据此误判执行环境,后续复现、排障全部走偏。

**做法:** 在**驱动连接后、首条用例前**(与第七节「实例归属防呆」同一时点、**共用同一次 `observe` 读取**,每轮一次)执行一次**运行环境取证**原子步骤,产出结构化**环境事实对象** `round-{M}/env-facts.json`(形状见 [`../assets/env-facts-schema.json`](../assets/env-facts-schema.json)),作为报告概况段的**唯一数据源**。

**能力归属(不新增原子能力):** 取证走 `observe` 的**运行环境通道**——端无关抽象,与既有 console/network 运行时错误通道**并列**(契约见 [`driver-adapters.md`](./driver-adapters.md) 第一节)。**具体读什么信号、怎么读属端专有,只落在 `driver-<端>.md`**;方法论层只声明「取到这些事实、标明来源」这一抽象需求。

### 10.1 三条铁律

1. **★取不到不许编(与「未获非空数据→绝不伪造」同口径):** 实测取不到的字段一律写 `null` + 来源 `未取到(原因)`;**严禁**回落成模板默认值、上游传入的期望值、或"看起来合理"的推断值。**「未知」是合法结论,编一个像样的值不是。**
2. **★每个事实字段配套来源标注:** 字段 `X` 必须有平行键 `XSource`,取值落在下面五类枚举内。没有来源标注的事实字段视为未取证。
3. **★复用已有实例时,以运行探测为准:** 若本次是**连到已存在的驱动实例**(而非本次新起),则**命令/编排层传入的启动参数不生效**——那份实例的形态在它启动时就定死了。此分支下 `renderModeSource` **不得**为「显式指定」,必须是「运行取证(方法)」或「复用已有实例(来源)」。这条由硬门脚本强制。

### 10.2 环境事实对象:字段 + 来源枚举

| 事实字段 | 类型 | 含义 | 典型 `XSource` 取值 |
| :- | :- | :- | :- |
| `renderMode` | string\|null | 渲染模式 `headless`/`headed`/`null` | `运行取证(驱动运行配置:…)` / `运行取证(运行时渲染标识)` / `无头不可用降级(原因)` |
| `browserVersion` | string\|null | 被测端版本标识 | `运行取证(方法)` |
| `viewport` | string\|null | 实际**视口**尺寸 | `运行取证(方法)` |
| `reusedInstance` | bool\|null | 是否复用已有实例(而非本次新起) | `运行取证(方法)` |
| `testUrl` | string\|null | 实际被测入口 | `显式指定` / `运行取证(方法)` |
| `loginRole` | string\|null | 实际登录角色 | `运行取证(方法)` / `未取到(原因)` |
| `executionPath` | string\|null | 本轮**派发路径**:`subagent`(按规范派执行子 Agent)/ `inline`(全程主流程内联)/ `subagent→inline`(派发失败后降级) | `运行取证(降级原因)` |
| (可按端扩展) | 标量\|null | 如设备型号 / 系统版本 | 同上,**新增字段一样要配 `XSource`** |

> **`executionPath` 为什么是环境事实而不是叙述:** 派发降级(子 Agent 起不来 → 主流程内联跑)会直接改变 token 开销、会话复用与证据留痕方式,是**读报告的人必须知道的运行形态**;此前它没有字段承载、只散落在报告叙述里,概况段根本读不到。它照样受三条铁律约束——**降级了就如实写 `subagent→inline` 并在 Source 里写降级原因,不许按规范默认值填 `subagent`**。

> ⚠️ **「运行配置」不是第六类来源。** 驱动能直接返回运行配置时,那是**取证方法里最权威的一种**,来源仍写 `运行取证(驱动运行配置:…)`。把方法名当来源类别写进去(如 `运行配置(args 含 …)`)会被硬门判「形态不合法」——枚举只有上面五类。

**来源枚举(五类,`XSource` 取值前缀):**

| 来源 | 何时用 | 括号内补什么 |
| :- | :- | :- |
| `显式指定` | 编排层/run-context 传入,**且本次未复用已有实例** | 可不带 |
| `复用已有实例(来源)` | 连到已存在的实例,传参不生效 | 该实例的来源/识别依据 |
| `无头不可用降级(原因)` | 显式降级 | 降级原因 |
| `运行取证(方法)` | 执行期实测 | **用什么信号测出来的** |
| `未取到(原因)` | 实测取不到 → **值必须为 `null`** | 取不到的原因 |

### 10.3 判定顺序(端无关)

1. **驱动能直接返回本次运行配置**(启动参数 / 运行时配置)→ **最权威的取证方法**,优先用;来源写 `运行取证(驱动运行配置:…)`。
2. 否则**读运行时环境信号**交叉判定,来源写 `运行取证(用了哪个信号)`。
3. **意图推断一律不作数**——编排层传的期望、模板默认、"通常都是这样"都不是事实来源。唯一例外是 `显式指定`,且**仅当已确认 `reusedInstance=false`**(复用实例或复用与否未知时,传参不生效或无法确认生效)。
4. 若 1、2 都拿不到 → 走铁律 1(`null` + 未取到(原因)),**不许回落到 3**。

> ⚠️ **信号有效性会随被测端版本漂移,判据须实测复核后再写进 `driver-<端>.md`。** 已知教训:某些广为流传的判据(如「窗口外框尺寸为 0 即无头」)在新版本下**已经失效**——照抄会得到一个自信的错误答案,比取不到更糟。各端当前有效的判据、以及**实测证否**过的判据,见对应 `driver-<端>.md`。

### 10.4 端相关降级

驱动不提供运行环境通道(或某字段该端不适用)时,对应字段写 `null` + `未取到(驱动不提供该通道)`,**不因此判失败、不挂起**(与优雅降级一致)。整个取证步骤失败时,`env-facts.json` 仍要落盘、字段全 `null` 带原因,**不允许缺文件**——缺文件即视为未取证。

### 10.5 延伸:事实字段来源通则(环境事实类 + 统计类)

**同一口径适用于报告里所有「事实类」字段,逐个确认来源是实测取证还是模板默认:**

- **环境事实类**(本节)→ 来源必须是实测取证(读驱动运行配置是其中最权威的一种方法),落 `env-facts.json`。
- **统计类**(用例总数 / Pass / Fail / Block / N/A / 通过率 / 自动化率等)→ 来源必须是 `results/*.json` 经 `gen_report.py` 聚合,**人不手工计数、不照抄模板示例数字**;N/A 不计入比例分母(见第六节与 `report-format.md` 三、统计口径)。
- 两类共同的红线:**没有实测支撑的数字/结论,写「未取到 + 原因」,不写一个像样的值。**

### 10.6 硬门

```bash
python3 <SKILL_DIR>/scripts/check_env_facts.py <round目录>/env-facts.json [--report <报告.md>] [--json] [--strict]
```

校验:必备字段齐全且类型合契约、**事实字段与 `XSource` 双向成对**(孤儿 `XSource` 也判错,堵掉「起个 `xxxSource` 名字就既不校验也不要求来源」的绕过)、来源落五类枚举且形态为「前缀」或「前缀(非空说明)」、`null` 与「未取到」互为充要条件、值与来源里都无模板占位残留、`reusedInstance` **为 true 或未取到**时渲染模式不得声称「显式指定」。

带 `--report` 时附加核对报告与取证事实一致,**检测范围严格限定在「一、测试概况」章节内**,渲染模式只看概况里的「渲染模式」行(判 error);概况其它位置出现相反模式词判 warn;`是否复用` 行写反判 error;其余字段未出现在概况判 warn;概况残留 `{…}` 占位判 warn。退出码 `0`(通过)/`1`(不通过)/`2`(输入错误,含文件缺失、根节点非对象)。

> ⚠️ **为什么限定在概况章节内:** 早期版本扫全文,两侧都翻车——概况整行不写渲染模式,却被 `browserVersion` 里的 `HeadlessChrome` 顺带满足了 presence 检查(**假绿灯**);结论章正常写「建议下轮补一轮有头回归」却被判自相矛盾(**假红灯**)。不要改回全文子串扫描。

**产物落点(固定,勿改):** `env-facts.json` 放 `round-{M}/` 根,用例结果放 `round-{M}/results/`。`gen_report.py` 在没有 `results/` 子目录时会回退到扫 round 根,届时靠文件名黑名单 + 「无 `case_id` 即非用例」把 `env-facts.json` 排除掉;但**规范做法仍是把用例结果放进 `results/` 子目录**,别依赖回退分支。

## 十一、数据源归属校验(datasource ownership · 双源对账的前置门)

**要解决的问题:** run-context 的 `datasource` 被直接用于 `[双源对账]` 用例的数据真值对账,**但全程没有任何一步确认这个库就是被测环境实际写入的那个库**。实际项目中曾出现:配的是另一套环境的库,用它查订单做真值判断、得出看似合理的对账结论;而被测环境成功下单后该库始终 0 行——它根本不是这套被测环境的库。

**为什么它比"不做对账"更危险:** 用错库时,SQL 查出来的数与被测页面**本就不该相等**。于是对账要么**假性全红**(把环境差异误报成一批产品缺陷)、要么**凑巧全绿**(两边都是 0 / 都是默认值,漏掉真缺陷),而 `db_assertion.match` 给出的结论**看上去自信笃定**,并一路污染整份报告。**没有归属校验的对账结论,不是"精度差一点",是"完全无意义"。**

### 11.1 触发时机与适用范围

- **时机**:环境准备阶段(驱动连接后、首条用例前),与「运行环境取证」同一时点,**每轮一次**。
- **适用**:run-context 配了 `datasource` **且**本轮存在 `[双源对账]` 用例或 SQL 途径的前置造删数。两者都没有 → 结论直接写 `not-applicable`,不做探针、不影响任何用例。
- **归属**:探针的具体 SQL / DB MCP 调用属**端专有**,只落 [`driver-db-assertion.md`](./driver-db-assertion.md);本节只声明端无关的抽象需求与判定规则。

### 11.2 三级探针(按成本由低到高,任一级判定 `mismatched` 即停,不必往下做)

| 级 | 探针 | 判据 | 成本 |
| :-: | :- | :- | :-: |
| **P1** | **环境标识比对** | run-context `datasource.environment`(`dev`/`test`/`uat`/`staging`/`demo`/`prod`)与**被测入口所属环境**是否一致 | 零成本,必做 |
| **P2** | **环境指纹比对** | 库中的环境标识表 / 配置行(如系统配置表里的环境名、回调域名、租户根)是否指向被测 URL 对应的环境 | 一条只读 SQL |
| **P3** | **端到端回读探针(最强)** | 经**被测环境**的 UI/接口产生一条带唯一标识的数据 → 用该 `datasource` 查是否可见 | 需造一条数据 |

- **`environment` 留空 / 写「未知」 = 判 `unverified`**,不许当成"大概是对的"放行。
- **P1 通过不代表 P2/P3 通过**:同名 `test` 可能是另一套 test 环境。**存在 `[双源对账]` 用例时,至少要做到 P2**;跨系统对账(如"订单中心删数 → 管理控制台看统计")建议做到 P3。

### 11.3 结论与处置(四态,写进 `env-facts.json` 的 `datasourceOwnership` 字段)

| 结论 | 含义 | 处置 |
| :- | :- | :- |
| `verified` | 探针通过,确属被测环境的库 | 正常执行 `[双源对账]` 与 SQL 造删数 |
| `mismatched` | 探针**证否**(如 DB=staging / 被测=test) | **datasource 整体标不适用**:`[双源对账]` 用例降级为纯 UI 断言,或标 `block(precondition-unmet)`;SQL 造删数途径禁用,改走 UI 途径或标 block |
| `unverified` | 未做探针 / 探针本身取不到结论 | 同 `mismatched` 处置(**保守侧**),报告写明"归属未校验" |
| `not-applicable` | 本轮无对账、无 SQL 造删数 | 不影响任何用例 |

- **★硬红线:结论不是 `verified` 时,报告里不得出现任何基于该库的 `db_assertion.match` 结论。** 相关用例必须显式降级并留痕,**绝不允许"先跑着、结论仅供参考"**。
- **报告落点**:`mismatched` / `unverified` 一律写进「三、结论 → 遗留风险」,文案形如「**DB 归属校验未通过(DB=staging / 被测=test),本轮双源对账不可用,N 条 `[双源对账]` 用例已降级为 UI 断言**」。
- **纪律同源**:与第十节「取不到不许编」同一口径——**校验不了就写"未校验"并降级,不写一个自信的对账结论。**

### 11.4 事实字段(纳入环境取证,受同一硬门约束)

`env-facts.json` 增加两个字段,与其余事实字段同规格(`check_env_facts.py` 的**字段自动纳管**会要求它们各配一个 `XSource`,无需改脚本):

| 字段 | 类型 | 取值 | 典型 `XSource` |
| :- | :- | :- | :- |
| `datasourceOwnership` | string\|null | `verified` / `mismatched` / `unverified` / `not-applicable` | `运行取证(P2 环境指纹比对:配置表环境名=test,与被测 URL 一致)` |
| `datasourceEnvironment` | string\|null | run-context 登记的 `environment` | `显式指定` / `未取到(run-context 未填)` |

> **上游契约对齐**:`environment` 字段在 dev-manual-testcase 的自测方案模板 §3.1「数据库」行同样为必填,并配有准入硬门「对账/造数 DB 的 environment 与被测环境一致」。两端同一口径:**上游在方案生成期就把它写死,本端在执行期再校验一次**。

## 十二、自由巡检(free scan · 可选 · 默认关)

### 12.1 为什么需要它

**用例集永远无法穷举页面。** 菜单点得到、但本轮没有任何用例覆盖的页面,其接口 500 / JS 未捕获异常 / 白屏,当前**完全测不出来**——第三节第 4 点的「运行时错误捕获」只在**用例执行后**触发,没有用例的页面就没有触发点。自由巡检补的正是这道缝:不写断言、只走一遍、把运行时错误捞出来。

**它不是用例的替代品**,而是「已知未知」之外的一层兜底:发现的是线索,不是结论。

### 12.2 触发与时机

- **触发**:run-context 执行参数 `free_scan: true`(**默认 false**,不开则整节不执行)。
- **时机**:**全部模块用例跑完之后**,报告生成之前,只跑一轮。
  > ⚠️ **不是"每个模块跑完之后"**——那时「已覆盖页面集合」还不完整,会把后面模块正要测的页面误判为未覆盖,既浪费一次导航,又可能把尚未准备好的前置状态当成缺陷。

### 12.3 未覆盖页面怎么确定(端无关)

1. **可达入口清单**:用 `observe` 读当前的导航/菜单结构,得到入口清单(端无关抽象;Web=菜单树、小程序=tabBar+页面栈、移动=导航项、桌面=菜单栏,各端读法归 `driver-<端>.md`)。
2. **已覆盖集合**:执行过程中累积 —— 每条用例结束时 run-context「五、当前页面/会话状态」记录的页面,并入 `visitedPages`。
3. **待巡检 = 可达入口清单 − 已覆盖集合**。

**端相关降级**:某端驱动读不到导航结构 → 待巡检集合为空,整节跳过、**不因缺该能力失败**(与优雅降级一致)。

### 12.4 执行与结果

每个待巡检页面:`act` 导航 → `observe` 读页面状态 → 拉一次 console/network(同第三节第 4 点的运行时错误通道,`capture_warnings` 同样生效)→ 写结果 JSON。

| 情况 | status | 说明 |
| :- | :-: | :- |
| 导航成功、页面正常渲染 | `pass` | 发现的错误进 `runtimeErrors`,**不判 fail**(没有断言,谈不上"断言失败") |
| 导航失败 / 白屏 / 页面级错误 UI | `fail` | 页面根本打不开,是确定性问题 |
| 入口不可点、权限不足、驱动异常 | `block` | 按既有 `block_reason` 枚举填 |

结果写 `round-{M}/results/`,**必须带 `entry_kind: "free-scan"`**,`case_id` 用 `运行时-<页面>`、`test_name` 填页面名。

> ⚠️ **漏标 `entry_kind` 是本节最容易犯的错**:巡检项会被当成用例计进 `total`,而它们大多 `pass` 且无断言 —— **巡检页越多,通过率越好看**,方向恰好是反的。`check_result.py` 对「`case_id` 已是 `运行时-…` 形态却没标 `entry_kind`」报 Important。

### 12.5 统计口径(硬约束)

- **不计入用例统计**:`total` / 通过率 / 自动化率 / 各模块通过情况一律不含巡检项(`gen_report.split_entries` 分流)。
- **不进缺陷列表**:巡检发现不自动记缺陷,**单列报告 §2.6**,由人确认后转 bug 或补成正式用例进下一轮。
- **通过准则不受影响**:P0=100% / P1≥95% / P2≥80% 只对用例生效。

### 12.6 边界保护(不静默截断)

巡检页数上限 `free_scan_max_pages`(默认 **20**)。超出时**不静默截断**——静默截断会让「巡检过了」这句话名不副实,读报告的人无从知道覆盖到哪为止。

做法**不引入任何新字段**:为"被跳过"这件事**单写一条巡检项**,于是它自动出现在报告 §2.6 表里:

```jsonc
{ "case_id": "运行时-<已达巡检上限>", "test_name": "已达巡检上限,以下页面未巡检",
  "entry_kind": "free-scan", "status": "block", "block_reason": "precondition-unmet",
  "error": "free_scan_max_pages=20 已用尽,跳过 7 个页面:角色管理/审计日志/…" }
```
