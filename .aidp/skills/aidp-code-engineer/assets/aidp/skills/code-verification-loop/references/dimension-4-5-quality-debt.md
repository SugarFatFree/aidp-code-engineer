#### 维度 4: 代码质量检查

> 🎨 **视觉还原两支柱(字段一致性 ⊕ 样式一致性):** 「代码渲染结果对齐**视觉基准**(高保真 mockup **或** 产品原型 `code/` + 设计令牌;二者同等强校验,不因只有原型无高保真而放松,见下「视觉还原度」行 ①)」由两根支柱共同支撑,缺一不可——**支柱① 字段一致性**:以实现页面可见列的**展示名(语义)** / 表单标签(展示语义名) ⟷ 需求字段清单(语义)逐项对账(见下「字段/列对账」行;对账主键为展示语义名,**非**代码级 `prop`/`dataIndex`);**支柱② 样式一致性**:布局结构 / 主色 / 间距 / 圆角 / token 等视觉表现(见下「视觉还原度(L1/L2)」行)。字段对了但样式偏、或样式对了但缺列/多列/改名,都**不算**视觉还原通过。两支柱对齐 AIDP **约定 4**(字段裁剪三件套:需求字段清单(语义) → 「需求字段→处置」对照 → 裁剪登记)与 **约定 22**(需求字段(语义) ⟷ 接口字段漂移防控)。

> 🧩 **对齐原型 = 视觉 + 内容 + 操作逻辑 三层(不止视觉还原):** 上面「视觉还原两支柱」只覆盖**① 视觉层**(见「字段/列对账」+「视觉还原度」行);完整对齐产品原型还必须核到 **② 内容层**——原型 `code/` 可见的**区块 / 卡片 / 表格列 / 表单字段 / 筛选排序 / 按钮次级操作 / 空态·加载·错误·成功等交互态 / 跳转**,一个不许静默漏;与 **③ 操作逻辑层**——**点击反馈·跳转 / 校验规则与时机 / 字段联动 / 条件显隐·禁用 / 增删改-保存-取消·批量流 / 二次确认 / 默认值·初始态 / 多步步序 / 错误处理 / 权限态差异**,禁擅自简化或改流程。内容层与操作逻辑层由下「**内容 + 操作逻辑完整性**」行覆盖,情形 B/C 与视觉还原**同等强度 L1**(与「视觉还原度」的情形解耦一致,不因"只有原型无高保真"放松)。**规划期铁律:原型元素 / 操作逻辑未显式标注「裁剪 / 延期 / 改为X」→ 默认必须照原型实现,漏做 = 违规。**「用项目已有组件」只约束组件实现选型层,不豁免本三层对齐(AIDP 约定28 语义)。

> 🧱 **唯一合规偏离——叶子组件替换白名单(约定28 实现选型层;用于区分「换组件=合规」vs「该对齐没对齐=违规」,「视觉还原度」与「内容 + 操作逻辑完整性」两行共用此边界):** 情形 B/C 下前端【样式·内容·操作逻辑】三层须尽量 100% 还原原型 `code/`,**唯一允许的偏离**是把原型里的**内部原子/叶子小组件**替换成项目已有技术栈的等价组件/载体(如原型 Antd 叶子件 → 项目 Element Plus 等价件)。**白名单(内部原子/叶子小组件 = 实现载体类 + 普通叶子件):** Layout 布局 / Container 布局容器 / Color 色彩 / Link 文字链接 / 单选框 / 多选框 / 下拉选择 / 日期时间选择器 / 进度条 / Tab 页 / Tag / Icon 图标 / 消息提醒 / 计数器 / 开关 / 滑块 / 上传 / 表单 / 列表 / 表格 / 分页 / Alert / Loading / MessageBox 弹框 / Message 消息提示 / NavMenu 导航菜单 / Card 卡片 等**同类叶子小组件**。
> - **★ 实现载体类(Layout / Container / Color / Link)入白名单的判定要点——只放行"换载体"、不放行"改结果":** (i) **合规**:用项目的 `el-container`/`el-row`/`el-col`/`el-link`/项目色彩变量机制去**实现**原型的布局与配色(换的是**载体**,不是**结果**);(ii) **仍判 🔴 Critical**:借"Layout/Container 进白名单"把**栅格划分 / 版心宽度 / 模块位置**改成组件库默认或偏离原型;借"Color 进白名单"把**主色 / 语义色的具体值**改成组件库默认色——这些"呈现结果"由下方硬约束① 锁定,**不因载体可换而放松**。
> - **① 命中白名单的等价替换 = 合规**,不因"不完全像原型组件库"判 Critical(其组件**内部微观样式**差异按 L2 记 🟡 Important)。
> - **② 命中白名单仍须过两条硬约束,任一不满足 = 🔴 Critical:** (i) **主题 token / 布局度量 取自 L1 原型体系**(主色/语义色**具体值** + 栅格划分/版心宽度/模块位置等**布局度量**均来自设计令牌 + 全局主题 + 原型,而非组件库默认观感);(ii) **操作逻辑/交互行为与原型一致**(换的是组件实现、不是行为;借"换组件"简化或改流程 = Critical)。
> - **③ 白名单之外的任何偏离一律 🔴 Critical**(情形 B 应 100% 还原、未标裁剪/延期/改为X):页面结构 / 区块·卡片编排 / 版心与栅格布局被改或简化;整体视觉体系偏离原型 token;内容元素缺失;操作逻辑缺失或被简化/改流程——这些**不属于"换组件",是"该对齐没对齐"**。
> - **判定速查:** 命中白名单 + 两约束满足 → **合规**(内部样式差异 L2/Important 不阻塞);命中白名单 + **主题 token / 布局度量** 或 操作逻辑 不符 → **🔴 Critical**;白名单之外·结构/布局/视觉体系(L1)/内容/操作逻辑 偏离且未标裁剪/延期/改为X → **🔴 Critical**;L2 组件内部微观样式差异(主题 token 已合规) → **🟡 Important 不阻塞**。

> ⚠️ **为什么这四类必须写成有明确锚点的判据、而不是靠「通读一遍看看有没有问题」：**（⚠️ 这里说的是**判据要可锚定**，**不是**说本行配了脚本 —— 见下一条「刻意不配脚本」，本行由验收 Agent 做静态语义核对。）它们的共同点是**「失败态」与「合法空态」在产物上完全同形**——`R.ok([])` 与「真的没数据」、fail-open 放行与「确实有权限」，肉眼分不开。**唯一能把两者分开的静态信号是「这段返回发生在哪个分支里」**，故上表的判据锚点写成「失败分支内」而不是「返回了空集合」。
>
> ⚠️ **本行刻意不配脚本。** grep 级判据抓不到「这是不是失败分支」——`catch` 块的边界、降级分支的条件、`return` 到底在不在块内，都要真正的语法树才判得准，而**判错的方向是假红**（把合法的「业务真空返回空集合」报成 Critical），按本仓库既有教训「假红常驻 = 硬门被绕过」，宁可只留语义核对。③ fail-open 那一条**是四类里唯一 grep 得动的**（安全判据函数内的 `return true` / `return allow()`），但它同样需要「这是不是安全判据函数」的语义前提，故一并留给验收 Agent。

> **与维度 5「硬编码配置」的职责边界(避免重复/矛盾)：** 维度 4 的「HTTP 客户端配置硬编码」是 🔴 **Critical 阻断项**,**只**针对**对外发起 HTTP 请求的真实端点/凭证**(base URL、IP、端口、密钥硬编码进源码,违反核心原则 16,必须改配置驱动);维度 5 的「硬编码配置」是 🔵 **非阻断的技术债登记**,覆盖**其余**魔法数字、内部常量、阈值等"宜提取为配置但不阻断验收"的项。同一处硬编码端点/凭证**只在维度 4 记 Critical,不在维度 5 重复登记**;维度 5 只收维度 4 未覆盖的非外部-HTTP 类硬编码。
