## 核心原则

1. **原型隔离** — HTML 原型仅作为交互逻辑和页面流转的参考，绝不复用其代码作为生产实现。**严禁从原型中推断或默认任何技术栈选择。**
2. **功规点全覆盖** — PRD 中的每一个功能规格点，在设计方案中都必须有对应的实现路径，不允许遗漏。
3. **设计即可测** — 每一项架构决策都配套测试走查逻辑，确保设计产出后可立即进入开发与测试。
4. **用户主权（技术边界不得推断）** — 所有技术选型必须由用户明确选择确认，禁止自动推断或默认绑定。可以用 ⭐ 标记推荐，但最终决定权在用户。据此派生三条 Phase 1 硬约束（落地细则见 Phase 1「⚠️ 技术边界确认硬化」）：
   - **① 禁止推断/静默补全** — 凡要写进详细设计的**每一项技术**（ORM、连接池、序列化方案、后端 WebSocket/SSE 服务端、HTTP 客户端、数据库、缓存、消息队列等），只要用户没在某一步显式选过，**必须先作为 ⭐ 推荐项弹出让用户确认/改选，严禁从已选语言/框架/原型静默推断或默认采用**。
   - **② 打包项透明化** — Step 3「后端核心组合」选定的打包选项（如 `Kotlin + Ktor`）**隐含**的子决策（ORM、构建工具）必须显式回显给用户确认或改选；打包项未覆盖、但本设计确需的配套维度（连接池、序列化、后端 WS/SSE 服务端）必须补充独立询问——**不得因"选了打包项"就当作全部后端栈已定**。
   - **③ 完成门（唯一闸门）** — 全部适用 Step 1~6 逐维度收集完 **且**「确认汇总」经用户最终 accept 之前，**禁止**输出"技术栈确定/技术栈已定"之类结论、**禁止**进入 Phase 2 生成设计；「确认汇总」是进入设计的唯一闸门。
5. **高效交互** — 将强关联的技术选项合并为组合方案，每个交互步骤最多让用户做 **3 次选择**，减少决策疲劳。每次选择只选**一个维度**的技术方案，不要在一次选择中混合多个维度。
6. **终端感知** — 通过分析原型判断项目终端类型（Web/移动端/多端），仅展示相关的技术选项。
7. **接口路径简洁** — 后端接口路径默认不使用 `/api/v1` 等版本号前缀，采用 `/{服务名称}/{接口路径}` 的简洁格式。除非用户明确要求版本化管理，否则不添加版本号。
8. **字段宽容原则** — 数据库字段默认允许 NULL，仅在有充分理由时才设置 NOT NULL。设置 NOT NULL 的字段**必须同时声明初始化方式**（DEFAULT 值、数据库触发器、或应用层强制赋值逻辑），确保任何 INSERT/UPDATE 路径都不会因空值而失败。代码层面对可空字段保持容错处理。

   **强制例外:索引字段必须 NOT NULL(Critical)** — 若字段被任何索引(普通索引 / 唯一索引 / 联合索引 / 主键)引用,**必须**设置为 NOT NULL,且与"字段宽容原则"冲突时**优先 NOT NULL**:
   - **单列索引**: 该列必须 NOT NULL + DEFAULT
   - **联合索引(多列)**: 联合索引涉及的**全部**列必须 NOT NULL + DEFAULT,即使其中部分列业务语义上"可空"也强制 NOT NULL,用业务级"空值哨兵值"代替(如空字符串 `''`、`0`、`'N/A'`、`-1`、`'9999-12-31'` 等)
   - **唯一索引/唯一键**: 涉及列**绝对**必须 NOT NULL,无任何例外
   - **Why**: MySQL 底层语义中 `NULL != NULL`(SQL 标准定义),导致:① 唯一索引允许重复 NULL 行(本应唯一却出现多条 NULL),引发数据完整性事故;② 联合索引中任一列为 NULL 时索引退化(部分查询计划无法走索引);③ 跨数据库迁移(如 Oracle/PostgreSQL/SQLite 对 NULL 处理不一致)行为分歧。设计阶段直接拦截索引列 NULL,从根上规避兼容性陷阱
   - **设计标注**: A.3 表 DDL 中,索引列必须显式声明 `NOT NULL` + `DEFAULT '...'`(类型相符的哨兵值),且在字段 COMMENT 中说明"索引列,空值用 X 表示"
   - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 5「性能与边界」+ 检查项 21「索引列 NOT NULL 强制」
9. **PRD 内容分层取舍** — PRD 中的内容按性质区别对待：
   - **样式/UI/文案/交互规则类内容（以 PRD 为准）**：字段标签、菜单名称、按钮文案、错误提示、颜色/字号规格、交互行为规则、校验规则、权限分级、业务流程步骤等。**即使与原型冲突，也以 PRD 为准**，原型作为参考但不覆盖 PRD 的业务/文案定义。
   - **技术实现类内容（仅供参考）**：PRD 中出现的技术栈、框架、中间件、表结构、字段类型、接口路径、部署方案、性能指标实现手段等属于研发决策范畴。设计方案可在满足 PRD 功能目标的前提下**自主调整**，**最终以详细设计方案为准**。若 PRD 的技术建议不合理或与用户选定的技术栈冲突，在设计方案中明确标注"PRD 建议 X，设计调整为 Y，理由：…"，不需要反过来修改 PRD。
10. **字典/枚举强制枚举类(Critical)** — A.4 中**所有**字典/枚举(无论条目数,即便只有 2 个候选值如启用/停用)必须在设计中明确生成对应**后端枚举类 + 前端枚举类 + 数据库映射器**三件套。**严禁**业务代码以"魔法值"(裸字符串/裸数字)判断状态。
    - **必备字段**: 每个枚举常量包含 `code`(数据库存储)/ `label`(展示文本)/ `description`(业务含义);状态类追加 `color`(展示颜色)
    - **命名规范**: 类名 PascalCase + Enum 后缀(后端,如 `OrderStatusEnum`);常量名 UPPER_SNAKE_CASE(如 `OrderStatusEnum.PENDING_PAYMENT`);前端类名 PascalCase(如 `OrderStatus`)
    - **代码契约 8 项硬约束**: 每个 A.4 条目必须输出"代码契约"小节,包含:① 后端枚举类名 ② 后端文件路径 ③ 前端枚举/常量类名 ④ 前端文件路径 ⑤ 前端定义方式(`enum` 或 `as const`)⑥ 数据库映射方式(`TypeHandler`/`@Convert`/TypeORM `enum`)⑦ Mapper/ORM 引用 ⑧ 前后端 code/label 对齐声明。**完整字段清单与表格格式见** `references/output-module-examples.md` > A.4.3 输出格式 > 代码契约
    - **前后端对齐**: code 与 label 在前后端完全一致;A.3 数据表枚举字段 COMMENT 必须引用枚举类(如 `参考 OrderStatusEnum`);Mapper/ORM 配置类型转换器实现枚举↔code 自动转换
    - **目录约定**: 后端 `enums/` 包(`com.{project}.enums` / `internal/enums/` / `app/enums/`);前端 `src/enums/` 或 `src/constants/enums/`(项目内统一二选一)
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 11「字典/枚举强制生成枚举类(Critical)」（= 本文件工程自检清单的**自检 12**，两套编号不可换算）
11. **货币金额整数原则(Critical)** — A.3 数据表中所有货币/金额字段**必须**使用 `BIGINT`(或等价 64 位整数)按当前国家/地区的**最小货币单位**存储,**严禁** `FLOAT` / `DOUBLE` 与元/美元等"展示单位"；`DECIMAL` **默认同样禁用**，仅在 `flow-money-field.md`「💰 货币金额字段设计规则」列出的**三类**降级场景（1. 已有项目沿用现有约定〔最高优先级〕/ 2. 遗留系统对接 / 3. 展示快照统计表）、且在设计中显式标注降级理由时才允许（`check_money_field.py` 对 FLOAT/DOUBLE 零容忍、对 DECIMAL 判「需降级理由」，两者判据不同）。
    - **必须配套字段**: 多币种业务必须额外存储 `currency_code CHAR(3)`(ISO 4217 三字母码,如 `CNY`/`USD`/`JPY`),并参考 ISO 4217 小数位指数还原展示金额
    - **命名与注释**: 字段命名建议加 `_amount` / `_minor_units` 后缀,COMMENT **必须**写明"单位:<最小单位中文名>"(如 `total_amount BIGINT NOT NULL COMMENT '订单总金额,单位:分(CNY)'`)
    - **展示层职责**: 前端/接口出参展示金额时再按币种小数位指数(中国 ÷100、日本 ÷1、科威特 ÷1000)还原为人类可读金额,后端只传整数
    - **NOT NULL 非强制**: 金额字段是否 NOT NULL 由业务语义决定(参考核心原则 8 字段宽容原则);`NOT NULL DEFAULT 0` 是常见做法(便于 SUM 聚合/避免 NULL 对账歧义),但"退款金额"等字段用 NULL 表示"未发生"也是合理设计
    - **货币最小单位对照表**: 详见`flow-money-field.md`「💰 货币金额字段设计规则」章节
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 17「货币金额字段整数化(Critical)」
12. **历史 SQL 风格沿用(Critical)** — 项目若存在历史 SQL(已上线表结构 / 既有 migration 脚本 / 公司/团队代码库可见的同类表),新生成的数据库设计**必须**与历史 SQL 在以下维度保持一致,不得自创新风格:
    - **命名风格**: 表名/字段名大小写约定(`snake_case` / `camelCase` / `PascalCase`),复数/单数约定(`users` vs `user`),前缀约定(如 `t_xxx`、`tb_xxx`、`biz_xxx`、`sys_xxx` 业务前缀分组)
    - **缩写与术语**: 历史表已统一使用的缩写(如 `user` 还是 `usr`、`address` 还是 `addr`、`description` 还是 `desc` 还是 `remark`),不得在新表混用
    - **公共字段**: 历史表的审计字段命名(如 `create_time` / `created_at` / `gmt_create`、`update_time` / `updated_at` / `gmt_modified`、`deleted` / `is_deleted` / `del_flag`、`creator` / `create_by` / `created_by`、版本号字段名),新表沿用同一套
    - **主键风格**: 历史表的主键类型与命名(自增 `id` BIGINT / UUID `id` CHAR(36) / 雪花 ID `xxx_id` BIGINT)
    - **索引/外键命名**: 历史已有命名前缀(如 `idx_xxx`/`uk_xxx`/`fk_xxx`)与拼接顺序
    - **字符集/排序规则**: 历史 SQL 已统一的 `CHARACTER SET` / `COLLATE` / 引擎(InnoDB/MyISAM)与新表保持一致
    - **检测方式**: Agent 在 Phase 2 数据库设计前,如检测到代码仓中存在历史 SQL(`*.sql`、`migrations/` 目录、`schema.sql`、`flyway/` 或 `liquibase/` 配置等)或用户在输入中提供了历史表结构,**必须先扫描归纳历史风格**(每个维度取出现频次最高的写法),再据此生成新表;扫描结果应在 A.3 数据表设计开头用一段"📜 历史 SQL 风格沿用说明"列出本次沿用的具体约定
    - **冲突时**: 若历史 SQL 内部风格本身就不统一(如老表 `t_xxx` 新表 `xxx`),按"最近一次大版本/最近 6 个月新增表"为准,并在该章节标注理由;若用户明确要求迁移到新风格,在该章节注明"用户授权重构"
    - **例外**: 仅当项目无任何历史 SQL(全新项目)或用户明确豁免时,才按通用默认风格(推荐 `snake_case` + `create_time`/`update_time` + `id BIGINT AUTO_INCREMENT`)生成
    - **Why**: 与历史 SQL 风格不一致会导致 ① ORM Mapper/Entity 注解需要逐字段重写映射 ② JOIN/复杂查询时手写 SQL 心智成本陡增 ③ 数据库 DBA/运维巡检脚本失效 ④ 全文检索代码库时漏命中
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 18「历史 SQL 风格沿用(Critical)」
13. **文本字段长度冗余原则** — 自由输入文本字段(用户可直接键入内容的输入框/多行文本/富文本)的数据库存储长度**必须 ≥ 前端输入限制的 3 倍**,COMMENT 中**必须**标注"前端限制 N 字符,DB 冗余 3×"。
    - **倍数计算**: 基础是前端 UI 设定的字符上限(`maxlength` / `Schema.max(N)` / 校验规则中明示的最大字符数);若 PRD/前端校验有"最长 N 字"则 DB 至少 `3N`,实务可向上取整到 64/128/255/512/1024 等常见档位
    - **字符 vs 字节**: 计算 3× 时按"字符数"计;**`VARCHAR(N)` 的 `N` 按字符还是按字节计随数据库方言而定**——MySQL `utf8mb4` 按字符、Oracle/SQL Server 默认按字节需相应放大。已选库的具体计量口径与上限见 `references/stack-db-*.md`（MySQL 系见 `stack-db-mysql.md` §二、§三；其它方言按该文件 §五 的指引自行核定）
    - **Why**: ① 用户实际输入常超出前端限制(粘贴/拼音输入法/复制富文本带格式),前端校验失效时数据库不应再次截断造成数据丢失;② 业务限制可能在产品迭代中放宽(如"昵称从 20 改 50"),DB 提前预留避免 ALTER TABLE 风险;③ 应用层多重转义(URL encode、HTML 实体、JSON 字符串转义)会让实际入库长度膨胀至 1.5~3 倍;④ 国际化场景中文/全角字符占用倍数差异;⑤ 写入 `Data too long for column` 错误用户体验极差,3× 冗余几乎覆盖所有正常溢出
    - **豁免白名单(无需 3×,按强格式精确长度)**:
      - **强格式字段**: 手机号 `VARCHAR(20)` / 身份证 `VARCHAR(18)` / 邮箱 `VARCHAR(128)` / 银行卡号 `VARCHAR(32)` / 邮编 `VARCHAR(10)` / IP `VARCHAR(45)` / MAC `VARCHAR(17)` / URL `VARCHAR(512~2048)`(格式由协议/法规固定,不应冗余)
      - **系统生成字段**: UUID `CHAR(36)` / 订单号 `VARCHAR(32)` / 雪花 ID 序列化字符串 / Token / Session ID / Trace ID / Request ID(由后端生成,长度固定)
      - **敏感字段**: 密码哈希(`password`/`passwd`/`pwd`,长度由 BCrypt/SHA 等算法决定)/ 盐值 / 密钥(`secret`/`api_key`/`access_key`)/ 签名 / Hash / 校验和 — 长度由加密算法决定,非用户自由输入
      - **设备/序列号**: `device_no` / `serial_no` / `sn`(由设备/系统分配)
      - **扩展属性 JSON 字符串**: `ext_attr` / `extra` / `metadata` / `config` / `settings` 等存储 JSON 字符串的字段(非自由输入,由后端结构决定)
      - **文件路径/对象存储 Key**: `file_path` / `oss_key` / `s3_key` 等(由后端生成)
      - **枚举 code**: 字典 code 字段(如 `OrderStatus.PENDING_PAYMENT`)按枚举常量名最长长度 +20% 余量即可
      - **强约束业务编号**: 与外部系统对接的业务号(如海关编码 13 位、增值税发票号 8 位)按规范精确长度
      - **历史沿用**: 已上线表的字段长度(配合核心原则 12 历史 SQL 沿用,不强行重构;新增同名字段时遵循历史)
      - **TEXT/MEDIUMTEXT/LONGTEXT**: 已是变长大字段,本身无固定上限,不适用 3× 规则(但前端依然应有合理输入限制;如 PRD 限制 5000 字,可保留 `TEXT` 类型)
    - **设计标注规范**: 字段 COMMENT 必须显式写明"前端限制 N 字符,DB 冗余 3×",如 `nickname VARCHAR(150) NULL COMMENT '昵称(前端限制 50 字符,DB 冗余 3×)'`;豁免字段在 COMMENT 标注豁免理由(关键词:`强格式` / `精确长度` / `系统生成` / `固定长度` / `算法决定` / `非自由输入` / `JSON 字符串` / `BCrypt` / `SHA` / `MD5` / `Base64` / `枚举 code` / `历史沿用`),如 `phone VARCHAR(20) NULL COMMENT '手机号(强格式,精确长度)'`、`password VARCHAR(255) NOT NULL COMMENT '密码哈希(算法决定长度,BCrypt)'`、`ext_attr VARCHAR(2000) NULL COMMENT '扩展属性 JSON 字符串(非自由输入)'`
    - **VARCHAR 大长度的注意事项**: 各库都有单行/单字段长度上限,**3× 冗余后可能触顶导致建表失败**,超出即改用 `TEXT`/大字段类型。具体阈值见已选方言文件（MySQL InnoDB 的 65535 字节行长上限与 utf8mb4 下 `VARCHAR` 实际上限见 `references/stack-db-mysql.md` §三）
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 5「性能与边界」> 文本字段长度冗余子项
14. **第三方接口临时 Mock 运行时可控原则(Critical)** — 第三方接口临时 mock 必须是**部署后运行时可控**的（任意环境通过环境变量启用/关闭），严禁使用构建期守卫导致 mock 代码在打包后被裁掉或部署后失效。 ⚠️ **本原则的适用对象只有 `THIRD_PARTY_MOCK`（第三方未交付）**，⛔ 不要套到 `DEV_MOCK`（同项目后端未部署）上——**两者的守卫策略相反**：`THIRD_PARTY_MOCK` 要活到 UAT/Demo 故必须运行时开关；`DEV_MOCK` 绝不能进生产，`import.meta.env.DEV` 这类构建期守卫正是它**要求的合规形态**。硬门 `check_third_party_mock_runtime.py` 已按此分流：**只含 `DEV_MOCK` 标注的代码块不查构建期守卫**，其标注块必填字段只有 `since` / `owner` / `REMOVE_WHEN`。`DEV_MOCK` 的定义与推荐写法的单一信源在 `dev-execution-planner/references/flow-edge-cases.md` 情况 1，运行时判据在 `code-verification-loop` 维度 2B。
    - **🚫 严禁构建期裁掉 / ✅ 必须运行时可控**: mock 的启用与否必须**部署后可切换**（改环境变量/配置即可），严禁任何在构建期被 tree-shake、被 profile 裁掉、被条件编译排除的写法——否则 UAT/Demo 环境部署后 mock 根本不可用，而那恰恰最需要它。**各栈的具体反模式与正确写法（代码示例）按需加载**：`references/stack-vue.md` §二（Vite `import.meta.env.DEV`）/ `stack-react.md` §二（另含 CRA `REACT_APP_*`、Next `NEXT_PUBLIC_*` **构建时静态替换**陷阱）/ `stack-java-spring.md` §五（`@Profile("dev")`、Maven Profile 条件编译）/ `stack-nodejs.md` §四 / `stack-go.md` §四（build tag）/ `stack-python.md` §四 / `stack-dotnet.md` §四（`#if DEBUG`）
    - **🎯 Mock 实现位置选型（优先级降序）**: 设计 B.7 必须为每个未交付的第三方接口标注 mock 实现位置选型，**优先选择前端 mock 方案**:
      - **P0 前端 mock（首选）**: 适用于第三方接口仅供前端调用的场景（如 OAuth 登录回调、地图 SDK、支付收银台、用户授权页跳转）。实现方式: axios/fetch 拦截器 + 运行时环境变量判断 + 独立 fixture 文件（`src/mocks/fixtures/*.json`）。**优势**: 无需后端介入，前端独立联调；不污染后端代码仓；切真实接口只需关闭前端环境变量，后端零改动；团队协作效率最高
      - **P1 后端 mock（次选）**: 仅当第三方接口供后端服务端调用时使用（如服务端鉴权、银行代扣、报关推送、回调签名验证）。实现方式: 统一 mock 端点 + 运行时配置开关（`@Value("${third-party.mock.enabled}")`）+ if 分支判断返回 mock 数据。**劣势**: 需后端开发介入；增加后端代码复杂度；切真实接口需后端修改配置
      - **P2 中间件 mock（最后）**: 仅当前后端都需调用且接口复杂、需团队共享 mock 服务时使用。实现方式: json-server / Mockoon / WireMock standalone
      - **判断口诀**: "前端能拦截就前端拦截，前端拦截不了再让后端 mock" — 大幅减少跨角色沟通成本
    - **Why**: ① 第三方接口在 UAT/Demo 环境部署时可能仍未交付，需在部署后环境启用 mock 展示功能 ② 真实接口对接完成后，开发环境应立即切换到真实接口验证，而不是继续用构建期 mock 拦截导致对接问题被掩盖 ③ 构建期守卫在前端会被 tree-shake 裁掉（Vite/Webpack 在 production mode 下移除 `if (false)` 死代码），后端会因 Profile 不匹配导致 mock 类不加载，造成"开发可用、部署失效"的不一致 ④ 运行时可控让 mock 的启用/禁用成为配置决策而非代码决策，降低风险
15. **第三方接口交付状态分类** — 详细设计 B.7 外部依赖与集成章节中，**每个**第三方系统集成必须明确标注交付状态（`✅ 已交付` / `⚠️ 已交付·字段不全` / `⏳ 未交付` / `🔧 暂行方案`），与 Module E 待澄清清单交叉引用:
    - **✅ 已交付**: 第三方已提供 base URL、凭证、联调环境，可开始对接真实接口；不允许使用 mock。**⚠️ 判"✅ 已交付"前必须先过下条「字段满足度核验」——接口能连通 / 契约已知 ≠ 入参出参满足我方需求；只有"字段/查询维度全部覆盖我方需求所需数据项"才算真正已交付**
    - **⚠️ 已交付·字段不全（部分满足，Critical）**: 第三方接口**已存在 / 契约已知**（有接口文档、Swagger、能调通、或可读对方源码），但其**入参或出参缺少我方需求所需的部分数据项**——**严禁**因"接口已经有了"就笼统判"✅ 已交付 / 接口已满足"而略过。必须:
      - **逐条列出缺失项（用业务语义，不写对方字段名/URL/结构）**: 分两类——「**缺失出参**」= 我方需求要展示/计算、对方接口未返回的业务数据项；「**缺失入参**」= 我方需要按某业务维度查询/筛选、但对方接口不支持该维度。逐条枚举，对齐需求字段清单(语义) + B.7「③ 业务数据项逐条枚举子表」的「是否必返 / 对应查询筛选维度」列，**严禁**用"等/若干字段"一笔带过
      - **转为字段补充需求**: 每个缺失项等同一条"需第三方补该数据项 / 补该查询维度"的对外诉求，并入 B.7 方向 2「需第三方提供的业务诉求清单」（标"🔧 字段补充"类型），在 Module E 登记 D-NNN「第三方接口 <能力名> 字段不全待补/待澄清」并双向引用
      - **处置分流（每个缺失项必显式标一种，严禁静默按"已满足"处理）**: `请第三方补` / `前端计算还原`（仅当能由对方已返的其他数据推导时）/ `裁剪`（须经产品确认该数据点可不要）
      - **Why**: 第三方接口"存在"只回答"有没有这个能力"，没回答"字段 / 维度够不够我方用"。把"部分满足"误判成"完全满足"，会让下游按"接口已就绪"编码，联调阶段才发现要读的字段对方根本没返、要按的维度对方根本不支持——返工成本高，且需求阶段没提字段补充，第三方无义务补，甩锅困难
    - **⏳ 未交付**: 第三方接口尚未交付，在 B.7 标注预计交付日期（`expected_ready: YYYY-MM-DD`），并在 Module E 登记 D-NNN 条目（状态 `⏳ 待第三方交付`）；**研发阶段允许使用带 `THIRD_PARTY_MOCK` 标注的临时 mock 占位**（实现方式必须符合核心原则 14「第三方接口临时 Mock 运行时可控原则」）
    - **🔧 暂行方案**: 第三方长期无法交付或项目决定暂不对接，说明替代方案（人工处理/简化流程/使用其他服务）；Module E 标注理由
    - **THIRD_PARTY_MOCK 标注协议（代码层面）**: 临时 mock 必须在代码中带完整的标注块（7 行：THIRD_PARTY_MOCK 标识 + 6 个必填字段），每行独占:
      ```typescript
      // THIRD_PARTY_MOCK: {一句话说明}
      // vendor: {第三方供应商，如：支付宝 / 微信支付 / 海关总署 / OAuth-IDP}
      // api: {对接的接口路径，如：POST /alipay/trade/refund}
      // since: {开始使用 mock 的日期，YYYY-MM-DD}
      // expected_ready: {预计交付日期，YYYY-MM-DD；未知填 UNKNOWN}
      // owner: {负责人}
      // REMOVE_WHEN: 真实接口可调通后立即删除本{函数/常量/文件}，禁止保留为兜底
      export async function mockAlipayRefund(orderId: string) { ... }
      ```
    - **关键判定规则**: 一旦真实 vendor SDK / 凭证 / base URL 出现 → mock 必须立即删除（否则违规）；严禁 catch / `||` / fallback 中调 mock（任何场景禁止 mock 兜底）；`expected_ready` 过期超过 14 天必须催第三方或转 Module E 暂行方案
    - **Why**: 第三方平台接口受外部交付节奏制约，完全禁止 mock 会阻塞研发；但 mock 与真实调用并存会改变业务语义 → 用结构化标注块 + 自动核验（下游 code-verification-loop / dev-execution-planner 的 scan_mock_data.py --third-party-mode，本 SKILL 不自带该脚本）代替主观判断
    - **下游协作**:
      - `dev-execution-planner`: 边界情况「情况 0：第三方平台接口未交付」按本协议拆 Task，**前端 mock 优先**（后端无需创建 mock 占位 Task，节省工时），Mock 实现必须符合核心原则 14「运行时可控」，验收标准强制"删除 THIRD_PARTY_MOCK"
      - `code-verification-loop`: 维度 2B 第三方临时 mock 协议核验，自动检测并存/兜底/过期/字段缺失；**新增反模式检查：构建期裁掉（DEV guard / @Profile）、真实对接后残留**；前端 mock 与后端 mock 均需符合 7 行标注块(THIRD_PARTY_MOCK + 6 个字段) + 运行时可控原则
      - `dev-manual-testcase`: 涉及未交付接口的用例标 `[待第三方交付]`，不计入正式回归覆盖率；**测试场景需覆盖 Mock 全生命周期（开发用 mock/真实、部署用 mock、真实对接后清理验证）**
16. **HTTP 客户端配置驱动铁律(Critical)** — 后端发起外部 HTTP 请求（对接第三方 / 调用其他微服务 / 聚合远程数据）时，**必须**使用 Phase 1 Step 3 选择 3 选定的 HTTP 客户端方案（如 OpenFeign / OkHttp / WebClient / RestClient / @HttpExchange / httpx / aiohttp / axios / fetch / undici / net/http / resty / HttpClient + IHttpClientFactory / Refit / Ktor Client），并在详细设计中**严格按以下铁律落地**:
    - **🛡️ 严禁硬编码**: 严禁在代码中硬编码 base URL / IP / 端口 / 凭证;所有可变参数必须走配置文件(`application.yml` / `config.yaml` / `.env` / `appsettings.json` 按语言对应);敏感凭证必须使用 `${ENV_VAR}` 占位符引用环境变量,运行时从 KMS / CI Secret / OS 环境变量注入
    - **🛡️ A.2 必须给出落地示例**: A.2 章节必须包含「HTTP 客户端落地」子章节,提供 (a) Bean / Client 初始化示例代码 (b) 配置文件示例(完整 YAML/JSON/.env 块)(c) 服务发现集成声明(若与 Nacos/Eureka/Consul/etcd 集成,标注服务名+命名空间+分组,直连服务名调用)。完整模板见 `references/output-module-examples.md` > A.2 > "HTTP 客户端落地规范"
    - **🛡️ B.7 必须引用 A.2 配置 Key**: 每个第三方系统集成在 B.7 章节必须 (a) 标注所选 HTTP 客户端方案,与 A.2 一致 (b) 引用 A.2 中的具体配置 Key(如 `third-party.alipay.base-url`)而非重复定义 (c) 标注服务发现集成方式(走服务名 / 直连域名)
    - **🛡️ D.3 依赖列表对齐**: D.3 后端依赖必须列出所选 HTTP 客户端依赖(如 OpenFeign 列 `spring-cloud-starter-openfeign` + Nacos Discovery + 熔断组件),版本与 A.2 示例一致
    - **🛡️ 失败返回契约 ⟷ 调用方失败判定对齐(Critical)**: 详细设计 / 接口设计时**必须显式规定"客户端 / 下游失败时返回什么"**——在【① 抛异常 / ② 返回带 `_error` 标记的结构 / ③ 返回 `Optional` / 空对象】三种失败返回风格中**明确三选一,并全链路统一**。**同一调用链严禁"吞异常返裸空(如 `return new HashMap<>()` / 裸空 Map / 空 List)"与"带 `_error` 错误标记"两种失败风格混用**：一端吞异常返空、另一端按错误标记判失败,会让**系统故障被静默降级成"真空数据"**(如下游超时 → 返空 Map → 上游 `isEmpty()` 判空 → 当成"用量为 0"),用户看到 0 却无任何错误提示、`partial` 仍为 `false`。**铁律**:系统故障(超时 / 连接失败 / 5xx / 无法解析)导致的"无数据"**必须能与"业务上真的没有数据(真空)"区分**——或抛异常上抛、或在返回体显式置 `partial=true` / 错误态字段 / `_error` 标记,**禁止把系统故障静默等同于空结果**。新老代码风格不一致时(老代码惯用"吞异常返空 + `isEmpty()` 判空"、新代码用错误标记)尤须在设计中点名对齐口径,不得让两种风格在同一链路相遇。**Why**: 失败返回契约不对齐是最隐蔽的一类线上事故——不报错、不抛异常、数据看似"正常为 0",监控与用户均无感知,直到业务对账才发现故障期数据全被吞成 0
    - **配置项强制走配置**: 第三方 base URL / IP / 端口、API Key / Secret / 私钥、连接超时 / 读超时、重试次数 / 退避策略、熔断阈值、服务发现地址、是否启用 mock / 降级开关 — 全部必须配置化,业务调优时无需改代码
    - **配置项严禁出现的写法**: ❌ `client.BaseAddress = new Uri("http://192.0.2.100:8080")` / ❌ `httpx.AsyncClient(base_url="https://api.example.com")` / ❌ `@FeignClient(url = "http://localhost:8080")` / ❌ API Key 写在代码或 yaml 明文 / ❌ 把 `.env` 提交到 git(用 `.env.example` 模板代替)
    - **跨语言/跨场景适配**: **按已选技术栈加载对应落地细则，勿全量读** —— `references/stack-java-spring.md` / `stack-kotlin.md` / `stack-go.md` / `stack-python.md` / `stack-nodejs.md` / `stack-dotnet.md` 各自的「核心原则 16 落地」节，含该栈的客户端初始化写法、配置块样例、服务发现集成方式与失败返回契约的语言化表达（索引见 `references/stack-index.md`）
    - **Why**: ① 不同环境(dev/test/prod)需走不同 base URL,硬编码必然导致部署事故 ② 凭证泄漏到代码仓后历史无法清除,即使 force-push 也会留在 fork / CI cache / Reflog ③ 业务调优(超时、重试、熔断阈值)频繁发生,改代码上线成本远高于改配置 ④ 服务发现使代码与拓扑解耦,IP / 端口变更不需要发版 ⑤ Mock / 降级开关用 feature flag 控制,可灰度可回滚
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 8「外部依赖与集成说明」(含 HTTP 客户端选型一致性 / 配置驱动 / 服务发现集成 / 失败返回契约对齐 4 个 Critical 子项),并与检查项 4「异常处理」的"系统故障吞成空数据"反模式镜像互补
17. **缓存机制用户确认原则(Critical)** — 在详细设计中，**严禁**未经用户明确要求就在接口设计、数据访问层、业务逻辑层中添加任何形式的缓存机制（Redis / Memcached / 本地缓存 / Spring Cache / HTTP 缓存头 / CDN 缓存策略）。即使从性能优化、减少数据库压力、降低接口调用频次等角度判断"应该使用缓存"，也**必须**在设计方案中标注"建议使用缓存（待用户确认）"并**主动向用户确认**后才能在最终设计方案中体现缓存实现细节。
   - **Why**: ① 缓存引入会显著改变系统行为(数据一致性、过期策略、雪崩风险、缓存穿透/击穿/雪崩防护、冷启动预热、多级缓存同步),属于架构级决策,用户有权决定是否接受复杂度成本 ② 用户可能有特定缓存方案偏好(如统一 Redis 集群 vs 本地 Caffeine、过期策略、Key 命名规范)③ 业务场景可能对数据实时性有特殊要求(如金融交易、库存扣减严禁缓存)④ 缓存会增加运维成本(监控、故障处理、容量规划)
   - **必须确认的场景**: 接口响应缓存、数据库查询结果缓存、**ORM 二级缓存(MyBatis `<cache/>` / Hibernate L2 Cache / JPA `@Cacheable(true)`)**、字典/枚举数据缓存、分页列表缓存、热点数据缓存、Token/Session 缓存、接口限流计数器、分布式锁(Redis 实现)、消息去重表/幂等键缓存
   - **豁免场景(无需确认)**: ① JVM/CLR/V8 内置缓存(如 Class 元数据、方法内联、字符串常量池)② HTTP 标准协商缓存(`Cache-Control` / `ETag` / `If-None-Match` / `Last-Modified` / `304 Not Modified` — 浏览器与服务器协商,不涉及服务端缓存组件)③ 浏览器静态资源缓存(前端 webpack 构建产物指纹缓存)④ 数据库连接池/语句缓存(`PreparedStatement Cache`,连接池机制非业务缓存)⑤ CDN 边缘缓存(纯 CDN 配置,无服务端代码改动)⑥ DNS 解析缓存(操作系统/网络层)
   - **确认方式**: Agent 在 Phase 2/Phase 3 生成设计方案时,若判断某接口/查询"适合使用缓存",**必须先停止生成**,向用户明确说明: (a) 哪个接口/数据访问适合缓存 (b) 缓存理由(查询频繁/数据变更低频/接口耗时长)  (c) 建议的缓存方案(Redis / 本地缓存 / 多级缓存)(d) 数据一致性权衡(过期时间 / 主动失效策略),并**等待用户明确回复"同意"/"使用XX方案"/"不需要缓存"后再继续生成**
   - **标注规范**: 若用户同意使用缓存,在 A.2 章节标注「缓存方案」子章节,说明 (a) 缓存中间件选型与版本 (b) 缓存 Key 命名规范 (c) 过期策略 (d) 一致性保障机制;在 B.X 接口设计章节对应接口标注 `[缓存: Redis, TTL 5min, 主动失效: 数据更新时]`;在 D.3 依赖列表中添加缓存依赖
   - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 23「缓存机制用户确认(Critical)」(另见检查项 8「外部依赖与集成说明」的缓存子项)

18. **代码事实采集深度铁律(Critical)** — 设计期扫描既有代码以判定"接口/能力是否已存在"时,**严禁仅凭 Controller / 路由层注解就判定为"沿用已有"**。Controller 存在 ≠ 能力可用。必须穿透到 Service 实现层,确认是真实业务实现还是占位实现。
    - **必读层级(三层穿透)**:
      - **L1 路由/Controller 层**: 接口路径 + HTTP 方法 + 请求/响应 DTO(回答"接口是否已声明")
      - **L2 Service 接口层**: 业务方法签名 + JavaDoc / 注释(回答"接口的业务语义")
      - **L3 Service 实现层(必须读)**: 方法体的实际逻辑(回答"业务能力是否真正可用")
    - **占位实现识别清单(L3 命中任一即判定"未实现"):**
      - `throw new BizException(501, "未实现")` / `throw new UnsupportedOperationException(...)` / `throw NotImplementedError()`
      - `return null` / `return Collections.emptyList()` / `return new XxxVO()` 且方法体仅 1-2 行无业务逻辑
      - `return mockData()` / 返回硬编码假数据(尤其字段含"测试""mock""demo"语义)
      - `// TODO: 实现` / `// FIXME: 占位` / `// XXX: 暂未实现` 注释 + 空方法体
      - `@Deprecated` 注解 + 提示"已废弃,使用 XX 接口"
      - 方法体仅 `log.warn("接口未实现")` 或类似日志后直接返回
    - **判定规则**: 凡 L3 命中占位实现的接口,在详细设计中**严禁**标注为"✅ 沿用已有",必须改标:
      - **🔧 待实现**: 接口声明已在,业务逻辑需新建/补全;在 B.1 标注 ❓ + 在 Module E 登记 D-NNN 条目
      - **❌ 已废弃**: `@Deprecated` 标记的接口禁止沿用,必须新建接口
      - **🛰️ 外部系统接口**: 占位实现是因为依赖外部系统未交付(如调用 `ORD-API-021` 但未对接) → 按核心原则 15「交付状态分类」处理
    - **强制核验步骤(每个"沿用接口"必跑)**:
      1. 定位 Controller 方法 → 找到调用的 Service 方法名
      2. 读取 Service 接口定义 + 实现类(`XxxServiceImpl`)
      3. 检查方法体是否命中"占位实现识别清单"
      4. 若命中,在 B.1 功规点映射表「实现状态」列标注准确状态,**不得**仅写"✅ 沿用"
    - **字段级契约核对(Critical 必跑,防"接口能调通但出参缺字段"伪沿用)**:
      - **前提**: Service 实现层已确认非占位(上述三层穿透通过)
      - **问题**: Controller 存在 + Service 非占位 ≠ 接口契约可用。实测发现 `/overview/dashboard` 接口能调通,但真实出参 `{ dashboardData: {...} }` 无 `userStats` 字段,设计文档 B.2 却写"出参含 userStats"(直接抄原型代码 `console.ts` 的字段消费),前端按设计读取永远 `undefined`,联调阶段才暴露。
      - **核对流程(每个标"✅ 沿用"的接口必跑)**:
        1. **信源优先级**: 已部署后端真实出参 > Swagger/OpenAPI 文档 > 代码 DTO 定义 > 原型代码字段消费(原型代码**仅供 UI 交互参考**,**严禁**当成接口契约信源)
        2. **抓取真实出参**: 运行 `curl -X GET <已部署后端 base-url>/<接口路径> -H "Authorization: ..."` 或 Postman 调用,抓取真实响应 JSON(若后端未部署 → 标"🔧 待实现"而非"✅ 沿用")
        3. **提取前端消费字段**: 扫描 PRD「六、字段规格表」+ 原型 HTML(`data-bind` / `{{field}}` / `v-model` / React `{data.field}`)+ 原型 JS(`console.ts` / `mock.js` / `response.data.field`),提取前端要读取的字段路径清单(如 `userStats.totalCount` / `dashboardData.revenue`)
        4. **字段级比对**: 对每个前端消费字段,检查是否存在于后端真实出参 JSON 中(支持嵌套路径,如 `data.items[0].name`)
        5. **契约缺口判定**: `前端要读的字段 ⊆ 后端真实出参字段` → ✅ 通过;否则 → 🔧 契约缺口(在 Module E 登记 D-NNN,列出缺失字段清单 + 处置方案:① 后端补字段 ② 前端改读其他字段 ③ 标"待澄清")
      - **B.2 接口契约字段说明信源铁律**: 必须以"已部署后端真实出参"为唯一信源;严禁直接抄原型代码的字段消费(`console.ts` 里读 `response.userStats` ≠ 后端真实出参有 `userStats`)。若后端未部署 / 出参缺字段 → 标"🔧 待实现"或"🔧 契约缺口",**不得**写"✅ 沿用"。
      - **自动化辅助**: 运行 `check_api_contract_alignment.py <设计文档> <PRD> <后端 base-url> [--auth-token <token>]` 自动核验(详见检查项 25)
    - **Why**: 实测发现 `UsageMonitorController.overview` 在 Controller 层存在,但 `UsageMonitorServiceImpl.overview()` 方法体只是 `throw new BizException(501)` — 这种伪沿用让需求方误以为"接口已就绪",导致联调阶段才发现"接口能调通但永远报错",上下游耦合的产能损失巨大。**字段级契约缺口更隐蔽**:接口能调通 + Service 非占位,但真实出参 JSON 缺字段(如 `/overview/dashboard` 返回 `{ dashboardData: {...} }` 但无 `userStats`,前端按设计读取 `response.data.userStats.totalCount` 永远 `undefined`),联调阶段才暴露"字段不存在"错误,返工成本高。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 25「代码事实采集深度核验」

19. **第三方依赖反向兜底识别(Critical)** — 第三方依赖识别**严禁**仅靠 PRD 关键词扫描("对接""调用第三方""外部平台")。PRD 漏写时必须从代码 / 数据库 / 数据来源映射三向反推。
    - **正向识别(PRD 信号,可能漏判)**:
      - PRD 第七章/第八章/第九章出现"对接 / 集成 / 调用 / 接入"等动词
      - PRD 字段规格表标注外部接口路径(如 `ORD-API-021 GET /xxx`)
      - PRD 数据来源章节标记"🛰️ 外部系统接口"(对应 ux-logic-extractor 六·2 强制规则)
    - **反向识别(代码兜底,Critical 必跑)**:
      - **代码扫描**: grep `RestTemplate` / `WebClient` / `OkHttp` / `Feign` / `httpx` / `axios.create` / `@FeignClient` / `IHttpClientFactory` / `Refit` 等 HTTP 客户端调用,检查 base URL 是否指向**非本系统域名**
      - **配置扫描**: grep `application.yml` / `.env` / `appsettings.json` 中所有 `base-url` / `endpoint` / `host` 配置项,标记非本服务地址
      - **依赖清单扫描**: 读 `pom.xml` / `package.json` / `requirements.txt` 中是否含 vendor SDK(`alipay-sdk` / `wechatpay-java` / `aws-sdk` 等)
      - **数据来源映射反查**: 对照 PRD 数据来源说明(六·2),凡标注"🛰️ 外部系统接口"或"🛰️ 外部系统消息推送"的字段,逐一定位其在代码中的调用位置
    - **判定规则**: 正向 + 反向**两路并集**为最终第三方依赖清单
      - 正向有 + 反向无 → 视为"PRD 提及但未实现",列入待实现清单
      - 正向无 + 反向有 → **关键漏判信号**,必须主动询问用户:"代码中检测到调用 X 系统,但 PRD 未提及,是否纳入本次需求?"
      - 正向无 + 反向无 → 真正"无第三方依赖",B.7 章节标注"无外部依赖(已扫描代码 + 配置 + 数据来源映射,均无外部系统调用)"
    - **关联项目事实清单消费(跨项目穿透,Critical):** 第三方/外部依赖不只来自"本项目代码 + references 文档";当上游命令端(`/version`、`/sprint-plan` 等)在**事实清单**中标注了"关联项目已提供接口"——含**接口路径 + 实现类 + 已穿透确认为真实实现**(非占位)——时,该接口等同"本系统已可用的既有外部能力",**必须**消费此标注:
      - **必须**按 `✅ 沿用关联项目现有接口` 处理,B.7 登记"沿用 <关联项目名> 现有接口 <路径>(实现类 <类名>,事实清单已穿透确认)",并纳入核心原则 20 类型 C 复用候选
      - **严禁**默判"第三方未就绪 / 需第三方新出文档 / D-NNN 降级兜底"——事实清单已穿透确认即视为真实存在(等同核心原则 18 穿透 Service 实现层确认可用)
      - **降级兜底的唯一前提**: 事实清单**未标注**该接口 **且** references 文档**也无** → 才允许标"待第三方交付 + 降级兜底(D-NNN)";事实清单已标注却仍标降级 = 漏判,不通过
      - **Why(P2 实测漏洞)**: 被设计项目可直接读兄弟项目(订单中心)源码,后者已有 `GET /api/v1/external/orders/statistics` 正好满足总览页"订单分析";但因 references 文档滞后、SKILL 只穿透"本项目"代码,误判"订单中心未就绪 → D-001 降级兜底"。命令端把可访问的关联项目源码扫进事实清单后,SKILL 必须消费该标注,认出"已存在可复用"。
    - **🔒 第三方接口入出参契约不臆造铁律(Critical):** 第三方/外部接口的**入参(名 + 类型)与出参(字段)严禁按命名习惯臆造**。参数来源优先级(降序):
      1. **可访问的对方源码**(穿透确认真实方法签名 / DTO,见上「关联项目事实清单消费」)→ 用**真实参数名**
      2. **用户 / PRD / references 提供的接口文档**(Swagger / OpenAPI / 字段规格表)→ 用**文档参数名**
      3. **都没有(只有 URL、缺入出参)→ 必须在 Module E 登记 `D-NNN 参数待第三方/用户确认` + 主动向用户询问真实入参 / 出参**,严禁默认 `startDate/endDate`、`pageNo/pageSize`、`code/msg/data` 等任何命名习惯
      - **"只有 URL ≠ 契约已知"**: URL 已知、参数未知时,接口契约视为「**未确认**」,**不得**在 B.2 / B.7 接口设计里写出具体参数名当作事实;只能写占位(如 `<入参待确认>` / `<出参字段待确认>`)+ D-NNN「参数待第三方/用户确认」
      - **我方后端"透传"第三方接口时,透传参数名必须与第三方实际参数名逐字一致**(对方用 `from/to`,我方就不能写 `startDate/endDate`);不一致即契约缺口,标 D-NNN「参数名不一致」并主动澄清
      - **Why(实测漏洞)**: 被设计项目对接订单中心统计接口,用户/PRD 只给了 URL 没给入出参,设计期按命名习惯把后端透传参数臆造成 `startDate/endDate`,而订单中心实际用 `from/to` → 联调才发现字段对不上、返工。只有 URL 时必须走 D-NNN 主动询问,严禁臆造参数名。
    - **严禁的默判行为(对应"第三方依赖识别失效"漏洞):**
      - ❌ "PRD 未提 → B.7 写'第三方对接:无'" — 这是漏判的铁证
      - ❌ 仅扫 PRD 关键词,不扫代码 / 配置 / 数据来源映射
      - ❌ B.7 留空或写"暂无"而无任何扫描证据
    - **必填证据**: B.7 章节即使判定为"无第三方依赖",也必须列出**已执行的扫描动作清单**(三向扫描各 1 次的脚本命令 / 关键词 / 时间戳),让下游可复核。
    - **Why**: 实测发现 PRD 主稿 + 补充 01 仅描述订单分析展示什么 UI,从未提"数据来自 ORD-API-021" → 设计期关键词扫不到 → 默判"无第三方依赖" → 编码计划"第三方对接:无" → 联调阶段才发现接口未交付。反向兜底是堵这一漏洞的唯一办法。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 26「第三方依赖反向兜底识别」

20. **复用优先与去重(Critical)** — 设计期判定"新增 vs 沿用"时,**严禁**仅凭 PRD 没说"沿用"就默判"新增";同样**严禁**已识别"沿用已有"就停止扫描。必须同时核验"该能力是否已存在"(纵向 = 核心原则 18)与"该能力是否已被多处调用"(横向 = 本原则)。
    - **四类复用场景必须主动识别:**
      - **类型 A 业务数据复用**: 同一份业务数据(如"用户信息""部门列表""订单状态")可能已有 Entity/Mapper/Service/Controller,新需求只是换 UI 位置展示。设计期必须扫描代码仓 `entity/`/`mapper/`/`service/`/`controller/`,识别同名/相似实体,**严禁**为同一份数据新建第二份 DDL。
      - **类型 B 接口复用**: 同一业务能力(如"查询用户列表""获取订单详情")可能已有 Controller endpoint,新需求只是换调用方/换响应字段。设计期必须扫描已有 Controller,识别同 path 或语义相近 path,**严禁**为同一能力新建同义接口。响应字段差异通过 query param / view 模型扩展解决,不重新建接口。
      - **类型 C 第三方接口复用**: 同一第三方接口(如 ORD-API-021、阿里云 SMS、支付宝退款)可能已被本系统其他模块对接过,新需求只是换调用 Service。设计期必须扫描代码仓 `@FeignClient` / `httpx.AsyncClient` / `axios.create`,识别已对接的 vendor + endpoint,**严禁**为同一第三方接口新建第二个 Client / 第二套配置 / 第二份重试策略。**复用候选还包括「关联项目已有接口」**: 当事实清单标注了可访问的兄弟 / 关联项目(如订单中台)已实现并穿透确认的接口时,把它纳入类型 C 复用候选,按"✅ 沿用关联项目现有接口"处理(详见核心原则 19「关联项目事实清单消费」),**严禁**默判"需第三方新提供 / 降级兜底"。
      - **类型 D 同源统计/聚合复用**: 已有"用户列表/订单列表/工单列表"等明细数据,新需求是基于同一数据源的**统计 / 分类 / 分组 / 汇总 / 聚合 / 透视**(如"用户按部门统计""订单按月汇总""工单按状态分布""消息按类型分类")。设计期必须识别"是否同一数据源",**严禁**为统计需求新建第二份明细表 / 重复采集相同业务数据。**正确做法**: 复用已有明细表 + 新建独立的统计 Service / GroupBy SQL / View,在 B.1 标注 `✅ 复用已有数据,新增统计逻辑`,在 A.3 不新建实体表,接口路径用 `/xxx/stats` / `/xxx/aggregate` / `/xxx/by-{维度}` 等命名以区别于明细查询接口。**典型反例**: 已有 `biz_user` 表 + `GET /user/list` 接口,新需求"用户按部门统计"绝**不**新建 `biz_user_dept_stats` 表,而是 `SELECT dept_id, COUNT(*) FROM biz_user GROUP BY dept_id` + 新增 `GET /user/stats/by-dept` 接口。
    - **🎯 展示型新需求强制正向核验(新页面 / 新区块 / 新概览节点展示指标时,Critical 触发点):** 当一个新页面 / 新区块 / 新概览节点要**展示某个指标**(如"企业员工数""本月积分消费总量""订单分析")时,**严禁**默判"总览页要展示 → 新建节点 / 新请求第三方 / 需订单中心新提供"。必须对**每一个要展示的指标**回头做正向核验,三向反查既有实现:
      - **既有页面/菜单反查**: 该指标或其同源数据,是否已被某个现有菜单 / 页面在展示或获取?(实测反例:"企业员工数"已被「用户与组织」菜单的企业员工列表展示;"本月积分消费总量"已被「费用账单」菜单的本月消费积分获取——二者都不是"需订单中心新提供的概览节点")
      - **既有接口反查**: 是否已有 Controller endpoint / 已对接的第三方接口在获取该指标的同源明细数据?
      - **命中即复用**: 任一反查命中 → 标 **类型 B(接口能力复用)** 或 **类型 D(同源统计聚合)**,复用既有数据路径;**严禁新建接口 / 新建统计节点 / 默判"需第三方新提供"**。只有三向反查**全部落空**,才允许判"真新增 / 需第三方提供"。
      - **计数/求和/Top/分布类指标 = 默认类型 D**: 凡"总数 / 总量 / 计数 / 求和 / Top-N / 占比 / 分布 / 趋势"等聚合指标,**默认先定位明细数据源**(员工数 → 既有员工列表 `biz_employee`;本月消费 → 既有费用账单明细),在其上做 `COUNT / SUM / GROUP BY` 聚合,**而非新建统计表 / 统计节点 / 向第三方新要一个统计接口**。
    - **强制核验流程(每张数据表 / 每个接口 / 每个第三方调用 / 每个展示指标 都要跑):**
      0. 展示指标正向核验:对新页面 / 新区块要展示的**每个指标**,先按上「展示型新需求强制正向核验」三向反查既有页面 / 菜单 / 接口是否已展示或获取其同源数据,命中即标类型 B/D 复用,严禁默判"新增 / 需第三方新提供"
      1. 上游核验:读 PRD「五·N 复用清单」对应行,识别状态值(✅ 复用已有 / ✅ 复用已有第三方接口 / ✅ 复用已有数据-新统计 / 🆕 新增 / ❓ 待澄清)
      2. 代码核验:对 ✅ 状态条目 → 读已有出处的代码,确认真实存在 + 业务语义匹配;对 🆕 状态条目 → 主动扫描代码,确认确实无可复用;对 ❓ 状态条目 → 优先扫描代码,有发现则升级为 ✅,无发现则保留 ❓ 升级到 Module E
      3. 反向核验:对每个 ✅ 复用已有第三方接口 → 跑 `check_third_party_dep_reverse.py` 看 `reuse_signals` 输出,确认该 endpoint 在代码中确实已被多处调用
      4. 类型 D 专项核验:对每个 ✅ 复用已有数据-新统计 → 必须能在 A.3 标注"复用已有 X 表,无新建 DDL",在 B.2 标注"基于已有 Mapper 新增 GroupBy 查询方法",在 B.1 描述统计维度(部门/月份/状态等)
      5. 输出标注:在 B.1 实现映射表的「复用映射」列写明具体复用代码位置(文件 + 行号),非"无可复用"必须给出位置;在 B.7 章节生成「第三方接口复用清单」子章节
    - **决策矩阵:**
      | PRD 复用状态 | 代码核验结果 | 设计文档应标注 | 不通过标志 |
      | :- | :- | :- | :- |
      | ✅ 复用已有 | 真实存在 + 业务匹配 | ✅ 沿用 + 代码位置 | 无位置 → 不通过 |
      | ✅ 复用已有数据-新统计 | 明细表存在 + 统计语义新颖 | ✅ 复用 X 表 + 新增 GroupBy 接口 | 新建第二份明细表 → 不通过 |
      | ✅ 复用已有 | 代码中找不到 | ❌ PRD 误判 → 升级 ❓ + Module E | 强制为 🆕 → 不通过 |
      | 🆕 新增 | 代码中已有同义实现 | ⚠️ 设计冲突 → 升级 ❓ + Module E + 主动追问 | 强制 🆕 不质疑 → 不通过 |
      | ❓ 待澄清 | 代码中已有 | 升级 ✅ 沿用 + 代码位置 | 保留 ❓ → 不通过 |
      | ❓ 待澄清 | 代码中无 | 保留 ❓ + Module E + 主动追问 | 默认 🆕 → 不通过 |
    - **与已有原则的关系:**
      - 核心原则 18(代码事实采集深度)= 看"沿用接口的实现是否真实可用"(纵向穿透 Service 层)
      - 核心原则 19(第三方反向兜底识别)= 看"第三方接口在代码中是否存在调用"(反向识别)
      - 核心原则 20(复用优先)= 看"已存在的能力是否已被多处调用 / 是否已有同源数据可统计聚合,新需求是否复用"(横向聚合)
      - 三者互补:18 防"伪沿用"(标'已有'实际占位);19 防"漏报"(PRD 没提但代码有);20 防"重复对接 / 重复采集 / 同源数据被新建第二份明细表"
    - **Why**: 实测发现新页面展示"当前用户信息""部门列表""订单状态"等数据,代码中早已有 UserController.getInfo / DeptController.list / OrderEnum,但设计期默判"新增"导致前端新建一套接口、后端新建一份 Mapper/Service/Entity、第三方接口被同一 vendor 多次调用。**类型 D 漏判**更隐蔽:已有"用户列表"明细,新需求"用户角色分布统计",设计期常常默判"统计是新需求 → 新建 biz_user_role_stats 表",实际只需复用 biz_user 表 + GroupBy 查询。复用优先原则强制设计期主动扫描已有代码,避免数据/接口/对接/统计源 重复。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 27「复用识别完整性核验」+ 配套脚本 `check_third_party_dep_reverse.py --aggregate` + `check_feature_reuse.py`

21. **数据单位标注与转换全链路一致性(Critical)** — 所有数值字段必须从 PRD → 详细设计 → 接口契约 → 第三方对接全链路标注单位,后端严禁返回已转换的展示字符串(如"1.5K"/"3分钟前"/"1MB"),转换在前端完成。
    - **7 类标准存储单位(对照 PRD ux-logic-extractor 字段规格表单位列)**:
      | 类型 | 推荐存储单位 | 类型 | 主流字段后缀 | 示例 DDL |
      | :- | :- | :- | :- | :- |
      | 计数 | 个/条/次(整数) | INT/BIGINT | `_count` / `_total` / `_num` | `total_count BIGINT COMMENT '订单总数,单位:个'` |
      | 时间长度/时长 | **秒(s)**(默认) | BIGINT | `_seconds` / `_duration_s` | `valid_duration_s BIGINT COMMENT '有效时长,单位:秒'`(⚠️ 亚秒精度才用毫秒 `_ms`,详见下「时长单位铁律」) |
      | 时间戳 | Unix 毫秒戳 | BIGINT | `_at` / `_time`(ts类) | `created_at BIGINT COMMENT '创建时间,单位:毫秒时间戳'` |
      | 字节大小 | 字节(B) | BIGINT | `_bytes` / `_size_bytes` | `size_bytes BIGINT COMMENT '文件大小,单位:字节'` |
      | 百分比/比率 | 万分点 BP(整数) | INT | `_bp` / `_rate_bp` | `rate_bp INT COMMENT '完成率,单位:万分点(85%=8500)'` |
      | 长度 | 毫米(mm) | INT | `_mm` / `_length_mm` | `length_mm INT COMMENT '商品长度,单位:毫米'` |
      | 重量 | 克(g) | INT | `_g` / `_weight_g` | `weight_g INT COMMENT '商品重量,单位:克'` |
    - **后端返原始值, 前端转展示**(对照核心原则 11 货币金额整数原则,推广到所有数值字段):
      - **后端接口**: 返回"存储单位"的原始数值(如 `count=1500` 个、`size_bytes=1048576` 字节、`duration_s=180` 秒、`rate_bp=8500` 万分点)
      - **前端展示**: 负责"展示单位"转换(`1500 个` → `1.5K`、`1048576 字节` → `1MB`、`180 秒` → `3 分钟`、`8500 BP` → `85%`)
      - **严禁**: 后端返回 `"1.5K"` / `"3 分钟前"` / `"1MB"` / `"85%"` 等已转换字符串(不可比较 / 不可计算 / 国际化困难 / 单元测试复杂)
      - **例外**: 受外部协议约束的字段(如 ISO 8601 时间字符串)在 A.3 COMMENT 显式标注协议名
    - **各层标注要求**:
      - **A.3 数据表**: 所有数值字段 COMMENT 必须含"单位:..."声明(同核心原则 11 货币金额规则,扩展到全数值字段)
      - **B.2 接口契约**: 每个数值字段必须含"单位(存储/接口):" + "展示侧换算建议:"(如 `count 整数 单位:个 展示侧:>1000 时 ÷1000 加 K`)
      - **B.7 第三方对接**: 新增「单位转换映射表」子章节,列明"第三方字段+单位 → 本系统存储字段+单位 → 转换关系"(若单位不一致必须明确系数)
    - **强制核验流程(每个数值字段都要跑)**:
      1. 上游核验: 读 PRD「六、字段规格表」对应行的"存储单位 / 展示单位 / 转换关系"三列
      2. A.3 DDL 核验: 字段 COMMENT 必须含"单位:..."且与 PRD"存储单位"一致
      3. B.2 接口核验: 接口字段说明必须含"单位:..." + "展示侧换算建议:",单位与 A.3 一致
      4. B.7 第三方核验: 若涉及第三方接口,B.7 必须有「单位转换映射表」子章节,列出每个字段的转换关系
      5. 后端禁返已转换字符串核验: B.2 字段类型严禁为 String/string 但 COMMENT 含 "K/M/G/分钟前/MB/小时/万" 等展示词
      6. 运行 `check_unit_field.py <设计文档> --json` 自动化核验
    - **决策矩阵(常见单位错位场景)**:
      | PRD 存储单位 | PRD 展示单位 | 设计 A.3 COMMENT 应标注 | 设计 B.2 接口单位 | 不通过标志 |
      | :- | :- | :- | :- | :- |
      | 个 | K(>1000时) | 单位:个 | 单位:个;展示侧:>1000 ÷1000 加 K | B.2 字段类型 String 且值含"K" |
      | 字节(B) | KB/MB/GB | 单位:字节 | 单位:字节;展示侧:1024 进位 | COMMENT 写"单位:MB"(错) |
      | 秒(s) | 分钟/小时 | 单位:秒 | 单位:秒;展示侧:÷60→分,÷3600→时 | COMMENT 单位写"分钟/小时"(应为秒)/接口返回分或时 |
      | 万分点(BP) | 百分比(%) | 单位:万分点(85%=8500) | 单位:万分点;展示侧:÷100 加 % | COMMENT 写"百分比"(歧义) |
      | 克(g) | 千克(kg) | 单位:克 | 单位:克;展示侧:÷1000 | 第三方返回千克未在 B.7 标转换 |
    - **百分比歧义处理(Critical 高频错误)**: 百分比/比率字段必须明确以下三种之一,严禁仅写"百分比"或"%":
      - **万分点(BP,0-10000)**:`rate_bp INT COMMENT '完成率,单位:万分点(85%=8500)'`(推荐,避免浮点/Decimal)
      - **百分比(%,0-100)**:`rate_pct INT COMMENT '达成率,单位:百分比%(85%=85,不除100)'`(仅当上游系统/法规强制要求)
      - **小数(0-1.0)**:`rate_decimal DECIMAL(5,4) COMMENT '转化率,单位:小数(0-1.0,85%=0.85)'`(仅浮点降级场景,需 Module E 说明)
    - **时间戳字段歧义处理(Critical 高频错误)**: 时间戳字段(记录"某一时刻",区别于下条的"时长")必须明确以下三种之一:
      - **毫秒时间戳(推荐)**:`created_at BIGINT COMMENT '创建时间,单位:毫秒时间戳'`
      - **秒时间戳**:`event_at BIGINT COMMENT '事件时间,单位:秒时间戳(Unix timestamp)'`
      - **ISO 8601 字符串**:`scheduled_at VARCHAR(30) COMMENT '预约时间,单位:ISO 8601 字符串,如 2026-06-15T10:30:00Z'`
    - **时长单位铁律(Critical,时间/时长专项)**: 时长/耗时字段(有效期、超时、间隔、播放/通话时长、时限等,区别于上一条的"时间戳")——
      - **最大单位统一为秒**:存储与接口一律以**秒(s)**为基本单位;**后端接口返回一律为秒**,**严禁**后端返回分钟/小时/天等展示单位(那是前端职责)。
      - **前端自行换算**:无论前端是否需要展示"秒",凡展示分钟/小时/天,一律由**前端**从后端返回的秒值换算(÷60→分、÷3600→时、÷86400→天);后端不代劳、不返回已换算的分/时数值或字符串。
      - **毫秒仅亚秒精度例外**:仅当业务确需亚秒精度(性能计时、精确通话时长)才用**毫秒(ms)**并在 COMMENT 显式注明"单位:毫秒";其余时长默认用秒。
      - **示例**:`valid_duration_s BIGINT COMMENT '有效时长,单位:秒'`;接口返回 `{"validDurationS": 7200}`(前端 7200 → 展示"2 小时"),**禁**返回 `{"validMinutes": 120}` 或 `"2小时"`。
    - **与已有原则的关系**:
      - 核心原则 11(货币金额整数化)= 特化到货币字段的单位规则,**仍独立运行**;本原则是货币之外的全数值字段通用规则,**不冲突不重叠**
      - 核心原则 18/19/20 关注"能力是否存在 / 是否复用",本原则关注"数值单位是否明确 / 转换是否一致"
      - 本原则与核心原则 11 共享"后端返原始值,前端转展示"的架构理念
    - **Why**: 实测发现单位错位是数据展示 bug 的高频源头:① 后端返回 `count=1500` 前端误以为是"千"展示成 `1500K` ② 第三方返回千克本系统存克但忘了 ×1000 ③ 时间戳秒/毫秒混用导致"1970 年" Bug ④ 百分比 0.85 / 85 / 8500 三种表示在前后端各用一种导致显示错乱 ⑤ 后端返回字符串 `"1.5K"` 导致前端无法排序 / 无法比较 / 国际化困难 ⑥ 时长字段后端直接返回分钟/小时,导致跨时长运算(累加/比较/排序)困难、前端二次换算歧义——统一以秒为接口基本单位、前端只做展示换算可消除。PRD 阶段字段规格表三列对照 + 详细设计 A.3/B.2/B.7 全链路标注单位 + 自动化脚本扫描,确保前后端 / 系统间单位契约明确。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 28「数据单位标注与转换合规」+ 配套脚本 `check_unit_field.py`
22. **审计字段操作人溯源与自动填充铁律(Critical)** — 业务实体表的审计字段(`create_by`/`create_time`/`update_by`/`update_time`)**必须取当前登录操作人 + 当前时间**,**严禁把 `create_by`/`update_by` 写死为字符串字面量**(`"system"`/`"admin"` 等)作为通用默认值;逻辑删除是一次写操作,**必须同步更新** `update_by`/`update_time`。
    - **适用范围(业务实体表)**: 有增删改的业务主表**必须**带审计四件套 + 逻辑删除标记(`is_deleted`/`deleted`/`del_flag`,命名沿用历史,见核心原则 12);纯字典/枚举/关联中间/日志流水/快照表可豁免审计人字段,豁免须在 A.3 表说明中标注理由。
    - **填充机制显式化(设计必须写明)**: A.3 数据表设计或 A.2 持久层设计**必须显式声明审计字段的填充机制 + 操作人来源**,不得留空让下游各自实现。优先**框架级自动填充**:Java/MyBatis-Plus → `MetaObjectHandler`(`insertFill` 填四件套、`updateFill` 填 `update_by`/`update_time`),Spring Data JPA → `@CreatedBy`/`@LastModifiedBy`/`@CreatedDate`/`@LastModifiedDate` + `AuditorAware`;操作人从**当前登录态**取得(`SecurityContext` / SSO / 网关透传的用户上下文 / 登录态 `ThreadLocal`),而非硬编码。设计须写明"操作人来源 = 当前登录用户如何取得"。
    - **逻辑删除同步修改人(高频坑)**: 逻辑删除本质是 `UPDATE ... SET is_deleted=1`,**必须同时** `SET update_by=当前操作人, update_time=当前时间`。**特别提示**:逻辑删除常走**自定义 SQL / Mapper 直接 UPDATE / `@TableLogic` 默认删除**,会**绕过** ORM 的 `updateFill` 自动填充 → 必须在删除逻辑里**显式补写** `update_by`/`update_time`,或确认拦截器/`MetaObjectHandler` 能覆盖逻辑删除路径。设计的删除接口/时序说明须显式交代这一步。
    - **"system" 兜底显式化**: 仅**定时任务 / 数据初始化 / 系统内部无登录态**场景可用固定系统账号(如 `system` / 系统用户 ID),且**必须在设计对应位置显式标注**该场景与取值来源;**不得**把 `system` 当作所有写操作的静默默认值。
    - **Why**: 下游实测踩坑——审计人字段被写死成字符串 `"system"`,导致所有数据的创建人/修改人都是 `system`、无法追溯真实操作人;逻辑删除只改了 `is_deleted` 却漏更新 `update_by`/`update_time`,删除操作无人可查。审计字段的价值在于**可溯源**,写死即失效。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 30「审计字段操作人溯源与逻辑删除同步」+ 配套脚本 `check_audit_field_fill.py`;下游代码验收由 `code-verification-loop` 维度 4「审计字段填充溯源」+ `scan_code_conventions.py --checks audit-fill` 拦截写死 `"system"` 与逻辑删除漏更新修改人。
    - **同源身份的另一处强约束 · 用户自我保护铁律(Critical,仅系统含用户管理时)**: 与审计填充同以**当前登录操作人身份**(JWT `sub` / 会话,**不接受前端传入的"当前用户 id"**)为基准。若系统含用户管理(用户 CRUD / 启停 / 角色权限分配),设计必须约束**登录用户不得对"自己"执行破坏性 / 自我降权操作**,且由**后端接口强校验**(前端按钮置灰仅辅助、不可替代后端):① **删除自己**的账号;② **禁用 / 锁定 / 冻结自己**(使自己无法再登录);③ **撤销 / 降级自己赖以管理的角色或权限**(尤其自己是最后一个管理员时,防止系统失去管理入口)。判定 = 目标用户 id == 操作人 `sub` → 拒绝并返回明确业务错误(如"不能删除 / 禁用当前登录用户自己")。质量检查见检查项 1「业务逻辑一致性核验」权限与自我保护子项;下游代码验收由 `code-verification-loop` 维度 4「用户自我保护校验」拦截。

23. **错误契约铁律(Critical)** — **每个接口都必须在接口设计里产出「错误契约」小节**,把"失败长什么样"在设计期定死,不留到编码期各写各的。核心命题:**失败必须以错误表达**。
    - **23.1 成功 / 空结果 / 失败三态判然区分(强制产出)**: 每个接口的错误契约小节必须写明三态边界——**成功** = 业务成功 + 业务数据;**空结果** = `code=0` + `data.list=[]`,**是合法成功、不是失败**;**失败** = 业务错误码 + **面向用户的中文 message**。**严禁**用 `HTTP 200 + 空 data`、`{success:true, data:[]}`、`{code:0, data:null}` 表达失败——前端会把它渲染成空态,故障对用户与监控**双双静默**。部分失败须显式 `partial=true` + 失败明细(与核心原则 16 第 4 子项同源:系统故障导致的"无数据"必须能与"业务真空"区分)。
    - **23.2 依赖 / 上游调用的失败契约(强制产出)**: 接口凡调用上游服务 / 第三方 / 中间件,错误契约必须有**上游不可达行**(超时 / 连接失败 / 5xx / 响应不可解析),文案格式固定为「**{上游中文名}服务无法连接,请稍后再试**」。服务名**必须用业务中文名**(如"订单中心""支付中心"),**严禁**内部代号 / 服务名 / IP / URL(❌ `order-svc 连接失败` — 用户看不懂,还泄漏内部拓扑)。**确需降级**(如字典类回退默认值)必须**就地注明降级理由 + 降级范围 + 用户是否可感知**,不写 = 违反不臆造兜底原则。
    - **23.3 安全判据默认 fail-closed(强制声明)**: 鉴权 / 权限 / 数据归属 / 签名校验类判断,设计必须声明「**取不到 / 解析失败 / 查询异常 → 拒绝或报错**」。**严禁 fail-open**——把"取不到"当"无限制"放行(❌ 租户 ID 取不到就不加过滤条件返全量 / ❌ `catch` 后 `return true` / ❌ 角色列表为空视为管理员)。前端按钮置灰只是辅助,**判据必须在后端**。
    - **23.4 上游契约权威(强制标注)**: 详细设计引用外部 / 上游接口契约时,必须注明「**以上游契约为准,上游变更即需跟进**」+ 契约来源与采集时间,防设计滞留旧契约(与核心原则 18 字段级契约核对互补:那条查"抓到的真实出参与设计是否一致",本条防"抓过之后上游又改了")。
    - **23.5 错误码必须全局统一枚举(Critical,禁各接口自编码)**: 全部错误码**只有一个信源**——A.4 的「**GlobalErrorCode 全局错误码**」枚举条目;接口错误契约表里的每一个错误码**必须能在该枚举中逐条对应上**,**严禁**接口自编码、就地新造。
      - **落位**: 作 A.4 字典与枚举的固定条目,与其它枚举同规格——按核心原则 10 在 A.3/B.2 引用它,按检查项 11 强制生成**枚举类**(如后端 `ErrorCodeEnum`、前端同名常量),受既有枚举机制全套约束(code/label 前后端对齐、ORM/序列化映射)。**不另起炉灶、不新造一套机制。**
      - **枚举表列**: `| 错误码 | label | HTTP Status | 业务含义 | 归属域 |`。**分段规范**须显式写明(如 `4xxxx` 客户端类 / `5xxxx` 服务端与上游类,再按业务域二级分段),新增错误码按段申请、全局唯一。
      - **接口侧对应关系**: 接口错误契约表的「错误码」「HTTP Status」必须与全局枚举**逐字一致**;接口只做**选用 + 写清本接口的触发条件 / 用户提示 / 失败降级行为**,不改码值与语义。
      - **新增错误码的去处**: 本次需求确需新错误码 → **先加进全局枚举**(含 label / HTTP Status / 业务含义 / 归属域),再在接口引用;不得只写在某个接口表里。

    - **产出物形态(硬性)**: 固定 5 列表,每个接口必填、不留空——`| 错误码 | HTTP Status | 触发条件 | 面向用户的中文提示 | 失败/降级行为 |`,且**每个错误码都出自 A.4 全局错误码枚举**。模板见 `assets/api-template.md`,B.2 落位见 `references/output-module-examples.md` > B.2。**旧版「错误码 | HTTP Status | 说明」三列表已作废。**
    - **与既有原则的边界(勿重复、勿互相替代)**:
      - 核心原则 16 第 4 子项 = 我方**作为调用方**,怎么判下游失败(客户端侧失败返回风格统一);
      - **本原则 = 我方作为被调用方**,怎么向前端 / 调用方**表达**失败(服务端侧错误契约)。二者是同一枚硬币的两面,方向相反、都要有。

24. **并发加锁选型优先级铁律(Critical)** — 凡设计涉及并发临界区(库存扣减 / 余额变更 / 号段发放 / 重复提交 / 状态机并发流转 / 定时任务多实例抢占),**必须按下列优先级选型,并在设计中写明"为什么是这一档"**。
    - **P0 进程内锁(语言自带,首选)** — 竞争只发生在**单进程内**时,一律用语言自带的锁关键字/类型(Java `synchronized` / `ReentrantLock`,Go `sync.Mutex`,Python `threading.Lock` / `asyncio.Lock`,C# `lock` / `SemaphoreSlim` 等)。**零外部依赖、无网络往返、无死锁残留风险**,是成本最低的一档。**各栈具体写法见 `references/stack-<栈>.md` 的「核心原则 24 落地」节**(本文件只写跨栈判据)。
    - **P1 Redis 分布式锁(其次)** — **仅当 P0 不够**时才升到这一档,且必须在设计里写明 P0 不够的**具体理由**(多实例 / 多副本部署、跨进程或跨服务竞争、水平扩容后单机锁失效)。**必须带自动过期(Critical)**:
      - 加锁必须原子(`SET key val NX PX <ttl>` / Redisson `RLock`),**严禁**"先 `SETNX` 再 `EXPIRE`"两步(中间崩溃即永久死锁);
      - 必须声明 **TTL / leaseTime**,并说明**长任务如何续期**(看门狗 / watchdog,或把临界区拆短);
      - **释放必须校验持有者**(Lua 脚本比对 owner 后删),防误删他人的锁;
      - 必须写明**获取失败的行为**(快速失败返错误码 / 有限重试 + 退避 / 排队),并与核心原则 23 的错误契约对应上;
      - ⚠️ **引入 Redis 依赖本身仍须过核心原则 17 的用户确认门**——本原则只定"锁该选哪档",不豁免"能不能引入 Redis"。
    - **P2 数据库级锁(谨慎谨慎再谨慎,必须人为确认)** — `SELECT ... FOR UPDATE` / `FOR SHARE` / `LOCK IN SHARE MODE` / `LOCK TABLES` / `GET_LOCK()` / `pg_advisory_lock()` / 悲观锁 / 行锁 / 表锁。**默认不可用**;**必须向用户显式说明并取得确认后方可写进设计**(确认门与核心原则 17 缓存机制同款:正文『用户已确认』标注 / 专章『数据库级锁方案(用户已确认 YYYY-MM-DD)』 / Module E `D-NNN` 条目,三者至少其一)。确认时须一并说明:锁定范围(行/间隙/表)、持锁时长与事务边界、对 QPS 与连接池的影响、超时与死锁处理、为何 P0/P1 都不适用。
    - **⚠️ 乐观锁不是锁,不受本原则约束**: `version` 字段 + CAS 重试、唯一索引幂等、幂等键,都是**无锁并发控制**,**仍是推荐做法**,不算 P2、不需要确认门。核对时别把它们误当数据库级锁——这是本原则最容易被误用的一处。
    - **必须写在哪**: B.3「异常处理与容错机制」的**并发冲突**行须落到具体档位 + 理由;涉及的接口在 B.2 错误契约中给出"获取锁失败"对应的错误码(取自 A.4 全局错误码枚举)。
    - **Why**: ① 一上来就用分布式锁,给单机就能解决的问题引入 Redis 依赖、网络往返与死锁风险,复杂度与故障面双升 ② 分布式锁**不带自动过期**是线上事故高发点——持锁进程崩溃后锁永不释放,整条业务线卡死且无自愈 ③ 数据库级锁把并发压力压到 DB 连接与行锁上,极易连锁放大成全站雪崩(锁等待 → 连接池耗尽 → 所有接口超时),且问题通常在压测或大促才暴露,故必须由人显式拍板、不许设计 Agent 自行决定。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 32「并发加锁选型与数据库级锁确认」+ 配套脚本 `check_lock_strategy.py`。

      | **脱敏** | 与上面同时落地——补日志而不脱敏,等于**放大**了泄漏面 |
    - **强制产出「上游调用日志与脱敏声明表」(固定 6 列,一个上游调用一行)**:
      `| 上游中文名 | 完整 URL(含环境变量占位) | 请求段必打字段 | 响应段必打字段 | 脱敏字段清单 | 二进制/大对象降级说明 |`
      - **「上游中文名」必填**:面向用户的错误文案要求**中文服务名**(与核心原则 23 的 23.2 同一条口径),**不得**写 `ops-service` 这类内部代号。
      - **「脱敏字段清单」允许写「无」,但不允许留空**——留空无法区分"确认过没有敏感字段"与"根本没考虑";「二进制/大对象降级说明」同理(不涉及就写「无」)。
      - **URL 写含环境变量占位的形态**(如 `https://${SMS_HOST}/v2/send`),与核心原则 16「严禁硬编码 base URL」一致;不是让你把真实域名抄进设计。
    - **落位**: B.7「外部依赖与集成方案」**整节产出一张表、一个出站调用一行**,放在「交付状态说明」之后、「集成示例」之前(与 `references/output-module-examples.md` 的模板一致);多册拆分时随 B.7 所在册走。⚠️ **不要写成「每个集成项各挂一张单行表」**——两种形态硬门都能过(每张表独立校验),不会替你发现不一致,只会长期产出两种版式、让下游对账时形态不统一。
    - **与既有原则的边界(勿重复登记)**:
      - **核心原则 16(HTTP 客户端铁律)** 管这次调用**怎么发**(客户端选型 / 配置驱动 / 失败返回契约);**本条管这次调用留下什么痕迹**。
      - **核心原则 23(错误契约)** 管我方**作为被调用方**怎么向前端表达失败;本条管我方**作为调用方**把出站调用记录下来。三条各管一段,同一处问题只登记一次。
    - **Why**: 下游实测——同一项目 **4 个上游客户端写出 4 种日志规格,另有 2 个直接漏掉**。根因不是编码时忘了,而是**详细设计从来没写过**这一段;而出站调用恰恰是最需要事后追溯的一环(对方说没收到、对方返回了什么 code、慢在哪一跳),没有成对的请求/响应日志就只能靠猜。另一条同样重要:**成功路径也必须打** —— 只在失败时打日志,等于只有出事才出声,既无法定位"对方成功返回了但内容不对"这类问题,也拿不到耗时基线。
    - **⚠️ 去重边界(硬约束)**: 运行时五条判据(出站调用类零日志 / 成功路径不可见 / 无一条日志提到 URL / 成功路径只有 debug / 疑似凭据明文入日志)由**被测项目侧**的 `check_upstream_call_log.py` 承担(经脚手架下发,不在任何 SKILL 内)。**本 SKILL 只承接设计期声明这一段,严禁重写那五条**——同一判据两份实现是最高频漂移源。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 35「上游调用日志与脱敏声明完整性」+ 配套脚本 `check_upstream_call_log_spec.py`(**缺表判 Important**——存量设计会大面积命中,一上来判死会让整个硬门被无视;**表在而缺列 / 格子空判 Critical**——那是新产物自身的缺陷)。
      - ⚠️ **U1 缺表不体现在退出码上** —— 它判 Important,只出现在 `--json` 的 `importants[]` 里;**只按 `$?` 判的调用方会把「整张表都没有」读成「通过」**。调用本脚本必须读 `--json`,⛔ 别只看退出码。

28. **业务计数声明表(Critical)** — 凡设计里出现**会被复述到别处的业务计数**(「支持 N 种告警类型」「最多 N 个应用」「共 N 个模块」「在售 N 款商品」),必须强制产出一张「业务计数声明表」,把「同一个数字被复述到多少处、哪一处才算数」定死在设计期。
    - **与核心原则 25 的分工(同级、互不替代)**: 25「统计指标口径五要素」管**一个数字怎么算出来**(单位 / 小数精度 / 时间窗 / 统计范围 / 取数粒度);本条管**这个数字被复述到多少处、哪一处才算数**。二者对象不同,同一处问题只登记一次。
    - **⚠️ 这类声明特有的失效方式:它不会报错,只会慢慢变成假话。** 「支持 8 种告警类型」写进帮助文案、README、接口注释、培训材料;某次迭代加到第 9 种,枚举类改了、页面自动跟着变了,**那四处文案一个都不会变**,也没有任何测试会失败。它不是写错,是**过期**——而过期没有任何自动信号。
    - **强制产出「业务计数声明表」(固定 5 列,一个声明一行)**:
      `| 声明名 | 当前值 | 是否动态 | 权威出处 | 散落面正则 |`
      - **「是否动态」只能填「动态」/「静态」**——这一格决定散落面里**能不能出现字面数字**:动态值一旦被写进文案就必然过期,只能由权威出处实时取;静态值才允许写死。
      - **「权威出处」须是可执行的单一信源**(枚举类 / 字典表 / 配置项 / 接口)。写「见 PRD 第 3 节」**不算**——那不是能被回扫的东西,人读得懂、脚本回不去。
      - **「散落面正则」须在登记时实跑过并记下命中数**。下游实测:该式子曾**误命中 javadoc 交叉引用**,不实跑发现不了——登记一个从没跑过的正则,等于登记了一个恒不命中的守护面,而它会**长期以全绿的形态存在**。
    - **⚠️⚠️ 正则里的 `|` 必须转义为 `\|`** —— GFM 里 `|` 是列分隔符,**反引号代码段保护不了它**;不转义会把该行切成 6 格、整张表当场散架。这是本表**实测第一次就会踩到**的坑,写表时先看这条。
    - **落位**: 与「统计指标口径表」同章节体系,随其所在册走。**允许多册各有一张、增量产物另起一张**——多册拆分是本 SKILL 在 M/L 档的强制行为,而增量按 `SKILL.md` >「增量 / 补充生成约定」第 2 条必落新的 `NN_<业务主题>.md`、**不改主文档正文**,所以「同名声明出现在第二张表」在正常工作流里几乎必然发生。⚠️ **不要写成「全设计只准一张表」**:那条规则会让「引入了新业务计数的增量」无路可走——另起表违反它、改主文档正文违反增量契约,二者必居其一。
      - **真正不可退让的是「权威出处唯一」,不是「表唯一」**: 同一个「声明名」无论出现在几张表 / 几册,**当前值与权威出处必须逐字一致**;要改就一起改。这与核心原则 25「统计指标口径表」的第 8 列「权威取数口径」是同一条纪律,**两条原则的多册处置也因此保持一致**(25 从来没要求过「全设计一张表」)。

29. **渲染层归并声明表(Critical)** — 凡设计里出现**列表 / 卡片 / 统计数**这类"多条上游记录汇成若干个页面条目"的位点,必须**强制产出一张「渲染层归并声明表」**,把「上游集合 → 页面条目」这一层转换写死在设计期。
    - **⚠️ 与核心原则 25 的边界(两者不同层,⛔ 勿合并)**: 25 第 8 列「权威取数口径」管的是**同一指标别在 N 处各算一遍**;本条管的是**上游记录数 ≠ 页面条目数**这一层转换。下游两例失效里**取数口径本身完全正确**,错的是判据写在上游集合上、而渲染表达式写在归并后的集合上,两边各写各的——这一层在设计里**根本没有落点**,于是永远对不上。
    - **两条真实失效(同一项目,本类单类发作 3 次,是该轮最高频)**:
      | # | 现象 | 根因 |
      | :- | :- | :- |
      | ① | 去重"功能没生效",不报任何错 | 去重判据取的是「订单台账」,而页面展示集合是「台账 ∪ 平台预约单」——**预约单那一整类从未进入去重** |
      | ② | 4 人订阅显示 4,页面只有 1 张卡 | 头部统计数取「上游订阅记录数」,而页面按 `skuId` 归并成卡片——**统计数与页面条目不是同一个集合** |
    - **强制产出「渲染层归并声明表」(固定 5 列,每个列表 / 卡片 / 统计数位点一行)**:
      `| 列表位点 | 数据来源 | 渲染层是否归并/过滤 | 上游记录数 == 页面条目数? | 该位点的计数与判据表达式 |`
      - **「数据来源」多来源必须全列**,写成 `A ∪ B` 的形态(如「订单台账 ∪ 平台预约单」)。只写主来源 = 本表最核心的失效形态①原样复现。
      - **「渲染层是否归并/过滤」** 填**归并键**(如 `按 skuId 归并`)或**过滤条件**;确实一条不并、一条不滤才填「无」。
      - **「上游记录数 == 页面条目数?」** 只能填「是」/「否」。这一格是给下游看的:填「否」意味着**任何以上游记录数表达的计数都是错的**。
      - **「该位点的计数与判据表达式」** 写实际用到的函数名或变量组(如 `mergedCards.length` / `dedupBy(skuId)`),让「判据挂在哪一层」变成**可核对的**而不是靠读代码猜。
    - **硬门判据(三条,均 Critical)**:
      1. **多来源覆盖** —— 「数据来源」含 `∪` / `+` / 顿号等多来源形态时,第 5 列的表达式必须**覆盖全部来源**;只取其中一个子集判 Critical(失效①的形态)。
      2. **归并后禁引上游记录数** —— 第 4 列填「否」时,第 5 列**不得引用上游记录数**(`xxxList.length` / `records.size()` / `total` 这类上游侧计数)判 Critical(失效②的形态)。
      3. **逐格填实、不留空不占位** —— 与核心原则 25 / 28 同款(`待定` / `TBD` / `—` / `{...}` 一律判不通过)。
    - **落位**: 与「统计指标口径表」同章节体系(`references/output-module-examples.md` 的 B.2.y 之后),随其所在册走。**允许多册各有一张、增量产物另起一张**——理由与核心原则 28 完全相同(多册拆分是 M/L 档强制行为、增量必落新 `NN_` 文件不改主文档正文),⛔ 不得写成「全设计一张表」。
    - **跨产物契约**: 下游 `dev-manual-testcase` 第五步之九「含数字的页」以本表为基准,**凡第 4 列「上游记录数 == 页面条目数?」填「否」的位点逐个**生成「两位点数值自洽」用例(卡片值 == 明细各行之和)。⚠️ **别写成「逐位点」**——第 4 列填「是」的行(如上例的「成员明细列表」)不存在两位点算术不自洽的可能,把它也算进应有用例数,会让下游 `dev-manual-testcase` 明明合规却被判覆盖不足。**本表是跨产物契约,不是本 SKILL 自用的表。**

30. **结论型断言必须附证据来源(Critical)** — 设计正文与 **Module E 待澄清问题清单**里出现「上游不支持 / 没有出口 / 结构性不可得 / 某规则禁止如此 / 做不到」这类**结论型断言**时,必须**同处写明证据**:接口文档原文位置、上游源码位置、或**实测记录(含日期)**。拿不出证据的,一律就地标注为「**未验证假设**」,且**禁止在后续轮次被引用为既定事实**。
    - **与核心原则 18 的关系(同族、不同侧,⛔ 勿合并)**: 18「代码事实采集深度铁律」管的是「**Controller 存在 ≠ 能力可用**」——别把看到的当成能用的;本条管的是「**我说没有 ≠ 真的没有**」——别把没找到的当成不存在。两条一正一反,合起来才闭环。
    - **真实代价(下游 11 轮返工的主线之一)**: 「上游没有按员工维度的出口」——**事实是该端点早就有可选入参**,只是本侧从未封装带该参数的重载。这句话一旦进了文档,就被后续**每一轮**当既定事实引用,衍生出一整套「只能显示占位值」的错误设计,还配了一份"产品知情决策"的论证。**一句没有证据的结论,比一个明写的待澄清项危险得多**——待澄清项会被追问,结论不会。
    - **证据形态(三选一,写不出就是「未验证假设」)**:
      | 形态 | 最低要求 |
      | :- | :- |
      | **接口文档** | 文档名 + 章节/锚点 + 那句原文(不是"见接口文档") |
      | **上游源码** | 仓库/路径 + 符号名(类名·方法名);**看的是哪个分支/版本也要写** |
      | **实测记录** | 请求形态 + 实际返回 + **日期**;没有日期的实测等于没做 |
    - **⚠️ 「未验证假设」不是不合格标记,是隔离标记。** 允许带着它推进设计(与核心原则「不阻塞下游」一致),但它**不得升级为既定事实**:后续轮次引用它时必须原样带着这个标记,要去掉只有一条路——补上证据。
    - **与上游 `ux-logic-extractor` 口径一致**: 同一句断言常常从 PRD 待澄清清单(Q-NNN 的 🔧 暂行方案)一路传到详细设计,**两侧必须同款要求**,否则在交界处证据就丢了。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 38。⚠️ **本条刻意不配硬门脚本**——「上游不支持 / 禁止 / 不可得」这些词在规范类正文里必然大量出现(本文件自己就有几十处),按关键词扫必满屏假红,与本仓库「新判据宁可窄到只覆盖一种明确形态」相悖;判据落在 QR 子 Agent 的语义核对上。

31. **禁令条目必须同时写反向边界(Important)** — 本 SKILL 各核心原则里的「严禁 X」条目、以及设计产出的 **ADR / 架构禁令**,必须同时写明【**禁止的对象**】与【**不在禁止范围内的相似形态**】。只写"禁止 X"、不写反向边界的条目判 Important。
    - **真实代价**: 一条架构决策禁止的是「**逐明细数 ÷ 聚合总量**」这种**分母错位**的占比展示(分子分母口径不同,比值无意义)。它被泛化成"不许画进度条",于是砍掉了「**逐明细数 ÷ 该明细自己的额度**」这个**分子分母同属一个主体、完全合规**的展示——直到使用者追问「怎么只有一个统计项」才补回来。**禁令的杀伤半径天然大于它的本意**,反向边界就是给它划的止损线。
    - **写法(两句话即可,不必长)**: `⛔ 禁止:<对象,写清楚为什么这个形态是错的>` + `✅ 不在禁止范围:<最容易被误伤的那个相似形态>`。**反向边界要挑"最容易被误伤的那一个"来写**,写一个泛泛的"其它情况另议"等于没写。
    - **附:聚合层级判定(同源规则,折入本条)** —— **聚合体上的 id 是聚合键,不是业务标识**;**聚合层成立的裁剪结论不得照搬明细层,反之亦然**;判断「某字段属于哪一层」必须看**数据实际挂在哪一层**,不靠直觉。
      > 真实失效:「聚合卡片只展示总量」是对的(多条明细不可加总),但把这个裁剪照搬到**逐明细的弹窗**就是错的——两者聚合层级根本不同。这与本条是同一个病:**一个在特定层级成立的结论被搬到了另一个层级**。
    - **与核心原则 20(复用识别)的边界**: 20 管「已有的东西要不要复用」,本条管「已下的禁令覆盖多大范围」,不重复登记。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 38(与核心原则 30 共用一个检查项:两者都是「文档里一句写死的话被后续当既定事实」这同一类失效的两种形态——30 是**没有证据的结论**,31 是**没有边界的禁令**)。

32. **新增列的消费者举证 + 重复性对账(Critical)** — 凡本次设计**给既有表新增列**(`ALTER TABLE ... ADD`),必须**强制产出 6 列「新增列举证表」**(`列名 | 类型 | 业务含义 | 谁读它(具体到界面/判据/接口出参) | 不加会怎样 | 与既有近似列的区别`),每个新增列各一行、逐格填实。**★ 判据一句话:建表的判据是「谁会读它」,不是「上游有什么」。**
    - **真实事故(实际项目中)**: 需求写「某列表改为查本应用自己的库表,缺字段可以加上」,执行体照着上游那个 21 字段的 VO 形状一次性加了 10 列。逐条验证后:本应用源码的映射函数只映射 13 个字段,新加的 10 列里 **8 列零消费**;其中一列是**证件号码**——留存一份用不上的敏感个人信息,是**凭空增加的合规负担**;另有一列与既有列是**同一个事实的两份副本**;10 列**全部无注释**(数据字典实查 10/10 无)。最终收敛为 2 列,**80% 的列是纯粹的浪费**。
    - **⚠️ 根因不是判断失误,是缺门**: 「缺字段可以加上」在没有硬门时被解读成「把上游 VO 的字段补齐」——这是极其自然、且几乎必然发生的误读:**上游 VO 就摆在眼前,而「谁会读它」需要主动去下游仓库翻源码。阻力最小的路径是错的那条。**
    - **判据(逐条 Critical)**:
      1. ⛔ **第 4 列写不出具体读取方 → 该列不得进入 DDL**。「以后可能要用」「上游有这个字段」「保持与上游一致」「先存着」「备用」「预留」一律不算。
      2. ⛔ **第 5 列答「没什么影响」→ 同样不得进入 DDL**。
      3. ★ **举证指向外部仓库的消费者时,必须附「该仓库的文件路径 + 映射函数名」**,不接受「我认为它会用」——那次事故里,**只要真的去读一眼那个映射函数,10 列会当场变成 2 列**。
      4. **重复性对账**: 新增列进入 DDL 前,对**同库全部已有列**(项目的数据库基线文档 + 本版 DDL)做一次**名称近似 + 含义近似**检索;判定重复 → 不加、复用既有列;判定不重复 → **必须在列注释里写明与那个近似列的区别**(只写在设计文档里不算)。
      5. **每个 `ADD COLUMN` 必须有配对的列注释**,内容 = 业务含义 + 取值域(枚举必须列全)+ 与近似列的区别(若第 4 条命中)。**两种方言形态都算配对**:MySQL 的内联 `COMMENT '...'`,与达梦 / Oracle 的独立 `COMMENT ON COLUMN t.c IS '...'`。
      6. 第 6 列**允许写「无近似列」、不允许留空**——留空无法区分「确认过没有」与「根本没考虑」(与核心原则 27「脱敏字段清单」同款取舍)。
    - **⚠️ 方言(会静默失效的那一处)**: 硬门必须**同时认** `ADD COLUMN` 与达梦 / Oracle 的 `ADD (COL TYPE)`,只认前者会在国产库项目上静默失效(达梦等国产库即此形态,且达梦**根本不支持**在 ALTER 里内联 COMMENT、必须另起 `COMMENT ON COLUMN`)。
    - **多存字段的三重成本(为什么这条是 Critical)**: ① 让人分不清哪个是权威源(`ADMIN_STATUS` 与既有 `T_PLATFORM_USER.STATUS` 是同一个事实的两份副本);② 与上游漂移后**无声出错**;③ 若含个人信息,是**实打实的合规负担**。
    - **重复性对账的真实样本**: `ADMIN_USER_ID` vs 既有 `SUPER_ADMIN_USER_ID` —— 两者**确实不同**(当前管理员 vs 首任创建人快照),但差别当时没写进任何注释,所以复核方的怀疑完全合理:**下一个人、以及下一次的 AI,必然重新怀疑一遍**。这正是判据 4「不重复也要写进注释」的全部理由。
    - **与既有维度的边界(⛔ 勿合并)**: 与**核心原则 20(复用优先与去重)** 不同层——20 管「**能力/接口**要不要复用」,本条管「**这一列**该不该存在」;与**检查项 29(字段实现清单)** 方向相反——那张表查**上游出处**(需求字段有没有落地),本表查**下游消费者**(这一列有没有人读),两者是同一个模式的两个方向、并存互补。
    - **落位**: A.3 数据定义,紧跟 DDL(`references/output-module-examples.md` > 「4b. 给既有表新增列」)。**允许多册各有一张、增量产物另起一张**,理由与核心原则 28 / 29 完全相同。
    - **★ 去重边界**: 「DDL 执行完之后回库实查列注释真的写进去了没有」由**被测项目侧**的 SQL 执行台账 / 发布基线核查承担,⛔ **本 SKILL 只管设计期这一段、不重写那一半**——那次事故里**脚本是对的、执行漏了**(只跑了 ADD 那段循环,注释语句整段没跑),静态门只是**必要条件、不充分**。
    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 39 + 配套脚本 `check_column_consumer_evidence.py`(举证表 6 列 + 逐格填实 + 与 DDL 双向对账)与 `check_ddl_column_comment.py`(每个 `ADD COLUMN` 有无配对注释)。⚠️ 两个脚本**都须传目录**(举证表与 DDL、`COMMENT ON COLUMN` 与 `ALTER` 常分册);⚠️ **缺表刻意判 Important 不判 Critical**——存量设计会大面积命中,一上来判死会让整个硬门被无视(同核心原则 27 的 U1 取舍),表**一旦产出**,缺列 / 格子空 / 举不出消费者 / DDL 加了列却没登记才判 Critical。

33. **权限与可见范围约束必须有落点(Critical)** — 研发需求里出现的**权限 / 可见范围类约束**,
    必须在详细设计里**逐条有可指认的落点**,并**强制产出 4 列「权限与可见范围约束落点表」**。

    - **判据只判「有无」,不判「对不对」**: 「这个权限设计得合不合理」要连业务才知道,那是人的活;
      但「需求写了、设计一个字没提」是确定性可判的。⛔ **不要在本原则下评判权限模型的合理性**。

    - **Why(为什么既有的一条都命不中)**: 这类约束的特征是**加在既有字段/页面上的限定,
      不新增任何实体**——「该列表仅本部门可见」「只有管理员能导出」「按角色过滤数据范围」。
      而规划期既有的基准全是「元素/字段存不存在」:
      **检查项 3** 挂在**原型元素**上(「编辑按钮置灰,条件是什么」)——而**加了部门过滤的列表
      和没加的在原型上长得一模一样**,原型驱动的检查天生看不见它;
      **检查项 29** 查**需求字段**有没有落地——约束不是字段;
      **检查项 39** 查**新增的列**——本类约束通常一列都不加;
      **核心原则 23.4 / 检查项 31** 管**取不到值时怎么办**——不管**约束本身有没有落地**。
      于是:需求写了、详细设计整条不落地,而规划期审计**照样报 ✅ 通过**。
      ⚠️ 这与 **ux 维度 14「语义/口径变更类需求」是同一种失效形态**——
      「代码改行为、页面零新增元素」,靠「新增/删除实体」驱动的覆盖一律够不着。
      **权限缺失是安全面缺陷:漏了不会白屏、不会报错,只会让不该看见的人看见。**

    - **表结构(4 列,每条约束各一行)**:
      `约束原文(引 PRD 位置) | 约束类型 | 约束主体来源 | 落点(可指认)`
      - **第 1 列**须**引 PRD 位置**(章节号/行号)**且带原文摘要**——与核心原则 30 同款。
        只写编号时,编号一位移两侧都仍「在范围内」,任何范围检查都发现不了。
      - **第 2 列「约束类型」只有四档**: `数据行过滤` / `字段脱敏` / `操作准入` / `页面可见性`。
        ⚠️ 四档按**落点该在哪一层**划分,不是业务分类: 数据行过滤→服务层/SQL where、
        字段脱敏→出参组装、操作准入→接口层鉴权、页面可见性→前后端双侧。
        **填错档 = 落点多半也挂错层。**
      - **⚠️ 第 3 列「约束主体来源」是最容易被忽略、却最致命的一列**:
        「本部门」的部门 ID 从哪来——登录态 / token / 会话,还是**请求参数**?
        **若取自请求参数,等于「客户端自称是哪个部门就是哪个部门」,过滤代码写得再对
        也等于没有。** 这一条**不需要懂业务**即可判定,故做成硬门 G5(Critical)。
        确需前端传(如管理员跨部门查询)须就地写明「服务端以登录态为准 / 服务端校验归属」。
      - **第 4 列「落点」须可指认**: 具体到接口 / 服务方法 / SQL 条件 / 前端组件。
        「由权限框架自动处理」「按业务」「见上」一律不算——**不可核对等于没写**。

    - **⚠️ 与核心原则 22「同源身份」的关系(必读,⛔ 勿合并也⛔ 勿各写各的)**: 核心原则 22 已立「**当前登录操作人身份**(JWT `sub` / 会话,**不接受前端传入的"当前用户 id"**)」这条底层判据,并已用在**两个对象**上——审计字段填充(`create_by`/`update_by` 写谁)与用户自我保护铁律(能不能删/禁用"自己")。**本条 G5 是同一条底层判据的第三处应用,对象换成了「权限主体」**:审计填充问的是「**谁在写**」,本条问的是「**谁在看**」(数据范围过滤按谁的部门/角色收窄)。⚠️ **三处对象不同、不可互相替代**:一个系统完全可能审计字段填得很规范(22 通过),而列表过滤的 deptId 却取自请求参数(G5 不通过)——**两者在代码里是两处完全不同的取值点**。故:**判据同源、登记分处**,⛔ 不要因为"22 已经说过身份不能前端传"就跳过本表第 3 列。

    - **⚠️ 刻意不设第 5 列「取不到主体时的行为」**: 那是**核心原则 23.4 的 fail-closed**(鉴权/权限/归属/签名取不到 → 拒绝或报错,禁把"取不到"当"无限制")。
      <!-- ⛔ 上面这句**必须保持单行**:`check_error_contract.py` 的 C6/C7 反模式扫描配的是
           **逐行**禁令语境护栏,把「fail-closed」与它保护的那句折成两行,第二行就只剩
           「取不到 → 拒绝或报错」、不含任何护栏词 → 当场被判 C7「安全判据 fail-open」。
           实测:折行时本文件与 quality-review-checklist.md 各假红一条。 -->
      同一条纪律**只登记一处**,⛔ 不在本表再要一遍——同判据两份实现是本仓库最高频漂移源。

    - **硬门**: `check_permission_constraint.py`
      (G1 缺列 / G2 逐格空或占位 / G3 数据行格数不符 / G4 类型不在四档 /
      G5 主体来源取自客户端 / G6 落点不可指认 / P0 上游有约束但未登记 = **Critical**;
      W1 缺表 / W2 登记了上游找不到的约束 = **Important 不占退出码**)。
      - ⚠️ **`--requirements` 是可选参数,不是必填**: 全仓 31 个姊妹脚本一律单入参,
        QR 步骤 0 的 bash 块也传不了 PRD 路径。**做成必填的后果**是漏传被 argparse
        判用法错 → `exit 2`,而 `exit 2` 按全仓约定是「入参/环境错、不计维度失败」
        → 这一档**既不算过也不算不过,实际是静默没跑**(维度 13 的 `--version` 正是这么栽的)。
        未传时 `--json` 出 `requirements_scanned: false`,**⛔ 不得读成通过**。
      - ⚠️ **信号识别刻意不认裸「权限」「角色」「只读」**: 实测全仓 SKILL 文档标题里
        「权限」命中 29 处、「角色」19 处,绝大多数是「权限校验模块」这类非约束语境(⚠️ **口径**:`grep -rn '^#\{1,6\} .*<词>' .aidp/skills/*/ --include='*.md' | wc -l`,不排代码围栏;⚠️ 该数会随仓库演进而变,引用时请**现算**、⛔ 别照抄数字;结论不依赖具体数值,只依赖「量级是几十处而非几处」)
        (与 `check_metric_spec.py` 的 M1 同一条教训)。设计侧**只扫标题、不扫散文**;
        需求侧**扫正文**(约束句天生不会是个标题)。
      - ⚠️ **W1 缺表判 Important 不判 Critical**(存量大面积命中,判死会让硬门被无视,
        同 U1/E1/Z1 先例),**但检查项 40 的维度结论仍按不通过判**;配套地
        **一张表都没有时只报 W1、不报 G1~G6**,否则该取舍会被自己当场抵消。

    - **落位**: A.2 接口设计(逐接口的鉴权/过滤说明)或独立小节均可,不强制独立章节;
      表本身建议紧跟接口设计,便于与错误契约表对读。

    - **★ 去重边界**: 本原则只管**设计期有没有落点**。「这个过滤条件写对没写对 /
      有没有被绕过」由**被测项目侧**的代码验收承担,⛔ 本 SKILL 不做语义等价证明。

    - **质量检查**: 详见 `references/quality-review-checklist.md` 检查项 40 +
      配套脚本 `check_permission_constraint.py`。
