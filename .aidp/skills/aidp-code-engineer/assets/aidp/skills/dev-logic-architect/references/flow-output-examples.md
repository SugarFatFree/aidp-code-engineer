**🛡️ B.2 对内接口必须设「需求字段(语义) ⟷ 我方接口字段」比对门(Critical)**:

> 对每个承载需求列表/详情可见列的**对内**查询接口(`GET .../list`、`GET .../detail` 等),B.2 必须以**研发需求文档的需求字段清单(语义)**(上游 ux-logic-extractor 产出的「需求字段清单」表 A〔只含业务语义名,无代码级字段名〕+ 「需求字段 → 处置对照表」表 B,字段对账**单一信源**)为基准,生成一张「需求字段(语义) ⟷ 我方接口字段」逐字段差异比对表。比对门本质 = 「需求语义字段 → 我方接口字段(代码级,我方契约权所定)」的**映射完整性**核验。

- **三维比对**:① 命名(需求语义字段 ↔ 我方接口字段的**映射**是否完整无丢字段,语义须对得上,映射须说明)② 集合(需求语义字段是否都有接口字段承载=缺 / 接口字段凭空多出需求无对应=多)③ 顺序(出参列序与需求展示顺序是否一致)。
- **差异显式标处置**:每个差异项必须落到 `保留 / 裁剪 / 前端计算还原 / 请第三方补`(对齐表 B 枚举)之一 + 理由/去向,**严禁**差异项静默存在。
- **🚫 直透必须回比需求字段清单(语义)**:采用「接口字段直透 / 直接取接口字段 / 沿用后端现有出参」时,**严禁**接口字段静默覆盖需求设计——必须把直透字段集合逐列回比需求字段清单(语义),确保每个需求语义字段都被接口字段覆盖、零遗漏方可通过;需求语义有而直透出参没有承载的字段须显式列"缺"并标处置。
- **差异过产品确认门**:裁剪需求可见字段 / 命名映射漂移 / 顺序不一致等差异必须经**产品确认**(比对表「确认状态」标 ✅;未确认登记 Module E D-NNN 双向引用),不得由设计 Agent 自行砍列。

**🛡️ B.1/B.2 列表 / 表单 / 详情类页面强制产出「字段实现清单」(Critical·跨段词表契约)**:

> **背景(反向覆盖缺口):** 实测发现「研发需求 → 详细设计」段字段粒度**静默衰减** —— 研发需求列了具体列(如「已购商品数 purchasedCount」)、后端也返回了,但详细设计把字段清单**概括成一句话**(如"按 PRD 重建为企业管理视角"),导致下游前端漏渲染该列、又自造出需求里没有的列(如「总浏览时长」)。根因:缺**反向覆盖校验**(以研发需求每个字段为基准查有没有在详设落点)。**对策:凡列表 / 表单 / 详情类页面,B.1/B.2 各产出一张字段级「字段实现清单」表,禁一句话概括。**

- **产物名固定叫「字段实现清单」,每页一张,列固定为(跨段词表契约,不得改列名/列序):**

  `| 列名/字段 | 顺序 | 数据来源（接口字段） | 展示规则 | 上游出处 |`

  示例行:`| 已购商品数 | 3 | memberStats.purchasedCount | 数字,无特殊配色 | 研发需求 REQ-B02 / PRD spec:168 |`

- **铁律:**
  - **「上游出处」列不可为空** —— 每行必须可追溯到研发需求或 PRD 的具体位置(REQ 号 / 章节 / 行号);空白或占位符(`-`/`—`/`无`/`N/A`/`待定`/`TBD`)一律判违规。
  - **研发需求已列出的字段一个都不能少** —— 以研发需求「需求字段清单」(语义)为基准逐字段落地;确需不做的字段 → 标处置(`裁剪 / 前端计算还原 / 请第三方补`,对齐表 B 枚举)并经**产品确认门**(把字段裁剪三件套从「原型字段」**扩展到「研发需求字段」**,未确认登记 Module E D-NNN 双向引用),**严禁**设计 Agent 自行砍列。
  - **新增字段须留痕** —— 研发需求 / PRD 均未列、但实现有价值的列(如「总浏览时长」),同样在「上游出处」列标注来源与理由(如 `新增·管理视角需要,产品已确认 D-002`),避免**静默增列**。
- **该「字段实现清单」是下游唯一字段基线:** dev-manual-testcase 的「列表列完整性」用例、code-verification-loop 的「字段集与设计双向比对」都以它为单一信源(词表严格一致)。
- **反向覆盖硬核回检:** 落盘后由 `scripts/check_field_impl_inventory.py` 做**结构性**核验(检测到列表/表单/详情页缺清单 / 表头缺 5 列任一 / 「上游出处」有空行 → 退出码非 0);**语义层反向覆盖**(研发需求每个字段是否都在清单出现、是否漏字段、是否出现研发需求+PRD 均无的字段)由 QR 子 Agent 以研发需求「需求字段清单」为基准逐字段核对判定。与 `check_upstream_reference.py`(**正向**溯源:详设元素段头部有无引用上游)方向相反、并存互补、不可互相替代。

**🛡️ 上述字段比对门是「原型内容基线(元素+交互态+操作逻辑)三级覆盖门」的字段级一支(Critical)**:

> 字段比对门以「需求字段清单(语义)」为基准,只覆盖到**字段级**;它是 Phase 2 步骤 6 建立的「原型内容基线」**三级覆盖**的其中一级。B.2/B.5/B.3 必须并列覆盖另两级,确保详设不漏原型元素与操作逻辑:

**🛡️ 语义/口径变更类需求必产「文案落点表」(Critical·「字段实现清单」章节体系的姊妹子表·仅语义变更类需求触发)**:

> **背景(散落文案漏改缺口):** 实测发现「口径/语义扩大」类需求(如「用量消费统计口径由『仅企业』扩为『企业+个人』」)后端/接口/前端取数全改对,但**解释该数值的散落文案**(tooltip / 副标题 / 图例 / 导出表头 / 空态说明 …)有遗漏未同步改——某处 tooltip 仍写"仅统计企业级、不含员工个人消费",与实际展示值相反、误导对账。根因:字段改对了,但**解释字段语义的文案落点没有清单化逐一落地**。对策:凡语义/口径变更类需求,以上游 ux-logic-extractor「表 E:语义变更 → 派生展示物影响清单」(列 `变更项 | 变更前语义 | 变更后语义 | 受影响展示物 | 处置 | 新文案`,处置 ∈ 改写/保持/新增/待产品确认)为基准,在字段实现清单章节体系内**追加一张与「字段实现清单」同级、同强制度的姊妹子表「文案落点表」**,把表 E 中**处置=改写**的每一项落到具体 `文件:展示位`。

- **触发条件:** 仅当本次需求属**语义/口径变更类**(上游产出「表 E」且其中存在处置=改写项)时强制产出;纯新增/无语义变更的需求不触发(与「字段实现清单」的列表/表单/详情页触发条件相互独立)。
- **产物名固定叫「文案落点表」,列固定为(与上游「表 E」列名同属跨产物契约,逐字保持,不得改列名/列序):**

  `| # | 文件路径 | 展示位（tooltip/副标题/图例/导出表头/…）| 改前文案 | 改后文案 |`

  示例行:`| 1 | src/views/usage/UsageOverview.vue | 用量卡片 tooltip | 仅统计企业级、不含员工个人消费 | 统计企业级 + 员工个人消费合计 |`

- **铁律:**
  - **表 E 处置=改写项逐条落地** —— 表 E 中每个处置=改写的受影响展示物,必须在「文案落点表」有对应行,落到具体 `文件:展示位`,**禁一句话概括/禁遗漏**;改前文案、改后文案两列均须逐字填实,**严禁**空白或占位符(`待定`/`按实际调整`/`TBD`/`-`/`—`/`无`/`N/A`),否则判违规。
  - **必须显式给出「不改边界」** —— 在「文案落点表」下方以独立小节(如"不改边界")显式列出**形似但不受影响**的文案(如另一处口径本就含个人、或指标含义与本次变更无关的相似文案)+ 不改理由,防实现方**过度改写**(把无关文案也改了)或**漏改**(误以为已覆盖)。不改边界缺失 = 覆盖不完整。
