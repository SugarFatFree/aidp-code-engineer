# 输出规范 + 路径占位符实施指南

> 本文件是 `SKILL.md` 的输出落盘细则分片,按需 Read。**多文件拆分规范、命名约定、路径占位符替换**都在这里。

## 输出规范

### 索引态输出（默认，AIDP 命名范式）

1. 设计文档以 Markdown 格式输出，保存到用户指定路径或项目根目录下的 `docs/design/` 目录（或其他约定目录）
2. **AIDP 文档命名范式（四 SKILL 统一）——`00_` 槽位恒给专职索引 `00_索引.md`，内容主文档一律从 `01_` 起**：
   - **即便只产一份内容文档，也产出两个文件**：`00_索引.md` + `01_<专题>.md`（如 `00_索引.md` + `01_详细设计.md`；独立默认可 `01_{项目名}_详细设计方案_v{版本号}.md`）。**废除**「单份主文档 `00_<专题>.md`」与「拆分主文档 `00_…_总览.md`」两种旧锚，`00_索引.md` 为唯一新锚。
   - **`00_索引.md` 三项必载**：① 本目录全部内容文档（`01_`+）清单 + 每份一句话范围；② 每份文件的生成时间（`YYYY-MM-DD HH:MM`，区分「首次产出/最近修订」）——生成时用 shell `date +"%Y-%m-%d %H:%M"` 取当前时间打戳，**AI 不得凭空填时间**；③ 主文档/补充标识（首产=「主」，`--supplement` 增量=「补充」）。建议列：`| 序号 | 文件 | 生成时间 | 类型 | 说明 |`；补充轮再加 `关联输入变更 | 状态 | 取代关系` 列。
   - ⚠️ **`00_` 槽位唯一**：任一时刻目录内 `00_` 文件唯一 = `00_索引.md`（不再有 `00_<专题>.md` / `00_*_总览.md` 占位）。内容主文档从 `01_` 起、`99_` 固定给待澄清（详见下文「多文件拆分」与「拆分一致性检查」）。
   - ⚠️ **历史存量 grandfather**：早期裸 `00_<专题>.md`（单份态）/ `00_…_总览.md`（总览态）/ `NN_补充-…`（补充中缀）/ 并列态裸中文名，`check_doc_split.py` 识别放行、不报错；仅**新生成不再产出旧锚**。
3. 文档开头包含元信息：项目名称、版本号、作者、日期、技术栈摘要
4. 所有代码示例使用对应语言的语法高亮
5. 表格和列表保持对齐，确保可读性

### 多文件拆分（详细设计内容过多时）

**职责边界(详细设计不写研发计划)**:
- ❌ **严禁**包含: 研发执行计划、Sprint 排期、研发计划、开发周期、工时估算、里程碑、上线时间表、版本发布计划、人员分工
- ❌ **严禁**将模块/功规点/接口/数据表绑定具体迭代版本号(如 `B.1.3 由 Sprint-002 实现`)或具体日期
- ✅ **可以**: 标注"存量兼容方案"、"数据迁移方案"(属技术方案,非研发计划);标注模块间的技术依赖关系
- ✅ **Why:** 研发计划归 `dev-execution-planner` 处理,详细设计混入会导致设计随排期变化频繁修订,失去技术基线作用

**拆分判定（默认单文件,强烈推荐）**：

内容不多时尽量保持单文件输出,便于阅读和维护。满足以下任一条件时,才考虑拆分:
- 单文件预估超过 **800 行** 或 **60KB**
- 业务模块超过 **5 个**(用户/订单/商品/支付/...)
- 数据表超过 **20 张**
- 接口超过 **50 个**
- **涉及对外开放接口时**,必须将对外接口独立为 `12_对外开放接口.md`,与内部接口 `11_内部接口契约.md` 分离
- 用户明确要求"拆分输出"

**拆分数量控制（Critical）:**
- **目标文件数: 3~5 个**（含主文档）,不要超出太多
- 宁可单个文件长一些（800~1200 行）,也不要拆成 7、8 个碎片文件
- 只有内容确实非常多（>2000 行）时才允许超过 5 个文件
- 拆分前先评估：能否将相近模块合并到同一文件？（如 A.3+A.4 合并为"数据与字典"、B.3~B.7 合并为"设计专项"）

**避免过度拆分(碎片化)**:
- 单个子文档**目标行数 300~800 行**(专职索引 `00_索引.md` 与内部索引文档除外)
> ⚠️ **碎片阈值口径(本 skill 唯一信源,其余各处一律引用本块、⛔ 不再各写一遍)**:合规 = **≥150 行 或 ≥6KB**(二选一满足即可);违规 = **<150 行且 <6KB**。
> 一份 **120 行但 8KB** 的密集文档(表格多、行长)**不是碎片**,合并它没有意义。
> ⚠️ ⛔ 不要写成「无 <150 行**或** <6KB 的碎片」——那是**反向**语义(要求合规须同时满足两条)。
> ⚠️ 同期废止的还有**斜杠写法**「不足 `150 行 / 6KB`」——它读不出是「且」还是「或」,⛔ 别写回来。
> ⚠️ **豁免集(闭合清单,⛔ 别再用「索引文档」这种没有定义的说法)**:
>   ① 专职索引 `00_索引.md`;② **文件名以「索引.md」结尾**的内部索引文档(如 `05_字典与枚举索引.md` / `13_接口索引.md`);③ 保留序号 **`98_` / `99_`**(跨系统清单 / `99_待澄清问题清单.md` —— 它们按性质**天然短**,而本 skill 的目录范式**强制产出**它们)。
>   ⚠️⚠️ **②必须是「以『索引.md』结尾」,⛔ 不能写成「文件名含『索引』」**:
>   「索引」在本 skill 是**高频业务词**(数据库索引,检查项里 18 处),
>   按「含」豁免会把 `08_数据库索引设计.md` 这类**业务文档**一并豁免掉,方向是**假绿**。
>   (姊妹 skill `ux-logic-extractor` 的同名脚本用的正是「含索引」——它那边 PRD 不讲数据库索引,安全;⛔ 移植到本 skill 必须收窄。)
> ⚠️ **③ 必须在豁免内**:`output-format-rules.md` 与本文件都**强制产出** `99_待澄清问题清单.md`,一份 40 行的待澄清清单不豁免就会被判「碎片、必须合并回上级模块」。
> ⚠️ **机器门**:见 `check_doc_split.py --check-fragment`(⛔ 不加该开关时脚本不查行数/体积)。

- **严禁**生成**同时**不足 **150 行且不足 6KB** 的碎片子文档(专职索引 `00_索引.md`、索引文档(如 `05_字典与枚举索引.md`、`13_接口索引.md`) 除外)
- 若按业务域拆分后某子文档**不足 150 行且不足 6KB**,**必须合并**到相邻业务域子文档或合并回上级模块(如 `02_用户域数据表.md` 过小则合并回 `02_数据库设计.md` 单文件)
- 宁可单文件 900 行不拆,也不要拆成 5 个 100 行的碎片
- 字典枚举按域拆分时遵循同一标准: 单个子文件 **< 150 行且 < 6KB** 的应合并回 `05_字典与枚举定义.md` 单文件

**对外接口文档强制要求**:
- **独立文档**: 涉及供第三方系统调用的接口时,必须生成独立的 `12_对外开放接口.md`,不与内部接口混在一起
- **统一文档**: 所有对外开放的接口**统一写在一个文档中**,不按对接系统拆分
- **自包含原则**: 对外接口文档是提供给第三方的独立文档,**严禁包含本项目内部编号**和内部引用
- **免登录设计**: 对外接口严禁依赖 Session/Cookie/JWT Token,必须采用无状态认证方式
- **完整规范**: 详见 `references/output-module-examples.md` > "B.7 外部依赖与集成" > "对外接口文档强制规范"

**需第三方提供接口的强制要求(职责边界)——🔒 核心原则「对外提需求 = 业务诉求;对内做设计 = 可定契约」(Critical)**:

> **判定边界(先分清是谁的接口):**
> - **对内(我方系统内部新建的 Controller / Service / 前端 API)** → 照常在详细设计里**定契约**:路径、Method、字段名、响应结构、鉴权全部可规定。本原则**不**约束这类。
> - **对外(请第三方系统新建/补充接口)** → 只能提**业务诉求**,接口地址、字段命名、鉴权、协议形态是**对方系统的设计权**,我方规定/推荐即越界(不专业、污染对方契约、引发后续不一致)。

- **只写业务诉求,不规定对方契约形态** — 提给第三方的需求**只描述业务**,**严禁**出现我方拟定/推荐的对方 URL 路径、请求/响应字段名、Method、响应结构(`{code,data,message}` 之类)、鉴权方式、协议形态。
- **第三方需求产物只写以下 7 项(业务诉求导向)**:① 业务场景/目的;② **对应第三方功能位置**(这些数据对应对方系统自己的哪个菜单/功能页,如"对应订单中心 结算管理→对账明细",让对方一眼对上是开放哪个**现有功能**——属业务上下文、指向对方已有功能,**不构成对其 URL/字段的规定**);③ 需要的业务数据项——必须用「③ 业务数据项逐条枚举子表」(6 列:业务语义名/业务含义/类型量纲/是否必返/对应查询筛选维度/用途)**逐条完整枚举**,从**研发需求文档的需求字段清单(语义)**(需求可见语义字段)+ 功能逻辑推导出的每一个数据点单独成行,用**业务含义**表述(如"账期/应付金额/结算状态"),**严禁**"等/若干字段"一笔带过、**严禁**因"不写对方字段名"就省略数据项本身,**不写字段名/类型形态/响应结构**;④ 查询/筛选维度(**业务维度**);⑤ 数据范围与隔离(如"按企业隔离,仅返回本企业数据");⑥ 非功能诉求(分页、可外部调用、时效/SLA、调用量);⑦ **明确声明**:接口地址、字段命名、鉴权、协议等技术细节由对方按其规范自定,交付后提供联调环境 + 接口说明。
- **🔁 真实对接落地后反向核查(对方出参不得静默覆盖需求)**:第三方接口文档到位/联调开始后,必须把对方实际返回数据逐条回比业务数据项子表与需求字段清单(语义);需求语义有而对方未提供的数据点须显式标处置(请第三方补/前端计算还原/裁剪并 Module E 登记)。口径铁律:列「我方需要哪些数据(业务语义)」要全,但**绝不**写"对方该叫什么字段名/什么 URL/什么响应结构"。
- **允许引用对方"已存在"的能力作为上下文** — 基于**读对方源码的事实**可引用对方自有的、已存在的接口/能力(如"据了解你们已有 XX 内部能力"),但**不得据此替对方拟新接口的路径/字段**。
- **强制生成业务诉求清单** — 需第三方提供的能力必须**单独成表格列出**(序号、功能/业务诉求、业务数据项、调用时机、调用量、SLA、优先级、期望就绪时间、反馈状态),**表内不含我方拟定的对方 URL/字段名**,便于作为"需求清单"发给第三方。
- **完整规范与模板**: 详见 `references/output-module-examples.md` > "B.7 外部依赖与集成" > "方向 2: 需要第三方开放的接口"(业务诉求导向模板 + 反向核查)。

**拆分原则**：按 Module + 业务域两个维度拆分,**主文档作为索引和总入口**。

**文件命名强制要求(简洁原则,AIDP 索引态)**:
- **所有**文档文件名**必须**以两位数字前缀开头(`00_` ~ `99_`),保证字典序与逻辑顺序一致(**仅历史存量并列态裸名主文档除外**——新生成的多专题目录一律走索引态,见下文)
- `00_` 槽位**恒给专职索引 `00_索引.md`**、目录内唯一;内容主文档一律从 `01_` 起。`99_` 固定分配给待澄清问题清单(如有);其余序号按内容顺延
- **格式：`{两位数字序号}_{中文文件名}.md`**(简洁格式,只需序号+中文名,不需要嵌入模块编号 A1/A3/B1 等)
- 示例：`01_技术架构与基础框架.md`、`02_数据库设计.md`、`03_字典与枚举定义.md`
- 若模块再细拆(如数据库按业务域拆),使用更大的序号即可,无需嵌套二级序号
- 示例：`02_用户域数据表.md`、`03_订单域数据表.md`、`04_商品域数据表.md`(主文档索引中标注它们对应 Module A.3)
- **严禁**出现复杂嵌套命名(如 `02_A3_01_用户域数据表.md`),让文件名保持清爽
- **索引态严禁**出现无两位数字前缀的裸文件名 — 以下均为**不合格示例(Critical 不通过)**:
  - ❌ `补充-01-用户域.md`、`追加-02-订单域.md` → ✅ `03_用户域数据表.md`、`04_订单域数据表.md`(补充文档不带"补充"字眼,直接用序号+业务名,只在 `00_索引.md` 标类型=补充)
  - ❌ `详细设计.md`(缺序号前缀) → ✅ `01_详细设计.md`,`00_` 恒让位给专职索引 `00_索引.md`
  - ❌ `接口设计.md` → ✅ `02_接口设计.md`
  - ❌ `数据库设计.md` → ✅ `03_数据库设计.md`
  - ❌ `测试方案.md` → ✅ `19_测试方案.md`
  - ❌ `1_xxx.md`、`A01_xxx.md`、`Module-A3.md` → 均不合格
- **🎯 索引态 = 唯一新生成形态(即便只有一份内容文档)**:无论产出 **1 份**还是 **≥2 份**内容文档,一律走索引态——与 `研发需求/00_索引.md`、`plans/00_索引.md`、`研发自测/00_索引.md` 等其他文档族对齐,让使用者进目录即见阅读入口与顺序。目标形态:
  - `00_索引.md` —— 专职索引/导航入口(`00_` 槽位恒给它;列全部内容文档 + 每份生成时间 + 主/补充标识 + 一句话范围)
  - `01_详细设计.md` / `02_接口设计.md` / `03_数据库设计.md` / …(内容主文档从 `01_` 起,按序号顺延)
  - `98_事实清单.md` —— 代码事实基线保留位(如有)
  - `99_待澄清问题清单.md`(如有)
  - **只有一份内容时**同样两文件:`00_索引.md` + `01_详细设计.md`(**废除**旧单份态 `00_<专题>.md`)。
- **📝 补充文档(`--supplement` 增量)**:文件名**不带「补充」字眼**,直接 `NN_<业务名>.md`(序号顺延、不跳号);`--supplement` 给 `00_索引.md` 追加一行(类型=补充 + 生成时间),**不改**内容主文档正文。
- **⚠️ 历史 grandfather(新生成不再产出)**:早期裸 `00_<专题>.md`(单份态)/ `00_…_总览.md`(总览态)/ `NN_补充-…`(补充中缀)/ 同目录并列 ≥2 份裸中文名主文档(并列态,无任何 `NN_` 文件)均属**历史存量形态**。`check_doc_split.py` grandfather 识别放行、warn 不报错(存量目录不受影响),但它们**不再是生成默认**——新生成一律走索引态。
- 数字序号在同级目录内**连续不跳号**(允许为未来保留 `10_`、`20_` 等整十号作为分组分界;`98_`/`99_` 为保留序号)
- **模块编号映射关系记录在主文档的"文档结构与拆分说明"表中**,让读者通过表格而非文件名了解模块归属

**目录结构（骨架示例）**：`docs/design/{项目名}/` 下平铺 `00_索引.md`（专职索引/导航入口，`00_` 槽位恒给它）、`01_技术架构...` ~ `20_版本归档.md`（各内容主文档，从 `01_` 起），`99_待澄清问题清单.md` 固定最后。序号为示例，按实际模块组合顺延累进，不跳号、不嵌套二级序号。

**字典/枚举的拆分规则与跨文档引用**：

字典/枚举单独拆分判定:
- A.4 字典枚举定义文档预估超过 **800 行** 或 **60KB**
- 字典/枚举条目数超过 **30 个**
- 业务模块超过 **5 个**(每个域有独立的状态/类型字典)
- 用户明确要求"字典枚举单独拆分"

拆分原则:
- **按业务域拆分**(优先): 用户域/订单域/商品域/支付域/通用域
- **按字典类型拆分**(次选): 状态枚举/类型枚举/分类字典/角色字典
- 字典/枚举编码必须**全局唯一**,即使分散到多个文件也不允许同名重复
- 必须有 `05_字典与枚举索引.md` 作为字典枚举的索引主文档

> 字典枚举索引主文档/子文档的骨架、跨文档引用的硬性要求表、字典枚举拆分一致性检查表详见 [output-format-rules.md](./output-format-rules.md)

**专职索引 `00_索引.md` 必备内容**：`00_索引.md` 必须含元信息头部(版本/作者/日期/技术栈 + 上游输入来源溯源)、「文档结构与拆分说明」表（列全部内容文档 + 一句话范围 + 生成时间 `YYYY-MM-DD HH:MM`（区分首次产出/最近修订，`date +"%Y-%m-%d %H:%M"` 打戳）+ 主/补充标识 + 行数估算）、全局技术架构图、模块间依赖关系、全局术语表，以及「字典/枚举索引」「API 端点全局索引」「数据表全局索引」三类全局索引和一致性问题与决策记录。

**子文档头部规范**：每个子文档必须有头部(版本与主文档一致、隶属模块编号、专职索引 `00_索引.md` 链接、上下游引用、上游输入来源**溯源必填**,所有上游来源字段均必填或标注"无")。

> 主文档总览骨架与子文档头部骨架详见 [output-format-rules.md](./output-format-rules.md)

**上游溯源强制说明**:
- **模块级溯源**(本头部)是 M 级别最小要求;**条目级溯源**(表内每行功规点/接口/数据表)仍需单独标注 PRD 来源,精确到章节+页码/行号
- 子文档内每个功规点表(B.1)、接口表(B.2)、数据表 DDL(A.3)、字典枚举表(A.4)、状态机(B.5)必须逐条标注 `PRD 来源`,详见 "B.1 功规点实现映射中的引用要求"

**拆分一致性检查（Critical 硬核项,违反即不合规）**：

- **文件名两位序号**: 索引态下**所有**文档以两位数字前缀命名(`00_` ~ `99_`),`00_` 恒给专职索引 `00_索引.md`、内容主文档从 `01_` 起;**严禁**无前缀的裸文件名(**仅历史存量并列态约定15 例外**:无 `NN_` 文件 + ≥2 份裸名专题主文档共目录时 grandfather 放行;**新生成一律走索引态、不再产出并列态**)
- **`00_` 槽位唯一(硬核)**: 目录内 `00_` 文件至多一个 = 专职索引 `00_索引.md`;内容主文档从 `01_` 起,出现第二个 `00_` 即不合规。历史裸 `00_<专题>.md` / `00_*_总览.md` 作旧锚由 `check_doc_split.py` grandfather 放行(warn),新生成不再产出。`check_doc_split.py` 自动检测
- **文件名分隔符(硬核)**: 必须用 `_` 作 NN 与中文名的分隔符;**严禁** `01-接口设计.md` 这类 `-` 分隔符(`check_doc_split.py` **脚本内部检查项 7** 自动检测;⚠️ 非 QR 维度 7)
- **目录结构平铺(硬核)**: 拆分后所有 markdown 分册**平铺**在版本目录下,**严禁**创建 `modules/` / `submodules/` 等二级子目录(`check_doc_split.py` **脚本内部检查项 8** 自动检测;⚠️ 非 QR 维度 8)
- **中文文件名(硬核)**: 文件名去 `NN_` 前缀后必须含中文字符(`[一-龥]`),**严禁**纯英文/拼音/kebab-case;业务模块代号只能写在文件**正文头部元数据**,不进文件名(`check_doc_split.py` **脚本内部检查项 9-10** 自动检测;⚠️ 非 QR 维度 9/10)
- **索引齐全**: 主文档必须有"字典/枚举索引"、"API 端点全局索引"、"数据表全局索引"三类索引
- **避免碎片化**: 无 **<150 行且 <6KB** 的碎片子文档(专职索引 `00_索引.md`、索引文档除外);存在则合并回上级模块或相邻子文档
- **上游溯源完备**: 主文档与每个子文档头部均标注 `PRD 来源`、`原型来源`(如有)、`产品需求文档来源`(如有)、`高保真设计来源`(如有);路径精确到文件 + 章节
- **职责边界**: 全文无研发执行计划、Sprint 排期、研发周期、工时、里程碑、上线日期等研发管理内容

> 完整拆分一致性检查表(主文档完整性、编号统一、引用准确、版本号同步、术语统一、拆分粒度等)详见 [output-format-rules.md](./output-format-rules.md);多文件拆分一致性的**权威审查维度**以 `./quality-review-checklist.md` 检查项 12 为准。

## 路径占位符实施指南

生成设计文档时遇到 `{SQL脚本目录}`、`{文档目录}`、`{API文档目录}`、`{测试文档目录}`、`{配置目录}` 等占位符,按以下策略确定实际路径:

### 发现策略

1. **扫描项目现有结构**:
   - **SQL 脚本**: `find . -name "*.sql" -type f 2>/dev/null | grep -v node_modules | head -10` 查看现有 SQL 文件位置
   - **设计文档**: `find . -path "*/doc*/design/*.md" -o -path "*/design/*.md" 2>/dev/null | head -5`
   - **API 文档**: `find . -path "*/doc*/api/*.md" -o -path "*/api/*.md" 2>/dev/null | head -5`
   - **测试文档**: `find . -path "*/test*/*.md" 2>/dev/null | head -5`
   - **配置文件**: 检查 `config/`、`conf/` 及**所选技术栈的约定目录**（Spring Boot `src/main/resources/`、Go-Zero `etc/`、Node `.env`、.NET `appsettings.json` —— 详见 `references/stack-*.md` 的「配置文件位置」节）是否存在

2. **优先级规则**:
   - 若发现多个候选目录,优先选择**包含版本号子目录**(如 `v1.0.0/`、`v1.2.0/`)的目录
   - 若都无版本子目录,选择**文件数量最多**的目录
   - 各技术栈的配置文件约定目录见 `references/stack-*.md`「配置文件位置」节（如 Spring Boot 优先 `src/main/resources/`）

3. **无历史时的默认建议**:
   - SQL: `db/migrations/`
   - 设计文档: `docs/design/`
   - API 文档: `docs/api/`
   - 测试文档: `docs/test/`
   - 配置文件: `config/`(通用项目) 或所选栈的约定目录(见 `references/stack-*.md`「配置文件位置」节)
   
   **重要**: 若项目无现有同类文件,使用默认建议路径,但应在 **Module E 待澄清清单**中添加条目,例如:
   > **路径确认** — SQL 脚本默认放置于 `db/migrations/`,若项目使用其他目录结构请确认

4. **占位符替换**:确定实际路径后,将生成文档中所有对应的 `{目录}` 占位符替换为实际路径值
