### 步骤表的强制要求

- **"操作动作"列**:只允许以下动词 — 打开、访问、登录、点击、双击、右键、长按、悬停、输入、清空、选择、勾选、取消勾选、上传、下载、拖拽、滚动、滑动、切换、返回、刷新、关闭、等待、确认、观察、记录、扫码、核对、检查、执行、重复(`核对` 用于「列集合 vs 需求字段」逐列核对用例(维度 17 / 第五步之二);`检查/执行/重复` 主要用于 mock 清理验证等特殊用例,见核心原则 1 的例外说明)
- **"操作对象"列**:
  - 页面元素必须用**用户可见的文案**(带引号),如 `点击"提交审核"按钮`、`在"工单标题"输入框`
  - 页面级对象描述位置,如 `页面右上角"用户头像"`、`左侧菜单第二项"订单管理"`
  - **禁止**写 CSS 选择器/DOM id/XPath(如 `#submit-btn`、`.el-button--primary`)
- **"操作数据"列**:
  - 具体的输入值(如 `13800138000`、`张三`、`2026-05-12`、`product-list.xlsx`)
  - 无需输入时写 `—`
  - 随机/变动数据用占位符 + 说明(如 `{当前时间戳后 4 位}`)
- **"预期现象"列**:必须是**可观察**的现象,至少包含以下一种:
  - 页面跳转(跳转到"XX 页",URL 变为 xxx)
  - UI 元素变化(按钮置灰/置亮、标签颜色变化、进度条前进、Loading 消失)
  - 弹窗/Toast/Message 出现(写清标题与文案)
  - 列表/表单数据变化(新增一行、删除一行、字段显示新值)
  - 跨系统现象(对方系统出现消息/邮件/推送)
- **步骤编号**:套件入口流程用 `S1, S2, S3...`(Setup);用例步骤用 `1, 2, 3...`;套件清理用 `T1, T2...`(Teardown)。便于区分

### 复杂分支的处理

涉及**分支(if/else)**、**循环(loop)**、**多角色切换**的场景,拆分为多个独立用例,不在一个用例内用"若...则..."混合步骤。例如:

- "登录成功走 A 路径 / 失败走 B 路径" → 拆成 `TC-LOGIN-001 登录成功` + `TC-LOGIN-002 密码错误` + `TC-LOGIN-003 账号锁定`(均在"登录测试套件"内,但每条用例独立测试一种路径)
- "管理员视角 vs 普通员工视角" → 拆成两个独立套件(`SUITE-01 管理员套件` + `SUITE-02 普通员工套件`),每个套件内用例承接登录态

## AI 浏览器执行兼容规范

用例必须支持 AI 工具(Claude Code + **chrome-devtools-mcp**(推荐) / Playwright MCP / OpenClaw / browser-use 等)接管真实浏览器自动化执行。规范如下:

### chrome-devtools-mcp 工具规范(推荐,**仅适用于 Web 浏览器项目**)

**chrome-devtools-mcp** 是 Chrome DevTools 官方提供、可经 npm 全局安装(`npm i chrome-devtools-mcp@latest -g`)的 AI 浏览器自动化方案,基于 Chrome DevTools Protocol 与浏览器调试端口直连,**优先推荐(仅适用于 Web 浏览器项目)**:
- **🛡️ 适用范围(Critical 前置门槛)**:仅适用于"前端是 Web 网页"的项目(Vue/React/Angular SPA、传统多页 Web、H5、PWA、企业内部 Web 后台);**不适用**于桌面客户端 / 微信小程序 / iOS Android 原生 APP / React Native / Flutter 等非 Web 客户端,这些场景应改用 Appium / 微信开发者工具自动化 / WinAppDriver / Detox 等专用方案。**Electron 调试包**与**移动端 H5(WebView 可调试)**为"有条件适用",需确认开放调试端口。**混合项目**(如 iOS APP + Web 后台)需明确 chrome-devtools-mcp 仅覆盖 Web 部分,非 Web 部分另行声明工具(如 Appium)。完整适用范围与替代方案表见 [`references/chrome-devtools-mcp-setup.md`](./chrome-devtools-mcp-setup.md) §0。
- **优点**:零额外依赖(只需 Chrome 客户端 + 调试端口),原生支持远程调试(WSL/SSH 友好),与 Claude Code Skill 调用流畅
- **🪟 渲染模式(优先无头)**:**无头模式**(`--headless=new`,**无需 GUI 桌面环境**,服务器 / WSL / SSH 可用,**应优先使用**);**有头模式**仅在① 需被网站当成真人(反无头 / 反爬验证)② 需测试不同分辨率 / 真实视觉效果 ③ 无头无法正常加载 / 操作 —— 三场景之一时启用:有头本地需 GUI 桌面,本地无 GUI 则走**有头 + 远程模式**。**走本地模式时,生成方案前须自动检测本机 Chrome,未装则引导用户安装(检测/安装命令见 references §2.0)**
- **本地模式 → `chrome-devtools-cli`(CLI 直调,免重启)**:Chrome 与 Claude Code 同机,启动 Chrome `--remote-debugging-port=9222` 后 CLI 直连本机调试端口,**不读 MCP 配置**(**无头本地无需 GUI;有头本地需 GUI 桌面**)
- **远程模式 → `chrome-devtools-mcp`(MCP 服务)**:Chrome 与 Claude Code 异机,需 `netsh interface portproxy` 端口转发把 IPv6 `::1:9222` 暴露为 IPv4 `0.0.0.0:9222`,端点写入 MCP 配置
- **⚠️ 切换:本地 CLI 免重启,远程 MCP 改端点才重启**:本地无头↔有头切换 = 改本机 chrome 的 `--headless=new` 开关并重启 chrome 进程,**Claude Code 无需重启**;仅"首次配置远程端点 / 换远程机器·端口"时才须改 MCP 配置文件再**重启 Claude Code**(见 references §6)
- **完整安装/启动/配置指令**:见 [`references/chrome-devtools-mcp-setup.md`](./chrome-devtools-mcp-setup.md)(SKILL "执行流程 > 第零步 > 0.5" 为速查摘要)
- **自测方案标注要求**:启用 chrome-devtools-mcp 时,自测方案 §2.2 必须填写工具名 + **客户端类型(必须为 Web)** + **渲染模式(默认无头)** + 本地/远程模式 + **(本地模式)本地 Chrome 检测结果** + 抽查比例 + 测试环境地址 + 账号 +(远程模式)远程 IP+端口 + **关键步骤截图(有头/无头都要求,无头下截图是唯一执行证据)**

### 多文件拆分

**默认输出单文件（强烈推荐）**。内容不多时尽量保持单文件,便于阅读和执行。

**触发条件**（满足以下任一条件时,才考虑拆分）:
- 用例总数超过 **40 条** 或单文件超过 **800 行/60KB**

**拆分数量控制（Critical）:**
- **目标文件数: 3~5 个**（含主文档）,不要超出太多
- 宁可单个文件长一些（800~1200 行）,也不要拆成 7、8 个碎片文件
- 只有用例确实非常多（>80 条）时才允许超过 5 个文件
- 拆分前先评估：能否将相近模块的用例合并到同一文件？

```
{测试文档目录}/{项目名}/
├── 00_索引.md               # 专职索引(必产,AIDP 范式)
├── 01_研发自测方案.md       # 自测方案(必产,字典序在用例之前)
├── 02_自测用例-总览.md              # 用例主文档(必需)
├── 03_{模块1}-自测用例.md
├── 04_{模块2}-自测用例.md
├── 05_{模块3}-自测用例.md
├── 98_跨系统验证清单.md                      # 汇总跨系统验证(如有,序号固定 98)
└── 99_待澄清问题清单.md                      # 待澄清问题(如有,序号固定 99,永远最后)
```

**拆分要求:**

1. 文件名两位数字前缀(`00_`~`99_`),字典序与逻辑顺序一致;`00_` 固定保留给**专职索引 `00_索引.md`**;`01_` 固定保留给**研发自测方案**;`02_` 固定保留给**用例总览主文档(多文件)或单文件用例(全量 / 增量)**;`98_` 保留跨系统验证清单(如有);`99_` 固定待澄清问题清单(如有);业务模块用例从 `03_` 开始顺序编号。**同目录所有文件一律带 `NN_` 前缀,无例外**(见上「文件命名总则」)
   - **严禁使用"补充"/"追加"作为文件名前缀**(如 `补充-04-订单用例.md`) → 正确格式: `04_订单管理用例.md`(补充用例文档直接用序号+模块名)
   - **后续文件序号接着上一个文档序号自动累进**(不跳号,不嵌套二级序号);允许保留整十号(10_/20_/30_...)作为分组分界
2. 用例总览主文档 `02_自测用例-总览.md` 包含:自测方案来源(L1 引用)、测试环境、账号、前置数据、用例索引(TC-ID → 所在子文档链接)、跨系统验证汇总
3. 用例编号**全局唯一**,不允许跨子文档重复
4. 子文档头部必须标注:隶属总览文档、所属模块、覆盖 TC-ID 范围、**自测方案来源**(必填)
5. 跨子文档的用例依赖(如"接续用例 TC-A-005 的数据状态")需明确引用路径
6. **前置数据准备章节只在用例总览主文档写一次**,子文档引用主文档章节
7. **自测方案文档不参与套件/用例拆分**,始终是单一文件 `01_研发自测方案.md`
