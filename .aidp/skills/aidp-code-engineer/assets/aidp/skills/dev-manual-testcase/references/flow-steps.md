# 执行流程细则(第一步 ~ 第四步 / 第六步 ~ 第八步)

> 本文件是 `SKILL.md`「执行流程」除第零步、第五步族之外各步的细则全文,按需 Read。
> 第零步见 [`flow-step0-test-plan.md`](./flow-step0-test-plan.md);第五步族(覆盖矩阵与特殊场景)见 [`flow-step5-coverage.md`](./flow-step5-coverage.md)。

### 第一步:环境与入口信息采集(缺失时走占位符策略)

生成用例前,需识别以下入口信息(若用户未提供,**严禁中断生成**,改用占位符 + T-NNN 登记策略,详见下文"入口信息缺失时不中断"段;也严禁自行编造 URL/账号):

1. **系统入口 URL** — 测试环境访问地址(如 `https://test.example.com`)
2. **客户端类型** — 浏览器(Chrome/Edge/Safari) / 桌面客户端 / iOS APP / Android APP / 小程序
3. **登录入口与方式** — 账号密码 / 扫码 / 手机号+验证码 / 单点登录(SSO/企业微信/钉钉)
4. **测试账号** — 至少提供覆盖所有角色的测试账号(如 admin / 管理员 / 普通员工 / 访客);若 PRD 定义了多角色,每个角色至少 1 个账号
5. **前置数据准备** — 用例依赖的已有数据(如"测试账号名下需预先有 3 条工单数据")。若需要则在用例开头统一列出"前置数据准备"章节
6. **跨系统依赖环境** — 若涉及 SSO/支付/短信/企业微信等,标注对方系统的测试环境地址与验证方式(如"SSO 测试环境:`https://sso-test.example.com`,登录后跳回应用")

**入口信息缺失时不中断,使用占位符 + 待澄清登记**(详见 `../SKILL.md` >「不中断原则」章节)。具体处理:
- 在文档头部"测试环境"章节用占位符标注,如 `测试环境 URL: {待用户填写}`、`admin 账号: {待用户填写: 用户名/密码}`
- 在"待澄清问题清单"登记 T-NNN 条目(主题:测试环境入口信息缺失;影响范围:全部套件入口流程 Suite Setup;暂行方案:以占位符代替,用户提供后替换;优先级 P0)
- **严禁自行编造** URL/账号(如不得写 `https://test.example.com` 这类未经用户确认的地址)
- 用户后续提供入口信息后,全局替换占位符即可

### 第二步:范围裁定与套件划分

1. 提取覆盖范围(全量 = PRD 全部功规点;增量 = 迭代 Task + 关联回归)
2. **按角色分组**:同一角色的用例归到同一套件(管理员套件、普通员工套件、未登录套件)
3. **按业务域细分**:若某角色用例 > 15 条,再按业务域拆套件
4. **特殊套件**:登录/登出测试、跨角色切换测试单独成套件
5. 输出套件清单(套件 ID、所用角色、覆盖模块、用例数预估)

### 第三步:套件内用例编排

对每个套件,**按"真实测试人员的操作顺序"编排用例**:

1. 入口流程后,先到工作台,然后按菜单顺序进入各模块
2. 同一模块内,先正向(新增/查询/编辑)后异常(校验/权限/状态约束)
3. 用例之间通过"导航步骤"衔接(点击菜单/Tab/返回按钮),**不重新登录**
4. 状态依赖明确:若 TC-002 需要 TC-001 创建的数据,在 TC-002 标注依赖

### 第四步:逐个用例生成

按"用例编号 → 标题 → 模块 → 优先级 → 类型 → 测试项 → 反向 → 覆盖 → 承接说明 → 测试步骤表 → 预期总结"结构生成。

- 用例编号规则:`TC-{模块缩写}-{序号}`(如 `TC-USER-001`)
- 优先级:P0 主流程 / P1 重要分支 / P2 边缘场景与异常
- **每个用例的元信息字段行必含以下显式字段**(对齐 9 字段规范,便于数据化统计与 QA 按反向筛选):
  - **类型**:正向 / 异常 / 边界 / 权限 / 回归 / 列集合核对 等
  - **测试项**:被测对象的极简概括,**≤5 字**(如"新增""必填校验""状态流转")
  - **反向**:`是` / `否`——正向 happy path 填 `否`,校验/异常/边界/权限/状态约束/并发填 `是`(供 `check_case_stats.py` 精确统计反向占比,不再靠类型推断)。**字段名契约:键统一为「反向」(值 是/否),与下游 `auto-test-runner` skill 的 `usecase-format.md` 解析契约一致(映射其结果 JSON `is_reverse`),不用「是否反向」等别名,避免自动化解析歧义**
  - **覆盖**:本例覆盖的**覆盖矩阵维度标签**(如 `F4,R1`,即创建 + 必填校验),供生成维度→用例覆盖映射表、核查哪个维度无用例覆盖(见第七步 / 维度 18)
- **每个用例的步骤表只写"本用例需要执行的操作"**,不重复套件级入口流程
- 用例第一步通常是导航(如"点击左侧菜单'用户管理'")或直接是功能操作(若承接上一用例的页面状态)

### 第六步:执行兼容性自检(默认手动浏览器,可选 AI 浏览器)

生成完成后,对每个步骤**自检**(无论默认手动执行还是可选 AI 浏览器执行,以下检查项都生效):

- [ ] 操作对象是否用"用户可见的文案/标签"(而非 CSS 选择器或 DOM id)
- [ ] 操作动作是否为浏览器可执行的原子动作(打开/访问/点击/输入/选择/上传/滚动/悬停/返回)
- [ ] 输入数据是否具体(如"输入手机号 13800138000",而非"输入手机号")
- [ ] 预期现象是否肉眼可验证(页面跳转、Toast 文案、弹窗标题、按钮状态变化)
- [ ] 是否出现"调用接口/查询数据库/执行 SQL"等非 UI 动作(若有必须删除)
- [ ] 套件内用例是否避免了重复的入口流程(只在套件开头出现一次)
- [ ] 含列表/表格/表单的功能点是否有「字段/列与需求字段清单逐列核对」用例或步骤(核对列展示名(语义)/展示顺序/缺多列/与「需求字段→处置」对照表一致),而非仅"页面可打开 + 数据加载成功"

### 第七步:覆盖率回检与完备性收敛(生成时自检闭环,强制)

**把单向"生成→补异常→交付"改成"生成→自检→补充→回检"闭环——让"事后 QA 才发现漏"提前到生成阶段自己补全。** 本步在交付前(即末尾独立 Agent QR 之前)由主流程执行一轮生成时自检,**与事后 QA 用同一套维度、同一份信源,不产生双信源**:

1. **逐维回检覆盖矩阵**:对照「测试设计方法论速查」的正向 9 维 + 反向 12 维,核对每个功能点是否逐维过一遍、不适用是否标注原因(判据同**维度 18**)。
2. **回检方法论套用**:BVA 六点法、等价类有效/无效枚举、状态机合法+非法迁移、并发 C1-C6 是否按第五步之三补齐(判据同**维度 18**)。
3. **回检数量基线与优先级**:各模块用例数是否落在数量基线区间(简单 30–60 / 中等 80–150 / 复杂 150+),低于下限是否已说明原因;P0/P1/P2 分布与反向占比(≥40%)是否达标(判据同**维度 19**)。
4. **输出用例统计摘要 + 维度覆盖映射表**:在文档末尾生成「用例统计摘要」(模板见方法论第七节)。用 `python3 <SKILL_DIR>/scripts/check_case_stats.py <用例路径>` 机检套件数/用例数/优先级分布/正反向占比(读各用例「反向」字段)/基线达标;加 `--coverage-matrix` 输出**维度→用例交叉表**,一眼看出哪个覆盖矩阵维度(F1-F9/R1-R12)无任何用例覆盖——未覆盖维度须补用例或就地标 `不适用 + 原因`;**发现未覆盖维度即回到第五步(或第五步之二/之三)补充对应用例 → 重跑第七步核验,如此循环直至全维收敛(每维 100% 覆盖或已标不适用)**,不是核对一遍就结束。
5. **回检原型内容基线覆盖(AIDP 广度基准)**:对照第五步之零取得的原型内容基线(或回退现场清单),核对**每个处置="实现"的元素/交互态/操作逻辑是否一一对应到用例、无遗漏**,裁剪/延期/改逻辑项是否已登记不覆盖原因(判据同**维度 18「原型内容基线覆盖度」子条**)。存在实现项既无用例、又未标不覆盖原因的 → 回到**第五步之零**补齐(元素/交互态/操作逻辑三层完整比对由主流程 Agent 语义完成)。
   - **回检语义/口径变更文案一致性(第五步之八)**:若命中语义/口径变更(有「表 E」/「文案落点表」或 PRD 命中),核对每个处置=改写的展示位是否有一组 `[文案一致性]`(正 + **反向 Critical** + 一致性)用例、旧口径字样是否已被 `断言(反向):不存在文本"X"` 反向断言覆盖;缺反向用例(只断言新文案存在)即回到**第五步之八**补齐(判据同**维度 18**)。无语义变更需求则标不适用。
6. **收敛循环(闭环,非单向回检)**:回检是一个**循环**,不是走一遍就结束——
   - 逐维核对每个覆盖维度(覆盖矩阵正向9维+反向12维、BVA/等价类/状态机非法迁移/并发、**原型内容基线实现项(元素/交互态/操作逻辑)**、数量基线、优先级/反向占比)的覆盖率;
   - **任一维度未达 100%**(有功能点缺维未标不适用、缺方法论用例、**原型实现项缺覆盖未标不覆盖原因**、数量低于下限未说明、反向占比 <40%)→ **自动进入补充**:回到**第五步之零~第五步之三**补齐缺口用例 → 再执行**第七步**回检;
   - **重复「补充 → 回检」直至全维收敛(每个维度 100%)**,收敛后才交末尾 21 维度独立 Agent QR 复核;
   - 每轮回检输出「**未达标维度清单**」(维度 → 缺口 → 补充动作),使收敛过程可追溯。

> **判定:** 第七步是**生成时的前置自检闭环**,不替代末尾独立 Agent QR;但缺第七步/未收敛会导致维度 18/19 大面积不通过、反复返工。第七步与维度 18/19 引用**同一份** [`references/test-design-methodology.md`](./test-design-methodology.md) 判据:**仅全维达标才算收敛通过,否则必须输出缺口维度清单并继续补充**。

### 第八步:生成 / 更新 `00_索引.md`(专职索引,收尾必产,AIDP 范式)

**所有内容文档(`01_研发自测方案.md` + `02_` 起的全部用例文档)落盘后,收尾必须用 Write 生成专职索引 `00_索引.md`**(与 ux/architect/planner 三个文档 SKILL 统一)。索引三项必载:

1. **本目录全部内容文档清单**(`01_`+,含方案与所有用例文档)+ 每份一句话范围;
2. **每份文件的生成时间**——用 shell `date +"%Y-%m-%d %H:%M"` 取当前时间打戳,**不得凭空填时间**;区分「首次产出 / 最近修订」;
3. **主 / 补充标识**(首次全量产出=「主」;增量补充轮=「补充」)。

建议表头:`| 序号 | 文件 | 生成时间 | 类型 | 说明 |`。**增量补充轮**只给 `00_索引.md` 追加一行(类型=补充 + 生成时间),不改内容主文档正文。

> **与自测方案的分工:** `00_索引.md` 是「文档族清单」级导航(本目录有哪些文件);`01_研发自测方案.md` §8 用例索引是「套件 → 用例」级业务导航(方案 ↔ 用例双向引用闭环)。二者职责不同、并存不冲突,**均必产**。
> **机检:** `python scripts/check_testcase_format.py {测试目录}` 会核 `00_索引.md` 存在(缺失报 Important;历史旧锚 `00_研发自测方案.md` 目录 grandfather 放行、提示迁移)。
