# 上游引用规则(L1~L4 四级引用)

> 本文件是 `SKILL.md`「上游引用规则」的细则全文,按需 Read。**四级引用是 Critical 强制要求**,骨架只留结论,判据与正反例在这里。

## 🔗 上游引用规则（Critical 强制要求）

**自测用例必须建立完整的"三层引用追溯"体系,每条用例必须可反查到 PRD/原型/设计/研发执行计划的精确位置。这是出 bug 时回溯需求源头、回归测试时定位影响范围的基础。**

### L1 文档级引用(必填,在主文档头部声明)

主文档头部**必须**包含以下引用块:

```markdown
> **自测方案来源:** `<研发自测方案文件路径>` (**Critical 必填**,默认 `./01_研发自测方案.md`——方案与用例同目录平级)
> **PRD 来源:** `<PRD 文件路径或目录>` (单文件给文件路径;多文件给根目录)
> **详细设计来源:** `<设计文件路径或目录>`(若有)
> **原型来源:** `<原型路径或目录>`
> **研发执行计划来源:** `<研发执行计划文件路径>`(增量模式必填)
> **高保真设计来源:** `<高保真设计目录>`(若有)
> **代码仓库来源:** `<代码仓库根目录>`(已有代码时,用于核对 URL/文案/校验规则)
```

**不适用的项必须显式标"无";"自测方案来源"不允许标"无"**(无方案时 SKILL 会先起草最小方案再生成用例)。

### L2 套件级引用(每个测试套件标注上游来源)

每个测试套件标题下方**必须**有引用块,**强制 6 行**(S0 自测方案章节 ~ S5 承上启下,顺序固定;"覆盖功规点/覆盖状态/affects"为推荐附加行):

```markdown
### 套件 SUITE-USER: 用户管理(管理员视角)

> **自测方案章节:** [§3.2 用户管理范围与通过准则](./01_研发自测方案.md#3-2-用户管理)(**Critical 必填**,定位本套件在自测方案中的范围/通过准则)
> **PRD 来源:** [REQ-NNN: 标题](../requirements/{version}/研发需求/xxx.md#REQ-NNN)(必填)
> **原型来源:** [<Component>](../prototype/{version}/code/xxx.jsx#L行号)(必填,如适用;纯后端套件标 `N/A,纯后端,无 UI 关联`)
> **详细设计来源:** [§X.Y 章节名](../docs/design/detail/{version}/xx.md#X-Y)(必填)
> **研发执行计划来源:** [Sprint-NNN T-NNN-NN](../docs/plans/{version}/研发执行计划.md#T-NNN-NN)(增量模式必填,全量模式标 N/A)
> **承上启下:** 前一套件 [SUITE-NNN](#SUITE-NNN) 完成的页面状态;本套件接着做什么(辅助阅读,允许空)
> **覆盖功规点:** [五-1](../requirements/{version}/研发需求/xxx.md#五-1)、[五-2](../requirements/{version}/研发需求/xxx.md#五-2)
> **覆盖状态:** 共 8 条用例 → P0×3 / P1×4 / P2×1
> **affects:** modules=[用户管理, 权限管理] pages=[/system/user, /system/role]
```

**★`affects:` 影响面标签(推荐附加行,供下游按 git diff 筛选应跑套件):**

下游跨 build 回归时可用它做**变更影响面筛选**——把本次 `git diff` 涉及的路径与各套件的 `affects` 做包含匹配,**命中的套件才需重跑,未触及的沿用上轮结论**。

- **位置**:套件块头部,与其余 L2 引用行**并列**(放在最后一行,不打乱 S0~S5 固定顺序)。
- **语法(单行,两个列表)**:`> **affects:** modules=[A, B] pages=[/x, /y]`
  - `modules` 取自本套件**上游详细设计的模块名**(与 L2「详细设计来源」指向同一批模块);
  - `pages` 取自**前端路由**(与 L2「原型来源」/ 用例步骤里的页面一致);
  - 两个列表**逗号分隔、都不得为空**;某维度确实没有(如纯后端套件无路由)写 `pages=[N/A]`,**不要留空列表**——空列表读起来像"忘了写"。
  - ⚠️ **刻意用单行而非嵌套 YAML**:L2 引用块是 blockquote,里面嵌套 YAML 缩进极易被 markdown 吞掉、也和其余 6 行的「`**键:** 值`」行式不一致;单行形态既能逐行 grep,也不破坏既有块结构。
- **纯增量元信息**:不改用例正文、不影响既有引用闭环;**缺失不判不通过**(存量文档 grandfather 放行),`check_testcase_suite.py` 只出 Info 提示。

**🛡️ 引用必须 markdown 可点击链接 + 相对路径(Critical):**

- ✅ **正例**: `[§B-2.1 用户列表接口](../docs/design/detail/V1.0/01_接口设计.md#B-2-1)` — 显示文本含**章节编号 + 章节名**,链接相对路径 + 锚点
- ❌ **反例(纯文本路径)**: `docs/design/detail/V1.0/01.md > §B-2.1`
- ❌ **反例(绝对路径)**: `[xxx](C:/Users/xxx/...)` 或 `[xxx](/home/...)` 或 `[xxx](https://...)`
- ❌ **反例(无锚点)**: `[xxx](../docs/design/detail/V1.0/01.md)`(链接到文件但没指向具体章节,QA 跑用例时无法精确定位)

**精细引用层级(尽可能精细,统一 5 级):**

| 层级 | 显示文本格式 | 链接路径格式 | 适用场景 |
| :- | :- | :- | :- |
| 文件级 | `[文件名](xxx.md)` | `xxx.md` | 整篇文档相关时(最低) |
| 章节级 | `[文件 §X.Y 章节名](xxx.md#章节锚点)` | `xxx.md#章节锚点` | **推荐基础级** |
| 行号级 | `[文件 §X.Y(L120-L180)](xxx.md#L120-L180)` | `xxx.md#L120-L180` | 长章节内精确范围 |
| 组件级 | `[<UserList>](xxx.jsx#L20-L80)` | `xxx.jsx#L20-L80` | 原型 React/Vue 组件 |
| HTML 锚点级 | `[#search-btn](xxx.html#search-btn)` | `xxx.html#search-btn` | HTML 原型按钮/表单 |

**用例步骤验收锚点也必须用 markdown 链接:** 每条用例步骤的"预期现象"列必须额外标注对应详细设计验收章节的精确锚点,如 `(验收: [§C-2.3 列表查询用例](../docs/design/detail/V1.0/19_测试方案.md#C-2-3))`,QA 跑用例时双向追溯到设计验收标准。

### L3 用例级引用(每条用例必须的"四源原则")

> **四源原则:** 每条用例(TC-XXX)抬头必须标注 4 类引用,**任一应填项缺失视为不通过**。

```markdown
#### 用例 TC-USER-001: 新增用户

> **PRD 来源:** [§五-1 用户列表 > 操作 4 新增用户(L150-L165)](../requirements/V1.0/研发需求/用户管理.md#五-1-用户列表)
> **原型来源:** [#add-user-btn 新增按钮 → 弹窗 #add-user-dialog](../prototype/V1.0/code/user-list.html#add-user-btn)
> **设计来源:** [§B.2 POST /user(L470-L490)](../docs/design/detail/V1.0/03_接口设计.md#B-2)(若有详细设计)
> **研发执行计划来源:** [Task 2.3 实现新增用户](../docs/plans/V1.0/研发执行计划.md#Task-2-3)(增量模式必填)
> **代码来源:** [UserList.vue L120-L180](../src/views/user/UserList.vue#L120-L180) / [createUser](../src/api/user.ts#createUser)(已有代码时,用于核对实际文案/URL/校验)
> **优先级:** P0 | **承接前置:** 上一用例结束于"用户列表"页

[步骤表格...]
```

**按用例类型的引用要求差异:**

| 用例类型 | PRD | 原型 | 设计 | 研发执行计划 | 代码 |
| :- | :-: | :-: | :-: | :-: | :-: |
| 主流程用例 | **必填** | **必填** | 推荐 | 增量必填 | 已有代码必填 |
| 异常路径用例 | **必填**(八、异常路径章节) | 推荐 | **必填**(B.3) | 增量必填 | 已有代码必填 |
| 字段校验用例 | **必填**(六、字段规格章节) | **必填** | 推荐(A.4) | 增量必填 | 已有代码必填 |
| 权限用例 | **必填**(四、RBAC + 七·2) | 推荐 | 推荐 | 增量必填 | 已有代码必填 |
| 状态机用例 | **必填**(七、字典枚举) | 推荐 | **必填**(B.5) | 增量必填 | 已有代码必填 |
| 第三方对接用例 | **必填**(七·4 对接说明) | 推荐 | **必填**(B.7) | 增量必填 | 已有代码必填 |
| Bug 修复用例 | 标注 Bug 复现路径 | 推荐 | 推荐 | **必填**(Task ID) | **必填**(修复 commit) |

### L4 步骤级引用透传(每个步骤的预期现象引用代码/PRD)

每个步骤的"预期现象"列**必须可反查代码或 PRD**,严禁凭推测描述:

```markdown
| 步骤 | 操作动作 | 操作对象 | 操作数据 | 预期现象 |
| 3 | 点击 | "提交"按钮 | — | Toast 提示"用户创建成功"(代码: `i18n/zh-CN.json#user.create.success`),弹窗关闭,列表顶部新增一行(PRD: 五-1 操作 4 步骤 5) |
```

**强制规则:**
- ✅ 已有代码时:Toast 文案、错误提示、按钮文案必须从代码提取(标注 `i18n` 文件或组件位置)
- ✅ 无代码但有原型时:文案从原型提取(标注原型锚点)
- ❌ **严禁推测**: "应该是'操作成功'" / "可能跳转到列表页"
- ❌ **严禁脱离来源**: 描述无对应代码/原型/PRD 的现象

### 引用格式标准化

**🛡️ 所有引用必须用 markdown 链接 + 相对路径 + 精细锚点(章节级 > 行号级 > 组件级 > HTML 锚点级):**

| 引用类型 | 格式 | 示例 |
| :- | :- | :- |
| 研发 PRD(.md) | `[显示文本](相对路径#章节锚点)` | `[§五-1 用户列表(L120-L150)](../requirements/V1.0/研发需求/用户.md#五-1-用户列表)` |
| 详细设计(.md) | `[显示文本](相对路径#章节锚点)` | `[§B.2 POST /user(L470)](../docs/design/detail/V1.0/03_接口设计.md#B-2)` |
| 原型文件 | `[显示文本](相对路径#组件名/锚点)` | `[#add-btn 新增按钮](../prototype/V1.0/code/user-list.html#add-btn)` 或 `[<UserListPage>](../prototype/V1.0/code/user-list.jsx#L20-L120)` |
| 研发执行计划 | `[显示文本](相对路径#Task-X-Y)` | `[Task 2.3 新增用户](../docs/plans/V1.0/研发执行计划.md#Task-2-3)` |
| 代码引用 | `[显示文本](相对路径#L行号 或 #符号)` | `[UserList.vue L120-L180](../src/views/user/UserList.vue#L120-L180)` 或 `[createUser](../src/api/user.ts#createUser)` |
| 国际化文件 | `[显示文本](相对路径#key路径)` | `[user.create.success](../src/locales/zh-CN.json#user.create.success)` |

**严禁的格式:**

| 反例类型 | 示例 |
| :- | :- |
| ❌ 纯文本路径 | `docs/prd/PRD.md > 五-1` |
| ❌ 反引号包裹纯文本 | `\`docs/prd/PRD.md > 五-1\`` |
| ❌ 绝对路径 | `[xxx](https://...)` 或 `[xxx](C:/Users/...)` |
| ❌ 无锚点 | `[xxx](../docs/PRD.md)`(指向文件但无章节锚点) |
| ❌ 模糊引用 | `参考 PRD` / `见原型` |

### 强制要求(违反任一即 Quality Review 维度 13 不通过)

1. **主文档头部** 包含 6 个引用字段(PRD/设计/原型/研发执行计划/高保真/代码),不适用项标"无"
2. **每个测试套件抬头** 包含 L2 引用块: PRD 来源 + 原型来源 + 设计来源 + 覆盖功规点
3. **每条用例抬头** 包含 L3 四源引用(PRD 必填、原型/设计/研发执行计划/代码 按类型必填)
4. **每个步骤的预期现象** 必须可反查代码或 PRD/原型(已有代码时强制从代码提取实际文案)
5. **路径必须为仓库相对路径**,不允许绝对路径
6. **不接受模糊引用**: ❌ "参考 PRD" / "见原型" → ✅ `[§五-1(L120)](../requirements/...md#五-1)`
7. **增量模式** 每条用例必须标注研发执行计划 Task ID
8. **Bug 修复用例** 必须标注修复 commit / Task ID + Bug 复现路径
9. **已有代码时** URL/文案/校验规则等必须从代码提取(`从代码读取:<位置>` 标注),不得推测
