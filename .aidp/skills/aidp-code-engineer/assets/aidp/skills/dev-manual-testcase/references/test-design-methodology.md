# 测试设计方法论(覆盖矩阵 + BVA + 等价类 + 状态机 + 并发 + 数量基线)

> **本文件是「测试用例设计方法论」的唯一信源**。SKILL.md「测试设计方法论速查」章节是本文件的精简摘要 + 入口;质量检查维度 18/19 以本文件为对照基准。
> **用途:** 解决"用例偏少、只堆正向 happy path、异常/边界/权限/状态流转/并发经常漏、数量不稳定无完备性下限"的问题。生成用例时(执行流程第五步、第五步之三、第七步)必须逐项套用本文件的模板清单。
> **口径统一:** 全 SKILL 优先级统一 **P0 / P1 / P2 三级**(不用 P1–P5);正向 = happy path,反向 = 校验/异常/边界/权限/状态约束/并发。

## 一、覆盖矩阵(逐维确认,不适用须显式标注)

**强制规则:每个功能点必须逐一过一遍下列每个维度;某维度不适用时,必须在用例文档就地显式标注 `不适用 + 原因`,严禁静默跳过。**"某功能点只有正向用例"本身即为覆盖缺口。

### 1.1 正向维度(happy path,通常 P0/P1)

| # | 正向维度 | 覆盖要点 |
| :-: | :- | :- |
| F1 | 页面加载 | 各区域正确渲染(布局/数据/默认状态/加载态) |
| F2 | 列表与展示 | 数据格式、排序、分页、视图切换、字段展示 |
| F3 | 筛选与搜索 | 单/多条件筛选、搜索触发时机、结果正确、重置 |
| F4 | 创建/新增 | 表单打开、必填合法提交成功、数据回显入列 |
| F5 | 编辑/修改 | 修改保存、持久化、状态更新、回显一致 |
| F6 | 删除 | 二次确认、删除后列表更新、关联数据处理 |
| F7 | 状态流转 | 每一条**合法迁移**路径都有用例(见第四节) |
| F8 | 导航与路由 | 页面间跳转、面包屑、路由参数、返回/前进 |
| F9 | 交互反馈 | 按钮反馈、Toast、弹窗、loading、置灰/置亮 |

### 1.2 反向维度(校验/异常/边界/权限,通常 P1/P2)

| # | 反向维度 | 覆盖要点 |
| :-: | :- | :- |
| R1 | 必填校验 | 必填留空提交被拦截 + 明确提示文案(逐字段) |
| R2 | 长度/格式限制 | 超长、超短、格式错误(见第二、三节 BVA/等价类) |
| R3 | 全空白输入 | 仅含空格的必填字段识别为无效 |
| R4 | 网络/请求失败 | 断网/超时:Toast 提示 + 保留已输入 + 可重试 |
| R5 | 空数据/无结果 | 列表空态、搜索无结果、空态引导操作 |
| R6 | 权限不足 | 未登录访问、越权角色访问、URL 直连被拦截 |
| R7 | 弹窗三种关闭 | 关闭按钮 / 点击蒙层 / ESC 三种方式均须测 |
| R8 | 服务端错误 | 5xx 友好提示,不暴露技术堆栈/SQL/异常栈 |
| R9 | 状态约束 | 非法操作被拒(见第四节非法迁移),如"已上架不可编辑" |
| R10 | 并发/竞态 | 重复提交、乐观锁冲突、他人已删等(见第五节) |
| R11 | 安全输入 | XSS/SQL 注入/特殊字符被转义或拦截(PRD 有要求时) |
| R12 | 依赖/数据源故障注入与降级提示 | 功能点聚合 ≥2 数据源 / 存在兜底返默认值逻辑时:逐数据源注入 **下游 500 / 超时 / 空返回** → 页面须**显式失败提示 / partial 标记**,**禁静默显示 0/空**;**必须与 R5 真空态用例配对**,验证"真空态(真没数据)"与"故障静默返空(数据源挂了)"两者的**页面表现可区分**(否则"用量为 0"与"真没数据"无法辨别) |

> **不适用标注示例:** `R7 弹窗三种关闭 — 不适用(本功能点无弹窗)`;`R10 并发 — 不适用(单用户只读页,无写操作)`;`R12 故障注入 — 不适用(功能点仅取单一数据源、无兜底返默认值逻辑)`。
> **R12 vs R4/R8/第三方降级 的边界:** R4=网络/请求整体失败、R8=服务端 5xx、第三方降级=外部系统不可用,三者都是"请求层能看出出错";R12 专治**后端返 200 但内部某数据源被静默兜底成 0/空**——请求成功、页面有数字,只有故障注入才能测出,与前三者不重叠。

## 二、边界值分析(BVA)清单

对每个受约束的输入字段,取**边界内外各一点**(标准六点法),缺一即视为边界覆盖不全。

### 2.1 数值型字段(min ≤ x ≤ max)

| 取点 | 说明 | 期望 |
| :- | :- | :- |
| min-1 | 下界外 | 拒绝 + 提示 |
| min | 下界 | 接受 |
| min+1 | 下界内 | 接受 |
| 典型中间值 | 正常值 | 接受 |
| max-1 | 上界内 | 接受 |
| max | 上界 | 接受 |
| max+1 | 上界外 | 拒绝 + 提示 |
| 0 / 负数 / 空 | 特殊值 | 按规则(金额/数量通常拒负) |

### 2.2 长度型字段(字符串,长度 0 ≤ len ≤ N)

| 取点 | 期望 |
| :- | :- |
| 空(len=0) | 必填→拒绝;选填→接受 |
| 1 字符 | 接受 |
| N 字符(上限) | 接受 |
| N+1 字符(超长) | 前端截断或拒绝 + 提示,**不静默交后端报错** |
| 纯空格 | 必填按无效处理 |
| 含前后空格 | 按 trim 规则(须与设计一致) |

### 2.3 日期/时间型字段

| 取点 | 期望 |
| :- | :- |
| 边界日(区间起/止当天) | 按"含/不含"规则(左闭右开须与设计一致) |
| 区间外一天 | 拒绝 + 提示 |
| 跨年/跨月边界 | 正确计算 |
| 闰年 2-29 | 正确 |
| 远期/远古日期 | 按业务上限(如不允许未来出生日期) |
| 起始 > 结束 | 拒绝 + 提示 |

### 2.4 列表/集合型

空列表(0 条)/ 1 条 / 满页临界(如每页 20,取 20、21)/ 超大数据量(如 1000+,验证分页与性能不崩)。

## 三、等价类划分示例库(有效类 + 无效类枚举)

常见格式字段直接套用。**每个字段至少 1 条有效类 + 覆盖下列每类无效类各 1 条。**

| 字段 | 有效类(接受) | 无效类(逐条须拒 + 提示) |
| :- | :- | :- |
| **手机号** | `13800138000`(11 位 1 开头合法号段) | 10 位/12 位、非 1 开头(`23800138000`)、含字母、含空格、空、`+86` 前缀(按规则) |
| **邮箱** | `user@example.com` | 无 `@`、无域名(`user@`)、无用户名(`@x.com`)、双 `@`、中文、含空格、超长本地部分 |
| **URL** | `https://a.com/p?x=1` | 无协议(`a.com`)、非法协议(`javascript:`)、含空格、只有协议(`https://`) |
| **身份证** | 18 位合法(校验位正确) | 15 位旧版按规则、17 位、末位校验位错、含字母(非 X 位)、出生段非法日期(`20001332`) |
| **金额** | `100.00`、`0.01` | 负数(按规则)、超 2 位小数(`1.234`)、非数字、千分位逗号(`1,000`)、超上限、`0`(按业务) |
| **密码** | 符合强度规则(如 8-20 位含大小写数字) | 过短、过长、纯数字、纯字母、含非法字符、与用户名相同、空 |
| **百分比/比例** | `0`~`100` | 负、`>100`、非数字、超小数位 |
| **枚举/下拉** | 合法枚举值之一 | 越界值(前端应无法选到,API 直连须拒)、空 |

> 无对应现成格式的自定义字段,按 PRD/详细设计的校验规则自行拆有效类 + 无效类,原则同上。

## 四、状态机迁移矩阵模板(合法 + 非法双向枚举)

**只测正向流转是最常见的漏洞。** 对每个有状态的对象(订单/工单/审批/上下架/启停…),须画一张迁移矩阵,**合法迁移逐条正向用例**,**非法迁移逐条"被拦截"反向用例**。

### 4.1 模板

| 起始状态 \ 目标状态 | 状态A | 状态B | 状态C | 终态 |
| :- | :-: | :-: | :-: | :-: |
| **状态A** | — | ✅合法 | ❌非法 | ❌非法 |
| **状态B** | ❌非法 | — | ✅合法 | ✅合法 |
| **状态C** | ❌非法 | ❌非法 | — | ✅合法 |

- **✅合法迁移** → 每格 1 条正向用例:执行触发操作 → 状态标签/徽章正确变更 + 列表同步刷新。
- **❌非法迁移** → 每格 1 条反向用例:验证入口不可达(按钮置灰/不出现)或强制触发(API 直连/URL)被拒 + 提示,**状态不变**。
- **幂等/重复触发**:对同一合法迁移重复触发(如重复"提交"),验证不产生重复副作用。

### 4.2 示例(订单:草稿→待支付→已支付→已完成 / 已取消)

- 合法:草稿→待支付(提交)、待支付→已支付(支付)、待支付→已取消(取消)、已支付→已完成(收货)。
- 非法(须拒):草稿→已支付(跳过支付)、已完成→已取消、已取消→已支付、已完成→编辑。

## 五、并发/竞态清单

写操作功能点(创建/编辑/删除/状态流转)须逐条核对下列竞态场景是否适用,适用则出用例:

| # | 竞态场景 | 用例要点 | 期望(可见现象) |
| :-: | :- | :- | :- |
| C1 | **重复提交** | 快速双击提交 / 提交中再次点击 | 按钮置灰或防抖,只产生 1 条记录,无重复 |
| C2 | **乐观锁版本冲突** | 用户A、B 同时打开编辑,A 先保存,B 再保存 | B 收到"数据已被他人修改,请刷新"提示,不覆盖 |
| C3 | **他人已删除后再操作** | A 打开详情,B 删除该记录,A 再保存/操作 | A 收到"记录不存在/已被删除"提示,不报错崩溃 |
| C4 | **锁超时/长事务** | 占用编辑锁超过锁超时时长后再提交 | 提示锁失效需重新获取,不静默丢失 |
| C5 | **多标签页一致性** | 标签页1修改,标签页2刷新 | 标签页2显示最新数据 |
| C6 | **并发库存/额度扣减** | 两请求同时扣减同一有限资源 | 不超卖/不透支,一方成功一方拒绝 + 提示 |

> 竞态现象若纯后端不可见,须借助"刷新后列表/详情的可见变化 + 提示文案"来断言,不写"数据库加锁"这类不可视断言(遵守核心原则 7)。

## 六、用例数量基线 + 优先级分布(完备性下限)

### 6.1 数量基线(按模块规模)

| 模块规模 | 页面数 | 参考条数 |
| :- | :- | :- |
| 简单模块 | 1–2 页 | **30–60 条** |
| 中等模块 | 3–5 页 | **80–150 条** |
| 复杂模块 | >5 页 / 多角色 / 多状态机 | **150+ 条** |

- **单功能点下限:** 每个功能点 **≥ 3 条**(1 条正向主流程 + ≥2 条反向/边界);列表/表格/表单功能点在此之外**额外 +1 条**字段逐列核对用例(见 SKILL 第五步之二 / 维度 17)。
- **硬护栏:** 单模块用例数低于上表下限,或全量集合 < 20 条,**必须在文档「用例统计摘要」中说明原因**(可能存在覆盖遗漏),否则维度 19 不通过。

### 6.2 优先级分布(P0/P1/P2 目标占比)

| 优先级 | 定义 | 目标占比 |
| :-: | :- | :-: |
| **P0** | 核心功能正向(冒烟):核心 CRUD、页面加载、核心业务闭环 | 约 15–25% |
| **P1** | 重要分支正向 + 核心反向:重要交互、核心必填/校验、核心异常路径 | 约 45–55% |
| **P2** | 边缘/低频正反向:输入边界、弹窗关闭方式、空数据、兼容性、极端场景 | 约 25–35% |

- **反向占比下限:** 反向用例(校验/异常/边界/权限/状态约束/并发)应 **≥ 全量用例的 40%**——正向 happy path 占比过高即为完备性不足。
- 分布偏离目标区间不强制拦截,但须在统计摘要中标注并说明合理性。

## 八之二、语义断言提示(配合自动化执行,可选)

> **本节是「语义断言 DSL」的唯一信源**;SKILL.md「测试设计方法论速查」只放入口摘要,不重复展开。

用例的"预期现象"是自然语言,由人或 AI 临场判定;当用例交下游 `auto-test-runner` skill 做自动化执行时,`observe` 拿到的是结构化快照,**计数 / 状态迁移 / 字段核对最易判错**。为此,**关键断言步骤除自然语言"预期现象"外,可附一行机器可判的语义断言**(仍用页面可见文案,不是选择器)。该 DSL 与 `auto-test-runner` 的 `usecase-format.md` **完全一致(两 skill 统一契约,逐字采用)**:

```
【语义断言 DSL(两 skill 统一契约,用页面可见文案,禁选择器/字段名/xpath)】
在用例"预期现象"之外,关键断言步骤可附一行机器可判的语义断言:
  格式  `断言: <断言表达式>`   反向用例用  `断言(反向): <断言表达式>`
支持的断言表达式:
  - 存在文本"X"                     页面可见区域出现文案 X          例:断言:存在文本"创建成功"
  - 不存在文本"X"                   页面不出现文案 X                例:断言:不存在文本"内部备注"
  - 列表行数+N / 列表行数-N / 列表行数=N   目标列表行数相对增减或等于  例:断言:列表行数+1
  - 字段"标签"显示为"值"            指定字段标签对应值              例:断言:字段"金额"显示为"1,234.00"
  - 状态由"A"变为"B"               状态文案迁移                    例:断言:状态由"待审核"变为"已通过"
  - 元素"文案"可点击 / 置灰 / 不可见     元素可交互态                例:断言:元素"提交"置灰
  - 存在错误提示"X"（反向）         反向用例校验错误提示            例:断言(反向):存在错误提示"必填"
规则:断言里的"标签/文案/状态"一律用页面可见语义文案,禁 CSS/xpath/DOM 选择器、接口字段名(与操作对象同规则)。
断言可选、增量附加:不写断言的步骤仍按自然语言"预期现象"由 AI 判定;写了断言的步骤由执行侧据断言做确定化判定。
```

### 探测类断言三项自检(强制)

当用例或配套脚本通过接口、文件、日志或其它外部信号**探测某项能力是否已交付**时,必须把断言标为「探测类」,并在用例文档中逐项登记「已实跑 + 反证样本」。这三项是断言产出前的硬性自检,不是提示语:

1. **方向——失败必须与合法空态可区分。** 探测脚本必须显式判 `success == false` / 非 2xx / 等价失败状态,失败时报告错误并退出非零;请求失败不得与"查询成功但结果为 0 条"使用同一种返回形态。空结果只能在请求成功且响应契约明确允许为空时成立。
2. **特异性——判据只能由目标变更触发。** 断言使用的特征短语或结构必须唯一指向被验证的变更;不得使用会被同段其它内容命中的通用子串。应记录特征的完整边界,并用邻近的相似文本验证不会误命中。
3. **有效性——按断言类型分档验证。** 第 1 条方向、第 2 条特异性对所有探测类断言全量强制;本条阳性对照按以下规则执行:
   - **必须做阳性对照(缺一不可,仍属硬性自检):** (a) 期望值为 0 的反向断言; (b) 式子含转义、正则或多条件组合; (c) 判据落在注释与代码混排的文件上。以上场景中必须构造一个必然命中的已知样本,当场运行并记录结果。
   - **可免阳性对照:** 期望值 > 0 的正向存在性断言,登记模板对应字段填写 `N/A（正向存在性断言，命中即自证）`;其正常样本命中本身即证明式子有效,不再重复构造阳性样本。
   - **共同要求:** 任何正常样本得到 0 命中都不能单独证明"没有交付";必须先确认失败态已区分,并按上述分档补做阳性对照或登记合法 N/A。

**探测类断言登记模板:**

```markdown
**探测类断言核验:**
- **探测目标:** <本次要验证的具体能力/变更>
- **失败态判定:** <success=false / 非 2xx / 等价失败状态的明确判据>;失败时 <错误输出 + 非零退出>
- **空态区分:** <成功空结果的合法形态> 与 <请求失败形态> 的差异
- **特征唯一性:** <仅指向目标变更的完整短语/结构>;相似文本排除验证: <样本与结果>
- **断言类型/期望值:** <反向零期望 / 含转义正则多条件 / 注释代码混排 / 正向存在性期望>
- **当场实跑:** 已实跑(时间/命令或脚本入口): <记录>
- **阳性对照:** <必然命中样本与实际命中次数> / `N/A（正向存在性断言，命中即自证）`
```

> **判定:** 探测类断言缺少失败态判定或特异性排除,不得据其 0 命中下"未交付/不存在"结论;必须阳性对照的类型缺少必然命中样本,或可免类型未登记规定的 `N/A`,同样标 `block` 或 `❓ 待澄清`。

**与核心原则 7「预期现象可观察」一致:** 语义断言只用页面可见信号(文案 / 列表行数 / 字段展示值 / 状态标签 / 元素可交互态 / 错误提示),**严禁**写"数据入库 / 缓存生效 / 日志记录"等后端不可视断言——不可视信号既不能人工核验、也无法被 `observe` 快照捕获。**适用位置:** 关键断言步骤(提交成功 / 列表增减 / 状态迁移 / 字段展示 / 校验拦截),不必每步都加;示范见 SKILL 两个用例模板的关键步骤。

### 变异对照:证明「这条用例守的就是那个行为」(与阳性对照是两回事,⛔ 勿合并)

> **两者证明的东西不同,缺一不可:**
> - **阳性对照** 证明的是:**式子能红**(去掉限定条件后确实会命中)。
> - **变异对照** 证明的是:**这条用例守的就是那个行为**(把实现改回缺陷原状,该用例**精确失败**)。
>
> 一条断言可以**阳性对照通过、变异对照失败**——它能红,但守的不是你以为的那件事。

**真实失效(下游连报两次同一缺陷):** 一条 `assertFalse(旧方法(某类型))` 放在「去重判据」分组里,
被当成该行为的期望。**对该方法的语义而言这条断言完全成立**,所以它一直是绿的;
可**判据换掉之后,它不再守任何东西**——去重行为没了守卫,缺陷照常上线,产品连报两次才被发现。

**三条规则:**

1. **断言绑行为,不绑方法名。** 断言必须放在**它所守护的那个行为**对应的分组里;
   **某方法不再是该行为的判据时,断言必须迁移到新判据上**,⛔ 不是留在原地继续绿着。
2. **换判据的提交必须同时出现「新判据的回归断言」**,否则判 **Critical**。
   ⚠️ 这一条是上一条的可执行形态:「应该迁移」是意愿,「换判据的那次提交里必须能看到新断言」是事实。
3. **关键行为的断言必须做变异对照** —— 把实现**改回缺陷原状**,确认该用例**精确失败**
   (失败在它该失败的那一条断言上,不是别处报错、也不是整体崩)。**变异未被抓到 = 该断言无效**,
   与「根本没写」同档。

**⭐ 与零残留断言的关系(别重复登记):** 对「不存在文本 X」形态的零残留断言,
**变异对照 ≡ 方向二·阳性对照** —— 把删掉的那段文本加回去,就是「改回缺陷原状」。
故**零残留断言登记表不为此新增列**;本节真正新增的适用面是**行为判据类断言**
(去重 / 状态迁移 / 权限拦截 / 归并 / 兜底降级),它们不是「不存在文本 X」形态,
在既有机制里没有任何位置。

**登记形态(写在用例的「变异对照」小节,不进步骤表):**

```markdown
**变异对照:**
- **守护的行为:** <一句话,写行为不写方法名,如「同一 skuId 的多条订阅在卡片列表里只出现一次」>
- **当前判据:** <该行为现在由什么保证,如 `dedupBy(skuId)`>
- **变异操作:** <怎么把实现改回缺陷原状,如「移除 dedupBy 调用」>
- **变异结果:** 用例 <TC-XXX-NNN> **精确失败**于 <哪一条断言>;恢复后通过。日期 <YYYY-MM-DD>
```

⚠️ **「精确失败」不能弱化成「失败了就行」。** 变异后整体报错 / 前置就崩 / 失败在别的断言上,
都**不能**证明这条用例守着那个行为——它可能只是碰巧被同一处改动带崩了。


### 零残留断言的实跑口径:默认排除注释行(通用前置,强制)

> **适用面:** 一切「**不存在文本 X**」形态的反向断言(`[反向-残留]` + `[文案一致性]` 反向用例,
> 统称「零残留断言」)在**登记期当场实跑**时的过滤口径。登记表三字段与退役规则见
> `quality-review-checklist.md` 维度 18「零残留断言登记表」子条,本节只管**式子怎么跑**。

**🛡️ 为什么是通用前置而不是各条自己想起来加:** 实际项目中实测一轮 8 条
零残留断言,**初稿 5 条假红,全部同一根因——命中的是本 Sprint 自己写的注释**:防回退注释
(「⛔ 不加合计行」)、变更留痕注释(「旧文案是……」)、给后续维护者的告诫(「别按老印象改回 X」)。
**订正式子即可,一行业务代码没改**——真要按初稿结论去"修",删掉的恰恰是那些防回退的注释。
五条以完全相同的方式失效,说明它是**模式不是偶发**,只能靠默认前置一次性消除。

**取材方式有两种,默认用第一种**(判据全文见本节下方「⭐ 默认取材方式:块级剥离」):

| 方式 | 命令 | 何时用 |
| :- | :- | :- |
| **① 块级剥离(默认)** | `python3 <SKILL_DIR>/scripts/strip_comments.py '<守护面>' \| grep -E '<式子>'` | 一律优先 |
| ② 行级 grep 前置(退路) | `grep -rnE '<式子>' <守护面> \| grep -vE '^([^:]*:)?[0-9]+:[[:space:]]*(//\|\*\|/\*\|<!--)'` | 跑不了 Python / 临时看一眼 |

⚠️ **走退路时必须在登记表「实跑命令」列写明用的是行级前置**——它有三个确定的漏面
(块中间行 / 跨行块中间行 / 行尾注释),不写明就无法判断结论可不可信。

⚠️ **退路方案的三条实测事实**(实跑复核,勿凭直觉改回;块级剥离已把这三条全部内建):

1. **必须锚定到「行号冒号之后」,不能只写 `:[[:space:]]*(//|…)`。** 后者会把
   `src/D.ts:5:const url = "https://api/合计行"` 这类**含 URL 的行整行静默丢掉**——`://` 正好命中
   `:` + `//`。方向是**假绿**(真命中被吞),是三条里唯一会掩盖缺陷的一条。
2. **必须带 `-n`。** 不带 `-n` 时 grep 输出是 `path:content`,锚定式的 `[0-9]+:` 匹配不上,
   **过滤器整体失效、一条都不过滤**。方向是假红(安全侧),但会让人误以为前置写坏了;
   而 `-n` 本来就要用来记命中行号进「反向复现片段」,没有不带的理由。
3. **`\*` 那一支会连带丢掉 C 系指针解引用行**(`    *ptr = 合计行;` 被判成 javadoc 续行)。
   C/C++ 项目须去掉 `\*` 分支并改用 `/*`+`*/` 配对判断;Java/TS/Vue 项目保留(块注释续行更常见)。

### 前缀集按守护面涵盖的文件类型选(固定表,⛔ 不要各自摸索)

> **🛡️ 为什么固定成表:** 下游实测该根因**跨 4 个版本复发 5 次**(连续多个 Sprint),而**第 5 次的直接原因是"项目自己加的排除集漏了一项"**——
> 让每个项目各自摸索前缀集,等于把同一次踩坑复制到每个项目。下表是全部合法分支,照查即可。

| 守护面涵盖的文件类型 | 追加分支 | 说明 |
| :- | :- | :- |
| Java / Kotlin / TS / JS / Vue `<script>` / Go / SCSS / LESS | `//` `/\*` `\*` | **⭐ 默认集**(上面那条命令用的就是它) |
| HTML / Vue `<template>` / XML | `<!--` | 已含在默认集里 |
| **Markdown(`.md`)** | `<!--`,但**必须去掉 `\*`** | ⚠️ 见下面「Markdown 守护面」那条实测,**假绿** |
| Shell / Python / YAML / Dockerfile / .properties | `#` | ⚠️ **守护面同时含 `.md` 或 `.css/.scss` 时禁止加**,见下 |
| SQL | `--` | ⚠️ 守护面含 `.md` 时会连带丢掉 `---`(YAML front-matter / 分隔线) |
| C / C++ | **去掉** `\*` | 见上面第 3 条实测事实 |

**⭐ `/\*` 已经同时覆盖 `/*` 与 `/**`,⛔ 不要另加一条 `/\*\*` 分支。** 它是**前缀匹配**不是全串匹配,
`/**` 的头两个字符就是 `/*`。实测:单行 JSDoc `    /** ⛔ 别按老印象改回 X */`、多行 JSDoc 的首行
`/**`、续行 ` * …`、收尾行 ` */` **四种形态全部被默认集过滤掉**。下游第 5 次复发的直接原因
(「前缀集漏了单行 JSDoc `/**`」)**在本节这个形态下不存在**——若你写的式子漏了它,
说明用的不是本节的锚定形态,回去对一下第 1 条实测事实。

⚠️⚠️ **守护面含 `.md` 时必须去掉 `\*`——和 C/C++ 是同一条,方向同样是假绿。**
`\*` 那一支匹配的是「行首若干空白后紧跟一个 `*`」,而 Markdown 里**列表项 `* 文本`** 与
**整行加粗 `**文本** …`** 恰好都是这个形状。实跑复核(GNU grep 3.11,同一批 fixture):

```
docs/F.md:1:# 合计行 标题          → 保留
docs/F.md:2:* 合计行 列表项        → ★ 被默认集静默吞掉
docs/F.md:3:**合计行** 加粗行      → ★ 被默认集静默吞掉
docs/F.md:4:- 合计行 短横列表      → 保留
docs/F.md:5:普通行 合计行          → 保留
docs/F.md:6:<!-- 合计行 注释 -->   → 被吞(正确,`<!--` 分支生效)
```

被吞的两行都是**会被用户看见的正文**,与 `#`/`--` 那条是同一类风险,只是它藏在**默认集里**、
不需要谁"额外加一项"就会中招。⚠️ 影响面比看上去大:模板示例里 Z-02 那种「全站不得出现」的断言
守护面写的是 `**`,**天然覆盖仓库里所有 `.md`**;守护面写 `docs/**` 的同理。
**处置:守护面涵盖 `.md` 时分两次跑**——代码面用默认集,文档面用去掉 `\*` 的变体,并在登记表
「实跑命令」列写出那条变体式子 + 理由(与「混合守护面分两次跑」是同一条操作,不是新规矩)。
⛔ 不要改成「只匹配 `* ` 后跟非空格」之类的收窄——JSDoc 续行 ` * 文本` 与 Markdown 列表项
`* 文本` **字面完全一致**,靠行级 grep 分不开——这是**行级退路**必须接受的代价。
⚠️ **本条只适用于退路**:默认取材方式已改为块级剥离 `strip_comments.py`,它对 Markdown
只剥 `<!-- -->`、列表项与整行加粗照样留下,**根本不存在这个代价**
(旧版这里写的是「本节刻意只给行级 grep 前置、不配脚本」,那句话在脚本落地后已作废)。

⚠️ **`#` 与 `--` 不进默认集,是因为它们在部分文件类型里是「会被用户看见的内容」。** 实测:
加上 `#` 分支后,`docs/F.md:2:# isEnterpriseOpened 标题`(Markdown 标题)与
`src/G.css:5:#isEnterpriseOpened { … }`(CSS id 选择器)**两行一起消失**——若这条断言查的正是
「这个 id 该删了」,唯一的真命中就被静默吞掉了,方向是**假绿**。
**判据:按守护面选,不按项目选**——同一个项目里,守护面只含 `.java` 的断言该加 `#`,
守护面含 `docs/**` 的断言就不该加。**混合守护面拿不准时分两次跑**(代码面一次、文档面一次),
⛔ 不要图省事上全集。改动或关闭默认集时,须在登记表「实跑命令」列写出完整式子 + 理由。

**⭐ 默认取材方式:块级剥离(`strip_comments.py`),⛔ 不再以行级 grep 前置为默认。**

```bash
# 方向一·现状实跑(期望 0 命中)
python3 <SKILL_DIR>/scripts/strip_comments.py '<守护面 glob>' | grep -E '<断言式子>'
# 断言目标本身就是注释内容时,反过来只扫注释
python3 <SKILL_DIR>/scripts/strip_comments.py --only-comments '<守护面 glob>' | grep -E '<断言式子>'
```

输出形态是 `路径:行号:正文`(与 `grep -rn` 一致),**行号守恒**——「反向复现片段」照旧记得下来。

⚠️ **为什么换掉行级前置:它有三个确定的漏面,而旧口径字样恰恰最爱躲在里面。**

| 漏面 | 行级前置 | 块级剥离 |
| :- | :-: | :-: |
| (a) `/* … */` 块里**不以 `*` 开头**的中间行 | ❌ 漏 | ✅ 剥掉 |
| (b) `<!-- … -->` **跨行块**的中间行(Vue / HTML 模板高发) | ❌ 漏 | ✅ 剥掉 |
| (c) **行尾注释** `doIt(); // 旧口径XXX` | ❌ 漏 | ✅ 剥掉 |
| 字符串里的 URL(`"https://api/x"`) | ❌ **整行吞掉(假绿)** | ✅ 保留 |
| Markdown 列表项 `* 文本` / 整行加粗 `**文本**` | ❌ **吞掉(假绿)** | ✅ 保留 |

实跑复核(同一批 fixture):A.ts 的块中间行 / 行尾注释 / 单行 JSDoc、B.vue 的跨行块中间行、
D.sql 的 `--` 注释**全部被剥掉**;而 A.ts 的 URL 字符串行、C.md 的标题 / 列表项 / 整行加粗、
D.sql 的 `SELECT` 语句**全部保留**。

**它的判据只有一条:宁可少剥(留下 → 假红 → 人看一眼排除),绝不多剥(剥掉 → 假绿 → 缺陷溜过去)。**
由此派生几条刻意的保守取舍(**均由脚本实现兜住,不靠人记**):

| 取舍 | 为什么 |
| :- | :- |
| `#` 默认不当注释;`--hash` **只对 Shell/Python/YAML 等 `HASH_FAMILY` 扩展名生效** | Markdown 标题 / CSS id 是**会被用户看见的内容**。⚠️ 早期 `--hash` 是**全局**开关,加了它 `.md` 标题与 `.css` id 选择器会一起消失(假绿),靠一句「守护面含 `.md`/`.css` 时不要开」防不住 |
| Markdown 只剥 `<!-- -->`,且 **``` 代码围栏内一律不剥** | `*` 开头是列表项、`**文本**` 是整行加粗;围栏里的 `<!--` 是**被展示的字面量**(本节自己就拿它举例),当成注释会开出跨几十行的块把正文整段吞掉 |
| 闭合串在整份文件里找不到时,`/*` 与 `<!--` **都不当注释开头** | 未闭合的开头几乎总是「文档在引用这个字面量」,照开会让其后**整份文件**静默消失 |
| 反引号跨行状态**只对 TS/JS 与 `.vue` 的 `<script>` 段**保留 | 那里反引号才是多行模板串;md 的 ``` 围栏会让跨行奇偶性失真 |
| **Markdown 里只认「行首 `<!--`」**,行中的一律不当注释 | md 的行内代码段靠反引号配对,而文档讲代码围栏时必然写出 ``` 这种**奇数个反引号**的字面量,它让本行后续反引号配对**整体错位**,于是一个本被保护的 `<!--` 跑到保护之外、开出跨行注释块。实测把本文件 435~437 行(一张表的三行正文)整段吞掉,方向是**假绿**。判据依据:全仓 182 份 md 里 `<!--` 出现 21 次、**只有 2 次在行首**,而那 2 次正是唯一真的注释块 |
| `://` 不作行注释起点 | 覆盖不带引号的 URL(CSS `url(https://…)`、模板串续行里的裸 URL) |
| `.vue` 按段处理:`<script>`/`<style>` 走 C 家族,`<template>` 只认 `<!-- -->` | 不分段的话 Vue 里最常见的 `<script>` 行注释一条都剥不掉(纯假红,而 `.vue` 恰是守护面里最典型的文件类型) |
| **未识别扩展名一律不剥**(`.txt`/`.csv`/`.json`/`.log` …),stderr 出一行提示 | 反过来做是**假绿**:`.txt` 里的 `plain // 旧口径XX` 会整段消失,而「全站不得出现」类断言的守护面写的正是 `**`、天然覆盖这些文件 |
| Python 三引号文档串不剥 | 它也可能是被展示的模板字符串,分不清就不剥 |

**保留行级 grep 前置作退路**(项目里跑不了 Python、或只想临时看一眼时):

```bash
grep -rnE '<断言式子>' <守护面> | grep -vE '^([^:]*:)?[0-9]+:[[:space:]]*(//|\*|/\*|<!--)'
```

⚠️ 用退路时,**登记表「实跑命令」列必须写明用的是行级前置**——上表 (a)(b)(c) 三个漏面随之存在,
而它们的方向是假红(可接受);但 `\*` 分支对 Markdown 是**假绿**,守护面涵盖 `.md` 时**必须去掉它**
(见上文「前缀集按守护面涵盖的文件类型选」小节)。⛔ 不写明用了哪种剥离方式 = 无法判断结论可不可信。

**⛔ 取代码段一律用块级解析或整文件扫,禁用「起止标签行范围」。**
模板语言(Vue SFC / JSX / HTML)常有**同名嵌套标签**,`sed -n '/<template>/,/<\/template>/p'`
这类**行范围**取段会在**第一个内层闭合标签处提前截断**,后半段根本没进入匹配。
下游真实发作:换一种取段方式后**阳性对照返回 0**,才发现式子彻底坏了——
⚠️ 注意这个失效的形态:**方向一照样是 0 命中(看着像通过)**,只有方向二把它暴露出来,
这也是「两个方向都要跑」不能省的又一条理由。本 SKILL 的 `strip_comments.py` 整文件扫、不做区间截取。

**⛔ 必须只扫注释的场景:断言目标本身就是注释内容。** 例如「被判作废的 REQ 编号,其代码注释处
是否已标注『该需求已于 {version} 作废』」「旧口径的变更留痕注释该不该清」——这类断言用
`--only-comments`(退路方案里则是把 `grep -v` 换成 `grep -E`)。**须在登记表「实跑命令」列就地写明理由**,
否则与"忘了加"无法区分。

**⚠️ 另一类假红不是注释问题,别混为一谈:** 同批实测里另有一条初稿命中 15 处,根因是断言文本
`PERSONAL` 作为 `ZONE_PERSONAL` / `OrderChannelEnum.PERSONAL` 的**子串**被命中——这属于
**上文「探测类断言三项自检」第 2 条「特异性」**(判据只能由目标变更触发,须用邻近相似文本验证
不会误命中),靠加词边界 / 补全上下文短语解决,**换多好的剥离器都没用**。把两类假红混为一谈,
结果是一边换工具一边仍然满屏命中。

## 八之三、跨模块集成闭环(触发条件 → 必生成集成用例)

> **本节是「集成用例触发条件」的唯一信源**;SKILL.md「第五步之四:跨模块集成用例生成」只放入口摘要,不重复展开。

单模块测试套件覆盖"模块内功能点";但**跨 ≥2 个模块/套件的端到端业务闭环**(数据在模块间流转、状态跨模块迁移)若无专门用例,就成了覆盖盲区——下游 `auto-test-runner` 备了 `self-heal` 模式承接集成/跨模块用例,本 skill 必须有对应生成章节以对称供需。

| 触发条件(命中即须生成集成用例) | 必生成的用例类型 | 侧重方法论维度 |
| :- | :- | :- |
| 一条业务闭环**横跨 ≥2 个模块/套件**,上游模块产生的数据/状态被下游模块消费(如"下单→支付→发货→通知"、"审批发起→多级审批→归档"、"报销提交→审批→财务打款") | **集成套件**(`SUITE-INT-*` 或标题标注"集成"),用例元信息**类型标注为「集成」**;步骤跨模块连续走通,预期验证**跨模块数据/状态一致性**(上游产生的数据在下游模块正确呈现、状态正确流转) | 状态机跨模块迁移(第四节)+ 数据闭环完整性 |

- **与套件模型关系:** 集成套件**不破坏**现有单模块测试套件组织,是其**补充**——单模块套件覆盖模块内功能点,集成套件覆盖跨模块闭环,两者并存。
- **类型对齐下游:** 用例「类型」写「集成」,让 `auto-test-runner` 识别为集成/跨模块 → 走 `self-heal` 模式。
- **断言:** 集成用例的跨模块一致性断言优先用本文件「八之二」语义断言(如 `断言:状态由"待发货"变为"已发货"`、`断言:列表行数+1`),仍限页面可见信号。

## 八之五、语义/口径变更类文案一致性用例族(`[文案一致性]`,消费「表 E」/「文案落点表」→ 含反向断言的文案一致性用例)

> **本节是「语义/口径变更文案一致性用例族」的唯一信源**;SKILL.md「测试设计方法论速查 ⑬」与「第五步之八」只放入口摘要,不重复展开。**本增强整体可选、向后兼容:无语义/口径变更需求时不触发,现有流程完全不受影响。** 本族**复用**"原型内容基线反向断言"的同一条 DSL(`断言(反向):不存在文本"X"`),是其在**文案维度**的延伸,不另造平行体系。

### 8-5.1 背景与根因(实际项目缺陷)

用量消费统计口径由「仅企业」扩为「企业+个人」,后端 / 接口 / 前端取数**全改对**,但 6 处解释该数值的 tooltip 有 1 处漏改、仍写"仅统计企业级、不含员工个人消费",与实际展示值**相反**、误导对账(P1)。**AI 测试全绿未抓到——因为用例只断言数值、不断言文案。** 根因:语义 / 口径变更时,数值取数改对 ≠ 所有解释该值的说明文案都同步改对;且**正向断言(查新口径字样存在)易被"文案里恰好有个『含』字"蒙混,只有反向断言(查旧口径字样是否残留)才能确定性拦截漏改的旧文案**。

### 8-5.2 触发条件与展示位口径

| 触发条件(命中即须生成) | 覆盖对象 |
| :- | :- |
| 上游有「**表 E:语义变更→派生展示物影响清单**」(`变更项\|变更前语义\|变更后语义\|受影响展示物\|处置\|新文案`)或「**文案落点表**」(`#\|文件路径\|展示位\|改前文案\|改后文案`);或 PRD/详设命中"口径变更/统计范围调整/含义扩缩/语义变更" | 每个**处置=改写的展示位**——一切"解释该数值口径含义"的说明文案:tooltip / 副标题 / 图例 legend / 帮助气泡 / 空态提示 / 列说明 / 单位注释 等 |

### 8-5.3 三类用例(类型标 `[文案一致性]`)

| 用例类型 | 断言 | 「反向」字段 | 说明 |
| :- | :- | :-: | :- |
| **正向** | `断言:存在文本"<新口径字样>"`(如"含员工个人") | 否 | 文案已体现新语义;新口径字样取自「表 E」变更后语义 / 「文案落点表」改后文案 |
| **反向(Critical,判失败关键)** | `断言(反向):不存在文本"<旧口径字样>"`(如`不存在文本"仅统计企业级"`、`不存在文本"不含员工个人"`) | 是 | **旧口径字样残留即 Fail**;旧字样取自「表 E」变更前语义 / 「文案落点表」改前文案,逐个各出一条(或一条多行断言)。**与 `[反向-残留]` 用同一「不存在文本"X"」DSL、同一判失败语义** |
| **一致性** | 文案声明口径 ⟷ 该处数值实际取数口径交叉验证(可附 `[双源对账]` 等价 SQL,按新口径统计,断言页面值 == SQL 值) | 否 | 验证"文案说的口径"与"数值真实取数口径"一致(如称"企业+个人"则数值应=企业+个人合计,非仅企业) |

### 8-5.4 生成规则与闭环

1. **逐处置读取** — 读「表 E」/「文案落点表」,逐条取处置=改写的展示位、其变更前/后语义(改前/后文案)。
2. **每展示位一组用例** — 生成正 + 反(Critical)+ 一致性;反向用例的"旧口径字样"逐个用 `断言(反向):不存在文本"X"` 覆盖。
3. **溯源** — 用例元信息加 `> **表 E 来源:** [...]` / `> **文案落点来源:** [...]`(markdown 链接 + 相对路径 + 锚点,格式同现有溯源)。
4. **覆盖闭环** — 每个处置=改写的展示位要么有一组 `[文案一致性]` 用例、要么就地标 `无对应可测展示位 — 不适用 + 原因`,不静默漏;**缺反向用例(只断言新文案存在、不断言旧文案不残留)即视作漏测根因未堵**。
5. **与 `[双源对账]` 协同(可选)** — 一致性用例落地统计/金额口径时,复用第五步之七的 `[双源对账]` 专段等价 SQL(含软删除/状态过滤),把"文案口径"锚到"数值真实口径"。

## 八之六、上游调用「日志可追溯」断言(`[日志可追溯]`,**本次新增/改动出站调用时**追加 · 通用规则 约定40)

> **本节是「上游调用日志断言」的唯一信源**;[`flow-step5-coverage.md`](./flow-step5-coverage.md)「第五步之十」只放入口摘要 + 用例结构示例,不重复展开判据。
> **本增强整体条件触发、向后兼容**:本次没动出站调用时不触发,现有流程完全不受影响。

### 8-6.1 背景与根因

同一项目里 **4 个上游客户端写出 4 种日志规格,另有 2 个直接漏掉**。根因不在编码期,而在
**详细设计从来没写过**"这个上游调用要打哪些日志、哪些字段脱敏"(上游 `dev-logic-architect`
已用检查项 35 的「上游调用日志与脱敏声明表」堵设计侧)。测试侧要堵的是另一半:
**只测失败路径的日志会全绿通过** —— 真实缺陷正是「**只有出事才出声**」。

### 8-6.2 触发条件与适用边界(窄口径)

- **触发** = 本次迭代**新增或改动**了出站调用(第三方 HTTP API / 微服务 RPC·Feign / 对象存储 /
  短信邮件消息网关 / 支付鉴权中心)。
- **不触发** = 本地 DB、本地缓存;以及本次**没有改动**的既有出站调用(不必回头补,更不必全量铺开)。
- 有上游「上游调用日志与脱敏声明表」(architect 检查项 35)时,以表中**本轮新增 / 改动的那些行**为基准逐行生成。
  ⚠️ **不是整表逐行**——那张表登记的是该设计**全部**出站调用,与本族「仅本轮动过的」窄口径触发不是一回事;
  按整表铺开会与上一条触发条件直接打架(表里 6 行、本轮只动 1 个客户端时,生成方与 QR 方会得出相反结论)。
- 无该表则从详细设计 B.7 / 执行计划识别本轮改动的出站调用,
  并把「设计缺声明表」登记进待澄清问题清单(**不因为上游没给就跳过本族**)。

### 8-6.3 三条断言(固定,勿弱化)

| # | 断言 | 为什么不能删 |
| :-: | :- | :- |
| ① | **正向(成功场景)**:同一 traceId 的请求行与响应行成对存在;请求行含**完整 URL**(含 query string)+ method + 入参,响应行含 **status + 上游业务 code + 出参 + 耗时** | 事后追溯全靠这一对;缺任一半都无法回答"对方返回了什么 code、慢在哪一跳" |
| ② | **级别**:上述两行在**成功场景**下同样存在且为 **INFO** | **本族核心**。只测失败路径的日志会**全绿通过**却什么都没保障 |
| ③ | **反向(脱敏)**:`断言(反向):日志中不存在明文验证码 / 令牌 / 密钥 / 密码` | 真实样本里**短信服务在补日志之前就已经明文打印验证码**——补日志只会**放大**它 |

### 8-6.4 生成规则与闭环

- 类型标 `[日志可追溯]`(元信息「类型」+ 标题);断言写进「**日志可追溯**」专段,**不进步骤表**
  (该段已由 `check_testcase_format.py` 的 end-marker 从步骤表扫描区剥离,与「双源对账」同款——
  否则「`断言:日志中存在 "POST /v2/sms/send" 请求行`」这种最自然的写法会命中「HTTP 方法 + 路径」判 Critical)。
- **执行方式:本族仅人工 / 运维查服务端日志执行,⛔ 不进 `auto-test-runner` 自动化。** 该执行器的四原子能力
  (locate / act / observe / capture)全在 UI 面,**没有任何驱动能读服务端应用日志**(`[双源对账]` 为此专门加过
  DB 断言驱动通道,本族没有对应通道);⛔ 别在用例里写「供下游自动化识别」这类兑现不了的承诺。
- 可以是独立用例,也可以**在既有功能用例上追加一个专段**(后者更常见,不必硬造新用例)。
- 步骤里确需体现"去看日志"时,**动作动词只用既有白名单里的「观察」/「检查」/「记录」**
  (与 `[外部调用方]` 族同一处置思路:不动脚本、改用既有动词)。
- **本族对核心原则 1(能不能这么操作)与核心原则 7(能不能这么断言)各开一条窄口径例外、二者成对**
  ——照 `[双源对账]` / WebMCP `[外部调用方]` 先例。**缺任一条,本族就没有合法写法**:核心原则 7 原文
  明令禁止「日志记录」这类后端不可视断言,不就地破例则 QR 与人工评审读到的仍是「禁止」。
- **折进维度 18(覆盖矩阵逐维确认)判定**,不另立维度:本次新增/改动了出站调用却无任何
  `[日志可追溯]` 断言,或正向断言没落在成功场景上,均判缺口。

### 8-6.5 ★ 去重边界(硬约束)

确定性判据(出站调用类零日志 / 成功路径不可见 / 无一条日志提到 URL / 成功路径只有 debug /
疑似凭据明文入日志)由**被测项目侧**脚本 `<项目根>/.aidp/scripts/check_upstream_call_log.py`
承担(经脚手架下发、不在任何 SKILL 内),上游 `code-verification-loop` 的**维度 12** 负责委派它。
**本 SKILL 只加用例侧断言,⛔ 不重写那套静态判据**——同一判据两份实现是最高频漂移源。
