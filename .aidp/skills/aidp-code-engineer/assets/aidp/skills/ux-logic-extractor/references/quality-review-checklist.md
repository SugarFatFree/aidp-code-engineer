## QR 变更范围裁剪协议（Δ 协议）

> **解决什么：** 生成侧已有「增量 / 补充生成约定」的协作接口，但 15 维度 QR 没有对应概念——
> 补充一个模块，QR 仍按全量规格核对整份 PRD。

### 入参

调用方可在 QR 派发 prompt 里传 **`qr_delta_scope`**：本轮变更的**模块 / 功规点 / 页面清单**
（自然语言即可，须可核对到具体章节）。**不传 = 全量**，与协议上线前完全一致。

### 三档裁剪（对照上表最后一列）

| 档 | 语义核对怎么做 | 报告怎么写 |
| :- | :- | :- |
| **Δ** | 只对 Δ 内模块逐条核对，标准不降 | Δ 外标 `前滚（未变更）` + **写明依据的上一轮 QR 报告** |
| **全量** | 无论 Δ 多小都全量核对 | 恒标 `全量` |
| **基线缩放** | 覆盖率类：分母换成 Δ 内的功规点/字段集合 | **写明分母口径**（「分母 = 本轮 3 个模块的 21 个功规点，非全量 184 条」） |

### 四条安全网（缺一不可）

1. **语义/口径类变更强制扩散**：命中「语义 / 口径 / 单位 / 默认值 / 状态机 / 权限范围变更（无新增实体）」
   或跨版本作废判定 → 受影响模块**强制并入 Δ**，即便本轮没有新增章节。
   —— **本 SKILL 是这条契约的源头**（维度 14 的表 E / 表 F），下游 architect / dmtc / cvl 的同名安全网都以它为准。
2. **共享单元传播**：变更落在**跨模块共享单元**（全局字典枚举 / 公共字段 / 统一权限模型 / 全站统计口径）→
   **所有引用它的模块并入 Δ**。宁可多算一个模块，绝不漏传播一处语义。
3. **全量档不可裁剪**（★ 与下游原始提议的唯一实质分歧，理由见下）。
4. **算不出 Δ 就退回全量**并在报告首行注明退回原因。⛔ 严禁猜一个 Δ。

> **★ 为什么维度 13 / 14 / 15 必须留在「全量」档：**
> 维度 13 的表 A/B/C/D 是**下游字段对账的单一信源**——「某个字段本轮没登记去向」这种缺陷，
> 只有拿全量字段清单对才看得出，Δ 内部永远是自洽的；
> 维度 14 更直接：**它就是安全网 ① 的判定来源**，把它纳入裁剪等于让安全网自己失效——
> 而语义变更类需求的特征恰恰是「代码改了数值行为、页面零新增元素」，靠文件 diff 驱动的 Δ 必然漏掉它；
> 维度 15 同理：**一句没被核过的断言会被后续每一轮当既定事实引用**，它上一次进 PRD 可能是好几轮之前，只看本轮 Δ 一条都发现不了。

### QR 执行台账（报告强制段落）

| 维度 | 本轮范围 | 机器门退出码 | 语义结论 | 分母口径 / 依据 |
| :-: | :-: | :-: | :-: | :- |
| 5 | 基线缩放 | `check_req_upstream.py` = 0 | 通过 | 分母 = 本轮 21 个功规点（非全量 184 条） |
| 13 | **全量** | `check_requirement_field_inventory.py` = 0 | 通过 | 全量档：漏登记只有全量对账才看得出 |
| 14 | **全量** | `check_semantic_change.py` = 0 | 通过 | 全量档：它是安全网 ① 的判定来源 |
| 15 | **全量** | —（无脚本） | 通过 | 全量档：一句没被核过的断言会被后续每一轮当既定事实引用 |
| 8 | **N/A** | — | 未触发 | 本 PRD 无第三方对接章节（条件维度，未触发也留行） |
| 4 | 前滚（未变更） | — | 前滚 | 依据 2026-08-20 第 2 轮 QR 报告 |

**四条硬要求：**
- **15 行一行不少**——条件维度 8（第三方）/ 9（多文件）未触发时照样留行，写明 `N/A + 触发条件为何不满足`。
- 基线缩放档的行**必须**写出分母口径；只写百分比一律判该维度**未完成核验**。
- 标 `前滚` 的行必须写明依据的上一轮报告；写不出来按**未跑**处理、退回该维度全量核对。
- 机器门那列**照抄退出码**，不写「通过」二字——退出码是证据，「通过」是结论。

## 15 维度检查清单

### 检查项 1：异常路径覆盖

**检查目标：** 非理想状态下的处理方案是否完整定义。

**必须覆盖的场景：**
- 网络超时（请求超过 N 秒无响应的提示和重试机制）
- 加载失败（接口返回 5xx / 网络断开的**错误反馈**:错误 Toast/Message + 重试按钮,**严禁**写"显示替代数据/上次缓存/示例数据"等数据源兜底,见维度 12)
- 搜索无结果（空态文案和引导操作 — 这属于 C 类空状态 UI 推断,允许)
- 数据获取异常（列表加载失败、详情页数据缺失 — 仅描述错误反馈与恢复路径,不替代数据)
- 大数据量场景（列表超过 XX 条的性能降级方案 — 仅指 UI 性能策略如分页/虚拟滚动,不指数据降级)

**核验步骤：**
1. 读取原型 HTML，识别所有涉及数据加载的页面（列表页、详情页、搜索页）
2. 读取 PRD 文档，检查是否有"异常路径"或"异常处理"章节
3. 逐一核对每个数据加载场景是否定义了异常态处理
4. 检查异常提示文案是否具体（不能只说"报错提示"）

**不通过标志：** PRD 中仅描述成功路径，未提及任何异常态；或仅说"报错提示"但无具体文案。

---

### 检查项 2：字段校验规则

**检查目标：** 原型中所有输入框是否都有明确的校验定义。

**必须覆盖的维度：**
- 字符长度限制（最小长度、最大长度）
- 格式要求（手机号 `/^1[3-9]\d{9}$/`、邮箱、身份证、URL、IP 等正则）
- 是否必填（必填标记 `*`）
- 非法输入的报错提示文案（精确到每个字段的错误提示）
- 特殊字符过滤（如禁止输入 `<>&` 防 XSS）

**核验步骤：**
1. 读取原型 HTML，提取所有 `<input>`、`<textarea>`、`<select>` 元素
2. 读取 PRD 文档的"字段规格表"章节
3. 逐一核对每个输入字段是否在字段规格表中出现
4. 检查必填字段是否有错误提示文案
5. 检查格式校验字段是否有正则表达式或明确的格式说明

**不通过标志：** 存在任意一个 `<input>` / `<textarea>` / `<select>` 未在字段规格表中出现，或必填字段无错误提示文案。

---

### 检查项 3：状态切换逻辑

**检查目标：** 页面元素在不同状态下的表现和触发条件。

**必须明确的状态：**
- 按钮的状态：可点击、点击中（Loading）、置灰不可点击、成功态、失败态
- 每种状态的**触发条件**（如"表单未填完整时置灰"、"提交中显示 Loading 图标并禁用"）
- 状态切换的回退规则（如提交失败后按钮是否恢复可点击）

**核验步骤：**
1. 读取原型 HTML，识别所有交互按钮（提交、保存、删除、审核等）
2. 读取 PRD 文档，检查是否有"状态机"或"状态切换"章节
3. 逐一核对每个按钮的状态定义（可点击、Loading、置灰、成功、失败）
4. 检查每种状态的触发条件是否明确
5. 检查是否定义了防重复提交机制

**不通过标志：** 按钮仅描述"点击提交"但未说明点击前后的视觉反馈；或未定义防重复提交机制。

---

### 检查项 4：逆向交互流程

**检查目标：** 用户在核心操作中点击"取消"、"返回"或"返回上一级"时的数据处理逻辑。

**必须明确的逻辑：**
- 已填写的表单内容：丢弃 / 自动保存草稿 / 提示"是否放弃编辑"
- 已上传的文件：清理临时文件 / 保留供下次使用
- 多步骤表单的返回上一步：保留已填项 / 清空
- 浏览器"返回"按钮的行为（是否拦截、是否二次确认）

**核验步骤：**
1. 读取原型 HTML，识别所有表单页面和"取消"、"返回"按钮
2. 读取 PRD 文档，检查是否有"逆向交互"或"取消操作"章节
3. 逐一核对每个表单的取消/返回逻辑
4. 检查已填写数据的处理方式是否明确
5. 检查多步骤表单的返回上一步逻辑

**不通过标志：** 仅描述"点击取消关闭弹窗"而未说明已输入数据如何处理。

---

### 检查项 5：数据一致性与上游引用完整性(**Critical 强制项,不可豁免**)

**检查目标：** 每个功规点、字段、字典枚举、异常路径都可反查到原始依据(产品需求文档/原型/高保真设计),下游 SKILL(详细设计/研发执行计划/测试用例)据此反查证据。**任何一处缺失上游引用直接判定不通过。**

> **🛡️ 实测发现:** PRD 多文件拆分模式下,部分分册"原型引用关键词命中 = 0",QR Agent 仅靠语义检查会被"印象式通过"。本维度强制以 bash/python grep 输出为唯一判定依据。

**🛡️ 必跑 grep 化硬核回检(违反即不通过,无任何例外):**

```bash
# 功规点段头部 4 类来源标注覆盖率核验
python3 <SKILL_DIR>/scripts/check_req_upstream.py <PRD路径或目录>
# 退出码 0 = 通过, 1 = 不通过

# 等价 bash 速查:
total=$(grep -c "^### REQ-\|^#### 5\." <PRD>)
prd=$(awk '/^### REQ-|^#### 5\./{f=NR} f && NR<=f+8 && /PRD 来源|产品需求文档来源/' <PRD> | wc -l)
proto=$(awk '/^### REQ-|^#### 5\./{f=NR} f && NR<=f+8 && /原型(文件|来源|路径)/' <PRD> | wc -l)
# H1 PRD 来源 / total 必须 = 100%, H2 原型来源 / total 必须 = 100%
```

**A. L1 文档级引用(头部声明)**
- [ ] 文档头部包含 `原型来源` 字段(模式 A/B 共用必填)
- [ ] 模式 B 文档头部包含 `产品需求文档` 字段(路径 + 文件名)
- [ ] 有高保真时包含 `高保真设计` 字段
- [ ] 路径为仓库相对路径,不使用绝对路径(如 `C:/...`、`/home/...`)
- [ ] 文档头部包含"原型页面索引"表格,列出所有页面 + 路径 + 路由 + 关联功规点

**B. L2 段头部强制四行(每个功规点必须满足,每段头部 8 行内 grep 命中)**
- [ ] **H1 PRD 来源**(关键词:`PRD 来源` / `产品需求文档来源` / `研发需求来源`)— **必填,100% 覆盖**
- [ ] **H2 原型来源**(关键词:`原型来源` / `原型文件` / `原型路径`)— **必填,100% 覆盖**(即便原型只展示 mock 数据也要标,让追溯链完整)
- [ ] **H3 高保真来源**(关键词:`高保真设计` / `高保真来源`)— 如有则填,无则标"无";覆盖率 ≥ 95%
- [ ] **H4 关联功规点**(关键词:`关联功规点` / `关联 REQ` / `依赖`)— 如有依赖则填,无则标"无";覆盖率 ≥ 95%

**B'. 🛡️ 引用必须使用 markdown 可点击链接 + 相对路径 + 精细锚点(Critical 强制)**

每条来源标注行**必须**符合以下 4 条:
- [ ] **格式**: `[显示文本](相对路径#章节锚点)` — 标准 markdown 链接语法,**严禁**纯文本路径
- [ ] **路径**: 必须是**相对路径**(如 `../requirements/V1.0/产品提供/xxx.md`),**严禁** `https://`、`/home/`、`C:\` 等绝对路径
- [ ] **后缀**: 链接必须指向具体文件(`.md` / `.jsx` / `.tsx` / `.html` / `.vue` / `.fig` / `.png` / `.docx` 等),不允许仅指向目录
- [ ] **锚点**: **尽可能精细** — 章节锚点(`#章节锚点`) > 行号锚点(`#L120-L180`) > 组件名(`#<UserList>`) > HTML 锚点(`#search-btn`),**严禁**仅链接到文件名而无锚点

| 类型 | 示例 |
| :- | :- |
| ✅ 正例(章节级) | `[产品需求 §3.2 用户列表(L120-L180)](../requirements/V1.0/产品提供/xxx.md#3-2-用户列表)` |
| ✅ 正例(组件级) | `[<UserListPage>](../prototype/V1.0/code/user-list.jsx#L20-L120)` |
| ✅ 正例(HTML 锚点) | `[#search-btn 搜索按钮](../prototype/V1.0/code/user-list.html#search-btn)` |
| ❌ 反例(纯文本) | `docs/requirements/V1.0/产品提供/xxx.md > §3.2` |
| ❌ 反例(绝对路径) | `[xxx](https://github.com/...)` 或 `[xxx](C:/Users/...)` |
| ❌ 反例(无锚点) | `[xxx](../requirements/V1.0/产品提供/xxx.md)` (链接到文件但没指向具体章节) |
| ❌ 反例(模糊引用) | `参考产品文档` / `参考 code/ 目录` / `见原型` |

**自动化核验:** `check_req_upstream.py` 会扫描每条来源行的链接合规度,任一行违规即整体不通过。

- [ ] PRD 中出现的展示单位词("K"/"万"/"MB"/"分钟前"/"%"/"千克"/"米"等)应能在字段规格表"展示单位"列找到对应条目

**G. 数据闭环完整性(对应 SKILL「数据闭环完整性原则」核心章节,Critical 强制子项)**
- [ ] **铁律 ②(有展必有源)**: PRD 中**每个**展示列表 / 卡片 / 统计区域都必须能在「六·2、数据来源说明」找到对应来源行(来源类型必落 7 类之一);展示区域无来源行 → 不通过

- [ ] **孤立端登记**: 增端孤立 / 展端孤立且无法回溯到已有实现的,必须以 `❓ 待澄清` + `Q-FLOW-NNN` 登记 Module E,不得默认"先存着不展示"或凭空指定数据源(与维度 11 联动,登记完整性仅由维度 11 核验)

### 检查项 6：权限与极端情况

**检查目标：** 权限差异和 UI 极端情况的规则。

**必须明确的维度：**
- 不同角色访问同一页面的差异（可见字段、可执行操作、数据范围）
- 未登录访问的跳转逻辑
- 长文本溢出的处理（截断 `...` / 换行 / Tooltip 展示全文）
- 数字极值（金额超过 1 亿的显示格式、库存为 0 的展示、负数的颜色）
- 时间极值（远期日期、空时间、秒级 vs 毫秒级）
- 列表无数据、仅 1 条、超过 1 万条的展示差异

**核验步骤：**
1. 读取 PRD 文档，检查是否有"RBAC"或"权限矩阵"章节
2. 检查每个角色在具体页面的差异是否明确（可见字段、可执行操作）
3. 检查未登录访问的跳转逻辑
4. 读取原型 HTML，识别所有文本展示区域和数字展示区域
5. 检查长文本溢出处理方式是否定义
6. 检查数字极值、时间极值的展示规则
7. 检查列表的空态、少量数据、大量数据的展示差异

**不通过标志：** RBAC 章节仅列角色但未说明每个角色在具体页面的差异；或无长文本/极值的处理说明。

### 检查项 7：隐藏逻辑挖掘

**检查目标：** 原型图未直接体现但业务上必须存在的逻辑。

**必须挖掘的逻辑：**
- 数据排序规则（按时间倒序 / 按权重 / 按优先级 / 自定义字段）
- 分页加载机制（传统分页 / 无限滚动 / 懒加载）
- 自动刷新频率（列表多久刷新一次、详情页是否实时更新）
- 默认筛选条件（初次进入页面的默认筛选器）
- 缓存策略（详情页数据缓存时长、列表数据多久失效）
- 审计日志（哪些操作需要记录操作人和时间）
- 幂等性要求（重复点击提交、网络重发的去重）

**核验步骤：**
1. 读取原型 HTML，识别所有列表页面
2. 读取 PRD 文档，检查是否有"隐藏逻辑"或"业务规则"章节
3. 检查每个列表页面的排序规则是否明确
4. 检查分页机制是否定义（每页条数、总页数计算）
5. 检查是否定义了自动刷新频率
6. 检查是否定义了默认筛选条件
7. 检查是否定义了缓存策略
8. 检查关键操作是否定义了审计日志
9. 检查提交操作是否定义了幂等性要求

**不通过标志：** 列表未说明排序规则；或分页仅展示组件但未明确每页条数、总页数计算。

**检查目标：** 产品需求文档中涉及的第三方系统对接是否在 PRD 中完整体现双方职责,且强制包含独立汇总清单。

- [ ] 七·4.4 各对接场景详细说明存在,展开每个场景的业务流程
- [ ] 七·4.5 对接约束与边界存在,明确职责/数据归属/异常归责/联调依赖等

- [ ] 失败处理/降级方案以业务降级表现描述,而非技术性描述
- [ ] 第三方需求清单的"反馈状态"列已初始化(⏳ 待确认)
- [ ] 对接约束章节明确了职责边界、数据归属、异常归责

### 检查项 9：多文件拆分一致性(仅多文件输出模式)

**检查目标：** PRD 拆分为多文件时,专职索引 `00_索引.md` + 内容文档结构、文件名序号、字典枚举独立性、跨文档引用的正确性、无过度碎片化。遵循 **AIDP 文档命名范式**:`00_` 槽位恒给专职索引 `00_索引.md`、内容主文档一律从 `01_` 起;即便只有一份内容文档也产出 `00_索引.md` + `01_<语义名>.md`(≥2 文件)。

### 检查项 12：不臆造兜底(Critical 强制项)

**检查目标:** 产品需求文档中没有明确说明"需要兜底/容错/默认值/降级方案"的地方,PRD 中不得自行增加任何形式的数据源兜底、缺省回退、容错降级。

**核验步骤:**

1. **扫描 PRD 中的兜底语句**: 全文搜索以下关键词出现位置(均为"疑似兜底语句"):
   - 中文: 兜底 / 默认值 / 缺省值 / 默认显示 / 缺失时显示 / 未配置时 / 失败时 / 异常时 / 失败回退 / 降级 / 缓存兜底 / 静态数据 / 示例数据 / mock / fallback / 占位
   - 英文: `default` / `fallback` / `mock` / `placeholder` / `cache fallback` / `degradation`
   - **缓存机制臆造(对应 `flow-principles.md`「缓存机制臆造(Critical)」)**: `Redis 缓存` / `本地缓存` / `接口响应缓存` / `缓存 N 分钟` / `缓存字典数据` — PRD 未说"需要缓存"却出现这些技术缓存机制描述,应标 ❓ 待澄清 / 🔧 暂行方案(建议缓存,待用户确认),不得作为确定需求混入正文
2. **三类分流**(注意区分 B 与 C):
   - **A. 异常处理(允许)**: 失败后向用户**告知错误**(显示错误提示/Toast/重试按钮/跳转登录页),不替代数据本身
   - **B. 数据源兜底(需溯源)**: 失败后用**替代真实数据假装成功**(显示静态列表/上次缓存/示例数据/默认配置)
   - **C. 空状态/加载态/错误态 UI 推断(允许)**: 数据真为空/真在加载/真出错时,设计**视觉反馈**(空插画/暂无数据文案/骨架屏/Spinner/错误 Toast),**不替代数据**;PRD 即使没明文说明,Agent 也允许自行推断 UI,**但需在 PRD 中标注"空状态 UI 推断,可后续按设计规范统一"**
3. **B 类逐条溯源**: 每条 B 类语句必须能在产品需求文档(模式 B)或原型注释中找到对应原文,核验方式:
   - 在产品需求文档/原型中搜索相同/同义关键词
   - 检查 PRD 该条目是否有"上游引用块"标 PRD 章节+行号
   - 模式 A(仅原型)下若原型本身没有兜底描述,则 B 类语句必须移到"十、待澄清问题清单"标 🔧 暂行方案
4. **十章节核验**: 若 Agent 因边界场景需要推断 B 类兜底,该兜底必须出现在"十、待澄清问题清单"中,标记 `🔧 Agent 暂行方案`,而非以"事实需求"形式混排在功规点/字段规格中
5. **空状态/加载态特殊豁免**: 维度 1「异常路径覆盖」与本维度协同,异常路径中的"空状态/加载态/错误反馈" UI 推断属 C 类,不需溯源;但"接口失败显示替代数据"属 B 类,必须溯源

### 检查项 13：需求字段去向登记 + 原型内容基线覆盖度完整性(Critical 强制项)

**检查目标:** 分**三支**核验,均 Critical:

- **③ PRD 条目反向覆盖级(表 D,模式 B 强制)= Critical 子项「产品 PRD 条目转写完整性」:** 以**产品原始 PRD 原文**(示例路径 `docs/requirements/{version}/产品提供/*.md`,自适应项目结构)为**条目完整性对账基准**,核验其**每个功能条目/字段(粒度 = 按钮 / 列 / 操作 / 规则 / 字段)是否都被转写进研发 PRD**——**既包括表格里每张表的每一行**(重点 4 类高危表:操作描述表 / 列表字段说明表[备注列必带] / 展开明细表 / 遗留问题·迭代建议表),**也包括散文段落 / 无序列表里描述的功能条目**(如正文写"点击『导出』下载 Excel"、"完成率<60% 标红"这类非表格的按钮/操作/规则,禁止因"不在表里"而漏拆)。每个条目必须 100% 在「六·4 表 D：PRD 条目映射表」有 1 条对应登记,去向(处置) ∈ {已承接(=已转写,指向研发 PRD 章节/字段) / 本版不做(=有意裁剪,注明原因) / 已存在无需重复};**漏转写 = 处置留空/越界 = 未分类条目 > 0 判不通过(命令 9)、并强制登记补齐,严禁静默丢弃**;处置 = 本版不做 须经产品确认门登记 `Q-ITEM-NNN`。「遗留问题 / 迭代建议 / 待办」章节是**需求输入**(非缺陷备忘),必须逐条进表 D。字段级已由表 A/B 兜,本支**补功能条目级(非字段的按钮/列/操作/规则)** 的转写完整性,与表 A/B 衔接不重复。**模式 A(纯原型逆向,无产品原始 PRD)本支标 N/A。** 这是一道**反向覆盖校验**(以产品原始 PRD 每个功能条目为基准查"有没有在研发需求里落点"),与命令 4 的正向溯源方向相反、并存不可替代。

本清单(表 A/B/C/D)是下游对账(dev-logic-architect 比对 / code-verification-loop 对账·原型覆盖度 / dev-manual-testcase 逐列·逐交互核对)的上游单一信源。

**核验步骤:**

*A 支——字段级(表 A/B):*
1. **盘点字段全集(采集看原型/产品需求)**: 读取原型 HTML/代码与产品需求,逐个列表(`<table>`/`el-table`/`a-table` 的列/表头)、表单(`<input>`/`<select>` 的 `label`)、表格,枚举出**用户可见的全部数据项**,形成字段全集(登记时一律转写为业务语义名)。

9. **基线「实现」项覆盖核验(有上游基线时 Critical)**: `原型内容基线.md` 中每个处置 =「实现」的元素/逻辑,必须能在 PRD(表 C 或对应功规点/交互描述)找到对应落地;**基线「实现」项在 PRD 缺失 = Critical 不通过**。

*C 支——PRD 条目反向覆盖级(表 D,模式 B):*
11. **PRD 原子条目化(采集看产品原始 PRD 原文)**: 把**产品原始 PRD 原文**(示例路径 `docs/requirements/{version}/产品提供/*.md`)拆成原子条目——**每个功能条目 = 1 条,粒度 = 按钮/列/操作/规则/字段**:表格里每张表的每一行 = 1 条目,**散文段落/无序列表里描述的按钮·操作·规则也逐条拆出**(禁止因"不在表里"而漏);表格「备注 / 展示规则」列 + 散文条目附带的展示/校验规则是该条目**必带属性,禁与字段名/操作名分离**(如"完成率"必带"进度条按阈值分色")。重点覆盖 4 类高危表 + 散文里的业务规则:操作描述表 / 列表字段说明表 / 展开明细表 / 遗留问题·迭代建议表 / 散文里的按钮·操作·业务规则。
12. **逐项比对表 D**: 产品原始 PRD 每个功能条目/字段必须能在表 D 找到 1 条对应登记行。**任何产品 PRD 条目在表 D 缺失 = 漏转写 = 静默丢失 = 不通过**(尤其散文里的按钮/操作/规则、操作类条目、遗留问题·迭代建议条目、字段说明表备注列)。

*三支共用:*
10. **待澄清联动**: 所有字段级 `裁剪` / `请第三方补` 项以 `Q-FIELD-NNN`、所有表 C 非实现项以 `Q-PROTO-NNN`、所有表 D `本版不做` 项以 `Q-ITEM-NNN` 登记「十、待澄清问题清单」,与维度 11 双向追溯。

### 检查项 15：结论型断言证据来源 + 引用编号回原文 + 禁令反向边界（**Critical**）

**检查目标：** PRD 里**一句写死的话**是否可核查——① 结论型断言有没有证据（**Critical**）；② 引用别处的编号时有没有回原文核对（**Critical**）；③ 禁令条目有没有写反向边界（**Important**）。

> **🛡️ 为什么三条合成一项：** 它们是同一类失效的三种形态——**文档里一句没被核过的话，被后续每一轮当既定事实引用**。三者都不报错、都没有任何自动信号，只会在返工时才暴露。下游一次前端迭代**产品反馈 11 轮才收敛**，这三条各贡献了一条主线。

**A. 结论型断言必须附证据来源（Critical）**

- [ ] **待澄清问题清单**（第十节 Q-NNN）的 `🔧 暂行方案` 旁、以及 **表 E / 表 F** 里，凡出现「上游不支持 / 无出口 / 不可得 / 禁止 / 不允许 / 做不到」这类**结论型断言**，都附了证据来源
- [ ] 证据形态三选一，且满足最低要求：
      | 形态 | 最低要求 |
      | :- | :- |
      | **文档原文位置** | 文档名 + 章节/锚点 + **那句原文**（写「见接口文档」不算） |
      | **源码位置** | 仓库/路径 + 符号名；**看的是哪个分支/版本也要写** |
      | **实测记录** | 请求形态 + 实际返回 + **日期**（没有日期的实测等于没做） |
- [ ] 拿不出证据的断言**就地标「未验证假设」**，并**未**在后续章节被当作既定事实引用
- [ ] ⚠️ 「未验证假设」是**隔离标记不是不合格标记**——带着它推进 PRD 是允许的（与不中断原则一致），但引用它的地方必须**原样带着这个标记**；要去掉只有一条路：补证据
- [ ] ⚠️ **与下游 `dev-logic-architect` 核心原则 30 / 检查项 38 同款口径**——同一句断言常常从 PRD 的 Q-NNN 一路传到详细设计，**两侧口径必须一致**，否则在交界处证据就丢了

> **真实代价：** 「上游没有按员工维度的出口」——**事实是该端点早就有可选入参**，只是本侧从未封装带该参数的重载。这句话进了 PRD 后被后续**每一轮**当既定事实引用，衍生出一整套「只能显示占位值」的错误设计和一份「产品知情决策」的论证。**一句没有证据的结论，比一个明写的待澄清项危险得多**——待澄清项会被追问，结论不会。

**B. 引用编号必须回原文核对（Critical）**

- [ ] 凡用「**约定 N** / **断言 Z-xx** / **需求 REQ-xx** / **表 E 第 N 行**」这类编号作为「**不能做某事**」的依据时，**回原文确认过该编号确实是那个意思**
- [ ] 引用处写成「**编号 + 一句话原意摘要**」，而不是光一个编号
- [ ] ⚠️ 编号是**最容易腐化的引用形态**：增删条目会让编号整体位移，而位移后的错误引用**两侧都仍在范围内**，任何范围检查都发现不了；带一句原意摘要，对不上时立刻暴露

> **真实代价：** 「某断言要求卡片模板不可外迁」——回查原文，**该断言讲的是完全无关的另一件事**。这条错误记载让公共组件迟迟没有抽取，并让宿主文件的复杂度超阈告警被长期豁免——**一条假前提同时冻结了两条工程纪律**。

**C. 禁令条目必须同时写反向边界（Important）**

- [ ] PRD 里的「严禁 X / 不允许 X / 不做 X」条目，同时写明【**禁止的对象**】与【**不在禁止范围内的相似形态**】
- [ ] 写法为 `⛔ 禁止：<对象 + 为什么这个形态是错的>` + `✅ 不在禁止范围：<最容易被误伤的那个相似形态>`
- [ ] 反向边界挑的是**最容易被误伤的那一个**，不是泛泛的「其它情况另议」（那等于没写）

> **真实代价：** 一条决策禁止的是「逐明细数 ÷ 聚合总量」这种**分母错位**的占比展示（分子分母口径不同、比值无意义），被泛化成「不许画进度条」，于是砍掉了「逐明细数 ÷ 该明细自己的额度」这个**分子分母同属一个主体、完全合规**的展示——直到使用者追问「怎么只有一个统计项」才补回来。**禁令的杀伤半径天然大于它的本意。**

**不通过标志：**

- （Critical）存在结论型断言而无证据、也未标「未验证假设」
- （Critical）已标「未验证假设」的断言在后续章节被当既定事实引用（标记被悄悄摘掉）
- （Critical）用编号作为「不能做某事」的依据，却没有回原文核对 / 引用处只有编号没有原意摘要
- （Important）禁令条目只写「禁止 X」而无反向边界

⚠️ **本检查项刻意不配硬门脚本。** 「不支持 / 禁止 / 不可得」这些词在 PRD 与规范正文里必然大量出现（本清单自己就有几十处），按关键词扫必满屏假红，与本仓库「新判据宁可窄到只覆盖一种明确形态、也不要宽到需要一堆护栏去救」直接冲突。判据全部落在 QR 子 Agent 的**语义核对**上。

## 检查清单使用说明

### 适用场景

本检查清单适用于以下两种模式生成的 PRD 文档：

- **模式 A（逆向提取）：** 仅从 HTML 原型逆向生成 PRD
- **模式 B（融合增强）：** 从产品需求文档 + 原型 + 参考文件融合生成研发视角的 PRD

### 检查原则

1. **只读审查：** 检查 Agent 严禁直接修改 PRD 文档，只输出检查报告
2. **证据引用：** 每个不通过项必须引用具体的 PRD 章节或原型元素作为证据
3. **具体建议：** 修订建议必须具体到章节、字段、文案，不能只说"需要补充"
4. **维度适用性：** 
   - 维度 8（第三方系统对接）：仅当产品需求文档涉及第三方对接时适用
   - 维度 9（多文件拆分一致性）：仅当采用多文件输出时适用
   - 维度 10（职责边界）：始终适用，必须检查
   - 维度 11（待澄清问题清单完整性）：始终适用，必须检查
   - 维度 12（不臆造兜底）：始终适用，Critical 强制项
   - 维度 13（需求字段去向登记 + 原型内容基线覆盖度完整性）：仅当 PRD 含列表/表格/表单或任何原型可见元素/操作逻辑时适用，Critical 强制项；上游有`原型内容基线.md`则以其为覆盖基准（有则强制消费、无则回退原型 code/）；无任何页面元素展示的纯说明 PRD 标 N/A。**另含 ③ PRD 条目反向覆盖级（表 D）**：模式 B（有产品需求文档）强制产表 D、跑命令 9 反向覆盖率，未分类条目 > 0 判不通过；模式 A（纯原型逆向，无产品文档）本支标 N/A
   - 维度 14（语义/口径变更类需求识别 + 表 E/F 完整性）：仅当命中语义/口径变更信号词（口径/范围/单位/默认值/改为/扩展为/由…改成/不再只/全口径/含…消耗/默认开启/默认关闭/反转/由仅…改为）或笼统豁免表述时适用，Critical 强制项；命中即强制产表 E（受影响说明性展示物逐行登记 + 具体新文案）+ 表 F（跨版本历史需求作废清算）；无语义变更的纯新增/纯逆向 PRD 标 N/A
5. **循环修订：** 主流程根据检查报告修订 PRD，再次调用检查 Agent，循环至全部通过或达到 3 轮上限

### 检查顺序

建议按以下顺序执行检查，以提高效率：

1. **先检查结构性问题**（维度 9、10、13、14）：文件结构、职责边界、需求字段去向登记 + 原型内容基线覆盖度、语义/口径变更类需求识别 + 表 E/F
2. **再检查完整性问题**（维度 1、2、5、8、11、12）：异常路径、字段校验、数据一致性、第三方对接、待澄清问题清单、不臆造兜底
3. **最后检查细节问题**（维度 3、4、6、7）：状态切换、逆向交互、权限极端情况、隐藏逻辑

### 常见问题

**Q1: 如何判断是否涉及第三方对接？**
A1: 读取产品需求文档（模式 B 时），搜索关键词：第三方、外部系统、对接、集成、API、接口调用等。如果产品需求文档明确提到需要与外部系统交互，则需要检查维度 8。

**Q2: 如何判断是否为多文件输出模式？**
A2: 检查 PRD 输出目录，如果存在多个 .md 文件（专职索引 `00_索引.md` + `01_`+ 内容文档），则为多文件输出模式，需要检查维度 9。历史裸单文件（旧单文件目录）grandfather 放行，脚本 warn 不判不通过。

**Q3: 职责边界检查的重点是什么？**
A3: 重点检查 PRD 是否混入了技术设计内容（接口定义、数据表设计、技术栈）或研发管理内容（研发执行计划、Sprint、工时、排期）。PRD 应该只包含业务需求和业务规则，不涉及技术实现和项目管理。

**Q4: 如何处理原型与产品需求文档冲突的情况？**
A4: 当原型图的页面流转与产品需求文档的业务逻辑冲突时，PRD 应该以**业务闭环**为准，优先保证业务逻辑的完整性。检查时需要验证 PRD 是否正确处理了这种冲突。

**Q5: 碎片化子文档的判断标准是什么？**
A5: 除专职索引 `00_索引.md`（及历史 `00_*` 总览/索引文档）外，所有子文档的行数应 ≥ 100 行或文件大小 ≥ 4KB。如果存在不足 100 行的子文档，应该合并到相邻业务域子文档或"通用/附录"中。
