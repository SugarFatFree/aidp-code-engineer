## 为什么不用表格（别改）

表格看着更规整，五列也确实更适合承载「编号/日期/类型/内容/级联目标」——但它**诱导把条目写详细**，
而「条目只记一行，能省则省」是本机制成立的前提：写得详细，记录本身就成了新的耗时，
正好抵消攒批省下的时间（下游的原始痛点就是"文档写太多"，别在这里把它请回来）。

「类型」「级联目标」两列也不该记 —— 拆成四族之后，**文件所在的族就是级联目标**，
再记一遍纯属冗余；「类型」级联时从代码 / git 现查更准，属于详规「⛔ 不要记」那一档。

## 收口后怎么处理这个文件

**默认（推荐）**：成功级联的条目**即删**；待级联段清空 → **删除整个文件**。
「增量册存在」本身就等于「本族有待级联项」，这个不变量让下次收口不必重新判断"这条级联过没有"。

**⚠️ 溯源引用的处置**：级联时在目标文档里**写明变更内容与理由本身**，
**不要写 `增量册 C-036-03` 这类编号引用** —— 增量册是中转站、不承担长期溯源，
写了编号就会在删档时集体断链，逼得执行体在「即删」与「不断链」之间二选一（两边都违规）。

**⛔ 已级联的条目【必须删除】，不是打个 `✅` 标记就算完** —— 条目级联完就删条目，
条目删空就删文件。`<!-- LEDGER-ARCHIVED -->` **不是出路、不豁免任何东西**：
打标记只是把"没删"换了个说法，册子仍在、条目仍在，读文档的人照样分不清
哪条已生效、哪条还欠着。机器侧同口径（`pending_cascade` 照常计数并点名
`archived_not_deleted`、`check_cascade_landing` 一律 FAIL）。
**编号引用删不掉时**：先按上面把引用处改写成变更内容与理由本身，**再真删**。

## 编号在四族之间怎么给（C-NNN 全版本唯一）

`C-NNN` 的编号空间是**版本级、四族共用**：同一次变更牵动三族，就在三族册里用**同一个 `C-NNN`**
（各记各的那一面）。⛔ 不要各族各起一套序号——那会让「同一次变更」在收口时无从合并同类项。
取号 = 本版四族册里现有最大 `C-NNN` + 1（拆分子项用 `C-036-01` 这类子编号）。
