# docs/deployment/ — 部署文档

> **隔离级别**：版本级（团队共享，不按用户隔离）
> **维护视角**：运维 / 上线 / 灰度
> **关键边界**：本目录承载**运维上线视角**的部署文档。
> - **★ 双轨（[约定 37](../../AGENTS.md)）**：SQL 与配置文件各自分 **增量轨**（回答「已有环境怎么升级」）与 **全量轨**（回答「从零怎么搭」）——`sql/增量/` + `sql/全量/`、`配置文件/增量/` + `配置文件/全量/`。**两套绝不叠加执行**：全新部署只跑全量、升级只跑增量，场景导航写在 `{version}/00_索引.md`。**零变更的版本同样要产全量。**
> - **⛔ `sql/` 与 `配置文件/` 根下不得直放两轨产物**（根下散落 `.sql` / `配置项清单*.md` / `*.conf` / `docker-compose*` / `k8s-*` → `verify.py::check_deployment_two_track_layout` **ERROR**，不设双读兼容）。存量历史版本目录由 `verify.py` 检出后按其指引手工 `git mv` 搬迁 + 回写引用。
> - `{version}/` 根留给固定契约文件 `00_索引.md` + 其他部署信息（上线步骤 / URL 指南 / 发布说明 / 拓扑等）。
> - 应用运行时配置（`application.yml` / `.env` / `vite.config.*`）保留在 `code/` / `env/` 真实文件本身，按 [AGENTS.md 约定 25「配置文件分层」](../../AGENTS.md) **不复抄**到本目录；`配置文件/全量/` 是约定 25 的唯一例外（真实 `.yml` 产物 + 主体是仓库内无权威原文件的配置中心层 + 随 tag 冻结的一次性快照，三条同时满足，见细则 37.7）。

## 双轨部署基线（增量轨 / 全量轨）★

> **权威定义见 [AGENTS.md 约定 37](../../AGENTS.md) + 细则 [`../../.aidp/reference/约定细则-5.md`](../../.aidp/reference/约定细则-5.md)**；本节为运维视角速览。

| | 增量轨 `sql/增量/` + `配置文件/增量/` | 全量轨 `sql/全量/` + `配置文件/全量/` |
|---|---|---|
| 回答的问题 | 已有上一版环境**怎么升级** | 空库 / 空配置中心**从零怎么搭** |
| 口径 | 相对上一个**已发布 tag** 的变更 | **只跟最新代码走，无历史包袱** |
| 含 ALTER / 数据迁移 | ✅ 以此为主 | ❌ 一条都不含 |
| 产出时机 | 开发期持续产出（`/sprint-dev` / `/sprint-design` / `/sprint-bugfix`），发布期只校准 | 发布期产出（`/version` Step 3.3.7.9，可 `--rebuild-baseline` 单步补跑） |
| 零变更时 | 为空，但要在 `00_索引.md` **显式成文**（写清为什么是零 + 判据 + SQL 只读核验脚本） | **照产不误**——与本版有无变更无关 |

**⛔ 两条铁律**：
1. **两套绝不叠加执行**——全新部署只跑全量、升级只跑增量。同时跑会重复建表、重复插初始化数据。选哪条路写死在 `{version}/00_索引.md`。
2. **全量的难点不在导出、在判断什么该进**——表清单以**代码 ORM 声明为准**再与真实库交叉核对（代码有而库查无 → 剔除并在 `全量/00_索引.md` 写明理由）；导出源必须是**应用实际连接的库 / schema**（从应用数据源配置反查，不用数据库客户端默认连接）；去环境绑定物（schema 前缀 / 表空间 / 存储子句）；按 owner 分 A 区自有表 / B 区共享表 + 建表幂等。把库和配置中心 dump 出来交差 = 没做本约定。

**全量配置的两条要点**：只收「部署方要配」的两层——引导层**环境**文件（只放目标环境那一份，**含明文凭据的 profile 不复制**）+ 配置中心业务配置（仓库内唯一基线）；值取**配置中心实况**（只读 API 直连，不信仓库镜像），按代码消费面三重检索（配置全名 / 驼峰字段名 / 外部 SDK）剔死配置，凭据一律 `${大写变量:__FILL_ME__}` 且**变量名必须由完整配置路径生成 + 过唯一性校验**（`sso.auth-code` 与 `sso.client.auth-code` 不得都脱敏成 `${AUTH_CODE}`）。

**⛔ 全程只读**：DDL 经元数据视图导出、配置经只读 API 拉取，**不执行任何 DDL/DML、不改任何环境配置、不启动任何服务**。基线环境须用户确认，不得拿研发环境冒充生产。

**机器门（不靠自觉）**：产出后必须跑 `python3 .aidp/scripts/release_baseline_check.py --version <version>`，覆盖 12 项确定性校验（结构完整性 / YAML 语法 / SQL 环境绑定物残留 / 明文凭据扫描 / 占位变量名唯一性 / `${a.b}` 引用目标存在性 / 注释完备性 / 生效形态唯一 / 相对链接有效性 / **增量极简度**）。

## `tools/` — 跨版本运维 / 一次性工具归档（非版本隔离）

> **权威定义见 [`../init/06_版本与用户目录约定.md`](../init/06_版本与用户目录约定.md) §2.5.4.1**；本节为运维视角速览。

`docs/deployment/tools/` 收纳**一次性运维 / 历史数据修复 / 字典导入 / 测试数据清理**类的工具 SQL 与脚本。

**★ 与 `{version}/` 的边界**：`{version}/` = 随版本发布的**正式部署产物**（DDL/配置/部署流程），**按版本隔离**；`tools/` = **跨版本、非版本隔离**的运维侧临时/历史工具，**按归属应用分类**，不随某个版本走。

| 子目录 | 归位规则 |
|--------|---------|
| `本应用/` | 操作业务应用**自有库**的工具（DDL / 历史数据修复 / 第三方同步补推 / 测试数据清理）|
| `<上游系统>/` | 操作**第三方 / 上游系统**的脚本（如订单中心 order-center 的字典导出导入；按系统名命名）|
| `其他/` | **跨系统**（多方联动）的迁移方案整目录 |

> 子目录名**可按项目实际应用命名**；`本应用 / <上游系统> / 其他` 为通用三分基线。

**命名**：SQL / 文档文件名**尽量中文**（描述用途）+ **保留日期前缀**（如 `20260715_字典表历史数据修复.sql`）；**可运行工具**（含被 README 交叉引用的 `.py`/`.sql`）**内部文件名保持稳定**、仅外层目录中文化；**不纳入构建产物**（`__pycache__` 等）。

**范式层职责（轻量）**：只做「识别 + 规范位置 + README 索引」，**不为工具生成/校验 SQL 内容**。`/version` 发布时纳入整理（README 索引对齐 + 清 `__pycache__`，见 [`/version`](../../.aidp/commands/version.md) Step 3.3.7.8）；`README.md` 属**用户内容**，脚手架 create-if-missing 不覆盖。

## 配置承载关系图

```
code/.../application.yml          ← 真实后端 Spring 配置（权威）
code/.../vite.config.*            ← 真实前端构建配置（权威）
env/.env / .env.production / ...  ← 真实全局环境变量（权威）
配置中心（Nacos / Apollo / …）      ← 业务配置真值所在（仓库内【无】权威原文件）

         ↓ git grep 消费面比对（上一发布 tag → 本版）        ↓ 发布期只读拉取实况
         ↓                                              ↓
docs/deployment/{version}/                       docs/deployment/{version}/
  配置文件/增量/配置项清单.md                        配置文件/全量/
  ← 只讲【本版改了什么】（索引层，不复抄）              ├── 00_索引.md（一共有哪些项 + 收录矩阵 + 核查发现）
                                                   ├── bootstrap-{env}.yml（引导层环境快照，权威仍是代码里的原文件）
                                                   ├── nginx.conf / docker-compose.yml / k8s-*.yaml（完整份 = 权威原件本身）
                                                   └── <配置中心>/*.yml（仓库内唯一基线，一 dataId 一文件）
```

**按 [AGENTS.md 约定 25](../../AGENTS.md)**：真实配置文件本身权威，`配置文件/增量/配置项清单.md` **只讲本版改了什么**——新增项 / 删除项 / 本版运行时配置文件变更片段，**纯代码块 + 行内注释 ≤20 字符，⛔ 无表格、无判定依据、无各环境对照**。

**⛔ 不进增量、归 `配置文件/全量/00_索引.md` 的 4 段【常驻信息】**（它们不是本版变更；开发期手工维护它们正是"仓库镜像落后三个版本"的来源，改由发布期从真实环境只读重建）：

1. **配置承载方式**（本地文件 / Nacos / Apollo / Consul 等）
2. **配置文件索引**（路径 + 用途 + 维护方）
3. **上线敏感项 checklist**（运维上线必须填值的 key 清单，**只列 key 不列值**）—— 本版新增的敏感项在增量代码块里标 `# 必填·敏感` 即可
4. **历史迁移沿革**

**4 类硬禁止**：
- ❌ 在 `.md` 复抄整份 `application.yml` / `.env` / `nginx.conf` 等（再大也别贴整文件）
- ❌ 维护 key → 示例值的全量大表（已被代码文件本身覆盖）
- ❌ 创建 `.env.example` / `application.example.yml` 等示例副本文件（真实文件 + 差异片段已足够，示例副本会双信源歧义）
- ❌ 增量做「代码块 + 下方表格」两处对照，或与 `部署流程.md` 双写配置内容（部署流程只声明"是否需改 + 指向清单"）

> `配置文件/全量/` 是约定 25 的**唯一例外**：产物是真实 `.yml` / `.conf` 文件而非 Markdown 复抄 + 主体是仓库内无权威原文件的配置中心层 + 随 tag 冻结的一次性快照，三条同时满足才成立（细则 37.7）。

## 配置项清单生成时机

| 阶段 | 触发条件 | 操作 |
|------|---------|------|
| **首版** | 本 Sprint 第一次改动任一配置文件 | `/sprint-dev` Step X.7 自动创建 `配置文件/增量/配置项清单.md` |
| **增量** | 每次 `/sprint-dev` / `/sprint-bugfix` 改了配置文件 | 在「①新增配置」/「②删除配置」段追加代码块条目；改了 nginx/compose/k8s 则在「③运行时配置文件变更」段补【改哪个文件 / 片段 / 插在哪个 server 或 location 块内 / 生效动作】四要素 |
| **配置中心迁移** | 用户手动触发 | `git mv 配置项清单.md 配置项清单-{中心}.md`（仍在 `增量/` 下）+ 更新代码块内的 dataId 坐标 |
| **发布期** | `/version` 发布 | 增量只**校准**不重造（基线区间 = 上一已发布 tag → 本版，用 `release_scope.py` 算，须跨过中间过渡版本）；`配置文件/全量/` 于 Step 3.3.7.9 产出 |

详细骨架 + 各场景操作步骤见 [`../../.aidp/commands/sprint-dev.md`](../../.aidp/commands/sprint-dev.md) Step X.7。

## 部署清单内容（`{version}-deployment-checklist.md` 推荐结构）

```markdown
# V0.1.0 部署清单

## 前置条件
- 数据库版本 / 中间件版本
- 依赖服务清单

## 部署顺序（★ 先选路：全新部署走【全量轨】/ 升级走【增量轨】，两轨绝不叠加执行）

### A. 全新部署（空库 + 空配置中心）
1. ★ 按 `配置文件/全量/00_索引.md` 的「上线敏感项 checklist」把所有 `${...:__FILL_ME__}` 占位替换为本环境实际值
2. 导入配置中心（`配置文件/全量/<配置中心>/*.yml`，一 dataId 一文件）+ 落地引导层环境文件 `bootstrap-{env}.yml`
3. 数据库建库（按序号执行 `docs/deployment/{version}/sql/全量/{NN}_建表-<业务域>.sql` → `{NN}_初始化数据.sql`；B 区共享表若已由对方系统建好可跳过）
4. 部署 `配置文件/全量/nginx.conf` / `docker-compose.yml` / `k8s-*.yaml`
5. 后端服务启动 → 前端构建部署 → 验证
> ⛔ 全新部署**不执行** `sql/增量/` 下任何脚本（会重复建表、重复插初始化数据）

### B. 升级部署（已有上一版环境）
1. ★ 按 `配置文件/增量/配置项清单.md` 的「①新增配置」「②删除配置」两段逐项在配置中心新增 / 删除（标 `# 必填·敏感` 的须填实际值）
2. 数据库变更（按序号执行 `docs/deployment/{version}/sql/增量/{NN}_<中文名>.sql`，如 `01_用户表DDL.sql`、`02_字典初始化.sql`，跳过 `99_回滚脚本.sql`；执行状态回填 `部署流程/SQL执行台账.md`）
3. 运行时配置文件按「本版运行时配置文件变更」段的**改动片段**就地修改（⛔ 不要用 `全量/` 的整份文件覆盖现网——会冲掉环境特有的证书路径 / 限流 / IP 白名单）
4. 后端服务重启 → 前端构建部署
5. Nginx reload / 容器重启（按变更段写明的**生效动作**执行）
6. 验证（含本版新增/删除的每项配置实际生效核验）
> ⛔ 升级**不执行** `sql/全量/` 下任何脚本

## 回滚方案
## 灰度发布
## 监控指标
```
