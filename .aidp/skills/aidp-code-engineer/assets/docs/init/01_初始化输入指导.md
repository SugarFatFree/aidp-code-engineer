## 1. 输入清单总览

```
必须提供（缺少会导致初始化不完整）：
  ✅ 项目名称和核心描述
  ✅ 产品需求文档（PRD），放在 docs/requirements/ 下

推荐提供（显著提升 AI 理解和输出质量）：
  📎 UI 静态原型代码，放在 docs/prototype/{version}/code/ 下
  📎 架构约束文档，放在 docs/architecture/ 下
  📎 前端脚手架代码放 code/frontend/{子项目}/（单/多项目都套 frontend/ 父目录）
  📎 后端脚手架代码放 code/backend/{子项目}/（单/多项目都套 backend/ 父目录）
  📎 环境配置文件，放在 env/.env

可选提供（有则更好）：
  📎 数据量级和性能要求
  📎 部署环境要求
  📎 合规和安全要求
  📎 团队成员和角色分工
```

## 2. 必需输入详解

### 2.1 项目名称和核心描述

**要求**：提供项目名称和 2~5 段话的核心描述，说清"做什么"、"解决什么问题"、"核心价值"。

可以直接在会话中粘贴，也可以写在 `docs/requirements/` 下的 PRD 文档中。

### 2.2 产品需求文档（PRD）

**路径**：★ 推荐版本级 `docs/requirements/{version}/产品提供/*.md`（产品交付的原始 PRD，可多文件多系统）；`docs/requirements/PRD-{项目名}.md` 为项目级兜底（版本级目录为空时使用）

> 💡 **自动归位**：若你把 PRD / 原型代码目录直接放在**项目根目录**，`aidp-code-engineer` init（Step 1.1.5）与 `/version`（Step 0）会**自动检测并询问**是否移动到上述 AIDP 目录（PRD→`产品提供/`、原型→`docs/prototype/{version}/code|mockup/`），确认后用 `git mv` 归位，无需手动搬。

这是初始化的最核心输入。PRD 应包含：

- 产品背景和目标
- 目标用户群体
- 核心功能模块列表（含优先级 P0/P1/P2）
- 各功能模块的详细描述
- 非功能需求（性能、安全、兼容性等）

> ⚠️ **PRD → 研发需求转化的两条防丢失约定**（AI 转化时严格遵守，`version-auditor` 审计 C Step C-4 据此反向核对、漏项 Critical 阻断）：
> 1. **逐条映射、非摘要式压缩**：PRD 里的**结构化表格**是需求的主要载体——「操作描述表」（操作/触发方式/前置条件/操作结果）、「列表字段说明表」（字段/说明/**备注**）、「展开明细表」等。转化必须**下探到每张表的每一行**：操作描述表**每个操作**（导出/导入/批量/审批/跳转…）、字段表**每个字段**都要承接，且字段的「**备注/展示规则**」列（如进度条分色阈值、绿色/琥珀色字体、脱敏规则）是该字段的**必带属性**，**不得只承接字段名而丢弃展示规则**。任何一条要"本版不做"必须经产品确认门**显式标注**，严禁静默丢弃（对齐核心约定 4「字段/列裁剪三件套」，从"原型字段"扩展到"PRD 条目"）。
> 2. **「遗留问题 / 迭代建议 / 待办」章节 = 需求输入，不是"已知缺陷备忘"**：PRD 中此类章节描述的是**本版或后续版本要补齐的能力**，必须**逐条**进入承接判定（本版做 / 后续版本 / 不做，均需留痕），**严禁**当作"原型已知缺陷记录"整段忽略。

## 3. 推荐输入详解

### 3.1 UI 资源（高保真图片 + 原型代码）

#### 3.1.1 高保真原型（视觉最高优先级）

**路径**：`docs/prototype/{version}/mockup/{module_name}/`

高保真原型来源有两种：
1. **人工提供**：设计师输出的高保真设计图（PNG/JPG 等图片）
2. **AI 自动生成**：当没有人工高保真图片、**且用户在 UI Agent 流程 A Step 0 显式选择情形 D 时**，UI Agent 在设计阶段基于原型代码 + UI 设计规范自动生成（⛔ 情形 A/B/C 下不得擅自生成——那会把一份臆造的视觉基线钉成 L1 严格对齐基准）（`.vue` / `.html` 文件）

**存放规范**：
- 按功能模块分目录存放
- 人工图片：命名建议包含页面名称，如 `industry-analysis.png`，支持 PNG、JPG、JPEG、SVG、WebP 格式
- AI 生成原型：命名与页面对应，如 `industry-analysis.vue`，使用项目实际技术栈

**优先级规则（4 情形 — 含 UI 设计规范维度）**：
> **情形 A — 有高保真原型（人工图片或 AI 生成）**：
> - **视觉/样式** → **严格按高保真原型实现**；**功能/交互** → 参考原型代码
>
> **情形 B — `mockup/` 无内容 + `docs/architecture/UI规范约束.md` 为空模板/缺失**：
> - 视觉/样式沿用 `code/` 原型代码自身样式，前端仅做项目技术栈替换；功能/交互参考 `code/`
>
> **情形 C — `mockup/` 无内容 + UI 设计规范有效 + 用户选"直接对齐原型"**：
> - 同情形 B（UI 规范留待后续优化）
>
> **情形 D — `mockup/` 无内容 + UI 设计规范有效 + 用户选"参考原型 + UI 规范优化"**：
> - ★ UI Agent 流程 C **基于 UI 规范优化原型样式**生成高保真到 `mockup/` → 之后按情形 A 执行
>
> 优先级排序：**人工高保真图片 > AI 生成高保真原型 > 原型代码（情形 B/C 作为视觉基准）**
>
> 情形 C/D 必须由用户显式选择（详见 `{{AIDP_HOME}}/agents/ui.md` 流程 A Step 0 询问 prompt）。

#### 3.1.2 原型代码（功能+交互参考）

**路径**：`docs/prototype/{version}/code/{module_name}/`

产品经理或设计师通过 vibe coding（如使用 Cursor/v0/Bolt 等工具）生成的静态页面原型代码。当有高保真图片时，原型代码**主要用于理解功能逻辑和交互行为**，而非视觉样式。

**存放规范**：
- 按功能模块分目录存放
- 保留完整的可运行代码（含 package.json、src/ 等）
- 原型代码可以是任何前端框架（React/Vue/纯 HTML），AI 会转换为项目实际技术栈

**AI 处理方式**：
- UI Agent 先检查 `docs/prototype/{version}/mockup/` 是否有对应模块的高保真原型
- **如无高保真原型**：按约定 4 的 4 情形决策树处置（见本文件 §3.1.1）——**仅情形 D（有 UI 规范 + 用户在 Step 0 显式选择「参考原型 + UI 规范优化」）** 才由 UI Agent 流程 C 生成到 `docs/prototype/{version}/mockup/{module}/`；情形 A/B/C 一律不生成（B/C 视觉沿用 `code/` 原型样式）
- UI Agent 读取原型代码，生成**组件映射清单**（原型组件 → 实际项目组件）
- Frontend Agent 视觉样式以高保真原型为准，功能交互以原型代码为准
- 原型中的 Mock 数据可转为后端初始化数据

### 3.2 架构相关文档（约束 + 架构设计）

**路径**：`docs/architecture/`（项目级全局，无版本前缀）

存放两类架构文档，读取时**全目录识别**（详见 `06_版本与用户目录约定.md` §2.1.1）：

**① 架构约束类**（全局技术约束/规范，初始化时导入，后续所有设计和开发必须遵循）：
- `架构约束.md` — 技术选型约束、分层架构约束、安全约束、性能约束等
- `UI规范约束.md` — 界面设计规范、品牌色彩、字体、间距等
- `技术选型.md` — 技术栈总览
- （可扩展）`编码规范.md` / `接口规范.md` 等

**② 架构设计类**（可选，项目级整体架构设计，区别于版本级 `docs/design/detail/{version}/*详细设计.md`，glob 兼容 `01_` 前缀名与历史裸名）：
- 单文档：`架构设计.md`
- 多文档：`架构设计/` 子文件夹（`00_索引.md` + `NN_*.md`，遵循约定 15）
- 存量任意命名的架构设计文档/子文件夹亦兼容识别，不强制改名

**AI 处理方式**：
- Architect Agent **全目录读取** `docs/architecture/`（约束 + 架构设计），在 `memory/systemPatterns.md` 中记录关键约束
- 架构设计文档作为详细设计的上游输入；架构约束优先级最高，所有设计和代码必须符合
- 项目记忆文件（AGENTS.md / CLAUDE.md）中列出 `docs/architecture/` 路径，确保每次会话可查阅

### 3.3 前后端脚手架代码

**路径**（统一规范，详见 `06_版本与用户目录约定.md` §2.5）：
- 前端：`code/frontend/{project-name}/`（单/多项目都套父目录；旧扁平 `code/web/` 仅 upgrade 兼容）
- 后端：`code/backend/{module-name}/`（单/多项目都套父目录；旧扁平 `code/server/` 仅 upgrade 兼容）

由开发者或 AI 预先生成的框架初始化代码，包含：
- 项目构建配置（pom.xml / package.json / vite.config.ts 等）
- 基础框架搭建（路由、状态管理、HTTP 封装等）
- 示例模块代码（作为新模块开发的参考）
- 开发规范文件（如 AGENTS.md）

**AI 处理方式**：
- Architect Agent 分析脚手架代码，提取技术栈信息到 `memory/techContext.md`
- Backend/Frontend Agent 参照已有模块的代码结构和编码风格开发新功能
- 保持与现有代码的一致性（包管理、分层结构、命名规范等）

### 3.4 环境配置

**路径**：`env/.env`

数据库连接信息、中间件配置、外部服务账号等。

**AI 处理方式**：
- 录入 `memory/techContext.md` 的环境配置章节
- 用于后端代码的 application 配置文件生成
- 注意：敏感信息不应出现在项目记忆文件中

## 4. 初始化过程各阶段说明

### Phase 0：★ 确定性骨架产出（先跑脚手架，⛔ 不可省）

**动作**：由 `aidp-code-engineer` 一次性建出全部目录骨架与模板文件。

**⛔ 不要手工 `mkdir` 补目录** —— 后续各 Phase 只在骨架上**填内容**、不负责建目录；手搓漏建（实际发生过 `sql/全量`、`产品提供/`）会让 `/sprint-start` 直接停在找不到目录上。

### Phase 1：PM Agent — 项目认知建立

**读取**：PRD 文档、项目描述

**输出**：

1. `memory/projectBrief.md` — 项目简介（北极星文件）
   - 项目名称、核心目标
   - 解决的核心问题
   - 目标用户
   - 项目范围
   - 关键成功指标

2. `memory/productContext.md` — 产品上下文
   - 核心功能模块列表（含优先级和状态）
   - 核心用户旅程
   - 产品约束和原则

### Phase 2：Architect Agent — 技术认知建立

**读取**：PRD、`docs/architecture/` 全目录（架构约束 + 可选架构设计文档）、脚手架代码、env 配置

**输出**：

1. `memory/systemPatterns.md` — 架构决策记录
   - 技术选型总览（从脚手架代码中提取）
   - 系统架构概述
   - 代码规范约定（从脚手架代码中提取）
   - 禁止事项（从约束文档中提取）
   - 初始 ADR

2. `memory/techContext.md` — 技术上下文
   - 运行环境要求
   - 快速启动命令
   - 环境变量说明
   - 外部服务依赖
   - 脚手架代码结构说明

3. `memory/databaseBaseline.md` — 累积数据库基线
   - 如已有数据库表（从脚手架或 SQL 脚本中检测），记录到基线
   - 如为全新项目，创建空基线文件（表清单为空）
   - 后续每个 Sprint 设计数据库表前必须先读取此文件

### Phase 3：UI Agent — 原型认知建立（可选）

**读取**：UI 原型代码、UI 规范约束

**输出**：
- 原型代码分析结果
- 组件映射清单（原型组件 → 项目技术栈组件）
- 回填 `docs/architecture/UI规范约束.md` 初版（从原型代码提取视觉特征：色板 / 字号 / 间距 / 圆角 / 阴影等设计令牌）

*注：如果没有 UI 原型代码，此阶段跳过。*

### Phase 4：PM Agent — 完成初始化

**输出**：

1. `memory/{version}/{user}/activeContext.md` — 初始状态
2. `memory/{version}/{user}/progress.md` — 初始进度（所有功能为"未开始"）
3. `AGENTS.md` — 主入口文件（Claude Code 下为 `CLAUDE.md`；本体由脚手架 `scaffold.py` 从模板渲染；命令只**回填**「当前状态」区）

## 5. 初始化完成后的验收检查

初始化完成后，发送以下提示词进行验收：

```
请执行初始化验收检查：

1. 列出 memory/ 目录下所有文件，确认以下文件都已生成：
   - projectBrief.md
   - productContext.md
   - systemPatterns.md
   - techContext.md
   - databaseBaseline.md
   - activeContext.md
   - progress.md

2. 确认 AGENTS.md 存在且包含：
   - 项目描述
   - 当前状态
   - Agent 路由表
   - 初始化输入文件清单

3. 读取 memory/{version}/{user}/progress.md，确认功能模块都已列出

4. 检查 memory/systemPatterns.md，确认技术栈信息与脚手架代码一致

5. 如有缺失，立即补充生成

输出验收结果：✅ 通过 / ❌ 缺失（列出缺失内容）
```
