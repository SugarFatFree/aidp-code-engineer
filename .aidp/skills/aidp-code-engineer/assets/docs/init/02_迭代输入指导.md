## 1. 迭代机制概述

### 1.1 两阶段流程

```
阶段 A：版本规划期（一次性）
  /version V0.1.0 "M1 MVP"
    ├─ /sprint-requirements → 01_研发需求.md（整个版本的需求）
    ├─ /sprint-design       → 详细设计 / 接口设计 / 数据库设计.md（按需可扩展安全/缓存/集成等专题）
    ├─ /sprint-plan         → 01_研发执行计划.md（Sprint 拆分 + 任务分配）
    └─ /sprint-selftest     → docs/testing/{version}/研发自测/（研发自测方案 + 用例 + 测试环境与账号）

阶段 B：Sprint 执行期（四种执行模式，详见 00_AIDP范式主文档.md §6.2）
  模式 1 ：/sprint-batch        批量执行多个 Sprint
  模式 2A：/sprint-full {NNN}   单 Sprint 一键（按计划）
  模式 2B：/sprint-full "<描述>" 自动累进（首轮后新增功能 / 修复）
  模式 3 ：/sprint-start → /sprint-dev → /sprint-test → /sprint-bugfix → /sprint-close

阶段 C：发布
  /version V0.1.0           所有 Sprint 完成后打 tag
```

### 1.2 各阶段输入来源

| 阶段 | 命令 | 主要输入 | 人类需要提供 |
|------|------|---------|------------|
| 版本规划 | `/version` | PRD、原型代码、项目上下文 | 版本号、里程碑名称 |
| 批量执行 | `/sprint-batch` | 01_研发执行计划.md + 详细设计 | 基本无需输入（阻塞时介入）|
| 单 Sprint 一键 | `/sprint-full` | 同上 | Sprint 编号 |
| 分步-启动 | `/sprint-start` | 已规划的需求和设计文档 | Sprint 编号 |
| 分步-开发 | `/sprint-dev` | 详细设计、API 设计、脚手架 | 范围参数（backend/frontend/all） |
| 分步-测试 | `/sprint-test` | 需求、代码 | 基本无需输入 |
| 分步-修复 | `/sprint-bugfix` | bug 记录文件 | Sprint 范围 |
| 分步-关闭 | `/sprint-close` | 测试结果 | 验收确认 |

> **关于版本号**：命令内部会尝试从 `AGENTS.md` 当前状态读取；读不到会询问用户。
> 一旦确认，同会话内所有路径都会沿用。切换版本需显式指定参数或更新项目记忆文件（AGENTS.md / CLAUDE.md）。

## 2. 版本规划期（一次性）

**命令**：`/version V0.1.0 "M1 MVP"`

**需要提供的输入**：
- ✅ 版本号（必需，格式 V{major}.{minor}.{patch}）
- ✅ 里程碑名称（必需，例 "M1 MVP"）
- 📎 PRD 文档：`docs/requirements/{version}/产品提供/*.md`（★ 推荐，版本级）或 `docs/requirements/PRD-*.md`（兜底，项目级）
- 📎 原型代码：`docs/prototype/{version}/code/`（推荐）
- 📎 高保真原型：`docs/prototype/{version}/mockup/`（推荐）

**执行示例**：
```
/version V0.1.0 "M1 MVP"
```

**内部串联执行**：
1. `/sprint-requirements` 调用 `ux-logic-extractor` → `docs/requirements/V0.1.0/研发需求/01_研发需求.md`
2. `/sprint-design` 调用 `dev-logic-architect` → `docs/design/detail/V0.1.0/*.md`（SQL 落 `docs/deployment/V0.1.0/sql/增量/`，见 06 §2.5）
3. `/sprint-plan` 调用 `dev-execution-planner` → `docs/plans/V0.1.0/01_研发执行计划.md`
4. `/sprint-selftest` 调用 `dev-manual-testcase` → `docs/testing/V0.1.0/研发自测/`（研发自测方案 + 用例 + 测试环境与账号）

**完成后人工可审核的文档**：
- 需求文档：功能模块、验收标准、非功能需求（**不含** Sprint 拆分与排期）
- 详细设计：模块结构、API 设计、数据库设计、公共组件清单
- 研发执行计划：Sprint 拆分、任务分配、依赖关系、风险评估、时间估算

如需重新生成某份文档，可单独调用子命令：
```
/sprint-requirements    # 重新生成需求
/sprint-design          # 重新生成设计
/sprint-plan            # 重新生成计划
/sprint-selftest        # 重新生成研发自测
```

## 3. Sprint 执行期 - 模式 1 批量执行

**适用场景**：★ 首次全量跑，规划文档齐全，希望一条命令从开发到测试全部自动化。

**命令**：`/sprint-batch [范围] [skip-bugfix]`

**需要提供的输入**：基本无需输入（版本规划文档齐全即可）

**参数**（完整清单以 [`{{AIDP_HOME}}/commands/sprint-batch.md`](../../{{AIDP_HOME}}/commands/sprint-batch.md) 为准）：
- 为空：从 01_研发执行计划.md 读取所有未完成的 Sprint
- `001-003`：执行 Sprint-001 到 Sprint-003
- `002-`：从 Sprint-002 开始跑到最后
- `skip-bugfix`：跳过 Sprint 内 bugfix 循环，所有 bug 留到最后统一修
- `--skip-context-check`：跳过 Step 0.0 上下文压缩建议
- `--stop-on-blocker`：遇阻即停（bugfix 循环超限就暂停；默认非阻塞继续）
- `--skip-aiauto-test`：跳过 Step 6 浏览器仿真测试整合（纯开发模式）
- `--auto-aiauto-test`：Step 6 跳过"是否跑 AI 自动化测试"询问门，直接部署确认 + 执行
- `--unattended`：无人值守标记，透传给每个 `/sprint-full → /sprint-dev`，内部决策门改为消费 PRD `autopilot_decisions` 预声明、不弹窗

> ⛔ **`--select <mode>` 不是 `/sprint-batch` 的参数**，它只属 `/sprint-aiauto-test`（`all` 全量 / `smoke` 仅 P0 / `regression` 仅带 `[回归]` 标记，默认 `all`）；`/sprint-batch` Step 6 调起 `/sprint-aiauto-test` 时**强制 `all`、忽略该参数并告警**——子集会让「通过率」「P0=100%」只对子集成立。  <!-- flag-check: ignore -->

**执行示例**：
```bash
/sprint-batch               # 全部 Sprint
/sprint-batch 001-003       # 前 3 个
/sprint-batch skip-bugfix   # 跳过 bugfix 循环
```

**末段 Step 6（Sprint 全部跑完后）**：询问是否部署 + 调 `/sprint-aiauto-test --once` 跑浏览器仿真测试；失败用例回写"问题汇总清单"交 `/sprint-bugfix`。`--skip-aiauto-test` / `--auto-aiauto-test` 可分别跳过或免询问。

**停止场景（默认软失败继续，仅硬失败停）**：
- **软失败 → 记入"待人工处理清单"后继续下一个 Sprint**：bugfix 循环超过 5 次仍有未修复 / 测试用例存在失败 / 验收 Critical 问题。仅 `--stop-on-blocker` 时才即停
- **硬失败 → 停止批量执行**：编译或前端校验失败 / 设计文档中找不到某 Sprint 的任务

## 4. Sprint 执行期 - 模式 2 单 Sprint 一键

**命令**：`/sprint-full`

**有两种子模式**：

### 4.1 模式 2A：按计划执行

**适用场景**：想跑完一个已规划的 Sprint 后手动审核结果。

**命令**：`/sprint-full {NNN} [skip-bugfix]`

**执行示例**：
```bash
/sprint-full 001            # 跑完 Sprint-001
/sprint-full 002 skip-bugfix
```

### 4.2 模式 2B：自动累进

**适用场景**：首轮规划的 Sprint 全部完成后，用户想继续新增功能或修复较大 bug，不想手动维护 Sprint 序号和设计文档。

**★ 前提（当前版本未发布）**：自动累进仅在当前版本【未发布】时适用。当前版本【已发布】时，累进前先过「版本落点决策门」三选一（落回已发布版重发 / 新开 patch / 新开 minor），绝不静默往已发布版本累进（单一信源见约定 2 / `/sprint-dev` Phase 0B.0）。

**命令**：`/sprint-full "<目标描述>" [skip-bugfix]`

**执行示例**：
```bash
/sprint-full "新增用户导出功能"
/sprint-full "修复批量导入重复校验逻辑"
/sprint-full "重构菜单加载性能" skip-bugfix
```

**自动化流程**（用户无需手动操作）：

1. **计算新 Sprint 序号**：`python3 {{AIDP_HOME}}/scripts/check_sprint_numbering.py next`（**跨全部版本**扫描取 MAX+1）——⛔ **严禁**自己 glob `memory/{version}/{user}/sprints/` 取 MAX：那个路径带 `{version}` 限定，新版本目录天然为空、必然算出 001（下游实测过的真实缺陷）。判据单一信源见 `06_版本与用户目录约定.md` §3.3
2. **产出增量文档（⛔ 不改主文档正文）**：复用 `/sprint-dev` Phase 0B.1.1 的同一套机制（单一信源，细则不在此复述）——把本次变更转化为**独立补充文档** `NN_<业务主题>.md` 落进各目录，并在该目录 `00_索引.md` 登记；**绝不**往主文档末尾内联追加章节（那会破坏约定 15 的 append-only 审计轨）
3. **级联必须四级齐全**：**L1 研发需求 → L2 详细设计 → L3 研发执行计划 → L4 研发自测用例**（约定 22），⛔ 不可只补前三级而漏 L4
4. **追加 SQL**：如有数据库变更，按"中文名 + 两位数字序号前缀"规范新增到 `docs/deployment/{version}/sql/增量/{NN}_<中文名>.sql`（`99_回滚脚本.sql` 序号保留；详见 `06_版本与用户目录约定.md` §2.5.4 与 `dev-logic-architect` SKILL Module D）
5. **更新计划**：在 `docs/plans/{version}/01_研发执行计划.md` 追加 Sprint 拆分行
6. **执行 Sprint**：完整跑 start → dev → test → bugfix 循环 → close

**典型输出**：
```
🎉 /sprint-full "新增用户导出功能" 完成（自动累进 Sprint-006）

📋 增量追加的文件：
- docs/requirements/V0.1.0/研发需求/NN_<业务主题>.md（独立增量文档）+ 00_索引.md（登记）
- docs/design/detail/V0.1.0/NN_<业务主题>.md（独立增量文档：设计 / 表 / 接口同主题合一）+ 00_索引.md（登记）
- docs/deployment/V0.1.0/sql/增量/{NN}_<中文名>.sql（新增 DDL；例 `03_订单表新增字段.sql`）
- docs/plans/V0.1.0/NN_<业务主题>.md（独立增量文档，含 Sprint-006）+ 00_索引.md（登记）

各阶段摘要：
  Phase 0B：✅ 增量文档已追加
  Phase 1-5：✅ 完成
```

### 4.3 模式 2A vs 2B 对比

| 维度 | 模式 2A（按计划）| 模式 2B（自动累进）|
|------|-----------------|-------------------|
| 参数 | Sprint 编号（数字） | 目标描述（字符串）|
| 前置 | 研发执行计划 中已规划 | 无需预先规划 |
| 文档更新 | 不追加（已在规划期完成） | 自动追加增量到版本级文档 |
| Sprint 序号 | 用户指定 | 自动累进（max + 1）|
| 适用 | 规划期排好的 Sprint | 首轮完成后继续迭代 |

## 5. Sprint 执行期 - 模式 3 分步执行

**适用场景**：需要在每个阶段后人工审核、讨论或调整。

### 5.1 启动 Sprint（PM Agent）

**命令**：`/sprint-start {NNN}`

**标准提示词**：
```
请执行 /sprint-start 001

该命令会自动：
1. 读取 docs/requirements/V0.1.0/研发需求/01_研发需求.md 中 Sprint-001 的任务范围
2. 读取 docs/plans/V0.1.0/01_研发执行计划.md 中的任务分配
3. 更新 memory/V0.1.0/{user}/activeContext.md
```

### 5.2 开发阶段（Backend + Frontend Agent）

**命令**：`/sprint-dev [backend|frontend|all]`

**标准提示词（全栈）**：
```
请执行 /sprint-dev

该命令会自动：
- 调用 superpowers:test-driven-development 做 TDD 开发
- 调用 superpowers:subagent-driven-development 前后端并行
- 按 docs/design/detail/V0.1.0/ 的设计实现代码
```

**仅后端或仅前端**：
```bash
/sprint-dev backend
/sprint-dev frontend
```

### 5.3 测试阶段（QA Agent）

**命令**：`/sprint-test`

**标准提示词**：
```
请执行 /sprint-test

该命令会自动：
- 调用 code-verification-loop skill 做核心验收
- 浏览器仿真测试（chrome-devtools-mcp）由独立命令 `/sprint-aiauto-test` 承担（独立测试链路，部署完成后跑），不在本命令内置
- 发现的 bug 写入 docs/bugfix/V0.1.0/bugfix-{YYYYMMDD}-{user}.md
```

### 5.4 修复阶段（Backend/Frontend Agent）

**命令**：`/sprint-bugfix sprint-001`

**标准提示词**：
```
请执行 /sprint-bugfix sprint-001

该命令会自动：
- 调用 bugfix skill 处理问题
- 调用 superpowers:systematic-debugging 分析根因
- 回填 bug 文件的修复信息
- 执行回归测试
```

### 5.5 Sprint 关闭（PM Agent）

**命令**：`/sprint-close 001`

**标准提示词**：
```
Sprint-001 验收结果：
功能1：✅ 通过
功能2：✅ 通过
功能3：⚠️ 部分通过，xxx 问题已记录

请执行 /sprint-close 001
```

## 6. 问题修复迭代（Bugfix）

### 6.1 问题记录流程

1. **人工发现问题**（或由 `/sprint-test` 自动记录）→ 在 `docs/bugfix/{version}/` 下创建/追加到 `bugfix-{YYYYMMDD}-{user}.md`
2. **文件命名**：一天一人一份汇总（如 `bugfix-20260509-alice.md`）
3. **文件结构**：
   - 标题 `# Bugfix {YYYYMMDD} - {user}`
   - **Bug 清单表格**（文件开头，必需）
   - 每个 Bug 的详情章节

### 6.2 Bug 清单表格格式

```markdown
| 编号 | 时间 | Sprint | 模块 | 现象 | 严重 | 优先级 | 难易 | 状态 | Commit | 备注 |
| :-: | :- | :-: | :- | :- | :-: | :-: | :-: | :-: | :- | :- |
| B-20260509-01 | 2026-05-09 | Sprint-001 | 后端-登录 | 登录返回 500 | P0 阻塞 | 高 | 简单 | Fixed 已修 | `abc123` | Token 密钥未配置 |
```

**字段说明**：
- 严重：P0 阻塞 / P1 严重 / P2 一般 / P3 轻微
- 优先级：高 / 中 / 低
- 难易：简单 / 中等 / 困难
- 状态：Open 待修 / In-Progress 修复中 / Fixed 已修 / Verified 已验证 / Closed 已关闭 / Reopened 回归
- **Sprint**：该 bug 归属的 Sprint 序号（可选，支持跨 Sprint 修复场景）

### 6.3 Bug 详情章节格式

每个 Bug 在表格后单独一个章节：

```markdown
# B-20260509-01: 登录接口返回 500 错误（Sprint-001）

## Bug 现象（用户原话）
> {用户反馈原文}

## 影响范围
- 端：{前端/后端/全栈}
- 页面：{涉及页面}
- Sprint：Sprint-001

## Root Cause
{AI 分析的根本原因，含代码级定位}

## 改动文件
### `{文件路径}`
- 第 XX 行：{修改说明}

## 验证步骤
1. ...

## 部署提醒
- **前端**：{是否需要重新构建}
- **后端**：{是否需要重启}

## Commit
- Commit hash: `{hash}`
```

完整模板见 `00_AIDP范式主文档.md` 第 7 节。

### 6.4 修复迭代触发方式

**场景 1：自动触发**（内嵌在 Sprint 流程中）
- `/sprint-full` 或 `/sprint-batch` 的 Phase 4 自动调用 `/sprint-bugfix` 循环

**场景 2：独立使用**（★ 推荐用于零散 bug）
```bash
# 在 docs/bugfix/{version}/bugfix-{YYYYMMDD}-{user}.md 添加 bug 条目
# 然后直接修复，无需 Sprint 依赖
/sprint-bugfix                                          # 修复当前用户所有待修复 bug
/sprint-bugfix sprint-001                                # 仅修复归属 Sprint-001 的 bug（按表格 Sprint 列过滤）
/sprint-bugfix bugfix-20260509-alice.md                   # 仅处理指定文件
```

**场景 3：较大功能性 bug**（需要设计变更）
- 走 `/sprint-bugfix "<bug 描述>"`（较大 bug 由它自动累进新 Sprint）——⛔ **不要顶替成 `/sprint-full` 模式 B**：`commands/sprint-full.md` 明写「bug 修复优先用 `/sprint-bugfix`（意图匹配、缺陷登记/复现更完整）」，约定 2 与意图路由亦指向它
- 因为涉及设计调整、接口变更等，需要完整流程

**选择建议**：

| Bug 类型 | 推荐命令 |
|---------|---------|
| 配置错误、单文件修复、明显 bug | `/sprint-bugfix` |
| 跨多文件修改、涉及接口变更 | `/sprint-bugfix` 也可以，自行评估 |
| 需要新增字段/表/接口 | `/sprint-bugfix "<描述>"`（较大 bug 自动累进新 Sprint）|
| 需要重构、架构级调整 | `/sprint-bugfix "<描述>"`（较大 bug 自动累进新 Sprint）|

## 7. 需求变更的处理方式

### 7.1 Sprint 内的小变更

不新增工作量的微调：

> ⚠️ **落盘形态走约定 22 攒批**：变更**先按族追加**到 `_开发期{族}增量.md`（四族落点见详规），
> 由**收口点**批量级联到「研发需求 → 详细设计 → 研发执行计划 → 研发自测用例」四级；
> ⛔ **开发过程中不当场改主文档正文**。口径被推翻（而不只是追加）时另按**约定 34** 清算旧结论。
> 收口点清单与台账格式的单一信源 = `{{AIDP_HOME}}/reference/开发期族增量.md`。

记录形态：

```
需求微调：功能 XXX
原始需求：{原始描述}
调整为：{新描述}

请更新对应的需求文档和设计文档，
并在 memory/{version}/{user}/activeContext.md 中记录此变更。
```

### 7.2 Sprint 内的大变更

影响较大的变更，需要评估后决定：

```
需求变更评估请求：

变更内容：{描述变更}
提出原因：{变更原因}

请评估：
1. 工作量影响
2. 对现有设计的影响
3. 建议方案：本 Sprint 内完成 / 移到下一 Sprint

评估后我来决定。
```

### 7.3 跨 Sprint 的需求变更

跨 Sprint 的需求变更：

```
PRD 变更通知：

{描述变更内容和原因}

请更新：
0. 受影响各族的 _开发期{族}增量.md 追加条目（约定 22 攒批，⛔ 先记册子再谈其余）
1. docs/requirements/{version}/产品提供/*.md（版本级，优先）或 docs/requirements/PRD-{项目名}.md（项目级兜底）
2. memory/productContext.md（项目级）
3. memory/{version}/{user}/progress.md（若涉及我负责的模块）
4. memory/{version}/{user}/activeContext.md 中记录此决策
```

## 9. 提交与推送

日常开发只按 AIDP 流程正常提交代码；以下三条约定在每次提交 / 推送时生效（详规见项目记忆文件 AGENTS.md / CLAUDE.md 对应约定）。

### 9.1 提交信息（约定 13）

### 9.2 提交前门禁（约定 24）

```bash

```

## 10. 文档输出约定（通用）

适用于所有 `/sprint-*` 命令、`/version` 生成的文档；后续新增命令默认遵守。

### 10.1 语言

- **正文中文为主**：章节标题、表格表头、描述性文本、注释、术语解释一律中文
- **保持原样不翻译**：
  - API 路径与 HTTP 方法（`GET /api/v1/users`）
  - 类/函数/变量/字段/列名
  - SQL 语句、JSON / YAML / TOML / .env 配置项键
  - 代码块（```...```）整体
  - 第三方专有名词：React / Vue / Vite / Element Plus / UnoCSS / Spring Boot / Mybatis / Redis / Nacos / Kubernetes 等
- **混排原则**：专有名词周围用中文语境包裹，例："调用 SSO 的鉴权接口"而非"call SSO auth API"

### 10.2 同类多文件编号规则

当同一类型文档因以下场景生成 ≥2 份时，**文件名必须以两位数字前缀排序**。

| 场景 | 示例 | 编号方式 |
|------|------|---------|
| 单次产出过长被拆分 | PRD/详细设计按模块或主题分册 | `01_业务流程.md` / `02_数据模型.md` / `03_接口约束.md` |
| 多次复查 / 自检 | 同一 Sprint 的检查报告 | `check-01.md` / `check-02.md` |
| Sprint 内补丁 | 需求或设计追加 | `NN_<业务主题>.md`（约定 15 统一数字前缀，文件名不带"补充"字眼，补充身份记入 `00_索引.md`，NN 续编主文档最大序号）|
| 架构文档细分 | `docs/architecture/` 下**新增的扩展文档**（三件套之外，如编码规范 / 接口规范）| `01_编码规范.md` / `02_接口规范.md`（⛔ **架构三件套 `架构约束.md` / `技术选型.md` / `UI规范约束.md` 为固定名、不加序号前缀**——它们被 4 个脚手架脚本硬编码、全仓约 250 处引用，改名即全线断裂；见 06 §2.1.1）|
| 架构设计多文档 | `docs/architecture/架构设计/` 子文件夹（区别于单文档 `架构设计.md`）| `00_索引.md` / `01_xxx.md` / `02_xxx.md`（见 06 §2.1.1）|

**规则细节：**

1. **数字固定 2 位 + `00_` 专职导航锚**：`00_` 槽位给**专职导航锚**；`01_` ~ `99_` 用于内容主文档 / 分册 / 补充内容；不足两位补 0；超 99 份应优先**合并**而非细分。（详见约定 15）★ 四类版本规划文档**恒有专职导航锚 + 内容主文档从 `01_` 起**（不再有裸 `00_<语义名>.md` 作内容主文档）。**导航锚 = `00_索引.md`（唯一，⛔ 非二选一：里程碑拆分态同样用它；`00_研发执行计划-总览.md` 仅识别存量、新生成不产）**：研发需求 / 详细设计 / 研发执行计划（单文件态与里程碑拆分态同）/ **研发自测目录**（已随上游 dev-manual-testcase 对齐：`00_索引.md` + `01_研发自测方案.md` + 用例从 `02_` 起）。旧锚 `00_研发自测方案.md`（研发自测方案占 `00_`、无 `00_索引`）grandfather 兼容识别。
2. **`00_索引.md` 三项必载**：① 文件目录清单（本目录全部 `NN_*.md` 内容文档路径 + 一句话范围）② 每份文件生成时间（`YYYY-MM-DD HH:MM`）③ 主/补充标识（首次规划 = `主`，后续增量 = `补充`，补充身份只靠索引列 + 更晚生成时间区分、不进文件名）；内容主文档生成即 `01_<语义名>.md`，第 2 份起 `02_`/`03_` 续编。历史存量裸 `00_<语义名>.md` 单主文档兼容识别、新生成不采用。
3. **顺序语义**：`00_` 是索引；`01_`~`99_` 表示**阅读顺序**或**生成顺序**（取决于上下文），由生成命令在文件首段明确。
4. **不重复编号**：已按日期命名的文件（如 `bugfix-YYYYMMDD-{user}.md`）已用日期排序，**不再额外加数字前缀**。
5. **目录优先**：能用子目录隔离的不要用前缀。如多个 Sprint 的测试报告分别放在 `docs/testing/{version}/sprint-001/` `sprint-002/`，每个目录内文件不需要全局编号。

### 10.3 不符合时的处理

- Claude 在执行命令期间发现旧文件未编号但本次要生成第 2 份 → 先把旧文件重命名为 `01_xxx.md`，再生成 `02_yyy.md`
- 命名涉及外部引用（其他文档/脚本引用了原文件名）→ 同步更新所有引用处的链接


### 10.4 /version 主产物的拆分指引

`/version` 体系默认生成「需求 / 详细设计目录 / 研发执行计划 / 研发自测」四类主产物（详细设计目录含 详设/接口/数据库 等自由命名文件，故下表按 3 类列）。当任一产物内容超出建议阈值时，**生成命令必须主动拆分**并按 约定 15 编号；阈值是**软指引**，跨度小可不拆，但跨度大必须拆。

| 文档 | 默认单文件路径 | 触发拆分的阈值 | 拆分方式 | 命名示例（同目录下） |
|------|---------------|---------------|---------|---------------------|
| 需求 | `docs/requirements/{version}/研发需求/00_索引.md` + `01_研发需求.md` | 拆分触发条件以 `ux-logic-extractor` SKILL 为单一信源（命令端不另立数值阈值）或 ★多系统 | 按业务模块 / 按系统 | `00_索引.md` + `01_用户模块.md` / `02_订单模块.md`（或 `01_<系统A>.md` / `02_<系统B>.md`）|
| 详细设计目录 | `docs/design/detail/{version}/` 恒有 `00_索引.md` + 内容 `01_` 起（详见下方说明）| 恒有专职索引，内容多专题分文件 | 按主题/模块分文件 | `00_索引.md` + `01_详细设计.md` / `02_数据库设计.md` / `03_接口设计.md` / `04_对外开放接口.md` / `05_集成对接.md` / … + `98_事实清单.md`（如有）+ `99_待澄清问题清单.md`（如有）。历史存量并列态裸名（`详细设计.md`+`接口设计.md`）/ 单份态 `00_<专题>.md` 仍被识别放行、新生成不采用。研发自测方案现归 `docs/testing/{version}/研发自测/`|
| 研发执行计划 | `docs/plans/{version}/00_索引.md` + `01_研发执行计划.md` | **阈值以 `dev-execution-planner` SKILL 为单一信源**（>800 行/60KB、Task>40、单 Phase Task>15）——⛔ 命令端不另立数值阈值 | 按 **Phase**（⛔ 不是里程碑） | `00_索引.md` + `01_研发执行计划.md` / `02_<Phase名>.md`；多用户为 `NN_研发执行计划-{开发者}.md` |
| 研发自测 | `docs/testing/{version}/研发自测/00_索引.md` + `01_研发自测方案.md` | **阈值以 `dev-manual-testcase` SKILL 为单一信源** | 按套件 / 用例量 | `00_索引.md` + `01_研发自测方案.md` / `02_全量自测用例.md`；`98_跨系统验证清单.md`、`99_待澄清问题清单.md` 序号固定 |

> **★ 详细设计目录约定**（本段为迭代输入期速览；**索引态目录/命名规则的权威单一信源 = 06 §2.2 + `dev-logic-architect` SKILL「多文件拆分」+ `check_doc_split.py`，口径冲突一律以其为准、勿在本段另立规则**）：不固化"必出 3 份（详细设计/接口设计/数据库设计）"，而是"专题自由 + 约定命名 + ≥2 份即拆分态"：
> - **目录唯一**：所有详细设计文档都在 `docs/design/detail/{version}/` 下
> - **文件名中文 + 自描述**：以主题命名（详细设计/接口设计/数据库设计/安全设计/缓存设计/集成对接/消息异步设计/部署架构/性能设计/...）
> - **基础骨架（推荐）**：至少详细设计；有 API 则接口设计；有数据库则数据库设计
> - **★ 恒有专职索引态**：目录**恒生成 `00_索引.md`（导航 + 文件清单 + 生成时间 + 主/补充标识）**，内容主文档从 `01_` 起——单专题 = `00_索引.md` + `01_详细设计.md`；多专题 = `00_索引.md` + `01_详细设计.md`/`02_数据库设计.md`/… + `98_事实清单.md`（如有）+ `99_待澄清问题清单.md`（如有）。历史存量并列态裸名 / 单份态 `00_<专题>.md` 仍被 `check_doc_split.py` 识别放行，新生成不采用。
> - **同主题超阈值再拆**：单主题文档过大（如详细设计 >10 模块）→ 按 约定 15 拆 `01_<模块>-详细设计.md` + `02_<模块>-详细设计.md`
> - **下游兼容**：sprint-dev/test/bugfix 通过 glob `docs/design/detail/{version}/*.md` 全量加载，不依赖固定文件名

> **需求文档的输入侧**：源 PRD 放在 `docs/requirements/{version}/产品提供/` 下；`/sprint-requirements` 读取并融合后输出到 `研发需求/`。**「产品提供」与「研发需求」是输入/输出分离，不参与 约定 15 编号**。

**拆分时的统一约束：**
1. **目录不变**：拆分后的文件仍放在原目录（`docs/requirements/{version}/研发需求/` / `docs/design/detail/{version}/` / `docs/plans/{version}/`）。
2. **必有索引**：拆分后必须在原目录追加 `00_索引.md`（开头数字 `00` 保持索引文件排首位），列出所有分册的标题、范围、对应 Sprint。
3. **下游兼容**：`/sprint-dev` / `/sprint-test` / `/sprint-bugfix` 等下游命令需读取**全部分册**（通过 glob `docs/.../{version}/[0-9][0-9]_*.md`——⛔ 不可写 `0?_*.md`：那只覆盖 `00_`–`09_`，而本规范的序号可到 `99_`，第 10 册起会被下游命令整批漏读）。
4. **跨版本增量**：`/sprint-design` 在做跨版本增量设计时，沿用前一版本的拆分粒度；上版未拆而本版需要拆 → 一并把上版重命名为 `01_xxx.md` 并补充索引。
5. **不要过度拆分**：阈值是参考，宁可不拆也不要拆出过小的分册。**具体最小分册阈值不在本段规定**——以 `dev-logic-architect` SKILL「多文件拆分」+ `check_doc_split.py` 为单一信源。

### 10.5 补充文档的 append-only + 结论取代标记双机制

`/version` 补充模式（B-2）对版本规划主产物采用 **append-only**：每轮产品 PRD / 原型变更只**新增** `NN_<业务主题>.md`（文件名不带"补充"字眼）+ 各目录 `00_索引.md` 登记（类型=补充 + 生成时间），**前序补充文档的正文永不删除 / 改写**（保全完整审计轨迹）。但纯 append-only 有一个读者陷阱——当后一轮的结论**推翻 / 修订**前一轮时，前序文档里的旧结论字面仍在、若无失效标记，读者只能靠"按时间倒序自行合并"判断现行结论，极易被旧表述误导（典型："第三方接口未交付，本期 Mock、不实现后端"在第三方交付后仍字面残留）。

为此补充模型区分两类补充，叠加"取代标记"自动化：

| 类型 | 场景 | 处置 |
|------|------|------|
| **A 纯增量** | 新增功能 / 接口 / 字段，不触碰前序任何结论 | 维持现状——仅追加 `NN_<业务主题>.md` + `00_索引.md` 一行 |
| **B 结论取代** | 后一轮推翻 / 修订前一轮判断（`Mock→真实` / `待确认→已确认` / `作废·取消` / 数据来源或接口契约变更 / 字段从无到有 等反转性变更）| 在**不动前序正文**前提下追加"取代标记" |

**B 类的取代传播**（由 `/version` Step 2.4.5.6 自动执行，依据 `输入变更-NN.md`「四、对前序结论的影响」表 + 各补充类 SKILL `--supplement` 产物的「对前序的修订」段）：
1. 后一轮补充文档头部含「对前序的修订」段（声明取代了哪一轮、哪些 REQ / 章节、由什么旧结论改成什么新结论）；
2. 被取代的前序补充文档**追加** 🔄 横幅（文档顶部一条 + 被取代章节标题下一条，指向现行结论链接）；
3. `00_索引.md` 登记「取代关系」列（如 `02 取代 01 的账单明细部分`）+ 被取代前序行「状态」标 `⚠️ 部分被 NN 取代`。

**核心不变量**：永不删除 / 改写前序补充文档正文，只**追加**失效横幅与取代关系登记。仅作用于**新触发**的取代场景；存量已漂移文档"改到哪标到哪"，不强制回溯。完整性由 `version-auditor` 审计 E-07 核验（缺横幅 / 缺清单标记 → warn，不阻塞）。
