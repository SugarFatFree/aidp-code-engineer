# /bugfix — 问题修复全流程技能

## 触发条件

当 `docs/bugfix/` 下有待修复的问题记录，需要执行分析、修复代码、验证和归档时触发。

## 输入

- `$ARGUMENTS`：Sprint 编号（可选）和问题文件名（可选）
  - 示例：（空）— **零散模式**：处理 `docs/bugfix/{version}/` 下全部「待修复」条目，不按 Sprint 过滤（约定 3 的零散 bug 没有 Sprint 编号）
  - 示例：`sprint-001` — 只处理 Sprint 列标注为 Sprint-001 的待修复条目
  - 示例：`sprint-001 bugfix-20260304-alice.md` / `bugfix-20260304-alice.md` — 仅处理指定问题文件
- 问题记录文件为 `docs/bugfix/{version}/` 下（含子目录）的 `bugfix-{YYYYMMDD}-{user}.md`。**这是本 SKILL 唯一的输入面**：其他来源（测试问题汇总清单、AI 测试失败清单、Issue 等）由调用方先落成这里的条目（带来源回链）再调用，本 SKILL 不扫其他目录。

## 前置条件

1. `docs/bugfix/{version}/` 目录下（含子目录）存在 `bugfix-*.md` 问题记录文件
2. `docs/init/00_AIDP范式主文档.md` 存在（用于确认文档归档范式）
3. 项目代码目录 `code/frontend/` / `code/backend/` 存在

## 执行步骤

### Step 1：读取项目规范与背景信息

读取以下文档，提取修复所需的项目上下文：

```
docs/init/00_AIDP范式主文档.md  → 提取：
  - 文档归档范式与命名规则（第7节 Bugfix Cycle）
  - 项目整体目录结构（第2节）
  - 前后端技术栈与模块划分
```

如果 `memory/` 目录下存在以下文件，也一并读取（`{version}` / `{user}` 由调用方给出；**迭代级文件按版本 + 用户双层隔离**，项目级文件在 `memory/` 根）：
```
memory/{version}/{user}/activeContext.md   → 当前 Sprint 状态（迭代级，版本+用户双层隔离）
memory/techContext.md                     → 技术环境与启动命令（项目级）
memory/systemPatterns.md                  → 技术决策与架构约束（项目级）
```

### Step 2：扫描并解析问题记录

**2.1 定位问题文件**

扫描目录：
```
docs/bugfix/{version}/
```

在该目录下（含子目录）glob 筛选所有 `bugfix-*.md` 问题记录文件（排除 `*-report.md`）。`$ARGUMENTS` 指定了具体文件名 → 仅处理该文件；给了 Sprint 编号 → 仅处理 Sprint 列匹配的条目；都没给 → 零散模式，处理全部待修复条目。

**2.2 解析每条问题记录**

对每个问题文件，提取：
- 问题编号 & 标题
- 问题描述（现象）
- 复现路径 / 触发条件
- 期望行为 vs 实际行为
- 优先级（P0 > P1 > P2）
- 修改建议（如有）
- 当前状态（仅处理"待修复"状态的问题）

**2.2b 反馈归因拆分（★ 强制，先归因再动手）**

**一条反馈可能含多个根因不同的问题——现象相同 ≠ 根因相同。** 解析出的每条记录必须先按四字段拆分登记，
**一条反馈含多现象时必须拆成多行**，拆完再进 Step 3：

| 字段 | 填什么 | 空着的后果 |
|------|--------|-----------|
| **现象** | 用户看到的表现（原话优先，不做提炼）| 提炼会丢掉区分根因的细节 |
| **归因** | 这一条的根因假设（**每个现象独立填**）| 多现象共用一个归因 = 必然错一半 |
| **证据** | 支撑该归因的可核查事实（代码位置 / 日志行 / 实测记录）| 无证据的归因属未验证假设，禁止据其修改代码 |
| **处置** | 本条要做什么（修代码 / 重新部署 / 确认需求 / 判为非缺陷）| — |

**典型代价**：一条反馈里「没去重」与「数值显示不对」被当成一件事处理——前者的根因是**环境未部署**、
后者是**真实漏改**。不拆分就会同时干两件错事：**重修已经对的代码** + **漏掉真正的缺口**。

**⚠️ 归因为「环境未部署 / 环境不一致」时**：须按权威事实源核实（CICD 运行记录里实际使用的 commitId），
⛔ 不得引用只在特定链路才写入的本地状态字段（典型误判：本地「上次部署时间」字段只有某一条链路会写，
推送自动触发的部署根本不写它 ⇒ 误判"没部署"，真缺陷晚一轮才暴露）。

**2.3 输出问题清单**

向用户展示待修复问题清单表格：

```
| 编号 | 标题 | 优先级 | 来源文件 |
|------|------|--------|---------|
| ... | ... | ... | ... |
```

### Step 3：影响范围分析

对每个待修复问题，**先定根因、再动代码**：本步的方法论 = `superpowers:systematic-debugging`（已安装则按其「复现 → 根因 → 定位」执行；未安装则按下方 3.0–3.3 执行）。⛔ **2.2b 的「证据」列未填实之前不得进入 Step 4**——修完再补根因分析等于没有根因分析。

**3.0 二次反馈强制走「推翻上次诊断」分支（★ 不得复述上次结论）**

**用户对同一问题复述第 2 次时，必须推翻上一次的诊断重新查**，而不是重复上次结论、也不是"再修一遍同一处"。
判定「是否二次反馈」：同一现象在 `docs/bugfix/{version}/` 已有记录（含已标"已修复"的），或用户表述含
"还是 / 依然 / 又 / 仍然 / 没好"。命中即：

1. **把上次的归因显式标记为已被推翻**（写进本次记录的「归因」列：`推翻上次归因：<原归因>，理由：<现象仍在>`）；
2. **重新做 Step 3 的定位**，⛔ 不得直接复用上次的影响范围表；
3. 若上次的修改已合入，**先确认那次修改本身是否引入了新问题**，再找真根因。

**「要和 X 一样」类反馈必须先确认是哪一层的一样**：`结构 / 命名 / 取值口径 / 视觉观感` ——
各层结论可能完全不同，问清楚再动手（典型代价：「弹窗卡片要和页签卡片一样」被理解成"一套通用样式"，
实际是三套命名、三套统计项、只共用一个外壳，返工两轮）。

**3.1 代码定位**

使用 Agent（Explore 类型）搜索相关代码：
- 根据问题描述中的模块名、功能名、接口路径等关键词
- 搜索前端文件：`code/frontend/*/` 下的 `.vue`、`.ts`、`.js` 文件
- 搜索后端文件：`code/backend/*/` 下的 `.java`、`.xml`、`.yml` 文件
- 搜索 API 定义、路由配置、Store/状态管理等

**3.2 阅读源码**

对定位到的文件逐一阅读，理解：
- 当前实现逻辑
- 数据流向（API → Controller → Service → Mapper → DB）
- 前端调用链路（组件 → API函数 → 后端接口）

**3.3 输出影响范围表**

对每个问题输出：

```
### 问题N：{标题}

| 层级 | 文件 | 修改内容 |
|------|------|---------|
| 前端组件 | src/components/xxx.vue | {需要修改什么} |
| 前端API | src/api/xxx.ts | {需要修改什么} |
| 后端Controller | xxx/controller/XxxController.java | {需要修改什么} |
| 后端Service | xxx/service/impl/XxxServiceImpl.java | {需要修改什么} |
| ... | ... | ... |
```

### Step 4：创建任务列表并执行修复

**4.1 创建 Task**

用 `TodoWrite` 为每个修复项建一条待办（⛔ 不要用 `TaskCreate`/`TaskUpdate`/`TaskList`——这三个工具不存在，写了这一步就恒不可执行、且没有任何门会报）：
- 后端修复任务优先（前端通常依赖后端接口变更）
- 前端修复任务在后端完成后执行
- 文档归档任务依赖所有修复任务

**4.2 执行修复**

按优先级和依赖顺序逐个修复：

**后端修复**（如涉及）：
1. 修改 Controller（接口参数、路由等）
2. 修改 Service 接口和实现（业务逻辑）
3. 修改 Mapper/SQL（数据查询）
4. 修改 VO/DTO（数据结构）

**前端修复**（如涉及）：
1. 修改 API 定义文件（参数类型、接口路径）
2. 修改 Vue 组件（模板、逻辑、样式）
3. 修改 Store/Composable（状态管理）
4. 修改路由配置（如涉及导航）

**修复原则**：
- 最小改动原则：只修改必要的代码，不做额外重构
- 保持一致性：修改风格与现有代码保持一致
- 前后端联动：接口参数变更必须前后端同步修改
- 不引入新问题：每次修改后检查是否影响其他功能

**4.3 逐项验证**

每个问题修复后立即验证：
1. 重新阅读修改后的代码，确认逻辑正确
2. 检查数据流完整性（前端参数 → 后端接收 → 查询 → 返回 → 前端展示）
3. 确认未影响其他功能（检查被修改函数/组件的其他调用者）
4. 使用 `git diff` 查看本次修改的完整差异，确认无遗漏

**未通过验证的修复不得进入归档步骤。**

### Step 5：生成修复记录文档

所有问题确认修复后，严格按照 AIDP 范式生成修复报告。

**5.1 确定文档路径**

报告文件命名规则（报告与问题记录文件**同目录**，即问题记录文件的**父目录**下）：
```
docs/bugfix/{version}/[{问题子目录}/]bugfix-{YYYYMMDD}-{序号}-report.md
```

如果问题记录文件位于子目录（如 `bug-20260304/bug-20260304-2.md`），则报告也放在同一子目录下。
如果问题记录文件直接在 sprint 目录下，则报告也放在 sprint 目录下。

**5.2 报告内容模板**

```markdown
# {Sprint-{NNN} | {version} 零散} Bug修复报告

> 修复日期：{YYYY-MM-DD} | 执行人：Claude Code | 问题来源：{问题文件名}

---

## 1. 问题清单总览

| 编号 | 标题 | 归因 | 证据 | 优先级 | 状态 |
|------|------|------|------|--------|------|
| {编号} | {标题} | {根因；二次反馈须写「推翻上次归因：X」} | {代码位置/日志行/实测记录} | {P0/P1/P2} | 已修复 |

> 「归因」「证据」两列来自 Step 2.2b 的四字段登记，**一条反馈拆出的多个现象各占一行**；
> 证据列留空 = 该条归因属未验证假设，不得据其判「已修复」。

---

## 2. 修复详情

### 2.N {问题标题}

**问题描述**：{简述问题现象}

**根因分析**：{分析问题的根本原因，不只是表面现象}

**修复方案**：{描述具体的修复思路}

**代码修改**：

| 文件 | 函数/区域 | 改动说明 |
|------|----------|---------|
| `{文件相对路径}` | {函数名/区域描述} | {改动说明} |

---

## 3. 修改文件汇总

| 文件路径 | 涉及问题 |
|---------|---------|
| `{文件相对路径}` | 问题N, 问题M |

---

## 4. 验证方式

{描述每个问题的验证方法和结论}

---

## 5. 归档信息

- **修复时间**：{YYYY-MM-DD}
- **执行人**：Claude Code
- **问题来源**：`{问题文件相对路径}`
- **归档路径**：`{报告文件相对路径}`
```

**5.3 注意事项**

- 问题记录原文件（`bugfix-*.md`）：SKILL 自身**不重写其正文/详情**；但**允许调用方（命令端）就地回填状态列 / Commit 列 / 修复报告链接**——`bugfix-*.md`（及其来源清单）是可审计"活文档"，状态就地演进（待修→已修→已验证）即审计轨迹
- **根因 / 证据 / 修复方案的权威落点 = 本报告**：问题记录与来源清单只放状态、Commit 与指向本报告对应小节的链接，⛔ 不再复写一份根因
- 详细修复报告单独生成为 `bugfix-*-report.md`（不塞进问题记录正文）
- 报告中文件路径使用相对于项目根目录的路径

### Step 6：输出完成报告

向用户输出修复总结：

```
✅ /bugfix {sprint-NNN | 零散模式} 完成

处理结果：
| 编号 | 标题 | 状态 | 修改文件数 |
|------|------|------|-----------|
| ... | ... | 已修复 | N |

文档归档：
- {报告文件路径} ✅

代码修改摘要：
- 后端：{N} 个文件
- 前端：{N} 个文件

建议下一步：
- 静态验证修复效果（类型检查 / lint / 单测）
- 需要运行期验证时转交调用方的自动化测试链路，**不在本 SKILL 内启动前后端服务**
- 或激活 QA Agent 执行回归测试
```

## 输出

- 修复后的代码文件（前端/后端）
- 修复报告文档：`docs/bugfix/{version}/[{问题子目录}/]bugfix-{YYYYMMDD}-{序号}-report.md`（与问题记录文件同目录）

## 注意事项

- **修复未验证 = 不归档**：每个问题修复后必须验证，未验证的修复不得写入报告
- **SKILL 不重写问题原文件正文**：问题记录（`bugfix-*.md`）的详情正文由 SKILL 保持原样、详细修复报告单独生成；但**状态列 / Commit 列允许调用方就地回填**（可审计活文档，见 5.3）
- **最小改动原则**：只修改与问题直接相关的代码，不做额外重构或优化
- **前后端联动**：接口变更必须前后端同步修改，避免调用链断裂
- **文档格式严格遵循范式**：参照 `00_AIDP范式主文档.md` 第7节的 Bugfix 文件格式
- **优先级排序**：多个问题时按 P0 > P1 > P2 顺序修复
- **依赖关系**：后端接口修改优先于前端组件修改
