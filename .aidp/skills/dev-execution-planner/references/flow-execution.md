# 执行流程细则(第零步 ~ 第三步)

> 本文件是 `SKILL.md`「执行流程」的细则分片,按需 Read。**SKILL.md 骨架里已保留每一步的强制结论**(判定规则、Critical 判据、硬门),本文件展开的是**怎么做、判据全文、正反例、表格列定义**。

### 第零步：多用户分配判定

**检查用户输入**：用户在调用 Skill 时是否明确说明了"功能模块-开发者"的分配关系？

**判定规则**：
- **触发多用户模式**：用户明确提供类似以下信息时
  - "功能模块 A 分配给张三，功能模块 B 分配给李四"
  - "用户管理模块由开发者 A 负责，订单管理模块由开发者 B 负责"
  - "前端页面分配给前端工程师 X，后端接口分配给后端工程师 Y"
  - 或提供包含人员-模块映射的表格/列表
- **默认单用户模式**：用户未提及人员分配，或仅说"团队开发"但未指定具体分工

**多用户模式输出**：
1. 生成 1 个专职索引（`00_索引.md`）：登记全部内容文档 + 每份生成时间 + 主/补充标识；包含全局任务清单、人员分配表、跨人员依赖关系
2. 生成 N 个内容文档（`NN_研发执行计划-{开发者姓名}.md`，从 `01_` 起）：每个开发者一个，仅包含其负责的任务 + 依赖的外部任务标注

**单用户模式输出**（AIDP 命名范式）：
- 恒产出**两个文件**：`00_索引.md`（专职索引）+ `01_研发执行计划.md`（内容主文档），不区分负责人。
- `00_` 槽位恒给专职索引；内容主文档一律从 `01_` 起。即便只有一份内容文档，也产出 `00_索引.md` + `01_研发执行计划.md`（废除旧的裸单文件 `00_研发执行计划.md`）。
- `00_索引.md` 必载：① 全部内容文档（`01_`+）清单 + 每份一句话范围；② 每份文件生成时间（`YYYY-MM-DD HH:MM`，用 shell `date +"%Y-%m-%d %H:%M"` 取当前时间打戳，不得凭空填）；③ 主/补充标识（版本规划首产=「主」，`--supplement` 增量=「补充」）。建议列：`| 序号 | 文件 | 生成时间 | 类型 | 说明 |`。

### 第一步：交叉校验

校验 PRD ↔ 原型 ↔ 设计方案 的一致性，不一致处列入 `⚠️ 一致性问题`。

**校验优先级规则：**
- PRD 定义的功能范围、业务规则、样式/文案/UI 细节为准，原型和设计方案必须覆盖 PRD 的所有功能点
- 原型中有但 PRD 中没有的功能，标注为"原型补充功能，待确认是否纳入"
- **样式/文案/UI 冲突**：原型与 PRD 冲突时以 PRD 为准，标注冲突并建议修正原型
- **技术实现冲突**：PRD 中的技术描述（技术栈、表结构、接口路径等）仅供参考，设计方案可自主调整；与详细设计冲突时以**详细设计为准**，无需修改 PRD
- 设计方案中的接口定义和数据库设计必须支撑 PRD 的所有功能需求

**一致性检查清单：**
1. PRD 中的每个功能点，是否在原型中有对应的页面/组件？
2. PRD 中的每个功能点，是否在设计方案中有对应的实现路径（接口/数据库/业务逻辑）？
3. 原型中的页面/组件，是否都能在 PRD 中找到对应的功能描述？
4. 设计方案中的接口定义，是否覆盖了 PRD 的所有数据交互需求？

### 第一步半：接口设计检测

检查详细设计方案中是否包含后端接口设计（API 契约定义、接口列表、Controller 定义等），或项目中是否存在独立的接口文档（如 Swagger/OpenAPI JSON、Apifox 导出文件、接口 Markdown 文档等）。**任一存在**，则在后续任务拆解中强制执行以下规则：

- **Phase 3（接口层）**：后端必须实现详细设计中定义的**所有接口**，逐个拆解为独立任务，不允许遗漏
- **Phase 4（前端展示层）**：
  1. **清除 mock 数据（前置强制步骤）**：每个前端页面任务的执行步骤中，**第一步必须是**扫描并删除该页面/模块中所有 mock 数据和静态假数据，包括但不限于：
     - 组件内硬编码的 `const data = [...]`、`const list = [...]` 等静态数组
     - `mock/`、`mocks/`、`__mocks__/` 目录下的 mock 文件
     - API 层中返回假数据的函数（如 `return Promise.resolve(fakeData)`）
     - 使用 Mock.js、MSW、json-server 等 mock 工具的配置和调用
     - 组件 `data()` / `setup()` 中用于模拟接口返回的静态对象
     - 任何 `// TODO: 替换为真实接口` 注释标记的临时代码
  2. **对接真实接口**：统一调用后端真实接口，每个前端页面任务的执行步骤中必须明确写出所对接的后端接口路径
  3. **验收标准**：必须包含"已删除所有 mock/静态假数据"和"联调后端真实接口通过"两项

### 第一步半之二：接口可用性深度核验(Critical,对应详细设计核心原则 18)

**实测痛点**: 详细设计标注"✅ 沿用 GET /xxx/overview"时,Agent 默认接口可用,直接生成 Phase 4 前端 Task 对接该接口。但 `XxxServiceImpl.overview()` 方法体可能只是 `throw new BizException(501)` 占位,联调阶段才暴雷。

**核验规则**: 详细设计中标注为「✅ 沿用已有」的每个接口,在生成执行计划前**必须**穿透到 Service 实现层验证可用性:

> **`<SKILL_DIR>` 占位符(全文统一):** 本 SKILL 的实际安装目录(本项目 = `{{AIDP_HOME}}/skills/dev-execution-planner`)。

```bash
# 强制运行接口可用性扫描(对应详细设计核心原则 18)
python3 <SKILL_DIR>/scripts/check_service_impl_stub.py <代码根目录>
# 退出码 1 时,详细设计标注「✅ 沿用」的接口至少有一个是占位实现 → 需要回到 dev-logic-architect 修正标注
# 注:抛 5xx/未实现等占位为 Critical(默认即返回 1);仅 @Deprecated 标注(无 throw)归 Important,
#     默认不返回 1,需加 --strict 才硬拦 —— 如需把"@Deprecated 接口必须 Phase 3 拆 Task"作为阻断项,跑 --strict
```

**判定矩阵(基于 Service 实现层扫描结果):**

| Service 实现状态 | 详细设计应标注 | 执行计划处理方案 |
| :- | :- | :- |
| ✅ 真实业务实现 | ✅ 沿用已有 | Phase 4 前端 Task 直接对接,Phase 3 无后端 Task |
| 🔧 占位实现(throw 5xx / return null) | 🔧 待实现 | **必须**在 Phase 3 拆出"补全 XxxService 业务实现"Task,Phase 4 前端 Task 标记"依赖 Task X.Y 完成" |
| 🛰️ 外部系统接口未交付 | 🛰️ 外部系统接口 + ⏳ 未交付 | 走「情况 0:第三方平台接口未交付」流程,前端 mock 优先,登记对接清单 |
| ❌ @Deprecated | ❌ 已废弃 | Phase 3 必须新建接口 Task,**严禁**继续使用废弃接口 |

**严禁的执行计划反模式(对应"代码事实采集深度不足"漏洞):**
- ❌ 详细设计写"✅ 沿用 GET /xxx",执行计划直接拆 Phase 4 前端 Task,从未核验 Service 实现
- ❌ 接口可用性靠 Controller 注解判断,不读 ServiceImpl 方法体
- ❌ 联调阶段才发现"接口能调通但永远报错",此时已错过 Phase 3 拆 Task 的窗口

**反向兜底(若详细设计未标注实现状态):** 执行计划 Agent 主动跑 `check_service_impl_stub.py` + `check_third_party_dep_reverse.py`,扫描结果回填到执行计划"接口可用性核验报告"附录,任何占位/废弃/外部依赖的接口必须在 Phase 3 单独拆 Task。

### 第二步：任务拆解

按「**EPIC × Sprint × Task**」三层拆分,严格按依赖顺序排列。

**🔴 三层拆分模型(Critical):**

| 层级 | 定位 | 编号 | 内容 |
| :-: | :- | :- | :- |
| **EPIC** | "**可独立交付的子功能闭环**",一个 EPIC 完成后用户能体验到一个完整的业务能力(如"用户列表与详情") | EPIC-NN | 含跨端的「**前端任务 + 后端任务 + 测试任务**」三类小节(除非 EPIC 头部明示「单端」)。EPIC 编号与上游 REQ 编号互引,在末尾「REQ 归属对照表」补充「所属 EPIC」列 |
| **Sprint** | 时间盒,把 EPIC 排到 Sprint 中(一个 Sprint 可含多个 EPIC,一个 EPIC 也可跨 Sprint) | Sprint-NNN | Day 轴**仅作为汇总信息**(如"本 Sprint 预估 N 工作日"),**严禁**按 Day 切散 Task |
| **Task** | 子功能粒度的最小执行单元 | Task X.Y | 必带 AI 执行指令四件套(主命令 + 设计/PRD/原型锚点 + 依赖 + 验收锚点),详见下方 |

**🚫 严禁的反模式(实测发现):**
- ❌ "**Sprint × Day × Task**" 三层(按时间轴 Day 水平切散,跨端任务挤在同一 Day 无法独立分工)
- ❌ EPIC 不分前端/后端/测试三类小节(团队接手时无法按角色并行)
- ❌ EPIC 编号与 REQ 编号无双向索引(需求方读"列表功能完整含哪些任务"要跨多个 Day 拼凑)

**每个 Task 必须对应"一个子功能",而非"一个功能模块"或"一个页面"。** 拆分粒度不足会导致下游代码生成 Agent 无法精准定位上游引用,出现"模糊参考整个详细设计"的引用退化。

### Sprint 并行分组(机器可读投影)

执行计划必须在 Sprint 排期之后产出下列固定格式的「Sprint 并行分组」表。它是现有**文件级冲突矩阵**的机器可读投影,不另写一套冲突判据:

```markdown
## Sprint 并行分组

| 并行组 | Sprint 链（有序，组内串行） | 涉及代码域（glob） | 与其它组的文件重叠 |
|---|---|---|---|
| G1 | Sprint-042 → Sprint-043 | `code/backend/*/agent/**`; `code/frontend/*/agent-mgmt/**` | 无 |
| G2 | Sprint-044 → Sprint-045 → Sprint-046 | `code/backend/*/finance/**`; `code/frontend/*/model-mgmt/**` | 无 |
```

**固定语义与生成规则:**

1. 表内每行是一个并行组;「Sprint 链」按硬依赖顺序书写,组内必须串行,组间默认无序可并行。
2. 「涉及代码域（glob）」必须填写可用于集合求交的 glob,多个 glob 用 `;` 分隔,不得只写自然语言域名。
3. 「与其它组的文件重叠」按组间两两声明;无重叠也必须填写 `无`,不得留空。存在重叠时写明对方组与重叠 glob。
4. 仅当文件级冲突矩阵和任务依赖均能证明组间无硬依赖时才拆成不同组;判不准则归入同一组,降级为串行。
5. 下游编排器可读取本表先按组并行、组内串行,再用 glob 对实际文件集合求交复核;发现交集必须强制降级为串行并记录原因。缺表时下游默认全串行且不报错。

**子功能定义(以下任一颗粒,选最小者):**
- **PRD 功规点级别** — 研发 PRD"五、页面交互明细"中每一条 `五-N.x` 功规点对应一个 Task(如"用户列表分页"和"用户列表搜索"是两个独立功规点)
- **接口级别** — 详细设计 B.2 接口契约中**每一个接口**对应一个 Task(`GET /user/list`、`POST /user`、`PUT /user/{id}`、`DELETE /user/{id}` 至少 4 个 Task,**严禁**合并为"用户接口开发")
- **数据表级别** — A.3 中**每一张表**对应一个 Task(包括 DDL + Entity + Mapper);严禁合并"用户域所有表"为单一 Task
- **页面/组件级别** — 前端每一个独立页面/弹窗/复杂业务组件对应一个 Task(列表页、新增弹窗、编辑弹窗、详情抽屉、删除确认是 5 个 Task)
- **状态/业务规则级别** — B.5 状态机中**每一条状态转移规则**或 B.1 中每条业务校验规则对应独立 Task(如"订单从'待支付'到'已支付'的转移逻辑"独立成 Task)

**禁止的粗粒度反模式:**
- ❌ "Task 2.1: 用户管理后端开发"(应拆为:列表查询 / 单条查询 / 新增 / 编辑 / 删除 / 状态切换 等 6+ 个 Task)
- ❌ "Task 4.1: 用户管理前端页面"(应拆为:列表页 / 新增弹窗 / 编辑弹窗 / 详情抽屉 / 删除确认 / 搜索栏 / 分页器 等)
- ❌ "Task 1.1: 创建数据库"(应拆为:每张表一个 Task,如 `Task 1.3: 创建 biz_user 表`、`Task 1.4: 创建 biz_role 表`)
- ❌ "Task 3.1: 实现所有接口"(应拆为:每个接口一个 Task)

**拆分粒度的判断原则(三选一):**
1. **可独立交付**:Task 完成后可独立提交 PR、独立 code review、独立测试
2. **单一上游来源**:Task 只引用详细设计/PRD/原型中的**一处**精确章节(章节范围 ≤ 100 行),不跨越多个功规点
3. **AI 一次完成**:Task 的 AI 执行指令一次调用即可完整生成产物,不需要分多轮迭代

**满足任一即合格;若 Task 描述中出现"等""及""相关""一系列""所有"等聚合性词汇,基本可判定粒度过粗,必须再拆。**

#### 🛡️ AI 执行指令四件套(Critical 强制)

每个 Task 的 AI 执行指令代码块**必须**包含以下四件套(① 主命令 + ② 设计锚点 + ③ 依赖 + ④ 验收锚点),严禁简写为单一主命令:

| 件 | 内容 | 强制要求 |
| :-: | :- | :- |
| **① 主命令** | 可直接输入到 AI 工具的 slash 命令 / shell 指令(如 `/dev-logic-architect`、`aidp gen:mapper --table biz_user`) | 代码块第一行,**严禁**写"请使用 xxx 工具"这类描述 |
| **② 设计锚点** | 精确到设计文档章节 / 接口编号 / 行号(如 `详见 docs/design/01_接口设计.md §B-2.1 (L120-L150)`) | 必填,grep `详见.*\.md.*§\|§A-\|§B-\|§\d+\.\d+` 至少命中 2 处 |
| **③ 依赖任务** | 「**依赖**: 无」或「**依赖**: Task X.Y」,前序产出路径(若有) | 必填,形成有向无环 Task 依赖图 |
| **④ 验收锚点** | 同样精确到设计文档章节(如 `验收: docs/design/19_测试方案.md §C-2.3 用户列表查询用例`) | 必填,Agent 接手时不需要回头猜验收标准 |

**严禁:** 简写为「主命令 + "参考设计"」三字搭配。实测发现这种简写会导致下游代码 Agent 无法定位,反复读全文。

**拆分后强制要求:**
- 每个 Task **必须**有独立的"四源引用"(详细设计精确章节 + PRD 精确章节 + 原型精确文件/锚点 + 高保真精确文件,见「🔗 上游引用规则」)
- 每个 Task 的 AI 执行指令代码块**必须**在提示词中重复透传这四源引用,不允许仅写"参考设计"
- 多个相关 Task **必须**通过 `**依赖**:Task X.Y` 字段串联,形成有向无环依赖图,不允许"扁平并列无依赖"

#### 📐 EPIC × Sprint × Task 与 Phase 1-5 的关系(避免歧义)

EPIC × Sprint × Task 与 Phase 1-5 是**两条正交的切分维度**,**不冲突共存**:

| 切法 | 维度 | 用途 |
| :- | :- | :- |
| **EPIC × Sprint × Task**(纵向) | 按"业务闭环"垂直切 | 一个 EPIC 是用户能感知的完整业务能力(如"用户列表 + 详情") |
| **Phase 1-5**(横向) | 按"技术分层"水平切 | Phase 1 数据层 / Phase 2 业务层 / Phase 3 接口层 / Phase 4 前端层 / Phase 5 测试 |

**EPIC 内含跨 Phase 的多个 Task:**

```
EPIC-01: 用户列表与详情(纵向闭环)
├── ### 前端任务
│   ├── Task X.Y: 列表页 (Phase 4)
│   └── Task X.Y: 详情抽屉 (Phase 4)
├── ### 后端任务
│   ├── Task X.Y: GET /user/list (Phase 3 接口层)
│   ├── Task X.Y: GET /user/{id} (Phase 3 接口层)
│   ├── Task X.Y: UserService 业务规则 (Phase 2 业务层)
│   └── Task X.Y: biz_user 表 DDL (Phase 1 数据层)
└── ### 测试任务
    └── Task X.Y: 端到端联调 (Phase 5)
```

**所以:**
- **EPIC 是组织方式** — 让前后端测试三类任务围绕一个业务能力聚拢
- **Phase 是技术标签** — 标注每个 Task 属于哪一层,便于按层并行 / 按层走查
- **下方「L2 Phase 级引用」、「Phase 1-5 上游引用矩阵」依然有效**,Task 同时挂 EPIC 编号(`所属 EPIC`)和 Phase 标签(`Phase 1-5`)
