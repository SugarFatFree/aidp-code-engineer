> 前端任务示例（含 Mock 清除、接口对接、原型对照）见 `./flow-granularity.md` >「前端任务示例（存在接口文档时）」。不读取该文件生成的 Task 可能缺失关键字段（执行步骤、产出物路径、验收标准）。

- **Phase 1: 基础设施与数据层**
  - **Task 1.1 必须是"项目代码框架搭建"**(仅当代码仓库为空或未搭建工程骨架时)。根据详细设计文档中的技术栈和架构规范,生成:
    - 后端:项目骨架(如 Spring Boot 的 pom.xml/主启动类/分层包目录)、`application.yml` 基础配置；`.env.example` 仅在调用方规范要求时产出
    - 前端:脚手架(如 Vite/Vue + 目录结构)、`package.json` 依赖；`.env.example` 仅在调用方规范要求时产出
    - 如果仓库已有代码且工程骨架完整,跳过此 Task,直接从数据库表创建开始
  - **Task 1.2 是"第三方中间件配置"**(涉及 MinIO、Redis、Nacos、消息队列等时必需)。在实际代码中配置:
    - **检查配置来源但不复制凭据**：`.env` 仅作为本机覆盖配置读取；`.env.example` 仅在调用方规范要求时创建，默认不强制产出
    - `.env.example`（如产出）只使用 `{待用户填写: 变量名}` 占位符，严禁写入真实地址、账号、密码、令牌或密钥；是否提交由调用方项目规范决定
    - `.env` 内容策略:
      - 开发者本机的个性化覆盖配置(如本地 MinIO 端口与团队默认不一致)
      - 不提交到代码仓库(`.gitignore` 必须包含 `.env`)
    - 后端配置文件(如 `application.yml`)引用环境变量(如 `minio.endpoint: ${MINIO_ENDPOINT}`),配置来源与优先级以项目既有规范为准，不由本 SKILL 臆造
    - 相应的 Java/Go 客户端 Bean/Client 初始化代码(如 `MinioConfig`、`RedisConfig`、`NacosConfig`)
    - 执行静态配置闭环验证(配置键无悬空、依赖已声明、配置类可编译，并运行 `check_env_config.py`);**不启动被测服务**，真实连通性验证转部署后
    - 若 `.env.example` 和 `.env` 均不存在,**严禁中断**(详见"不中断原则 > 环境信息缺失的处理"):生成 `.env.example` 模板时,缺失项使用占位符 `{待用户填写: MINIO_ENDPOINT}` 标注,并在执行计划"待澄清问题清单"登记 P-NNN(优先级 P0);严禁自行编造真实连接地址
  - **Task 1.3+ 是数据库表、DO/Mapper 等数据层任务**
- **Phase 2: 业务逻辑层** — 领域模型、仓储、领域服务、应用服务。**涉及第三方系统对接时**,本 Phase 必须包含第三方接口调用封装 Task(客户端类、超时重试、失败降级)
- **Phase 3: 接口层** — Controller、DTO、参数校验。若详细设计包含接口定义,必须逐个实现所有接口,不允许遗漏。**涉及第三方系统对接时**,本 Phase 必须包含对外开放接口 Task(供第三方调用的接口,含认证/限流/幂等)
- **Phase 4: 前端展示层** — 页面组件、路由、接口对接(**禁止复用原型 HTML**,**禁止使用 mock 数据**——若详细设计包含接口定义或存在接口文档,前端必须**先删除所有 mock/静态假数据**,再对接后端真实接口)
- **Phase 5: 测试与质量保障** — **必须包含**代码走查 + E2E 集成测试 + 单元测试 + 接口测试 + Mock 残留扫描(若存在接口文档,Phase 5 必须包含一个独立任务:全局扫描项目中是否残留 mock 数据/静态假数据,确保所有前端页面均已对接真实接口)。**涉及第三方系统对接时**,本 Phase 必须包含第三方联调验证 Task

### 第三方系统对接任务拆解规则

**当详细设计(B.7 外部依赖与集成方案)或 PRD 中涉及第三方系统对接时,必须按以下规则拆解任务:**

#### 核心原则:逐个接口独立成 Task(强制)

**对接第三方业务系统时,双方通常在并行开发,开发节奏不同步。必须按"每个接口 1 个独立 Task"拆分,而不是"每个系统 1 个 Task",原因:**

1. **并行开发友好** — 第三方系统 A 开发完接口 a1 后,我方的 Task 可以立即启动联调,不必等 a2、a3 全部就绪
2. **进度可视化** — 每个接口独立标注状态(未开始/开发中/待联调/联调通过/联调阻塞),便于跟踪"已对接 N 个 / 共 M 个"
3. **阻塞隔离** — 某个接口联调阻塞时,不影响其他接口任务推进
4. **责任清晰** — 每个接口 Task 明确标注"我方开发者"和"第三方对接人",沟通有单点
5. **灰度上线** — 接口逐个对接通过后,可先上线已就绪的部分功能,不必全量等待

**禁止做法:**
- ❌ 把"对接某第三方系统的所有接口"合并为 1 个 Task
- ❌ 把"第三方接口封装"笼统列为 1 个 Task,不展开具体接口清单
- ❌ 把多个接口的联调合并为 1 个"联调 Task"(应在 Phase 5 按接口独立拆)

#### 判定规则

| 场景 | 任务安排 |
|------|---------|
| 详细设计 B.7 定义了 N 个"我方对外开放的接口" | Phase 3 中拆为 **N 个独立 Task**,每个接口 1 个 Task(与内部接口并列) |
| 详细设计 B.7 定义了 N 个"调用第三方的接口" | Phase 2 中拆为 **N 个独立 Task**,每个第三方接口 1 个封装 Task |
| 涉及 N 个第三方回调/通知 | Phase 3 中拆为 **N 个独立 Task**,每个回调接收 1 个 Task |
| 联调验证 | Phase 5 中为每个接口生成 **1 个独立联调 Task**,不合并 |

**第三方接口联调验证 — 每个接口 1 个独立 Task(Phase 5):**

```markdown
### Task 5.N: 联调验证 — [具体接口名,如"支付系统-创建订单接口"]

**严格依据:** 详细设计 > B.7 > [接口编号]
**对接清单编号:** API-T01
**前置依赖:** Task 2.X(本接口的封装)+ 第三方接口已就绪
**触发条件:** 第三方对接人确认接口已部署到测试/沙箱环境

**执行步骤:**
1. 与第三方对接人确认接口地址、认证凭证、测试数据
2. 切换本接口配置为第三方真实测试环境(关闭本接口的 mock 运行时开关并删除 mock 实现)
3. 执行正向联调:正常参数调用,验证响应符合预期
4. 执行异常联调:非法参数、鉴权失败、业务错误码;**并验证第三方业务错误透传**——构造第三方返回业务错误(如"余额不足"),确认前端展示的是第三方业务文案而非本系统通用文案
5. 执行降级验证:模拟第三方不可用(系统/基础设施错误),确认降级逻辑生效(系统错误才走通用兜底,业务错误须透传)
6. 记录联调结果到对接清单(通过/阻塞/待第三方修复)
7. 若阻塞,明确标注阻塞原因和第三方修复预期

**验收标准:**
- [ ] 正向流程联调通过
- [ ] 异常流程联调通过(或标注阻塞原因)
- [ ] **第三方业务错误透传验证通过**:第三方返回业务错误时前端展示第三方业务文案(非被替换成通用"操作失败,请稍后重试");仅系统/基础设施错误才通用兜底
- [ ] 降级方案验证通过
- [ ] Mock 实现已删除(拦截逻辑/if 分支/fixture),mock 开关已关闭或移除
- [ ] 对接清单中本接口联调状态已更新为"✅ 通过"或"⛔ 阻塞+原因"
```

**设计原则:**
- **粒度强制要求** — 每个第三方接口必须是独立 Task,严禁合并
- **对接清单同步** — 每个 Task 执行过程中必须更新对接清单状态,对接清单是双方协作的"看板"
- **严禁为第三方系统编写实现代码** — 仅封装调用逻辑和对外开放接口
- **第三方接口未就绪时使用 Mock/桩** — 但必须用运行时开关隔离(非构建期守卫,见「情况 0」)并带 `THIRD_PARTY_MOCK` 标注,联调时按接口粒度切换(不是全量切换)
- **联调按接口粒度独立验证** — 允许部分接口先联调通过、部分阻塞,推动已就绪的接口尽早上线

### 每 Phase 末尾的验证任务(强制)

每个 Phase 的最后一个 Task 必须是**自动化验证任务**,确保当前 Phase 的产出可用、无回归:

| Phase | 末尾验证任务示例 | 可执行指令 |
|-------|----------------|-----------|
| Phase 1 | 验证工程骨架类型/编译通过 | 后端:**按 `stack-java-spring.md` >「二、开发期轻量验证」的判据选命令(⛔ 别直接写 `mvn compile`——它会跑完 generate-* 相、可触发前端全量构建)** / 前端:`vue-tsc --noEmit`(或 `pnpm type-check`) |
| Phase 2 | 核心业务逻辑单元测试 | `mvn test -Dtest=*ServiceTest` |
| Phase 3 | 接口联调测试 | Postman Newman / Apifox CLI / 调用 `/code-verification-loop` |
| Phase 4 | 前端 E2E 测试 + Mock 残留扫描 | Playwright / Cypress / `python3 <SKILL_DIR>/scripts/scan_mock_data.py src/`(对接第三方平台时加 `--third-party-mode`) |
| Phase 5 | 完整回归测试 + 性能基准 + 安全扫描 | 调用 `/code-verification-loop`、`mvn dependency-check` |

> **⚠️ 开发期验证 = 轻量类型/语法检查，禁全量 build（前后端对称）：** Phase 1「验证工程骨架」与各 Task 验收标准里写的**必须是轻量类型/语法检查**（秒级~十几秒），**不是完整构建**（分钟级）——把全量 build 写进开发期 Task 会让每个 Task 的验证耗时翻几十倍、拖垮迭代节奏。
>
> - **开发期验证**（本表 Phase 1、生成计划时的骨架校验任务、各 Task 验收标准）：只跑轻量检查
> - **发布/部署期构建**（构建机 / CICD，非开发期任务）：才用完整打包命令
>

### 零残留断言的选择性重跑与发布总闸(轮次收尾验证任务)

**问题:** 零残留断言(一切「不存在文本 X」形态的反向断言,含 `[反向-残留]` 与 `[文案一致性]` 反向用例)
**只增不退**——下游实测规划期 20 条、两个 Sprint 后 33 条,而规矩是每轮收尾原则上全部重跑,
**成本线性增长且不可逆**。

⚠️ **不削弱那条规矩。** 「每条写完必须当场实跑两个方向」是这套断言唯一的质量来源
(下游正是靠它在写代码之前抓出「式子会误命中 javadoc 交叉引用」)。**登记期照旧全跑两个方向**,
本节只规定**收尾期跑多大范围**。

**轮次收尾验证任务必须按下表落位:**

| 时机 | 跑哪些 | 依据 |
| :- | :- | :- |
| **Sprint / 迭代收尾** | 守护面 ∩ 本轮 git diff ≠ ∅ 的断言 —— **强制重跑** | 上游 `dev-manual-testcase` 登记的「守护面」(文件/目录 glob) |
| 同上 | 其余标 `skipped(out-of-scope)` | **必须登记**,见下 |
| **版本发布前** | **全部断言全量跑一次,作总闸** | 总闸**不接受任何 `skipped`** |

**四条不可退让:**

1. **`skipped` 必须登记,不能只是不跑。** 每条跳过的断言登记
   `断言 ID | 守护面 | 比对基线(diff 两端的 commit/tag) | 跳过轮次`。
   ⚠️ **没有这份台账,「这条过了」与「这条没跑」在报告里长得一模一样**,
   而后者会以全绿的形态存在——这正是本仓库 QR 执行台账要解决的同一个问题。
2. **算不出 diff 就退回全量并注明。** 无 git / 浅克隆 / 合并提交两端歧义 / 守护面 glob 语法错——
   ⛔ 一律退回全量,**严禁猜一个范围**。
3. **发布总闸不可裁剪。** 选择性执行的代价是「守护面写窄了的断言会连续多轮不跑」,
   发布前的全量跑就是兑现这笔代价的地方。总闸出现 `skipped` = 该版本的零残留结论不成立。
4. **守护面是上游登记的,不在这里现编。** 计划侧只做「守护面 ∩ diff」这一次交集判断;
   守护面本身必须由 `dev-manual-testcase` 在登记时**从正向实跑的命中集合导出**。
   ⛔ 执行计划里临时给某条断言指一个守护面 = 绕过了那条「不得手写」的规则。

> **边界:** 本节只管**跑多大范围**,不管断言写得对不对(那在上游登记期)、也不管断言能不能退役
> (退役规则见 `dev-manual-testcase` 维度 18「零残留断言登记表」子条:只有「守护对象已消失」
> 与「判据已移交常设机制」两条合法路径,⛔「多轮未红」不是理由——常绿正是这类断言的正常状态)。

**每个功能 Task 的验收标准也必须包含一项自动化可执行的检查点**(见核心原则)。
