# 研发执行计划 — 输出格式详细骨架

> 隶属 dev-execution-planner SKILL，是 SKILL.md「输出格式」章节的详细骨架（产物长什么样的完整模板）。判定规则（何时用单/多文件、三种模式判定、关键命名约束）见 SKILL.md「输出格式」摘要，本文件提供完整骨架示例与拆分检查表，按需查阅。

> ⚠️ **两条与硬门直接绑定的硬约束（本文件曾与它们不一致，照旧骨架产出会让 Critical 硬门整体空转）：**
>
> 1. **Task 抬头必须是三级或四级标题**（`### Task X.Y:` / `#### Task X.Y:`），**冒号可省**。
>    `check_task_granularity.py` 的 `TASK_HEADER_RE` 只认 `^#{3,4}\s+Task\s+(\d+\.\d+)`，
>    `check_doc_split.py` 的 `TASK_ID_PATTERN` 认 `^#{2,4}`。**用两级标题 `## Task` 写，粒度硬门
>    会输出 `scanned_tasks: 0, skipped: true, exit 0`——不是"通过"，是"一个 Task 都没看见"。**
> 2. **本文件是 Phase 分层的骨架，不替代 EPIC × Sprint × Task 三层模型**（见 `SKILL.md`「任务模型」
>    与维度 14a Critical）。Phase 1~5 是**正交的技术分层维度**，EPIC / Sprint 层与 9 列任务表
>    仍须按 SKILL.md 与 [`flow-task-model.md`](./flow-task-model.md) 产出——
>    **只照本文件的 Phase 骨架写会缺 EPIC 层**。

### 多用户分配的任务编号规则

**保持全局唯一编号**：所有开发者的任务编号在主文档中统一分配，子文档中沿用相同编号，不重新编号。

**Phase 内按依赖顺序排列**：即使任务分配给不同开发者，Phase 内的 Task 编号仍按依赖关系从小到大排列，确保 Task 1.1 → 1.2 → 1.3 的顺序反映真实依赖链。

**示例**：
- Phase 1: Task 1.1（开发者A）→ Task 1.2（开发者A）→ Task 1.3（开发者A）→ Task 1.4（开发者B，依赖 1.2）→ Task 1.5（开发者A）
- 开发者A 的子文档包含 Task 1.1, 1.2, 1.3, 1.5
- 开发者B 的子文档包含 Task 1.4，并在"我依赖的其他人任务"中标注 Task 1.2（开发者A）

### 多用户分配的文件命名（AIDP 命名范式）

- 专职索引：`00_索引.md`（`00_` 槽位恒给索引，登记全部内容文档 + 生成时间 + 主/补充标识）
- 内容文档：`NN_研发执行计划-{开发者姓名}.md`（从 `01_` 起，如 `01_研发执行计划-张三.md`、`02_研发执行计划-李四.md`）
- 所有文档放在同一目录下，方便交叉引用

### 按内容量拆分多文档(单用户/多用户均适用)

**AIDP 命名范式:恒产出 `00_索引.md`(专职索引) + `01_研发执行计划.md`(内容主文档)**。即便只有一份内容文档也是两个文件;内容不多时把内容集中在 `01_研发执行计划.md` 单份,便于阅读和维护。

**触发进一步拆分的条件**（满足以下任一条件时,才把内容拆成 `02_`..）:
- `01_` 内容预估超过 **800 行** 或 **60KB**
- Task 总数超过 **40 个**
- Phase 内 Task 超过 **15 个**(单 Phase 过长)
- 用户明确要求"拆分输出"

**拆分数量控制（Critical）:**
- **目标文件数: 3~5 个**（含 `00_索引.md`）,不要超出太多
- 宁可单个内容文件长一些（800~1200 行）,也不要拆成 7、8 个碎片文件
- 只有 Task 确实非常多（>60 个）时才允许超过 5 个文件
- 拆分前先评估：能否将相邻 Phase 合并到同一文件？（如 Phase 1+2 合并、Phase 3+4 合并）

**拆分原则**：

1. **文件名必须带两位数字序号前缀**(`00_`、`01_`、`02_`...),保证字典序与逻辑顺序一致
   - `00_` 恒给专职索引 `00_索引.md`;内容主文档一律从 `01_研发执行计划.md` 起;`99_` 固定分配给待澄清问题清单(如有);其余序号按内容顺延
   - **严禁使用"补充"/"追加"/"附加"/"扩展"作为文件名前缀或中缀**(如 `补充-05-Phase3.md`、`05_补充-Phase3.md`) → 正确格式: `05_Phase5-测试与质量保障.md`(补充文档直接用序号+业务名)
2. **必须生成专职索引**(`00_索引.md`),作为索引和总入口(必载:全部内容文档清单 + 每份生成时间[shell `date` 打戳] + 主/补充标识)
3. **按 Phase 拆分内容文档**(优先,从 `02_` 起);Phase 仍过大时再按业务域拆分
4. **避免过度碎片化**: 单个内容文档目标 200~800 行,严禁不足 150 行的碎片(`00_索引.md` 除外);若某 Phase 任务过少(如 Phase 5 仅 1 个 Task),应合并到相邻 Phase 文件中
5. **内容文档间需要互相引用时**,使用相对路径 + Task 编号
6. **任务编号全局唯一**,跨内容文档不重复(如 Task 2.3 在索引和任意内容文档中均为 Task 2.3)
7. **索引不展开 Task 详情**,仅做索引和全局视图;详情都在内容文档中
8. **后续文件序号接着上一个文档序号自动累进**(不跳号,不嵌套二级序号);允许保留整十号(10_/20_/30_...)作为分组分界

**跨子文档引用的硬性要求**:

| 引用方 | 引用方式 | 示例 |
|-------|---------|------|
| Task 的"前置依赖"字段引用其他子文档的 Task | `Task X.Y(详见 ../{NN}_PhaseN-xxx.md)` | `前置依赖: Task 2.1(详见 ../02_Phase2-业务逻辑层.md > Task 2.1)` |
| 子文档之间引用 | 相对路径 + Task 编号锚点 | `参考 ../03_Phase3-接口层.md > Task 3.2` |
| 索引引用内容文档 | 相对路径 + 章节 | `详情见 03_Phase3-接口层.md > Task 3.2` |
| 引用详细设计章节 | 仍按零冗余原则 | `参考 [设计文档.md] > B.2 接口契约 > L120-L180` |

**拆分一致性检查**:

| 检查项 | 要求 |
|-------|------|
| 文件名序号 | 所有文档以两位数字前缀命名(`00_`、`01_`...),序号唯一,字典序与逻辑顺序一致;`00_` 恒给 `00_索引.md`,内容从 `01_` 起 |
| 索引存在 | `00_索引.md`(专职索引)必须存在,包含内容文档清单(+生成时间+主/补充标识)、文档结构表、全局任务清单、API/数据表全局索引 |
| Task 编号全局唯一 | Task 编号(如 2.3)在索引和所有内容文档中完全一致,不重复定义、不重新编号 |
| 索引不展开详情 | 索引的全局任务清单只列编号/标题/依赖/负责人,不写 Task 详情(详情都在内容文档) |
| 内容文档头部 | 每个内容文档必须标注隶属、索引路径、上下游依赖文档、Task 范围 |
| 引用可定位 | 内容文档间引用使用相对路径,Task 编号锚点存在 |
| 零冗余仍生效 | 拆分后仍严禁在 Task 中复述详细设计已定义的字段/接口/枚举(以章节引用代替) |
