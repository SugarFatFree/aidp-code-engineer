# dev-logic-architect 设计来由(rationale)

> SKILL.md 正文只写**现行行为**;各条规则「为什么这样定」、曾经出过什么问题,集中记在这里。
> 本文件只解释来由,**不新增任何判据**——判据以 SKILL.md、`core-principles.md`、`quality-review-checklist.md` 与脚本为准。

## 1. 需求规模档位(scale=S/M/L)

不分档时,一个只改两个页面的小需求也会产出与大版本同规格的文档族。实际项目中曾测得「代码 : 文档 ≈ 9.4 : 1」,
收益递减而成本线性增长,因此引入 S/M/L 三档,由编排层按 REQ 数 / 页面数 / 是否建表判档后传入;缺省 L(全套)。

## 2. Critical 名册必须与 `core-principles.md` 顶部逐字一致

两份名册各自维护时曾出现漂移:一份停在原则 25,漏掉了 28/29/30 三条 Critical,读者按旧名册只读结论行,
做不出合规设计。故约定以 SKILL.md「结论速查」那份为准、两份必须逐字一致。

## 3. Critical 原则条数只数名册,不用 grep 现算

`core-principles.md` 参考资源行里的「N 条 Critical」曾两次滞后于名册(停在 16、又停在 18)。
改用 `grep -c '^[0-9]\+\. \*\*.*(Critical)'` 现算会得到多 1 的结果:原则 8 正文里有一个
「数据库强制例外(Critical)」子项,而原则 8 整条并非 Critical(该 Critical 落点在检查项 21)。
名册是人工判定的结果,没有可靠的 grep 替代品。

## 4. QR 维度清单里的 Critical 维度数

「N 个标题就标 Critical 的维度」曾停在旧值而实际已增长,故只能由 checklist 里的 `Critical` 标记现数。

## 5. 核心原则 26(列表页数据量级)只挂 `check_list_page_scale.py`

该原则落地后一段时间内没有任何机器门,而外部约定索引把它与「统计指标口径表」并列挂在
`check_metric_spec.py` 名下——那个脚本只校验 8 列口径表,不含任何量级/分页判据。读者据此误以为
「有机器门兜着」,量级漏写时什么都不会报红。因此补了专用硬门,并约定引用时只挂它。

## 6. `check_sql_version_isolation.py` 支持两种目录布局

实际项目里 SQL 有两种组织方式:每个版本一个目录直接放脚本(flat),或按版本目录再分「增量 / 全量」双轨
(versioned)。只认前者时,后者的「把上一版增量 SQL 复制进本版」完全扫不到,门恒绿;
而把全量轨也纳入基线复制比对又必然假红(全量轨按定义就是整库快照)。故两种布局都支持、`auto` 自动识别,
versioned 下 V2 比增量轨(上一版只有全量轨时改与其全量轨比,本版增量照抄上一版全量即复制基线),两轨之外的 .sql 判 V5;flat 只扫版本目录当层;版本目录的 `v`/`V` 前缀都认(只认小写时 `V1.2.0/` 会被当成「本版无 DDL 变更」而放行)。

## 7. 碎片阈值机器门

`check_doc_split.py --check-fragment` 于 2026-09-17 补上;此前本阈值**零机器门**,而两处文档把该脚本摆在旁边,读者据此得到过假安全感。

## 8. 权限信号词计数

口径:对 SKILL 文档标题行按 `grep -rn '^#\{1,6\} .*<词>' <skills 目录>/ --include='*.md' | wc -l` 计数,不排代码围栏;2026-09-16 于源仓库 commit `9645265` 实测「权限」29 处、「角色」19 处,该次改动落地后同口径即 35/20。

## 12. QR 索引表的来由

脚本总数刻意不写死:它此前停在 31 而实际已是 33（漏了 `check_list_page_scale.py` 与 `check_permission_constraint.py` 两次新增），而这句话自称「现算为准」，读者照它去核会得出「表少了 2 个」的**错误结论**——**而这张表恰恰是当初靠逐行核对才发现「27 个脚本只有 11 个被派发」的那张表**。

⚠️ **本表在 2026-08-31 之前是缺失的，直接后果是：27 个脚本里只有 11 个进了 QR 派发，
另外 16 个「写好了、能跑、零上下文」的硬门从未被调用**，对应维度全靠子 Agent 语义判断。
那一轮把其中 **6 个**「传目录即可 + 实测 `exit 0` + 支持 `--json`」的接进了步骤 0
（维度 **11 / 17 / 20 / 21 / 28 / 30**）；2026-09-10 补第 7 个（维度 **8**
`check_third_party_mock_runtime.py`，接入前先修掉了它的块内反例段假红）。
**新增脚本时必须同步更新本表**，否则又会重演同一件事。

⚠️ **上面这段自己就腐化过一次，改它时请照着表现算、别照抄旧句子：** 原文写的是
「本轮把其中 **7** 个……（11 / 17 / 20 / 21 / **26** / 28 / 30）」——数目多算了一个，
而多出来的那个 **维度 26（`check_third_party_dep_reverse.py`）恰恰是被明令撤下的那个**
（它的位置参数是被测项目源码根，传设计文档目录必然「没扫到文件 → `exit 0`」= 恒绿灯，
本表第 26 行标的就是 ❌）。照那句话去「补齐」，等于把已经拆掉的假绿灯重新装回去。
