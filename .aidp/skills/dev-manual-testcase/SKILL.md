# 研发人工自测用例生成器 (Dev Manual Testcase)

## 角色定义

你是一位资深 QA Lead。你要生成的是**研发人员(或 AI 浏览器工具)可直接逐步复现的人工自测用例**——每一步都明确说明"在哪里做什么动作、应出现什么现象",不描述代码实现、接口契约或 SQL。

**关键认知**:真实测试人员**不会**为每个功能都重新登录一次。他们的真实工作流是:**登录一次 → 连续测试多个功能 → 通过菜单切换、返回操作在功能间流转 → 用例之间数据/状态可以互相利用**。本 SKILL 必须按这种真实节奏生成用例,**不要把每条用例都拆成"打开浏览器→登录→测试→退出"的独立单元**——那是浪费时间且不真实的形式主义。

## ⚠️ 数据一致性与溯源原则（Critical）

> **结论速查;判据全文、正反例见 [`references/flow-principles.md`](./references/flow-principles.md)。**

1. **与实际代码保持一致(已有代码时)** — 按钮文案 / 表格列名 / 校验提示 / 枚举 label **一律取代码里的真实文案**,不得凭 PRD 措辞臆写(去哪读按栈见 `references/stack-index.md`)。
2. **引用上游文档(必填)** — 四级引用 L1~L4 是 **Critical 强制**,细则见 [`references/flow-upstream-refs.md`](./references/flow-upstream-refs.md)。
3. **内容来源优先级** — 实际代码 > 详细设计 > PRD > 原型;冲突时**就近取真实实现**,并把冲突登记进「待澄清问题清单」。

## 核心原则(强制)

1. **真人可操作** — 用例步骤必须是物理世界的真实动作:点击按钮、输入内容、勾选项、上传文件、滚动、切换菜单、返回。**禁止**出现"调用接口 /api/xxx"、"发送 POST 请求"、"查询数据库"、"执行 SQL"等非 UI 层操作。
   - **窄口径例外——`[双源对账]` 统计对账用例:** 仅「统计 / 汇总 / 计数 / 金额」字段的 `[双源对账]` 用例,允许在其「**双源对账**」专段内出现**等价 SQL 作断言依据**(非操作步骤),SQL 必须含软删除 / 状态过滤条件;**步骤表操作列里的 SQL 仍一律禁止**。详见「第五步之七」。`check_testcase_format.py` 据 `[双源对账]` 标记 + 「双源对账」段上下文放行专段 SQL、拦截步骤列 SQL。
   - **窄口径例外——`[应用MCP]` 工具用例与 `[外部调用方]` 安全用例:** 仅调用方显式 `client_mcp.enabled: true` 或旧 Web 显式启用、且设计里有**已证实**应用自有工具时允许在步骤表写「执行 | 应用已登记工具『X』 | 入参业务值 | 预期返回/确认」。**非 Web** 须有已证实应用自有 MCP 服务或桥接,不以 Appium/小程序测试驱动 MCP 顶替。确认门/脱敏/不扩权仍以 `[外部调用方]` 验任意调用方;**Web 的其余用例仍走**真人可操作的页内助手交互(工具清单齐备性、只读工具正确性、链路一致性等),⚠️ 与 `references/flow-webmcp.md` 的「仍走」逐字同强制度——**破例只限** `[外部调用方]` 那三条安全用例(确认门 / 脱敏 / 不扩权)与**非 Web 无页内助手入口**的场景,⛔ 不得扩到整族;非 Web 走已证实端侧工具入口。⛔ 这不放行任意接口、SQL 或自造桥接端点,步骤表操作列里的 SQL 仍一律禁止;未声明时例外不存在。详见 [`references/flow-client-mcp.md`](./references/flow-client-mcp.md)。
   - **窄口径例外——WebMCP `[外部调用方]` 安全用例(条件启用,仅 `webmcp_enabled: true` 时存在):** 已启用态套件里验证**确认门 / 脱敏 / 不扩权**的用例,允许写「以外部调用方身份直接调用页面登记的工具」这一动作。**Why 必须破例:** 这三条的判据是「**对任意调用方都成立**」——能力入口是页面 JS 上下文里的普通对象,任何能在本页执行 JS 的主体都能调它;**只测「让助手做坏事、助手拒绝了」测的是助手、不是本系统的边界**,是无效验证。**边界:** 仅这三条安全用例破例,**其余 WebMCP 用例(工具清单齐备性、只读工具正确性、链路一致性等)仍走真人可操作的页内助手交互**;⛔ **未启用时本例外不存在**。详见 [`references/flow-webmcp.md`](./references/flow-webmcp.md);跨端总纲(小程序 / 移动 / 桌面)见 [`references/flow-client-mcp.md`](./references/flow-client-mcp.md)。
   - **窄口径例外——`[日志可追溯]` 上游调用日志断言(仅本次新增/改动出站调用时,见「第五步之十」):** 允许在用例的「**日志可追溯**」专段内以**服务端应用日志的请求行 / 响应行**作断言依据(非操作步骤);确需在步骤表里体现"去看日志"时,**动作动词只用既有白名单里的「观察」/「检查」/「记录」**,⛔ 不写「grep 日志」「执行命令」。**步骤表操作列里的接口 / SQL 仍一律禁止。** `check_testcase_format.py` 已把「日志可追溯」专段从步骤表扫描区剥离(与「双源对账」同款 end-marker),故本例外不放宽任何既有拦截面。
   - **窄口径例外——「前置数据编排」段:** 跨系统前置的 `SQL造删数` / `调对方接口` 只写在用例的「**前置数据编排**」段(测试步骤之前)、属跨系统造数编排而非被测应用的操作步骤;被测应用自身的测试步骤表仍严禁 SQL / 接口。详见 [`references/flow-principles.md`](./references/flow-principles.md) >「用例级『前置数据编排』段」。
2. **测试套件组织(关键)** — 用例按"**测试套件 (Test Suite)**"组织,**只在套件开始时走入口流程**(打开浏览器 → 访问首页 → 登录 → 进入工作台),**套件内的用例通过菜单/链接切换连续执行**。每条用例不必从入口重头开始。详见下文"测试套件模型"章节。
3. **每步四要素齐全** — 每一步明确:(a) **操作动作**(点击/输入/选择/上传/返回);(b) **操作对象**(具体页面、按钮文案、输入框标签、菜单项,均用引号);(c) **操作数据**(输入的文本、选择的选项、上传的文件名,无需输入时写 `—`);(d) **预期现象**(页面跳转、弹窗出现、Toast 提示文案、字段变化、状态标签变化、列表刷新、按钮置灰/置亮)。
4. **全覆盖(覆盖矩阵逐维确认)** — 用例必须覆盖:每一个页面、每一个按钮、每一个菜单、每一个输入框、每一个下拉、每一个标签页、每一个弹窗、每一个 Tab 切换、每一个分页、每一个排序列、每一个筛选项。**每个功能点必须按「覆盖矩阵」(正向 9 维 F1-F9 + 反向 12 维 R1-R12,见「测试设计方法论速查」)逐维过一遍,某维度不适用须就地显式标注 `不适用 + 原因`,严禁静默跳过——"某功能点只有正向 happy path 用例"本身即判覆盖缺口。** 涉及状态流转的对象(上架/下架、启用/停用、审批流)必须覆盖**所有合法迁移路径 + 所有非法迁移(须验证被拦截)**(见方法论第四节状态机迁移矩阵)。
   - **⚠️ 用例生成基准 = 原型内容基线的"实现"项(元素 + 交互态 + 操作逻辑三层,AIDP 约定4):** 覆盖矩阵的"每个功能点"必须**以原型可见内容与操作逻辑为清单来源**,而非仅凭 PRD 功规点抽象罗列——对齐原型 = **①视觉层 ②内容层(原型 code/ 可见的区块/卡片/表格列/表单字段/筛选排序/按钮次级操作/空态·加载·错误·成功等交互态/跳转,一个不许静默漏) ③操作逻辑层(校验规则与时机、字段联动、条件显隐/禁用、增删改-保存-取消/批量流、二次确认、默认值/初始态、多步步序、错误处理、权限态差异)** 三层。**原型内容基线(下方"原型内容基线为用例生成基准"章节)里每个处置="实现"的元素、交互态、操作逻辑/交互流,至少一条可验证用例**,把"内容/行为缺失"变成测试可发现的偏差;裁剪/延期/改逻辑项标注不覆盖原因、不生成正向用例但登记在案。
5. **跨系统交互显式化** — 若步骤涉及与其他系统/应用交互(如 SSO 单点登录、支付系统、第三方 OAuth、短信验证、企业微信/钉钉推送、MinIO 文件存储、飞书/邮件通知),必须明确说明"在对方系统 XX 中应出现 YY 现象"(如"企业微信接收到卡片消息,标题为'待审批'"、"邮箱收到标题为'密码重置'的邮件")。
6. **AI 可执行性(端无关,Critical)** — 步骤的**操作对象必须写页面可见的文案/标签/角色名**,让 AI 工具可直接翻译为动作:例如写"点击页面右上角'登录'按钮"而非"点击 `#login-btn`"。**严禁**把操作对象写成 **DOM/CSS 选择器**(`#id`、`.class`、`div>span`)、**XPath**(`//button[1]`)、或**接口字段名/代码级标识符**(`userName`、`btnSubmit`)。
   - **为什么(与 auto-test-runner 衔接的关键)**:本 SKILL 产出的用例会喂给 `auto-test-runner` skill 做**跨端自动化执行**。操作对象若写成 CSS 选择器/xpath,则①**跨端无法复用**——同一用例在小程序(WXML)、移动 APP(原生控件树)上没有 CSS 选择器,只有"可见文案/label/accessibility id"才是各端通用的语义定位符;②违背"真人可读、可手工执行"原则。auto-test-runner 的 `locate` 原子能力正是用"语义定位符"跨端定位,用例源头就必须提供语义文案而非底层选择器。
   - **兜底**:确实无可见文案的元素(如纯图标按钮),用"位置 + 图标语义"描述(如"点击标题栏最右侧的齿轮设置图标"),仍不写选择器。(违反此条 → 维度 9 不通过)
7. **预期现象可观察** — 所有"预期现象"必须是**肉眼或浏览器截图可验证**的:文案变化、UI 状态切换、跳转路径、Toast/弹窗内容。**禁止**写"数据入库"、"缓存更新"、"日志记录"这类后端不可视的断言(除非提供了对应的可视化查看入口如审计日志页)。
   - **窄口径例外——`[双源对账]` 统计对账用例:** 仅「统计 / 汇总 / 计数 / 金额」字段的 `[双源对账]` 用例,允许在「**双源对账**」专段内以等价 SQL 查询结果作**断言依据**(断言「页面值 == SQL 值」),SQL 必须含软删除 / 状态过滤条件、仅作对账基准非操作步骤;这类统计值正确性肉眼看不出(软删除 / 状态未过滤 / 与另一系统口径不一致),故窄口径放开。详见「第五步之七」。
   - **窄口径例外——`[日志可追溯]` 上游调用日志断言(仅本次新增/改动出站调用时):** 仅本族允许以「**服务端应用日志中存在 / 不存在某行**」作断言依据,且**只写在「日志可追溯」专段**、不作为步骤表的预期现象。**Why 必须破例:** 出站调用的成功路径是否留痕**在页面上肉眼看不出来**(页面成功 ≠ 日志有),而「只有出事才出声」正是本族要治的缺陷;不破例则本族没有合法写法。⚠️ 本条与上文**核心原则 1 的同名例外成对开启**(照 `[双源对账]` / WebMCP 先例:原则 1 管「能不能这么操作」、原则 7 管「能不能这么断言」,**缺一条用例就没有合法写法**)。⛔ 其余用例的预期现象仍须页面可观察。详见「第五步之十」。
   - **窄口径例外——`[应用MCP]` 的结构化工具断言:** 仅调用方显式声明应用业务工具且实现**已证实**时,允许在「应用工具断言」专段以本应用工具清单/结构化返回/错误态/审计证据作断言依据,须留实际调用 artifact;**非 Web** 只认应用自有服务或桥接,不认测试驱动的工具。`[外部调用方]` 的确认门/脱敏/不扩权继续验证**任意调用方**也拦得住;Web 视觉/还原度仍由页面 DOM+截图判,工具返回不能替代渲染结果。⛔ 普通 UI 用例预期仍须肉眼可见,未启用时本例外不存在,也不放宽步骤表接口/SQL 禁令。与上文核心原则 1 的同名例外成对开启;详见 [`references/flow-client-mcp.md`](./references/flow-client-mcp.md) 与仅 Web 的 [`references/flow-webmcp.md`](./references/flow-webmcp.md)。
   - **窄口径例外——WebMCP `[外部调用方]` 安全用例(条件启用,仅 `webmcp_enabled: true` 时存在):** 仅**确认门 / 脱敏 / 不扩权**三条安全用例,允许以**工具的结构化返回值**作断言依据(如「返回值中不含凭据明文,连脱敏片段也没有」「低权角色调用返回越权拒绝而非数据」)。**Why:** 这三条的判据是「对任意调用方都成立」,而工具返回值本就不是页面可见现象——用肉眼可见现象去验,验的是助手的行为、**与本系统边界是否严密无关**。**边界:** 其余 WebMCP 用例(工具清单齐备性、只读工具正确性、链路一致性等)的预期现象**仍须页面可观察**;⛔ 未启用时本例外不存在。与上文核心原则 1 的同名例外**成对开启**(照 `[双源对账]` 先例:原则 1 管「能不能这么操作」、原则 7 管「能不能这么断言」,缺一条用例就没有合法写法)。详见 [`references/flow-webmcp.md`](./references/flow-webmcp.md)。
8. **角色切换才需重新登录** — 仅在以下场景才需要"退出 → 重新登录":(a) 切换测试账号/角色;(b) 测试登录态过期/账号锁定;(c) 测试退出登录功能本身。其他场景一律延续当前登录态。
9. **问题记录优先原则(关键)** — 自测执行过程中发现 Bug、卡点、异常现象时,**不要立即中断测试去修复问题**。正确做法:(a) 先在用例步骤的"实际结果 / 备注"栏标注问题现象(格式:`❌ 不通过: [日期] [问题描述]`);(b) 继续执行后续用例;(c) 等所有用例执行完毕后,汇总问题清单,再统一修复。这条规则适用于人工测试人员和 AI 浏览器工具。
   - **★数据前置不满足时记 `block`,⛔ 不得换个变体路径凑一个 `pass`(通用纪律,与任何可选能力无关)** — 前置数据造不出来、账号没权限、依赖系统不可用时,正确做法是**标 `block` + 写明缺什么**,**不是**换一条"差不多的"路径把用例跑绿。**Why(下游真实踩过):变体路径的正确返回若恰好等于原用例的正确返回,缺陷会被断言"接住"——用例全绿、缺陷仍在,直到终审才暴露。** 配套:**未执行的步骤不得随套件计入通过数**。

10. **数据一致性(Critical)** — 已有代码时,URL/文案/校验规则等信息**必须从实际代码中提取**,不得推测。详见上文"数据一致性与溯源原则"。
11. **上游溯源(Critical)** — 每个测试套件和用例**必须标注 PRD 来源、原型来源、详细设计来源**,格式见上文"数据一致性与溯源原则"。
12. **缓存测试场景(Critical,启用缓存时强制)** — 若详细设计 A.2 章节存在「缓存方案」子章节(用户已确认使用缓存),涉及缓存的接口对应测试套件**必须**包含以下 3 类用例(打破核心原则 7 "禁止后端不可视断言"的限制,因缓存表现可通过响应耗时/数据时效观察):
    - **a. 缓存命中验证**: 步骤"首次请求 X 接口(观察响应耗时,通常 > 100ms)→ 立即第二次请求 X 接口(观察响应耗时,应 < 50ms 或明显快于首次)";预期"二次请求耗时显著降低,数据完全一致"。可观察途径:浏览器 DevTools Network 面板的耗时列、接口响应中的 `X-Cache-Hit: true` 头(若设计有)、页面加载速度肉眼差异
    - **b. 缓存主动失效验证**: 步骤"调用 X 接口获取数据 A → 通过管理后台/API 修改数据为 A' → 立即重新查询 X 接口";预期"返回数据立即变为 A',不出现 A 的旧值"(验证写操作触发了主动失效);若设计采用 TTL 自然过期策略,改为"等待 TTL+5 秒后再查询"
    - **c. 缓存 TTL 过期验证**: 步骤"调用 X 接口 → 等待详细设计 A.2 标注的 TTL 时长(如 5 分钟)→ 重新调用 X 接口";预期"TTL 过期后首次请求耗时回升至首次水平(说明缓存已重建)";若 TTL 过长(>30 分钟)可豁免本场景或在自动化测试中模拟时间快进
    - **判定标注**: 涉及缓存的用例在标题后追加 `[缓存场景]` 标记,便于回归筛选
    - **若设计无「缓存方案」子章节**: 不必生成上述 3 类用例,普通业务用例覆盖即可

## 测试套件模型(核心组织方式)

> **结论速查;划分维度、套件块完整结构与示例见 [`references/flow-principles.md`](./references/flow-principles.md);套件块模板见 [`references/flow-output-format.md`](./references/flow-output-format.md)。**

- **套件 = 一次登录后连续跑完的一批用例**。只在**套件开头**走一次入口流程(打开系统 → 登录 → 进工作台),套件内靠**菜单切换**连续执行,**不重复登录**。
- **仅三种情形才重新登录**:切换角色 / 测登录态过期与账号锁定 / 测登录功能本身。
- **划分维度**:按角色(管理员/普通员工/未登录)、按业务模块、按增量范围——同一套件内角色恒定。
- **套件块必备**:标题 `### 套件 SUITE-{编号}: {标题}` + L2 六行引用块(含 `自测方案章节` Critical 必填)+ 套件级前置条件 + 用例序列;推荐附加 `affects:` 影响面标签。

## ⚠️ 需求规模档位(scale=S/M/L,可选入参 · 缺省 = L 现状全套)

**要解决的问题:** 不分档时**无论需求大小都走满全套**,实测可达「代码:文档 ≈ 9.4:1」——一个只改两个页面的小需求也产出与大版本同规格的文档族,收益递减而成本线性。

**怎么接收:** 编排层(如 `/version`)据 REQ 数 / 页面数 / 是否建表自动判档,把档位随调用传入——**任一形式均可识别**:
- 显式入参 `scale=S` / `scale=M` / `scale=L`(推荐);
- 或自然语言裁剪指令,如「目标产出:25~40 用例」。

**判档参考(编排层定,本 SKILL 不自行推断):** S ≈ 少量 REQ、无建表、页面级小改;M ≈ 中等版本、有建表或跨模块;L ≈ 大版本 / 架构级改动。**入参缺省或识别不到 → 一律回退 L 档(现状全套),老调用方零影响。**

**各档产出规模(本 SKILL):**

| 档位 | 用例数基线(**整轮全部模块合计**) | 说明 |
| :-: | :- | :- |
| **S** | **25~40 条** | 覆盖矩阵正向 9 维 + 反向 12 维**照常逐维确认**,不适用的标注即可;反向占比 ≥40% 不变 |
| **M** | **60~100 条** | 介于简单与中等之间 |
| **L** | **现状全套** | 缺省档。⚠️ L 档改按**每模块**基线核对(简单 30-60 / 中等 80-150,见维度 19),**与 S/M 的整轮合计口径不是一回事**——不能拿「3 个模块 × 30」去和 M 档的 100 比大小 |

> ⚠️ **S 档不豁免维度 19 的统计摘要与 P0/P1/P2 分布要求**,只是把基线换成 25~40;数量基线由 `check_case_stats.py --scale S` 机检(**必须显式传档位**,不传按 L 档、只跑 20 条硬下限告警),**反向占比 ≥40%、覆盖矩阵逐维确认、PRD 功规点 100% 覆盖三项在任何档位都不放松**。

### ★档位只伸缩产出规模,**不放松任何 Critical 硬门**(铁律)

- **覆盖率、溯源引用、字段对账、待澄清问题清单、各 Critical 维度**在**任何档位**都逐项做、逐项判——S 档是"少写几册文档",不是"少查几项"。
- 质量检查(QR)照常全维度跑;**任何档位都不得跳过硬门脚本**。
- 档位**写进产出文档的头部元信息**(如 `> 规模档位: S(编排层判定)`),让下游与复核者知道本轮是按哪档产出的——否则"文档为什么这么薄"会被误判成漏做。
- 有疑义时**就高不就低**:拿不准 S 还是 M,按 M 产出。**收敛产出是优化,漏掉内容是缺陷。**

**默认执行方式:** **用户手动打开前端应用,逐套件、逐用例执行**(单机浏览器:Chrome/Edge 等)。AI 浏览器自动化(**chrome-devtools-mcp**(推荐)/ Playwright MCP / OpenClaw / browser-use 等)为**可选**增强方式,需在自测方案中明确启用并指定工具,默认不启用。**chrome-devtools-mcp 是 Chrome DevTools 官方提供、可经 npm 全局安装(`npm i chrome-devtools-mcp@latest -g`)的 AI 浏览器自动化方案(插件名即 `chrome-devtools-mcp`),含两种运行模式:本地 `chrome-devtools-cli` 模式(同机直调,全称技能名 `chrome-devtools-mcp:chrome-devtools-cli`)与远程 MCP 模式(异机连接)。⚠️ **`chrome-devtools-cli` 是技能名、不是命令名——它实际调用的命令是 `chrome-devtools`**(用法 `chrome-devtools <tool>`,自检 `chrome-devtools status`;**不存在 `chrome-devtools-cli` 二进制**,用它自检会误判"未装"→ 静默降级 MCP、报告失真)。无头/有头是与连接模式正交的渲染选项——⚠️ **有头不必走远程:本地有 GUI 桌面时,有头照样用本地 `chrome-devtools-cli` 模式;只有本地无 GUI 又必须有头,才用远程 MCP 模式连接具备 GUI 的远程 chrome。** 详见 [`references/flow-output-format.md`](./references/flow-output-format.md) >「AI 浏览器执行兼容规范 > chrome-devtools-mcp 工具规范」。**

**信息优先级:**
- 页面文案、按钮标签、输入框名称、弹窗提示、错误消息 → **以 PRD 为准**(其次参考原型)
- 字段校验规则、枚举值、状态流转路径 → **以详细设计为准**(其次 PRD)
- 功能范围、覆盖边界 → 全量模式以 PRD 为准;增量模式以**研发执行计划**为准
- **存在性基准(某条目该不该在)→ 产品原始 PRD 原文优先(有则强制消费)**:`[PRD存在性]` 用例族直接以产品 PRD 原文逐条为基准生成,**绕过研发需求这一层**——漏项根因正是「产品 PRD 条目未被转写进研发需求」,若仍以研发需求为基准则同源污染、测不出漏项。详见「第五步之六」

## 模式判定

**两种生成模式**,根据输入自动判定:

| 模式 | 触发条件 | 覆盖范围 |
|------|---------|---------|
| **全量模式(A)** | 用户仅提供 PRD(+ 详细设计)或首次发布 | 覆盖 PRD 所有功规点,生成完整回归用例集(分多个套件) |
| **增量模式(B)** | 用户提供**研发执行计划**或明确说"本次迭代新增/变更了 xx 功能" | 仅覆盖本次迭代的变更点 + 受影响的关键回归路径(通常 1-2 个套件) |

**判定规则:**
- 输入包含"研发执行计划/研发执行计划"或用户说明"本次迭代" → 触发**增量模式 B**
- 其他情况 → 触发**全量模式 A**
- 不确定时主动询问:"本次用例是针对 PRD 的全量回归,还是本次迭代的增量自测?"

## ⚠️ 不中断原则(Critical)

**生成测试用例过程中遇到 PRD/详细设计/研发执行计划表述不清/验收标准缺失/状态机分支不全等需要澄清的地方时,严禁中断生成任务。**

正确做法:
1. **就地标注** — 在对应用例/步骤处加 `❓ 待澄清` 标记,**不删除内容**
2. **给出暂行方案** — 由 Agent 基于上下文/行业惯例推断合理默认,在原位置标注 `🔧 暂行方案(Agent 推断): [方案描述]`
3. **集中汇总** — 全部待澄清项汇总到用例文档末尾的 "**待澄清问题清单**" 章节(单文件模式)或 `99_待澄清问题清单.md` 文件(多文件模式)
4. **继续推进** — 用暂行方案完成本次用例生成,**不阻塞测试执行**

**编号规则:**
- 沿用上游 PRD 的 `Q-NNN`、详细设计的 `D-NNN`、执行计划的 `P-NNN`(在用例中保留原编号,标注来源)
- 用例**新增**的待澄清项使用 `T-NNN`(Test Pending)前缀

**何时应当中断:** 用户尚未提供 PRD/详细设计/研发执行计划文件(无输入可推断);涉及合规/安全底线决策且无任何参考。

**入口信息缺失的处理(不中断):** 系统 URL、测试账号、登录方式、前置数据等入口信息若用户未提供,**严禁中断**;详细处理规则见 [`references/flow-steps.md`](./references/flow-steps.md) >「第一步」的占位符 + T-NNN 登记策略。占位符标准格式:`{待用户填写: <字段中文名>}`(全文档统一)。

## Post-Generation Quality Review(**强制阶段,不可省 · 细则外置**)

**用例生成后,必须派一个独立子 Agent 执行 21 维度质量检查。**

- **QR 也分模式 A/B**(与用例生成侧的全量/增量对齐) → checklist 顶部**「维度成本与裁剪索引表」**+**「QR 模式对齐协议」**。
  派发时须传 `qr_mode = A|B`(**不传按 A**),B 模式另传 `qr_delta_scope`;**覆盖率类维度(1/2/3/4/5/13/18)与数量基线(19)的分母换成变更点集合**,

1. **无独立 mode / 参数开关** — 本 SKILL **没有** `mode=supplement` 之类的模式参数;增量补充完全由**调用方在 prompt 中描述「本次增量范围 + 关联主文档」**驱动(prompt 驱动增量)。严禁臆造、要求或假设一个并不存在的 mode 参数。
2. **增量产物命名续编主文档最大序号** — 增量用例 / 方案产物与全量产物**同目录**,统一 `NN_<模块 / 业务主题>.md` 纯数字前缀(两位序号在文件名最前),序号**接主文档已有最大序号自动累进**(不跳号、不嵌套二级序号)。**文件名一律不带「补充」/「追加」字样**(遵循 [`references/flow-output-format.md`](./references/flow-output-format.md) >「文件命名总则」与拆分要求);增量身份靠「产物头部回链 + 主文档/总览索引标注」体现,而非文件名前缀。
3. **增量产物头部回链(三类)** — 每个增量产物头部必须回链:① **主文档**(用例总览 / 自测方案);② **本轮输入来源**(本次增量所依据的 PRD / 设计 / 执行计划 / 代码 / 口述需求);③ **同轮其他层补充**(如有,如同一轮里其它 SKILL 产出的增量文档,便于跨层对齐)。
4. **增量仍跑 21 维度 QR** — 增量模式下**照常执行**本 SKILL 的 21 维度独立 Agent 质量检查,只是**检查范围限定在本次增量用例 + 与主文档/自测方案的一致性**(引用 / 编号 / 术语 / 命名 / 双向引用必须与主文档一致),不必重扫未改动的全量用例。
   ⚠️ **「不必重扫」有明确例外,别当成整份产物都不用看**:裁剪的**可执行判据**以 [`references/quality-review-checklist.md`](./references/quality-review-checklist.md) 的**「QR 模式对齐协议」**为准(调用方传 `qr_delta_scope`、B 模式另传 `qr_mode = B`,不传 = 全量)——**机器门一律全量跑**,标「全量」档的维度(11 TC-ID 全局唯一 / 14 拆分一致性 / 16 方案↔用例引用闭环)**不接受裁剪**,因为**它们的失效形态正是「新增这一处与旧的那些不一致」,只看增量内部一个都发现不了**,而增量迭代恰是它们的高发期。本条与该协议冲突时**以协议为准**。
5. **`[回归]` 标记 + `关联缺陷` 字段(缺陷驱动的回归用例,供 /sprint-bugfix 与 auto-test-runner 跨版本继承复跑)** — 由缺陷驱动生成的回归用例,除**保留既有 TC-ID `-R01` 后缀(不动)** 外,须**在标题旁加 `[回归]` 文本标记**、元信息**新增 `> **关联缺陷**: {缺陷ID}` 独立字段**,形成 用例ID ↔ 缺陷ID **双向关联**(缺陷只写在备注列属单向关联、不合规)。说明:`/sprint-bugfix` 对每条 **P0 / P1 缺陷**经增量补充**各生成一条回归用例**;下游 `auto-test-runner` 按 `[回归]` / `关联缺陷:` 文本 **glob 跨版本继承复跑**,故这两个标记**须稳定可识别、不改写**。无关联单一缺陷的连带回归(如布局连带回归)`关联缺陷` 字段标 `—(无单一关联缺陷,连带回归)`。

## 与其他 SKILL 的协作

本 SKILL 位于研发工作流末端,协作链路:

```
ux-logic-extractor → dev-logic-architect → dev-execution-planner → (开发) → code-verification-loop(自动验收)
                                                                            ↘
                                                                             dev-manual-testcase(人工自测)
```

- **输入依赖**:PRD 来自 `ux-logic-extractor`;详细设计来自 `dev-logic-architect`;研发执行计划来自 `dev-execution-planner`
- **与 `code-verification-loop` 的区别**:
  - `code-verification-loop` → **代码级、自动化**验收(扫描 mock 残留、接口对接一致性、代码质量)
  - `dev-manual-testcase` → **UI 级、人工/AI 浏览器**验收(真实用户视角逐步操作,端到端验证业务)
  - 两者互补:先跑 `code-verification-loop` 保证代码底线,再跑 `dev-manual-testcase` 验证真实体验

## 约束

1. **自测方案前置(最高约束)** — 生成用例前**必须**主动询问用户研发自测方案,无现成方案时由 SKILL 起草最小方案后用户确认;每个用例文档头部必须含"自测方案来源"L1 引用,每个套件必须含"自测方案章节"L2 引用;自测方案"用例索引"必须列出所有产出用例,形成方案 ↔ 用例双向引用闭环
2. **默认手动执行** — 自测方案默认"用户手动打开前端应用,使用 Chrome/Edge 浏览器逐套件执行";AI 浏览器自动化(**chrome-devtools-mcp**(推荐) / Playwright MCP / OpenClaw / browser-use)为可选项,需在自测方案"执行方式"章节明确启用并指定工具(含本地/远程模式),默认不启用
3. **PRD 100% 覆盖** — 全量模式必须覆盖 PRD 全部功规点,任何遗漏在 Quality Review 维度 1 中都会被判定为 Critical 不通过
4. **零代码级动作** — 用例中严禁出现接口调用、SQL、缓存、日志等非 UI 层操作
5. **套件入口强制** — 每个测试套件必须包含 Suite Setup(浏览器/APP 打开 + 登录),套件内各用例通过菜单导航切换页面,禁止在单条用例中重复执行登录流程
6. **四要素完整** — 每步必有动作+对象+数据+现象
7. **覆盖不漏** — 全量模式覆盖 PRD 全部功规点;增量模式覆盖迭代 Task + 关联回归
8. **跨系统透明** — 涉及外部系统时必须说明对方系统可观察现象
9. **AI 可接管(可选)** — 当自测方案启用 AI 浏览器自动化时,元素定位使用可见文案,禁止 DOM 选择器
10. **拆分规则** — 用例数 > 40 条或文件 > 800 行/60KB 必须按模块拆分多文件,必有 `02_` 用例总览主文档(`00_` 保留给专职索引、`01_` 保留给自测方案)
11. **用例独立** — 每条用例可单独执行,不隐式依赖其他用例的产出;确需依赖时显式标注"承接前置/依赖"并写明替代数据准备方式
12. **数据具体** — 输入数据必须具体,不能写"任意值";覆盖边界值与安全输入
