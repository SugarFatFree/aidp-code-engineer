## 输出规范：单文件 vs 多文件拆分

### 职责边界（PRD 不写研发计划）

**PRD 只描述"做什么、为什么做、做出来什么样",严禁包含研发管理内容**:

- ❌ **严禁**包含: 研发执行计划、Sprint 排期、研发计划、开发周期、工时估算、里程碑节点、上线时间表、版本发布计划、人员分工
- ❌ **严禁**将功能点绑定具体迭代版本号(如 `Sprint-001 实现 X`、`第二期上线 Y`)或具体日期(如 `2026-06-30 前交付`)
- ✅ **可以**: 标注业务优先级(P0/P1/P2)表达"业务必要性"(必须有 / 应该有 / 锦上添花),但**不**绑定迭代版本或时间点
- ✅ **可以**: 写"功能 A 依赖功能 B 先就绪"这类**业务依赖关系**

**Why:** 研发执行计划属于 `dev-execution-planner` 的职责,在 PRD 中混入会导致 PRD 随排期变化频繁修订,失去需求基线作用。

### 拆分判定

**默认输出内容集中的 PRD（强烈推荐）**。内容不多时尽量把正文集中在**一份内容文档**,便于阅读和维护。

**⚠️ AIDP 文档命名范式（四 SKILL 统一，逐字遵循）：**
- **`00_` 槽位恒给专职索引 `00_索引.md`；内容主文档一律从 `01_` 起。** 已废除旧锚「单文件主文档 `00_PRD-{项目名}.md`」与「多文件主文档 `00_PRD-{项目名}-总览.md`」。
- **即便只有一份内容文档,也产出两个文件：`00_索引.md` + `01_PRD-{项目名}.md`。** 内容主文档命名 `01_PRD-{项目名}.md`;多文件时再 `02_`..`97_` 子文档、`98_`/`99_` 固定聚合(如 `99_待澄清问题清单.md`)。
- **`00_索引.md` 三项必载：** ① 本目录全部内容文档(`01_`+)清单 + 每份一句话范围;② 每份文件的生成时间(`YYYY-MM-DD HH:MM`,区分「首次产出/最近修订」)——生成时用 shell `date +"%Y-%m-%d %H:%M"` 取当前时间打戳,**AI 不得凭空填时间**;③ 主文档/补充标识(版本规划首产=「主」,增量补充=「补充」)。建议列：`| 序号 | 文件 | 生成时间 | 类型 | 说明 |`;补充轮再加 `关联输入变更 | 状态 | 取代关系` 列。
- **补充文档：** 文件名不带「补充」字眼,直接 `NN_<业务名>.md`;增量产出时给 `00_索引.md` **追加一行**(类型=补充 + 生成时间),而非改内容主文档正文。
- **历史存量**(裸 `00_<语义名>.md` / `00_…-总览.md` / `NN_补充-…`)：grandfather 识别放行、不报错;仅新生成不再产出旧锚。

**拆分触发条件**（满足以下任一条件时,才考虑拆分）:
- 单文件预估超过 **800 行** 或 **60KB**
- 页面数量超过 **15 个**
- 业务模块超过 **4 个**(如 用户/订单/商品/营销/...)
- 字典/枚举条目超过 **25 个**
- 用户明确要求"拆分输出"

**拆分数量控制（Critical）:**
- **目标文件数: 3~5 个**（含主文档）,不要超出太多
- 宁可单个文件长一些（800~1200 行）,也不要拆成 7、8 个碎片文件
- 只有内容确实非常多（>1500 行）时才允许超过 5 个文件
- 拆分前先评估：能否通过合并相近章节减少文件数？

### 拆分原则

1. **文件名必须采用简洁命名格式**: `{两位数字序号}_{中文文件名}.md`(如 `01_PRD-{项目名}.md`、`06_字典枚举.md`)
   - `00_` **固定分配给专职索引 `00_索引.md`**(内容主文档从 `01_` 起);`99_` 固定分配给待澄清问题清单(如有);其余序号按内容顺延
   - **严禁嵌套二级序号**(如 `06_01_用户域字典枚举.md`),拆分时应使用相邻序号顺延(如 `06_字典枚举索引.md`、`07_用户域字典枚举.md`、`08_订单域字典枚举.md`)
   - **严禁嵌入章节编号**(如 `03_五-1_用户列表.md`),保持文件名简洁清爽
   - **严禁使用"补充"/"追加"作为文件名前缀或中缀**(如 `补充-07-订单域.md`、`07_补充-订单域.md`) → 正确格式: `07_订单域字典枚举.md`(补充身份靠 `00_索引.md` 登记「类型=补充」,不进文件名)
2. **必须生成专职索引 `00_索引.md`**,作为索引和总入口(载全部 `01_`+ 内容文档清单 + 生成时间 + 类型),内容正文从 `01_PRD-{项目名}.md` 起
3. **子文档按业务域拆分**,每个子文档聚焦一个业务域或一类内容
4. **字典/枚举单独成文件**: 即使其他模块未拆分,只要字典枚举条目较多(>15 个或预估 >300 行),也必须独立为 `{NN}_字典枚举.md`
5. **子文档之间需要互相引用时**,使用相对路径 + 章节锚点格式
6. **章节编号与文件名的映射关系记录在主文档的"文档结构与拆分说明"表中**,读者通过索引表了解归属,而非文件名本身
7. **避免过度拆分(碎片化)**:
   - 单个子文档**目标行数 200~800 行**(专职索引 `00_索引.md` 除外,作为索引可较短)
   - **严禁**生成不足 **100 行且不足 4KB** 的碎片子文档(两条件同时满足才判碎片;专职索引 `00_索引.md` 除外)
   - 若按业务域拆分后某子文档不足 100 行,**必须合并**到相邻业务域子文档或"通用/附录"中
   - 宁可单文件 850 行不拆,也不要拆成 5 个 80 行的碎片
   - 字典枚举拆分时也遵循同一标准: 单个子文件 < 100 行的应合并回 `{NN}_字典枚举.md` 单文件
   - **阈值说明**: PRD 内容密度高(表格/枚举/交互流程),100 行已含足够信息;详细设计文档含 DDL/API 表头,需 150 行才能容纳完整一张表

### 🚫 多文件分册白名单(Critical 强制约束)

模式 A/B 多文件输出**严禁**生成以下"技术分册"文件,即便产品需求文档原文如此组织,也必须在「上游内容净化」Step 中剥离 + 重组:

| ❌ 禁止的分册类型 | 违规示例文件名 | 原因 |
| :- | :- | :- |
| 字段+字典混合分册 | `05_字段与字典.md`、`06_DTO与VO定义.md` | 字段是字段、字典是字典;字段表如有业务约束应分散在各业务子文档,只有"业务字段中文名 + 业务规则",**不含变量名/类型/校验正则** |
| 数据库设计先验分册 | `08_数据库设计.md`、`09_表结构与ER图.md`、`10_数据库设计先验.md` | 数据库设计归 `dev-logic-architect`,PRD 不出表名/字段英文名/DDL/ER 图 |
| 接口设计分册 | `11_接口设计.md`、`12_API契约.md` | 接口契约归 `dev-logic-architect`,PRD 不出 HTTP Method/URL/Request/Response |
| 技术架构分册 | `01_技术架构.md`、`02_技术栈选型.md` | 技术选型归 `dev-logic-architect`,PRD 不出 Vue/Spring/Redis 等技术词典 |
| 非功能技术分册 | `13_非功能需求.md`(若内容是缓存策略/索引设计/部署架构) | PRD 只描述业务级非功能指标(如"列表加载 < 2s"),不写实现手段 |

**允许的字典枚举独立分册**(白名单):

- ✅ `06_字典枚举.md` — 集中收录所有业务状态/类型/分类/角色枚举,只含 `编码 / 显示文本 / 业务含义`
- ✅ `06_字典枚举索引.md` + `07_用户域字典枚举.md` 等 — 字典枚举条目超过 30 个时的二次拆分

**判定脚本:** 落盘后强制运行 `python3 <SKILL_DIR>/scripts/check_split_blacklist.py <PRD目录>`,命中违规即不通过。

### 目录结构与序号分配示例

> ⚠️ **本树是「序号如何分配」的示例，不是推荐拆成这么多份。** 它把各类章节可能占用的序号一次列全，便于查"某类内容该给几号"；**实际产出仍受上文「拆分数量控制（Critical）」约束——目标 3~5 个文件（含 `00_索引.md`），只有内容 >1500 行时才允许超过 5 个**。多数项目的真实形态是 `00_索引.md` + `01_PRD-{项目名}.md`（+ 视情况 `06_字典枚举.md` / `99_待澄清问题清单.md`）。

```
docs/product/{项目名}/
├── 00_索引.md                           # 专职索引(必需):内容文档清单 + 生成时间 + 类型(主/补充)
├── 01_PRD-{项目名}.md                   # 内容主文档(必需,从 01_ 起)
├── 02_业务流程与角色权限.md             # 三、业务流程 + 四、角色权限
├── 03_用户域-页面交互.md                # 五、页面交互(用户相关页面)
├── 04_订单域-页面交互.md                # 五、页面交互(订单相关页面)
├── 05_字段规格与数据来源.md             # 六、字段规格 + 六·2、数据来源
├── 06_字典枚举.md                       # 七、字典枚举(独立成文件)
│   字典枚举过多时可再拆分(简洁命名,不嵌套二级序号):
│   ├── 06_字典枚举索引.md              # 索引主文档(必需)
│   ├── 07_用户域字典枚举.md            # 占用序号 07
│   ├── 08_订单域字典枚举.md            # 占用序号 08
│   └── 09_全局通用字典枚举.md          # 占用序号 09
├── 10_权限矩阵与隐藏逻辑.md             # 七·2 + 七·3(序号接着上一文档自动累进)
├── 11_异常路径处理.md                   # 八、异常路径
├── 12_验收测试点.md                     # 九、验收测试点
└── 99_待澄清问题清单.md                 # 十、待澄清问题(若有,序号固定 99)
```

**注意**：字典枚举拆分时使用相邻的序号，不嵌入二级序号（如 `06_01_用户域字典枚举.md` 这种复杂命名）。后续文件序号接着上一个文档序号自动累进(不跳号,不嵌套二级序号)。

### 字典/枚举独立成文件的硬性规则

**只要 PRD 拆分为多文件,字典/枚举章节必须独立为单独文件**(不允许散落在各业务子文档中)。

字典/枚举文件必须满足:
- 集中收录所有字典和枚举值定义(状态/类型/分类/角色/...)
- 编码在所有字典/枚举间**全局唯一**,不允许跨域重复
- 若字典枚举条目超过 30 个或单文件 >800 行,再拆分为多个子文件,且必须有 `{NN}_字典枚举索引.md` 作为该组索引子文档(序号接着最大序号自动累进,不嵌套二级序号)

**其他子文档引用字典/枚举的标准格式**:

| 场景 | 引用格式 | 示例 |
|------|---------|------|
| 字段规格表中的枚举字段 | `枚举值参见 ./{NN}_字典枚举.md > {章节}` | `状态字段(枚举值参见 ./06_字典枚举.md > 订单状态)` |
| 页面交互中引用状态 | `参考 ./{NN}_字典枚举.md > {章节}` | `点击"上架"按钮,状态变更为 ON_SHELF(参考 ./06_字典枚举.md > 商品状态)` |
| 状态迁移图中的状态名 | 状态节点名必须与字典文件中的 label 一致 | — |
| 跨子文档引用枚举 | `参考 ../{NN}_字典枚举.md > {章节}` | `参考 ../06_字典枚举.md > 用户角色` |

严禁在多个子文档中**重复定义**同一字典/枚举;严禁字段说明中直接列出枚举值的全部含义(只列编码,完整含义引用字典文件)。

### 子文档头部规范

每个子文档必须有以下头部:

```markdown
# {NN} {模块/章节名称}

> **版本**: V{版本号}(与内容主文档一致)
> **隶属**: PRD V{版本号} > {模块名}
> **索引文档**: `00_索引.md`
> **内容主文档**: `01_PRD-{项目名}.md`
> **相关文档**:
> - 上游引用: `[依赖的子文档列表]`
> - 下游引用: `[被哪些子文档引用]`
> **原型来源**: [<ComponentName>](../prototype/{version}/code/xxx.jsx#锚点) > 对应页面
```

### 拆分一致性检查

| 检查项 | 要求 |
|-------|------|
| 文件名序号 | 所有文档以两位数字前缀命名(`00_` ~ `99_`),保证字典序与逻辑顺序一致 |
| 专职索引存在 | `00_索引.md` 必须存在,载全部 `01_`+ 内容文档清单 + 生成时间 + 类型(主/补充)+ 全局索引/术语表(历史 `00_*-总览.md`/裸 `00_<语义名>.md` grandfather 识别,不报错) |
| 字典枚举独立 | 多文件模式下字典枚举必须独立为 `{NN}_字典枚举.md`,不允许散落 |
| 编码全局唯一 | 字典/枚举编码跨文件唯一,不重复定义 |
| 引用可定位 | 子文档间引用使用相对路径,锚点存在,可点击跳转 |
| 版本号同步 | 所有子文档的版本号与主文档完全一致 |
| 子文档头部 | 每个子文档必须有标准头部,标注隶属、上下游引用、原型来源 |
| 避免碎片化 | 详见检查项 9 不通过标志中的具体阈值(无 <100 行**且** <4KB 的碎片子文档;两条件同时满足才判碎片,密集短文档 ≥4KB 按字节豁免) |
| 职责边界 | 全文无研发执行计划、Sprint 排期、研发周期、工时、里程碑、上线日期等研发管理内容 |

### 何时不拆分

- 页面数 ≤ 15、业务模块 ≤ 4、字典枚举 ≤ 25、单文件 < 800 行 → 保持单文件输出
- 用户明确要求"输出单文件" → 保持单文件输出
