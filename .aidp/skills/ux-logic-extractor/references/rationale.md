# ux-logic-extractor 设计来由(rationale)

> SKILL.md 正文只写**现行行为**;各条规则「为什么这样定」、曾经出过什么问题,集中记在这里。
> 本文件只解释来由,**不新增任何判据**——判据以 SKILL.md、各 `references/flow-*.md`、`quality-review-checklist.md` 与脚本为准。

## 1. `style-dna.md` 里保留了「已作废」条目

风格 DNA 是从多份 PRD 样本中归纳的。早期版本的职责边界允许 PRD 写「对外 API 设计」「数据需求 / ER 图」
「字段名 / 类型」,这些条目随样本一并被归纳进来;现行职责边界收紧为 PRD 零 API / 零 ER 图 / 零字段类型,
相关条目在原位标「已作废」保留,便于读者理解旧样本为何长那样,但严禁据此生成。

## 2. 样本原件不随 SKILL 分发

最初随 SKILL 附带的是若干份真实业务 PRD 原件(规格说明书、功能说明、研发补充需求)。它们含真实组织、
人名与内部系统信息,且包含大量本 SKILL 现行规则判为违规的技术内容,不适合随 SKILL 分发。
现以一份虚构的小样本 `sample-prd/示例PRD-会议室预约.md` 演示版式,风格规则归纳保留在 `style-dna.md`,
模式 A 的章节骨架并入 `style-dna.md` §19。

## 3. `check_prd_item_coverage.py --prd-source`

表 D 只校验「已登记条目是否都分类」时,产品原文里**根本没登记进表 D** 的条目对脚本完全不可见——
这正是「PRD 条目未转写进研发需求」最常见的形态。传 `--prd-source` 即以产品原文为基准反向比对;
为避免散文抽条目带来的满屏假红,脚本只抽按钮/操作名与字段/列类表格两类高精度条目,
其余仍须 QR Agent 逐条比对。不传时行为不变,以免让存量调用方的结论漂移。

S1 匹配刻意做成**单向**:早期实现「原文条目包含表 D 条目或反之」都算覆盖,表 D 里写一个泛词「订单」
就能吞掉原文的「导出订单」「订单编号」整类条目,是假绿。表格列取值也从「只取首列」放宽为「表头任一列命中
即取该列」——原文常把字段列放在「序号」之后;同时排除步骤/预期/序号/说明类列,避免把测试步骤或散文描述
当条目。抽到 0 条显式标 `zero_items`,因为「0 条未覆盖」与「0 条可比」在旧输出里长得一样。

## 4. QR 清单与派发流程为什么分两份、且不许互抄

`quality-review-checklist.md` 曾整段复制 `flow-qr-dispatch.md` 的 Agent 调用示例(约 50 行),两份副本随后
实质漂移:同一个维度在两处的判定口径不一样——维度 11 一处写「十、章节存在 + Q-NNN 双向追溯 + Agent 暂行
方案必填 + 不中断行为合规」、另一处只写「不中断原则的强制落地」;维度 12 一处带「空状态 UI 推断允许」豁免、
另一处没有。QR 子 Agent 先读到哪份就按哪份判,只读到清单那份时,合规 PRD 会因空状态 UI 推断被判维度 12
不通过(假红);台账行数也曾一处写 14、一处写 15。去重后清单只管「查什么」,派发只管「谁来查、怎么派」。

## 5. 需求编号为什么必须认带版本段的形态

`check_req_upstream.py` 早期只认 `REQ-\d+`,带版本段的段头(`REQ-V0.17.0-004`)一条都匹配不上,整份 PRD
被判「未发现功规点段」并 exit 0——维度 5 是 Critical、不可豁免,这是假绿而非假红。现行正则两种形态都认,
且两侧词边界不可省(否则 `REQ-3P-001` 会被前缀匹配成 `REQ-3`)。

## 6. SKILL.md 为什么分片

分片前 SKILL.md 约 2247 行 / 173 KiB,每次调用都要全量载入,是下游上下文压缩的主要触发源。分片按
「整节平移、内容一字未改」执行并做了行级零丢失回比(唯一差异是 `./references/x.md` 搬进 `references/`
后必须改写成 `./x.md` 的链接重定位)。分片只改加载时机,骨架里每条结论仍是硬要求。

## 7. 示例里的业务场景均为虚构

各分片中的语义变更样例(「工单统计口径由仅本部门扩为本部门+协办部门」)、外部接口样例(`EXT-001`
管理后台「订单总览」接口)等均为虚构的中性样例,只保留原始缺陷的**形态**——后端/接口/取数全改对,
但解释该数值的说明性文案有一处没跟着改、与展示值相反。不对应任何真实组织或系统。
