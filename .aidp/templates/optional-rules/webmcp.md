# WebMCP 能力详规（★ 按需安装的可选规则 · 安装后编辑前端代码时自动加载）

> # ⛔ 本文件默认【不在】`{{AIDP_HOME}}/rules/` 下 —— 这是刻意的
>
> `{{AIDP_HOME}}/rules/*.md` 的加载是**路径触发**的：只要编辑的文件命中 `paths:`，**整份文件就进上下文**。
> 若把本文件直接放在 `rules/` 下，**绝大多数根本不启用该能力的项目**每次编辑前端代码都要
> 白读这十几 KB —— 而它们读完的唯一结论是"本项目不适用"。这与本能力
> 「**未启用即零成本**」的总原则直接冲突。
>
> 故本文件**存放在模板位**（`{{AIDP_HOME}}/templates/optional-rules/webmcp.md`，**不被 rules 机制扫描**），
> **只有项目显式启用后才安装到 `{{AIDP_HOME}}/rules/webmcp.md`**：
>
> ```bash
> python3 {{AIDP_HOME}}/scripts/check_webmcp.py --install-rule     # 幂等；未启用时拒绝安装
> ```
>
> - **未启用的项目**：`rules/` 下没有本文件 → **一个字节都不加载**，零成本。
> - **已启用的项目**：安装一次即可，此后编辑前端代码**自动加载**，无需任何人记得去 Read。
> - **漏装会被硬拦**：`check_webmcp.py` 有一条守卫——已启用但 `rules/webmcp.md` 不存在 → **ERROR**，
>   并给出安装命令。所以不会出现"启用了却没规则可读"的静默失效。
> - **★ 本文件更新后，下游装的那份会随升级自动刷新**：
>   `scaffold.py::refresh_optional_rules` 专门补这条通道——**安装位不在 bundle 的下发面里**
>   （`assets/aidp/rules/` 下没有它），所以 `force_overwrite` 的目录镜像和 `skip_all` 的
>   create-if-missing **两条路径都碰不到它**，若不专门处理就会永久停在安装那天的版本、且无任何告警。
>   刷新**只针对已安装的项目**（未安装的一律不动，否则未启用项目会凭空背上常驻规则），
>   且**下游手改过安装副本时不覆盖、只告警**（宁可留着让人判，也不静默丢改动）。
>   兜底可见性：`check_webmcp.py` 另有 `rule-stale` **WARN**，万一自动刷新没跑到也看得见。
> - **升级不会删**：安装位不在契约真源里，运行包把它当用户文件原样带过去，装好的这份不会在下次 upgrade 被删掉。
> - **改动请改模板位**（本文件即权威源）；`rules/` 下那份是安装副本，改了无法回流、下次重装被覆盖。

> # ⛔ 适用前提
>
> **本文件描述的是一项【可选】前端能力，绝大多数项目不需要它。项目未【显式声明启用】时，本文件整份不适用**——
> 不产任何产物位、不生成任何检查项、不发任何告警、不在需求/设计/计划/自测中占据篇幅，
> 一切与 WebMCP 相关的判定一律为 **N/A**。
>
> **启用判定的唯一实现**（禁止各处各自 grep，那正是判据漂移的来源）：
>
> ```bash
> python3 {{AIDP_HOME}}/scripts/check_webmcp.py --detect --json
> # → {"enabled": true|false, "source": "...", "rule_installed": true|false}
> ```
>
> 声明位置（脚本按序读，命中即止）：① PRD 头部 `autopilot_decisions.webmcp.enabled: true`
> （**可选段，不计入必填 8 段；段不存在 = 未启用**）② `docs/architecture/架构约束.md` 显式声明。
>
> **⛔ 不得因为"这个项目是前端项目"、"这个能力看起来有用"就自行视为启用。** 启用是项目的显式决策。

WebMCP 让网页把自身能力以**带 JSON Schema 的函数**形式登记给浏览器，**能在该页面执行 JS 的 AI Agent**
（浏览器内置 AI / 外部 Agent 经 CDP / 浏览器扩展 / 页面自带助手）可直接调用业务函数，
而不必靠无障碍树快照去猜 DOM。

> ⚠️ **它不是网络协议、没有传输层**：消费方**必须先有办法进入该页面的 JS 上下文**。
> WebMCP 提升的是「**已能操作该页面的 Agent**」的调用效率与准确性，**不为远端 Agent 新增接入通道**。
>
> 这条决定了两件事：① 不要把它当成"给服务端/远端 AI 开的 API"来设计；
> ② 它的安全边界不能建立在"调用方是某个可信助手"上（见 §4.4）。

**与 chrome-devtools-mcp（CDP 外部控制）互补而非替代**：CDP 通用、任何页面可用、模拟真人操作、页面是黑盒；
WebMCP 需页面主动实现、直接调业务函数、页面自己声明能力边界。自动化测试中两者配合使用
（分工表见 `{{AIDP_HOME}}/flows/sprint-aiauto-test/phase-0-8.md`）。

## 一、运行前提：secure context 与放行手段

### 1.1 规范层面的约束 —— feature-detect 是唯一正确的探测方式

能力入口在 IDL 上标注 **`[SecureContext]`**：**不满足时该属性根本不会出现在宿主对象上**——是 `undefined`，
**不是抛异常、不是降级可用、不是返回空实现**。

因此探测必须**三段判定**：

```
宿主对象存在  &&  能力入口存在  &&  入口上的登记方法是 function
```

只判前两段，会在"对象在、但方法名随规范演进改了"时抛错。**整段包 try/catch，任何异常一律按不可用处理。**

### 1.2 什么算 secure context —— ⚠️ 不等于「只有 HTTPS」

按 W3C Secure Contexts 规范，"potentially trustworthy origin" 包含：

| 形态 | 是否 secure context |
| :- | :-: |
| `https://` / `wss://` | ✅ |
| `http://localhost`、`http://127.0.0.1`、`http://[::1]`（任意端口） | ✅ |
| `file://` | ✅ |
| **被浏览器策略显式列入白名单的 origin** | ✅ ← 本节重点 |
| `http://` + 内网 IP / 域名（如 `http://192.0.2.10:8080`） | ❌ |

> ⚠️ **两条最容易出事的推论**：
>
> 1. **`localhost` 算 secure context** —— 所以**本地开发一切正常，部署到 HTTP 测试环境才崩**。
>    这类能力的验收**必须在真实部署环境做**：静态检查、Node 直验、localhost 三处一概查不出来。
>    （下游真实踩过：同一根因导致 3 个 Critical 里的 2 个。）
> 2. **不要一看是 HTTP 就否掉该能力** —— 还有白名单这条路，且能力可以做成「开了才有、没开无感」。

### 1.3 三种放行手段（互相等价，按场景选）

| 手段 | 形态 | 适用场景 |
| :- | :- | :- |
| **启动参数** | `--unsafely-treat-insecure-origin-as-secure=<origin>`，**必须同时配** `--user-data-dir=<独立目录>` | 个人开发机、**自动化测试** |
| **企业策略** | `OverrideSecurityRestrictionsOnInsecureOrigin`（列表型策略） | 组织批量下发，无需改快捷方式或让每人手工配 |
| **图形界面** | `chrome://flags/#unsafely-treat-insecure-origin-as-secure` | 手工临时验证 |

**启动参数为何必须配独立 `--user-data-dir`**：该参数被浏览器视为破坏安全模型的调试开关，
不允许作用在使用者的日常 profile 上。顺带的好处是不污染日常浏览器。

#### 1.3.1 ★ 自动化测试链路：参数由命令端推导，不需要人预先登记

「内网 + 裸 HTTP 所以 WebMCP 用不了」是**误解**——白名单这条路对自动化测试完全成立，
而且 `chrome-devtools` CLI **原生支持透传**：

```bash
python3 {{AIDP_HOME}}/scripts/check_webmcp.py --launch-args --driver cli
# 不传 --origin 时自动读「测试环境与账号」的前端地址（约定 38 保证已归档）
# → chrome-devtools start --categoryExperimentalWebmcp true \
#     --chromeArg "--enable-features=WebMCP" \
#     --chromeArg "--unsafely-treat-insecure-origin-as-secure=http://192.0.2.10:8002"
```

| 参数 | 作用 | 缺了会怎样 |
| :- | :- | :- |
| `--categoryExperimentalWebmcp true` | 暴露 WebMCP 工具面（**要求 Chrome 150+**） | 工具面不出现 |
| `--chromeArg "--enable-features=WebMCP"` | 打开浏览器侧特性 | 同上，两者缺一即无 |
| `--chromeArg "--unsafely-treat-insecure-origin-as-secure=<origin>"` | 让 HTTP 内网站点成为 secure context | `isSecureContext` 恒 false，能力永不挂载 |

**两个"参数被静默丢弃"的坑**（丢弃时零报错，表现与"浏览器不支持"完全一样）：

- **CLI daemon 跨会话长驻**：直接跑工具命令时后台隐式启动的是**旧 daemon**，新参数不生效。
  启用 WebMCP 必须**显式** `chrome-devtools start <上面那串>` 重启一次。
- **手工起 chrome 必须换独立 `--user-data-dir`**：与既有实例共用目录时，Chrome 单例机制把 URL
  转交给先启动的实例、后启动的自己退出，新参数被吞。实测表现是同一页面两次探测**结论相反**。

> 📌 三个上游 SKILL 被明令「⛔ 不要自拟启动命令」——那是因为**它们不知道环境**。命令端知道
> （前端地址在手、浏览器也是它启的），所以走上面这条**确定性推导**，不算自拟。项目若已在
> `01_测试环境与账号.md` 登记了完整启动命令，**以登记的为准**，推导只作缺省兜底。
> 编排落点 = `/sprint-aiauto-test` Phase 0.1.3.5（**必须在浏览器启动之前**，启动后无法追加）。

### 1.4 origin 必须精确匹配 —— ★ 最常见的失败原因

`scheme + host + port` **三段全对**才生效：

| 写法 | 实际访问地址 | 结果 |
| :- | :- | :-: |
| `http://192.0.2.10` | `http://192.0.2.10:8002` | ❌ **端口漏了** |
| `https://192.0.2.10:8002` | `http://192.0.2.10:8002` | ❌ scheme 不符 |
| `http://app.example.com` | `http://192.0.2.10:8002` | ❌ 域名 vs IP |
| `http://192.0.2.10:8002` | `http://192.0.2.10:8002` | ✅ |

**自检方法**（须写进「测试环境与账号」文档，见 `/sprint-selftest` Step 3）——⛔ **别手写 `typeof <入口>` 逐个试**，用脚本产的探测片段（**白名单优先 + 全局扫描兜底**）：

```bash
python3 {{AIDP_HOME}}/scripts/check_webmcp.py --probe-snippet   # 输出一段 JS，注入页面 evaluate
```

它返回 `{isSecureContext, whitelist:{<各入口>: typeof}, suspects:[{where,name,type}]}`。

**★ 为什么必须有全局扫描兜底**：只查白名单 = 只做了阳性猜测，**没有"如果它改名了我能不能发现"的兜底**——而一次改名（哪怕只是大小写）就让整份白名单一起失效，且**失效表现与"能力真的不存在"完全一样、无法区分**。下游实测踩中过：Chrome 152 下白名单三个全 `undefined`，据判据表判"能力不可用"，整套 SUITE-MCP-ON（10 条用例）被记 block；实际能力就在 `window.ModelContext`（**大写 M**）。

**★ 三态判据表（第三态是实测补的，别再按两态排查）**：

| # | `isSecureContext` | 接口类（如 `window.ModelContext`）| 实例挂载点（`navigator.modelContext` 等）| 含义 | 处置方向 |
| :-: | :-: | :-: | :-: | :- | :- |
| 一 | `false` | — | — | 白名单没生效 | 查 origin 三段是否精确匹配（见上表）、`--user-data-dir` 是否独立、**参数是否真的生效**（见 1.4bis）|
| 二 | `true` | `undefined` | `undefined` | 缺实验特性开关，或该版本不支持 | 加 `--enable-experimental-web-platform-features`；仍无则换版本 |
| 三 | `true` | **`function`** | `undefined`（`new` 报 `Illegal constructor`）| **特性代码在，但实例未挂到 navigator/window 上** | 与前两态处置**不同**：多半还需额外 feature flag 或 origin trial token；⛔ 别按第二态去加实验开关（已经加了），也别据此判"能力不可用" |

⛔ **`suspects` 非空 = 有疑似入口，必须人工确认后更新 `entry_symbols`，不得静默判"不可用"**；确认后写进 PRD `autopilot_decisions.webmcp.entry_symbols`（声明后内置兜底清单不参与判定）。

### 1.4bis ⚠️ 同 `--user-data-dir` 起第二个实例 → 启动参数被静默丢弃

实测踩坑：先起了一个带参实例，随后用**同一个 `--user-data-dir`** 起第二个（只多加一个 feature flag）——Chrome 单例机制把 URL 转交给先启动的实例、后启动的自己退出，**第二次的启动参数被静默丢弃、没有任何报错**。表现：同一次排查里第一次测到 `isSecureContext=true` + `ModelContext=function`，第二次同样的页面变成 `false` + `undefined`，**结论完全相反**。

**硬纪律**：
1. 每次改启动参数**必须先 `pkill` 干净 + `rm -rf` 该 profile 目录**再起；
2. 起完**读回浏览器实际命令行核对参数是否真的生效**——`cat /proc/<pid>/cmdline | tr '\0' ' '`，或页面上开 `chrome://version` 看「命令行」一栏。

不做这一步，**"改了参数没生效"与"改了参数没用"无法区分**，排查会在两个相反结论之间反复横跳。

### 1.5 WebMCP 需要两个开关，作用域不同

| 开关 | 作用域 | 说明 |
| :- | :- | :- |
| **secure context 白名单** | 针对特定 origin | 只放行你指定的那个站点 |
| **实验特性开关** | **全局** | 会打开浏览器**全部**实验特性，且**无对应企业策略可精细控制** |

**缺一则能力入口不存在。** 第二个开关的粒度问题**直接决定了本能力的定位**：
**适合开发机 / 小范围试点，不适合要求全员开启。**
本条须写进设计文档的「待澄清 / 风险」段，避免把它当成可全员推广的特性。

> 📌 **另一条待验证路径**：Origin Trial（页面自带 token，使用者端零配置）。若 OT 能为 http origin 签发，
> 则可免去白名单这一步。**列为「值得验证的免配置方案」，在验证通过前不得写成推荐路径。**

### 1.6 为什么规范要求得这么严（决定了配置该怎么下发）

能力入口一旦存在，页面就能把自身操作面暴露给 AI 助手。若允许在裸 HTTP 下使用，中间人可以篡改页面、
**注入任意工具定义**，而使用者从助手侧完全看不出区别——助手只会看到"这个页面声称它能做这些事"。

对下节配置的直接启示：**开关配置本身也应经可信通道下发，且失败方向偏保守（fail-closed）。**

## 二、能力开关：三层 AND 模型

登记工具的前提是三层同时为真，**任一为否即不登记**：

| 层 | 判定 | 控制方 | 取不到时 |
| :- | :- | :- | :- |
| **L1 浏览器能力** | §1.1 的三段 feature-detect | 使用者的浏览器环境 | 视为否（**常态路径**） |
| **L2 服务端配置** | 后端下发的启用标志为真 | 部署方 / 组织策略 | 见 §2.2 fail-closed |
| **L3 页面总开关** | 使用者在界面上开启 | 使用者本人 | 沿用本地持久化值 |

### 2.1 时序铁律（实测教训，务必写死）

```
挂载
 └─ L1 同步探测 ──不可用──> 结束：不登记 / 不提示 / 不报错 / 无任何 DOM 元素
        │可用
        ├─ 取 L2 配置（异步）
        ├─ 读 L3 本地开关
        └─ 三者皆真 ──> 登记工具
```

**必须"等配置到位再登记"，严禁"先登记、配置回来再撤销"**：

实测 Chrome 152 的能力入口原型上**只有** `registerTool` / `getTools` / `executeTool` / `ontoolchange`，
**没有 `unregisterTool`**——撤销根本撤不掉，"先登记后撤销"走不通。
（下游曾按协议草案假设它存在、用可选链做防御，结果**撤销静默失效**、文档与实际不符。）

**L1 放最前面是刻意的**：它同步、零成本，绝大多数使用者在这里就结束，
不必为一个用不上的功能发出一次网络请求。

### 2.2 L2 服务端配置项落地要求

- **不新造接口**：挂到项目**已有的**前端配置下发 / bootstrap / 站点信息接口上，多加一个布尔字段即可。
  确实没有此类接口时才新增，且须走**约定 22** 级联。
- **必须运行时可变**（对齐**约定 26** 精神）：改配置后**无需重新构建前端**即生效；用配置中心的项目须支持
  **热刷新**（**约定 27**）。⛔ **禁止用构建期常量 / 环境守卫实现**——那会让"关不掉"或"要重新发版才能开"。
- **字段命名跟随项目既有配置命名习惯**，不强制统一名称。
- **fail-closed，但要有缓存**：配置取不到（超时 / 404 / 后端为旧版本无此字段）时——
  - 有上一次已知值 → **沿用**；
  - 无已知值 → **按关闭处理**。

  理由：该能力扩大攻击面（§1.6），默认关比默认开安全；加缓存是为避免"后端抖一下功能就没了"。

  > 若项目场景更看重可用性（纯内网、该能力被当成常规功能而非实验特性），**可反转为默认开**——
  > 但**必须在设计文档里显式记录这个决定及其理由，不得默默反转**。

- **★ 界面必须能区分三种「没有」**（混为一谈会让人完全无从排查）：

  | 情形 | 界面表现 |
  | :- | :- |
  | 浏览器不支持（L1） | **无任何元素**，与能力上线前逐像素一致 |
  | 被服务端策略关闭（L2） | 可提示"本环境未启用"，但**不给开启入口** |
  | 使用者自己关的（L3） | 显示已停用 + **可重新开启** |

## 三、能力入口的 API 表面（Chrome 152 实测事实，非据规范推测）

1. **挂载位置迁移过、且还在动。** 旧位置已废弃，探旧位置会得到"不存在"，**极易被误判成"这能力不可用"**。
   探测前先确认当前挂载位置，方法见 §1.4（`--probe-snippet`，白名单优先 + 全局扫描兜底）。
   **实测锚点（Chrome 152.0.7977.64）**：接口类 = `window.ModelContext`（**大写 M**），
   `Object.getOwnPropertyNames(window.ModelContext.prototype)` = `["ontoolchange","executeTool","getTools","registerTool","constructor"]`，
   与本节记录的 API 表面一致；`new window.ModelContext()` 报 `Illegal constructor`（属 §1.4 判据表第三态）。
   ⛔ 这只是**某一版的实测事实、不是规范承诺**——别把它硬编码进业务代码，入口解析归单一适配层。
   （这正是下方「单一适配层铁律」的由来：规范再变一次，改动面恒为一个文件。）
2. **`getTools()` 是异步的**，返回 `Promise<Array>`。不 `await` 只会拿到一个 Promise——
   下游曾据此误判"它返回的是对象不是数组"。且它返回**浏览器侧全量工具、不只本页登记的**，
   所以**已登记名单请自维护账本**，别依赖它。
3. **`executeTool(tool, argsJson)` 的两个参数形态都容易搞错**：
   - 第一参是**从 `getTools()` 取到的工具对象**，传名称字符串会报 `provided value is not of type 'RegisteredTool'`；
   - 第二参**必须是 JSON 字符串**，传对象会报 `Failed to parse input arguments`。
4. **没有 `unregisterTool`**（见 §2.1）。因此：
   - **停用的正确性必须由执行体的 fail-closed 判定保证**，而不是靠撤销；
   - **文档与代码不得声称"停用即从助手清单移除"**——实际它仍在清单里，只是调用被拒。
5. 工具对象上可见的字段：`name` / `description` / `inputSchema` / `origin` / `title` / `window`。
   `inputSchema` 就是登记时给的 JSON Schema，助手据此构造入参。

## 四、实现铁律（10 条，回检见文末）

### 4.1 单一适配层铁律

与浏览器能力入口的**全部接触面收敛到一个文件**；该文件之外**禁止出现能力入口标识符**。
回检 grep **命中文件数必须 == 1**。

> ⚠️ **注释里写了也算命中** —— 否则 grep 形同虚设（下游实际触发过这条）。

**Why**：§3.1 的挂载位置已经迁移过一次，规范仍在演进。收敛到一个文件后，规范再变，改动面恒为一处。

### 4.2 工具注册表与适配层解耦

工具定义为**纯数据 + 纯函数**，通过**依赖注入**拿运行所需能力；**不 import 适配层、不触碰宿主对象**。
这样工具逻辑可在无浏览器环境下直接测。

### 4.3 ★ 降级是常态路径不是异常分支

不可用时：**不登记 / 不提示 / 不报错 / 不上报 / 界面无任何相关 DOM 元素**。

> ⚠️ **这是本能力最容易做反的一点。** 绝大多数使用者的浏览器都不支持它——
> 「不支持」是**主流路径**，不是需要被告知的错误。任何"您的浏览器不支持 XX，请升级"式提示都是违规。

### 4.4 ★ 调用方不可信假设（下面三条安全铁律的前提）

能力入口是**页面 JS 上下文里的一个普通对象**，**任何能在本页执行 JS 的主体都可调用**——
含外部 Agent（经 CDP）、浏览器扩展、页面自带助手，**不限于浏览器内置助手**。

因此：⛔ **工具的安全边界不得建立在"调用方是可信助手"之上。**
下面的**确认门（§4.5）、值脱敏（§4.6）、不扩权（§4.7）** 三条是**对任意调用方生效的硬边界**，
**不是给某个特定助手的礼貌提示**——不能因为"反正只有我们自己的助手会调"就放宽任何一条。

> 本项目的自动化测试链路本身就是一个**非页内的外部消费方**（测试 Agent 经 CDP 进入页面 JS 上下文
> 再调 WebMCP 工具），它既是验证手段，也是这条假设的现成佐证。

### 4.5 写操作分级

| 类别 | 定义 | 处置 |
| :- | :- | :- |
| **只读** | 不产生任何变更 | 直接执行 |
| **本地写** | 仅改界面状态、无外部副作用、可撤销 | 直接执行 |
| **外发写** | 产生真实外部请求 / 数据变更 | **必须经使用者在页面上确认** |

外发写的确认门：**取消与超时一律按未同意**；**同一时刻仅允许一个待决确认**。
⛔ **「使用者同意」这一步必须留在真实 UI 上，不得由工具自行代劳**——这是整套设计的地基。

### 4.6 敏感数据边界

凭据 / 密钥 / 令牌类的值**一律不经工具通道返回，包括脱敏片段**；只返回**名称、位置、作用域**这类元信息。

### 4.7 不扩权

工具可见范围**严格等于当前身份的既有授权范围**，**权限过滤在数据源侧完成**。
**越权与"不存在"必须返回同一文案** —— 文案不同就等于给出了一条**探测资源是否存在的旁路**。

### 4.8 复用既有链路铁律

工具的写操作**必须复用业务既有的执行通道，绝不另写一条**（对齐**约定 20**「判据类逻辑禁止平行实现」）。

**Why**：另写一条会出现「**手工操作能通、让助手做就不通**」，且两条链路的日志形态、参数校验、
变量替换各不相同。若既有链路耦合在组件内部，**须先重构抽出再复用**，重构**只搬不改、行为逐字节不变**。

### 4.9 「什么算可调用对象」须用白名单

若业务对象有多种类型（如目录 / 文档 / 接口），工具暴露的集合必须**白名单列举可调用类型**，
⛔ **不得用"排除某类"的黑名单**——黑名单会随类型增加而失效，把不可调用的对象放进去，
助手拿它执行会产生**意外副作用**。

**列表、详情、执行三处共用同一判据，任一处放行即构成绕过。**

### 4.10 错误契约（对齐约定 23 姊妹条）

工具调用**无 HTTP 状态码可用**，失败必须以**结构化结果**表达（`{ok: false, reason}`）：
⛔ 禁止抛裸异常，⛔ 禁止用空数据冒充成功。

**文案的分合取决于是否泄露信息**：会泄露的**合并**（越权 / 不存在，见 §4.7），
不泄露的**分开**（"指名的取不到" ≠ "一个都没选"）。

> ⚠️ **新增一条错误文案时，须 grep 旧文案的全部使用点逐一判断该不该改** ——
> 只改"发现问题的那一处"会留下**姊妹路径**（下游真实踩过）。

## 六、边界：不要做什么

- ⛔ 不要把 WebMCP 做成**默认开启或强制约定**；
- ⛔ 不要新增一条独立的 `sprint-*` 命令——它是前端能力的一个**可选维度**，应融进既有的需求 / 设计 / 开发 / 测试链路；
- ⛔ 不要为它**新造后端接口**（挂既有配置接口）、**新增表**、**新增错误码**；
- ⛔ 不要因为"AI 能调用"就把**确认门**省掉（§4.5）；
- ⛔ 不要把"两个浏览器开关"写成**可全员推广**——实验特性开关是全局的（§1.5）。
