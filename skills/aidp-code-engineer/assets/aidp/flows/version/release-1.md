### tag 风格识别约定

> 本节定义"前一已发布版本"的识别规则，供**发布期** Step 3.3.5 / Step 3.4.2 统一引用。下游各处按本约定取最新，不再各自复述。
>
> ⛔ **不适用于规划期**：Step 2.4.7 的 `prev_version` **不走本节**——规划期要的是「上一**迭代**版本」（含未发布的中间过渡版本），按产物目录 SemVer 扫描取值，单一信源在 `planning-7.md`「prev_version 取值口径」。两套口径刻意不同：过渡版本从未对外发布，发布期更新日志要跨过它把其变更并入本次条目，规划期增量基线却必须落在它上面。

本仓库存在**三种 tag 命名风格**，识别"前一已发布版本"时必须三种全覆盖、按时间排序取最新：

| 风格 | 示例 | 出现时期 |
|------|------|---------|
| `V*` | `V0.0.1` | 早期直接大写 |
| `release-V*` | `release-V0.1.0` | 中段短暂启用 |
| `v*` | `v0.1.0` | 当前标准 |

统一识别命令：

```bash
# 取最新一个已发布 tag（三种风格全覆盖，按 version:refname 倒序）
PREV=$(git tag --sort=-version:refname | grep -iE '^(release-)?[Vv][0-9]+\.[0-9]+\.[0-9]+' | head -1)
```

如需归一为 `V{major}.{minor}.{patch}` 形式（如日志展示）：`echo "$PREV" | sed -E 's/^release-//; s/^v/V/'`。首次发布（无任何 tag）时 `PREV` 为空，记为 `（首版）`。

### Step 3.1：前置条件检查（未关闭 Sprint 自动关闭）

> **★ 铁律：交互式 `/version` 发布 = 全量正式发布，一律自动关闭所有 Sprint 后打 tag + 建分支，绝不弹「轻量还是全量 / 打不打 tag」选择。** 未关闭 Sprint 由下方流程**静默自动 `/sprint-close`**（不询问、不因"有未关闭 Sprint"就退化成不打 tag 的轻量模式）。**`--no-tag` 准发布（不打 tag/不建分支）仅供 `/sprint-autopilot` 无人值守调用，绝不作为交互式发布的选项呈现给用户**——用户手动跑 `/version {version}` 永远走全量正式发布。

> **★ 本步唯一允许的交互 = 第 4 点 P0 强制发布确认（且须先过「P0 闭环自动判定」，命中数为 0 则不询问）。** 除此之外本步任何形式的「是否继续 / 是否发布 / 要不要先验证」问询**均属违规**（决策纪律铁律，见本节开头）。

**★ 前置自愈（memory 状态文件 / Sprint 归档缺失 → 按模板补建，不询问、不中断）**：本版本可能走的是「直接 `/sprint-dev` 累进 + bugfix 驱动」路径，从未跑过 `/version` 规划期的 Step 2.5/2.6，故 memory 状态文件与部分 Sprint 归档可能整体缺失。发布流程**原生兼容**、不把补齐留给临场发挥：
- `memory/{version}/{user}/progress.md` / `activeContext.md` **缺失** → 按 Step 2.5/2.6 模板**自动补建**（版本历史行/状态按当前实际交付事实填），**不询问、不中断**。
- 研发执行计划列出、但 `memory/{version}/{user}/sprints/` 下**无归档文件**的 Sprint → **自动补建归档记录**（状态按代码交付事实判定），而非跳过或报错。

**⚠️ memory 是本地快照、不是实时权威**：涉及**外部系统状态**（GitHub Issues、对端部署、他人负责项）时**必须以实时查询结果为准**，memory 记录仅作线索——多人协作项目尤甚，他人的操作不会反映到你的 memory 文件里（如 `progress.md` 写「任务均未开始」，实际可能已被另一成员完成）。**如项目使用 GitHub Issues 跟踪缺陷，其现状一律先 `gh issue list` 实时拉取再决策（未装 gh 即跳过），绝不按 memory 旧值重复处理他人已关闭的问题。**

逐项检查：
- ✅ 该版本包含的所有 Sprint 已关闭（`memory/{version}/{user}/sprints/` 下有对应文件，`progress.md` 中所有 Sprint 状态为 ✅ 完成）
- ✅ 所有 P0 功能已验收通过（验收结论见各 Sprint 的 AI执行报告「需求功能」段 + `memory/{version}/{user}/progress.md`）
- ✅ 无阻塞性 Bug（查看 `docs/bugfix/{version}/` 下未修复的 P0 问题）

**★ 未关闭 Sprint 自动关闭流程**：

1. **扫描未关闭 Sprint**：遍历 `memory/{version}/*/progress.md`（多用户场景全量扫描），收集所有"状态 ≠ ✅ 完成"的 Sprint（含状态为「进行中」/「已开发待测试」/「测试中」/「待验收」等）。输出清单：
   ```
   🔍 检测到 {N} 个未关闭 Sprint：
     - {user}/sprint-001（状态：进行中）
     - {user}/sprint-003（状态：测试中）
   ```
2. **逐一自动关闭**：对每个未关闭 Sprint，**调用 `/sprint-close {NNN} [--unattended]` 命令**（带该 flag 时必透传）（按用户上下文切换 `{user}`），命令端等待每次 close 完成后再处理下一个。每次关闭会自动跑 `sprint-close.md` Step 1~Step 8（记录验收结论 / Reviewer 走查 / 归档 activeContext / 更新 progress.md / systemPatterns / databaseBaseline / 重置 activeContext / 更新 AGENTS.md / 输出关闭报告）。
3. **关闭过程中若验收存在阻塞**（如 Reviewer 走查发现 Critical 问题）：
   - **交互式** → 中断自动流程并提示用户手动处理；处理完毕后用户重新执行 `/version {version}`。
   - **★ 无人值守（`--unattended` / `--no-tag` / `LOOP_UNATTENDED`）→ 绝不中断等人**：记 `docs/audit/{version}/发布欠账.md`（阻塞项 + 所属 Sprint + 时间）+ 置 baseline `versions.{V}.needs_human=true` + `aiauto_frozen_at=@now` + `freeze_reason=release-blocked`（交接类，仅人工解冻；`needs_human_reason=发布期验收阻塞`）后退出本 tick，留待人工，绝不停等（对齐 autopilot 熔断精神）。
4. **关闭后重新检查 P0 / 阻塞 Bug（★ 先自证据机械判定，问用户之前必做）**：

   **P0 闭环自动判定（客观判据，替代"仍有 P0 未通过"的模糊裁量）**：
   ```bash
   # 取 严重度=P0 且 状态列不含闭环关键字 的缺陷条目数（客观判据、非自然语言裁量）
   # 闭环关键字：已修复 / 已验证 / 已关闭 / 已根治 / 已解决 / Closed / Fixed
   OPEN_P0=$(grep -rhE 'P0|严重|阻塞' docs/bugfix/{version}/*.md 2>/dev/null \
     | grep -viE '已修复|已验证|已关闭|已根治|已解决|closed|fixed' | wc -l)
   ```
   1. 上式 `OPEN_P0=0` → **不询问、不留暂停理由**，直接进入 Step 3.2。
   2. 对**责任方 = 运维 / 外部团队**的 P0（如"线上待运维清理"）**额外核验闭环证据**（只读）：部署产物回写 / 跨系统通信记录 / 对端仓库 commit——有证据即视为已闭环、剔出未闭环集。
   3. **状态列滞后但正文根因已澄清为「非本系统缺陷」** → 不作阻塞项，记 Step 3.6「待验证」段，不弹窗。
   4. 仍无法机械判定的残留项 → **归入 Step 3.1「一次性收齐清单」**，与其它待裁决项**合并问一次**；**严禁逐个 P0 单独弹窗**。

   经上述判定后**仍有真实未闭环 P0 / 阻塞 Bug** →
   - **交互式** → 输出警告并询问 `是否强制发布？（y/N）`（**本步唯一合规问询**）：`y` → 进入 Step 3.2；`N` → 终止流程，提示用户先解决阻塞项。
     ```
     ⚠️ 全部 Sprint 已自动关闭，但仍有发布阻塞项（已过 P0 闭环自动判定，确属未闭环）：
       - {具体问题 1}
     是否强制发布？（y/N）
     ```
   - **★ 无人值守（`--unattended` / `--no-tag` / `LOOP_UNATTENDED`）→ 绝不弹 y/N**：`--no-tag` 准发布下 → WARN + 在发布报告「发布欠账」段留痕（列残留阻塞项）+ 继续 Step 3.2（准发布不打 tag、风险可控，正式 tag 留运维 review 时把关）；要打 tag 的正式发布 → 置 baseline `needs_human=true` + `aiauto_frozen_at=@now` + `freeze_reason=release-blocked`（`needs_human_reason=残留 P0/阻塞未清`）+ 退出本 tick，不强制发布。
