### 约定 2 — **新增功能/修复大 bug 走自动累进（★ 限定前提：当前版本【未发布】）**
- **★ 版本落点决策门（当前版本【已发布】时累进前置，先于任何持久副作用）**：若「当前版本」**已发布**（有 release tag / progress.md·版本更新日志标「✅ 已发布」）且未开始新版本规划，**累进前必须让用户三选一、执行体绝不自行裁量版本号、绝不决策前建目录**——**① 落回已发布版本 re-release**（⚠️ 强制移动已推送 tag，若被他人/CI/制品库消费有实际风险）**② 新开 patch `{x.y.z+1}`（推荐默认、不动 tag、风险最低）③ 新开 minor `{x.y+1.0}`**；**patch/minor 版本号语义由用户定**（对外 SemVer 兼容性承诺，命令只给推荐+理由，不由技术判据自裁）。交互式 `AskUserQuestion` 三选一；`--unattended` 罕见命中→**保守默认新开 patch**（不动 tag）+ `decidable_skips` 留痕。**绝不静默往已发布版本累进 / 绝不自动 re-release 动 tag**（与「报告不可变」同理）。单一信源见 `/sprint-dev` Phase 0B.0「版本落点决策门」（`/sprint-bugfix` Phase 0C.0 同口径引用）；本门属「⛔ 统一决策纪律」正向判据（持久目录/对外 tag 承诺/高回退成本）下的**合规结构化门**，不因"不许自发问"跳过。
- **★ 中间过渡版本（当前版本【未发布】时直接开下一版规划 = 合法操作，不是流程缺陷）**：当前版本尚未发布（无 tag、状态非「✅ 已发布」）时，用户**直接跑 `/version {下一版本号}` 开始下一版规划**——这本身即用户的显式声明「当前版本属中间过渡版本、不需要正式发布」。执行体**照常规划下一版**：不弹「要不要先发布当前版本」、不阻塞、不报异常、不自行补发布、不把它记成欠账。过渡版本的产物照常沉淀并被下一版继承（目录/设计/SQL/memory 均保留），只是**不打 tag、不进对外发布节奏**。**Why**：版本号承载的是产品与发布节奏（对外 SemVer 承诺），是否把某一版对外发是用户决策；内部连续迭代中「攒几个小版本一起对外发一次」是常态。与上一条互为**对称两半**——已发布版本上累进要拦（tag 已是对外承诺），未发布版本被跨过不拦（尚无任何对外承诺）。
- **★ 由此派生的「上一版本」取值口径二分（易错点，两者刻意不同、不可混用）**：① **规划期** = **上一迭代版本**——按**产物目录 SemVer 扫描**取小于本版的最近一版，**含未发布的中间过渡版本**（单一信源见 `/version` Step 2.4.7 `planning-7.md`「prev_version 取值口径」）；② **发布期面向使用者的对比基准**（`版本更新日志.md` 条目区间、tag/版本分支识别）= **上一已发布版本**——按 tag 取（单一信源见 `release-1.md`「tag 风格识别约定」）。**规划期误用 ② 会跳过过渡版本、令增量基线错位**：增量一致性审计把过渡版本已交付的内容重判为"新增"、跨版本作废清算（约定 34）读不到过渡版本的历史需求而漏检结论反转。反之发布期用 ① 会把过渡版本的变更从更新日志区间里漏掉（它从未对外发过，其内容应并入本次发布条目）。

### 约定 6 — **数据库基线必读 + ★ SQL 开发期自动应用（幂等）**
- **★ 开发期 SQL 自动应用（检测驱动，不依赖研发执行计划是否显式列 SQL 任务）**：`docs/deployment/{version}/sql/增量/` 下存在 `01_*.sql`~`98_*.sql`（跳过 `99_回滚脚本.sql`）时（**兼容 legacy `code/sql/{version}/`**——存量项目 grandfather 识别），`/sprint-dev` 后端开发阶段（Phase 1.2 Step 1）**自动把它们按两位序号顺序应用到开发库**——DB 连接取后端 `application.yml`（生效 profile 的 `application-{profile}.yml`）的 datasource（url→host/port/库名 + 账号密码，其它技术栈取等价 datasource），本地/可直连场景由命令端用对应 DB 客户端直接执行。
- **幂等**：只应用**本版本尚未应用过**的 SQL——已应用清单记 `memory/{version}/{user}/.applied-sql.json`（文件名 + 应用时间 + SQL 内容 sha256），已在清单且 sha 未变的跳过、SQL 内容变更则重跑该文件；配合设计期 `CREATE TABLE IF NOT EXISTS` / `INSERT ... ON DUPLICATE KEY UPDATE`（见约定 23 / dev-logic-architect）双重防重复。应用成功后同步回写 `databaseBaseline.md`。
- **不静默跳过**：DB 不可达 / datasource 解析不到 / 无 DB 客户端 → **WARN + 标为「部署阻断风险：SQL 未应用、部署后表将缺失」**（无人值守记 baseline + #4 提示），绝不"当作已执行"继续，避免复现「部署后报错」。**★ 修复下游反馈：研发执行计划未提 SQL 也照常自动应用**（检测驱动、与计划是否列 SQL 任务无关）。单一信源见 `/sprint-dev` Phase 1.2 Step 1。

### 约定 9 — **关闭前归档**
- **★ 发布后冻结（版本级对称约定）**：一个版本**已发布**（已打 tag / 已归档）后，**不得在该版本上直接累进新 Sprint** —— 除非用户在「版本落点决策门」（约定 2 / `/sprint-dev` Phase 0B.0）**显式选择 re-release**（落回该版本重新发布，接受 tag 移动风险）。已发布版本是已交付/已归档产物，与 Sprint 关闭后不可再动、AI 报告 finalize 后冻结同理：默认新需求/bug 走新版本，落回旧版本须用户显式决策。

### 约定 11 — **目录隔离**
- **★ 版本落位一致性（补充/增量模式必守）**：本次迭代新增/变更的 SQL（最终落 `docs/deployment/{version}/sql/增量/`）与其它 `docs/deployment/{version}/` 部署产物**一律落"当前迭代版本"目录**，绝不写进 `{prev-version}` 目录（防补充模式下 SKILL 扫既有目录推断路径而复用上一版本目录）；**文件头版本注释 == 所在目录版本 == 本次迭代版本**三者一致；目标版本目录不存在则先建（不惰性）。**SQL 两阶段落位**：上游 `dev-logic-architect` SKILL 原生暂存到 **`code/sql/v{version}/`**（★ 带 `v` 前缀，SKILL「SQL 版本严格隔离铁律」硬约定，如 `code/sql/v0.2.0/`；占位符 `{SQL脚本目录}=code/sql/`）——**写 glob 时务必带 `v`**，漏了会匹配不到 SKILL 的真实产物、SQL 静默不归位（存量无 `v` 形态需双模式扫描），命令端 `/sprint-design` Step 3.2 钉死版本 + 返回后校验纠正 + **`git mv` 搬迁到最终位置 `docs/deployment/{version}/sql/增量/`**；`verify.py::check_sql_version_dir_consistency` 巡检兜底。单一信源见 `06_版本与用户目录约定.md` §2.5.4

### 约定 13 — **提交信息规范**
- **格式**：遵循 Conventional Commits——`<type>(<scope>): <subject>`，`type` ∈ `feat` / `fix` / `docs` / `refactor` / `test` / `chore`（按需可用 `perf` / `build` / `ci` / `style`）；`scope` 可选，取模块或子项目名；`subject` 一句话说清「做了什么」，中文为主（约定 14）
- **一次提交只做一件事**：功能、重构、格式化、文档级联分开提交（约定 20「抽取与重构分两次提交」、约定 35「格式化不卷入既有文件」同口径）；⛔ 不把无关改动夹带进同一笔
- **正文（可选）**：写「为什么」与已知取舍，不复述 diff；破坏性变更在正文加 `BREAKING CHANGE:` 段
- **Why**：提交历史是可追溯性的底座——约定 9 归档「不记 git log 查得到的」、约定 41 链外任务的可追溯性都依赖提交信息本身可读、可按类型检索

### 约定 21 — **★ 命令调用 SKILL 的内容职责分层**
- **禁止**：复述 SKILL 内部检查项（如把 N 维度清单列进命令或注入 prompt）；改 SKILL 判定逻辑（如把"3 轮 QR"改"5 轮"）；绕过 SKILL 内置检查；重复实现 SKILL 已覆盖功能（除非明确标注"兜底"）
- **允许**：传路径/参数/版本上下文；SKILL 之外的项目级回检（如回写 `databaseBaseline.md`）；跨 SKILL 编排 + 副作用回滚；失败兜底；调 SKILL 前后用 `AskUserQuestion` 对齐；笼统引用 SKILL 含哪类检查（不复述具体维度）
- **判定边界**：SKILL 已写过的规则命令端只能引用；SKILL 没覆盖的项目特有规则命令端可定义；同一规则两处都出现 → 只在 SKILL 保留、命令端删
- **Why**：避免命令与 SKILL "知识双写"——SKILL 升级命令不同步会误导按旧规则跑，两处分歧时权威靠猜
