### 约定 31 — **★ CICD 与协作平台集成（多提供方，默认 GitHub Actions）**
- **31.3 开发/缺陷读取（`/sprint-dev`·`/sprint-bugfix`，可选）**：用户**主动提及 GitHub Issue**（编号或链接）时，用 `gh issue view <num>` / `gh issue list` 读取 → **先预读、确认缺陷存在/可复现再修**（人工填写的标题不可盲信）；未提及不强制拉取；未安装或未登录 `gh` 即跳过、不阻塞。
- **31.5 CICD 编排 —— 推送分类与监听（★ 作用域 = **代码推送这一事实**、与命令入口无关：**裸对话路径**〔用户口述 → 执行体改码 → 直接 `commit`+`push`、全程没走 `/sprint-*`〕**同样适用**，与约定 22 / 24 / 36 同口径；不限 `/sprint-autopilot`）**：CICD 平台 = `memory/aidp-config.yaml` 的 **`cicd.provider`**：`github-actions`（默认，经 `gh` CLI）/ `gitlab-ci`（REST API，`cicd.gitlab-ci`）/ `jenkins`（REST API，`cicd.jenkins`）/ `command`（任意平台自定义命令模板，如 Gitee、Gitea、自建平台，`cicd.command`）/ `none`；部署环境 → 流水线标识映射在 `cicd.pipelines`（如 `{dev: deploy-dev.yml, test: deploy-test.yml}`，含义随 provider：workflow 文件名 / 分支名 / Job 路径 / 命令模板的 `{pipeline}`）；⛔ 令牌只经 `*_env` 指向的环境变量引用。`provider=none` 或未配置有效流水线 → 明确结束 CI 观察，不构造提供方、不循环探测、不借历史 baseline 补配置，也不记部署成功。提供方 CLI/凭据不可用时，普通推送只汇报环境不可用；autopilot 自有推送按既有环境故障分支处理。若用户另已授权项目现有部署入口，消费其真实执行回执；CI 降级不取消该请求。已接入时，**先过推送分类门再决定要不要监听**：
    **⓪ 先读 `python3 {{AIDP_HOME}}/scripts/aidp_config.py cicd-enabled`**（退出 0=已启用）：**未启用 → 推送只有 `git push`**，不跑脚本、不写文件、不监听。**已启用才分类**：`python3 {{AIDP_HOME}}/scripts/classify_push.py --root . [--base-ref R --head H]`（纯只读、不落盘；子模块指针/嵌套子仓/源码根配置类变更及 `docs/deployment` 内实际 SQL、配置资产保守视为正式代码，说明文档继续按非正式变更判定）；监听所需 commit 现场 `git rev-parse HEAD`、`git ls-remote` 取得，不依赖任何落盘记录。
    **无正式代码变更且分类无错误** → 仍校验 push 成功，**不触发/不监听远端 CICD、不等待部署、不跑就绪探针**，本条后续六步整段跳过。
    **有正式代码变更、分类结果缺失或分类出错** → 只读 detect/watch/poll，锚定本次 commit 的真实运行；分类失败不授予部署权限。
  - **普通推送（含裸对话及独立 light/formal 命令）**：只用现场 Git commit 与平台记录观察；不要求 version / execution-context，不为交付新建 context/grant/回执文件，不读写 autopilot tick/baseline/pending/retry 状态。已启用 CICD 且分类需监听时执行 `python3 {{AIDP_HOME}}/scripts/cicd_watch.py --root . --mode watch --commit <本次推送SHA> --env <已配置环境>`；不传 `--execution-context` / `--version` / `--baseline`，不要调用 `consume`。`readonly=true` 时用 `observed_verdict`（缺省取 `verdict`）报告真实成功、失败、运行中或不可用；`NOT_REQUESTED` 仅表示后续部署写动作未请求，不能抹掉失败。运行中需继续观察时只按同一 commit/run_id 续 `--mode poll --run-id <id>`；当前调用到时仍运行就如实汇报，不装调度、不造 tick。禁止据返回值主动 trigger/retry、跑就绪探针或记录部署成功；用户另已授权项目现有部署脚本则独立执行该脚本。
  - **autopilot 自有推送的写动作授权**：动作模型、来源及预算见 `{{AIDP_HOME}}/flows/sprint-dev/light-context.md`；仅该编排调用传 `--execution-context`，push grant只支持只读监听，trigger/retry需deploy。主动 trigger/retry、就绪探针及结果记账由 `phase-3-6.md` / `phase-3-6b.md` 定义。`auto_trigger` 是执行偏好，旧模板true不是用户grant。NOT_REQUESTED不冻结、不记部署欠账、不伪造部署成功，也不逐项询问未要求动作。
  - **★ 环境事实取本次部署入口的真实记录，⛔ 不得引用只在特定链路才被写入的本地状态字段**：判断「代码部署了没 / 当前环境跑的是哪个提交」时，**CICD 部署以平台运行记录里的 commit 为权威；项目现有独立部署入口以其真实回执为权威**；本地 baseline 的 `last_deployed_at` / `last_autopilot_head` 这类字段**只有走完特定链路才会被写**（推送自动触发的部署就不写它），当环境事实用必然误判。**判定口径**：任何状态字段被用作判据前，先回答「**这个字段是谁写的？当前路径下它会被写吗？**」——答不上来就不能拿它下结论（写入方声明义务见 `flows/sprint-autopilot/invariants.md` IRON-9）。
  - **⛔⛔ `cicd_watch.py` 调不通时【不得自行实现轮询】**：自写轮询能「看状态」，却丢掉了本脚本**唯一重要的产出**——`next_action`（该不该重试、第几次）、`retry_run_id`/`retry_commit`、`retry_count`/`max_retries`、`trigger_cmd`/`retry_cmd`。执行体失去权威指令就会「自己判断」，而「构建失败」天然诱导人回头查业务代码。正确做法：保留 TOOL_ERROR 和具体最小修复/成本建议；同根因同输入不重试，不自写轮询/controller。没有 deployment-tool-development grant 不实现部署工具。
  - **★ 脚本可用性要有主动信号**：`python3 {{AIDP_HOME}}/scripts/cicd_watch.py --selftest`（离线自测，用假平台输出覆盖各提供方，不访问网络），已挂进 `verify.py`。**Why**：脚本坏掉时调用方会回落到自写轮询把故障吸收掉，主路径死了却零信号。
  - **两个场景按授权分开**：普通 push 自动触发时只读监听本 commit；普通部署请求只运行项目现有部署入口。autopilot 编排才在明确 deploy grant 与共享 retry 预算内主动 trigger/retry。真实故障与未请求动作分别返回，不用“未部署”倒逼普通开发加全套测试。
  - **★ autopilot 编排分工（读写分离、全部经同一脚本；普通推送只用上述只读分支）**：①③ 由确定性脚本 `python3 {{AIDP_HOME}}/scripts/cicd_watch.py --mode watch|detect|poll --commit <sha> (--env <env> | --pipeline <标识>) [--run-id <id>] [--version <v>] [--max-retries N]` 承担（平台差异收在 `cicd_providers.py`；输出 `provider` / `pipeline` / `pipeline_source` / `verdict` + `next_action`：`trigger`/`retry`/`probe`/`poll`/`abort`，需写动作时附 `trigger_cmd` / `retry_cmd`）；② 与重试由命令端显式调 `--mode trigger [--ref <branch>]` / `--mode retry --run-id <id>`（受理后 `next_action=poll` 已拿到 run id，`=detect` 需按 commit 再探测）。**退出码** 0=运行成功 / 已命中 / 写动作已受理 · 1=需调用方做写动作（触发/重试）· 2=需人工（含 `trigger-failed` / `retry-failed`）· 3=未接入或环境不满足（`disabled` / `not-configured` / `cli-missing` / `unauthenticated` / `provider-unavailable` / `bad-args`）。④⑤⑥ 就绪探针走 `python3 {{AIDP_HOME}}/scripts/autopilot-deploy-watch.py`。
  - **★ 穷尽判定，不留悬空态**：运行**失败** → 仅deploy获授权、输入/根因已改变且预算允许才重试；**CICD 平台不可达 / 提供方凭据中途失效** → ≠ 失败态，**不消耗重试配额、不空触发新运行**，告警后下次再查；**锚定运行消失/被顶替** → 判异常交人工，⛔ 绝不静默滑到"最近一条"顶替；**结论无法归类**（如 `cancelled`/`action_required`）→ 不给绿灯、交人工。
  - **★ autopilot 单次调用有上限、跨 tick 续跑**：`cicd_watch.py` poll / watch 到 `--timeout`（默认 480s）仍在运行 → `verdict=running`、`next_action=poll`、退出码 0，下个 tick 按同一 run id 续 poll（不交人工、不耗重试配额）；就绪探针 `--max-seconds`（默认 480）到时未就绪 → 退出码 4（pending），下个 tick 带同一 `--since` 续探。
  - **★ 终态由现场获知，不落盘**：监听结束的真实终态在回复/autopilot 自有状态里体现，⛔ 不经任何脚本写入 baseline 的推送记录。`provider=none` / CLI 不可用 → 只 push、不监听。`commit_gate.py::pending_cicd` 仅 CICD 已启用时输出现场 commit 的提示行（advisory，不计债、不影响退出码，约定 24）。
  - autopilot 自有推送的编排细节单一信源 = `/sprint-autopilot` Phase 3.2.1（`{{AIDP_HOME}}/flows/sprint-autopilot/phase-3-6.md` Step A0–C + `phase-3-7.md` Step D）+ 「推送分类与监听不变式」（`invariants.md`）。其他入口只在继承 autopilot 任务时引用该编排；独立推送引用本节「普通推送」，不进入 tick/baseline 路径（约定 21）。
- **Why**：推送后不监听，部署在远端红了也无人知，依赖它的测试链路对着旧版本空转；就绪探针兜住"部署完成≠可测"。

### 约定 32 — **★ 里程碑通知渠道装配**
- **发送入口**：`python3 {{AIDP_HOME}}/scripts/notify.py`，字段式参数 `--title --header-color --section --section-file --link-text --link-url --footer --node --version --build --gate --project-name --check-name`，`--print-only` 仅渲染不发送、`--json` 输出结构化结果。
- **渠道选择**：`--auto` 按 `memory/aidp-config.yaml` 的 `notify.channels` 顺序依次尝试，成功即停（`notify.fallback=false` 时只试第一个）；`--sender '<命令>'` 指定自定义发送命令（从 stdin 读消息 JSON）。支持渠道：`feishu`（飞书自定义机器人 webhook）/ `lark-cli`（飞书 CLI）/ `dingtalk`（钉钉机器人 webhook）/ `wecom`（企业微信机器人 webhook）/ `command`（自定义命令读 stdin JSON）。自定义命令（含 `--sender`）退出码：0 = 成功、3 = 渠道不可用（按未配置渠道合规降级）、其它非零 = 发送失败。
- **配置示例**：
  ```yaml
  notify:
    enabled: true
    fallback: true
    channels:
      - {type: feishu, webhook_env: AIDP_FEISHU_WEBHOOK, secret_env: AIDP_FEISHU_SECRET}
      - {type: wecom, webhook_env: AIDP_WECOM_WEBHOOK}
  ```
- **⛔ 密钥不入库**：webhook 地址与签名密钥**只经环境变量引用**（`webhook_env` / `secret_env`），⛔ 不把明文写进 `aidp-config.yaml` 或任何入库文件。
- **退出码**：0 成功 / 1 全部渠道失败 / 2 参数错误 / 3 未配置任何渠道或 `notify.enabled=false`——**3 = 合规降级：静默跳过本播报节点，⛔ 不弹窗问人**；1 仅告警、不阻塞主流程。
- **Why**：7×24 无人值守下，里程碑通知是人感知进度与冻结的唯一主动信号；渠道配置化让不同团队各用各的 IM，密钥走环境变量避免泄露。

### 约定 33 — **★ 规划期基线类文档 → 测试期消费入口对账铁律**

消费者仅在对应test/review/full-cvl/live-tests动作获授权时启用；未启用NOT_REQUESTED不成流程欠账。完整显式测试职责仍按公开组合执行，缓存使用真实inputs hash。
- **基线 → 测试期消费者映射**（消费机制以各 SKILL 为单一信源，此处只定"必须被消费"契约）：**原型内容基线**（约定 4）→ `dev-manual-testcase` 逐元素/交互态/操作流断言用例 + `auto-test-runner` 执行（含"标裁剪/延期的元素仍存在"**反向断言**判失败）+ `code-verification-loop` 逐页核对；**设计令牌**（约定 4 B/C）→ `code-verification-loop` 维度 4 L1 强校验；**PRD 原子条目原文**（`docs/requirements/{version}/产品提供/*.md`）→ `dev-manual-testcase`「PRD 原子条目存在性用例族」（**引 PRD 行号、绕过研发需求层**，唯一捕获"设计本身漏项"）+ `auto-test-runner` 该族失败判 **Critical** 不降级 + `code-verification-loop`「PRD↔实现」直接比对维度；**统计/计数/金额字段** → **双源对账用例**（页面取值 vs 含软删除/状态过滤的等价 SQL、断言相等）+ `auto-test-runner` **DB 断言驱动**；**字段处置对照表/PRD 待澄清清单**（约定 4 三件套）→ 据处置项生成正/反向用例；**表 E 语义变更→派生展示物影响清单 / 表 F 历史需求作废清单 / 文案落点表**（约定 22 第三类 / 约定 34）→ `dev-manual-testcase`「语义/口径变更类文案一致性用例族」正/反向断言（旧口径字样出现即判 Critical）+ `code-verification-loop` 维度 4「文案与数据口径一致性」扫旧口径文案残留 / 失效 REQ 编号注释。；**业务计数声明表**（`dev-logic-architect` 核心原则 28 / 检查项 36 的 5 列表）→ **测试期**由 `/sprint-test` 只核当前 task/单 Sprint 触达的声明/代码/文案；扫描器不支持该范围时保留未核验，不全库回扫（规划期那一次只能看到当时的散落面，看不到 `/sprint-dev` 之后引入的过期副本——而「加到第 9 种、四处文案一个都不改」正是本条要堵的形态，它只发生在规划之后）；**待澄清问题清单**（ux「十、待澄清问题清单」的 `Q-NNN` 表格 / `99_待澄清问题清单.md` 的 `Q-/D-/P-/T-` 四阶段编号（Q 需求期 / D 设计期 / P 计划期 / T 用例新增））→ `/sprint-selftest` Step 2 传 `check_case_stats.py --issue-record`，产出 `issue_coverage`（覆盖 M/N + **逐条点名未覆盖项**），未覆盖不判 Fail 但必须列名进「问题汇总清单」等产品澄清后补用例（⛔ **判据须读三态**：`issue_coverage.error`＝清单在但一条编号都解析不出、`skipped`＝显式标了「无待澄清项」、其余才是真实覆盖数。把 error/skipped 当 0 处理会得到「✅ 全覆盖」——那种假绿灯比不接更危险。**`error` 态落 exit 1 + stderr**（上游刻意不用 2：2 是整脚本 return，会让维度 19 的主体判据一条都跑不到、被 QR 按「入参错不计失败」整档略过）；`skipped` 与正常态退出码同为 0。故 **exit 1 有两种成因**〔用例文档不合格 / 清单解析失败〕，用 `--json.passed`〔**只反映用例文档本身**〕分辨——别拿退出码判「用例数量基线」那一项，会把清单路径写错误报成基线不达标）。**★ 零残留断言登记表**（规划期强制产出、只增不退）→ **形态**由 `/sprint-selftest` Step 2 的 `check_residual_assertions.py` 机检（7 类，含 Z4「方向二·阳性对照」拦恒 0 假绿）；**执行范围**由 `dev-execution-planner` 的「轮次收尾验证任务」定：Sprint 收尾只跑「守护面 ∩ 本轮 git diff ≠ ∅」的断言、其余标 `skipped(out-of-scope)`，而**版本发布前必须全部跑一次作总闸、⛔ 总闸不接受任何 `skipped`**（否则规划期产出一张只增不退的表、测试/发布期无任何消费入口，正是本约定要堵的「产出即沉睡」）
- **命令层责任**（约定 21 只传参不复述）：`/sprint-selftest`·`/sprint-test`·`/sprint-aiauto-test` 调测试类 SKILL 时**必须显式传入基线文档路径 + PRD 原文路径 + DB datasource + 多系统「测试环境与账号」+ 表 E/表 F/文案落点表（语义变更类需求，供文案一致性用例族与「文案与数据口径一致性」维度消费）**（缺则 SKILL 无从消费）；未传 = 违反本约定。SKILL 层（`dev-manual-testcase`/`auto-test-runner`/`code-verification-loop`）实现消费机制。
- **测试深度**：仅真实 autopilot 委派且 version/build/验收基线/完整清单齐备时，`--select all` 才表示**当前版本清单全部用例及必要依赖**；独立 aiauto 只明确目标，full/batch/autopilot 开发子任务的 sprint-test 只当前 task/单 Sprint，禁止 project-wide/system-wide/历史测试全集（子集三条硬护栏单一信源 = `/sprint-aiauto-test` 6bis；⛔ 不存在 `release` 套件）；数值/状态/权限业务用例不得以"页面能打开/无 console error/元素存在"作**唯一**判据、须值级断言。回检 = 规划期 version-auditor（约定 4 F + C-4/C-5）+ 测试期三 SKILL 消费门。关联约定 4/22/26，是它们「规划期→测试期」轴的收口。
