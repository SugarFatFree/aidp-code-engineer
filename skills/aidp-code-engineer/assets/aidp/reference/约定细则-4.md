### 约定 34 — **★ 需求作废清算（跨版本 + 同版本/同 Sprint 内口径反转；补约定 22「级联只版本内单向向下」的反向盲区）**
- **① 研发需求登记表 F**：生成本版研发需求时，把本版变更的关键语义词检索历史版本 `docs/requirements/{历史版本}/研发需求/*.md`，命中的历史需求条目在本版「历史需求作废清单」表 F 显式判定 `沿用 / 作废 / 修订`（历史版本 + 需求编号 + 原结论 + 本版处置 + 理由）。机制单一信源 = `ux-logic-extractor` 表 F。
- **② 产物同步清理**：判「作废」的历史需求，其派生产物（文案/校验/默认值/开关）必须同步清理；代码中引用被作废 `REQ` 编号处的注释必须标注"该需求已于 {version} 作废"（防据旧编号回退）。回检 = `code-verification-loop` 维度 4「文案与数据口径一致性」子行（扫失效 REQ 注释残留）。
- **③ 发布期收敛扩展**：`/version` 发布期收敛（约定 22 Step 3.3.10）扫描范围扩展至**历史版本被本版推翻的需求**——不止收敛本版增量，也据表 F 清理跨版本失效产物。
- **④ 回检**：`version-auditor` 审计 H（跨版本需求作废完整性：本版是否产出表 F、判作废项代码残留是否已清理）。
- **⑤ ★ 作用域边界（dev/test 期只读、全量/历史文档口径统一是发布期唯一职责）**：②的产物清理在 dev/test 期**只作用于当前版本正在开发的代码 + 当前版本文档**（`code/` + `docs/design/detail/{version}/` + 当前版本页面文案，随开发同步标注失效 REQ）；**`docs/design/detail/全量/`（正式发布全量详细设计）+ 历史版本全量设计的口径统一，是 `/version` 发布期唯一职责**（③ Step 3.3.10 收敛 + Step 3.3.11 全量详细设计**重算**〔默认变更范围增量、可 `--full-rebuild` 全量，机制单一信源见 `release-6.md`〕，`--no-tag` 准发布都跳过）。故 dev/test 期 `全量/` 及历史全量设计**仍是"上一次正式发布"的旧口径 = 预期正常态**（由下次正式发布重算），**Agent 绝不在 dev/test 期提议 / 主动处理其"旧口径"**——诸如"全量详设仍写 V0.9.2 旧口径，要不要帮你处理"这类提议**判为越界、答案恒为否**（留给发布期），dev/test 期只读历史、不重写全量/历史设计（与约定 1「执行期只读设计不重新生成」同源）。回检维度（约定 33 / code-verification-loop 维度 4「文案与数据口径一致性」）的 grep 作用域同此边界——只扫当前版本交付物，不扫 `全量/` 与 `{prev-version}` 历史全量设计。
- **⑥ ★ 同版本 / 同 Sprint 内的口径反转清算（下游实证反馈补入；补①~⑤只覆盖"跨版本"的盲区）**：①~⑤治的是**跨版本**推翻；但**同一个版本、同一个 Sprint、甚至同一天内**，产品第二次口述反转第一次已写入文档的结论**同样会留下失效结论**，且此时**没有任何"历史版本"可供表 F 检索**——完全落在①~⑤之外。故补本项，触发与处理如下（决策门落点 = `/sprint-dev` Phase 0B.1.3，见该命令文档）：
  - **判定「追加」还是「反转」**：新口述**只增加新结论** = 追加，按常规增量处理；新口述**推翻了已写入文档的既有结论**（口径反向、白名单方向调转、默认值/状态机/权限范围改写）= **反转**，必须走下面三步。⛔ 二者处理方式不同，先判定再动手。
  - **强制「失效结论清算」（逐条，不许整体重跑）**：列出**所有引用旧结论的落点**并逐条判失效或改写——**研发需求条目 / 详细设计的 ADR「代价与守卫」段 / 自测用例的断言方向 / 反向断言式子 / 各处铁律与禁止性注释 / 代码里的 `REQ-XXX` 编号注释**。⛔ 不得靠"重跑一遍 Phase 0B.1.1"解决：那会**重复生成**而不是**订正**，旧结论仍原地留着。
  - **⭐ 强制回答一个问题（本项最不可省的一条）**：**「旧口径下被判定为安全 / 无害的设计，在新口径下是否仍然安全？」** 口径反转会**在一行代码都不改的情况下改变安全等级**。下游实证：某 resolver 的 fail-closed，旧口径下误标只是「展示错误」，口径反转后同一处误标立刻变成「本该统一开通的资源出现**可用的解绑按钮**」，而解绑在上游是永久取消、不留恢复快照 ⇒ **不可逆数据破坏**。详设里那句「⛔ 不会误放行解绑」若不重写，就成了误导后人的**错误结论**。**⛔ 这个问题不会被任何静态检查发现**，只能靠本项强制提问。
  - **作废用显式标记、不用静默改写**：被推翻的条目一律加**显式作废标记并指向新结论**（`⛔ 本条已于 sprint-{NNN} 反转，改见 REQ-XXX`），整册被推翻的加**整册作废标记**；⛔ 直接把旧文字改掉 = 代码注释里的旧编号无处可查，把后来者引回错误方向。
  - **回检**：`code-verification-loop`「文案与数据口径一致性」维度同样扫**同版本**失效 `REQ` 注释残留（不只跨版本）。
- **⑦ ★ 清算的完整面（跨版本①~⑤与同版本⑥【共用】本项；下游实证补入——一条错误结论曾扩散到至少五处）**：作废一个结论时，**只订正锚点会留下残留，后续维护者按残留改回去**。故除作废条目本身外，还必须逐项做完下面四件：
  - **⑦.1 作废其衍生论证**：当时基于旧结论写下的**「知情决策」记录、风险分析、代价与守卫段**同样失效，必须一并标作废并指向新结论。⛔ 只删结论、留着论证，等于把一份**看起来经过论证**的错误方案留在原地——下一个人读到的是"这事讨论过、结论是这样"。
  - **⑦.2 作废其衍生用例与断言，并注明预期**：受影响的用例 / 正反向断言 / 反向断言式子必须同步改写或作废，且**在用例册显式注明「按旧册跑会失败，这是预期的」**——不注明就会在下一轮回归里被当成新缺陷重开一遍。
  - **⑦.3 扩散面全库检索（不是只改锚点）**：以旧结论的**关键语义词**全库检索，逐处订正。实证扩散面 ≥ 5 处：**全局铁律 / 需求规则条目 / 架构决策记录（ADR）/ 代码注释 / 用例册**。检索命令与命中数须留痕（与约定 39 的散落面回扫同款：**没实跑过的检索不算做过**）。
  - **⑦.4 若该结论是"技术妥协"而非"产品偏好"，必须注明妥协前提与消失条件**：写清**妥协前提是什么、何时消失**。⛔ 不写等于把临时方案沉淀成永久设定——前提消失后没有任何信号提示可以回到正确做法。
- **Why**："代码已改、旧需求没作废"会让被推翻的历史结论静默残留（旧口径文案/旧默认值/旧开关），且旧 REQ 编号注释诱导后续维护回退——这是版本内单向级联（约定 22）覆盖不到的反向盲区，与约定 33「规划期基线→测试期消费」轴互补：约定 33 管"本版基线不漏测"，本约定管"历史结论被推翻要清算"。**边界（⑤）**同样关键：全量/历史文档口径统一是**发布期批量收敛**的事，塞进 dev/test 期会天天拿"全量旧口径"打扰开发者、诱导中途重写不该动的发布产物（违约定 1），故 dev/test 期恒判越界、只读不改。

#### 34.1 执行时机：两段式（⛔ 别在开发期就做全文订正）

本条的执行时机与约定 22 对齐：约定 22 明写"攒批、收口点才就地改主文档"并给了理由
（下游实证：改 2 个前端文件、配套产出 16 份文档 1139 行、80% 时间在写文档）。
⇒ 两条对同一件事给出**相反的执行时机**，执行体只能选更严的那条：不做 = 违反 34，做 = 当场写 300+ 行。
下游实证正是后者 —— 一次口径反转的全文订正单项 **+312 行**（流程图 / 状态机 / 异常路径表 /
验收测试点 / 语义变更表 / 作废清单 / 断链锚点全部就地改写）。

**定规（与约定 22 同口径，不再冲突）**：

| 时机 | 做什么 | 规模 |
| :- | :- | :- |
| **开发期（当场）** | ① 在被推翻的条目**标题处**加一行显式作废标记 + 指向新结论的锚点；② 把"扩散面待清算"记进**需求族增量册**的「已知失准点」段 | **≤10 行** |
| **收口点（批量）** | 才做全文订正：流程图 / 状态机 / 各类表 / 锚点修复 / ⑦.3 全库检索留痕 / ⑦.1 衍生论证 / ⑦.2 衍生用例 | 不限 |

⛔ **两段式不削弱"不静默改写"**：开发期那一行作废标记是**必须当场落**的 —— 它正是"不静默"的载体。
被推迟的只是**全文订正的工作量**，不是"让旧结论继续看起来有效"。
⛔ 反过来也不许只标不清：增量册里那条「已知失准点」是收口点的**唯一触发信号**，漏记等于清算永远不会发生。

> ⚠️ **链外任务同样适用**（约定 41）：链外只做开发期那 ≤10 行，全文订正等到下一个收口点。
> 这正是本条与约定 22 冲突时最容易把一个小改动拖成半天的地方。

### 约定 36 — **★ 子 Agent 派发授权（授权来源有二且并列生效：站位授权 + 命令入口；派不出【后台】→ 转前台/内联，绝不静默跳过）**
- **典型被授权派发的子 Agent**：`version-auditor` 终审（`/version` Step 2.4.7）/ `code-verification-loop` 验收 QR（`/sprint-test`）/ `dev-logic-architect`·`ux-logic-extractor`·`dev-execution-planner`·`dev-manual-testcase`·`auto-test-runner` 的质量检查子 Agent / `sprint-autopilot`·`sprint-aiauto-test` 的隔离执行子 Agent / 约定 22 台账收口子 Agent（约定 24 门禁触发）/ `/sprint-design` Step 1.6 产物回检子 Agent 等——凡命令文档写明"派独立子 Agent"处，均在本授权覆盖内。
- **★ 授权来源 = 项目记忆文件的常驻站位授权（不止命令入口）**：项目记忆文件（`AGENTS.md` / `CLAUDE.md`）顶部的「★ 站位授权」段是**项目所有者写在记忆文件里的显式指令**，优先级**高于**宿主 / 会话级『非用户请求不主动调 Agent』类**默认**约束（后者是缺省保守值、不是用户表态）。故本项目内**默认自动派后台子 Agent**、无需逐次征询。
- **★ 判定方式 = 先试后降，不是先判后做（下游实证反馈修复）**：⛔ **不得**靠"解读会话里某句宿主约束算不算禁用后台 Agent"来决定降级——那是**纯自然语言判读、没有任何确定性判据**，同一条约定在不同会话会得出相反结论，行为不可预期（下游实证：执行体读到一句宿主默认约束即自判命中②走前台，用户随后质疑"不是说默认后台吗"）。**正确做法 = 直接发起后台派发**（`Agent({run_in_background:true})`），**只有实际被拒 / 报错 / 派发失败**才落下面的降级阶梯。判据是**客观结果**，不是对一句话的解读。
- **★ 降级阶梯（试过后台、确实派不出时，由确定性判据钉死、执行体不自选最保守档）**：① **【首选】后台子 Agent**（隔离上下文、不阻塞主对话）。② **后台派发【实际失败】（只是派不出后台、前台仍可行）→ 转前台/内联执行该子 Agent 的等价工作**（当轮即产出、只慢不丢），**⛔ 绝不**因"派不出后台"就跳过该质量门 / 直奔"静默当作已完成"（那正是"自动化命令派不出子 Agent 就什么都没做"的黑洞根因）。**★ 降级②必须在本轮完成摘要里向用户交代代价（强制，不是可选）**：后台派发的**核心收益是上下文隔离**，转前台后该子 Agent 读写的全部内容**都进主上下文**——功能上仍合规，但这项收益**整个丢掉**。故摘要须写明一行：**「本次 <子 Agent 名> 走前台（原因：<后台派发的实际失败信息>），代价 = 主上下文纳入 N 个文件约 M 行」**。⛔ 只写"必须改前台"而不写代价，用户只能**靠自己发现**（实际项目中：一次前台子 Agent 把 14 个文件约 1500 行灌进主上下文，用户事后才察觉）。③ **宿主彻底禁用 Agent 工具（连前台子 Agent 都不行）→ 由主执行体内联完成该子 Agent 的等价检查 + 显式告警**"本应独立子 Agent 执行、已降级内联、上下文可能受影响、结论请人工复核"，**仍不静默略过检查**。
- **★ 作用域不止于命令内（堵「裸对话开发」断链）**：本授权的触发面是**「用户在本项目里做业务开发并提交」这一事实**，**不是「用户敲了哪条命令」**。故 **`/sprint-*`·`/version` 等命令之外、用户全程自然语言提需求 → 执行体改代码 → `git commit`+`push` 的路径，同样在授权覆盖内**——最典型的就是**约定 24 门禁触发的台账收口子 Agent**：它由 `commit_gate.py` 的 `should_dispatch_cascade=true` 触发，**与命令入口无关**。**⛔ 执行体不得以「本轮没有 AIDP 命令、拿不到约定 36 授权」为由不派单**——那是把本条读窄了：命令入口只是**最常见的**触发场景、不是**唯一的**授权前提。宿主/会话级『非用户请求不主动调 Agent』默认指令在此**同样不构成豁免**（见上条降级阶梯：至多改变执行形态，不改变必须执行）。**Why**：约定 24 的触发条件是变更事实（任何 commit），若本条的授权面窄于它，两条约定就在「裸对话提交」这个差集上字面冲突，执行体只能临场权衡——同一项目不同会话行为不一致（台账积压由 `commit_gate.py` 下次运行时结算并抬高退出码兜底，见约定 24 详规）。
- **★ 边界（不扩权）**：本授权**只覆盖"派子 Agent 去做命令文档既定的工作"**，**绝不**扩权去做命令职责外 / destructive / 对外发布类动作——那些仍受各自约束与确认门（如约定 2 版本落点门、约定 31 CICD 写动作授权、tag/merge 等人工 destructive 动作）。"授权自动派发" ≠ "授权子 Agent 越权"。
- **与约定 24 的关系**：约定 24 的门禁在台账积压时要求派台账收口子 Agent，其派发授权与降级阶梯即沿用本约定；本约定是**通用版**，覆盖**所有** AIDP 自动化命令的子 Agent 派发。
- **Why**：多数"自动化命令派不出子 Agent"其实是执行体被"默认不主动调 Agent 工具"约束住、并非宿主真禁用——一条站位授权即消解，让并行/上下文隔离/独立质量门的收益拿回来；同时明确真受限时转前台/内联而非静默丢弃，既不在受限环境里丢检查、也不让用户面对"命令跑了却什么子 Agent 产物都没有"的黑洞。
