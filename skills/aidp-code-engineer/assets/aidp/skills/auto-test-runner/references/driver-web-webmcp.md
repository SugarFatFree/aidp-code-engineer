# 驱动适配层 · Web 端补充能力：WebMCP 工具调用（`invoke`，可选 · 条件启用）

> ★ **定位**：「客户端 MCP 能力」是**跨端**功能点（Web / 小程序 / 移动 / 桌面），**WebMCP 只是它的 Web 端实现**（`client_type=web` + `implementation_kind=webmcp`）。跨端总纲见 [`driver-client-mcp.md`](./driver-client-mcp.md)；本文件只讲 Web 端怎么落地。

> **本文件只在调用方传入 `webmcp_enabled: true` 时适用。** 为 `false` 或未传时，本文件描述的
> 一切**整体不适用**：不做版本校验、不写 run-context 相关字段、不产生告警、报告里不留位置。
>
> **归属声明：WebMCP 不是第五个「端」。** 它仍在浏览器里、仍经同一个 Web 驱动，是 **Web 适配器
> 的一项补充能力**。故它落在 `driver-*` 适配层（本文件），**方法论层零改动**——方法论层只知道
> 有一个可选的 `invoke` 抽象能力，不知道它底下是什么 API。

## 〇、门控与入参（执行内核不自行探测）

| 入参 | 形态 | 说明 |
| :- | :- | :- |
| `webmcp_enabled` | `true` / `false` | **唯一开关**。为 `false` 或未传 → 本文件整体不适用 |
| `webmcp_entry_symbols` | 数组 | 该项目**实测**的能力入口标识符。⚠️ 挂载位置已迁移过一次、规范仍在演进，**写死任何名字都会过期**，故由调用方传入 |

**⛔ 严禁在本 skill 内自行探测是否启用**（不 grep 用例、不扫被测站点）。判定散落多处必然漂移，
一处判错就给未启用项目凭空长出 block 项与报告位。

## 一、驱动版本要求（≥ 1.8.0，**仅路径 A**）

**路径 A** 的工具列出与调用要求 `chrome-devtools-mcp` **≥ 1.8.0**（该版本起才带这两个 MCP
工具）。`detect_drivers.py web --webmcp` 会校验版本。**走路径 B 时该版本门不适用**——但版本
探测照跑无害，结论按「本轮用哪条路径」解读。

**版本不足 / 版本取不到时的处置（三条，缺一即违规）：**

1. 给出升级命令 `npm i chrome-devtools-mcp@latest -g`；
2. 把相关用例标 **`block(webmcp-driver-too-old)`**（版本取不到 → `block(webmcp-driver-version-unknown)`，
   **fail-closed**：确认不了达标就不能声称可用）；
3. **⛔ 不要静默降级为「就当没有 WebMCP」。**

> **Why 第 3 条是硬要求：** 静默降级会让这一整类用例**全绿式消失** —— 报告里 total 变小、
> 通过率照样 100%，**看不出漏测**。标 `block` 才会把缺口如实留在「缺陷列表 + 遗留风险」里。
> 这与本 skill「环境事实取不到写 `未取到(原因)`、不写像样的默认值」是同一条纪律。

**同时：绝不因此终止整轮、绝不挂起**（无人值守硬要求）——其余用例照跑。

## 二、启动方式：两个作用域不同的开关

WebMCP 需要**两个作用域不同的浏览器开关同时满足**，缺一则**能力入口根本不存在**：

| 开关 | 作用域 | 说明 |
| :- | :- | :- |
| `--unsafely-treat-insecure-origin-as-secure=<origin>` | **仅该 origin** | HTTP 环境必须；**必须同时配 `--user-data-dir=<独立目录>`**，该参数**不允许作用在日常 profile 上** |
| 能力开关（**形态随 Chrome 版本不同**） | 见下 | ⚠️ 有两种，**先确认目标 Chrome 版本再选**，别假定只有一种 |

**能力开关的两种形态（这一条最容易照抄错）：**

| 形态 | 适用 | 作用域 | 风险 |
| :- | :- | :- | :- |
| `chrome://flags` 里的**实验特性总开关** | 老版本 Chrome（调用方实测走的这条） | **全局** | 会打开浏览器**全部**实验特性、**无对应企业策略可精细控制** → 只适合开发机 / 小范围试点，⛔ **不得作为可全员推广的特性** |
| `--enable-features=WebMCP` | **Chrome 150+**（本机 `chrome-devtools-mcp@1.8.0` 的 `README.md:707` 明写） | **定向** | 定向开关，无「打开全部实验特性」这一层风险 |

> ⚠️ **上游设计文档里那条「实验特性开关是全局的、不得全员推广」的风险结论，前提是走第一种形态。**
> 若目标环境是 Chrome 150+ 且用定向开关，该风险的**适用性须重新评估**；但在确认之前**保守取
> 第一种**（结论更严），⛔ 不要因为「有定向开关」就把风险段删掉。

两个开关通过 CLI 的「附加 Chrome 参数」入口传入。**完整启动命令由调用方传入
（`webmcp_launch_command`），不要自拟。**

### ★ origin 必须 scheme + host + port 三段精确匹配

**这是最常见的失败原因**，三种写法都会静默失效（能力入口就是不出现，且没有任何报错）：

| 写法 | 实际访问 | 结果 |
| :- | :- | :- |
| `http://192.0.2.10` | `http://192.0.2.10:8002` | ❌ **端口漏了** |
| `https://192.0.2.10:8002` | `http://192.0.2.10:8002` | ❌ **scheme 不符** |
| `http://app.example.com` | `http://192.0.2.10:8002` | ❌ **域名 vs IP** |

> ⚠️ 注意 `http://localhost` 本身就算 secure context（W3C Secure Contexts 规范），**本地开发
> 一切正常、部署到 HTTP 测试环境才崩**。故这三行的失败形态只在真实部署环境上才出现。

## 三、连接后自检（两行，缺一不可）

```js
window.isSecureContext      // 期望 true      —— 为 false 说明白名单没生效
typeof <能力入口>            // 期望 "object"  —— 为 "undefined" 有三个可能原因，见下表
```

**两个都查才能区分「白名单没配对」与「能力开关没开」；只查一个必然误判成「这能力不可用」。**

⚠️ **第二行为 `"undefined"` 时有三个可能原因，不能一律归到「实验开关没开」**：

| 可能 | 怎么排除 |
| :- | :- |
| 能力开关没开 | 核对启动命令里有没有那个开关（两种形态之一，见 §二） |
| **Chrome 版本不够**（路径 A 要求 150+） | 读 `env-facts.json` 的 `browserVersion`（环境准备阶段已取证，不必另测） |
| 走路径 A 却没加 `--categoryExperimentalWebmcp`（默认 `false`） | 查驱动启动参数——**不加这两个 MCP 工具压根不存在** |

三项都记进 block 证据，**别只写一句「实验开关没开」**——那会让排查从第一步就走错方向。

**自检不过 → 标 `block` + 记录两行的实际返回值**（这是排查的唯一线索），**继续其余用例**。

> 归属：本自检走 `observe` 的**运行环境通道**（与「运行环境取证」同一条通道），端专有读法只落
> 本文件；方法论层只出现抽象信号名。

## 四、调用约定（两个坑都会静默失败或报晦涩错误，逐字照做）

> ⚠️ **本节的 API 名逐字登记在此、且只能出现在本文件**：它们是端专有 API，写进方法论层会被
> `check_layer_isolation.py` 判泄漏（维度 1 Critical）。⚠️ 同时注意区分——**方法名相对稳定，
> 而「能力入口挂载在哪个对象上」不稳定**（已迁移过一次、规范仍在演进），故入口一律用调用方传入的
> `webmcp_entry_symbols`，本文件用 `<能力入口>` 占位，**不写死**。

### 4.1 `<能力入口>.getTools()` 是**异步**的，返回 `Promise<Array>`

- **不 `await` 只会拿到一个 Promise** —— 下游曾据此误判「它返回的是对象不是数组」，然后去写
  兼容代码，方向完全错了。
- **它返回浏览器侧全量工具、不只本页登记的。** 校验「本页登记了哪些」须以**用例/设计文档的
  工具清单**为准，不能拿它的返回值当本页账本。

### 4.2 `<能力入口>.executeTool(tool, argsJson)` 两个参数形态都容易搞错

| 参数 | 正确形态 | 传错的报错 |
| :-: | :- | :- |
| 第一参 `tool` | 从 `getTools()` 取到的**工具对象** | 传名称字符串 → `provided value is not of type 'RegisteredTool'` |
| 第二参 `argsJson` | **JSON 字符串** | 传对象 → `Failed to parse input arguments` |

> 两个报错都很晦涩、且不指向真正原因，故此处逐字登记。

### 4.3 原型上**有什么、没什么**（决定用例怎么断言）

实测能力入口原型只有：`registerTool` / `getTools` / `executeTool` / `ontoolchange`。

**⛔ 没有 `unregisterTool`。** 据草案臆想它存在会让撤销**静默失效**（曾用可选链做防御，撤销悄悄
没生效、代码零报错、文档与实际不符）。**故「停用」的正确表现是：工具仍在 `getTools()` 清单里、
但调用被拒**——断言「清单里没了」必然误判为缺陷。

## 五、与 CDP 的分工（★ 不是二选一，是配合使用）

| 用途 | 用哪个 |
| :- | :- |
| 调业务能力、取结构化数据、验错误契约 | **WebMCP 工具调用** |
| 点确认框、读控制台错误、看界面状态、验「未启用态无任何元素」 | **CDP**（快照 / 点击 / 控制台） |

**典型组合：** 用 WebMCP 发起一个需确认的操作 → 调用挂起 → 用 CDP 点确认按钮 → 调用返回。

> ★ **这个组合本身就证明了「外部 Agent 可消费页面 WebMCP」**：测试链路里的 Agent 就是一个
> **非页内的外部消费方**（经 CDP 进入页面 JS 上下文再调工具）。这正是「调用方不可信」假设的
> 现实依据 —— 用例据此应把**确认门 / 脱敏 / 不扩权**当作**「外部调用方也拦得住」**来验，
> 而不是验「助手很守规矩」。

## 六、`invoke`：Web 适配器的可选第五能力

在四原子能力（`locate` / `act` / `observe` / `capture`）**之外**，为 Web 适配器加一个**可选**能力：

| 能力 | 语义 | 输入 → 输出 |
| :- | :- | :- |
| **invoke** | 列出 / 调用页面登记的工具 | `()` → `工具清单`；`(工具, 入参)` → `结构化结果`。**落地按路径二选一**：路径 B（页内 JS）= `getTools()` / `executeTool(tool, argsJson)`；路径 A（驱动 MCP 工具）= `list_webmcp_tools` / `execute_webmcp_tool(toolName, args)`。⚠️ 两条路径的作用域与第一参形态不同，见 §〇·补 |

- **可选**：能力探测不到时**优雅降级** —— 相关用例标 `block`，其余用例照跑，**方法论层零改动**。
- **不新增第五个「端」**：它是 Web 适配器的补充能力，不是新的被测端类型。
- **其它端**：小程序 / 移动 / 桌面 **本端不适用**（无浏览器 WebMCP 能力入口），明写不适用而非留空。

## 七、报告纪律

沿用既有的「driver 字段必如实」纪律：**用了 WebMCP 工具调用的用例，其证据须体现是经 WebMCP
达成的，而非纯 CDP 模拟点击**，⛔ 不得混为一谈。

> 两者的失败形态完全不同（工具调用失败 = 业务能力或契约问题；模拟点击失败 = 界面或定位问题），
> 混记会让缺陷归因整体走偏。
