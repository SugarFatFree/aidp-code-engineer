# 用例格式对接契约(消费 dev-manual-testcase 产物)

> 本文件是 auto-test-runner **输入侧的硬契约**:规范如何解析上游自测用例(由 `dev-manual-testcase` skill 生成)。执行前先按本契约把用例解析为可调度的结构化任务(相当于参考项目的 test-case-prepare/generator 职责)。
> **独立性**:本 skill 不引用 dev-manual-testcase 的任何文件,只按本契约识别其**输出格式**;上游若调整格式,同步更新本契约即可。

---

## 一、目录与文件结构

上游产物落在 `{测试文档目录}/{项目名}/`,命名带两位序号前缀:

| 文件 | 说明 | 是否用例源 |
| :- | :- | :-: |
| `00_索引.md` | 专职索引(文档族清单导航) | ❌(索引,跳过) |
| `01_研发自测方案.md` | 自测方案(范围/环境/通过准则/缺陷跟踪) | ❌(读通过准则/证据要求,不当用例) |
| `02_全量自测用例.md` / `02_增量自测用例.md` | 单文件模式用例 | ✅ |
| `02_自测用例-总览.md` | 多文件模式总览(索引各模块) | ✅(入口)|
| `03_`~`97_{模块}.md` | 多文件模式各模块用例 | ✅ |
| `98_跨系统.md` | 跨系统验证清单 | ✅ |
| `99_待澄清问题清单.md` | 待澄清项 | ❌ |

- **单文件模式**:直接解析 `02_*.md` 用例文件。
- **多文件模式**:从 `02_自测用例-总览.md` 取模块清单 → 逐个解析 `03_`~`97_` 模块文件。
- 解析用例时**跳过 `00_`(索引)、`01_`(方案)与 `99_`**(非用例)。
- **历史旧锚兼容(grandfather):** 旧上游目录可能是 `00_研发自测方案.md`(方案)+ `01_全量/增量自测用例.md` / `01_自测用例-总览.md`(用例)+ `02_` 模块;遇到时按旧布局解析(方案在 `00_`、用例从 `01_` 起),不报错。

## 二、结构层级与命名

```
### 套件 SUITE-{编号}: {套件标题}        ← 模块 = 一个套件 = 一个执行批次
  #### / ##### 用例 TC-{模块}-{序号}: {标题}   ← 最小执行单元
```

- **套件**:`### 套件 SUITE-*`(如 `SUITE-USER`、`SUITE-01`)。auto-test-runner 以**套件为批次粒度**(一个套件 = 一个执行子 Agent = 一次会话)。
- **用例**:`#### 用例 TC-*` 或 `##### 用例 TC-*`(标题层级 3~6 级都识别)。TC-ID 全局唯一。
- **入口流程**:套件下的 `#### 入口流程 (Suite Setup)` 只在套件开头执行一次(登录/进工作台),对应执行流程"模块开头走一次入口"。

### ★套件/用例标题形态契约(两 skill 统一,**宽进**)——本节是本端解析口径的单一信源

**解析端必须同时识别下列全部形态,只能比上游更宽、不得更窄**,与上游 `dev-manual-testcase` 的
**5 个**套件解析脚本(`check_testcase_suite` / `check_testcase_format` / `check_suite_upstream` /
`check_case_stats` / `check_test_plan_alignment`)口径一致:

| 元素 | 必须识别的形态 | 本端正则(`scripts/tasks_state.py`) |
| :- | :- | :- |
| 套件 | `套件` \| `测试套件` 两种前置词 **×** `SUITE-` \| `TS-` 两种编号前缀 = **4 种组合**;标题层级 `##`~`####` | `^#{2,4}\s*(?:测试)?套件\s+((?:SUITE\|TS)-[\w\-]+)\s*[:：]?\s*(.*)$` |
| 用例 | 「用例」二字**可省略**(`#### 用例 TC-A-001: 标题` 与 `#### TC-A-001: 标题` 都要认);标题层级 `###`~`######` | `^#{3,6}\s*(?:用例\s+)?(TC-[\w\-]+)\s*[:：]?\s*(.*)$` |

**规范形态 = `套件 SUITE-*` + `用例 TC-*`**(上游新生成一律用它,其检查脚本对其余形态出 Info 提示);
`测试套件` / `TS-` / 省略「用例」属**历史兼容形态**,存量文档仍会出现。

> ⚠️ **收窄的后果是静默漏跑、不是报错**:本端 `tasks_state.py` 曾只认 `套件 SUITE-` 且必带「用例」二字——
> 套件扫不到 → tasks.md 分组丢失;用例扫不到 → 该用例**根本不进 tasks.md**,报告里连"未执行"都不会体现。
> 改动本端解析正则前请先跑 `python3 <SKILL_DIR>/scripts/tasks_state.py selftest`(内置形态自检,收窄即 exit 1)。

### `affects:` 影响面标签(套件级,**可选**,上游 dev-manual-testcase 产出)

套件块的 L2 引用区可能带一行影响面标签,供**跨 build 回归的变更影响面筛选**——把本次 `git diff` 涉及路径与各套件 `affects` 做包含匹配,命中的套件才重跑,未触及的沿用上轮结论。

```
> **affects:** modules=[用户管理, 权限管理] pages=[/system/user, /system/role]
```

- **解析**:整行匹配 `\*\*affects[:：]?\*\*` 后取 `modules=[…]` / `pages=[…]` 两个列表,逗号分隔。
- **可选**:存量用例文档一律没有本行,**缺失时退化为全量重跑**(与旧行为一致),**不得因缺失报错或跳过套件**。
- **`pages=[N/A]`** 表示该套件无前端路由(纯后端),按"无页面维度"处理,不要当成一个叫 `N/A` 的路由去匹配。
- ⚠️ **筛选决策归编排层,不归执行内核**:本 skill 只负责**能解析出**这两个列表;"本轮该跑哪些套件"由上层按 diff 决定后再把用例路径传进来。执行内核**永远跑它拿到的全部用例**,不自作主张跳过——跨 build 全量重跑那条硬边界不受影响。
  > **`tasks_state.py init --select` 与本条一致、不冲突**:它是**编排层显式传参**(即本条说的「上层决定后再传进来」的一种形态),发生在建 tasks.md 阶段;执行内核照旧跑它拿到的**全部** tasks.md 条目。⚠️ 但 **`--select regression` 绝不可用于新 build 回归轮**(违反跨 build 全量重跑硬边界),且子集 tasks.md 头部必须带留痕行。

## 三、用例字段(元信息字段行)

用例标题下的引用块 `> **字段**: 值 | **字段**: 值` 提供元信息:

| 字段 | 键 | 用途(执行侧) |
| :- | :- | :- |
| 优先级 | `优先级` | P0/P1/P2 → **执行模式分级**(P0/P1→verified,P2→direct) |
| 类型 | `类型` | 正向/异常/边界/权限/回归…→ 辅助模式判定(含"集成"→self-heal) |
| 测试项 | `测试项` | ≤5 字被测对象描述(元信息,执行侧仅作参考,不单独落结果 JSON 字段) |
| 反向 | `反向` | 是/否 → 映射结果 JSON `is_reverse`(是=true),随结果透传供下游对账消费 |
| 覆盖 | `覆盖` | 覆盖矩阵维度标签(F/R),透传报告(可选) |
| 承接前置 | `承接前置` | 前置状态/依赖 → 感知阶段判断是否需导航/登录 |
| 前置探测 | `前置探测` | 结构化前置项 ID(如 `ED-001`) → 浏览器前批量数据面探测并按 ID 复用结果 |

> **★字段名契约(两 skill 统一,不得歧义):** 反向字段的键**统一为「反向」**(值 `是`/`否`),与上游 `dev-manual-testcase` 用例元信息 `> **反向**: 是/否` **完全一致**。解析时只认字面键「反向」;**不使用「是否反向」等别名**(避免自动化解析歧义)。若上游产物出现旧别名,先归一到「反向」再解析。

- **模式判定**:类型含「集成/跨模块」**或**上一轮 fail/block → self-heal;否则 P0/P1 → verified;否则 direct。

## 四、步骤表(四要素)→ 原子能力映射

每条用例的测试步骤表列为:`步骤 | 操作动作 | 操作对象 | 操作数据 | 预期现象`。执行时逐行映射到四原子能力:

> ⚠️ **「步骤」列允许「数字 + 一个可选方括号标注」**,形如 `| 1 [加速可选] | 登录 | … |`(上游
> `dev-manual-testcase` 的**步骤级加速标注**)。**解析步骤号时必须容这个可选段**——上游实测:
> 解析器只认纯数字时,带标注的行**整行匹配不上**,于是该行不被当成步骤行、一整套逐行检查
> 对它全部失效,外在只表现为一句看似无关的「缺少测试步骤章节」,**方向是假绿**。
> ⚠️ **`[加速可选]` 是提示不是许可**:是否真走 WebMCP 仍按「一·补三 WebMCP 分层铁律」的
> **步骤性质**判 —— **没标不等于禁止加速,标了也不等于必须加速**;
> 且**视觉还原度 / 布局 / 样式断言无论标没标,一律必须 DOM + 截图**(`mechanism` 填 `webmcp` 时
> `check_result.py` C14 判 Critical)。

| 用例列 | → 原子能力 | 说明 |
| :- | :- | :- |
| **操作对象**(页面可见文案/标签) | `locate(操作对象)` → 句柄 | 上游保证操作对象是**语义文案**非 CSS 选择器(dev-manual-testcase 核心原则 6),故可跨端 locate |
| **操作动作**(点击/输入/选择/上传/返回…) | `act(句柄, 动作词, 操作数据)` | 动作词映射见 `driver-adapters.md`(端无关契约)与被测端的 `driver-<端>.md` |
| **操作数据** | act 的数据参数 | 无数据时为 `—` |
| **预期现象** | `observe()` + 断言 | 与预期现象比对,判 pass/fail;关键步骤 `capture` 取证 |

> **对接铁律**:操作对象若出现 DOM/CSS 选择器、xpath、接口字段名(违反上游核心原则 6),`locate` 跨端无法复用——此时标该用例 `block`,并在 error 注明"用例操作对象非语义文案,需上游修正",不臆造选择器。

## 五、解析产出(供调度)

### 5.1 结构化前置探测字段

用例若依赖进入浏览器前即可确认的数据状态,必须在测试步骤前声明「前置探测」段,而不是只在「前置条件」散文中描述。每个前置项使用全册唯一的 `ED-NNN` 编号;相同实体/状态/探测方式的用例复用同一编号,供执行内核合并为一次探测。

```markdown
**前置探测:** ED-001

| 前置项 | 探测实体/状态 | 探测方式（只读） | 不满足时 block 归因 |
| :- | :- | :- | :- |
| ED-001 | 订单，存在 ≥1 条 `status=待交付` | 只读接口 `GET /orders?status=待交付`，成功响应按 `total` 判断 | 缺少 status=待交付 的订单样本 |
```

**解析要求:**

- `前置项` 必须是 `ED-NNN` 并可在用例册内回查;缺失、重复定义不一致或编号无法回查时，记录解析问题，不得静默当作无前置。
- `探测实体/状态` 必须写出实体与状态/数量关系(如 `≥1`、`=0`);`探测方式（只读）`只能描述只读接口或数据面查询，禁止写入、删除或修改操作。
- `不满足时 block 归因` 必须是可直接放入 `block(precondition-unmet)` detail 的具体短语，不允许写「见前置条件」「数据不足」等不可核对占位。
- 同一 `ED-NNN` 的三列定义必须全文一致;执行侧按编号只探测一次，将结果广播给关联用例。
- 这些前置探测属于探测类断言，必须遵守 `test-design-methodology.md` 的方向、特异性及阳性对照分档自检；尤其探测失败必须与合法空结果区分，不能把请求失败当成“0 条”。

解析后的内部任务对象需增加:

```json
"preconditions": [{
  "id": "ED-001",
  "entity_state": "订单，存在 ≥1 条 status=待交付",
  "probe": "只读接口 GET /orders?status=待交付，按 total 判断",
  "block_detail": "缺少 status=待交付 的订单样本"
}]
```


解析后每条用例产出内部任务对象:
```json
{ "tc_id": "TC-USER-001", "suite": "SUITE-USER 用户管理", "title": "新增用户成功",
  "priority": "P0", "type": "正向", "is_reverse": false, "coverage": ["F4"],
  "preconditions": [{"id":"ED-001","entity_state":"订单，存在 ≥1 条 status=待交付","probe":"只读接口 GET /orders?status=待交付，按 total 判断","block_detail":"缺少 status=待交付 的订单样本"}],
  "mode": "verified", "steps": [{"action":"点击","target":"新增按钮","data":"—","expect":"弹出新增弹窗"}] }
```
- `mode` 由字段判定;`steps` 从四要素表逐行解析。
- ⚠️ **这是解析期的内部任务对象,字段名与「执行结果 JSON」不同名**:结果 JSON 用 `case_id` / `execution_mode`(schema 见 `../assets/result-schema.json`、字段表见 `report-format.md` §一),写结果时须用结果 schema 的字段名,`gen_report.py` 只认后者。
- tasks.md 只登记 `tc_id + title`,详细 steps 执行时按 TC-ID 现查(降载,见 execution-methodology.md 第一节)。

## 六、语义断言解析(可选,确定化判定)

用例「预期现象」多为自然语言,而 `observe` 拿到的是结构化快照,pass/fail 判定(尤其**计数 / 状态迁移 / 字段核对**)最易靠 AI 临场判错。为此上下游共享一层**确定化的语义断言契约**:用例关键步骤可在「预期现象」之外附一行**机器可判**的语义断言。

> **★共享 DSL(与 `dev-manual-testcase` 完全一致,逐字采用,不得改动语法):**

```
【语义断言 DSL(两 skill 统一契约,用页面可见文案,禁选择器/字段名/xpath)】
在用例"预期现象"之外,关键断言步骤可附一行机器可判的语义断言:
  格式  `断言: <断言表达式>`   反向用例用  `断言(反向): <断言表达式>`
支持的断言表达式:
  - 存在文本"X"                     页面可见区域出现文案 X          例:断言:存在文本"创建成功"
  - 不存在文本"X"                   页面不出现文案 X                例:断言:不存在文本"内部备注"
  - 列表行数+N / 列表行数-N / 列表行数=N   目标列表行数相对增减或等于  例:断言:列表行数+1
  - 字段"标签"显示为"值"            指定字段标签对应值              例:断言:字段"金额"显示为"1,234.00"
  - 状态由"A"变为"B"               状态文案迁移                    例:断言:状态由"待审核"变为"已通过"
  - 元素"文案"可点击 / 置灰 / 不可见     元素可交互态                例:断言:元素"提交"置灰
  - 存在错误提示"X"（反向）         反向用例校验错误提示            例:断言(反向):存在错误提示"必填"
规则:断言里的"标签/文案/状态"一律用页面可见语义文案,禁 CSS/xpath/DOM 选择器、接口字段名(与操作对象同规则)。
断言可选、增量附加:不写断言的步骤仍按自然语言"预期现象"由 AI 判定;写了断言的步骤由执行侧据断言做确定化判定。
```

**执行侧映射说明(供 `observe` 判定,断言全部基于 observe 可观测信号,禁不可视断言):**

| 断言表达式 | → observe 判定逻辑 |
| :- | :- |
| 存在文本"X" / 不存在文本"X" | 在 `observe` 快照文本里查找 X 是否出现 |
| 列表行数+N / -N / =N | 对**目标列表**计数,与前置快照(步骤前 observe 的行数)比对相对增减,或与 N 相等 |
| 字段"标签"显示为"值" | 在快照里**定位该标签**,读其邻近值与期望值比对 |
| 状态由"A"变为"B" | 比对**状态文案**由 A 迁移到 B(前置快照为 A、当前快照为 B) |
| 元素"文案"可点击 / 置灰 / 不可见 | 读该元素的**可交互态**(enabled/disabled/visible) |
| 断言(反向):存在错误提示"X" | 反向用例**期望该错误提示出现**(校验拦截生效) |

> **判定优先级(执行侧):** 用例步骤**带 `断言:` 行 → 优先按语义断言做确定化判定**(逐条按上表映射到 observe);**无断言行 → 回退自然语言「预期现象」由 AI 判定**。断言可选、增量附加,不改变原有四要素解析。

> **★值级断言硬约束(不限 P0/P1):** 凡涉及**数值 / 状态 / 权限**的用例**必须带值级断言**,禁止把「页面加载成功 / 无 console error / 元素存在」当作唯一通过判据(细则见 execution-methodology.md「值级断言硬约束」)。带断言步骤走确定化判定,不再靠 AI 临场判。

> **★反向断言术语对齐(不新增能力):** 上游 dev-manual-testcase 的 `[反向-残留]` 用例(裁剪元素若仍存在则失败)由本 skill 既有的**「不存在文本"X"」DSL** 承载执行(即 `断言: 不存在文本"X"`),结果 JSON 的 `is_reverse` 照常透传。这只是术语对齐——反向能力早已在 DSL 内,**下游勿误以为缺失或需另建**。

## 七、用例族标记与结果透传(与 dev-manual-testcase 共享契约,按文本标记识别)

上游在用例标题/元信息里打若干**文本标记**,本 skill 按标记识别用例族并在结果 JSON 透传对应字段;**不新建能力,只按标记路由**:

| 上游标记 / 字段 | 识别 | 结果 JSON 透传 | 严重度 / 执行影响 |
| :- | :- | :- | :- |
| `[回归]` 标记 + `关联缺陷: {缺陷ID}` 字段 | 用例族=回归 | `is_regression=true`、`related_defect_id={缺陷ID}` | 失败(fail / **非环境类**的 block)**一律判 Critical,不许降级为 Important**(见 report-format.md §2.3 + gen_report 用例族锁定) |
| `[PRD存在性]` | 用例族=PRD 功规点存在性 | (可选)`case_family` 含标记,或标题/类型保留 `[PRD存在性]` 字样供 gen_report 识别 | 失败**一律判 Critical**(同上) |
| `[双源对账]` + 「双源对账」段等价 SQL | 用例族=双源对账 | `db_assertion={pageValue, sqlValue, match}` | 由**驱动适配层 DB 断言驱动**执行等价 SQL 与页面值比对,`match=false` 判 fail(见 [`driver-db-assertion.md`](./driver-db-assertion.md)) |
| `[反向-残留]`(DSL `不存在文本"X"`) | 用例族=反向残留 | `is_reverse=true` | 由既有「不存在文本X」DSL 承载,元素仍存在则 fail(能力已有,仅术语对齐) |
| `[文案一致性]`(正向文案断言 + 反向 DSL `不存在文本"旧口径字样"` + 可配 `[双源对账]` 一致性) | 用例族=文案一致性(语义/口径变更) | 反向用例透传 `is_reverse=true`;标题/类型保留 `[文案一致性]` 字样供 gen_report 识别 | 失败**一律判 Critical,不许降级**(口径误导对账,与 `[回归]`/`[PRD存在性]` 同级;反向断言由既有「不存在文本X」DSL 承载,旧口径文案仍在则 fail) |
| `[还原度]`(通用还原度套件:列表页 10 条 / 详情页 4 条 / 表单页 2 类 / 含数字的页 6 条固定模板项) | 用例族=通用还原度 | 标题/类型保留 `[还原度]` 字样 | ⚠️ **不锁 Critical**,按用例自身优先级走常规 FAIL_LEVEL 映射——族内 severity 不齐(「导出只导当前页」是确定的 Critical,「截断没 tooltip」只是 Important),**整族锁 Critical 会把后者拔高成阻断项**。⛔ 勿把它加进 `gen_report.py` 的 `CRITICAL_FAMILY_MARKERS` |

> **★用例族锁定 Critical 的执行侧含义(注意 `[还原度]` 不在其中):** `[回归]`、`[PRD存在性]` 与 `[文案一致性]` 用例族失败时,缺陷等级**锁 Critical**,覆盖"按优先级映射(P0→P1…)"的常规逻辑——即便用例本身是 P2,这三类用例族一旦失败也判 Critical。**环境类 `block_reason`(driver-missing / driver-hung / precondition-unmet / network-error / env-unavailable / account-invalid)一律不在此列**——环境没起来不算产品缺陷(不算真失败)。gen_report.py 已内建该锁定(FAIL_LEVEL 映射前先判用例族)。
