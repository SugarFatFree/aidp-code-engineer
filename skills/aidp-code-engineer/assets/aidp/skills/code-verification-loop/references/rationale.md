# 维护者说明：关键约定的根因

> 本文件只给**维护本 SKILL 的人**看，执行验收时不必读。`SKILL.md` 正文只写现行行为，
> 「为什么这样定、改回去会怎样」集中记在这里，避免正文堆积历史对比。

## 1. 全程静态、视觉类回检不得写成「跑起来看」

- **实际发生过的事故**：验收 Agent 为「确认 UI」自作主张执行 `npx vite`，抢占端口、与开发者已在运行的服务冲突、把开发机拖卡。验收 Agent 与开发者共用同一台机器，起服务是有外部副作用的动作。
- **直接诱因**：维度 4 的回检一度写成「跑起来逐页截图比对，无法跑起来时按 DOM 静态比对」——把静态比对降格为退路，等于在文档里教 AI 先起服务。
- **现行口径**：维度 4「视觉还原度」「内容 + 操作逻辑完整性」的回检一律纯静态（读样式 token / DOM 结构 / 原型源码对读），静态判不了的在报告里标注转 `/sprint-aiauto-test`。⛔ 不要把「跑起来看」以任何形式（含「作为首选、静态作退路」）写回任何维度。

## 2. Step 4 不内联报告示例

- **根因**：SKILL.md 内联的两份报告示例与 `assets/verification-report.md` 脱节（缺「0. 静态基线门」「6b 样式等价」「维度 9」，还引用了不存在的小节）。同一份模板两处维护必然漂移。
- **现行口径**：响应内呈现与落盘一律以 `assets/verification-report.md` / `assets/issue-list.md` 为单一信源，SKILL.md 只写要点。

## 3. 「被测项目根」一格不写「其余 N 个维度」

- **根因**：维度数一增删，这个数字就腐化——实际出现过停在「11」而漏算维度 15 的情况。
- **现行口径**：只写「除这四个委派式维度外的其余维度」，不写具体数字。

## 4. `mode = verify-only`

- **根因**：本 SKILL 作为编排流程一环被调用时，代码已由上游开发命令完成，修复另有归口（例如由独立的缺陷修复命令处理）。若仍按 `loop` 执行，会再创建 Agent1 修改源码，与编排层的修复归口冲突，且多轮循环让编排层无法拿到一份确定的单轮结论。
- **现行口径**：`verify-only` 跳过 Step 1/2/5、单轮结束，只交付「结论 + 维度汇总表 + 问题清单」；非缺省值只由编排层传入，独立调用一律按 `loop`，避免 Agent 因「代码看起来已写完」自行改走只验不修、把本该修复的问题留在原地。
- **verify-only 的四条边界**：① 结论判据取「无 Critical 且无 Important」，与 `loop` 的循环终止条件同口径——否则同一份代码两种模式结论不同；② 维度 0 失败不短路：verify-only 只有一轮、修复归调用方，短路会交出残缺清单，修完再验又冒出一批；③ 汇总表多一个 `未执行（原因）` 状态，且必配一条 Important「本项未核验」——没有它，「执行不了」只能在 `Pass`/`Fail`/`不适用` 里三选一，任选其一都是失真（`不适用` 尤其会被读成「门控跳过、无需关心」）；④ 基线一律取改动前——verify-only 时代码已改完，沿用 `loop` 的「首轮记存量作基线」会把本次引入的错误整批吞成存量。未知 `mode` 值报错而非回落 `loop`：回落会在编排层传错值时静默改源码。
- **守护**：`tests/test_mode_contract.py` 断言 SKILL.md 含 `mode` 入参与缺省 `loop`、verify-only 契约要素（跳过 Step 1/2、不进入修复循环、结论判据、未执行状态、基线取改动前、未知值报错、输出契约字段），并断言 `assets/issue-list.md` / `assets/verification-report.md` 的 loop 专属指令按 mode 分支、问题条目含 `证据` / `维度` 字段；均自带变异测试（删掉任一要素即红）。

## 5. `{{AIDP_HOME}}` 路径占位

- **根因**：本 SKILL 会被逐字节下发到不同 Agent 工具链的项目里，运行根随工具链不同（对照表见 `SKILL.md`「运行路径约定」）。写死某一个目录名会让其它工具链下的委派脚本「找不到 → 标不适用」，失效方向是假绿；让 SKILL 自行探测运行根则会出现「两个目录都在时取哪个」的歧义，且判定散落多处必然漂移。
- **现行口径**：运行根由**安装方渲染** `{{AIDP_HOME}}`、SKILL 不探测；正文一律写 `{{AIDP_HOME}}/...`（相对被测项目根、命令在被测项目根下执行），⛔ 不与「被测项目根 + 斜杠 + 占位符」的前缀写法混写。安装器拒收写死「另一个」运行根 + 受管目录的行，对照表行须带 `runtime-path-ignore:` 标注；守护 `tests/test_open_source_distribution.py`。

## 6. 维度 2A 对 `DEV_MOCK` 的豁免

- **根因**：2A 的 `scan_mock_data.py --third-party-mode` 早先只豁免 `THIRD_PARTY_MOCK` 标注块，于是 dev-execution-planner 推荐的两种 `DEV_MOCK` 写法（axios 拦截器 / MSW）在 2A 照样判 Critical + exit 1——「照着上游示例写会被本 SKILL 的扫描器判 Critical」，只是从 2B 换到了 2A。
- **现行口径**：字段完整（`since` / `owner` / `REMOVE_WHEN`）的 `DEV_MOCK` 块同样豁免 2A、转交 2B；缺字段的裸标记买不到豁免（否则「写个标记就能关掉 2A」是后门）；该豁免不受「真实 vendor SDK 并存」条件影响。
