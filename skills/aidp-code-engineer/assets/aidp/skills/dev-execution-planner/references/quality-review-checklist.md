## QR 变更范围裁剪协议（Δ 协议）

> **解决什么：** 生成侧已支持 prompt 驱动的增量，但 QR 侧没有对应概念——补充几个 Task，14 维度仍按全量规格核对整份计划。

### 入参

调用方可在 QR 派发 prompt 里传 **`qr_delta_scope`**：本轮变更的 **Phase / Task / 文档清单**（自然语言即可，须可核对到具体 Task 编号或文件）。**不传 = 全量**，与协议上线前一致。

### 三档裁剪（对照上表最后一列）

| 档 | 语义核对怎么做 | 报告怎么写 |
| :- | :- | :- |
| **Δ** | 只对 Δ 内的 Task/Phase 逐条核对，标准不降 | Δ 外标 `前滚（未变更）` + **写明依据的上一轮 QR 报告** |
| **全量** | 无论 Δ 多小都全量核对 | 恒标 `全量` |
| **基线缩放** | 覆盖度类：分母换成 Δ 内元素集合 | **写明分母口径**（「分母 = 本轮 6 个 Task，非全量 43 个」） |

### 四条安全网（缺一不可）

1. **语义/口径类变更强制扩散**：命中「语义 / 口径 / 单位 / 默认值 / 状态机 / 权限范围变更（无新增实体）」或跨版本作废判定 → 受影响 Phase/Task **强制并入 Δ**，即便无文件命中。
2. **共享单元传播**：变更落在**跨 Task 共享单元**（公共基础设施 / 基类实体 / 共享 DTO / 全局配置 / 数据库表结构）→ **所有依赖它的 Task 并入 Δ**。宁可多算，绝不漏传播。
3. **全量档不可裁剪**（★ 与下游原始提议的唯一实质分歧）。
4. **算不出 Δ 就退回全量**并在报告首行注明退回原因。⛔ 严禁猜一个 Δ。

> **★ 为什么本 SKILL 的「全量」档必须包含维度 6 和 14：**
> 维度 6「依赖链条」查的是**有没有环、前置是否闭合** —— 环是**新 Task 与旧 Task**一起构成的，
> 只看 Δ 内部永远看不到；维度 14「EPIC 完整性」查的是**端到端是否缺端**，
> 而增量最典型的缺陷就是「补了后端 Task、忘了前端那一端」。**把这两个纳入裁剪，等于精准地关掉增量最需要的两道门。**
> 同理维度 7（框架/中间件是全局的）、10/11（分配与拆分是全局的）、13（清单是全局的）。

### QR 执行台账（报告强制段落）

报告**必须**含逐维度台账，否则调用方拿到的只是结论，无法判断某项是「过了」还是「没跑」：

| 维度 | 本轮范围 | 机器门退出码 | 语义结论 | 依据 |
| :-: | :-: | :-: | :-: | :- |
| 3 | Δ（T-07~T-09） | `check_task_granularity.py` = 0 | 通过 | — |
| 6 | 全量 | — | 通过 | 全量档：环由新旧 Task 共同构成 |
| 10 | **N/A** | — | 未触发 | **单用户模式**（条件维度，未触发也留行） |
| 11 | **N/A** | `check_doc_split.py` = 0 (`skipped:true`) | 未触发 | **单文件模式** |
| 2 | 前滚（未变更） | — | 前滚 | 依据 2026-08-20 第 1 轮 QR 报告 |

**四条硬要求：**
- **14 行一行不少**——**条件维度 10 / 11 未触发时照样留行**，写明 `N/A + 触发条件为何不满足`。
  这正是下游反馈的痛点：现在只拿得到结论，分不清「过了」还是「压根没跑」。
- 条件维度的 `skipped:true` 属**跳过不是通过**，台账里必须写成 `N/A`，⛔ 不得记为「通过」。
- 标 `前滚` 的行**必须**写明依据的上一轮报告；写不出来一律按**未跑**处理、退回该维度全量核对。
- 机器门那一列**照抄退出码**，不写「通过」二字——退出码是证据，「通过」是结论。

### 14 维度检查清单(始终必查 12 项 + 条件触发 2 项)

#### 检查项 1:三方一致性深度核验

**检查目标:** 以 PRD 为最高准则,核验详细设计和执行计划的一致性。

**必须核验的维度:**
- **PRD → 详细设计覆盖度**:详细设计是否完全覆盖 PRD 的所有功能点,无遗漏
- **详细设计 → 执行计划覆盖度**:执行计划是否覆盖详细设计的所有接口、数据表、业务逻辑
- **冲突项识别**:
  - PRD 要求实时同步,设计采用异步延迟 → 冲突
  - PRD 要求强一致性,设计采用最终一致性 → 冲突
  - PRD 要求的字段,设计中缺失或类型不一致 → 冲突
- **冲突标记**:发现冲突项必须在执行计划中显式标记,不得隐藏

**不通过标志:** PRD 第 N 条功规点在执行计划中无对应任务;或 PRD 与设计冲突但计划未标注冲突。

---

#### 检查项 2:详细设计完备性评估

**检查目标:** 在生成计划前,检查详细设计是否完备。

**必须包含的核心内容:**
- **数据库 Schema**:所有表的 DDL 定义、索引、约束
- **接口定义**:所有接口的 Method、Path、Request、Response、错误码
- **关键算法逻辑**:核心业务算法的伪代码或流程图(如订单计算、推荐算法)
- **外部依赖**:第三方系统集成的协议和降级方案
- **非功能需求实现**:性能、安全、审计的技术方案

**不通过处理:** 如详细设计缺失核心技术链路(如无接口定义、无数据库 Schema),Skill 必须**报错中断**,输出提示:

```
❌ 由于详细设计文档不完善,无法生成具体的 Command 级执行计划。

缺失项:
- [ ] 数据库表 XXX 的 DDL 定义
- [ ] 接口 YYY 的 Request/Response 定义
- [ ] 算法 ZZZ 的逻辑描述

请先补充详细设计文档后再生成执行计划。
```

#### 检查项 3:迭代粒度与 AIDP 范式对齐

**检查目标:** 研发执行计划的阶段划分符合 AIDP 范式,且**每个 Task 必须对应一个子功能(而非一个功能模块/页面)**。

**必须核验的维度:**
- **阶段划分**:是否符合"基础架构层 → 数据层 → 业务逻辑层 → 接口层 → 前端展示层 → 测试"的 AIDP 范式
- **任务命名规范**:Task 编号格式 `{Phase}.{Seq}`,命名动词统一(创建/实现/开发/联调/测试)
- **目录结构规范**:每个 Task 的产出物路径符合项目约定
  - Spring Boot:分层优先(`controller/`、`service/`、`mapper/`、`entity/`)
  - Go:分层优先(`handler/`、`service/`、`repository/`)
  - 前端:`views/`、`components/`、`api/`、`store/`
- **产出物类型**:每个 Task 的产出物明确(代码文件 / DDL / 配置 / 文档)
- **🔴 子功能粒度**(SKILL.md「拆分粒度强制要求」落地):
  - 每个 B.2 接口对应一个独立 Task(`GET /user/list`、`POST /user`、`PUT /user/{id}`、`DELETE /user/{id}` 至少 4 个 Task)
  - 每张 A.3 数据表对应独立 DDL+Entity+Mapper Task(严禁合并"用户域所有表")
  - 每个 PRD 功规点(五-N.x)对应独立 Task(分页/搜索/排序是 3 个 Task)
  - 每个独立页面/弹窗/复杂业务组件对应独立 Task(列表页/新增弹窗/编辑弹窗/详情抽屉/删除确认 ≥ 5 个 Task)
  - 每条 B.5 状态转移或 B.1 校验规则对应独立 Task
- **聚合性词汇扫描**:Task 标题或描述中出现以下词汇,基本可判定粒度过粗:
  - "等"、"及"、"相关"、"一系列"、"所有"、"全部"、"整体"
  - "用户管理后端开发"、"订单管理前端页面"、"实现所有接口"等大颗粒命名
- **三选一合格判定**(每个 Task 必须满足至少一项):
  1. 可独立交付(独立 PR / code review / 测试)
  2. 单一上游来源(只引用 ≤ 100 行的精确章节)
  3. AI 一次完成(单次 AI 调用产生完整产物)

**不通过标志(任一即不通过):**
- Phase 顺序倒置(如 Phase 3 接口层在 Phase 2 业务逻辑层之前)
- Task 产出路径与项目结构不一致
- 单个 Task 跨越多个 B.2 接口(如"实现用户增删改查 4 个接口"应拆 4 个 Task)
- 单个 Task 涵盖多张表的 DDL+Entity+Mapper
- Task 标题含"等/及/相关/一系列/所有/全部/整体"等聚合性词汇且实际跨越多个子功能
- Task 抬头的"四源引用"指向的章节范围超过 100 行(说明该 Task 跨越了多个子功能)
- 多个 Task 扁平并列无 `**依赖**:Task X.Y` 串联,不形成依赖图

**自动化辅助:** `scripts/check_task_granularity.py` 扫描研发执行计划文件,识别聚合性词汇 + 引用章节跨度 + 同类 Task 合并嫌疑,输出疑似粗粒度 Task 清单。

```bash
python3 <SKILL_DIR>/scripts/check_task_granularity.py <研发执行计划路径>
python3 <SKILL_DIR>/scripts/check_task_granularity.py <研发执行计划路径> --json
```

#### 检查项 4:指令化(Command-Driven)检查

**检查目标:** 每一步研发执行计划是否都挂载了具体的、可直接运行的指令,且**必须按 5 级优先级**选择:`AIDP 命令/范式 > 项目 .claude/ 资源 > 系统 Claude Code 资源 > 通用工具 > Shell`。  <!-- runtime-path-ignore: 指 Agent 自身目录这一概念，非运行契约路径，两包均保持原样 -->

**指令来源优先级(检查时必须核验):**

1. **项目 AIDP 命令/范式文档**(L1,最高优先级) — 如 `aidp gen:mapper`、`aidp scaffold:controller`
2. **项目 `.claude/` 下的 commands/skills/plugins/agents/mcp**(L2) — 如项目级 `/项目slash`、项目级 skill、项目级 agent、项目级 MCP server  <!-- runtime-path-ignore: 指 Agent 自身目录这一概念，非运行契约路径，两包均保持原样 -->
3. **系统 Claude Code 的 commands/skills/plugins/agents/mcp**(L3) — 如 `/dev-logic-architect`、`/code-verification-loop`、`/api-tester`、全局 plugin、全局 agent、全局 MCP server
4. **通用构建/代码生成工具**(L4) — 如 `mvn archetype:generate`、`mybatis-plus-generator`、`pnpm create vite`、`go mod init`
5. **Shell / 脚本**(L5,兜底) — 如 `bash scripts/init-db.sh`、`git commit -m "..."`、`curl xxx`

**自动化辅助(L1 层扫描,复核"可用指令清单"是否遗漏 AIDP 资源):**

#### 检查项 9:详细设计一致性深度核验(强制)

**检查目标:** 执行计划中所有数据库 SQL、接口地址、字段定义、枚举值、错误码、状态机、校验规则等关键技术要素,必须与详细设计文档严格一致,不得遗漏、不得自行修改、不得杜撰。**同时必须满足"零冗余"原则:这些技术要素不得在 Task 中重复抄写,只能以"参考设计 `<章节+行号>`"方式引用**。

**9.1 数据库 SQL 一致性**

对 Phase 1 的每个数据库 Task,核验:
- **表名**:是否与详细设计 `A.3 数据定义` 章节定义的表名一致
- **字段清单**:是否完整包含设计中定义的所有字段,无遗漏、无多余
- **字段名**:命名(如下划线/驼峰)必须与设计完全一致
- **字段类型**:VARCHAR 长度、DECIMAL 精度、INT 位数等必须与设计一致
- **NOT NULL 约束**:哪些字段 NOT NULL、哪些允许 NULL,必须与设计一致(尤其要遵守"字段宽容原则")
- **DEFAULT 值**:默认值必须与设计一致(如 `status DEFAULT 1`)
- **索引**:索引字段、索引类型(UNIQUE/普通)、联合索引顺序必须与设计一致
- **外键约束**:是否建立外键、级联规则必须与设计一致
- **字段注释**:字段 COMMENT 应与设计中的"业务含义"一致
- **💰 金额字段类型守恒**:设计 `A.3` 金额字段为 `BIGINT`(按最小货币单位存储)时,对应 Entity/Mapper/DTO/前端类型 Task 必须保持整数类型(Java `Long`、Go `int64`、Kotlin `Long`、TypeScript `string`),**严禁**改为 `BigDecimal`/`number`/`float`/`double`(对应 SKILL.md 约束 7)

**9.1.1 SQL 路径透传(对接 dev-logic-architect Module D 铁律)**

研发执行计划 Task 引用的 SQL 路径必须与详细设计 Module D 规定的命名规范一致:
- **路径格式**:`{SQL脚本目录}/v{版本号}/{NN}_{中文描述}.sql`(如 `sql/v1.2.0/01_用户表DDL.sql`)
- **英文通用名禁止**:`init.sql` / `schema.sql` / `migration.sql` / `baseline.sql` / `setup.sql` 一律不允许
- **版本子目录约束**:必须含 `/v{版本号}/` 子目录,体现 Module D 的版本隔离铁律
- **中文命名 + NN_ 序号**:文件名必须 `{NN}_{中文描述}.sql`,**严禁**英文/拼音/kebab-case
- **版本号一致**:同一研发执行计划内,所有 SQL 引用的版本号应一致(允许仅一个版本)
- **99_ 回滚配套**:若任一 SQL 为 `99_*.sql`,文件名必须含「回滚」二字

**自动化核验(必跑):**

```bash
python3 <SKILL_DIR>/scripts/check_sql_path_handoff.py <研发执行计划路径>
# 退出码 0 = 通过(或无 SQL 引用), 1 = 不通过, 2 = 输入路径错误(修正后重跑)
```

**9.2 接口地址一致性**

对 Phase 3 的每个接口 Task,核验:
- **接口路径**:Method + 完整 URL(含 context-path + 资源路径 + 路径参数)必须与详细设计 `B.2 API 契约定义` 逐字符一致
- **HTTP 方法**:GET/POST/PUT/DELETE/PATCH 必须一致
- **路径参数**:`/user/{id}` 中的 `{id}` 命名必须与设计一致
- **Query 参数名**:`?pageNum=1&pageSize=20` 的参数名必须与设计一致(如 `page` vs `pageNum`)

**9.3 请求/返回字段一致性**

- **Request Body 字段名**:驼峰/下划线风格、字段命名必须与设计一致(如 `userName` vs `username`)
- **Request Body 字段类型**:String/Integer/Long/Boolean/Array/Object 必须与设计一致
- **Request Body 必填项**:哪些字段必填、哪些可选必须与设计一致
- **Response 数据结构**:嵌套层级、字段名、类型必须与设计 `B.2` 的响应示例完全一致
- **分页结构**:`{total, list, pageNum, pageSize}` 的字段命名必须与设计一致
- **字段校验规则**:长度、正则、数值范围必须与设计一致

**9.4 枚举值一致性**

- **枚举编码**:如订单状态 `PENDING_PAYMENT`/`PAID`/`CANCELED` 必须与设计 `A.3` 或 `B.5 状态机` 中定义一致
- **枚举映射**:前后端的枚举值映射关系(如后端 `1` 映射前端 `"启用"`)必须与设计一致
- **字典表**:字典编码、显示文本必须与设计或 PRD 七、字典枚举表一致

**9.5 错误码一致性**

- **HTTP 状态码**:200/201/400/401/403/404/500 的使用场景必须与设计一致
- **业务错误码**:如 `40001 参数校验失败`、`40101 登录已过期` 必须与设计 `B.2 错误码定义` 一致
- **错误消息**:中文错误提示文案必须与设计或 PRD 一致(**例外**:第三方透传的业务错误文案来自第三方运行时响应、非本地固定文案,不在此本地一致性核验范围,见 9.7「第三方业务错误透传」)

**9.6 状态机一致性**

- **状态枚举**:所有业务状态必须与设计 `B.5 状态机模型` 定义一致
- **状态迁移路径**:合法迁移路径必须与设计状态机图一致
- **迁移触发条件**:触发状态变更的操作/事件必须与设计一致
- **不可迁移约束**:如"已上架不可编辑"等约束必须在代码中实现

**9.7 异常处理与性能一致性**

- **幂等性方案**:是否使用幂等令牌/唯一索引,必须与设计 `B.3 异常处理` 一致
- **★第三方业务错误透传**:涉及调用第三方接口的 Task,其异常处理须承接设计检查项 4 的透传契约——第三方返回**业务错误**(业务码 + 用户向 message)须透传前端、不得替换成通用文案;仅**系统/基础设施错误**(超时/5xx/连接失败)兜底。相关对接 Task 的验收标准须含「第三方业务错误透传」检查点(对接检查项 8)
- **并发锁方案**:乐观锁/悲观锁/分布式锁选型必须与设计一致
- **缓存策略**:缓存 Key、TTL、失效策略必须与设计 `B.4 性能与边界` 一致
- **索引设计**:是否与设计 `A.3` 要求的索引一致
- **分页策略**:传统分页/游标分页必须与设计一致
- **缓存确认 → 独立 Task**:仅当详细设计 `A.2` 存在「缓存方案」子章节时,执行计划才允许出现缓存相关 Task(且必须按 SKILL.md 核心原则第 10 条拆为 中间件配置/缓存层封装/失效一致性/监控告警 4 类独立 Task);设计未声明缓存方案时出现"添加 Redis 缓存"等自创缓存 Task 即不通过

**9.8 接口可用性核验(「✅ 沿用已有」接口穿透 Service 实现层,对应 `flow-execution.md` >「第一步半之二」)**

- 详细设计标注「✅ 沿用已有」的每个接口,执行计划必须有 Service 实现层核验结论(或附「接口可用性核验报告」附录)
- 🔧 占位实现(throw 5xx / return null)的接口,Phase 3 必须有"补全 XxxService 业务实现"Task,对应 Phase 4 前端 Task 标注依赖
- ❌ `@Deprecated` 接口必须在 Phase 3 新建接口 Task,严禁继续沿用
- 自动化核验:`python3 <SKILL_DIR>/scripts/check_service_impl_stub.py <代码根目录>`(⚠️ 退出码口径:**抛 5xx / 未实现等占位 = Critical → exit 1**;**仅 `@Deprecated` 标注(无 throw)= Important → 默认 exit 0**,须加 `--strict` 才硬拦。检查项 9.8 要拦的「`@Deprecated` 接口必须在 Phase 3 新建 Task」恰好落在 exit 0 那一档——**只看退出码会漏**,须读文本/`--json` 明细)+ `python3 <SKILL_DIR>/scripts/check_third_party_dep_reverse.py <代码根目录>`(第三方依赖反向兜底)

**9.9 字段处置 → Task 拆分承接(对接 PRD「需求字段→处置对照表」+ dev-logic-architect `B.2` 字段比对门,SKILL.md 核心原则第 11 条)**

> 约定22 字段契约四级级联中本层为 L3。详细设计承接的「需求字段→处置对照表」里凡处置非「保留」的字段,执行计划必须显式承接,严禁静默当保留字段排进常规 Task。

- **前端计算还原**:对照表中处置为「前端计算还原」的字段,执行计划必须有**独立前端计算 Task**(实现派生逻辑 + 引用设计计算规则章节行号);缺失,或把该派生字段当后端返回字段直接排进列表/表单渲染 Task,即不通过
- **请第三方补**:处置为「请第三方补」的字段,必须**关联到第三方对接 Task**(纳入第三方依赖机制),不得假定本系统接口已含该字段
- **裁剪**:处置为「裁剪」的字段,执行计划**不得静默**当保留字段排进接口/前端 Task;须登记"已裁剪(原因 + 产品确认状态)";标「待产品确认」者须标注"⚠️ 字段处置待澄清"暂缓相关 Task
- **对照表缺失**:详细设计无「需求字段→处置对照表」时,提示回 dev-logic-architect 补齐(关联检查项 12 上游引用核验),避免计算/第三方补字段漏拆独立 Task

**检查方法:**

检查 Agent 必须**逐字段逐接口**对比执行计划中的引用内容与详细设计文档:
1. 从执行计划的每个 Task 中提取其 `设计来源` 指向的章节
2. 读取详细设计文档对应章节的定义
3. 将 Task 的执行步骤、产出物、验收标准中涉及的 SQL/接口/字段/枚举等要素,与设计定义逐项对照
4. 发现任何不一致必须列出:字段名/类型/长度差异、路径差异、参数名差异、枚举值差异等

**不通过标志:**
- Task 1.3 建表 SQL 中的字段清单少于设计 `A.3` 定义的字段(遗漏)
- Task 3.5 接口路径是 `/api/v1/user/list`,但设计 `B.2` 定义为 `/api/user/list`(版本号不一致)
- Task 3.8 Request Body 字段是 `userName`,但设计定义为 `username`(命名风格不一致)
- Task 2.4 Service 使用的状态枚举值与设计 `B.5` 定义不同(如设计是 `PAID`,代码是 `PAYED`)
- Task 4.3 前端解析分页字段为 `{total, records}`,但设计返回为 `{total, list}`(字段名不一致)
- Task 1.5 数据库索引遗漏了设计要求的联合索引(未创建 `idx_user_status_time`)
- Task 的"设计来源"字段为空或仅引用文件名未标注章节和行号范围
- **【冗余违规】** Task 描述中复述了详细设计已定义的字段清单、接口字段、枚举值、SQL 约束等技术细节(如 Task 1.3 中列出了 `biz_work_order` 的完整字段表,或 Task 4.2 中列出了表格的全部列名)。应改为"按设计 `<章节+行号>` 实施"
- 设计 `A.3` 金额字段为 `BIGINT`,但 Entity/DTO/前端 Task 中类型写为 `BigDecimal`/`number`(违反金额字段类型守恒)
- 设计「需求字段→处置对照表」标注某字段「前端计算还原」,但执行计划无对应独立前端计算 Task(漏拆),或把该派生字段当后端返回字段直接排进列表渲染 Task;处置「请第三方补」却未关联第三方对接 Task;处置「裁剪」字段静默回流到接口/前端 Task 当保留字段(违反核心原则 11 字段处置承接)
- 详细设计未声明「缓存方案」,但执行计划自创"添加 Redis 缓存"等缓存 Task;或已声明缓存方案但缓存逻辑混入业务接口 Task 未独立拆分
