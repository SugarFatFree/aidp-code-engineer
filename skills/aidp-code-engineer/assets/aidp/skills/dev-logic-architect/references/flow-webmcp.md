# WebMCP 前端能力的设计期产出（条件启用 · 维度 33 判据全文）

> **本文件只在调用方传入 `webmcp_enabled: true` 时适用。** 为 `false` 或未传时，本文件描述的一切
> ——六项产出、两条风险登记、三条禁令、维度 33——**整体不适用**：不产出、不留空章节、不写
> 「本项目不适用 WebMCP」之类的占位段、不在 QR 报告里占一行。

---

## 一、这是什么（先对齐概念，否则六项产出会写歪）

**WebMCP = 网页把自身能力以「带 JSON Schema 的函数」形式登记给浏览器**，能在该页面执行 JS 的
AI Agent（浏览器内置 AI / 外部 Agent 经调试协议 / 浏览器扩展 / 页面自带助手）可直接调用业务函数，
不必靠无障碍树快照猜 DOM。

**⚠️ 它不是网络协议、没有传输层。** 消费方必须先有办法进入该页面的 JS 上下文。它提升的是
「**已经能操作该页面**的 Agent」的调用效率与准确性，**不为远端 Agent 新增接入通道**。设计里把它
写成「对外开放的一套 API」是根本性误解——会一路错到鉴权、限流、网关这些根本不存在的章节上。

由此派生一条贯穿全部产出的安全假设：**调用方不可信**。能力入口是页面 JS 上下文里的普通对象，
任何能在本页执行 JS 的主体都能调它。所以确认门、脱敏、不扩权这三件事，判据是「**对任意调用方
都成立**」，不是「助手会守规矩」。

## 二、启用判定由调用方负责，本 SKILL 不自行探测（硬前提）

| 入参 | 形态 | 说明 |
| :- | :- | :- |
| `webmcp_enabled` | `true` / `false` | **唯一开关**。为 `false` 或未传 → 本文件整体不适用 |
| `webmcp_entry_symbols` | 数组 | 该项目**实测**的能力入口标识符。⚠️ 挂载位置已经迁移过一次、规范仍在演进，**写死任何一个名字都会过期** |
| `webmcp_launch_command` | 字符串 | 带参浏览器的完整启动命令（供下游用例与执行器复现同一环境） |

**⛔ 严禁在本 SKILL 内自行探测是否启用**——不要 grep PRD 找关键词、不要扫代码里有没有相关
标识符。**Why：判定散落多处必然漂移，而一处判错就会给未启用的项目凭空长出告警和产物位。**
判定权归调用方，本 SKILL 只消费该输入。

## 三、六项强制产出

`webmcp_enabled: true` 时，详细设计须**额外**产出以下六项。产出位置随规模档位落在主设计文档的
对应章节或独立小节，但**六项一项不能少**。

### 产出 1：分层落点表

| 层 | 落在哪个文件 | 职责 |
| :- | :- | :- |
| 适配层 | | 与浏览器能力入口对接的**唯一**一处（**设计期只要求把它落到一个文件**；「实现里是不是真的只有一处」由下游 code-verification-loop 的静态硬门查，不在本维度） |
| 工具注册表 | | 工具的语义/入参/出参声明集中处 |
| 接入层 | | 何时登记、登记谁、与页面生命周期的关系 |
| 确认门 | | 写操作的二次确认在哪实现 |
| 界面 | | 用户可见的开关/状态提示落在哪个组件 |

**Why 要按文件写死**：这五层里最容易散开的是适配层。一旦有第二处直接碰能力入口，后面的
「停用能否真正生效」「规范迁移时改几处」全部失控。

### 产出 2：工具清单表

固定列：`| 工具语义 | 类别 | 入参 | 出参要点 | 数据来源 |`

- **类别只有三档：只读 / 本地写 / 外发写。** 三档决定后面的确认门与错误契约强度，不是标签。
- 「数据来源」写清取自哪个既有接口或既有状态，**不新造数据通道**。

### 产出 3：错误契约表

结构化失败结果的字段与文案。**文案的分与合取决于是否泄露信息**，这是本表唯一容易做错的地方：

| 情形 | 处置 | Why |
| :- | :- | :- |
| 越权 ≡ 不存在 | **合并成同一条文案** | 文案不同 = 给出一条「探测某资源是否存在」的旁路 |
| 「指名的取不到」≠「一个都没选」 | **分开** | 两者是完全不同的用户处境，合并会让人无从下手 |

### 产出 4：三层开关与时序图

`L1 浏览器能力（feature-detect）→ L2 服务端配置 → L3 页面总开关`，三者是 **AND** 关系，
并画出登记时序（谁先就绪、登记在哪一步发生）。**时序必须画**——「先登记后撤销」这一类缺陷
只在时序图上看得出来（详见产出 6 与下游验收维度）。

### 产出 5：运行前提表

| 项 | 内容 |
| :- | :- |
| secure context 三种放行手段 | 启动参数 / 企业策略 / 图形界面开关 |
| 两个开关的**作用域差异** | 一个仅对指定 origin 生效，另一个是**全局**的 |

### 产出 6：ADR

引入**非标准轨**的浏览器协议属架构级决策，须走 ADR，且**必须含**：

- 替代方案（不引入它时怎么办）；
- **回归路径**——规范变动或该能力下线时如何退回。**这条不能省**：它是非标准轨，写死当前形态
  等于把回退成本推给未来的人。

## 四、两条必须登记进 **Module E 待澄清问题清单**的结论（不能只写在正文里）

> ⚠️ **落点写死为 Module E，不要写成「风险段」** —— 本 SKILL 的输出模块只有 Module A~E，
> **没有独立的「风险」章节**（单文件 = 文末 `Module E: 待澄清问题清单`；多文件 =
> `99_待澄清问题清单.md`）。两条结论按 Module E 的既有格式登记为 **`D-NNN` 条目**，
> 否则会反过来被维度 16「待澄清问题清单完整性」判不通过。

### 风险 1：实验特性开关是**全局**的

打开它会打开浏览器**全部**实验特性，且**无对应企业策略可精细控制**。

**这直接决定适用范围：开发机 / 小范围试点。⛔ 不得把它写成可全员推广的特性。**

### 风险 2：`http://localhost` 本身就算 secure context

按 W3C Secure Contexts 规范，`localhost` 是 secure context 的特例。所以：**本地开发一切正常、
部署到 HTTP 测试环境才崩。** 设计里必须点明「**验收须在真实部署环境做**」。

> 下游真实踩过：同一根因导致 3 个 Critical 里的 2 个。本地全绿 → 部署即挂，是这条的固定形态。

## 五、三条「不要做」（设计阶段最容易越界的三处）

1. **⛔ 不为它新造后端接口。** 服务端开关挂到项目**已有**的前端配置下发 / bootstrap / 站点信息
   接口上，多加一个布尔字段即可；确实没有此类接口时才新增。**⛔ 不新增表、不新增错误码。**
2. **⛔ 不新增独立命令 / 独立流程。** 它是前端能力的一个**可选维度**，融进既有的需求 → 设计 →
   计划 → 自测链路，不另起一条并行链路。
3. **⛔ 服务端开关必须运行时可变。** 改配置后**无需重新构建前端**即生效；用配置中心的项目须支持
   热刷新。**严禁用构建期常量 / 环境专属守卫实现**——那会让开关要么关不掉、要么要重新发版才能开。
   （与核心原则 14「第三方接口临时 Mock 运行时可控」同一条工程判据：**构建期决定的开关不是开关**。）
