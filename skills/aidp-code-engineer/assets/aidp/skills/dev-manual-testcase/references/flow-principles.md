## ⚠️ 数据一致性与溯源原则（Critical）

**自测用例必须基于实际代码和产品原型,严禁推测或臆造：**

### 1. 与实际代码保持一致（已有代码时）
如果项目已有正式开发的代码,用例中的以下信息**必须从实际代码中提取**,不得推测：
- **URL 路径**：从路由配置文件/代码中读取实际路径（如 `/user/list`、`/console/billing`）
- **页面标题/菜单文案**：从前端代码/模板中读取实际文案
- **按钮文案/表单标签**：从前端代码中读取实际 label/placeholder
- **Toast/错误提示文案**：从前端代码/国际化文件中读取实际提示语
- **状态枚举值**：从后端枚举定义/前端常量中读取实际值
- **字段校验规则**：从前端校验代码/后端校验逻辑中读取实际规则

**检测方法**（四类来源，**具体文件位置随技术栈而定，按需加载 `references/stack-*.md`**）：
1. 前端路由配置 —— 页面入口与路径
2. 前端页面组件 —— 按钮/表单标签/Toast 的**真实文案**
3. 国际化文件 —— 项目启用 i18n 时**以此为准**（组件里只有 key，用例要写用户看到的中文）
4. 后端枚举与校验提示 —— 枚举 label、错误码提示、`@NotBlank(message=…)`（反向用例预期提示的高价值来源）

> ⚠️ **按被测项目技术栈加载对应文件，勿全量读**：`references/stack-vue.md`（`vue-router` / `el-table-column` 的 `label` / `src/i18n/`）、`references/stack-react.md`（react-router 或 Next 文件路由 / Antd `columns.title` **不是 `dataIndex`** / `src/locales/`）、`references/stack-java-spring.md`（`*Enum.java` 的 `label` 而非 `code` / 错误码枚举 / DTO 校验 `message`）。索引与边界见 `references/stack-index.md`。

### 3. 内容来源优先级
用例步骤和预期现象的信息来源优先级：
1. **实际代码**（最高优先级）：已有代码时,URL/文案/校验规则等必须从代码中提取
2. **产品原型**：页面布局、交互流程、按钮位置、弹窗样式
3. **PRD 需求文档**：业务规则、字段含义、状态流转、权限矩阵
4. **详细设计**：字段校验规则、枚举值定义、异常处理

**严禁推测**：
- ❌ 推测 URL 路径（如"应该是 `/api/user/list`"）
- ❌ 推测按钮文案（如"应该是'提交'按钮"）
- ❌ 推测错误提示（如"应该提示'操作失败'"）
- ❌ 推测页面跳转（如"应该跳转到列表页"）

**正确做法**：
- ✅ 从路由配置读取：`/user/list`（来自 `router.js` L45）
- ✅ 从原型读取：点击"新增用户"按钮（来自 `user-list.html` L120）

- ✅ 从原型读取：跳转到用户详情页（来自原型页面跳转流程图）

## 原型内容基线为用例生成基准(AIDP 对齐,强制)

> **背景(问题根因):** 以往用例只以 PRD 功规点/功能点为基准生成,原型里**实际画了但 PRD 未逐条列全**的可见元素、交互态、操作逻辑一旦在实现里缺失/走样,**自测用例根本发现不了**——因为用例清单本身就不以原型元素为基准。本章节把用例生成基准**下沉到原型可见内容与操作逻辑**,让"内容/行为缺失"变成测试可发现的偏差。

### 什么是"对齐原型 = 视觉 + 内容 + 操作逻辑 三层"(AIDP 约定4)

- **① 视觉层** — 布局、配色、间距、图标、字号等(本 SKILL 侧重可观察断言,视觉细节以肉眼/截图核对)。
- **② 内容层** — 原型 `code/` 可见的**区块/卡片/表格列/表单字段/筛选项/排序项/按钮及次级操作/空态·加载·错误·成功等交互态/页面跳转**,**一个不许静默漏**。
- **③ 操作逻辑层** — **校验规则与时机、字段联动、条件显隐/禁用、增删改-保存-取消/批量流、二次确认、默认值/初始态、多步步序、错误处理、权限态差异**。

> **规划期铁律(承接上游,用例侧同样遵守):** 原型元素/操作逻辑**未显式标注「裁剪/延期/改为X」→ 默认必须照原型实现**,对应到用例侧就是**默认必须有覆盖用例**;漏写覆盖 = 违规。
>
> **AIDP 约定28 边界:** "用项目已有组件实现"只约束**组件实现选型层**,**不豁免**上述三层对齐——即便某元素用了现成组件,其内容与操作逻辑仍须逐条被用例覆盖 (AIDP 约定28)。

### 消费方式(有则强制消费,无则回退,防臆造)

> **基线已升级为六类逐项清单(AIDP 侧已落地):** 数据字段 / 操作入口 / 统计卡片 / 筛选排序 /
> 空态·加载·错误态 / 二次确认,每项四列 `页面 → 类别 → 元素名 → 处置` + `✓ 已实现` 打勾列。
> **六类分别喂给「第五步之九 通用还原度套件」的哪些模板项**,见
> [`flow-fidelity-suite.md`](./flow-fidelity-suite.md) 第二节的映射表(数据字段→字段守恒、
> 操作入口→按钮守恒、统计卡片→含数字页六条、筛选排序→筛选排序守恒、空态加载错误态→空态与加载态无跳变、
> 二次确认→表单页二次确认)。散文形态的旧基线仍按下面的通用规则消费。

1. **优先消费 AIDP 产物(若上游已产出):**
   - **`原型内容基线.md`**(路径作示例、**自适应项目结构**,如 `docs/design/{version}/原型内容基线.md`):逐页给出「可见元素 + 交互态 + 操作逻辑/交互流」及**处置列**(实现 / 裁剪 / 延期 / 改为X)。**强制作为用例生成基准**——遍历每一处置="实现"的条目,保证元素/交互态/操作逻辑各有 ≥1 条可验证用例。
   - **`DESIGN-MANIFEST.json` / `DESIGN-HANDOFF.md`**(自适应项目结构):读取 **screens / appModules / requiredStates / tokens / flows**——用 `requiredStates` 补齐交互态用例(空态/加载/错误/成功/禁用等),用 `flows` 补齐操作逻辑/交互流用例。
2. **回退(AIDP 产物不存在时):** **直接从原型 `code/` 现场逐页提取**可见元素与操作逻辑,自行在心中(或临时清单里)建立"原型元素 × 交互态 × 操作逻辑"覆盖表,再逐项配用例。**不臆造上游产物、不硬依赖其路径存在。**

### 逐项配用例规则

| 基线条目类别 | 用例要求 |
| :- | :- |
| **处置=实现 的可见元素**(区块/卡片/列/字段/按钮/筛选/排序/跳转) | 至少 1 条可验证用例,预期现象写明该元素**可见 + 文案/位置/交互正确**;表格列/表单字段并入第五步之二逐列核对 |
| **处置=实现 的交互态**(requiredStates:空态/加载/错误/成功/禁用…) | 每个声明的交互态至少 1 条用例触发并断言其可见表现(如"无数据时展示空态插画 + 文案'暂无数据'") |
| **处置=实现 的操作逻辑/交互流**(flows:校验时机/字段联动/条件显隐禁用/保存取消/二次确认/默认值/多步步序/错误处理/权限态) | 每条操作逻辑至少 1 条用例验证其**行为**(如"未选择部门时'保存'按钮置灰"、"选'企业'类型后显示'统一社会信用代码'字段") |
| **处置=裁剪 / 延期 / 改为X 的项** | **不生成正向覆盖用例**,但**必须登记在案不静默漏**——在用例文档"原型内容基线覆盖登记"小节或对应功能点处标注 `原型元素「X」处置=裁剪/延期/改为Y — 不覆盖,原因:<引用约定4三件套(视觉/内容/操作逻辑)对应处置说明>`,溯源指向基线条目。**另对处置=「裁剪 / 延期」的元素,除登记外强制新增一条 `[反向-残留]` 反向断言用例**——用 DSL「**不存在文本"X"**」(`断言(反向):不存在文本"X"`)表达「该元素仍存在则失败」,捕获"该删没删 / 该延没延"的残留(处置=改为X 项按新语义走正向覆盖,不走残留断言) |

> **判定:** 原型内容基线中处置="实现"的元素/交互态/操作逻辑存在既无覆盖用例、又未标注不覆盖原因的,判**覆盖缺口**(折进维度 18,见 QR 维度 18「原型内容基线覆盖度」子条)。**验收语境:用例集能一一对应原型内容基线的"实现"项(元素 + 状态 + 操作流),无遗漏。**

## 测试设计方法论速查(解决"用例偏少、只堆正向、异常/边界/并发漏")

> **完整模板清单(覆盖矩阵全表 + BVA 六点法 + 等价类示例库 + 状态机矩阵 + 并发清单 + 数量基线 + 统计摘要 + 特殊场景清单)见唯一信源 [`references/test-design-methodology.md`](./test-design-methodology.md)。** 生成用例时(第五步 / 第五步之三 / 第七步)必须逐项套用;质量检查维度 18/19 以该文件为对照基准。本速查是入口摘要,**不重复展开、不构成第二信源**。

**① 覆盖矩阵(逐维确认,不适用须标注原因):**
- **正向 9 维:** F1 页面加载 / F2 列表展示 / F3 筛选搜索 / F4 创建 / F5 编辑 / F6 删除 / F7 状态流转(合法迁移)/ F8 导航路由 / F9 交互反馈
- **反向 12 维:** R1 必填校验 / R2 长度格式 / R3 全空白 / R4 网络失败 / R5 空数据 / R6 权限不足 / R7 弹窗三种关闭(按钮/蒙层/ESC)/ R8 服务端错误 / R9 状态约束(非法迁移被拒)/ R10 并发竞态 / R11 安全输入 / R12 依赖/数据源故障注入与降级提示(功能点聚合 ≥2 数据源 / 有兜底返默认值逻辑时:逐数据源注入 500/超时/空返回 → 页面须显式失败提示/partial 标记、禁静默显示 0/空;须与 R5 真空态配对验证"真空 vs 故障静默返空"可区分)
- 每个功能点逐维过一遍,不适用就地标 `R7 不适用(无弹窗)`;只有正向即判缺口。

**② 边界值 BVA(受约束字段):** 数值取 `min-1/min/min+1/max-1/max/max+1 + 0/负/空`;长度取 `空/1/N/N+1/纯空格`;日期取 `边界日/区间外一天/跨年/闰年/起>止`;列表取 `0条/1条/满页临界/超大量`。

**③ 等价类(格式字段):** 手机号/邮箱/URL/身份证/金额/密码等各出「1 条有效类 + 每类无效类各 1 条」(完整枚举见方法论第三节)。

**④ 状态机矩阵:** 每个有状态对象画迁移矩阵——**合法迁移逐条正向用例 + 非法迁移逐条"被拦截"反向用例 + 幂等重复触发**,不止测正向流转。

**⑤ 并发/竞态:** 写操作功能点逐条核对——C1 重复提交 / C2 乐观锁版本冲突 / C3 他人已删后再操作 / C4 锁超时 / C5 多标签页一致性 / C6 并发扣减不超卖(现象用刷新后可见变化断言)。

**⑥ 数量基线 + 优先级(完备性下限):** 简单模块 30–60 条 / 中等 80–150 条 / 复杂 150+ 条;单功能点 ≥3 条(1 正向 + ≥2 反向/边界),列表/表格/表单再 +1 字段逐列核对;P0 约 15–25% / P1 约 45–55% / P2 约 25–35%,**反向用例 ≥ 全量 40%**;低于下限须在统计摘要说明原因。

**⑦ 统计摘要(生成结束必输出):** 文档末尾附「用例统计摘要」(套件数/用例数/优先级分布/正反向占比/特殊场景条数/数量基线核对),模板见方法论第七节,可由 `scripts/check_case_stats.py` 机检。

**⑧ 特殊场景清单(触发条件→必生成用例类型):** 缓存 / Mock 全生命周期 4 阶段 / 第三方对接(成功·降级·回调·超时)/ 已交付字段不全 / 列表表单逐列核对 / 状态机 / 并发 / BVA 字段 / 权限矩阵 / 文件上传 / **跨模块集成闭环** ——逐行核对命中即补,详见方法论第八节。

**⑨ 语义断言提示(配合自动化执行):** 关键断言步骤除自然语言"预期现象"外,可附一行机器可判的语义断言(仍用页面可见文案,禁选择器/字段名),格式 `断言: <表达式>`,反向用例用 `断言(反向): <表达式>`(如 `断言:存在文本"创建成功"` / `断言:列表行数+1` / `断言(反向):存在错误提示"必填"`)。该 DSL 与下游 `auto-test-runner` 的 `usecase-format.md` **统一契约**,唯一信源见方法论「八之二」节;与核心原则 7 一致——只用页面可见信号,禁不可视断言。用于探测交付状态的断言另须登记「失败与合法空态可区分 / 特征只指向目标变更 / 按类型完成阳性对照或登记正向存在性断言 N/A」三项自检,详见方法论「八之二」探测类断言模板。

**⑩ 跨模块集成闭环(供需对称,详见方法论「八之三」+ 第五步之四):** 单模块套件覆盖模块内功能点;**横跨 ≥2 模块/套件的端到端业务闭环**(数据跨模块流转、状态跨模块迁移)须另出**集成用例**(集成套件 `SUITE-INT-*` / 标题标注"集成",用例类型标「集成」,让 `auto-test-runner` 走 self-heal),集成套件是单模块套件的**补充**、两者并存。

**⑪ 需求澄清点专项用例(可选,消费《需求问题记录》时启用,详见方法论「八之四」+ 第五步之五):** 提供上游《需求问题记录 / 需求澄清记录》(条目 `### 问题 #N`)时,为**每个已澄清/有争议点**主动补一条专项用例验证约定行为,用例名末尾标 `(需求问题#N)` 并按现有溯源格式指向该条目;**与 T-NNN 方向相反**——T-NNN 记"我不确定等答案"(UNresolved),本条记"这点被澄清过、专门验证它"(resolved)。缺省则跳过、不影响现有流程;`check_case_stats.py --issue-record` 机检 M/N 覆盖。

**⑫ 原型内容基线覆盖(AIDP 对齐,用例生成基准,详见"原型内容基线为用例生成基准"章节 + 第五步之零):** 覆盖矩阵的"每个功能点"以**原型可见内容与操作逻辑**为清单来源——原型内容基线里每个处置="实现"的**元素、交互态(requiredStates:空态/加载/错误/成功/禁用等)、操作逻辑/交互流(flows:校验规则与时机/字段联动/条件显隐禁用/增删改保存取消/二次确认/默认值/多步步序/错误处理/权限态差异)**,各至少一条可验证用例;裁剪/延期/改逻辑项标注不覆盖原因(引用约定4三件套留痕)、不出正向用例但登记在案。**AIDP 产物有则强制消费为基准,无则回退直接从原型 `code/` 现场逐页提取。** 与正向 9 维/反向 12 维**并行、互补**:9/R 维保证测试方法论深度,本条保证**"原型每个可见元素与每条操作逻辑都被测到"的广度**,把内容/行为缺失变成测试可发现的偏差。

**⑬ 语义/口径变更类文案一致性用例族(`[文案一致性]`,消费上游「表 E:语义变更→派生展示物影响清单」/「文案落点表」时启用,详见第五步之八):** 当需求是**语义 / 口径变更**(如"用量统计口径由『仅企业』扩为『企业+个人』")时,后端/接口/取数改对了、但**各展示位解释该值的说明文案(tooltip / 副标题 / 图例 / 帮助气泡 / 空态提示)未同步改**是高发漏测——只断言数值不断言文案则全绿放行。故对每个处置=改写的展示位生成三类用例:**正向**(文案已体现新口径,如含"含员工个人");**反向(Critical,判失败关键)**——复用原型内容基线的反向断言 DSL,以「**不存在文本"旧口径字样"**」(`断言(反向):不存在文本"仅统计企业级"` / `断言(反向):不存在文本"不含员工个人"`)表达"旧口径字样出现即 Fail";**一致性**(文案声明口径 ⟷ 该处数值实际取数口径交叉验证,可配 `[双源对账]` DB 断言)。与约定33「原型内容基线反向断言」同思路,是其在**文案维度**的延伸——正向断言易被"文案里有个『含』字"蒙混,反向断言才能确定性拦截残留旧文案。无语义变更需求时本族标 `不适用 + 原因`。

## 测试套件模型(核心组织方式)

### 概念

- **测试套件 (Test Suite)**:一组相关用例的集合,共享同一个登录会话。一个套件 = 一次登录 + N 个连续执行的用例。
- **入口流程 (Suite Setup)**:套件级一次性步骤——打开浏览器、访问首页、登录、进入工作台。**只在套件开头出现一次**。
- **用例 (Test Case)**:套件内的最小测试单元,默认**承接上一用例的页面状态**(或通过简短的"导航步骤"切换到目标页面)。
- **导航步骤 (Navigation)**:用例开头的 1-3 步页面切换(如"点击左侧菜单'用户管理'"),不是从浏览器重新开始。

### 套件划分规则

按以下原则切分套件,**同一套件内的用例共用一次登录**:

| 划分维度 | 示例 |
|---------|------|
| **按测试账号/角色** | 套件 1:管理员视角(所有需要 admin 角色的用例);套件 2:普通员工视角;套件 3:未登录访问 |
| **按业务领域** | 用例数较多时,管理员套件再细分:套件 1A 用户管理 + 部门管理;套件 1B 工单管理 + 报表 |
| **按测试目标隔离** | 登录/登出本身的测试单独成套件(因为它们要反复操作登录态) |

**经验法则**:一个套件控制在 **5-15 条用例**;少于 5 条建议合并到相关套件;多于 15 条考虑按业务领域拆分。

### 套件结构

每个套件包含:
1. **套件元信息**:套件 ID、套件标题、所用角色/账号、覆盖模块、用例总数、预计执行时长
2. **套件级前置条件**:测试环境 URL、所用账号、所需前置数据
3. **入口流程 (Suite Setup)**:打开浏览器 → 访问首页 → 登录 → 进入工作台,**只写一次**
4. **用例列表**:套件内所有用例,按"页面流转的合理顺序"排列
5. **套件级清理 (Suite Teardown)**:可选,如"清理测试中创建的脏数据"

> **★套件/用例标题前缀契约(与下游 `auto-test-runner` 统一,新生成单一形态):**
> **新生成一律写 `套件 SUITE-{编号}: {标题}` + `用例 TC-{模块}-{序号}: {标题}`**——
> **前置词与编号前缀固定**,标题层级不限(套件 `##`~`####`、用例 `###`~`#####` 都合法:
> 单文件模式套件在「三、测试套件详情」之下多为 `###`,多文件分册里套件是顶层 `##`)。
> 不要再产出 `测试套件` 前置词、`TS-` 编号前缀、或省略「用例」二字的标题——那三种是**历史兼容形态**,
> 本 skill 的 5 个套件解析脚本(`check_testcase_suite` / `check_testcase_format` / `check_suite_upstream` /
> `check_case_stats` / `check_test_plan_alignment`)会照常放行存量文档。
> 混用前缀曾在下游 `auto-test-runner` 造成**静默漏跑**(套件扫不到 → 分组丢失;用例扫不到 → 该用例
> 根本不进 tasks.md,报告里连"未执行"都不体现),故新生成收敛为单一形态。
>
> ⚠️ **本项无闸门,靠自觉 + 提示**:`check_testcase_suite.py` 对三种历史形态出 **Info 级
> `legacy_suite_prefix` / `legacy_case_prefix`**,**report-only、不影响退出码**(存量文档 grandfather
> 放行,不该因此变红)。下游 `auto-test-runner` 已按「宽进」契约认全部形态、不会漏跑,但**其它/未来
> 消费端不作此保证**——收敛的收益在后者。

### 用例之间的状态衔接

用例之间允许**状态衔接**(这是真实测试的常态),但必须**显式标注**:

- **延续状态**:用例开头标注 `> **承接前置**: 上一用例 TC-XXX 结束于 XX 页面`
- **回到根**:若用例需要从工作台开始,标注 `> **从工作台开始**`,然后第一步是导航
- **依赖前置数据**:若用例依赖前序用例创建的数据,标注 `> **依赖**: TC-XXX 创建的"测试用户 A"`,并写明若 TC-XXX 失败时如何手工准备数据

### 用例级「前置探测」段(浏览器前数据面探测,强制结构化)

凡用例依赖某个可在进入浏览器前通过只读接口或数据面查询确认的状态,必须在用例元信息中引用一个全册唯一的 `ED-NNN` 前置项,并在测试步骤前产出固定三列定义。相同实体、状态、数量关系和探测方式的用例复用同一个 `ED-NNN`,供下游执行内核合并为一次探测。

```markdown
> **前置探测:** ED-001

| 前置项 | 探测实体/状态 | 探测方式（只读） | 不满足时 block 归因 |
| :- | :- | :- | :- |
| ED-001 | 订单，存在 ≥1 条 `status=待交付` | 只读接口 `GET /orders?status=待交付`，成功响应按 `total` 判断 | 缺少 status=待交付 的订单样本 |
```

**三列必须可直接消费:**

- **探测实体/状态:** 明确实体、状态和数量关系(如 `≥1` / `=0`),不得只写「需要测试数据」。
- **探测方式（只读）:** 写只读接口或数据面查询的最小描述,不得包含创建、修改、删除等写操作;具体端专有调用由下游适配层决定。
- **不满足时 block 归因:** 写成可直接放入 `block(precondition-unmet)` detail 的具体短语,不得写「见前置条件」或「数据不足」。

> **前置探测不是前置数据编排:** 前置探测只读确认状态,应在浏览器连接前执行;前置数据编排用于必须跨系统造/删数的主动动作,仍按下节表格执行。两者可以同时存在,先探测已有状态,不满足时才按编排规则决定是否造数。
>
> **探测类断言纪律:** 前置探测必须遵守探测类断言的方向、特异性和阳性对照分档自检;尤其必须显式区分 `success=false` / 非 2xx 与合法空结果,不得把调用失败当成 0 条或前置缺位。登记格式与唯一信源见测试设计方法论「八之二、探测类断言三项自检」。

### 步骤级 `[加速可选]` 标注 + `[还原度]` 禁走 WebMCP(与下游执行端的分层契约)

**立论(同一批实证):** WebMCP 已在被测页面启用、驱动原生支持,而 116 条用例里**只有 16 条用到它,
且全部在测 WebMCP 自己**。其余 100 条里大量「登录 / 切环境 / 选中某接口 / 构造请求参数 / 发起调用」
这类**状态准备**步骤,仍走「快照 → 找元素 → 点击 → 等待 → 再快照」的 **5+ 次驱动往返**,
本可压缩成 **1 次工具调用**。

**但绝不能一刀切 —— 分层判据(与 `auto-test-runner` 逐字一致):**

| 步骤性质 | 走什么 | 为什么 |
| :- | :- | :- |
| 状态准备 / 数据构造 / 业务流程驱动 / **非视觉**断言 | **可走 WebMCP 工具调用** | 快、稳、不依赖选择器 |
| **视觉还原度 / 布局 / 样式 /** 通用规则集 约定39-R1·R2·R3 | ⛔ **必须 DOM + 截图** | **WebMCP 读的是页面「声明的能力」,不是「渲染结果」** —— 用它验还原度会让渲染层缺陷 **100% 漏测,而且全绿** |

**怎么标(两条,一正一反):**

1. **正向加速提示** —— 在**步骤号后**加 `[加速可选]`,只标**状态准备类**步骤:

   ```markdown
   | 步骤 | 操作动作 | 操作对象 | 操作数据 | 预期现象 |
   | :-: | :- | :- | :- | :- |
   | 1 [加速可选] | 登录 | 登录页 | admin / ****** | 进入工作台，右上角显示当前账号 |
   | 2 [加速可选] | 切换 | 环境下拉框 | 测试环境 | 顶部环境标识变为「测试环境」 |
   | 3 | 点击 | 「接口列表」第 1 行 | — | 右侧详情区显示该接口的方法与路径 |
   ```

   ⚠️ **`[加速可选]` 是提示不是许可** —— 执行端仍按上表的「步骤性质」判;
   **没标不等于禁止加速,标了也不等于必须加速**。它的价值是:**写用例的人在最清楚这一步在验什么的时刻
   把判断固定下来**,而不是留给执行体临场猜。

2. **反向硬约束 —— `[还原度]` 用例整条禁走 WebMCP,不需要新标记。**
   还原度用例本来就带 `[还原度]` 族标记,该标记**已经**透传到下游结果 JSON;
   执行端据此判定「本条断言必须走 DOM」,结果 JSON 的 `mechanism` 字段填 `webmcp` 时
   由 `check_result.py` C14 判 **Critical**。
   ⚠️ **⛔ 不要为此再发明一个 `[必须DOM]` 标记** —— 那会变成**两套判据**:
   一条用例同时带 `[还原度]` 和 `[必须DOM]` 时,后加的那个反而会被当成「只有标了才必须」,
   于是**没标的还原度用例被放行**,方向恰好是本条要防的那个。
   `mechanism` 填 `mixed`(状态准备走 WebMCP、断言走 DOM)**是被鼓励的形态,不判**。

### 用例级「环境能力前置」段(`EC-NNN`,与 `ED-NNN` 同族、判据不同)

**立论(auto-test-runner 执行实证):** 实际项目两轮 116 条用例里 **41 条(35%)因前置不满足被判 block**,
成因高度集中 —— **25 条缺 `exposure=public` 独立实例 / 10 条缺服务端日志读取通道 / 6 条缺靶场样本**,
且**全部是逐条执行到前置检查时才发现的**,每条白走一遍「导航 → 等待 → 探测 → 判定」。
**根因不在执行端,在用例册**:这类前置只有自然语言形态、散在正文里,机器读不了,只能靠执行时试。

⚠️ **它们够不着上一节的 `ED-NNN`**:`ED-NNN` 问的是「**样本在不在**」(可用只读接口/数据面查询确认),
而「部署形态是不是独立实例」「有没有服务端日志读取通道」「靶场里有没有 ≥3 级目录的样本」问的是
「**这个环境提供不提供这个能力**」。⛔ **不要把它们硬塞进 `ED-NNN`** —— 探测方式、失效频次、
不满足时的处置范围都不同(见下表)。

| | `ED-NNN` 数据面前置 | `EC-NNN` 环境能力前置 |
| :- | :- | :- |
| 问的是 | 样本在不在 | 环境提供不提供这个能力 |
| 探测方式 | 只读接口 / 数据面查询 | 环境已知事实 + 一次性能力探测 |
| 频次 | 每轮重探(数据会变) | **整轮一次**(环境形态一轮内不变) |
| 不满足时 | 该前置项关联的用例 block | **同一能力的整批用例一次性 block** |

**固定四列(跨产物契约,⛔ 不得改列名/列序 —— 执行端按列名读):**

```markdown
> **环境能力前置:** EC-001, EC-002

| 前置项 | 能力标识 | 判定方式 | 不满足时 block 归因 |
| :- | :- | :- | :- |
| EC-001 | `deploy:standalone-public` | 环境清单声明「独立实例、exposure=public」 | 当前为共享实例，无 exposure=public 独立实例 |
| EC-002 | `channel:server-log` | 环境清单提供服务端日志读取入口（只读） | 未提供服务端日志读取通道，无法核对后端落库日志 |
| EC-003 | `fixture:deep-tree` | 靶场资产清单含 ≥3 级目录样本 | 靶场无 ≥3 级目录样本，无法验证深层级渲染 |
```

**「能力标识」用受控词表 `<类别>:<值>`,类别是闭集:**

| 类别 | 含义 | 例 |
| :- | :- | :- |
| `deploy` | 部署形态 | `deploy:standalone-public` / `deploy:multi-env` |
| `channel` | 可读写的通道 | `channel:server-log` / `channel:db-readonly` |
| `fixture` | 靶场/样本资产 | `fixture:deep-tree` / `fixture:ws-sse-node` / `fixture:frozen-project` |
| `account` | 角色账号能力 | `account:admin` / `account:guest-link` |
| `data` | 环境级数据形态(≠ 单条样本,那是 `ED-NNN`) | `data:multi-tenant` |

⚠️ **为什么必须收敛词表:** 完全自由的字符串意味着执行端只能做**字面匹配**,拼写不一致就**静默失配** ——
而失配的表现是「该跳过的没跳过」,**与「前置真的满足」完全同形**,报告上看不出任何异常。

**⚠️ 三条不可退让(与下游 `auto-test-runner` 逐字一致,⛔ 两边不得各定一套):**

1. **未识别的能力标识 → 按「未探明」处理**:该用例**回落旧流程**(照常进浏览器、由用例内前置检查判定),
   并在报告显式登记「`EC-NNN` 词表未识别,本轮未预判」。
   ⛔ **既不得静默当作满足,也不得静默当作缺位** —— 当作满足只是白跑;
   **当作缺位则是不该跳过的被跳过了,而报告显示 block、看上去很正常**,那是漏测。
2. **无声明 = 无前置**(向后兼容)。存量用例册没有 `EC-NNN` 时一切照旧,
   ⛔ 不得因为「没写声明」就整批跳过。
3. **能力探测本身失败** → 执行端标 `block(env-unavailable)` 并记证据,⛔ **不得**转换成「该能力不具备」。

> **与「前置探测 `ED-NNN`」「前置数据编排」三者并存不冲突:**
> `EC-NNN` 管**环境给不给得了**(整轮一次)、`ED-NNN` 管**数据在不在**(每轮重探)、
> 「前置数据编排」管**必须跨系统主动造/删**(可执行动作)。写用例时按这三问依次判。

### 用例级「前置数据编排」段(跨系统前置状态,区别于只读前置条件)

**只读「前置条件 / 前置数据」段**声明的是"执行前该有哪些数据",**不足以**表达"被测应用内根本造不出、必须先去别的系统动手"的跨系统前置状态。对这类用例,新增一个**用例级「前置数据编排」段**——声明执行本用例前必须在**其他系统**完成的前置动作,每条动作标**动作类型 + 目标系统**:

- **动作类型(三选一):** `他系统UI操作`(在对方系统页面手动操作)/ `SQL造删数`(在目标库直接造 / 删数据)/ `调对方接口`(调用对方系统接口造数)。
- **目标系统标识:** 每条动作标明目标系统,**该系统的入口 URL / 账号 / DB 连接一律登记在本 SKILL 产出的 `01_研发自测方案.md` §3 测试环境与准入**(§3.1 测试环境信息的「跨系统依赖环境」「数据库」行 / §3.2 测试账号 / §3.3 前置数据准备);若项目另有外部的 `测试环境与账号.md`(aiauto-test 端配置、**不由本 SKILL 产出、不占本目录 `NN_` 序号**),以之为准。下游 `auto-test-runner` 据此路由到对应系统 / 库执行。
- **典型场景:** 缺陷复现如「**订单中心删商品 → 商户后台看统计**」——商品的删除动作**在被测的商户后台内无法构造**,必须先到订单中心删商品(跨系统前置),再回商户后台验证统计。这类前置只能用本段表达,普通「前置条件」段承载不了。

**段格式(写在用例内、测试步骤之前):**

```markdown
**前置数据编排**(跨系统前置,执行本用例前完成):
| 序号 | 动作类型 | 目标系统 | 具体动作 | 完成判据 |
| :-: | :- | :- | :- | :- |
| 1 | 他系统UI操作 | 订单中心(见 01_研发自测方案.md §3.1 跨系统依赖环境) | 在"商品管理"删除商品"测试商品A" | 订单中心列表不再显示"测试商品A" |
| 2 | SQL造删数 | 统计库(见 01_研发自测方案.md §3.1 数据库) | (UI 不可达时)在统计库软删除该商品 `UPDATE t_product SET del_flag=1 WHERE name='测试商品A'` | 影响行数 = 1 |
```

> **与只读「前置条件」的分工:** 「前置条件 / 前置数据」段仍写**本系统内、执行前应就绪的数据**(只读声明);「前置数据编排」段写**必须跨系统主动执行的前置动作**(可执行编排,标动作类型 + 目标系统)。二者并存、不冲突。
> **与"步骤列禁 SQL / 接口"的边界:** 「前置数据编排」段位于**测试步骤表之前**,其中的 `SQL造删数` / `调对方接口` 属**跨系统造数编排**、不是被测应用的操作步骤,故不受核心原则 1「步骤列禁 SQL / 接口」约束(`check_testcase_format.py` 只扫「**测试步骤**」区域,不扫本段);但被测应用自身的测试步骤表仍严禁 SQL / 接口。

### 何时强制重新走入口流程

只有以下情况需要在用例开头**重新走入口流程**(打开浏览器→访问首页→登录):

1. **角色切换**:从管理员切换到普通员工(单独成立新套件,不在旧套件内强制切换)
2. **登录态测试**:测试登出、登录态过期、强制下线、单点登录跳转等场景
3. **未登录场景**:测试未登录访问受保护页面跳转登录页的行为(套件起点是未登录状态)
4. **跨设备/跨浏览器测试**(如适用)

其他所有场景,套件内用例**直接延续当前会话**,通过菜单点击/返回按钮在功能间切换即可。
