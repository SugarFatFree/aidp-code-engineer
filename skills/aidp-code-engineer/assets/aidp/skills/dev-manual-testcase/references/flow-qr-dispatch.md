## Post-Generation Quality Review (用例生成后独立检查)

**强制要求:**用例生成后必须调用独立 Agent 执行 **21 维度检查**(覆盖率核验 6 项 + 用例质量 7 项 + 结构 1 项 + 流程 2 项 + 需求字段对账 1 项 + 完备性度量 2 项 + **条件启用 1 项**〔维度 20 仅 `webmcp_enabled: true` 时存在,否则连行都不留〕+ **通用还原度 1 项**〔维度 21〕),发现问题修订后重试,最多 3 轮。**其中"PRD 功规点 100% 覆盖"是最高优先级,任何遗漏都判定为 Critical 不通过;"自测方案对齐与引用闭环"为前置门槛,缺方案 / 缺引用直接整体不通过。**

> 🧹 **执行主体与上下文隔离(Critical):** 本节全部检查——`🛡️ 落盘后 bash 硬核回检` 的 7 条脚本 **+** 21 维度语义审查——一律在**独立子 Agent**内完成。主流程**禁止**在当前对话上下文内联跑脚本或内联逐维度自查(脚本输出与逐项核对会挤占/污染主上下文)。主流程只负责:① 派发子 Agent(传入用例/PRD/详细设计/执行计划/自测方案路径);② 接收子 Agent 回传的**精简结构化报告**(含每个脚本退出码 + 各维度通过/不通过 + 修订建议);③ 据报告决定修订并重新派发,循环至全部通过或达 3 轮上限。

### 🛡️ 落盘后 bash 硬核回检(子 Agent 强制第一步,先于语义维度审查)

> **`<SKILL_DIR>` 占位符:** SKILL 实际安装位置(本项目 = `{{AIDP_HOME}}/skills/dev-manual-testcase`),由子 Agent 在执行前替换。

**用例文档落盘后,以下 bash 一次性回检脚本由下方派发的**质量检查子 Agent**作为强制第一步执行(见子 Agent prompt 步骤 0),任一命中即拒绝标记完成、强制重写违规段落。主流程**禁止**在当前上下文内联运行这些脚本:**

# 退出码 0 = 通过, 1 = 不通过(缺「用例统计摘要」/ 反向占比 < 40%(用例数 ≥10 时)/ 摘要 P0+P1+P2 之和与实际用例数不符

# ⚠️ 优先级分布偏离目标区间、用例数 < 20(数量基线下限)均为 warning-only,不触发退出码 1——
#    「模块用例数低于基线下限且未说明原因」由 QR 子 Agent 据 --json 语义判定(脚本不知模块规模,只对 <20 告警),不能只看退出码
# ⚠️ 给了 --issue-record 时,--json 的 issue_coverage 是**三态**,禁止只读 uncovered_nums 判绿(维度 13.8):
#      · 正常  {'covered':M,'total':N,'uncovered_nums':[...],'tagged_extra_nums':[...]}  → 有未覆盖澄清点即 13.8 不通过
#      · 跳过  {'skipped':true,'reason':...}   → 清单显式标注「无待澄清项」,13.8 记 N/A(不是通过)
#      · 错误  {'error':...}                    → 清单解析不出编号,13.8 **不得判通过**,退回上游修清单格式
#    后两态**没有** covered/total/uncovered_nums 三个键,`len(uncovered_nums or [])==0` 在两态下恒真 → 假绿灯。
# 6. 通用还原度覆盖表结构性核验(维度 21:覆盖表存在性 + 4 列 + 列表页 ≥10 + 编号逐个回查)

# 检测: F1 有用例却缺「通用还原度覆盖表」 / F2 缺列(页面|页面类型|还原度用例数|用例编号) /
#      F3 任一列表页还原度用例 < 10 / F4 表里声明的编号在文档里找不到同编号且标 `[还原度]` 的用例
# ⚠️ W1(详情页<4 / 表单页<2 / 含数字页<6)、W2(页面类型不在四类枚举内)、W3(数量与编号条数不符)
#    是 Important、**不触发退出码 1**——须读 --json 的 `warns` 另行判定,不能只看退出码
# ⚠️ `skipped=true` 表示整档没跑,**不等于通过**;报告须如实标「跳过(原因)」
# ⚠️ 「10 条模板项是不是都真写了」属语义层,须子 Agent 对照 flow-fidelity-suite.md 第三节逐页核——
#    **脚本全绿 ≠ 维度 21 通过**

# 7. 零残留断言登记表形态核验(维度 18 子条:登记表存在性 + 7 列 + 两个方向实跑记录 + 退役理由合法)
python3 <SKILL_DIR>/scripts/check_residual_assertions.py <用例路径或目录> --json
# 退出码 0 = 通过或跳过(扫描范围里一条零残留断言、一张登记表都没有), 1 = 不通过, 2 = 输入路径错误
# 检测(Critical): Z2 缺列(# | 断言 | 守护面 | 实跑命令 | 方向一·现状命中 | 方向二·阳性对照 | 退役状态) /
#      Z3 逐格空或占位 / Z4 **两个方向任一**读不到 `N 命中`(阳性对照另加「命中数为 0」) /
#      Z5 以「多轮未红」为由退役或已退役后没有任何依据 /
#      Z6 文档里的零残留断言漏登记进表 / Z7 数据行格数不符(最常见根因:实跑命令里的 `|` 未转义为 `\|`)
# ⚠️ Z1(有断言却缺登记表)是 **Important、不触发退出码 1**——存量用例文档会大面积命中,
#    一上来判死会让整个硬门被无视(同 architect `check_upstream_call_log_spec.py` 的 U1 取舍);
#    须读 --json 的 `findings` 里 level=Important 的条目另行判定,不能只看退出码
# ⚠️ **必须传目录**:Z1/Z6 是跨文件聚合判定(多册拆分时登记表常落在总览册、断言散在模块册),
#    传单文件时 --json 出 `scope: "single-file"` + `aggregation_scope_note`,见到即按「未全范围核验」处理
# ⚠️ `skipped=true` 表示整档没跑,**不等于通过**;表该不该有由子 Agent 判
# ⚠️ **先看 `read_errors`**:> 0 表示有 .md 读不出来,此时 `assertions`/`rows` 是残缺样本上的结果,
#    「0 条断言」不代表真没有断言(该条以 Important 出现在 findings 里,不占退出码)
# ⚠️ 「那两个方向是不是真跑过」属语义层——**脚本全绿 ≠ 维度 18 零残留子条通过**
