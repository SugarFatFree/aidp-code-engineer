### 第五步之零:原型内容基线覆盖(AIDP 对齐,用例广度基准,强制)

**在按覆盖矩阵反向维度补异常/边界之前,先以原型内容基线把"原型每个可见元素与每条操作逻辑都被测到"这条广度基准落地**(详见上方"原型内容基线为用例生成基准"章节唯一信源,本步仅执行入口)。

1. **取基准** — **若上游 AIDP 已产出**:用 Read 读取 `原型内容基线.md`(自适应项目结构),遍历每一页的「可见元素 / 交互态(requiredStates) / 操作逻辑·交互流(flows)」及其**处置列**;并读取 `DESIGN-MANIFEST.json` / `DESIGN-HANDOFF.md` 的 screens/appModules/requiredStates/flows 扩充覆盖项。**无 AIDP 产物则回退**——直接读原型 `code/` 逐页现场提取可见元素与操作逻辑,自建覆盖清单。**不臆造上游产物、不硬依赖其路径。**
2. **逐项配用例(处置=实现)** — 对每个处置="实现"的**元素 / 交互态 / 操作逻辑**,保证各有 ≥1 条可验证用例(规则见上方章节"逐项配用例规则"表):元素→可见且文案/位置/交互正确;交互态→触发并断言(空态/加载/错误/成功/禁用…);操作逻辑→验证行为(校验时机/字段联动/条件显隐禁用/保存取消/二次确认/默认值/多步步序/错误处理/权限态)。这些用例的「覆盖」字段照常标 F/R 维度标签,并在功能点处标注其对应的原型基线条目(溯源指向基线/原型锚点)。
3. **登记不覆盖项(处置=裁剪/延期/改为X)** — **不生成正向覆盖用例,但登记在案不静默漏**:在用例文档"原型内容基线覆盖登记"小节(或对应功能点处)标注 `原型元素「X」处置=裁剪/延期/改为Y — 不覆盖,原因:<引用约定4三件套(视觉/内容/操作逻辑)对应处置说明>`,溯源指向基线条目。
   - **裁剪 / 延期项强制配 `[反向-残留]` 反向断言用例(不止登记):** 对处置=**裁剪 / 延期**的元素,除登记原因外,**新增一条 `[反向-残留]` 反向断言用例**——用例类型标 `[反向-残留]`,核心断言用 DSL「**不存在文本"X"**」(`断言(反向):不存在文本"X"`)表达"该元素若仍存在则 Fail",专门捕获"决定删 / 延却没删干净"的残留。处置=**改为X** 的项按新语义走正向用例,不需残留断言。
   - **⭐ 每条零残留断言必须同时登记三个字段(守护面 / 反向复现片段 / 退役状态)**——
     **守护面**(文件/目录 glob,多条用 `;` 分隔)**由本条断言正向实跑的命中文件集合导出、不得手写**;
     **反向复现片段**记下能让它失败的最小片段(否则半年后文件改名,断言永久失去命中能力却始终全绿,
     「常绿」与「已腐化」在报告里长得一模一样);语义为「全站不得出现」的断言守护面只能写 `**`。
     退役只有「守护对象已消失」「判据已移交常设机制」两条合法路径且须留在清单里标注,
     ⛔ **「多轮未红」不是退役理由**——常绿正是这类断言的正常状态,按它退役等于专挑还在生效的删。
     判据全文见 `quality-review-checklist.md` 维度 18「零残留断言登记表」子条;
     **登记表承载形态**见两个用例模板的「零残留断言登记表」节(7 列),配硬门
     `check_residual_assertions.py`(⚠️ 须传目录:Z1/Z6 跨文件聚合)。
     **⭐「两个方向」= 方向一跑现状期望 0 命中 + 方向二对着必然命中的样本跑同一式子期望 ≥1 命中**;
     方向二的样本就是「反向复现片段」,**一次实跑同时兑现两条规则、不是两项义务**——
     ⛔ 只跑方向一的断言可能是「式子写错、永远不会命中」的**恒 0 假绿**,在报告里与真正的零残留一模一样。
     **实跑口径(默认排除注释行的通用前置)** 见 `test-design-methodology.md`「八之二 · 零残留断言的实跑口径」——
     下游实测一轮 8 条断言初稿 5 条假红、**全部**命中的是本 Sprint 自己写的防回退注释,是模式不是偶发。
     **本轮跑哪些、跳哪些**属执行计划职责(见 `dev-execution-planner` 轮次收尾验证任务),本步只负责登记齐字段。
4. **交回收敛** — 第七步覆盖率回检时,把"原型内容基线实现项是否一一对应用例 + 裁剪 / 延期项是否已配 `[反向-残留]` 反向断言用例"作为一维纳入收敛循环(见第七步第 5-6 项);缺覆盖又未标不覆盖原因的,回本步补齐。

> **判定:** 原型内容基线中处置="实现"的元素/交互态/操作逻辑,存在既无覆盖用例、又未标不覆盖原因的 → 判覆盖缺口(折进维度 18「原型内容基线覆盖度」子条)。无 AIDP 产物且原型极简/纯后端时,本步标 `不适用 + 原因`。

### 第五步:异常与边界用例补充(按覆盖矩阵反向维度逐维过)

每个功能点**必须**按「测试设计方法论速查」的**反向 12 维(R1-R12)** 逐维过一遍并配套生成用例,不适用的维度就地标注 `不适用 + 原因`:

- **表单校验类(R1/R2/R3)**:必填留空、超长输入、特殊字符、格式错误的每个字段都独立 1 条用例,验证错误提示文案
- **权限类(R6)**:未登录访问、无权限角色访问、URL 直接访问的行为(放在专门的"未登录套件"或"低权限角色套件")
- **状态约束类(R9)**:"已上架不可编辑"、"已完成不可取消"等约束路径(即状态机的非法迁移,须验证被拦截)
- **异常分支(R4/R8)**:网络断开、接口超时、服务端错误的用户可见现象
- **依赖/数据源故障注入(R12)**:功能点聚合 ≥2 数据源、或存在"某下游 500/超时/空返回时兜底静默返 0/空"逻辑时,**逐数据源注入 500/超时/空返回**,断言页面**显式失败提示 / partial 标记、禁静默显示 0/空**;并与 R5 真空态用例**配对**,验证"真空态(真没数据)"与"故障静默返空(数据源挂了)"两者页面表现**可区分**(区别于 R4=请求整体失败、R8=服务端 5xx、第三方降级=外部不可用,R12 专治"后端返 200 但内部数据源被静默兜底")。单一数据源、无兜底逻辑时标 `R12 不适用 + 原因`
- **并发/竞态(R10)**:重复提交、乐观锁冲突、他人已删等(见第五步之三)
- **空/大数据(R5)**:列表无数据、仅 1 条、超大数据量时的展示差异
- **弹窗关闭(R7)**:含弹窗的功能点须测关闭按钮 / 点击蒙层 / ESC 三种关闭方式
- **安全输入(R11)**:PRD 有要求时,XSS/SQL 注入/特殊字符被转义或拦截

### 第五步之二:列表/表格/表单字段与需求字段清单逐列核对(强制)

对**列表 / 表格 / 表单类功能点**,**不能止步于**"页面可打开 + 数据加载成功"——**必须**额外生成一条「字段/列与需求字段清单逐列核对」用例(或在该功能点主流程用例中追加专门的核对步骤),逐列比对页面实际呈现的**列展示名 / 字段标签(语义名)**与**研发需求的需求字段清单(语义) /『需求字段→处置』对照表**是否一致(核对的是页面呈现的语义展示名,而非代码级字段名)。

**核对维度(缺一不可):**
- **列展示名 / 字段标签(语义)**:表格每一列表头文案、表单每一个字段标签(均为业务语义名),与需求字段清单逐一对照,文案一致
- **展示顺序 / 字段顺序**:表格从左到右、表单从上到下的呈现顺序与需求字段清单一致
- **是否缺列 / 多列**:页面不得缺少需求字段清单标「保留」的字段,也不得出现需求字段清单 + 处置对照表之外的额外列
- **与「需求字段→处置」对照表一致**:标「保留」的字段正常展示;标「裁剪」的字段不出现;标「前端计算还原」的字段有值且口径正确;标「请第三方补」的字段按对照表的暂行处置呈现(占位 / 置灰 / 隐藏)

**⚠️ 每个列表类页面强制生成一条「列表列完整性」结构用例(强制子项,不可省略):**

> **背景(下游暴露的漏洞):** 现有用例大多只测**行为**(计算是否正确、能否展开),不测**结构**(表格到底该有哪些列、顺序如何)。结果详设漏列、前端漏渲染,却**没有一条用例去核对"表格该有哪些列"**。本子项把"列结构"本身变成一条独立可判的断言用例。

- **强制范围:** 每个**列表 / 表格类页面**(含列表、明细表、可展开子表)**必须有且至少有一条**独立的「列表列完整性」结构用例(用例类型固定标 `列表列完整性`)——它与逐列语义核对(上文 4 维)并列,专测"列集合与顺序"这一结构维度。
- **断言固定形态:** 用例的核心断言写成——「**表格自左至右应依次为 A / B / C / …,缺列或多出未登记列即 Fail**」(A/B/C… 为实际列展示名,按从左到右顺序逐一列全)。
- **期望值来源固定:** 该结构用例的**期望列序列直接取自详细设计的「字段实现清单」**——即 dev-logic-architect 产出的字段级实现清单表(列为 `列名/字段 | 顺序 | 数据来源（接口字段） | 展示规则 | 上游出处`)。以「字段实现清单」的**列名 + 顺序**列为期望基准,形成 **设计 →(本用例)→ 实现** 的闭环校验:详设漏列 → 期望列缺失可暴露;前端漏渲染 → 实际列缺失即 Fail;实现多出未在「字段实现清单」登记的列 → 判"多出未登记列"Fail。
- **上游缺失兜底(不臆造):** 若详细设计未产出「字段实现清单」,期望列序列**回退取自** PRD 需求字段清单(语义) + 原型可见表头,并就地标 `T-NNN 待澄清:缺详设「字段实现清单」,期望列暂取自 PRD/原型`,登记进"待澄清问题清单",**不静默跳过、不凭空编列**。

**步骤写法示例(操作对象 + 预期现象,沿用四要素风格):**

| 步骤 | 操作动作 | 操作对象 | 操作数据 | 预期现象 |
| :-: | :- | :- | :- | :- |
| 1 | 点击 | 左侧菜单"用户管理" | — | 进入"用户列表"页,表格加载完成 |
| 2 | 观察 | "用户列表"表格表头 | — | 表头列依次为「用户名 / 手机号 / 部门 / 状态 / 创建时间 / 操作」,列展示名(语义)、展示顺序与需求字段清单完全一致,无缺列、无多列 |
| 3 | 核对 | 表格各列与「需求字段→处置」对照表 | — | 标"保留"的列均展示;需求字段清单标"裁剪"的"内部备注"列未出现;标"前端计算还原"的"在职时长"列有值且按"入职日期至今"口径显示 |

> **判定:** 仅"页面能打开 + 列表有数据"**不足以**通过列表/表格/表单类功能点的自测——必须有逐列核对的步骤或独立用例,且预期现象写明与**需求字段清单(语义) /『需求字段→处置』对照表**的逐列一致性结论。**此外,每个列表类页面还必须有一条「列表列完整性」结构用例(断言"表格自左至右应依次为 A / B / C / …,缺列或多出未登记列即 Fail",期望列取自详设「字段实现清单」),缺此结构用例同样判不通过。**(对应质量检查维度 17)

### 第五步之三:按测试设计方法论系统补充(BVA + 等价类 + 状态机 + 并发,强制)

**这是解决"用例偏少、只堆正向"的关键步骤。** 对每个功能点,套用 [`references/test-design-methodology.md`](./test-design-methodology.md) 的模板清单**系统性补齐**,而非临时想到哪测哪:

> **💡 语义断言提示(配合自动化执行):** 本步及第五步生成用例时,**关键断言步骤**(提交成功 / 列表增减 / 状态迁移 / 字段展示 / 校验拦截)在自然语言"预期现象"之外,**可按方法论「八之二」的语义断言 DSL 附一行 `断言:` 行**(反向用例用 `断言(反向):`),供下游 `auto-test-runner` 做确定化判定;断言仍用页面可见文案、禁选择器/字段名,与核心原则 7 一致。若断言用于探测某项能力是否已交付,还必须按方法论「八之二」的**探测类断言三项自检**登记失败态区分、特征唯一性,并按断言类型完成阳性对照或登记 `N/A（正向存在性断言，命中即自证）`,不得只凭正常样本 0 命中判定未交付。DSL 语法与示例见方法论「八之二」唯一信源,示范见两个用例模板。

1. **BVA 边界值(方法论第二节)**:每个受约束输入字段按六点法(`min-1/min/min+1/max-1/max/max+1`)+ 长度/日期/列表边界取点,逐字段成例。
2. **等价类(方法论第三节)**:手机号/邮箱/URL/身份证/金额/密码等格式字段,各出「1 条有效类 + 每类无效类各 1 条」。
3. **状态机迁移矩阵(方法论第四节)**:每个有状态对象画迁移矩阵,**合法迁移逐条正向用例 + 非法迁移逐条"被拦截"反向用例 + 幂等重复触发**。
4. **并发/竞态(方法论第五节)**:写操作功能点逐条核对 C1-C6(重复提交/乐观锁/他人已删/锁超时/多标签页/并发扣减),适用即成例,现象用"刷新后可见变化 + 提示文案"断言。
5. **特殊场景清单(方法论第八节)**:逐行核对触发条件(缓存/Mock 4 阶段/第三方对接/文件上传/权限矩阵…),命中即补对应用例类型。
6. **第三方接口已交付但字段不全(逐字段处置对账,Critical)**:
   - **识别规则**:把 **PRD「需求字段清单」(语义)** 与 **第三方接口实际返回字段** 逐项比对——**需求要、但对方实际不返回**的字段,即"已交付但字段不全",触发本场景(区别于"接口整体未交付"走 Mock 全生命周期)。识别依据来自上游 PRD/详细设计的「需求字段→处置」对照表中被标为非"✅ 已交付"的字段。
   - **按对照表三处置逐字段各出用例**:
     - **请第三方补 → 占位显示**:该字段在页面以占位符/置灰/"—"呈现,用例验证"占位正确、不报错、不展示脏值",并在预期现象注明"待第三方补齐"。
     - **前端计算还原 → 有值且口径核对**:该字段由前端用已有字段计算得出,用例验证"有值 + 计算口径正确"(如"在职时长 = 入职日期至今"),等同一条字段核对用例。
     - **裁剪 → 不出现**:该字段已决定不展示,用例验证"页面确实不出现该列/该字段"(与维度 17 列集合核对联动)。
   - **对账闭环**:三处置的用例合起来,须覆盖「需求字段→处置」对照表中该接口所有"字段不全"的字段,无遗漏。

> **判定:** 缺 BVA / 等价类 / 状态机非法迁移 / 适用的并发场景 / **第三方字段不全的三处置逐字段用例**,均在维度 18 判覆盖缺口。

### 第五步之四:跨模块集成用例生成(端到端业务闭环,强制)

**单模块测试套件只覆盖"模块内功能点";跨 ≥2 个模块/套件的端到端业务闭环若无专门用例,就是覆盖盲区。** 下游 `auto-test-runner` 备了 `self-heal` 模式承接集成/跨模块用例,本 SKILL 必须有对应生成章节以对称供需。触发条件与唯一信源见 [`references/test-design-methodology.md`](./test-design-methodology.md)「八之三」节。

1. **识别集成场景**:一条业务闭环**横跨 ≥2 个模块/套件**——上游模块产生的数据/状态被下游模块消费,数据在模块间流转、状态跨模块迁移。典型如"下单→支付→发货→通知"、"审批发起→多级审批→归档"、"报销提交→审批→财务打款"。
2. **生成方式**:新增一类**集成套件**——套件 ID 用 `SUITE-INT-*`(或套件标题标注"集成"),用例**元信息「类型」标注为「集成」**(与元信息字段行的 类型 字段对齐,让 `auto-test-runner` 识别为集成/跨模块 → 走 `self-heal` 模式)。步骤**跨模块连续走通**(在上游模块产生数据 → 切到下游模块验证),预期**验证跨模块数据/状态一致性**:上游产生的数据在下游模块正确呈现、状态正确流转(如订单在"订单模块"下单后,状态在"发货模块"由"待发货"变为"已发货")。
3. **与套件模型关系**:集成套件**不破坏**现有单模块测试套件组织,是其**补充**——单模块套件覆盖模块内功能点,集成套件覆盖跨模块闭环,两者**并存**。集成套件同样遵守测试套件模型(一次登录 + 套件内连续执行);跨角色的多级审批闭环,可在套件内按"角色切换才重新登录"规则处理(见核心原则 8)。
4. **与方法论呼应**:集成用例侧重**状态机跨模块迁移**(方法论第四节)+ **数据闭环完整性**;关键跨模块一致性断言可按方法论「八之二」附 `断言:` 行(如 `断言:状态由"待发货"变为"已发货"`、`断言:列表行数+1`),仍限页面可见信号。

> **判定:** 若 PRD/详细设计中存在横跨 ≥2 模块的端到端业务闭环,却无对应集成套件/集成类型用例,在维度 18 判覆盖缺口(集成闭环未覆盖);无跨模块闭环的单模块项目,本步标 `不适用 + 原因`。

### 第五步之五:需求澄清点专项用例(可选,消费《需求问题记录》时启用)

> **仅当用户提供了《需求问题记录 / 需求澄清记录》可选输入时启用;未提供则本步整体跳过、不影响任何现有流程(向后兼容)。** 详细方法论(唯一信源)见 [`references/test-design-methodology.md`](./test-design-methodology.md)「八之四」节,本处仅入口摘要。

**背景(与 T-NNN 的分工边界,务必分清):** 本 SKILL 已有「待澄清问题清单 / T-NNN」机制——那是**用例作者自己写用例时发现歧义 → 就地 `❓ 待澄清` 标注 → 挂起等答复**(面向 UNresolved、占位阻塞)。本步方向相反且互补:**消费一份上游已存在的《需求问题记录》** → 对每个被讨论/已澄清的需求点,**主动生成一条专项用例验证"约定的正确行为"**,标注来源编号做正向溯源(面向 resolved/contested 点的覆盖保证)。**二者不重叠、不并行造体系:** T-NNN 记"我不确定、等答案";本步记"这点被澄清过、这是专门验证它的用例"。**已澄清点若后又反悔转 UNresolved,仍走 T-NNN**(登记待澄清清单),不由本步处理。

**生成步骤:**
1. **读取** — 用 Read 读取《需求问题记录》,逐条解析条目(条目结构 `### 问题 #N` + 问题描述 / 涉及需求 / 问题类型 / 问题状态(待确认·已确认·已解答) / 解答内容),记录每条 `#N` 涉及的**功能点 / 模块**。
2. **补专项用例** — 在覆盖矩阵逐维覆盖(第五步系列)之外,**为每个澄清点补一条专项用例**,验证该澄清点约定的正确行为(如"评审确认金额保留 2 位小数" → 出一条验证金额展示为 2 位小数的用例)。用例名**末尾标注 `(需求问题#N)`**(与条目编号 `#N` 一一对应)。
3. **溯源** — 按本 SKILL **现有上游溯源格式**(markdown 链接 + 相对路径 + 精细锚点)在该用例元信息中加一行指向该澄清条目,例:
   `> **需求问题来源:** [问题 #3 金额小数位](../requirements/V1.0/需求澄清记录.md#问题-3-金额小数位)`
4. **覆盖登记** — 若某澄清点纯属流程/非功能约定、无可测行为,就地标注 `(需求问题#N) 无对应可测行为 — 不适用 + 原因`,不静默漏掉;所有澄清点须要么有专项用例、要么标不适用。

> **判定:** 提供了《需求问题记录》却存在澄清点既无 `(需求问题#N)` 专项用例、也未标不适用,判覆盖缺口(折进维度 13 溯源完整性核验,见 QR 维度 13;`check_case_stats.py --issue-record <记录路径>` 可机检 M/N 覆盖并列出未覆盖澄清点)。未提供本输入时本步不产出、不判定。

### 第五步之六:产品原始 PRD 存在性用例族(可选,消费产品 PRD 原文时启用)

> **仅当用户提供了「产品原始 PRD 原文」(`../requirements/{version}/产品提供/*.md` 等,自适应项目结构)可选输入时启用;未提供则本步整体跳过、不影响任何现有流程。有则强制消费。**

**背景(真缺口):** 本 SKILL 的需求基准默认是**研发需求**(研发 PRD)。但研发 PRD 由产品 PRD 转写而来,**产品 PRD 里明确要求、却在转写时被漏掉的条目**(某按钮 / 某列 / 某操作)——用研发需求作基准的用例**根本发现不了**,因为用例清单本身就不含那条。漏项根因正是「产品 PRD 条目没被转写进研发需求」,**若仍以研发需求为基准则同源污染**。故本步以**产品 PRD 原文**为独立基准,**绕过研发需求这一层**。

**生成步骤:**
1. **读取产品 PRD 原文** — 用 Read 逐条解析产品 PRD 原文的功能条目(按钮 / 列 / 操作 / 页面区块),记录每条的**行号 / 条目号**。
2. **逐条生成 `[PRD存在性]` 存在性用例** — 用例族标 `[PRD存在性]`(元信息「类型」字段 + 标题标注),断言「**页面必须存在 X 按钮 / 列表必须存在 Y 列 / 必须有 Z 操作**」这类存在性命题(可用 DSL `断言:存在文本"X"`)。**基准取产品 PRD 原文条目、不取研发需求**——这是本族关键,否则同源污染测不出漏项。
3. **正文引用产品 PRD 行号 / 条目号** — 每条用例元信息加一行 `> **产品PRD来源:** [显示文本(条目号 + 行号)](../requirements/{version}/产品提供/xxx.md#条目锚点)`(markdown 链接 + 相对路径 + 精细锚点 / 行号,格式同 S1)。
4. **逐条闭环** — 产品 PRD 每个可测存在性条目要么有一条 `[PRD存在性]` 用例、要么就地标 `无对应可测存在性 — 不适用 + 原因`,不静默漏。

> **判定:** 提供了产品 PRD 原文却存在条目既无 `[PRD存在性]` 用例、也未标不适用,判覆盖缺口(折进维度 1「产品 PRD 原文条目存在性覆盖」子条);该族失败可让下游 `auto-test-runner` 判 Critical。未提供本输入时本步不产出、不判定。

### 第五步之七:统计/金额双源对账用例族(窄口径放开 SQL 作断言依据)

> **适用范围(窄口径):** 仅**统计 / 汇总 / 计数 / 金额**类字段(如"订单总数""退款总额""在售商品数")。这类字段的正确性无法只靠"页面能打开、有数字"判定——常见漏洞是**软删除未过滤、状态未过滤、与另一系统口径不一致**,肉眼看不出。故对这类字段窄口径放开:用例可给出**等价 SQL** 作断言依据。**普通业务字段不适用本族,仍严禁 SQL。**

**用例族约定:**
- **类型标 `[双源对账]`**(元信息「类型」字段 + 标题标注),供下游 `auto-test-runner` 跨端识别。
- 用例含一个 **「双源对账」专段**(`**双源对账**:`),段内给三项:
  1. **①页面取值方式** — 该统计值在页面哪里、如何取(如"'订单管理'页顶部'订单总数'卡片数字")。
  2. **②等价 SQL** — 与页面口径等价的查询,**必须含软删除 / 状态过滤条件**(如 `WHERE del_flag = 0 AND status = 'paid'`);SQL **仅作断言依据、非操作步骤**。
  3. **③断言「页面值 == SQL 值」** — 断言页面取值与 SQL 结果一致(可用 `断言:页面值 == SQL 值`)。
- **SQL 只能出现在「双源对账」专段**,**严禁**写进步骤表操作列(步骤表仍是纯 UI 动作);`check_testcase_format.py` 据 `[双源对账]` 标记 + 「双源对账」段上下文放行专段 SQL、拦截步骤列 SQL,并校验专段 SQL 含软删除 / 状态过滤条件。
- 一条 `[双源对账]` 用例即同时覆盖「软删除未过滤 / 状态未过滤 / 与另一系统口径不一致」三类隐患。

**用例结构示例:**

```markdown
##### 用例 TC-ORDER-D01: [双源对账] 订单总数统计双源对账

> **优先级**: P1 | **类型**: [双源对账] | **测试项**: 统计对账 | **反向**: 否 | **覆盖**: F2
> **PRD 来源**: [§五-4 订单统计](../requirements/{version}/研发需求/订单.md#五-4)

**测试步骤**:

| 步骤 | 操作动作 | 操作对象 | 操作数据 | 预期现象 |
| :-: | :- | :- | :- | :- |
| 1 | 点击 | 左侧菜单"订单管理" | — | 进入"订单列表"页,顶部显示"订单总数"卡片 |
| 2 | 观察 | 顶部"订单总数"卡片 | — | 记录卡片显示的订单总数(如 128) |

**双源对账**:
- **①页面取值方式**: "订单管理"页顶部"订单总数"卡片数字
- **②等价 SQL(仅作断言依据,非操作步骤)**: `SELECT COUNT(*) FROM t_order WHERE del_flag = 0 AND status <> 'draft'`(含软删除 `del_flag=0` + 状态过滤)
- **③断言**: 页面"订单总数" == SQL 查询结果 `断言:页面值 == SQL 值`

**预期总结**:
- 页面统计口径与数据库一致;若软删除 / 状态未过滤,页面值会大于 SQL 值,暴露口径缺陷
```

> **判定:** 统计 / 汇总 / 计数 / 金额字段无 `[双源对账]` 对账用例、或对账 SQL 缺软删除 / 状态过滤条件,折进维度 8 判缺口。

> **交叉引用(统计字段可信度同族):** "页面用量/统计值为 0"既可能是**真没数据(真空态)**,也可能是**后端聚合某下游 500/超时/空返回被兜底静默返 0**——与本族"软删除/状态未过滤、口径不一致"同属"统计字段肉眼看不出的可信度隐患"family。故**反向 R12「依赖/数据源故障注入」用例(见第五步 R12 + 方法论第一节 R12 / 第八节)与本节双源对账并列于"统计字段可信度"**:双源对账查"口径对不对",故障注入查"数据源挂了会不会被静默兜底成 0";聚合 ≥2 数据源 / 有兜底返默认值逻辑的统计字段两者都应覆盖。

### 第五步之八:语义/口径变更类文案一致性用例族(`[文案一致性]`,消费「表 E」/「文案落点表」时启用)

> **仅当需求是语义 / 口径变更(上游提供「表 E:语义变更→派生展示物影响清单」/「文案落点表」,或 PRD 命中语义/口径变更)时启用;无语义变更需求则本步整体跳过、标 `不适用 + 原因`。有则强制消费。** 本族**复用**"原型内容基线为用例生成基准"章节已有的反向断言机制(`断言(反向):不存在文本"X"`),不另造平行体系——它是该机制在**文案维度**的延伸。

**背景(真缺口,实际项目缺陷):** 用量消费统计口径由「仅企业」扩为「企业+个人」,后端 / 接口 / 前端取数全改对,但**6 处解释该数值的 tooltip 有 1 处漏改**、仍写"仅统计企业级、不含员工个人消费",与实际展示值**相反**、误导对账(P1)。AI 测试全绿未抓到——**因为用例只断言数值、不断言文案**。根因:语义 / 口径变更时,数值取数改对不等于"所有解释该值的说明文案都同步改对";而正向断言(查"文案里有没有新口径字样")易被"文案里恰好有个『含』字"蒙混,**只有反向断言(查"旧口径字样是否残留")才能确定性拦截漏改的旧文案**。

**触发条件:** 上游有「表 E」/「文案落点表」,或 PRD / 详细设计命中"语义变更 / 口径变更 / 统计范围调整 / 含义扩缩"类需求。命中则对**每个处置=改写的展示位**(tooltip / 副标题 / 图例 / 帮助气泡 / 空态提示 / 列说明等一切"解释该数值口径含义"的说明文案)生成下述三类用例。

**用例族约定(类型标 `[文案一致性]`,元信息「类型」字段 + 标题标注,供下游 `auto-test-runner` 识别):**

1. **正向用例** — 断言该展示位文案**已体现新口径语义**(如 tooltip 含"含员工个人消费")。可附 `断言:存在文本"含员工个人"`。「反向」字段=否。
2. **反向用例(Critical,判失败关键)** — **复用反向断言 DSL**,断言**旧口径字样不再残留**:`断言(反向):不存在文本"仅统计企业级"` / `断言(反向):不存在文本"不含员工个人"`——旧口径字样一旦出现即 **Fail**。逐个"变更前语义"关键字样各出一条(或一条内多行断言)。「反向」字段=是。这是本族**拦截漏改的关键**,与 `[反向-残留]` 用同一条「不存在文本"X"」DSL、同一判失败语义(该处仍出现旧内容则 Fail)。
3. **一致性用例** — **文案声明的口径 ⟷ 该处数值的实际取数口径交叉验证**:验证"该展示位说明的统计范围"与"该处数值真实的取数范围"一致(如说明称"企业+个人",则数值应等于企业+个人合计,而非仅企业)。统计 / 金额类值可**配 `[双源对账]` DB 断言**落地(见第五步之七:等价 SQL 按新口径统计,断言页面值 == SQL 值),把"文案说的口径"与"数值真实口径"对齐。

**逐处置闭环:** 「表 E」/「文案落点表」中每个处置=改写的展示位,要么有一组 `[文案一致性]`(正 + 反 + 一致性)用例、要么就地标 `无对应可测展示位 — 不适用 + 原因`,不静默漏。反向用例的"旧口径字样"取自「表 E」的**变更前语义** / 「文案落点表」的**改前文案**;新口径字样取自**变更后语义** / **改后文案**。
**⭐ 本族的反向用例同属「零残留断言」,须与 `[反向-残留]` 一并登记进「零残留断言登记表」**(守护面 / 实跑命令 / 方向一·现状命中 / 方向二·阳性对照 / 退役状态),口径与硬门见第五步之零同名条目;旧口径字样常出现在**变更留痕注释**里,实跑时务必带注释前置(见方法论「八之二 · 零残留断言的实跑口径」)。

**用例结构示例:**

```markdown
##### 用例 TC-CONSOLE-C08: [文案一致性] 用量统计 tooltip 口径文案一致性(企业+个人)

> **优先级**: P1 | **类型**: [文案一致性] | **测试项**: 文案一致性 | **反向**: 是 | **覆盖**: F9
> **表 E 来源**: [用量口径变更(仅企业→企业+个人)](../requirements/{version}/研发需求/用量统计.md#表E-语义变更影响清单)
> **文案落点来源**: [#3 用量卡片 tooltip](../docs/design/{version}/详细设计.md#文案落点表)

**测试步骤**:

| 步骤 | 操作动作 | 操作对象 | 操作数据 | 预期现象 |
| :-: | :- | :- | :- | :- |
| 1 | 点击 | 左侧菜单"用量消费统计" | — | 进入"用量消费统计"页,顶部显示"总用量"卡片 |
| 2 | 悬停 | "总用量"卡片右上角"?"帮助图标 | — | 弹出 tooltip,显示口径说明文案 |

**预期总结**:
- 各展示位口径说明文案与新语义一致,旧口径字样零残留(反向断言拦截漏改);文案声明口径与该处数值真实取数口径一致
```

> **判定:** 提供了「表 E」/「文案落点表」(或 PRD 命中语义/口径变更)却存在处置=改写的展示位既无 `[文案一致性]` 用例、也未标不适用,或**缺反向用例(只断言新文案存在、不断言旧文案不残留)**,判覆盖缺口(折进维度 18)。该族反向用例失败可让下游 `auto-test-runner` 判 Critical。无语义变更需求时本步标 `不适用 + 原因`。

### 第五步之九:通用还原度套件(**不读业务语义,按页面类型逐类固定生成 · 强制**)

> **与本步其余各族的根本区别:其余族靠读懂需求,本族只看页面类型。** 下游实测 71 条已关闭缺陷里
> **96%(68/71)属「正常发现」**——走一遍正常流程就会碰到,却全部漏到 QA 侧。**问题不是测得不够狠,
> 是测得太晚。** 这批缺陷与业务领域无关,能被固定模板用例覆盖。

**做法(四类页面 × 固定模板项,逐条生成,每条标 `[还原度]`):**

| 页面类型 | 固定模板项 | 条数 |
| :- | :- | :-: |
| **列表页** | 字段守恒 / 按钮守恒 / 筛选排序守恒 / 空态 / 长文本截断+tooltip / 导出全量 / 导出与页面一致 / 编辑后自动刷新 / 大数据量加载 / 加载态无跳变 | **≥10(硬基线)** |

表里声明的每个编号必须真有一条同编号 `[还原度]` 用例,**⛔ 不得为凑数写假用例**——不适用的模板项

**上游输入(有则强制消费,无则回退):**
- **六类结构化原型内容基线**(数据字段 / 操作入口 / 统计卡片 / 筛选排序 / 空态·加载·错误态 / 二次确认)
  → 守恒类用例的"应有清单"直接取 `处置=实现` 的条目;无则从原型 `code/` 现场提取。

### 第五步之十:上游调用「日志可追溯」断言(`[日志可追溯]`,**本次新增/改动出站调用时**追加)

> **⚠️ 判据全文的唯一信源是 [`test-design-methodology.md`](./test-design-methodology.md) 八之六**
> (触发条件与适用边界 / 三条断言各自的「为什么不能删」/ 生成规则与闭环 / ★去重边界)。
> **本节只放入口摘要 + 用例结构示例**,勿在此复制第二份判据全文——照第五步之五的先例。

**一句话:** 本次迭代**新增或改动**了出站调用(第三方 HTTP API / 微服务 RPC·Feign / 对象存储 /
短信邮件消息网关 / 支付鉴权中心;**本地 DB 与本地缓存不算**)时,给相关用例追加三条固定断言 ——
**①正向(成功场景成对请求/响应行,含完整 URL 与 status + 上游业务 code + 耗时)+ ②级别(成功路径 INFO)
+ ③反向(日志中不存在明文凭据)**。本次没动出站调用则本族标 `不适用 + 原因`。

**上游输入:** 有 architect 检查项 35「上游调用日志与脱敏声明表」时,以表中**本轮新增 / 改动的那些行**
为基准逐行生成(⛔ 不是整表逐行——那张表登记的是该设计**全部**出站调用,与本族的窄口径触发不是一回事);
无该表则从详细设计 B.7 / 执行计划识别,并把「设计缺声明表」登记进待澄清问题清单。

**写法约定(与既有例外同款,细则见八之六):** 类型标 `[日志可追溯]`;断言写进「**日志可追溯**」专段、
**不进步骤表**(该段已由 `check_testcase_format.py` 的 end-marker 从步骤表扫描区剥离);步骤里确需体现
"去看日志"时**动作动词只用「观察」/「检查」/「记录」**。核心原则 1 与核心原则 7 已就此**成对开** 窄口径例外。

**用例结构示例:**

```markdown
##### 用例 TC-SMS-L01: [日志可追溯] 发送短信验证码成功时的上游调用日志

> **优先级**: P1 | **类型**: [日志可追溯] | **测试项**: 上游调用可追溯 | **反向**: 否 | **覆盖**: F7
> **PRD 来源**: [§三-2 短信验证码](../requirements/{version}/研发需求/账号.md#三-2)

**测试步骤**:

| 步骤 | 操作动作 | 操作对象 | 操作数据 | 预期现象 |
| :-: | :- | :- | :- | :- |
| 1 | 输入 | "手机号"输入框 | 13800000000 | 输入框显示手机号,"获取验证码"按钮变为可点击 |
| 2 | 点击 | "获取验证码"按钮 | — | 按钮变为倒计时 60s,页面提示"验证码已发送" |
| 3 | 观察 | 服务端应用日志 | — | 断言以下方「日志可追溯」专段为准 |

**日志可追溯**:
- **①正向断言(成功场景)**: 日志中存在**同一 traceId** 的请求行与响应行;请求行含**完整 URL**(含 query string)+ method + 入参;响应行含 **status + 上游业务 code + 出参 + 耗时**。`断言:请求行与响应行成对存在且 traceId 相同`
- **②级别断言**: 上述两行在**成功场景**下同样存在且为 **INFO**(不是只有失败时才打)。`断言:成功路径日志级别 == INFO`
- **③反向断言(凭据脱敏)**: `断言(反向):日志中不存在明文验证码 / 令牌 / 密钥 / 密码`

**预期总结**:
- 成功调用同样留下可配对的请求-响应日志,事后可追溯"对方返回了什么 code、慢在哪一跳";
- 补日志的同时完成脱敏,不因为补日志而放大凭据泄漏面
```

> **执行方式(必须就地标注):** 本族**仅人工 / 运维查服务端日志执行**,⛔ **不进 `auto-test-runner` 自动化** ——
> 该执行器的四原子能力(locate / act / observe / capture)全在 UI 面,**没有任何驱动能读服务端应用日志**
> (`[双源对账]` 为此专门加过 DB 断言驱动通道,本族没有对应通道)。别在用例里写"供下游自动化识别"。

> **判定:** 本次新增 / 改动了出站调用却无任何 `[日志可追溯]` 断言,或正向断言**没落在成功场景**上,
> 均折进**维度 18** 判缺口(详见 `quality-review-checklist.md` 维度 18「不通过标志」)。
