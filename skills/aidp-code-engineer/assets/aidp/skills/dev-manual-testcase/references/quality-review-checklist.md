## QR 模式对齐协议（模式 A 全量 / 模式 B 增量）

> **解决什么：** 用例生成侧早就分**模式 A（全量）/ 模式 B（增量，仅覆盖本次迭代变更点 + 受影响关键回归路径）**，
> 但 21 维度 QR **没有跟着分模式**——B 模式只产 1~2 个套件，QR 却仍按全量规格核对。
> 典型如维度 1「PRD 功规点 100% 覆盖」：B 模式下本就不该以**全量 PRD** 为分母。
> 结果要么误报覆盖不足、要么得靠调用方在 prompt 里临时解释，两种都不稳。

### 入参

QR 派发时**必须显式告知本轮模式**：`qr_mode = A | B`。B 模式下另传 **`qr_delta_scope`**
（本轮变更点清单：功规点 / 页面 / 接口 / Task 编号，须可核对）。
**不传 = 模式 A（全量）**，与本协议上线前完全一致。

### 三档（对照上表最后一列）

| 档 | 模式 A | 模式 B |
| :- | :- | :- |
| **Δ** | 全部用例逐条核 | 只核 Δ 内用例，标准不降；Δ 外标 `前滚（未变更）`+ 依据的上一轮报告 |
| **全量** | 全量 | **仍然全量**，不接受裁剪 |
| **基线缩放** | 分母 = 全量 PRD / 全量用例集 | **分母换成 Δ 内的变更点集合**，且报告里**必须写明分母口径** |

### 分母口径怎么写（B 模式强制）

> ⛔ 只写「覆盖率 100%」是不合格的——分母是什么没人知道，这个数就没有意义。

- 维度 1：`本轮分母 = 变更点涉及的 12 个功规点（非全量 PRD 的 184 条）；覆盖 12/12`
- 维度 19：`本轮分母 = 增量用例 14 条；数量基线按增量口径不判绝对值（脚本 3a/3 两项本就是 warning-only、不占退出码），
  但反向占比 ≥40% 与 P0/P1/P2 分布照判——它们是质量要求，不随规模豁免`
- 维度 13 / 18：同理，写明「本轮矩阵的行集合 = Δ 内变更点」

### 四条安全网（缺一不可）

1. **语义/口径类变更强制扩散**：命中「语义 / 口径 / 单位 / 默认值 / 状态机 / 权限范围变更（无新增实体）」或
   跨版本作废判定 → 受影响页面/功规点**强制并入 Δ**，即便本轮没有新增用例。
   —— 与上游 ux 表 E / 表 F、`[文案一致性]` 用例族是同一条契约：**这类变更的特征就是「页面零新增元素」**，
   靠「本轮改了哪些文件」驱动的 Δ 必然漏掉。
2. **共享单元传播**：变更落在**跨套件共享单元**（登录/入口流程、公共组件、共享测试数据、全局字典枚举）→
   **所有引用它的套件并入 Δ**。
3. **全量档不可裁剪**（★ 与下游原始提议的唯一实质分歧，理由见下）。
4. **算不出 Δ 就退回模式 A** 并在报告首行注明。⛔ 严禁猜一个 Δ。

> **★ 为什么维度 11 / 14 / 16 必须留在「全量」档：**
> 维度 11 查 **TC-ID 全局唯一**——重号是「新用例与旧用例」撞的，只看 Δ 内部永远查不出；
> 维度 16 查 **自测方案 ⟷ 用例双向引用闭环**——B 模式最典型的缺陷就是
> **「新增了用例文件、忘了在方案 §8 里登记」**，而这只有拿方案对全量用例文件才看得见；
> 维度 14 同理（拆分一致性是整棵目录树的属性）。**把这三个纳入裁剪，等于精准关掉增量最需要的三道门。**

### QR 执行台账（报告强制段落）

| 维度 | 本轮模式/范围 | 机器门退出码 | 语义结论 | 分母口径 / 依据 |
| :-: | :-: | :-: | :-: | :- |
| 1 | B · 基线缩放 | — | 通过 | 分母 = 12 个变更功规点（非全量 184 条），覆盖 12/12 |
| 11 | B · **全量** | `check_testcase_format.py` = 0 | 通过 | 全量档：重号由新旧用例共同构成 |
| 16 | B · **全量** | `check_test_plan_alignment.py` = 0 | 通过 | 全量档：查「新文件有没有被方案登记」 |
| 6 | B · Δ | — | 通过 | 增量模式专属维度 |
| 20 | — | — | — | **未启用：按门控铁律不留行**（本行仅为说明，实际报告中不出现） |

**四条硬要求：**
- **21 行一行不少**——维度 14（多文件）未触发也留行写 `N/A + 单文件模式`；
  **唯一例外**是维度 20 WebMCP 未启用时按门控铁律**连行都不留**（与其它条件维度口径刻意不同）。
- 基线缩放档的行**必须**写出分母口径，只写百分比一律判该维度**未完成核验**。
- 标 `前滚` 的行必须写明依据的上一轮报告；写不出来按**未跑**处理、退回该维度全量核对。
- 机器门那列**照抄退出码**；⚠️ 本 SKILL 多个脚本的 Important 档**不占退出码**
  （维度 9 / 14 的 DOM 选择器与命名、维度 13 的 `step_acceptance_coverage`），
  台账里必须另记 `--json` 读到的结论，**不能只贴一个 0 就算过**。

## 🎯 一、覆盖率核验类(对照 PRD / 设计 / 研发执行计划)

### 维度 1:PRD 功规点 100% 覆盖(**最高优先级**)

**检查目标:** 用例必须 100% 覆盖 PRD 中定义的全部功规点,**任何遗漏直接判定为 Critical 不通过**。

**核验步骤:**
1. 解析 PRD 的"五、页面交互明细"章节,提取所有页面/功规点(以 `五-1`、`五-2`...或 `5.1`、`5.2`...为单位)
2. 解析用例文档每条用例的"PRD 来源"引用(如 `PRD 来源: xxx > 五-3 用户管理`)
3. 生成覆盖率矩阵:

```markdown
| PRD 功规点 | 章节 | 覆盖用例 TC-ID | 覆盖状态 |
| :- | :- | :- | :-: |
| 用户登录 | 五-1 | TC-LOGIN-001, TC-LOGIN-002, TC-LOGIN-003 | ✅ 已覆盖 |
| 用户列表 | 五-2 | TC-USER-001, TC-USER-002 | ✅ 已覆盖 |
| 用户详情 | 五-3 | — | ❌ 未覆盖 |
| 批量导入 | 五-4 | TC-USER-I01 | ⚠️ 仅 1 条,建议补充异常场景 |
```

4. 计算覆盖率:`已覆盖功规点数 / PRD 总功规点数 × 100%`
5. **必须达到 100% 覆盖**才能通过此维度

**优先级匹配检查:**
- PRD 标注为核心/主流程的功规点 → 至少 1 条 **P0 用例**
- PRD 标注为重要分支的功规点 → 至少 1 条 **P1 用例**

**详细设计缓存方案覆盖(对应核心原则 12):**
- 若详细设计 A.2 存在「缓存方案」子章节(用户已确认使用缓存),涉及缓存的接口对应套件**必须**含「缓存命中 / 主动失效 / TTL 过期」3 类用例(标题带 `[缓存场景]` 标记);若设计无缓存方案则本项 N/A

**⭐ 产品 PRD 原文条目存在性覆盖(有产品 PRD 输入时强制,Critical 子项 — 对应 SKILL 第五步之六):**
- **仅当**用户提供了「产品原始 PRD 原文」(`../requirements/{version}/产品提供/*.md` 等)可选输入时强制;未提供则本子项标 `N/A(未提供产品 PRD 原文)`
- 判定基准是**产品 PRD 原文条目**(**而非研发需求**)——因为漏项根因正是「产品 PRD 条目未被转写进研发需求」,以研发需求为基准会同源污染、测不出漏项
- 产品 PRD 原文的每个可测存在性条目(某按钮 / 某列 / 某操作)**要么**有一条标 `[PRD存在性]` 的存在性用例(断言"页面必须存在 X"、正文引用产品 PRD 行号 / 条目号)、**要么**就地标 `无对应可测存在性 — 不适用 + 原因`,不得静默遗漏
- **不通过:** 提供了产品 PRD 原文却存在条目既无 `[PRD存在性]` 用例、也未标不适用;或 `[PRD存在性]` 用例未引用产品 PRD 行号 / 条目号(**该子项失败可让 auto-test-runner 判 Critical**)

**反向核验:**
- 用例文档中是否存在 PRD 未定义的"额外功能"用例?如有,列出并提示"该功能在 PRD 中未提及,请确认是否需要保留"

**不通过标志:**
- 任一 PRD 功规点的"覆盖用例"列为空
- 覆盖率 < 100%
- P0 功规点无 P0 用例
- 详细设计有「缓存方案」但缺「缓存命中 / 主动失效 / TTL 过期」三类用例(违反核心原则 12)
- (有产品 PRD 原文输入时)产品 PRD 原文条目存在既无 `[PRD存在性]` 用例、也未标不适用

### 维度 2:字段规格与校验规则覆盖

**检查目标:** PRD 字段规格表(六、数据字段)或详细设计中定义的每个字段及其校验规则,必须有对应用例验证。

**核验步骤:**
1. 提取 PRD/详细设计中所有字段规格(字段名、类型、必填、长度、格式、错误提示)
2. 对每个**必填字段**:必须有 1 条"留空提交"异常用例,验证错误提示文案与 PRD 一致
3. 对每个**格式校验字段**(手机号/邮箱/身份证/URL 等):必须有"格式错误"和"格式正确"各 1 条用例
4. 对每个**长度限制字段**:必须有"超长提交"用例
5. 对每个**特殊字符过滤字段**:必须有"含特殊字符提交"用例(如 `<>&`、emoji、SQL 注入特征 `' OR 1=1`)

生成覆盖率矩阵:

```markdown
| 字段 | 必填校验 | 格式校验 | 长度校验 | 特殊字符 | 覆盖状态 |
| :- | :-: | :-: | :-: | :-: | :-: |
| 用户名 | TC-USER-002 | — | TC-USER-005 | TC-USER-008 | ✅ |
| 手机号 | TC-USER-002 | TC-USER-006 | — | — | ⚠️ 缺长度校验 |
| 邮箱 | TC-USER-002 | ❌ 缺 | — | — | ❌ 缺格式校验 |
```

**不通过标志:** 任一必填字段无"留空"用例,或任一格式字段无格式错误用例。

### 维度 3:字典/枚举与状态机覆盖

**检查目标:** PRD 字典枚举表(七、字典枚举)定义的所有状态、类型、分类,必须有对应用例触发或验证。

**核验步骤:**
1. 提取 PRD 七、字典枚举表中所有枚举值(状态码 / 类型 / 角色)
2. 对每个**状态枚举**:必须覆盖所有合法迁移路径(如订单 `待支付 → 已支付 → 已发货 → 已完成`,以及 `待支付 → 已取消`)
3. 对每个**类型/分类**:每种类型至少有 1 条用例验证其展示/筛选行为
4. 对**不可迁移路径**(如"已上架不可编辑"):必须有用例验证约束生效

生成状态机覆盖矩阵:

```markdown
| 业务对象 | 状态迁移路径 | 覆盖用例 | 状态 |
| :- | :- | :- | :-: |
| 订单 | 待支付 → 已支付 | TC-ORDER-002 | ✅ |
| 订单 | 已支付 → 已发货 | TC-ORDER-003 | ✅ |
| 订单 | 待支付 → 已取消 | TC-ORDER-005 | ✅ |
| 订单 | 已完成 → 已取消(不可) | ❌ 缺 | ❌ 缺约束验证 |
```

**不通过标志:** 任一合法状态迁移路径无对应用例;或不可迁移路径无约束验证用例。

### 维度 4:角色权限矩阵覆盖

**检查目标:** PRD 角色权限说明(四、RBAC)和权限差异矩阵(七·2)定义的所有角色×页面组合,必须有用例验证可见性/可操作性差异。

**核验步骤:**
1. 提取 PRD 四、RBAC 章节中所有角色(如:系统管理员/部门管理员/普通员工/未登录)
2. 提取每个受权限保护的页面/功能
3. 对每个角色×页面组合:至少有 1 条用例验证该角色访问该页面时的差异(可见字段、可执行按钮、数据范围)

生成权限覆盖矩阵:


### 维度 5:异常路径覆盖

**检查目标:** PRD 异常路径处理章节(八、异常处理)定义的所有异常场景,必须有用例验证用户可见的处理方式。

**必须覆盖的异常类型:**
- **接口异常**:401 未授权(跳登录页)、403 无权限、404 资源不存在、500 服务错误
- **网络异常**:断网、请求超时
- **数据边界**:空列表、单条数据、超大数据量(若 PRD 有规定阈值)
- **并发冲突**:重复提交、数据被他人修改(乐观锁)
- **操作约束**:已上架不可编辑/删除、已生效订单不可取消
- **下游数据源静默降级(R12,聚合 ≥2 数据源 / 有兜底返默认值逻辑时)**:后端聚合多下游,某下游 500/超时/空返回被兜底静默返 0/空 → 页面须**显式失败提示 / partial 标记**,**禁静默显示 0/空**(否则"用量为 0"与"真没数据"无法辨别);须与"真空态(R5)"用例配对验证两者可区分。区别于上文 500/断网/超时——那些是请求层能看出出错,本项专治"后端返 200 但内部数据源被静默兜底"

```markdown
| 异常类型 | PRD 章节 | 覆盖用例 | 状态 |
| :- | :- | :- | :-: |
| 401 未授权 | 八-1 | TC-LOGIN-004 | ✅ |
| 网络断开 | 八-3 | ❌ 缺 | ❌ |
| 空列表 | 八-5 | TC-USER-010 | ✅ |
| 并发冲突 | 八-6 | ❌ 缺 | ❌ |
```

**不通过标志:**
- 任一 PRD 定义的异常场景无对应用例(网络断开/超时/并发冲突等容易遗漏)。
- **下游数据源静默降级(注入后仍显示 0/空且无失败提示/partial 标记)** —— 聚合 ≥2 数据源 / 有兜底返默认值逻辑的功能点,未生成 R12 故障注入用例,或注入下游 500/超时/空返回后页面仍静默显示 0/空、无提示,又未与 R5 真空态配对验证可区分。

### 维度 8:步骤四要素完备性 + UI 可操作性

**四要素完备:** 每个步骤必须包含**操作动作、操作对象、操作数据(或 —)、预期现象**四要素。遗漏任一项即不通过。

**UI 可操作性(无代码级动作):** 扫描用例文本,如出现以下关键词需立即标注为不通过:
- "调用接口"、"发送请求"、"POST /api"、"GET /api"
- "查询数据库"、"执行 SQL"、"SELECT"、"INSERT"
- "查看日志"(除非有对应的日志查看 UI 页面)
- "查看缓存"、"Redis"、"键"

**例外:** 在"跨系统验证清单"中说明"可视化查看入口"的场景允许,但必须提供具体的查看 UI 路径。

**⭐ 窄口径例外——`[双源对账]` 统计对账用例(Critical 子项,SQL 豁免边界):** 仅**统计 / 汇总 / 计数 / 金额**字段的 `[双源对账]` 用例,允许在其「**双源对账**」专段内出现**等价 SQL 作断言依据**(非操作步骤),且 SQL **必须含软删除 / 状态过滤条件**。豁免边界严格限定,任一越界即不通过:
- ① 用例须标 `[双源对账]`(元信息「类型」+ 标题);未标却用「双源对账」段夹带 SQL 规避禁令 → 不通过
- ② SQL 只能在「双源对账」专段,**步骤表操作列出现 SQL 仍判不通过**
- ③ 「双源对账」专段 SQL 缺软删除 / 状态过滤条件(应含 `del_flag` / `is_deleted` / `status` / 状态 等)→ 判缺陷
- ④ 统计 / 汇总 / 计数 / 金额字段**缺** `[双源对账]` 对账用例(只测"页面有数字")→ 判缺口(**该子项失败可让 auto-test-runner 判 Critical**)
- **另:** 用例级「**前置数据编排**」段(测试步骤之前)内的 `SQL造删数` / `调对方接口` 属跨系统造数编排、不是被测应用操作步骤,不受本维度 SQL 禁令约束(`check_testcase_format.py` 只扫「测试步骤」区域);但被测应用自身步骤表仍严禁 SQL / 接口

**自动化辅助:** `check_testcase_format.py` 自动检测(含 `[双源对账]` 标记识别 + 「双源对账」段 SQL 放行 / 步骤列 SQL 拦截 + 专段 SQL 软删除 / 状态过滤条件校验)。

**13.5 与实际代码一致性检查(已有代码时 Critical)**

如果项目已有正式开发的代码,必须检查以下信息是否从实际代码中提取:

1. **URL 路径一致性:**
   - [ ] 读取前端路由配置文件(如 `router.js`、`routes.ts`、`vue-router` 配置)
   - [ ] 对比用例中的 URL 路径(如 `/user/list`、`/admin/billing`)是否与代码一致
   - [ ] 不通过标志: 用例中的 URL 路径与代码不一致,或明显是推测的(如"应该是 `/api/user/list`")

2. **页面文案一致性:**
   - [ ] 读取前端页面组件(如 `.vue`、`.tsx`、`.jsx` 文件)
   - [ ] 对比用例中的按钮文案、菜单文案、页面标题是否与代码一致
   - [ ] 不通过标志: 用例中的文案与代码不一致,或使用了"应该是'提交'按钮"等推测性描述

3. **Toast/错误提示一致性:**
   - [ ] 读取国际化文件(如 `i18n/zh-CN.json`、`locales/`)或前端代码中的提示语
   - [ ] 对比用例中的 Toast 提示、错误提示文案是否与代码一致
   - [ ] 不通过标志: 用例中的提示文案与代码不一致,或使用了"应该提示'操作失败'"等推测性描述

4. **状态枚举值一致性:**
   - [ ] 读取后端枚举定义(如 `enums/`、`constants/`)或前端常量
   - [ ] 对比用例中的状态值(如"待支付"、"已支付")是否与代码一致
   - [ ] 不通过标志: 用例中的状态值与代码不一致

5. **字段校验规则一致性:**
   - [ ] 读取前端校验代码或后端校验逻辑
   - [ ] 对比用例中的校验规则(如"长度 2-50 个字符")是否与代码一致
   - [ ] 不通过标志: 用例中的校验规则与代码不一致

**检测方法:**
```bash
# 1. 读取路由配置
find . -name "router.js" -o -name "routes.ts" -o -name "router.ts" | xargs grep -n "path:"

# 2. 读取前端组件文案
find . -name "*.vue" -o -name "*.tsx" -o -name "*.jsx" | xargs grep -n "label\|placeholder\|title"

# 3. 读取国际化文件
find . -path "*/i18n/*" -o -path "*/locales/*" | xargs cat

# 4. 读取枚举定义
find . -path "*/enums/*" -o -path "*/constants/*" | xargs grep -n "enum\|const"
```

## 🧩 五、需求字段对账类

### 维度 17:列集合 vs 需求字段核对用例覆盖(**Critical**)

**检查目标:** 每个含**列表 / 表格 / 表单**的功能点,必须有一条「列集合 vs 需求字段」逐列核对用例(或主流程用例中的专门核对步骤),逐列比对页面实际呈现的**列展示名 / 字段标签(语义名)**与**研发需求的需求字段清单(语义) /『需求字段→处置』对照表**是否一致(核对的是页面呈现的语义展示名,而非代码级字段名)——而**不仅是**"页面可打开 + 数据加载成功"。

> **🛡️ 背景:** 列表/表格/表单类功能点若只测"页面能打开、列表有数据",会漏掉**缺列 / 多列 / 列展示名错 / 展示顺序错 / 展示了本应裁剪的字段 / 漏了应前端计算还原的字段**等结构性偏差。本维度强制把"列集合与需求字段清单逐列对账"作为这类功能点的必测项。

**适用判定:** 功能点页面含表格(列表/明细表)、表单(新增/编辑表单)即纳入本维度;纯跳转/纯按钮/纯文本展示页可标 `N/A(无表格/表单)`。

**核验步骤:**
1. 从用例文档识别所有含表格/表单的功能点(对应套件 + TC-ID)
2. 对每个这类功能点,核对是否存在「列集合 vs 需求字段」核对用例 / 步骤,且该用例 / 步骤逐项覆盖以下 4 个子项:
   - **a. 列展示名 / 字段标签(语义)一致**:每一列表头文案、每一个表单字段标签(均为业务语义名),与需求字段清单逐一对照,文案一致
   - **b. 展示顺序 / 字段顺序一致**:表格从左到右、表单从上到下的呈现顺序与需求字段清单一致
   - **c. 无缺列 / 无多列**:不缺少需求字段清单标「保留」的字段,也不出现需求字段清单 + 处置对照表之外的额外列
   - **d. 与「需求字段→处置」对照表一致**:标「保留」正常展示;标「裁剪」不出现;标「前端计算还原」有值且口径正确;标「请第三方补」按对照表暂行处置呈现(占位/置灰/隐藏)
   - **e.(列表类页面强制)「列表列完整性」结构用例**:每个**列表 / 表格类页面**须有一条独立的「列表列完整性」结构用例(用例类型标 `列表列完整性`),断言固定形态「**表格自左至右应依次为 A / B / C / …,缺列或多出未登记列即 Fail**」,且**期望列序列取自详细设计的「字段实现清单」**(dev-logic-architect 产出的字段级实现清单表:`列名/字段 | 顺序 | 数据来源（接口字段） | 展示规则 | 上游出处`),形成"设计 → 用例 → 实现"闭环——测**结构**(该有哪些列、什么顺序),而非仅**行为**。详设无「字段实现清单」时回退取 PRD 需求字段清单 + 原型表头并登记 T-NNN,不臆造。**缺此结构用例判不通过。**
3. 生成列集合对账覆盖矩阵:

```markdown
| 功能点(表格/表单) | 套件 | 列集合核对用例/步骤 | 列名 | 列顺序 | 缺/多列 | 处置表一致 | 列完整性结构用例 | 状态 |
| :- | :- | :- | :-: | :-: | :-: | :-: | :-: | :-: |
| 用户列表 | SUITE-USER | TC-USER-001 步骤 2-3 | ✅ | ✅ | ✅ | ✅ | ✅ TC-USER-003 | ✅ |
| 订单明细表 | SUITE-ORDER | TC-ORDER-002 步骤 4 | ✅ | ✅ | ❌ 漏"优惠金额"列 | — | ❌ 缺 | ❌ |
| 新增用户表单 | SUITE-USER | ❌ 缺 | — | — | — | — | N/A(表单非列表) | ❌ 缺列集合核对 |
```
（"列完整性结构用例"列:列表/表格类页面须填对应「列表列完整性」用例 ID;纯表单页无列表可标 `N/A(表单非列表)`。）

**不通过标志(任一即不通过):**
- 任一含表格/表单的功能点**仅有**"页面可打开 + 数据加载成功"类用例,**无**「列集合 vs 需求字段」逐列核对用例 / 步骤
- 列集合核对用例 / 步骤缺 a/b/c/d 任一子项(只对列展示名不对展示顺序、不对缺多列、不对处置表一致)
- **任一列表 / 表格类页面缺「列表列完整性」结构用例(子项 e):无一条断言"表格自左至右应依次为 A / B / C / …,缺列或多出未登记列即 Fail"、期望取自详设「字段实现清单」的独立结构用例**
- 核对未引用需求字段清单(语义) /『需求字段→处置』对照表(凭空罗列列名,无对账依据)
- 预期现象只写"列表加载成功 / 表格有数据",未写明与需求字段清单(语义) / 处置对照表的逐列一致性结论

## 🧮 六、完备性度量类(对照测试设计方法论)

> 维度 18/19 以唯一信源 [`test-design-methodology.md`](./test-design-methodology.md) 为对照基准,与 SKILL 执行流程"第七步:覆盖率回检"共用同一套判据,**不构成第二信源**。本组解决下游反馈的"用例偏少、只堆正向 happy path、异常/边界/权限/状态流转/并发漏、数量不稳定无完备性下限"。

### 维度 18:覆盖矩阵逐维确认 + 测试设计方法论套用(**Critical**)

**检查目标:** 每个功能点是否按覆盖矩阵(正向 9 维 F1-F9 + 反向 12 维 R1-R12,见方法论第一节)逐维过一遍、不适用维度是否就地标注 `不适用 + 原因`;受约束字段是否套用 BVA 六点法(方法论第二节)+ 等价类有效/无效枚举(第三节);有状态对象是否含状态机**非法迁移"被拦截"**用例(第四节);写操作功能点是否核对并发/竞态 C1-C6 适用项(第五节);**聚合 ≥2 数据源 / 有兜底返默认值逻辑的功能点是否含 R12 依赖/数据源故障注入用例(注入下游 500/超时/空返回 → 显式失败提示/partial 标记、禁静默 0/空,且与 R5 真空态配对可区分)**;命中方法论第八节特殊场景触发条件的是否补齐对应用例;**并含「原型内容基线覆盖度」子条(见下)——用例集是否一一对应原型内容基线的"实现"项(元素 + 交互态 + 操作逻辑三层),无遗漏。**

> **🛡️ 背景:** 只堆正向 happy path、临时想到哪测哪,是"用例偏少、覆盖不全"的根因。本维度强制用覆盖矩阵 + BVA + 等价类 + 状态机 + 并发这套系统化方法逐维过一遍,把隐性遗漏变成显性可查。**另一根因是"用例不以原型可见元素/操作逻辑为基准生成"——原型画了但 PRD 未逐条列全的内容/行为一旦实现里缺失就测不出来;故本维度增设「原型内容基线覆盖度」子条,把用例广度基准下沉到原型内容基线(AIDP 约定4三层)。**

**⭐ 子条:原型内容基线覆盖度(元素 + 交互态 + 操作逻辑,AIDP 对齐):**
- **基准来源(有则消费无则回退):** 上游 AIDP 若已产出 `原型内容基线.md`(逐页可见元素 + 交互态 + 操作逻辑/交互流 + 处置列)/ `DESIGN-MANIFEST.json`(requiredStates/flows),**强制以其为对照基准**;无则回退——对照原型 `code/` 现场逐页提取的可见元素与操作逻辑。路径自适应项目结构,不臆造上游产物、不硬依赖其存在。
- **核对(三层,完整比对由 Agent 语义完成):** 基线中每个**处置="实现"** 的 ① 可见元素(区块/卡片/表格列/表单字段/筛选排序/按钮次级操作/跳转)② 交互态(requiredStates:空态/加载/错误/成功/禁用…)③ 操作逻辑/交互流(flows:校验规则与时机/字段联动/条件显隐禁用/增删改保存取消/二次确认/默认值/多步步序/错误处理/权限态差异)是否**各有 ≥1 条可验证用例**。
- **不覆盖项登记:** 处置=**裁剪/延期/改为X** 的项不要求正向用例,但必须在用例文档"原型内容基线覆盖登记"小节或功能点处标注 `不覆盖,原因:<引用约定4三件套(视觉/内容/操作逻辑)对应处置说明>` 并溯源;**静默漏(既无用例又无不覆盖标注)即不通过。**
- **⭐ 裁剪/延期项强制配 `[反向-残留]` 反向断言用例(不止登记):** 处置=**裁剪 / 延期**的元素,除登记原因外,须有一条 `[反向-残留]` 反向断言用例——用 DSL「**不存在文本"X"**」(`断言(反向):不存在文本"X"`)表达"该元素仍存在则 Fail",捕获"该删没删 / 该延没延"的残留(处置=**改为X** 项按新语义走正向用例,不需残留断言);**裁剪 / 延期项缺此 `[反向-残留]` 反向用例判缺口。**
- **边界:** "用项目已有组件实现"只约束组件选型层,不豁免三层对齐 (AIDP 约定28)。无 AIDP 产物且原型极简/纯后端时可标 `不适用 + 原因`。

**⭐ 子条:零残留断言登记表(守护面 / 复现片段 / 退役,折入本维度·维度计数不变):**

> **「零残留断言」** = 一切「**不存在文本 X**」形态的反向断言,含 `[反向-残留]`(裁剪/延期项该删没删)
> 与 `[文案一致性]` 的反向用例(旧口径字样残留)。它们**只增不退**:下游实测规划期 20 条、
> 两个 Sprint 后 33 条,而规矩是「每条写完当场实跑两个方向」+「每轮收尾原则上全部重跑」,
> **成本线性增长且不可逆**。

⚠️ **先说不能动的部分:「每条写完必须当场实跑两个方向」这条规矩不削弱、不打折。**
它是这套断言唯一的质量来源——下游正是靠它在**写代码之前**抓出「式子会误命中 javadoc 交叉引用」。
本子条要补的是它**没覆盖的两件事:退役与选择性执行**。

**⭐「两个方向」的确切含义(下游实测按这两条各自失效过,别只跑一个):**

| 方向 | 跑什么 | 期望 | 只跑它会漏什么 |
| :- | :- | :-: | :- |
| **方向一·现状实跑** | 在当前代码树上跑这条式子 | **0 命中** | 只跑它 → **恒 0 的假绿**:式子本身写错/写窄,永远不会命中,而报告一路全绿 |
| **方向二·阳性对照** | 对着**必然命中的已知样本**跑同一条式子 | **≥1 命中** | 只跑它 → 证明了式子能红,但没证明现状已清干净 |

**⭐ 方向二的产物就是「反向复现片段」——两个名字,同一件东西,别当成两项义务。**
方法论「八之二」探测类断言三项自检第 3 条要求「期望值为 0 的反向断言必须构造一个必然命中的
已知样本,当场运行并记录结果」,本子条要求「反向复现片段 = 能让它失败的最小片段(原始违规文本 +
出处路径)」——**同一个样本,一次实跑同时兑现两条规则**。下游实测正是把二者读成了两件事:
一条断言只跑了方向一、全绿交付,后来额外手工补一条对照用例才证明它不是恒 0 的假绿。
⛔ 因此登记表里**阳性对照命中数为 0 或留空 = 这条断言未经验证**,与「根本没写」同档。

**⭐ 实跑口径(排除注释)见方法论「八之二 · 零残留断言的实跑口径」,那里是唯一信源、本处不复述。**
一句话:**默认取材方式是块级剥离**
`python3 <SKILL_DIR>/scripts/strip_comments.py '<守护面>' | grep -E '<式子>'`——
它把行级前置的三个漏面(`/* */` 块中间行 / `<!-- -->` 跨行块中间行 / 行尾注释)一次关掉,
且不会误吞字符串里的 URL 与 Markdown 列表项。之所以必须排除注释:下游实测一轮 8 条断言
初稿 5 条假红、**全部**命中的是本 Sprint 自己写的防回退注释,是**模式不是偶发**
(该根因**跨 4 个版本复发 5 次**);断言目标本身就是注释内容时用 `--only-comments`
**并就地写明理由**。
⚠️ **行级 grep 前置保留为退路**(项目里跑不了 Python 时),走退路时
**登记表「实跑命令」列必须写明「行级前置」**,否则无法判断结论可不可信;
**且那张「前缀集按守护面涵盖的文件类型选」的固定表只适用于退路**——
(`#` / `--` 何时能加、`/\*` 已同时覆盖 `/*` 与 `/**` 不必另加、**守护面涵盖 `.md` 时必须去掉 `\*`**
——行级默认集里的 `\*` 会把 Markdown 列表项与整行加粗一起静默吞掉,方向是**假绿**,
而「全站不得出现」类断言的守护面 `**` 天然涵盖 `.md`);
下游第 5 次复发的直接原因正是「项目自己加的排除集漏了一项」。
**块级剥离没有这一整类问题**(它对 Markdown 只剥 `<!-- -->`、且围栏内一律不剥),
这正是把它定为默认的原因。

**登记形态(每条零残留断言必须带三个字段):**

| 字段 | 要求 | 判不通过的写法 |
| :- | :- | :- |
| **守护面** | 文件/目录 glob,多条用 `;` 分隔。**必须由登记时正向实跑的命中文件集合导出**,不得凭印象手写 | 空 / 手写一个「大概在这一块」的目录 |
| **反向复现片段** | 能让该断言**失败**的最小片段(原始违规文本 + 出处路径) | 只记「已验证通过」这类结论 |
| **退役状态** | `在役` / `已退役(轮次 + 依据)` | 直接从清单里删掉 |

**⭐ 承载形态:用例文档必须有一节「零残留断言登记表」**(全量模板「七之三」/ 增量模板「八之三」),
固定 7 列 `# | 断言 | 守护面 | 实跑命令 | 方向一·现状命中 | 方向二·阳性对照 | 退役状态`,逐格填实。
配硬门 `check_residual_assertions.py`(Z1 有零残留断言却缺登记表 = **Important**〔存量文档会大面积
命中,一上来判死会让整个硬门被无视,同 `check_upstream_call_log_spec.py` 的 U1 取舍〕;表**一旦产出**,
Z2 缺列 / Z3 逐格空或占位 / Z4 **两个方向任一**读不到 `N 命中`(阳性对照另加「命中数为 0」)/
Z5 以「多轮未红」为由退役或 `已退役` 后没有任何依据 / Z6 文档里的零残留断言漏登记进表 /
**Z7 数据行格数不符**(最常见根因:实跑命令里的 `|` 未转义为 `\|`)= **Critical**;
另有 W2 实跑命令缺前置声明 / W3 方向一命中 > 0 = Important 仅告警)。
⚠️ **`--json` 的 `read_errors` > 0 时,`assertions` / `rows` 是残缺样本上的结果**——
有文件读不出来,「0 条断言」不代表真没有断言,须先解决可读性再看结论。
⚠️ **脚本只判登记表的形态,判不了「那两个方向是不是真跑过」**——那属语义层,由 QR 子 Agent
对照实跑记录核;**脚本全绿 ≠ 本子条通过**。

- **守护面必须导出、不得手写**:正向实跑本来就会告诉你「这条式子命中了哪些文件」,
  守护面就取那个集合的最小覆盖 glob。手写的守护面是**对断言真实作用域的猜测**,
  猜窄了就等于给这条断言开了一扇永远不会被触发的后门——而且**它仍然天天报绿**。
- **语义是「全站不得出现」的断言,守护面只能写 `**`**。这类断言(如旧口径字样全站零残留)
  的失效形态恰恰是「**别处**又冒出来一份」,把它的守护面缩窄,等于把它变成一条查不出问题的断言。
  ⚠️ 这不是特例豁免,而是「守护面须覆盖断言真实作用域」这条规则的**自然结果**——
  只要守护面是照实登记的,它自然会与每一轮 diff 相交、自然每轮都跑。
- **反向复现片段是抗腐化的唯一手段**:断言写完那一刻是能失败的,但半年后文件改名/文案重构,
  它可能**永久失去命中能力却始终全绿**——「常绿」与「已腐化」在报告里长得一模一样。
  留着复现片段,任何时候都能零成本重验「这条断言现在还能不能红」。

**退役(只有两条合法路径,都必须登记,⛔ 不许静默删):**

1. **守护对象已消失** —— 整页/整模块被删除,断言守护的东西不存在了。登记退役轮次 + 依据。
2. **判据已移交常设机制** —— lint 规则 / CI grep 门 / 硬门脚本接管了同一判据。登记接管者。

⛔ **「跑了很多轮都没红过」不是退役理由。** 零残留断言的**正常状态就是常绿**——
它红一次说明有人把删掉的东西又加回来了,那是意外不是常态。按「没红过」退役,
等于**专挑还在生效的断言删**,把这套机制反向拆掉。

### 维度 19:用例数量基线 + 优先级分布 + 统计摘要(**Critical**)

> ⚠️ **反向占比的分母是「业务用例集」= 总用例数 **减去** `[还原度]` 族。** 维度 21 要求每个列表页
> ≥10 条通用还原度用例,而那批固定模板项绝大多数是正向断言;若把它们算进分母,**业务用例本身
> 已达标的文档也会被这条 Critical 判死**(实测:20 条业务用例中 8 条反向 = 恰好 40%,再加 3 个
> 列表页 × 10 条还原度 → 掉到 16%)。两条都是 exit 1 的硬 Critical,必须错开分母。
> `check_case_stats.py` 已按此实现,人读输出会显式打印「分母 = 业务用例 N 条,不含 [还原度] 族」。

**检查目标:** 各模块用例数是否落在数量基线(简单 30–60 / 中等 80–150 / 复杂 150+,方法论第六节),低于下限是否已在统计摘要说明原因;P0/P1/P2 分布是否接近目标区间(15–25%/45–55%/25–35%),反向用例是否 ≥ 全量 40%;单功能点是否 ≥3 条;文档末尾是否附「用例统计摘要」(方法论第七节)。

**核验步骤:**
1. 运行 `python scripts/check_case_stats.py <用例路径或目录>` 取套件数/用例数/优先级分布/正反向占比(**反向占比按各用例显式「反向」字段统计,缺字段才回退类型推断**)。
2. 核对统计摘要章节存在,且「合计」行 P0+P1+P2 之和与实际用例数一致。
3. 核对反向占比 ≥ 40%;偏离优先级目标区间为 warning(读 `--json` 的 `priority_distribution`)。
4. 核对模块用例数是否达基线下限;未达须在摘要说明原因。
5. (可选)加 `--coverage-matrix` 交叉核对各用例「覆盖」字段标注的维度是否与实际用例内容相符。

> **★与规模档位(scale=S/M/L)的关系(SKILL.md「需求规模档位」):** **S 档基线换成 25~40 条**,此时"低于 30"不算低于下限、不需另行说明原因——但**统计摘要须写明本轮档位**(如 `规模档位: S(编排层判定)`),否则复核者无从判断该用哪条基线。**除数量基线外,本维度其余各项(反向占比 ≥40%、优先级分布、单功能点 ≥3 条、统计摘要必附)在任何档位一律不放松**;`check_case_stats.py` 的硬下限 `MIN_TOTAL_FULL=20` 也不因档位改变。**核验时须显式传档位**:`check_case_stats.py <路径> --scale S`(S=25~40 / M=60~100,**整轮合计**口径;L 档按每模块基线、脚本不判,仍走 20 条硬下限)——不传 `--scale` 则脚本无从得知档位、只按 L 档行为跑。

**不通过标志(任一即不通过):**
- 模块用例数低于基线下限,且统计摘要未说明原因(**S 档基线为 25~40,且摘要须写明档位**)
- 反向用例占比 < 40%(用例数 ≥10 时;happy path 过度堆积)
- 单功能点用例 < 3 条且未说明原因
- 文档末尾缺「用例统计摘要」,或摘要 P0+P1+P2 之和与实际用例数不符

**自动化辅助:** `python scripts/check_case_stats.py <用例路径或目录>`(退出码 1 = 缺统计摘要 / 反向占比 <40% / 合计不符;优先级分布偏离为 warning-only,读 `--json` 另判)。

> 一处判错就给未启用项目凭空长出 Critical。启用判定归调用方。

**检查目标:** 启用时须生成**两类套件**(未启用态 + 已启用态),覆盖齐全、无三条已知写错形态。
**判据全文见 [`flow-webmcp.md`](./flow-webmcp.md)**,本节只列核验清单。

**核验清单:**

1. **两类套件都在** —— 缺任一即不通过。**只写已启用态是最常见形态**(未启用态才是绝大多数使用者的真实体验)。
2. **未启用态优先级不低于已启用态** —— 不得因为「这是没开启的情况」降到 P2。
3. **未启用态三条断言齐全**:无任何相关 DOM 元素(与上线前逐像素一致)/ 控制台零报错 / 既有功能零回归。⛔ **把「浏览器不支持」当异常分支处理**(弹「您的浏览器不支持 XX,请升级」)**是违规**——不支持是主流路径,正确表现是**什么都不发生**。
4. **已启用态九项覆盖齐全**:工具清单齐备性 / 只读工具正确性 / 敏感值脱敏 / **写操作确认门(确认·取消·超时·并发四态)** / 不扩权 / 服务端配置关闭时的表现 / 总开关停用与恢复 / 刷新与重复登记 / 工具执行 ⟷ 手工操作链路一致性。
5. **无「清单里没了」型断言** —— 实测能力入口原型**没有** unregister 类方法,停用的正确表现是**仍在清单里、但调用被拒**。断言「工具从助手清单消失」**必然误判为缺陷**,本族最高频写错点。
6. **工具齐备性以设计工具清单表为基准** —— 列出工具的方法返回**浏览器侧全量工具**(不只本页登记的)且是**异步**的,拿它的返回值当本页账本会把别的页面/扩展登记的工具算进来。
7. **安全三条按「外部调用方也拦得住」验** —— 确认门 / 脱敏 / 不扩权不是验「助手很守规矩」。能力入口是页面 JS 上下文里的普通对象,任何能在本页执行 JS 的主体都可调用(含外部 Agent 经调试协议、浏览器扩展)。**用例应模拟外部调用方直接调工具。** 只测「让助手做坏事、助手拒绝了」= 无效验证。 ⚠️ 这三条用例的**动作动词须写「执行」**、调用语义写进「操作对象」列(写「调用」/「发起」会被 `check_testcase_format.py` 报 Important `invalid_action_verb`,而本流程要求子 Agent 读 `by_level.Important` 并入判定 → **合规用例反被判不通过**);断言依据可用**工具的结构化返回值**(核心原则 7 的窄口径例外,与核心原则 1 成对开启)。
8. **双窗口前置在用例头部显式标注** —— 未启用态用常规浏览器 / 已启用态用带参浏览器。不标注则执行者会用同一个浏览器跑完两套,**其中一套必然结论失真**。
9. **启动命令未自拟**(Important) —— 取自 `webmcp_launch_command` 或「测试环境与账号」文档;引用该文档处须带**「目标段缺失即判 `block` 并写明缺哪一段」**的校验(下游真实踩过:文件在、内容锚点空,链接检查查不出来,执行者第一步就卡住)。

10. **步骤级 `[加速可选]` 只标状态准备类,且 `[还原度]` 用例整条未被标为可走 WebMCP** —— 分层判据见 [`flow-principles.md`](./flow-principles.md)「步骤级 `[加速可选]` 标注」:状态准备 / 数据构造 / 非视觉断言可走 WebMCP;**视觉还原度 / 布局 / 样式必须 DOM + 截图**(WebMCP 读的是页面**声明的能力**、不是**渲染结果**,用它验还原度会让渲染层缺陷 **100% 漏测且全绿** —— 下游 `check_result.py` C14 判 Critical)。⛔ **不得为此另发明 `[必须DOM]` 标记**:一条用例同时带 `[还原度]` 和 `[必须DOM]` 时,后加的那个会被读成「只有标了才必须」,于是**没标的还原度用例被放行**,方向恰好相反。

**不通过标志:** 只有已启用态套件;未启用态被降级为低优先级或只写一条冒烟;出现「清单里没了」断言;确认门只测「确认」不测取消/超时/并发;安全三条只验助手不验外部调用方;双窗口前置未标注;`[加速可选]` 标到了视觉断言步骤上,或文档里出现自造的 `[必须DOM]` 标记。

## 约束

1. **PRD 100% 覆盖(最高约束)** — 全量模式必须覆盖 PRD 全部功规点,任何遗漏在 Quality Review 维度 1 中都会被判定为 Critical 不通过
2. **零代码级动作** — 用例中严禁出现接口调用、SQL、缓存、日志等非 UI 层操作(**窄口径例外:** 仅「统计 / 汇总 / 计数 / 金额」字段的 `[双源对账]` 用例可在其「双源对账」专段内用等价 SQL 作断言依据,SQL 须含软删除 / 状态过滤条件、非操作步骤;用例级「前置数据编排」段的跨系统 `SQL造删数` / `调对方接口` 属造数编排也不受此约束;步骤表操作列 SQL 仍一律禁止)
3. **套件入口强制** — 每个测试套件必须包含 Suite Setup(浏览器/APP 打开 + 登录),套件内各用例通过菜单导航切换页面,禁止在单条用例中重复执行登录流程
4. **四要素完整** — 每步必有动作+对象+数据+现象
5. **覆盖不漏** — 全量模式覆盖 PRD 全部功规点;增量模式覆盖研发执行计划 Task + 关联回归
6. **跨系统透明** — 涉及外部系统时必须说明对方系统可观察现象
7. **AI 可接管** — 元素定位使用可见文案,禁止 DOM 选择器
8. **拆分规则** — 用例数 > 40 条或文件 > 800 行/60KB 必须按模块拆分多文件,必有 `02_自测用例-总览.md` 主文档(`00_` 给专职索引、`01_` 给自测方案)
9. **文件命名总则(单/多文件通用)** — 同测试目录下所有产出文件必须带两位数字前缀 `NN_`、有序自增、序号唯一,严禁无序号散文件;`00_` 专职索引 `00_索引.md`、`01_` 研发自测方案、`02_` 单文件用例或总览、`03_`~`97_` 模块用例、`98_` 跨系统、`99_` 待澄清。单文件用例须命名为 `02_全量自测用例.md` / `02_增量自测用例.md`,不得用无前缀的 `全量自测用例.md`
10. **用例独立** — 每条用例可单独执行,不依赖其他用例的产出
11. **数据具体** — 输入数据必须具体,不能写"任意值";覆盖边界值与安全输入
12. **数据一致性** — 用例中的 URL、文案、校验规则必须与实际代码一致,不得推测
13. **溯源完整** — 每个测试套件和用例必须标注上游溯源(PRD/原型/设计/研发执行计划)
14. **自测方案对齐** — 必须主动询问并产出 `01_研发自测方案.md`,与用例形成双向引用闭环;默认手动浏览器执行,AI 自动化为可选项

## 使用说明

Quality Review Agent 在执行检查时:

1. **读取本文件**作为检查清单
2. **按维度逐项检查**用例文档
3. **生成覆盖率矩阵**和问题清单
4. **输出检查报告**,格式参考上述"检查报告输出格式"
5. **循环修订**直到所有维度通过或达到轮次上限

**关键原则:**
- 维度 1(PRD 100% 覆盖)、维度 13(数据一致性与溯源)、维度 15(待澄清问题清单完整性)、维度 16(自测方案对齐与引用闭环)不可豁免
- 覆盖率类维度(1-6)优先级高于用例质量类维度(7-13)
- 流程类维度(15-16)为前置门槛,缺方案 / 缺引用 / 缺待澄清清单直接整体不通过
- 完备性度量类维度(18-19)与 SKILL 执行流程"第七步:覆盖率回检"共用同一份信源 [`test-design-methodology.md`](./test-design-methodology.md),生成时自检与事后 QA 判据一致、不产生双信源
- 每轮检查必须生成完整的覆盖率矩阵和问题清单
- 修订建议必须具体可执行,包含 TC-ID 和具体操作
