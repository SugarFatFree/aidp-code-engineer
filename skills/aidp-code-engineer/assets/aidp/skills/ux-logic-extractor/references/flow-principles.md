## ⚠️ 职责边界（Critical）

**PRD 只描述"用户要什么/系统做什么"，严禁包含技术实现细节：**

❌ **严禁出现的内容**（即使产品需求文档中存在也必须过滤）：
- 代码块（```typescript/javascript/python/java 等）
- 接口定义（interface/class/type/struct/enum）
- 技术变量名（camelCase 如 `agentCount`、`activeUsers`、`orderStatus`）
- 数据类型标注（number/string/boolean/int/varchar/datetime）
- 接口设计（HTTP Method/URL 路径/状态码/Request/Response 结构）
- 数据表设计（表名/字段名/DDL/索引/外键/ER 图）
- 技术栈/框架（Vue/React/Spring/Redis/MySQL）

✅ **正确做法**：用业务语言描述
- ❌ `agentCount: number` → ✅ "已订阅的智能体总数"
- ❌ `status: '待支付' | '已支付'` → ✅ "订单状态：待支付、已支付"
- ❌ `interface BillingRecord { id: string; amount: number }` → ✅ "账单记录包含：订单编号、金额"

**违规后果**：下游 `dev-logic-architect` 会重复设计，导致冗余和不一致。


## ⚠️ 不臆造兜底原则（Critical）

**产品需求中没有明确说明"需要兜底/容错/默认值/降级方案"的地方，PRD 中严禁自行增加任何形式的兜底逻辑、默认数据源、缺省回退、容错降级。**

❌ **严禁臆造的兜底类型**：
- **数据源兜底**：PRD 没说"接口失败时显示默认数据"，不要自己加"接口异常时回退到本地静态列表/上次缓存/示例数据"
- **字段兜底**：PRD 没说"为空时显示 N/A"，不要自己加"字段缺失时显示横线/空字符串/0"
- **业务规则兜底**：PRD 没说"未配置时按某规则",不要自己加"如未配置审批流则默认走单级审批"等假设
- **权限兜底**：PRD 没说"无权限时如何处理",不要自己加"无权限时显示降级视图/只读模式"
- **状态兜底**：PRD 没说"枚举外的值如何处理",不要自己加"未知状态显示为'其他'"
- **加载兜底**：PRD 没说"加载失败的容错"，不要自己加"加载失败显示 mock 数据/上次成功的快照"
- **缓存机制臆造(Critical)**：PRD 没说"需要使用缓存提升性能"，**严禁**在需求文档中自作主张添加"使用 Redis 缓存接口响应"/"本地缓存字典数据"/"接口响应缓存 5 分钟"等缓存相关描述。即使从性能优化角度判断"应该缓存"，也**必须**标注为 `❓ 待澄清` 或 `🔧 暂行方案(建议使用缓存，待用户确认)` 并汇总到「十、待澄清问题清单」，**不得**作为确定需求混入正文。**下游链路:** 详细设计阶段的缓存确认协议见 `dev-logic-architect` SKILL 核心原则 17「缓存机制用户确认原则」+ 检查项 23(配套脚本 `check_cache_user_confirmed.py`)

✅ **正确做法**：
- 严格按 PRD 已写明的规则实现，PRD 没覆盖到的边界由"⚠️ 不中断原则"流程处理:在原位置加 `❓ 待澄清` 标记 + `🔧 暂行方案(Agent 推断)` + 汇总到「十、待澄清问题清单」
- 推断的兜底**必须**显式打标"🔧 暂行方案",**不得**作为正式需求与 PRD 已确认内容混排
- 暂行方案应**明确标注"无兜底"作为推断结果**(若行业惯例是"快速失败"),不要默认添加兜底

**Why:** 兜底逻辑常常**改变业务语义**(如"无数据"和"接口失败显示空列表"用户体验完全不同,但代码表现一样),会让产品后续验收时无法分辨哪些是"已确认需求"哪些是"研发臆造"。下游详细设计/开发 Agent 会把 PRD 中的兜底当作硬需求实现,导致**虚假的需求蔓延**。

**例外**: PRD 明确写了"接口异常显示默认 XX/缺失时使用 XX/失败时降级到 XX"等字样的兜底,正常引用产品定义即可。

### ✅ "数据源兜底"与"空状态 UI 展示推断"的区别（允许的灰区）

**严格区分两种情况，后者属于合理 UI 推断，无需产品明文授权：**

| 类型 | 是否允许臆造 | 说明 | 示例 |
| :- | :-: | :- | :- |
| **数据源兜底**（本原则禁止） | ❌ 禁止 | 数据为空/接口失败时，**用替代的真实数据假装有数据**，改变业务事实 | 接口失败 → 显示上次缓存 / 显示静态示例 / 回退 mock 接口 |
| **空状态 UI 展示推断**（允许） | ✅ 允许 | 数据真的为空时，描述**给用户的视觉反馈/文案**，不替代数据 | 列表为空 → "暂无数据"插画 + 居中布局；搜索无结果 → "未找到匹配记录"文案 + 引导操作按钮 |
| **加载中状态推断**（允许） | ✅ 允许 | 数据真在加载时，描述**过渡态的视觉表现** | 列表加载中 → 骨架屏 / 旋转 loading |
| **错误反馈推断**（允许） | ✅ 允许 | 失败时**告知用户错误并提供恢复路径**，不替代数据 | 接口失败 → 错误 Toast + 重试按钮 |

**判断口诀**：用真实数据替代不存在的数据 → 数据源兜底（禁）；告诉用户没数据/在加载/出错了 → UI 展示（允许推断）。

**允许推断的常见空状态/加载中/错误 UI**：列表为空插画+暂无数据文案、详情页占位卡片+数据不存在文案、搜索无结果引导、骨架屏、Spinner、错误 Toast + 重试按钮。这些 UI 推断应在 PRD 中以"空状态/加载态/错误态"小节描述，**不应**写成"接口失败时显示上次缓存"等数据源兜底语句。

## ⚠️ 原型对齐三层原则 —「原型可见 = 隐含需求」（Critical）

**约定4「对齐原型」= 视觉 + 内容 + 操作逻辑 三层全部与原型一致，不止「字段裁剪三件套」。研发 PRD 必须把原型 `code/` 里每一层都转写成对应的功能点/字段/流程/交互规则，禁止静默漏、禁止擅自简化或改流程。**（AIDP 约定4）

> **本原则专治「情形 B」缺失**：项目有原型 `code/`、无高保真，落地后前端比原型内容/功能大量缺失——根因是 PRD → 研发需求转写时没把原型 `code/` 的可见元素与操作逻辑逐项清点进去。本原则把「逐页 × 可见元素 × 操作逻辑」的结构化清点定为 PRD 生成的强制动作。

**三层对齐范围：**
- **① 视觉层**：颜色/主色/字号/行高/间距/圆角/阴影/布局。视觉技术值（hex/px 等）由下游详细设计消费「设计令牌.md」落地，**本 PRD 层不写技术样式值**（避免违反职责边界），但须在字段清单/交互描述里保留原型可见的**展示形态与布局语义**。
- **② 内容层**：原型 `code/` 可见的每个区块/卡片/表格列/表单字段/筛选排序/按钮次级操作/空态·加载·错误·成功等交互态/跳转，**一个不许静默漏**。
- **③ 操作逻辑层**：点击反馈/跳转、校验规则与时机、字段联动、条件显隐/禁用、增删改-保存-取消/批量流、二次确认、默认值/初始态、多步步序、错误处理、权限态差异——**禁止擅自简化或改流程**。

**规划期铁律：**
- **原型可见 = 隐含需求**：PRD 没逐字写到 ≠ 可丢弃；需求没写不等于不做、不等于可随意改逻辑。转写 PRD 时未把某原型元素/操作逻辑清点进研发需求，即**规划期漏写 = 违规**，不是「默认不做」。
- 未对某原型元素/功能/操作逻辑**显式标注**「裁剪 / 延期 / 改为 X」→ 默认必须照原型转写为研发需求。
- 任何裁剪 / 延期 / 改逻辑走**约定4三件套**：① 在「六·4」留痕「原型元素·操作逻辑 → 处置」对照（见 **表 C**）；② 产品确认门——登记「十、待澄清问题清单」；③ 触发约定22级联（AIDP：裁剪/改动向下游详细设计·执行计划·验收级联透传追溯）。**严禁** SKILL/AI 自行删减或简化。

**AIDP 规划期上游产物消费（有则强制消费为基准，无则回退现场提取；不臆造）：**
- **`docs/design/{version}/原型内容基线.md`**（若上游已产出）：逐页列出全部可见元素 + 操作逻辑/交互流 + 处置列（实现(默认)/裁剪/延期/改为X）。**强制消费为覆盖基准**——基线里每个处置 =「实现」的元素与逻辑，都必须有对应功能点/字段/流程/交互规则被写进本 PRD。**无基线时回退**直接从原型 `code/` 现场逐页清点。
- **`docs/design/{version}/设计令牌.md` + 全局主题文件**（若已产出）：视觉层令牌单一信源，本 PRD 层仅引用其存在、不复制技术值；视觉落地由下游详细设计消费。
- **原型自带 `DESIGN-MANIFEST.json` / `DESIGN-HANDOFF.md`**（若原型目录含）：读取其 `screens / appModules / requiredStates / tokens / flows`，据此**扩充覆盖清单**（页面/模块/必需交互态/流程一个不漏）。
- 上述路径均为**示例，自适应项目实际结构**；一律「有则消费、无则回退原型 `code/`」，**不得**写成本 SKILL 自己产出、**不得**硬依赖某路径存在。

**约定28边界：**「用项目已有组件」只约束组件实现选型层，**不豁免**本三层对齐——复用已有组件不代表可以少一个原型可见元素或改一条操作逻辑。（AIDP 约定28）

**下游链路：** 本原则的「原型元素·操作逻辑 → 处置」登记（表 C）与「需求字段 → 处置」（表 B）共同构成下游对账基准；处置 = 实现的项若在研发需求缺失，下游代码验收/版本审计据「原型覆盖度」判 Critical。由 Quality Review 维度 13（已扩展为「需求字段去向登记 + 原型内容基线覆盖度」）强制核验。

## ⚠️ 不中断原则（Critical）

**遇到信息缺失、表述不清、文档与原型冲突等需要澄清的地方时,严禁中断生成任务。**

正确做法:
1. **就地标注** — 在功规点/字段/规则原位置加 `❓ 待澄清` 标记,但**不删除内容**
2. **给出暂行方案** — 由 Agent 基于上下文与行业惯例推断一个合理默认,在原位置标注 `🔧 暂行方案(Agent 推断): [方案描述]`
3. **集中汇总** — 全部待澄清项汇总到 PRD 末尾的 "**十、待澄清问题清单**" 章节(见输出模板第 十 节),给出主题、影响范围、Agent 推断的暂行方案、优先级、待用户确认项
4. **继续推进** — 用暂行方案完成本次 PRD,**不阻塞下游 SKILL 的工作**

**Why:** 中断生成等同于"等用户回答 N 个零碎问题",体验差且效率低;集中汇总+暂行方案让用户**一次性看到全部待澄清项**并对照决策,Agent 推断的暂行方案让下游 SKILL 仍可基于一个完整 PRD 推进工作,后续用户确认后只需局部修订相关段落即可。

**何时应当中断而非继续推断:**
- 用户身份/项目目标本身不清楚,无任何上下文可推断(此时应主动询问)
- 涉及合规/法律/财务边界的关键决策(如金额计算公式、隐私协议、用户分级)且无任何参考(应明确询问)
- 输入文件根本不存在(模式 A 时连原型都未提供;模式 B 时连 PRD 都未提供),或所有提供的文件均完全无法解析(乱码/损坏)。**单一文件缺失时优先降级到适用的模式**(如无 PRD 但有原型 → 降级为模式 A)而非中断

### ⭐ 追问清单:「XX 要和 YY 一样」必须问清是**哪一层**的一样

需求澄清期遇到「**XX 要和 YY 一样**」这类表述时,**不得直接照做**,必须确认是下面**哪一层**——
各层的结论可能完全不同,而这句话本身四层都能读通:

| 层 | 「一样」意味着什么 | 照做后典型形态 |
| :- | :- | :- |
| **结构** | 字段集合、层级、分组方式相同 | 同一套字段清单 |
| **命名** | 字段名 / 标签文案逐字相同 | 同一套 label |
| **取值口径** | 同一指标的统计范围、时间窗、单位相同 | 同一个数值来源 |
| **视觉观感** | 只是长得像(间距 / 圆角 / 配色) | 共用一个外壳,内容各自不同 |

⚠️ **四层是正交的,可以只成立其中一层。** 「一样」在需求方嘴里通常只指**视觉观感**,
而研发默认理解成**结构 + 命名 + 取值口径全都一样**——这个落差不问清就一定会返工。

> **真实代价:** 「弹窗卡片要和页签卡片一样」被理解成"一套通用样式",
> 实际是**三个页签三套命名、三套统计项、只共用一个外壳**,返工两轮。

**处置(仍遵不中断原则):** 问不到人时按上表**逐层给出暂行方案**(如「结构=一样 / 命名=各页签沿用自己现有 label /
取值口径=待澄清 / 视觉观感=一样」),并把**取值口径那一层**登记进第十节待澄清清单,
⛔ 不得把一句「和 YY 一样」原样抄进 PRD——那等于把四层歧义整个传给下游。

**严禁:** 因为"PRD 第 X 节模糊"或"原型与文档冲突"或"字段校验规则未指定"而中断;这些都属于本节"就地标注 + 暂行方案 + 集中汇总"的处理范围。

## ⚠️ 复用优先原则（Critical）

**生成 PRD 时,Agent 必须主动追问"这块功能/数据在已有系统是否已经存在,只是展示位置不同 / 统计维度不同",严禁默认所有需求都是全新的。**

**触发主动询问的信号(满足任一即触发):**
- 字段名/标签与常见已有概念重叠("用户信息""用户列表""部门列表""角色权限""审批流""订单状态""消息中心""通知配置")
- 数据语义为查询展示类(非新写入),原文出现"显示""列表""卡片""统计""汇总""图表"等词
- **同源统计/聚合信号(关键漏判点)**: 原文出现"按 X 统计""按 X 分组""X 分布""X 占比""X 排行""X 总数""年/月/日/周/季统计""分类汇总""透视""聚合"等词,且统计对象语义与本系统已有列表/明细数据重叠
- 同一概念在 PRD 上下文已多次出现(比如多个页面都展示"当前部门""下属员工")
- 数据来源被标注为外部系统接口(参见「六·2 数据来源说明」),且字段名相似于已知第三方系统对接过的接口
- 用户提供的产品需求文档明示或暗示"在 X 页面也展示这个数据"

**正确做法:**
1. 第一次生成 PRD 前,主动询问用户:"本次需求中是否有数据/功能在已有系统已存在(只是展示位置不同)?是否有基于已有列表的统计/分类/聚合需求(只是聚合维度不同)?如有,请告知已有出处或代码位置;如不确定,Agent 会按疑似复用项暂记 ❓ 待澄清"
2. 在「五、页面交互明细」末尾生成「**五·N 复用清单 (Reuse Inventory)**」子章节,列出所有疑似复用项 + 状态(`✅ 复用已有` / `✅ 复用已有第三方接口` / `✅ 复用已有数据-新统计` / `🆕 新增` / `❓ 待澄清`)
3. 待澄清项同步登记到 Module E 待澄清问题清单(沿用 Q-NNN 编号,新增前缀 `Q-REUSE-NNN`)
4. 严禁默认"全新需求",任何 🆕 新增 状态都必须经过用户确认或明显语义新颖(如新业务线 / 新模块从零开始)

**复用类型四分(对应 dev-logic-architect 核心原则 20):**

| 类型 | 含义 | 典型场景 | 处理方案 |
| :-: | :- | :- | :- |
| **A 业务数据复用** | 同一份明细数据,换 UI 展示位置 | "用户信息卡片"在多页出现 | 标 ✅ 复用已有,引用已有页面 |
| **B 接口复用** | 同一业务能力,换调用方 | 多页都查"用户列表" | 标 ✅ 复用已有,引用已有接口 |
| **C 第三方接口复用** | 同一第三方接口被多模块调用 | 订单中心订单统计接口在监控页 + 经营汇总页都展示 | 标 ✅ 复用已有第三方接口 |
| **D 同源统计聚合** | 已有明细列表,新需求是基于其统计/分类/聚合 | 已有"用户列表",新需求"用户按部门统计""用户角色分布""按月新增用户" | 标 ✅ 复用已有数据-新统计,引用已有明细数据出处,并在备注列说明统计维度 |

**用户回答前严禁默认"全新需求",必须以 `❓ 待澄清` 标注 + 列入「五·N 复用清单」+ Module E。**

**Why:** 实测发现新页面展示的"用户信息""部门列表""订单状态"等数据,本系统其他页面早已展示并对接过同样接口;同时,基于"用户列表/订单列表"的统计需求(如"用户按部门统计""订单按月汇总")也常被误判为"新增数据需求 → 新建统计表"。Agent 默认每个新页面 / 每个统计需求都新设计接口/数据表,造成数据重复存储 + 同义接口并存 + 第三方接口被多次重复对接 + **同源数据被新建第二份明细表**。复用清单让产品 + 研发在 PRD 阶段达成"哪些是真新增、哪些是换位置展示、哪些是基于已有数据的新聚合"的共识,避免下游研发盲目重新设计。

**下游链路:** 详细设计阶段(`dev-logic-architect` SKILL)的核心原则 20「复用优先与去重」+ 检查项 27「复用识别完整性」会强制核验代码层面的具体复用位置,本阶段的「五·N 复用清单」是其上游输入。类型 D 的处理方案在详细设计阶段必须落实为"复用已有 X 表 + 新增 GroupBy SQL + 独立统计 Service",**严禁**新建第二份明细表。

## ⚠️ 数据闭环完整性原则（Critical）

**生成 PRD 时,Agent 必须把每条数据视为有"来源"和"去向"两端的闭环,严禁只描述单端。两条铁律:**

- **铁律 ①(有增必有展)**: 需求中只要有数据的**新增/录入/保存/上报/同步写入**,就**一定有展示/消费方**——要么本系统自己展示(列表/详情/卡片/导出/统计),要么交付给第三方系统去展示/消费(对外接口/推送/回调)。
- **铁律 ②(有展必有源)**: 需求中只要有业务数据的**列表/卡片/统计展示**,就**一定有数据来源**——要么来自第三方系统(外部接口/消息推送),要么来自本系统某处的新增/录入/同步入库。

**两条铁律的共同前置动作(Critical): 优先回溯本系统已有实现。**
对每个"新增数据"或"展示列表",Agent 必须**先主动分析本系统已实现的业务/代码**,判断是否存在业务关联(已有页面是否已展示这份数据 / 已有模块是否已在录入存储这份数据 / 已有接口是否已对接这个第三方),再据此在 PRD 中**显式描述这种关联**,而不是默认"新增数据就新做一个展示页""展示列表就新建一张表 / 新对接一个接口"。

**触发主动分析与追问的信号(满足任一即触发):**
- 需求只写了"新增/录入/上报某数据"但通篇没有对应的展示 / 导出 / 对外接口(**增端孤立**)
- 需求只写了"展示某列表/统计"但没说这份数据从哪来、由谁产生(**展端孤立**)
- 新增的数据语义与本系统已有列表/详情数据重叠(疑似应展示在已有页面 → 关联「复用优先原则」)
- 展示的列表语义与本系统已有录入/存储入口重叠(疑似数据本系统已存在 → 关联「复用优先原则」)
- 展示的数据带聚合统计语义,但其明细来源未在 PRD 出现(疑似来自已有明细表的统计,或来自第三方)

**正确做法:**
1. 「五、页面交互明细」逐功规点核对数据两端:**新增动作必标"数据去向",展示区域必标"数据来源"**(展示侧来源回填到「六·2、数据来源说明」)。
2. 新增数据的"去向"若本系统无对应展示,且产品未说明对外交付 → 标 `❓ 待澄清`,登记 Module E(前缀 `Q-FLOW-NNN`),追问"这份新增数据在哪展示 / 交付给谁";**不得默认"先存着不展示"**。
3. 展示列表的"来源"若本系统无对应录入/入库入口,且未标外部系统 → 标 `❓ 待澄清`,登记 Module E(前缀 `Q-FLOW-NNN`),追问"这份数据由谁 / 哪个系统产生"。
4. 凡回溯到本系统已有实现的,按「复用优先原则」在「五·N 复用清单」标 `✅ 复用已有` / `✅ 复用已有第三方接口` / `✅ 复用已有数据-新统计`,并在 PRD 正文显式描述关联出处(关联到哪个已有页面 / 模块 / 接口)。

**Why:** 实测发现 PRD 常出现"半截数据流":① 设计了录入表单 / 上报接口,却没有任何页面消费这份数据,研发实现后数据成"黑洞"(白做);② 设计了展示列表 / 统计卡片,却没说数据从哪来,研发只能凭空新建一张表或盲目新对接第三方,与本系统已有同义数据 / 接口重复。把"有增必有展、有展必有源"作为强制闭环核对,并强制先回溯本系统已有实现,能在 PRD 阶段堵住"数据黑洞"和"凭空造数据源"两类高频缺口,同时与复用优先打通,避免重复建表 / 重复对接。

**下游链路:** 本原则的闭环结论是详细设计阶段(`dev-logic-architect` SKILL)核心原则 20「复用优先与去重」+ 数据来源 / 接口契约设计的上游输入;未澄清的两端缺口经 Module E 透传到详细设计的「待澄清问题清单」。`Q-FLOW-NNN` 待澄清项的完整性由本 SKILL Quality Review 检查项 11「待澄清问题清单完整性」强制核验。与「复用优先原则」、「六·2、数据来源说明」协同。

## ⚠️ 数据单位标注原则（Critical）

**生成 PRD 时,Agent 必须主动识别"数值字段在系统中的存储单位 vs 用户看到的展示单位 vs 第三方传输单位",严禁默认三者一致。**

**触发主动识别的信号(满足任一即触发):**
- 字段名/标签含数量类词汇(数量/总数/计数/次数/条数/笔数 / count / total / num)
- 字段名/标签含时间类词汇(时长/时间/耗时 / duration / elapsed),且需要展示
- 字段名/标签含大小类词汇(大小/容量/尺寸 / size / capacity)
- 字段名/标签含比率类词汇(比例/百分比/概率/达成率 / rate / ratio / percent)
- 字段名/标签含物理量词汇(长度/距离/重量/温度/速度 / length / distance / weight / temperature / speed)
- 原型上数值后带量词(K/万/MB/GB/分钟/小时/天/%/‰/kg/米)
- 字段来自第三方接口(参见「六·2 数据来源说明」),且单位与本系统其他字段不一致

**正确做法:**
1. PRD「六、字段规格表」**必须**为每个数值字段填写三列: `存储单位 / 展示单位 / 转换关系`(非数值字段标 `—`)
2. 后端返回"存储单位"原始数值(如 `count=1500` 个、`size_bytes=1048576` 字节、`duration_ms=180000` 毫秒、`rate_bp=8500` 万分点)
3. 前端负责"展示单位"换算(`1500 个` → `1.5K`、`1048576` → `1MB`、`180000ms` → `3 分钟`、`8500 BP` → `85%`)
4. 第三方对接若返回不同单位,在「七·4、第三方系统对接说明」标注转换关系(如"第三方返回千克 → 本系统存储克,×1000")

**核心约定: 后端返原始值, 前端转展示**

类比已有"货币金额整数原则"(数据库存最小单位整数"分",前端展示主单位"元"),本规则推广到所有数值字段:
- **后端**: 严禁返回 `"1.5K"` / `"3 分钟前"` / `"1MB"` / `"85%"` 等已转换字符串(不可比较 / 不可计算 / 不可国际化 / 单元测试困难)
- **后端**: 返回原始数值 + 接口契约明确"接口字段单位 = 存储单位"
- **前端**: 按 PRD 标注的"展示单位"做换算,展示给用户看
- **例外**: 受外部协议约束的字段(如 ISO 8601 时间字符串、半结构化对象)在 PRD 字段表「转换关系」列显式标注协议名

**严禁的反模式:**
- ❌ 后端返回字符串 `"1500 个"` 或 `"1.5K"`(应返回数值 `1500`)
- ❌ 单位歧义:字段 `rate=85` 但不说明是百分比(85%)还是小数(85.0=8500%)还是万分点(85 BP)
- ❌ 时间字段 `time=1718000000` 不说明是秒级时间戳还是毫秒级
- ❌ 同一概念在 PRD 多处出现但单位不一致("文件大小"在 A 页面写"MB"在 B 页面写"字节")

**Why:** 实测发现单位错位是数据展示 bug 的高频源头:① 后端返回 `count=1500` 前端误以为是"千"展示成 `1500K` ② 第三方返回千克本系统存克但忘了 ×1000 ③ 时间戳秒/毫秒混用导致"1970 年" Bug ④ 百分比 0.85 / 85 / 8500 三种表示在前后端各用一种导致显示错乱。PRD 阶段强制三列对照让产品 + 研发达成"用户看到什么 / 系统存什么 / 怎么换算"的共识,避免下游研发凭直觉处理单位。

**下游链路:** 详细设计阶段(`dev-logic-architect` SKILL)的核心原则 21「数据单位标注与转换全链路一致性」+ 检查项 28「数据单位标注与转换合规」会强制核验 A.3 DDL COMMENT + B.2 接口字段单位 + B.7 第三方对接单位转换映射,本阶段的「六、字段规格表」单位三列是其上游输入。配套自动化脚本(在 `dev-logic-architect` 内): `check_unit_field.py`。

## ⚠️ 语义/口径变更类需求原则（Critical）

**生成 PRD 时,Agent 必须主动识别「语义/口径变更类需求」——同一实体的统计对象范围 / 单位 / 默认值 / 权限范围 / 状态机语义 / 时间窗口发生变化,代码改数值行为但页面零新增元素。这类需求现有原型/字段级联盘不到(级联是「新增/删除实体」驱动),必须强制清点其派生的说明性展示物影响(表 E)并跨版本作废被推翻的历史需求(表 F)。**

> **🛡️ 根因(实际项目缺陷):** 用量消费统计口径由「仅企业」扩为「企业+个人」,后端/接口/前端取数全改对,但 6 处解释该数值的 tooltip 有 1 处未改、仍写"仅统计企业级、不含员工个人消费",与实际展示值**相反**、误导对账(P1)。两缺口:① 级联是"新增/删除实体"驱动,覆盖不到"同一实体语义/口径/范围变更、页面零新增元素";② 级联只版本内单向向下,无环节回头作废被本版推翻的历史需求。

**触发主动识别的信号词(命中任一即判定为语义变更类需求):**
- **强信号词**:`口径` / `全口径` / `改为` / `改成` / `扩展为` / `扩为` / `不再只` / `反转` / `默认开启` / `默认关闭` / `由…改成` / `由仅…改为` / `由…改为` / `含…消耗`
- **弱信号词**(与变更动词同行才计):`范围` / `单位` / `默认值`
- **特征**:同一实体的统计对象范围 / 单位 / 默认值 / 权限范围 / 状态机语义 / 时间窗口变化,**代码改数值行为但页面零新增元素**。

**命中后强制落地四项(违反任一即 Quality Review 维度 14 不通过):**
1. **强制产出「表 E：语义变更 → 派生展示物影响清单」**(见「六·4 表 E」):逐行登记受影响说明性展示物(tooltip / 副标题 / 图例注释 / 空态文案 / 导出文件表头 / 报表标题 / 帮助文档 / 单位标注 / 筛选项标签 / 告警提示),处置 ∈ {改写 / 保持 / 新增 / 待产品确认},`改写` 给具体新文案、`保持` 写明理由。**缺表 E → 判不通过**(命令 10)。
2. **禁止笼统豁免覆盖说明性文案**:严禁用"页面版式/指标项/图表类型全部保持不变""仅数值变化""UI 不变"等笼统表述覆盖说明性文案;确要写"版式不变"须同行声明"本条约束版式与指标构成,不覆盖口径说明文案;文案同步见表 E"。命中笼统表述且无表 E → 判不通过。
3. **强制产出「表 F：历史需求作废清单」**(见「六·4 表 F」):把本版关键语义词检索历史版本 `docs/requirements/{历史版本}/研发需求/*.md`,命中的历史需求条目逐条判定(沿用 / 作废 / 修订)。**命中却未逐条判定 → 判不通过**。
4. **表 A/B/C/D 仍照常产出**:语义变更常伴随字段/元素变化,表 E/F 与表 A/B/C/D 并列、不互相替代——表 A/B/C/D 守"元素级增删",表 E/F 守"同一元素的语义/口径变更"。

**下游链路:** 表 E 是下游 dev-logic-architect(文案落地)、dev-manual-testcase(用例断言 tooltip 文案==新口径)、code-verification-loop(实现与表 E 新文案逐条对账)的上游单一信源;表 F 的作废结论触发下游对被推翻历史需求的清理。由 Quality Review 维度 14 + `check_semantic_change.py`(命令 10)强制核验。
