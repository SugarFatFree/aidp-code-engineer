### 🛡️ 落盘后硬核回检(Critical 强制)

**PRD 文档生成完毕(单文件或多文件)后,以下 bash 硬核回检命令由文末「Post-Generation Quality Review」派发的**独立质量检查子 Agent**作为强制第一步执行(见该章节子 Agent prompt 步骤 0),命中任一即视为不通过、强制 SKILL 重写违规段落,通过后才能标记任务完成。主流程**禁止**在当前对话上下文内联运行这些脚本(脚本输出会挤占主上下文),只接收子 Agent 回传的退出码与结论:**

> **路径说明(本 SKILL 全部文档统一):** 本 SKILL 各文档中所有 `python3 <SKILL_DIR>/scripts/xxx.py` 命令中的 `<SKILL_DIR>` 是本 SKILL 的所在目录,本项目为 `{{AIDP_HOME}}/skills/ux-logic-extractor`(**不要**按当前工作目录去找 `scripts/`)

```bash
# 1. 6 类正则硬核扫描(技术栈/字段类型同行表/完整 API 路径/DDL/HTTP 错误码/T_ 前缀表名)
python3 <SKILL_DIR>/scripts/check_technical_content.py <PRD路径或目录>
# 退出码 0 = 通过, 1 = 不通过

# 2. 多文件白名单(仅多文件模式触发,单文件模式自动跳过)
python3 <SKILL_DIR>/scripts/check_split_blacklist.py <PRD目录>

# 3. 上游净化记录核验(模式 B 必查)
grep -q "已剥离技术细节" <PRD主文档路径> || { echo "❌ 模式 B 缺「⚠️ 已剥离技术细节」净化记录"; exit 1; }   # ⚠️ 必须 exit 1:早期写成 `grep ... || echo`,`||` 后的 echo 必然成功、整条命令**恒返回 0**,而 QR 子 Agent 按退出码判定 → 缺净化记录被读成通过

# 4. 功规点段头部上游溯源覆盖率(每段头部 8 行内必须含 4 类来源标注)
python3 <SKILL_DIR>/scripts/check_req_upstream.py <PRD路径或目录>
# H1 PRD 来源 + H2 原型来源必须 100% 覆盖,H3/H4 ≥ 95%

# 5. 不臆造兜底硬核扫描(维度 12,Critical 始终必查)
python3 <SKILL_DIR>/scripts/check_no_fabricated_fallback.py <PRD路径或目录>
# 退出码 0 = 通过 / 1 = 存在未溯源疑似兜底 **或** Mock 兜底(强制不通过;是否 Mock 看 --json 的 is_mock_fallback) / 2 = 输入错误(路径不存在或无 .md)

# 6. 第三方对接清单合规(维度 8,仅 PRD 含七·4 第三方对接章节时触发,不含则跳过)
python3 <SKILL_DIR>/scripts/check_3p_capability.py <PRD路径或目录>
# 退出码 0 = 通过 / 1 = 编号重复·格式违规·双向追溯断链 / 2 = 输入错误(路径不存在或无 .md)

# 7. 多文件拆分结构一致性(维度 9,仅多文件模式触发;单文件传入会因"非目录/单文件"返回非阻塞,标 N/A 跳过)
python3 <SKILL_DIR>/scripts/check_doc_split.py <PRD目录>
# 退出码 0 = 通过(含目录内仅 1 个 .md 的单文件模式) / 1 = 序号前缀缺失·主文档缺失·序号跳号·碎片子文档(<100行且<4KB)·主文档引用断链 / 2 = **入参错**(路径不存在 / 既非文件也非目录)——修正路径后重跑,不计维度失败。⚠️ **传入单个 .md 文件属合法的单文件模式,返回 0 + `skipped:true`**;exit 2 专留给路径打错,二者不共用,否则路径错会被当 N/A 静默略过

# 8. 需求字段去向登记 + 原型内容基线覆盖结构性检查(维度 13,仅 PRD 含「需求字段清单」/表 C 章节时触发;主体 report-only,**但表 A 代码级标识判 Critical**)
python3 <SKILL_DIR>/scripts/check_requirement_field_inventory.py <PRD路径或目录>
# 退出码 0 = 通过 / **1 = 表 A「字段语义名称」混入代码级标识(Critical,判错型)** / 2 = 入参错(路径不存在或无 .md)。表 B/C 疑点仍为 report-only 采集,交 Agent 判定:有无表 A 表头特征列 / 表 B 处置取值是否 ∈ {保留·裁剪·前端计算还原·请第三方补} / 裁剪项是否带「待产品确认」/ 有无表 C 表头特征列 / 表 C 处置取值是否 ∈ {实现·裁剪·延期·改为X} / 表 C 非实现项是否带「待产品确认」

# 9. PRD 条目反向覆盖率(维度 13 子项·判错型,仅 PRD 含「表 D：PRD 条目映射表」时触发;与命令 4 正向溯源方向相反、并存不可替代)
python3 <SKILL_DIR>/scripts/check_prd_item_coverage.py <PRD路径或目录> [--prd-source <产品提供目录>]
# 退出码 0 = 表 D 条目 100% 已分类(已承接/本版不做/已存在无需重复)通过,或无表 D 且无产品原始 PRD 源(模式 A)跳过;探测到 `产品提供/`(或 `--prd-source`)却无表 D 同判 1 / 1 = 存在未分类·未落点条目(处置为空或越界),覆盖率 <100%,强制不通过并列出未落点条目原文 / 2 = 输入错误(路径不存在或无 .md);另内置三类高危丢失点 report-only 告警(操作类条目整类缺失·0 承接 / 备注·展示规则属性丢失 / 遗留问题·迭代建议未逐条进表 D)

# 10. 语义/口径变更类需求识别 + 表 E 完整性(维度 14·判错型,仅命中语义变更信号词或笼统豁免表述时生效;既无信号又无豁免的 grandfather 放行)
python3 <SKILL_DIR>/scripts/check_semantic_change.py <PRD路径或目录>
# 退出码 0 = 通过(命中语义变更且表 E〔6 列:变更项/变更前语义/变更后语义/受影响展示物/处置/新文案〕齐备,或既无语义变更信号又无笼统豁免的 grandfather 放行) / 1 = 缺表 E 且命中语义变更信号词或笼统豁免表述("版式.*保持不变"/"仅数值变化"/"UI 不变"),强制不通过 / 2 = 输入错误(路径不存在或无 .md);表 F(历史需求作废清单)存在性 report-only 提示(跨版本历史扫描超脚本能力,由 QR Agent 语义硬门)

# 10'. 表 E/表 F 机器可读副本(供下游 architect 文案落点表 / dmtc [文案一致性] 用例族 /
#      调用方的跨版本需求台账消费;仅在产出了表 E/F 时有意义)
python3 <SKILL_DIR>/scripts/check_semantic_change.py <PRD目录> \
  --emit-json <PRD目录>/98_语义变更与需求作废.json
# ⚠️ **markdown 表 E/F 仍是唯一信源,JSON 是脚本确定性抽取的派生产物** —— 人只写一处、机器派生一处。
#    ⛔ 严禁让 PRD 同时手写一份 JSON:同一数据两份手写是本仓库最高频的漂移源
#    (与「同一判据两份实现」同类),而这份数据恰恰要被跨版本清算消费,对不上比没有更糟。
#    副本随时可重新生成,过期就重跑;它不参与 check_doc_split 的 .md 命名校验。
# 需求编号同时给 `raw` 原文与解析结构(prefix/version/seq/number),覆盖实测存在的四种历史写法
# (REQ-001 / REQ-3 / REQ-V0.10-A02 / 纯数字);认不出时 `parsed:false` + 原文照传,**绝不猜**——
# 猜错编号会让跨版本清算张冠李戴,比认不出更糟。
# `--emit-json -` 输出到 stdout(此时人读报告与 --json 让位到 stderr,免得两段内容首尾相接、调用方解析报错)。
```

**严禁**只跑独立 Agent 的语义维度审查而跳过本 bash 硬核回检 — 维度 10 实测显示,仅靠语义检查会被"印象式通过";硬核 grep 才能拦住 605 处真实违规。脚本搬进子 Agent 后**仍然必跑**(护栏不变),只是改由子 Agent 在其上下文内确定性执行、回传退出码,主上下文不再被脚本输出占用。

**自动化建议:** 由质量检查子 Agent 在其 prompt 步骤 0 用 `Bash` 工具串联调用上述 10 条命令(命令 1/4/5 始终跑,命令 2/7 仅多文件模式触发、命令 6/8/9/10 视内容触发,命令 3 模式 B 跑),除退出码 2（入参/环境错——修正参数后重跑、**不计维度失败**）外,任一**判错型**命令退出码非 0 即对应维度直接判不通过并回传主流程;命令 8 **主体 report-only、但表 A 代码级标识为判错型**(exit 1 即维度 13 不通过;表 B/C 采集结果仍交 Agent 判定),命令 9 为**判错型**(PRD 含「表 D」时未分类条目 > 0 即退出码 1;探测到产品原始 PRD 源却无表 D 同判退出码 1,均判维度 13 不通过),命令 10 为**判错型**(仅命中语义变更信号词或笼统豁免表述时生效,缺表 E 即退出码 1 判维度 14 不通过;既无信号又无豁免时退出码 0 grandfather 放行);**主流程不在当前上下文跑这些命令**。

## Post-Generation Quality Review (文档生成后独立 Agent 检查)

**强制要求：PRD 文档生成完成后，必须调用一个独立的 Agent 执行质量检查，对 15 个维度逐项核查（单文件 7 维度核心 + 第三方对接 1 维度 + 拆分一致性 1 维度 + 职责边界 1 维度 + 待澄清问题清单 1 维度 + 不臆造兜底 1 维度 + 需求字段去向登记 1 维度 + 语义/口径变更类需求 1 维度 + 结论型断言证据来源 1 维度），发现问题则补充修订后再次输出。**

> 🧹 **执行主体与上下文隔离(Critical):** 本节全部检查——`🛡️ 落盘后硬核回检` 的 10 条 bash 硬核回检命令 **+** 15 维度语义审查——一律在**独立子 Agent**内完成。主流程**禁止**在当前对话上下文内联跑脚本或内联逐维度自查(脚本输出与逐项核对会挤占/污染主上下文)。主流程只负责三件事:① 派发子 Agent(传入 PRD/原型/产品文档路径);② 接收子 Agent 回传的**精简结构化报告**(含每个脚本退出码 + 各维度通过/不通过 + 修订建议);③ 据报告决定修订并重新派发,循环至全部通过或达 3 轮上限。

> 📋 **完整检查清单**: 各检查项的核验步骤、grep 命令、逐条判定规则以 `./quality-review-checklist.md` 为唯一权威来源,检查 Agent 必须读取该清单执行;本文件「15 维度检查清单」一节仅为精简摘要。

### 执行方式

使用 Claude Code 的 Agent 工具派发独立检查任务（推荐 `subagent_type: general-purpose`），传入：
- 生成的 PRD 文档路径
- 原型文件路径
- 产品需求文档路径（模式 B 时）
- `client_mcp` 显式业务能力声明（缺省关闭）;旧 `webmcp_enabled` 仅为 Web 兼容入参。两者客户端/启停冲突须在 QR 报告明确报错,不静默覆盖;测试驱动是否使用 MCP 不能作为启用证据。

```
调用示例：
Agent({
  description: "PRD 质量检查",
  subagent_type: "general-purpose",
  prompt: "你是一位资深产品经理。请对 {PRD 文档路径} 执行 15 维度质量检查，参考原型 {原型路径}、产品需求文档 {产品文档路径}（模式 B 时）。

  执行步骤（必须按顺序）：
  0. **(先于一切,强制)** 逐个运行本 SKILL『🛡️ 落盘后硬核回检』列出的全部 bash 脚本(将 <SKILL_DIR> 替换为本 SKILL 实际安装目录,即 ./quality-review-checklist.md 的上一级):check_technical_content.py、check_split_blacklist.py(多文件模式)、模式 B 净化记录 grep、check_req_upstream.py、check_no_fabricated_fallback.py(维度 12,始终跑)、check_3p_capability.py(维度 8,仅 PRD 含七·4 第三方对接章节时跑)、check_doc_split.py(维度 9,仅多文件模式跑;单文件 N/A 跳过)、check_requirement_field_inventory.py(维度 13,仅 PRD 含「需求字段清单」/表 C 章节时跑;主体 report-only 据采集结果做语义判定,**但表 A「字段语义名称」混入代码级标识为 Critical、退出码 1**)、check_prd_item_coverage.py(维度 13 子项·命令 9·判错型,始终跑;未分类条目 > 0 即退出码 1;探测到产品原始 PRD 源(`产品提供/` 或 `--prd-source`)却无表 D 同判退出码 1;无表 D 且无产品 PRD 源时退出码 0 跳过)、check_semantic_change.py(维度 14·命令 10·判错型,仅命中语义变更信号词或笼统豁免表述时生效;缺表 E 即退出码 1;既无信号又无豁免时退出码 0 grandfather 放行)。把**每个脚本的退出码原样贴进报告**作为证据;**任一判错型脚本退出码非 0 即对应维度(维度 5 上游溯源 / 维度 8 第三方对接 / 维度 9 拆分一致性 / 维度 10 职责边界 / 维度 12 不臆造兜底;维度 13 命令 9 表 D 反向覆盖率 < 100%;维度 14 命令 10 缺表 E)直接判不通过**,无需再做语义判断;维度 13 据 check_requirement_field_inventory.py 采集结果(表 A/B/C 存在性 + 处置枚举)+ check_prd_item_coverage.py 表 D 反向覆盖判定(命令 9,模式 B 必产表 D、未分类条目 = 静默丢失)+ 原型 code/(或上游`原型内容基线.md`/`DESIGN-MANIFEST.json`)逐列·逐元素·逐操作逻辑比对 + 产品需求文档逐表逐行比对做语义判定;维度 14 据 check_semantic_change.py 命中(表 E 齐备性)+ 表 F 历史作废清单(实际读历史版本`docs/requirements/{历史版本}/研发需求/*.md`,命中本版语义词的历史需求条目须逐条判定沿用/作废/修订)做语义判定;
  1. 读取原型 HTML，提取所有页面、表单字段、按钮、状态标签、交互流程；
  2. 读取 PRD 文档，提取所有章节（异常路径、字段规格、状态机、权限矩阵、隐藏逻辑、第三方对接）；
  3. 读取产品需求文档（模式 B 时），提取功能清单、业务规则、角色权限、第三方对接要求；
  4. 对照 15 个维度逐项检查;若 `client_mcp`/Web 旧入参显式启用,在检查项 4/6 同一轮核应用业务工具声明、权限/确认/失败/审计来源;未声明不增加维度或报告行,旧新冲突判不通过,不得把 Chrome/Appium 的测试驱动 MCP 当成应用工具:
  4. 对照 15 个维度逐项检查:
     - 维度 1: 异常路径覆盖
     - 维度 2: 字段校验规则
     - 维度 3: 状态切换逻辑
     - 维度 4: 逆向交互流程
     - 维度 5: 数据一致性
     - 维度 6: 权限与极端情况
     - 维度 7: 隐藏逻辑挖掘
     - 维度 8: 第三方系统对接完整性(涉及第三方对接时)
     - 维度 9: 多文件拆分一致性(仅多文件输出模式,含碎片化检查)
     - 维度 10: 职责边界(PRD 不含接口设计/数据表设计/技术栈/代码,不含研发执行计划/Sprint/工时/排期/上线日期等研发管理内容)
     - 维度 11: 待澄清问题清单完整性(十、章节存在 + Q-NNN 双向追溯 + Agent 暂行方案必填 + 不中断行为合规)
     - 维度 12: 不臆造兜底(数据源兜底/字段兜底/业务规则兜底/状态兜底等需在产品文档找到来源,或显式标 🔧 Agent 暂行方案并汇总到十章节;空状态 UI 推断允许)
     - 维度 13: 需求字段去向登记 + 原型内容基线覆盖度(① 字段级:原型/产品需求可见每个数据项 100% 以业务语义名进「六·4」表 A 登记,裁剪/变更进表 B 且处置 ∈ 固定枚举、裁剪带"待产品确认",无静默丢弃;② 原型内容基线级:原型 code/(或上游`原型内容基线.md`/`DESIGN-MANIFEST.json`)可见非字段元素 + 操作逻辑 + 交互态 100% 进表 C,处置 ∈ {实现/裁剪/延期/改为X},上游基线「实现」项在 PRD 缺失判 Critical)
     - 维度 14: 语义/口径变更类需求识别 + 表 E/F 完整性(命中语义变更信号词[口径/范围/单位/默认值/改为/扩展为/由…改成/不再只/全口径/含…消耗/默认开启/默认关闭/反转/由仅…改为]→ 判为语义变更类需求[同一实体统计范围/单位/默认值/权限范围/状态机语义/时间窗口变化、代码改数值行为但页面零新增元素];① 强制产表 E[6 列:变更项/变更前语义/变更后语义/受影响展示物/处置/新文案],逐行枚举 tooltip/副标题/图例/空态/导出表头/报表标题/帮助文档/单位标注/筛选项标签/告警 等说明性展示物,处置∈{改写/保持/新增/待产品确认},改写给具体新文案、保持写明理由,缺表 E 判不通过[命令 10];② 严禁"版式全部保持不变/仅数值变化/UI 不变"等笼统表述覆盖说明性文案,除非同行声明"不覆盖口径说明文案·见表 E";③ 强制产表 F[5 列:历史版本/需求编号/原结论/本版处置/理由],本版关键语义词检索历史版本研发需求,命中历史需求条目逐条判沿用/作废/修订,命中却未逐条判定判不通过)
```

#### 检查项 14：语义/口径变更类需求识别 + 表 E/F 完整性(Critical 强制项)

**目标：** 识别语义/口径变更类需求(同一实体统计范围/单位/默认值/权限范围/状态机语义/时间窗口变化,代码改数值行为但页面零新增元素);命中即强制产表 E(受影响说明性展示物逐行登记 + 具体新文案)+ 表 F(跨版本历史需求作废清算)。堵实际项目缺陷(口径改了但 tooltip 说明文案未同步、与展示值相反)。

**不通过标志：**
- `check_semantic_change.py` 退出码非 0(命中语义变更信号词或笼统豁免表述但缺表 E)
- 表 E 受影响展示物枚举不全(漏 tooltip/导出表头/图例等),或"改写"项未给具体新文案(写"待定/按实际调整")
- 出现"版式全部保持不变/仅数值变化/UI 不变"等笼统表述覆盖说明性文案,且未同行声明"不覆盖口径说明文案·见表 E"
- 缺表 F,或历史版本研发需求命中本版语义词的条目未逐条判定(沿用/作废/修订)

**自动化脚本：**
```bash
python3 <SKILL_DIR>/scripts/check_semantic_change.py <PRD路径> [--json]
# 退出码 0 = 通过(命中语义变更且表 E 齐备,或既无信号又无豁免 grandfather 放行) / 1 = 缺表 E 且命中语义变更信号或笼统豁免表述 / 2 = 输入错误
```

**仅当命中语义/口径变更信号词或笼统豁免表述时执行**;无语义变更的纯新增/纯逆向 PRD 标 N/A。

> 核验细节见 `./quality-review-checklist.md > 检查项 14`。

#### 检查项 15：结论型断言证据来源 + 引用编号回原文 + 禁令反向边界(Critical 强制项)

**目标：** PRD 里**一句写死的话**是否可核查——① 结论型断言(「上游不支持 / 无出口 / 不可得 / 禁止 / 做不到」)有没有证据(Critical);② 引用别处的编号(约定 N / 断言 Z-xx / REQ-xx / 表 E 第 N 行)当「不能做某事」的依据时有没有回原文核对(Critical);③ 禁令条目有没有写反向边界(Important)。三者是同一类失效的三种形态:**文档里一句没被核过的话,被后续每一轮当既定事实引用**。

**不通过标志：**
- (Critical)存在结论型断言而无证据(文档原文位置含原句 / 源码位置含分支或版本 / 实测记录含日期,三选一)、也未就地标「未验证假设」
- (Critical)已标「未验证假设」的断言在后续章节被当既定事实引用(标记被悄悄摘掉)
- (Critical)用编号作为「不能做某事」的依据,却没有回原文核对 / 引用处只有编号、没有一句话原意摘要
- (Important)禁令条目只写「禁止 X」而无「✅ 不在禁止范围:<最容易被误伤的相似形态>」

**自动化脚本：** ⛔ **刻意不配** —— 「不支持 / 禁止 / 不可得」这些词在 PRD 与规范正文里必然大量出现(本清单自己就有几十处),按关键词扫必满屏假红,与本仓库「新判据宁可窄到只覆盖一种明确形态」的取舍冲突。本项**纯语义核对**。

**始终适用**;PRD 里三类形态一个都不出现时才标 N/A + 写明理由。

> 核验细节见 `./quality-review-checklist.md > 检查项 15`。
> ⚠️ 与下游 `dev-logic-architect` 核心原则 30「结论型断言必须附证据来源」/ 31「禁令条目必须同时写反向边界」(合用检查项 38)**同款口径**——同一句断言常从 PRD 的 Q-NNN 一路传到详细设计,两侧口径必须一致,否则在交界处证据就丢了。

### 循环终止条件

- **通过终止：** 所有适用维度均 ✅（不涉及第三方对接时维度 8 标注 N/A;单文件模式维度 9 标注 N/A;维度 10/11/12 始终适用;维度 13 仅当 PRD 含列表/表格/表单或任何原型可见元素/操作逻辑时适用,纯说明类无任何页面元素展示的 PRD 标 N/A;维度 14 仅当命中语义/口径变更信号词或笼统豁免表述时适用,无语义变更的纯新增/纯逆向 PRD 标 N/A;**维度 15 始终适用**——结论型断言/编号引用/禁令条目三者中只要 PRD 里出现任一，就必须逐条核；三者都不出现时才标 N/A + 写明理由）,直接交付 PRD
- **轮次上限：** 最多循环 3 轮。超过 3 轮仍有未通过项，暂停并向用户报告剩余问题，由用户决定是否豁免。**严禁**在 QR 未通过的情况下静默结束、跳过报告、或声称"PRD 已完成"
- **用户豁免：** 用户明确表示"某个维度可跳过"时，在报告中标注"⚠️ 已豁免"后视为通过
