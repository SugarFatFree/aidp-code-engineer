## 🔗 上游引用规则（Critical 强制要求）

**研发 PRD 必须建立完整的"三层引用追溯"体系,确保下游(详细设计/研发执行计划/自测用例)可反查每一条信息的源头。**

### L1 文档级引用(必填,在文档头部声明)

模式 A 必须包含:`原型来源`(原型根目录路径)
模式 B 必须包含:`产品需求文档`(.docx/.md/.pdf 路径) + `原型来源`(原型根目录路径)
有高保真时追加:`高保真设计`(Figma/Sketch/XD 文件路径)

### L2 章节级引用(每个主章节标注上游来源)

PRD 的每个主章节(如"五、页面交互明细"下的每个页面、"六、字段规格"、"七、字典枚举"、"八、异常路径")**必须**在章节标题下方标注上游引用块:

```markdown
#### 五-1 用户列表页

> **产品需求文档来源:** [§3.2 用户列表(第 15-28 页)](../product/用户管理需求说明V1.2.docx#3-2-用户列表)
> **原型来源:** [<UserListPage>(/user/list)](../ui/code/user-management/user-list.html#user-list-page)
> **高保真来源:** [用户列表页画板](../design/高保真/用户列表.fig#用户列表页)(如有)

[页面交互描述...]
```

### L3 条目级引用(每个表行/字段/枚举/规则标注精确位置)

**字段规格表**:每个字段的"备注"列必须标注 `来源:产品文档 X.X` 或 `来源:原型 文件名`

| 字段 | 必填 | 长度 | 校验 | 备注 |
| :- | :-: | :- | :- | :- |
| 用户姓名 | 是 | 2-20 | 中英文+空格 | 来源:产品文档 4.1 字段表 |
| 头像 URL | 否 | ≤500 | URL 格式 | 来源:原型 user-list.html#avatar 字段 |

**字典/枚举表**:每个枚举值的"业务含义"列必须标注 `来源:产品文档 X.X` 或 `来源:原型`

**异常路径**:每个异常场景必须标注 `来源:产品文档 X.X` 或 `来源:原型异常态截图`

**冲突标注必须双向引用**:
```markdown
> ❗ **文档与原型不一致**:
> - 产品文档 `docs/product/需求说明.docx > 3.2 节 第 20 页`: 用户状态为"启用/停用"两种
> - 原型 `docs/ui/code/user-list.html#status-filter`: 状态为"启用/停用/待审核"三种
> - **采用方案**: 以产品文档为准
```

### 引用格式标准化(必填字段)

> ⚠️ **格式权威性(读前必看):** 本表**仅说明一条引用应包含哪些字段**;**实际写入 PRD 时一律采用「五、页面交互明细 > 精细引用层级」表的 markdown 可点击链接形态**(`[显示文本](仓库相对路径#锚点)`)。**纯文本 `路径 > 章节` 写法、绝对路径(`C:/…`、`/home/…`)均不通过 `check_req_upstream.py`(维度 5)**——本表示例里的纯文本 `>` 仅为字段拆解示意,非最终写法。

| 引用类型 | 格式 | 示例 |
| :- | :- | :- |
| 产品需求文档(.docx/.pdf) | `<文件路径>` > `<章节编号及名称>` (第 X-Y 页) | `docs/product/需求说明.docx` > `3.2 用户列表` (第 15-28 页) |
| 产品需求文档(.md) | `<文件路径>` > `<章节编号及名称>` (L行号-L行号) | `docs/product/PRD.md` > `## 3.2 用户列表` (L120-L180) |
| 原型文件 | `<文件路径>` (路由: `<路由>`) [+ 锚点] | `docs/ui/code/user-list.html` (路由: `/user/list`) #status-filter |
| 高保真设计 | `<文件路径>` > `<画板名称>` | `docs/design/用户列表.fig` > "用户列表页" 画板 |
| 内部章节引用 | `参考本文档 > <章节>` | `参考本文档 > 五-3 用户详情页` |
| 跨子文档引用 | `参考 ../<文件名> > <章节>` | `参考 ../06_字典枚举.md > 用户角色` |

### 强制要求(违反任一即 Quality Review 维度 5 不通过)

1. **每个功规点(五-N)** 必须有上游引用块,包含:产品需求文档(模式 B)+ 原型 + 高保真(如有)
2. **每个字段规格表行** 必须在备注列标注来源
3. **每个字典/枚举值** 必须标注来源
4. **每个异常路径** 必须标注来源
5. **路径必须为仓库相对路径**,不允许 `C:/...`/`/home/...` 绝对路径
6. **不接受模糊引用**: ❌ "参考产品文档" / "见原型" → ✅ `docs/product/PRD.md > 3.2 用户列表 (L120-L180)`
7. **冲突项必须双向标注**: 列出文档侧引用 + 原型侧引用 + 采用方案
8. **模式 A** 不强制产品需求文档引用,但仍需逐条标注原型出处(如"来源:原型 user-list.html 工具栏")

### 五·N、复用清单 (Reuse Inventory) — Critical 强制章节

**对应核心原则「复用优先」。本章节列出 PRD 中所有疑似与已有系统功能/数据/第三方接口/统计聚合重复的条目,标注复用状态,供下游详细设计阶段强制核验。**

```markdown
| 编号 | 新功能/数据/接口 | 已有出处 | 复用状态 | 说明 / 待澄清问题 |
| :-: | :- | :- | :-: | :- |
| Q-REUSE-001 | 用户基本信息卡片(头像 + 姓名 + 部门) | 已有页面「个人中心」 / 接口「用户信息查询」 | ✅ 复用已有 | 类型 A 业务数据复用,同一份用户数据,仅展示位置不同 |
| Q-REUSE-002 | 订单分析图表 | 已有「订单监控」页面 / 接口 ORD-API-021 订单中心「订单总览」 | ✅ 复用已有第三方接口 | 类型 C,第三方接口已对接,本次仅 UI 不同 |
| Q-REUSE-003 | 政策补贴查询表单 | 无 | 🆕 新增 | 全新业务能力 |
| Q-REUSE-004 | 当前用户所属部门 | ❓ 待澄清:疑似已存在于"组织架构"模块 | ❓ 待澄清 | Agent 推断已有,登记 Module E 待用户确认 |
| Q-REUSE-005 | 用户按部门统计图表 | 已有「用户列表」明细数据 / 接口「用户列表查询」 | ✅ 复用已有数据-新统计 | 类型 D,基于已有 biz_user 表 GroupBy dept_id 统计,无需新建明细表;新增独立"按部门统计"接口 |
| Q-REUSE-006 | 订单按月汇总图表 | 已有「订单列表」明细 / 接口「订单列表查询」 | ✅ 复用已有数据-新统计 | 类型 D,基于 biz_order 表 GroupBy YEAR-MONTH(create_time),新增"按月汇总"接口 |
```

**复用状态五值(必须严格使用,不允许自创):**

| 状态 | 含义 | 触发条件 | 类型映射 |
| :-: | :- | :- | :-: |
| ✅ 复用已有 | 用户明确告知已有同等功能/数据 | 用户在 prompt 中显式说明,或本系统其他 PRD/设计文档已记录 | 类型 A / 类型 B |
| ✅ 复用已有第三方接口 | 同一第三方接口已被本系统其他模块调用 | 用户告知已对接,或「六·2 数据来源说明」与已知第三方接口重叠 | 类型 C |
| ✅ 复用已有数据-新统计 | 基于已有明细数据的新统计/分类/聚合需求 | PRD 出现"按 X 统计""分组""分布""占比""排行""年/月/日 汇总"等词,且统计对象在本系统已有明细数据 | 类型 D |
| 🆕 新增 | 全新功能,无可复用 | 用户明确确认新需求,或语义明显新颖(新业务线/新模块从零开始) | — |
| ❓ 待澄清 | Agent 推断疑似复用,等待用户确认 | 触发"复用优先"原则的信号 + 用户尚未确认 | — |

**强制要求(违反任一即维度 5 + 维度 11 不通过):**

1. PRD 中出现的**每个**新页面 / 新字段 / 新数据 / 新接口 / **新统计指标**,都必须能在「五·N 复用清单」找到对应行(允许多个相似条目合并成一行)
2. ❓ 待澄清状态的条目必须**全部**登记到「十、待澄清问题清单」(沿用 Q-REUSE-NNN 编号)
3. ✅ 复用已有 / ✅ 复用已有第三方接口 / ✅ 复用已有数据-新统计 必须给出"已有出处"(已有页面名 / 已有接口路径 / 已有模块名 / **类型 D 还要标明统计维度**),不允许仅写"已有"
4. 🆕 新增 状态必须经用户确认,不允许 Agent 默认所有需求都是 🆕 新增
5. **类型 D 专项约束**: ✅ 复用已有数据-新统计 状态条目的"说明"列必须明确写出 ① 复用的明细表/接口名 ② 统计维度(部门/月份/状态等) ③ 推荐的新统计接口路径(`/xxx/stats/by-{维度}` 或 `/xxx/aggregate`),供下游设计期直接复制
6. 多文件拆分模式下,本章节归入「03_页面交互明细.md」末尾或独立成「04_复用清单.md」(若条目数 > 20 条)

**与下游 SKILL 的协作:**
- `dev-logic-architect` 核心原则 20「复用优先与去重」会读取本清单,B.1 实现映射表的「复用映射」列必须与本清单 ✅ 状态条目对齐
- `dev-logic-architect` B.7「第三方接口复用清单」会读取本清单 ✅ 复用已有第三方接口 状态条目,作为反向核验输入
- `dev-logic-architect` A.3 数据表设计读取本清单 ✅ 复用已有数据-新统计 条目,**严禁**为这些条目新建第二份明细表;只允许新增独立的统计 SQL / View / Service
- 任何下游设计未能引用本清单 ✅ 状态条目就直接 🆕 新增的接口 → `dev-logic-architect` 维度 27「复用识别完整性」不通过(本 SKILL 只有 15 个维度,此处引用的是下游 SKILL 的维度号)

```markdown
|2|文件大小|是|≥0|0|字节(B)|KB/MB/GB 自适应|前端按 1024 进位选展示单位(`1048576 → 1MB`)|—|
|3|通话时长|否|≥0|空|毫秒(ms)|秒/分钟/小时 自适应|前端按 1000/60/60 进位(`180000 → 3 分钟`)|—|
|4|完成率|是|0-10000|0|万分点(BP)|百分比(%)|前端 ÷100 加 %(`8500 → 85%`)|0.85% 用 85 表示|
|5|创建时间|是|—|当前时间|毫秒时间戳|相对时间(如"3 分钟前")|前端按时间差还原(如"3 分钟前")|—|
|6|商品重量|否|>0|—|克(g)|千克(kg)|前端 ÷1000(`2500 → 2.5kg`)|—|
|7|用户姓名|是|长度≤50|—|—|—|—|非数值字段,无单位|
```

**单位标注三列填写规则(对应「⚠️ 数据单位标注原则」核心章节):**

- **存储单位**: 数据库与接口传输的单位(必须是基础单位 / 最小单位,如 个/字节/毫秒/万分点 BP/克/毫米),数值字段必填,文本/枚举字段标 `—`
- **展示单位**: 用户界面看到的单位(如 K/MB/分钟/百分比/千克),数值字段必填
- **转换关系**: 从存储单位 → 展示单位的换算公式(如 ÷1000 加 K / ÷100 加 % / 1024 进位选 KB/MB/GB),数值字段必填

**特殊单位类型说明:**

> ⚠️ **「推荐存储单位」只写业务基础单位,严禁带 DB 类型(`BIGINT`/`INT` 等)** —— DB 类型归下游 dev-logic-architect,且 PRD 出现 DDL 类型词会被职责边界检查(`check_technical_content.py` R4)判违规、维度 10 不通过。

| 数据类型 | 推荐存储单位(业务基础单位) | 展示单位 | 换算关系 |
| :- | :- | :- | :- |
| 计数 | 个/条/次(整数) | 个 / 千(K) / 万 | >1000 ÷1000 + K;>10000 ÷10000 + 万 |
| 时间长度 | 毫秒(ms) | 秒/分钟/小时/天 | 1000ms→1s,60s→1min,60min→1h,24h→1d |
| 时间戳 | Unix 毫秒戳 | 绝对时间 / 相对时间 | dayjs / Intl.DateTimeFormat |
| 字节大小 | 字节(B) | KB / MB / GB / TB | 1024 进位 |
| 百分比/比率 | 万分点(BP,0-10000) | 百分比 % / 千分比 ‰ | ÷100 加 %;不允许小数 0.85 表示 |
| 长度 | 毫米(mm) | 厘米/米/千米 | 10/1000 进位 |
| 重量 | 克(g) | 千克/吨 | 1000 进位 |
| 温度 | 摄氏度 ×100(避免浮点) | 摄氏度 °C | ÷100 |
| 速度 | 毫米/秒(mm/s) | 米/秒 / 千米/小时 | 不同上下文不同 |
| 货币金额 | 最小货币单位(分) | 元 / 美元 / 日元 | 详见「💰 货币金额字段设计规则」(下游 dev-logic-architect 核心原则 11) |

**严禁的字段定义反模式:**

- ❌ `rate DECIMAL(5,2)` 但 COMMENT 仅写"完成率",不说明是 % / ‰ / 小数(歧义)
- ❌ `time BIGINT` 但 COMMENT 仅写"时间",不说明是秒戳 / 毫秒戳 / ISO 字符串
- ❌ 后端返回字符串 `"1.5K"` / `"3 分钟前"` / `"1MB"`(应返回原始数值)
- ❌ 同字段 PRD 多处出现单位不一致(如"文件大小"在用户上传写"MB",在容量统计写"字节")

**字段校验规则必须覆盖:**
- 字符长度限制(最小/最大长度)
- 格式要求(手机号/邮箱/身份证/URL/IP 等正则)
- 是否必填(必填标记)
- 非法输入的错误提示文案(精确到每个字段)
- 特殊字符过滤(如禁止输入 `<>&` 防 XSS)

**校验规则示例(每个字段都必须达到此详细程度):**

### 六·2、数据来源说明 (Data Source Map)

**必须明确每个展示字段的数据来源,且当来源是"外部系统"时必须穿透标注:**

```markdown
|**字段/区域**|**来源类型**|**具体来源**|**外部系统标识**|**交付状态**|**更新时机**|**缓存策略**|
| :-: | :-: | :- | :- | :-: | :- | :- |
|用户列表|后端接口实时获取|「用户列表查询」接口|本系统|✅ 已实现|每次进入页面|不缓存|
|用户昵称|本地缓存读取|LocalStorage `user_info`|本系统|✅ 已实现|登录时写入|会话期内有效|
|订单分析|外部系统接口|ORD-API-021 订单中心「订单总览」接口|🛰️ 订单中心 order-center|⏳ 未交付(预计 2026-XX-XX)|每次进入页面|不缓存|
|当前部门|跨模块调取|来自部门管理模块 store|本系统|✅ 已实现|页面初始化时|部门切换时更新|
|待办数量|前端计算|按列表数据计数(状态=待处理)|本系统|✅ 已实现|列表数据变更时|—|
```

**来源类型必选其一(7 类):**
1. **后端接口实时获取** — 本系统后端接口
2. **本地缓存读取** — LocalStorage / SessionStorage / IndexedDB
3. **跨模块调取** — 同系统其他模块的 store / context
4. **前端计算** — 纯前端基于已有数据计算
5. **静态配置** — 编译期常量 / 配置文件
6. **🛰️ 外部系统接口** — **来自本系统之外的其他系统/平台**(如订单中心 order-center、统一认证 SSO、支付宝、海关总署)
7. **🛰️ 外部系统消息推送** — 由外部系统主动推送(WebSocket / MQ / 回调)

> **「具体来源」列写法(Critical):** 写**接口的业务名称 / 数据出处**(如 `「订单总览」接口`、`LocalStorage user_info`、`来自部门管理模块 store`、`按列表数据计数(状态=待处理)`),外部接口再叠加其**编号/系统名**(如 `ORD-API-021 订单中心「订单总览」接口`)。**严禁写 HTTP Method+URL**(如 `GET /ord/orders/overview`)——接口契约由 dev-logic-architect 详细设计 B.2 定义,PRD 不出技术实现细节(见 [`flow-principles.md`](./flow-principles.md) 的「职责边界」节;`check_technical_content.py` R3 会拦截 PRD 中的 HTTP Method+URL)。

**🛰️ 外部系统数据强制标注规则(Critical):**

任何来源类型为 6 或 7 的字段,**必须**在表格中额外明确:
- **外部系统标识**: 写明来源系统的产品名/项目代号(如 `ORD-API-021 订单中心`、`SSO 统一认证`、`支付宝沙箱`),不允许仅写"第三方"
- **交付状态**: ✅ 已实现 / ⏳ 未交付(标预计日期) / 🔧 暂行方案(占位 mock)
- **接口契约负责人**: 由本系统对接 or 外部系统提供 — 在 PRD「七·4、第三方系统对接说明」章节登记完整契约

**触发"外部系统"判定的关键信号(Agent 主动识别):**
- 字段所属页面被产品文档标为"展示运营/监控/统计/对账"类
- 字段名含"用量""使用量""调用次数""配额""结算""计费""审计日志"等聚合统计语义
- 数据来自非本项目代码仓的接口(独立产品 / 跨业务线)
- 原型/设计稿来自其他产品基底(见下文「原型版本基底对齐」)
- 字段在本系统数据库 schema 中查不到对应表/字段(强信号:必查项)

**反向兜底(防漏判)**: 即使 PRD 编写者未明确告知,Agent 也必须基于上述信号**主动询问**用户:"字段 X 看起来像来自外部系统,请确认数据出处与交付状态。"用户确认后回填。**严禁**默认所有字段都来自本系统。

> **数据闭环双向核对(关联「数据闭环完整性原则」):** 本表覆盖**铁律 ②(有展必有源)**——每个展示字段都必须能在此表找到来源行。反方向的**铁律 ①(有增必有展)**——每条新增/录入/上报的数据都必须有展示或对外交付去向——在「五、页面交互明细」逐功规点核对:无对应展示且无对外交付的新增数据,标 `❓ 待澄清` 并以 `Q-FLOW-NNN` 登记 Module E。

### 六·3、原型版本基底对齐 (Prototype Base Version Alignment)

**Why:** 实测发现原型作者用更高版本(如 V0.8)作基底绘制,本次需求只交付 V0.7.1 子集时,原型里调用的接口可能在 V0.7.1 语境下**未交付/未实现/已被裁剪**。原型表面"已存在的能力"在当前版本可能是**虚假信号**。

**强制核验**: PRD 第二章「上游输入声明」必须新增以下两行,Agent 主动询问用户:

```markdown
- **原型基底版本**: 原型基于 V{原型基底版本}(如 V0.8)绘制
- **本次需求版本**: V{当前交付版本}(如 V0.7.1)
- **版本基底关系**:
  - ✅ 一致(原型基底 = 本次版本) → 无版本裁剪风险
  - ⚠️ 原型基底 > 本次版本 → **必须**生成「原型超前能力清单」(见下表),逐项判定是否纳入本次范围
  - ⚠️ 原型基底 < 本次版本 → 标注"本次版本新增功能,原型不覆盖,需补充设计稿/口头需求"
```

**原型超前能力清单(原型基底 > 本次版本时必填)**:

```markdown
| 原型功能区/页面 | 原型调用的接口 | 在本次版本是否就绪 | 在本次需求范围内 | 处理方案 |
| :- | :- | :-: | :-: | :- |
| 订单分析卡片 | ORD-API-021 订单中心「订单总览」接口 | ❌ 未交付 | ❌ 不在范围 | 裁剪本期不实现,标注 V0.8 再交付 |
| 政策补贴查询 | 「政策补贴查询」接口 | ✅ 已就绪 | ✅ 在范围 | 正常实现 |
| 现金管理 | 「现金余额查询」接口 | ✅ 已就绪 | ❌ 不在范围(V0.8 才上) | 裁剪原型该区域,不进入研发 PRD |
```

**Agent 主动询问触发场景:**
- 用户提供原型路径含版本号(`V0.8/code/`)且与当前需求版本号(`V0.7.1`)不一致
- 原型代码里出现 PRD 字段表中未提到的页面/区块
- 原型调用的接口数量明显多于 PRD 字段规格表覆盖的接口数量
- 用户口述"基于现有原型裁剪"但未明确说明裁剪清单

**严禁默认行为(对应"原型信源偏差"漏洞):**
- ❌ 默认"原型已有的功能 = 本次版本已交付的能力"
- ❌ 默认"原型调用的接口 = 当前后端已实现的接口"
- ❌ 默认"V0.7 已有能力 = 原型展示的所有能力"
- ✅ 必须用「原型超前能力清单」逐项核验,**未在清单中的功能不进入研发 PRD**

### 六·4、需求字段清单 (Requirement Field Inventory) — Critical 强制章节·下游字段对账单一信源

**Why:** 实测发现下游"字段对账"链路(详细设计比对 → 代码验收对账 → 自测逐列核对)缺一个**权威的需求字段基线**:研发常因"接口不支持/数据缺失"在落地时**静默删掉**原型可见的某些列/字段,产品验收时才发现列丢了却无从追责。本章节强制 PRD 在源头产出一份结构化「需求字段清单」,作为整条链路的**单一信源(single source of truth)**——下游 `dev-logic-architect`(比对)、`code-verification-loop`(对账)、`dev-manual-testcase`(逐列核对)均以研发需求文档提供的本清单为基准核验字段去向。

> **本清单是需求层产物,只登记业务语义名称,严禁代码级标识。** ux-logic-extractor 产出的是研发需求文档 PRD,属**需求层**而非原型/实现层。字段**逐项盘点原型 / 产品需求中用户可见的每个数据项**(采集来源是原型 + 产品需求,这是事实输入),但**登记时一律用业务语义名**(如"账期""应付金额""结算状态")。**严禁**填代码级标识:英文变量名 / 拼音 / 列表 `prop`/`dataIndex` / 表单 `v-model`/`name`/`id` / 数据库列名等一律不得出现 —— 这些归下游 dev-logic-architect。

**核心铁律(Critical):原型 / 产品需求中用户可见的每一列 / 每一个数据项,必须 100% 在本清单有显式去向登记,无遗漏、无静默丢弃。** 任何因"接口不支持 / 数据缺失"需裁剪的字段,**严禁静默删除**,必须进「表 B」登记裁剪原因并标"待产品确认"。

**强制产出范围:** PRD 中出现的**每个列表 / 表格 / 表单**各产出一张「表 A」(以页面 + 组件名命名,如 `表 A-1 用户列表`、`表 A-2 新增用户表单`);当存在字段裁剪 / 变更时,**强制**追加并保留「表 B」。

- **字段语义名称**: 用户可见的业务语义名(中文),如"账期""应付金额""结算状态"。**禁**填任何代码级标识(英文变量名 / 拼音 / `prop`/`dataIndex` / `v-model`/`name`/`id` / 数据库列名)。表单取 `label` 文案、列表取表头文案对应的业务语义。

- **是否筛选项**: 该字段是否对应页面上的筛选/搜索条件(是/否)。
- **业务含义**: 一句话说明该数据项的业务口径/说明 + 展示特征(颜色/默认排序/脱敏等),为下游理解保留语境。

#### 前置步骤·表 D「PRD 条目映射表」— PRD 原子条目反向覆盖(模式 B Critical 强制,与表 B/表 C 并列)

> **本表即维度 13 Critical 子项「产品 PRD 条目转写完整性」的落地载体** —— 治本地堵住「产品原始 PRD 里的功能条目/字段,在提取成研发 PRD 时被漏掉」这一源头缺口:下游测试期漏测的根因常是**产品 PRD 条目根本没被转写进研发需求**,导致一切以研发 PRD 为基准的下游检查同源污染、测不出漏项。故本表把「产品原始 PRD 原文 → 研发 PRD 去向」逐条对账定为 PRD 生成的强制动作。

> **条目对账基准输入(模式 B 必备):** **产品原始 PRD 原文**(示例路径 `docs/requirements/{version}/产品提供/*.md`,自适应项目实际结构)是表 D 的**条目完整性对账基准**——表 D 的每一条都必须能反查到产品原始 PRD 原文里的某个出处;反过来,产品原始 PRD 原文里的**每个功能条目/字段**都必须在表 D 有 1 条去向登记。**模式 A(纯逆向,无产品原始 PRD)本表标 N/A、跳过。**

**前置步骤「PRD 原子条目清单化」(模式 B 生成 PRD 正文前先做):** 把**产品原始 PRD 原文**拆成原子条目——**每个功能条目 = 1 条**,粒度为 **按钮 / 列 / 操作 / 规则 / 字段** 五类:既包括**表格里每张表的每一行**(每行 = 1 条),也包括**散文段落 / 无序列表里描述的功能条目**(如正文写"点击『导出』按钮下载 Excel"、"完成率低于 60% 标红"这类非表格的按钮/操作/规则,一样逐条拆出,禁止因"不在表里"而漏拆)。表格的「**备注 / 展示规则**」列、以及散文条目里附带的展示/校验规则,是该条目的**必带属性,严禁与字段名/操作名分离**(如"完成率"条目必须带"进度条按阈值分色"这一属性)。重点覆盖 4 类高危表 + 1 类高危散文:① **操作描述表 / 散文里的按钮·操作**(每个操作 1 条,如「导出」「批量删除」)② **列表字段说明表 / 散文里的列·字段**(每个字段 1 条 + 其备注属性)③ **展开明细表** ④ **遗留问题 / 迭代建议表** ⑤ **散文里的业务规则**(每条规则 1 条,如"仅管理员可见""金额超阈值需二次确认")。

### 七·4、第三方系统对接说明 (Third-Party Integration)

**当产品需求文档中涉及与第三方系统对接时,必须生成本章节,明确双方职责边界。** 不涉及第三方对接的 PRD 不生成本章节。

**七·4 的强制结构要求与 Critical 约束(必守,不可省略):**

- **(Critical)双清单缺一不可:** 除在五-N 各功规点描述具体对接细节外,**必须**独立汇总两个顶层子章节——「**七·4.2 本系统需要提供的能力清单**」与「**七·4.3 需要第三方提供的能力清单**」,以表格形式跨场景汇总所有能力,作为发送给第三方对接人的对接需求清单。严禁仅在功规点散点描述而无汇总。
- **(Critical)PRD 不出技术细节:** 本章节只描述**业务能力/业务需求**,**严禁**包含 HTTP Method、URL 路径、字段英文名(camelCase/snake_case)、字段类型、JSON/SQL 片段、错误码列表、技术栈选型、加密算法等(由 dev-logic-architect 详细设计阶段决定);描述统一用业务中文,必填性用"必填/选填"标注。
- **(Critical)失败/降级用业务表现描述:** 如"订单保留待支付状态,1 小时后自动取消",而非"返回 503,等待重试"。
- **(Critical)不设计第三方内部实现:** 我方只描述需求清单,接口路径/字段结构由第三方决定。
- **(Critical)双向追溯:** 七·4.4 场景中提到的能力/需求必须在 七·4.2 或 七·4.3 中存在;反之 七·4.2 / 七·4.3 中的每个能力/需求必须能追溯到至少一个 七·4.4 场景。
- **能力/需求编号全局唯一:** `CAP-OUT-NNN`(对外开放)/ `CAP-IN-NNN`(主动调用第三方)/ `REQ-3P-NNN`(第三方开放接口需求)/ `REQ-3P-CB-NNN`(第三方回调需求),三位数字,PRD 中不重复。
- 对接方向必须标注:我方调用第三方 / 第三方调用我方 / 双向调用;模式 B 时每个对接场景必须标注产品需求文档来源章节。

**七·4 子章节结构(标题文字须照此生成,缺一不可):**

- **七·4.1 对接总览** — 列出所有第三方系统及对接场景、方向、文档来源。

### 八、异常路径处理 (Error Handling)

**按控件类型的通用校验规则：**

```markdown
|**控件类型**|**校验规则**|
| :- | :- |

|SELECT 选择类|<p>1、 必选校验：未选择时提示"请选择[字段名]"</p>|
|上传类|<p>1、 文件大小限制：超出时提示"文件大小不能超过xxMB"</p><p>2、 文件格式限制：不符合时提示"仅支持xx格式"</p>|
```

**接口异常处理：**

> ⚠️ **异常场景一律用业务语言描述,严禁写 HTTP 状态码数字(401/403/404/500 等)** —— 否则触发职责边界维度 10 / `check_technical_content.py` R5(与 S5 上游净化规则一致:`资源不存在`、`登录失效` 而非 `404`/`401`)。

```markdown
|**异常场景**|**处理方式**|**用户提示**|
| :-: | :-: | :-: |
|登录失效 / 未授权|跳转登录页|"登录已过期，请重新登录"|
|无操作权限|停留当前页|"您没有权限执行此操作"|
|资源不存在|展示空状态|"数据不存在或已被删除"|
|服务异常|展示错误提示|"系统繁忙，请稍后再试"|
|网络断开|展示断网提示|"网络连接异常，请检查网络"|
```
