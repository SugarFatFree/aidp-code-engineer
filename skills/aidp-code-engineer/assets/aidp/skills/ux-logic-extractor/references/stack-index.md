# 技术栈内容说明 —— **本 SKILL 刻意不拆分**（反例记录）

> 本仓库其余 5 个 dev-workflow SKILL 都把「语言/框架专有内容」拆成 `stack-*.md` 供按需加载（见各自 `references/stack-index.md`）。**ux-logic-extractor 是唯一的例外，且是刻意为之**——本文件记录原因，防止后来者把它当成"漏拆"而去补拆，那会直接削弱本 SKILL 的核心能力。

## 为什么不拆

本 SKILL 里出现的技术栈词汇（Vue / React / Spring Boot / MyBatis Plus / Element Plus / UnoCSS / MySQL / 达梦 / Redis / Nacos …）**不是"落地细则"，而是"识别词典"**——它们的用途是**认出并剥离**技术实现痕迹，产出纯业务语义的研发 PRD：

| 出现位置 | 用途 |
| :- | :- |
| 「S1 技术栈词典」 | 命中即判定为技术实现词汇，**从需求描述中剔除**（PRD 只写业务语义，不写技术选型） |
| 「代码示例一律丢弃」规则 | 识别 Java/TS/Python 等代码片段并整段丢弃 |
| 前端框架特征识别（`v-model`/`v-if`、`useState`、`el-`、`a-` 前缀等） | 从原型 HTML 中反推交互语义，**同时把框架痕迹本身剥掉** |

**关键点：本 SKILL 运行时并不知道、也不应该知道项目最终用什么技术栈**——

1. 它的输入是**产品需求文档 + HTML 原型**，技术选型是**下游 `dev-logic-architect` 才做的事**（Step 3 才让用户选）；
2. 原型可能是任意工具产出的（Antd 风、Element 风、纯 HTML、AI 生成），**词典必须全量持有才认得全**；
3. 按语言拆开后，Agent 需要"先探测栈才加载词典"——可它正是靠词典去识别栈的，**逻辑上循环依赖，必然漏识别**：加载了 Vue 词典就认不出 React 痕迹，漏剥的技术词会直接污染产出的 PRD。

## 同类例外

`dev-logic-architect` SKILL 里的**技术选型表**（该 SKILL 自己的 `references/` 下，**不在本 SKILL 目录内、也不要去本目录找**）出于相同性质也不拆——它用于**选型期**，那时用户尚未选定技术栈，正是要看到全部候选才能选。

> **共同判据**：内容用于「**在未知技术栈的前提下做识别或选择**」→ **必须全量加载，不拆**；内容用于「**技术栈已确定后照着落地/审计**」→ **按栈拆分、按需加载**。

## 本 SKILL 技术栈内容的实际体量

SKILL.md 与其 `flow-*.md` 分片合计约 2200 行中，技术栈关键词命中仅约 30 行（≈1%），且高度分散在识别规则里，即便忽略上述循环依赖问题、强行拆分，收益也接近于零。
