# 06 — 版本与用户目录约定

> 本文件是 AIDP 范式中所有"版本 + git 用户"目录约定的**单一权威来源**。
> 00/02/03/05 等范式文档、`{{AIDP_HOME}}/commands/` 下所有命令、`{{AIDP_HOME}}/agents/` 下所有 Agent 指令，
> 在提到路径时都必须遵循本文件的规则。`{{AIDP_HOME}}` 是下游运行目录（仅 Claude Code 为 `.claude`，有 Codex / DSH 为 `.agents`；十个契约目录平铺其下）；模板 `.aidp/` 只作维护源。`{git-user}` 是兼容历史的路径槽名，无 Git 时由显式 `--user` 提供开发者标识，脚手架不会自动 `git init`；无 Git 仍可规划/开发/本地测试/归档，正式发布必须 fail closed，不得宣布已发布。

---

## 1. 为什么要按版本 + git 用户组织

| 场景 | 旧约定的问题 | 新约定如何解决 |
|------|---------------|-----------------|
| 一个项目同时开发多个版本（如 V0.1.0 主线 + V0.1.1 热修）| sprint 目录全部堆在 `docs/requirements/` 下，无法区分属于哪个版本 | 每个版本有独立的一级目录 `{category}/{version}/` |
| 同一版本内多人并行（alice / bob 同时开 sprint-003）| 不同人的需求文档、设计文档、bugfix 记录会互相覆盖 | 版本目录下再按 `{git-user}/` 隔离，各自写各自的目录 |
| 需要归档一个版本的所有产出 | 需要扫描多个目录收集 | 一个版本的所有产出集中在 `{category}/{version}/` 子树下 |
| memory 切回旧版本继续维护 | activeContext 只有一份，切换版本会丢状态 | 迭代级 memory 按 `{version}/{git-user}/` 隔离，彼此独立 |

## 2. 目录层级规则总览

按**隔离级别**把所有产出分成 4 类：

> **★ README 放置规则**（防 README 泛滥，判定唯一实现 = `readme_policy.py::is_readme_required_directory`，三档）：**① 代码单元 README** 只覆盖正式源码根、前后端子项目根、正式多模块的模块根，或 `memory/.aidp-state.json` 的 `README_REQUIRED` 显式声明目录；源码单元内部目录不生成。**② 导航 README** 覆盖源码树之外、目录结构本身需要导航的枢纽目录——判据是「直接子目录数 ≥ 2，或 1 个非空子目录」，只看子目录结构、不按目录名猜测；内容只列子目录清单与用途，不写技术栈与启动命令。**③ 其余不生成**：源码树之外且无多级子目录的平铺目录（如 `docs/deployment/tools/<上游系统>/`），文件再多也不构成导航需求。依赖树与构建产物目录（`node_modules`/`dist`/`build`/`target`/`vendor` 等）、备份归档与隐藏目录一律不计子目录数、不参与判定。`docs/{分类}/README.md` 与版本枢纽目录 README 同受该判定门控，脚手架资产只决定用什么内容渲染、不决定该不该铺。已有范围外 README 只诊断并保留（`README_OUT_OF_SCOPE` + `preserve-and-report`），扫描排除上列目录且不报未被 git 跟踪的文件。

### 2.1 项目级（全局单一真源，不隔离）

| `memory/projectBrief.md` | L1 项目简介 |

**约束**：这些路径**不允许**出现版本号或 git 用户目录。ADR 和数据库基线必须只有一份权威来源。

#### 2.1.1 `docs/architecture/` 目录结构（架构相关文档，兼容识别）

`docs/architecture/` 是**项目级**架构文档目录（全局、无版本前缀），存放两类文档，读取时**全目录识别**（不只认约束三件套）：

| 类别 | 文件/子目录 | 说明 |
|------|------------|------|
| **① 架构约束类** | `架构约束.md` / `技术选型.md` / `UI规范约束.md` | 全局约束三件套（动态填充；`/sprint-design` Step 4 维护）|
| **② 架构设计类**（可选）| 单文档 `架构设计.md` **或** 多文档子文件夹 `架构设计/` | 项目级整体架构设计（区别于版本级 `docs/design/detail/{version}/01_详细设计.md`）|

- **架构设计两形态（兼容识别）**：
  - **单文档**：`docs/architecture/架构设计.md`
  - **多文档**：`docs/architecture/架构设计/` 子文件夹，内含 `00_索引.md` + `NN_*.md`（遵循约定 15 同类多文件编号）
  - **存量兼容**：历史项目中 `docs/architecture/` 下任意命名的架构设计文档（单文件或子文件夹）**也识别**，不强制改名——新建走规范名 `架构设计`，存量按现状读取。
- **读取规则**：任何读 `docs/architecture/` 的环节（`/sprint-design`、`/sprint-dev`、Architect / Reviewer Agent）都**全目录扫描**——约束三件套 + 架构设计（单/多/存量）一并纳入，架构设计文档作为详细设计的上游输入。
- **★ 仅有架构设计、缺架构约束时的派生**：若 `docs/architecture/` 下**只有架构设计文档、架构约束（`架构约束.md`）缺失或为空模板** → Architect 在 `/sprint-design`（Step 4.2）**据架构设计派生一份 `架构约束.md`**（从架构设计中提取分层规则、技术选型、命名规范、安全策略、性能要求等约束条目），使全局约束基线不缺失；随后再叠加本次详细设计提取的增量约束。技术选型 / UI 规范约束同理可据架构设计补足。
- **约束**：架构设计类为**可选**（无则跳过，不强制创建、不因缺失报错）；约束三件套仍是初始化基线（scaffold 铺空模板）。

#### 2.2.1 plans 文件命名约定

```
docs/plans/{version}/
├── 00_索引.md                   # 专职索引（必需）：文件清单 + 生成时间 + 主/补充标识
├── 01_研发执行计划.md              # 内容主文档（必需）：总任务清单 + 分配人员 + 依赖关系
```

### 2.5 代码目录 `code/` 组织规则 ★ 统一为 frontend/+backend/（含 upgrade 豁免规则）

**统一标准（新建/空 code/ 项目）**：`code/` 下源代码强制按"前/后端"二分，无论单项目还是多项目都套 `frontend/` 和 `backend/` 父目录。

**Upgrade 豁免**：旧版 AIDP 升级、或 code/ 下已有任何代码子目录的项目（如 `code/web/`、`code/server/`、`code/foo-server/`、`code/foo-web/`、`code/legacy-platform-server/` 等历史命名）→ **保留代码原位置不动**，scaffold/migrate/verify **不会**主动创建 `code/frontend/`+`code/backend/` 空目录或 README 指针；改由用户**在 `memory/techContext.md`「项目代码结构」段 + 各文档引用处指向实际路径**（让文档跟随代码，而不是用空目录掩盖真实代码位置）。

```
code/
├── sql/                          # SQL 暂存位（上游 SKILL 落此，命令端当轮搬迁走，不留产物；见 §2.5.4 / §8.7）
├── frontend/                     # 前端代码父目录（必含）
│   └── {项目名}/                 # 单前端时只有一个子目录；多前端并列多个
└── backend/                      # 后端代码父目录（必含）
    └── {项目名}/                 # 单后端时只有一个子目录；多后端并列多个
```

#### 2.5.1 单前端 + 单后端（最常见）

```
code/
├── sql/                          # 暂存位（不留产物，见 §8.7）
├── frontend/
│   └── web/                      # 单前端项目；名字由脚手架/项目命名
└── backend/
    └── server/                   # 单后端项目；名字由脚手架/项目命名
```

- 子项目名必须只含 `[a-zA-Z0-9_-]`
- 不再支持"扁平 `code/web/` + `code/server/`"形式（仅 upgrade 模式遗留兼容）

#### 2.5.2 多前端 或 多后端

```
code/
├── sql/                          # 暂存位（不留产物，见 §8.7）
├── frontend/
│   ├── web-admin/                # 管理后台
│   └── web-portal/               # 用户门户
└── backend/
    ├── gateway/                  # 网关
    ├── auth-service/             # 认证服务
    └── biz-service/              # 业务服务
```

某一侧单项目、另一侧多项目时**仍各自套 `frontend/` / `backend/`**，不再"按需省略"。

#### 2.5.3 模式切换（旧扁平结构 → 新统一结构）

扁平形态（`code/web/` + `code/server/`，不含 `{子项目}` 中间层）切换到统一结构：

```bash

# 仅当用户主动决定迁移时，执行：
mkdir -p code/frontend code/backend
git mv code/web code/frontend/web        # 单前端：搬入 frontend/ 下
git mv code/server code/backend/server   # 单后端：搬入 backend/ 下
# 同步更新 memory/techContext.md "项目代码结构" + 构建脚本/CI 中所有路径
```

**migrate 模式（非 AIDP 现存项目）**：scaffold 检查 code/ 下是否已有代码子目录：
- code/ 为空 / 仅含 sql/ → 创建 `code/frontend/` + `code/backend/` 空骨架
- code/ 已有自定义代码子目录 → **不创建**新规范空目录，保留原结构；用户在 `memory/techContext.md` 和文档引用处指向实际路径

**init 模式（新建项目）**：scaffold 强制创建 `code/frontend/` + `code/backend/`（含 `.gitkeep` 占位）。

**upgrade 模式（旧版 AIDP 升级）**：同 migrate — code/ 已有代码子目录则保留不动，文档跟随代码。

```
├── README.md      # 索引：分类 + 用途说明（登记 分类/文件/用途/归属应用/日期）

├── <上游系统>/     # 操作【第三方 / 上游系统】的脚本（如订单中心 order-center 的字典导出导入）
└── 其他/           # 【跨系统】（多方联动）的迁移方案整目录
```

- **分类原则**：操作本应用自有库 → `本应用/`；操作第三方 / 上游系统（如订单中心）→ `<上游系统>/`（按系统名命名，如 `order-center/`）；跨多系统联动 → `其他/`。子目录名**可按项目实际应用命名**，`本应用 / <上游系统> / 其他` 为通用三分基线。
- **文件命名**：SQL / 文档文件名**尽量用中文**（描述用途）+ **保留日期前缀**便于时序排序（如 `20260715_字典表历史数据修复.sql`）；**可运行工具**（含被 README 交叉引用的 `.py`/`.sql`）**内部文件名保持稳定**、仅外层目录中文化（避免引用断链）；**不纳入构建产物**（`__pycache__` 等）。
- **范式层职责（轻量）**：只做「识别 + 规范位置 + README 索引」，**不为其生成 / 校验具体 SQL 内容**（脚本多为一次性、带环境上下文）。`verify.py::check_deployment_tools` 仅在目录存在时轻量识别（不误判）、`README.md` 缺失时 INFO 提示。
- **发布期整理**：`/version` 发布时纳入整理范围（`docs/deployment/tools/README.md` 索引对齐刷新 + 清理 `__pycache__` 等构建产物），详见 `/version` Step 3.3.7.8（**跨版本、独立于 `{version}/` 是否存在**）。
- **脚手架下发**：init / migrate / upgrade 三模式交付 `docs/deployment/tools/` 骨架 + `README.md` 索引模板；**README 属用户内容、create-if-missing 不覆盖**（区别于结构性 `docs/deployment/README.md` 的 upgrade 刷新）。

### 2.6 `docs/references/` 版本化与生命周期 ★

`docs/references/` 同时承载**跨版本通用资料**与**版本专属对外需求**，两者按目录层级分流：

| 子路径 | 内容 | 层级 |
|------|------|------|
| `docs/references/`（根） | 第三方平台**跨版本通用**的全接口文档 / 能力清单 / 长期参考（OCR、TTS、IAT 等对方已有能力的资料）| 项目级（不隔离）|
| `docs/references/{version}/` | 本版本「**提给第三方的需求**」（对外协作业务诉求文档）+ 本版本相关的对方资料 | 版本级（按版本隔离）|

**生命周期（三阶段）**：
1. **版本规划期**（`/version` 规划流程）：① 确保 `docs/references/{version}/` 存在；②「提给第三方的需求」由 `/sprint-design` 落盘到此（与内部详设 `docs/design/detail/{version}/集成对接.md` 分离——前者=对外业务诉求、后者=我方内部对接设计）；③ ★ **引用链强制**：本目录规划期生成的文件**必须**被研发需求（`00_索引.md`+`01_研发需求.md`；历史裸 `00_研发需求.md` 兼容）+ 详细设计（`00_索引.md`+`01_详细设计.md`；历史裸名 `详细设计.md` 兼容）在「关联文档」中引用（缺失即 `version-auditor` E 引用链审计告警，与研发需求↔详设引用密度铁律同级）。
2. **开发期**（`/sprint-dev` / `/sprint-design` 读取）：消费端读「对方接口资料」时同时覆盖 `docs/references/{version}/`（版本专属）+ `docs/references/` 根（通用）。
3. **版本发布期**（`/version` 发布流程，情况 B-3）：① 确保 `{version}/` 存在；② 维护 `docs/references/README.md` 索引（「通用区」+「各版本区」）；③ ★ **复核 `{version}/` 提给第三方的需求**：对已满足（第三方已交付 / 已切真实对接，结合约定 26 Mock 清理状态判定）的需求，在文档内**追加"✅ 已满足"说明**（含满足方式 + 日期）；不确定的提示用户确认；④ 根目录散落的版本专属文件**仅提示**用户归位，不自动移动（范式无法可靠判定版本归属）。

## 3. 命名规范

### 3.1 版本号 `{version}`

- 格式：`V{major}.{minor}.{patch}`，例：`V0.0.1`、`V0.4.0`
- **必须以大写 V 开头**，与 tag 保持一致
- 可选子版本后缀：`V0.4.0_0424`、`V0.4.0_0427`（用于同一版本内多轮设计/发布）
- 正则参考：`^V\d+\.\d+\.\d+(_[a-zA-Z0-9]+)?$`

### 3.2 git 用户 `{git-user}`

- 来源：`git config user.name`
- **必须只包含** `[a-zA-Z0-9_-]`；有空格、中文或其他字符时，要求用户显式设定一个符合规则的短标识
- 示例：`alice`、`bob-01`

### 3.3 Sprint 编号 `{NNN}`

- 三位数字，从 001 起，例：`sprint-001`、`sprint-042`
- 模块化命名：允许加模块前缀，如 `sprint-web003`、`sprint-mobile002`
- **★ 跨版本连续自增、不随版本重置（项目全局流水号）**：Sprint 编号在**整个项目生命周期内唯一且单调递增**，
  `V0.1.0` 用到 `sprint-003`，则 `V0.2.0` 的第一个 Sprint 是 **`sprint-004`**，**不是** `sprint-001`。
  - **Why**：编号是 Sprint 的**唯一标识**——bugfix 记录的「Sprint」列、`docs/testing/{version}/sprint-{NNN}/`、
    研发执行计划与 Sprint 归档都靠它定位。一旦每个版本都从 001 重来，同一项目里就有
    多个 `sprint-001`，跨版本回溯时**只凭编号无法定位**，必须再带版本号才能消歧（而多数引用处并不带）。
  - **取号唯一方式**：`python3 {{AIDP_HOME}}/scripts/check_sprint_numbering.py next`（**跨全部版本**扫
    `memory/*/*/sprints/` + `docs/plans/*/…研发执行计划.md` 取 MAX+1）。
    ⛔ **严禁**自己 glob `memory/{version}/{user}/sprints/` 取 MAX——那个路径带 `{version}` 限定，
    新版本目录天然为空、必然算出 001（下游实测过的真实缺陷）。
  - **断号允许**：Sprint 被取消/合并导致编号不连续属正常，检查器只提示不拦截；**重复才是错**。

### 3.4 Sprint 划分粒度（★ 一个 Sprint = 一个可独立验收的功能单元）

- **同一功能的前后端任务必须归属【同一个】Sprint**，作为该 Sprint 下的不同 **Task**；
  **严禁**把一个功能的前端、后端拆成两个 Sprint。
- **Why**：Sprint 是**验收单位**而非任务批次。前后端分属两个 Sprint 时，任一 Sprint 都无法独立验收——
  「前端 Sprint」没有接口可联调、「后端 Sprint」没有页面可验证，`/sprint-test` 的验收循环与
  `/sprint-close` 的归档都失去意义，Sprint 退化成"任务批次"。（下游实测问题）
- **对应关系**：上游 `dev-execution-planner` 按「**EPIC × Sprint × Task**」三层模型产出（Sprint = 时间盒，一个 Sprint 可含多个 EPIC、一个 EPIC 也可跨 Sprint；单一信源 = 其 `references/flow-execution.md`），
  Sprint 由命令端映射——**一个 Sprint 承载一个或多个 EPIC 的完整交付**，EPIC 内的前端/后端/测试三类 Task
  （由该 SKILL 的 `check_task_granularity.py` 维度 14a **提示**——severity=1 警告档，需人工复核，⛔ 不是硬门）一并落入同一 Sprint。
- **落点**：`docs/plans/{version}/01_研发执行计划.md`「任务分配矩阵」——表头
  `| 功能模块 | 后端任务 | 前端任务 | 负责人 | Sprint | … |` 即已表达该语义：
  **一行 = 一个功能模块 = 一个 Sprint，前后端是同一行的两列**。
- **唯一豁免**：确属纯前端 / 纯后端的需求（如"登录页样式改版"），在该行显式标注
  **「单端 / 仅前端 / 仅后端 / 纯前端 / 纯后端」**（与上游 `check_task_granularity.py` 同款标记词）。
- **回检**：`python3 {{AIDP_HOME}}/scripts/check_sprint_numbering.py check`
  （B1 同一功能模块跨 Sprint = Critical；B2 单端 Sprint 无豁免标记 = Important）。

## 4. 路径解析算法（所有命令和 Agent 必须统一遵循）

每个涉及"版本/用户"路径的命令，执行前必须走以下流程：

### 4.1 确定 `{version}`（流程 A）

```
1. 如果命令参数中显式指定了版本号 → 使用该值
2. 否则读项目记忆文件（AGENTS.md / CLAUDE.md）「当前状态」的"当前版本"字段（★ 优先级高于 memory，
   与会话启动流程一致：先项目记忆文件定版本，再据版本去读对应 memory）
3. 项目记忆文件读不到时，再回落读 memory/{任一已存在版本}/{任一用户}/activeContext.md 的"当前版本"字段
4. 仍读不到 → 询问用户：
   "请问本次操作对应哪个版本号？(格式 V{major}.{minor}.{patch}，例 V0.1.0)"
5. 获取版本号后校验格式（见 3.1）
6. 不符合规则 → 重新询问，并给出规则说明
```

### 4.2 确定 `{git-user}`（流程 B）

```
1. 执行 `git config user.name` 获取 git 用户名
2. 校验是否只含 [a-zA-Z0-9_-]
3. 如果包含非法字符或为空 → 询问用户：
   "git user.name 不符合目录命名规则（只允许字母数字 _ -）。
    请提供一个用于目录名的短标识（如 alice）"
4. 获取合法的 git-user 短标识
```

### 4.3 路径变量展开（流程 C）

获取到 `{version}`、`{git-user}` 后，按第 2 节的模板拼出完整路径。
如果目标目录不存在，**先创建再写入**。

### 4.4 一致性回写（流程 D）

把当前使用的 `{version}` 和 `{git-user}` 回写到：
- `memory/{version}/{git-user}/activeContext.md` 的头部"当前版本 / 当前开发者"
- `AGENTS.md` 的"当前状态"区域

保证下次启动会话时 流程 A 能直接读出来，不用再问。

### 4.5 文档内引用路径的写法（★ 全仓单一信源，各命令/Agent/flow 一律指此，不复述）

- **版本作用域内**（`docs/{requirements,design,plans,prototype,testing,...}/{version}/...`）
  → 用**文件相对路径**（同一版本目录里的兄弟文档互指，版本号变了不用逐处改）。
- **全局锚点**（`memory/`、`docs/architecture/`、根级 `code/` / `env/`、
  项目级 `docs/requirements/PRD-*.md`）→ 用**仓库根相对路径**。

> ⚠️ **本条曾在三处各写一份**（`sprint-plan.md` / `sprint-design` 与 `sprint-requirements` 的
> flow 分片），其中一份的「全局锚点」清单已经和另两份分叉——多出 `项目级 docs/requirements/PRD-*.md`
> 一项。这正是双写的典型下场：三份看起来都对，读到哪份取决于走的是哪条命令。
> 现收口于此，其余各处只留指针。

### 8.7 SQL 目录 `code/sql/{version}/` → `docs/deployment/{version}/sql/增量/` 迁移 ★

SQL 已从 `code/sql/{version}/` 迁到部署资产目录 `docs/deployment/{version}/sql/增量/`（版本层在 `sql/` 之上）。**存量项目（`code/sql/{version}/` 或上游 SKILL 原生的 `code/sql/v{version}/` 已有 SQL）的搬迁**：

- **脚手架不自动搬动 SQL**：`aidp-code-engineer` 的 `migrate` / `upgrade` 只做体检与指引，存量 `.sql` 由 Agent 或人按下方步骤 `git mv` 到 `docs/deployment/{version}/sql/增量/`（保序号/文件名不变，逐版本搬），并同步刷新引用了旧路径的设计文档。
- **读取端 grandfather 兼容**：约定 6 开发期 SQL 自动应用、baseline 回写、`{prev-version}` 风格扫描等读取端**同时识别** `code/sql/{version}/`（旧/未搬迁）与 `docs/deployment/{version}/sql/增量/`（新），避免搬迁前后断档。
- **手工搬迁步骤**：
  ```bash
  # ⚠️ glob 必须 [Vv] 都收：上游 SKILL 原生输出的是**小写** `code/sql/v{版本}/`
  for d in code/sql/[Vv]*/; do
    ver="V$(basename "$d" | cut -c2-)"      # 归一大小写：v0.2.0 → V0.2.0
    mkdir -p "docs/deployment/$ver/sql/增量"
    git mv "$d"*.sql "docs/deployment/$ver/sql/增量/" 2>/dev/null
    rmdir "$d" 2>/dev/null || true
  done
  ```
- **新生成不再落 `code/sql/`**：`/sprint-design` Step 3.2 起，SKILL 暂存的 `code/sql/{version}/` 会被命令端当轮 `git mv` 到 `docs/deployment/{version}/sql/增量/`，暂存位不留产物。

## 10. 跨版本增量约定

### 10.1 设计文档增量规则（`docs/design/detail/{version}/`）

`/sprint-design` 命令在生成新版本设计时，必须先定位**前一版本 `{prev-version}`**，并以增量方式产出本版本的设计：

#### 10.1.1 前一版本定位规则

```
1. 扫描 docs/design/detail/ 下所有版本目录
2. 过滤掉 {version} 自身
3. 按版本号语义排序（V0.1.0 < V0.1.1 < V0.2.0 < V1.0.0）
4. 取版本号 < {version} 的最大版本作为 {prev-version}
5. 该目录须有详细设计专题主文档（★ **三态 glob 探测、不硬编码裸名**：`ls {prev}/{00_索引,00_详细设计,01_详细设计,详细设计}.md 2>/dev/null` 任一命中即视为存在——拆分态 `00_索引.md`/`01_详细设计.md` / 单份态 `00_详细设计.md` / 历史存量裸名 `详细设计.md`），否则视为不存在前一版本
6. 若无前一版本 → 视为首版，按完整设计模式产出
```

#### 10.1.2 设计文档头部要求

本版本的详细设计主文档（拆分态 `01_详细设计.md`〔新生成〕 / 历史单份态 `00_详细设计.md` / 历史存量裸名 `详细设计.md`，按约定 15 实际命名；新生成一律拆分态 `00_索引.md`+`01_`，后两者仅存量 grandfather）必须在文首加入「基线引用」章节：

```markdown
## 基线引用

本版本相对前一版本 **{prev-version}** 增量设计。

- 前一版本设计基线：[前一版本设计目录](../{prev-version}/)（★ 链接指向前版实际主文档，按其命名三态取值：拆分态 `01_详细设计.md`/`02_数据库设计.md`/`03_接口设计.md` / 单份态 `00_<专题>.md` / 历史存量裸名 `详细设计.md` 等——不写死裸名，避免拆分态前版断链）
- 本版本变更清单：见下方第 1 节「变更范围概述」
- 未列出的模块/接口/表，视为完全复用前一版本的设计，不重复定义
```

#### 10.1.3 设计文档目录下全部分册的增量原则

| 文档 | 完整内容 | 增量内容 | 复用方式 |
|------|---------|---------|---------|
| `详细设计.md` | 首版必填全部章节 | 只描述变更模块的设计 | 不变模块：「沿用 {prev-version}」+ 锚点链接 |
| `接口设计.md` | 首版列出所有接口 | 只列出新增/变更/废弃的接口 | 不变接口：「沿用 {prev-version}」+ 锚点链接 |
| `数据库设计.md` | 首版列出所有表 | 只列出新增/变更/废弃的表 | 不变表：在表清单中标注「复用，参考 {prev-version}」 |

### 10.2 SQL 文件增量规则（`docs/deployment/{version}/sql/增量/`）

跟随 `dev-logic-architect` SKILL「Module D 版本归档完整性」的**增量原则**（以 SKILL.md 为准）——每个版本的 SQL 目录**仅包含本版本新增/修改的内容**，不累积历史。跨版本继承通过"目录隔离 + 序号续编"实现：

```
1. 如存在 {prev-version}：
   - 选项 A（推荐，与 SKILL 增量原则一致）：本版本目录 docs/deployment/{version}/sql/增量/ 只放本版本新增/变更的 SQL；
     新部署时按 prev-version → version 的目录序执行（旧版数据库已有 prev-version 的表 → 仅跑增量；新环境 → 历史 + 当前都跑）
   - 选项 B（兼容历史，可选）：把 prev-version 目录整体复制到 version/ 作继承基线，再追加本版本新增（序号续编）；
     适合单文件还原优先的项目，但代价是 git diff 噪声大
2. 如不存在 {prev-version}（首版）：
   直接从 数据库设计.md 输出本版本完整 DDL，按"中文名 + 两位数字序号前缀"规范拆成多个 SQL 文件
```

**文件命名（与 §2.5.4 一致）**：`{NN}_<中文名>.sql`（两位数字序号前缀按执行顺序自增；DDL/DML 同一序号空间混排；`99_回滚脚本.sql` 序号固定保留）。

**幂等性**：所有 CREATE/ALTER 必含 `IF NOT EXISTS` / `IF EXISTS` 判断（SKILL「Module D 版本归档完整性」强制核验）。

**示例（选项 A）**：
```
docs/deployment/V0.1.0/sql/增量/
├── 01_用户表DDL.sql
├── 02_订单表DDL.sql
├── 03_订单状态字典初始化.sql
└── 99_回滚脚本.sql
docs/deployment/V0.2.0/sql/增量/
├── 01_权限表DDL.sql              # 本版本新增，序号在本目录内重新从 01 开始
├── 02_订单表新增字段.sql
└── 99_回滚脚本.sql
```
